### 1. 業務担当者（工場現場 / 事務所 / 倉庫）

**基本情報**

| 項目 | 内容 |
|------|------|
| 名前例 | 田中 博（架空） |
| 所属 | 第一製造部 生産管理課、工場フロア勤務 |
| 経験年数 | 現場業務 8 年、IT スキルは基本操作のみ |
| 場所 | 工場内検査ライン / 倉庫 / 事務所 |

**使用端末・環境**

- iPad / Windows tablet（現場）
- Companion アプリ（オフライン透過）
- WinForms 業務画面（レガシー端末）
- React SPA（事務所 PC）

**1 日の流れ**

| 時間帯 | 業務 |
|--------|------|
| 朝 | ライン稼働確認・生産指示確認（live tile） |
| 昼 | 検査結果入力（オフライン環境含む）・在庫確認 |
| 夕方 / 夜 | 警報対応・発注承認（WebAuthn step_up）・日報送信 |

**現状業務での痛み（k1s0 なし世界）**

- 通信断時にタブレットへ入力したデータが消失し、再入力コストが毎回発生する
- 並行編集による業務エラー（競合）が発生しても対処方法が不明で上長エスカレーション頼り
- 紙 + ERP の二重入力が常態化しており、転記ミスが品質問題に直結する
- レガシー端末上の非直感的 UX で操作ミスが多発し、検査結果の修正票が発生する
- 警報通知の見逃しが発生し、ライン停止の初動対応が遅れる

**k1s0 でこう変わる**

- 25h オフライン透過（4 layer state + IndexedDB encrypted）でデータ消失がゼロになる
- BusinessConflict 4 種の標準 UI（stale_write / lost_update / supersede / concurrent_edit）で即座に自己解決できる
- Companion 統合で紙・ERP・タブレットが一元化され、転記ミスが構造的に排除される
- WebAuthn step_up による業務承認がスムーズになり、操作ミスも 13 層強制機構で防止される
- 警報配信（v1_alert）の低遅延配信で警報見逃しゼロを達成できる

**個人 KPI / 達成感**

- オフライン起因の再入力件数：月 0 件
- BusinessConflict エスカレーション件数：月 0 件
- 警報初動対応時間：< 2 分
- 転記ミス起因の修正票：月 0 件

**主に踏むシナリオ**

- [07_業務担当者シナリオ](07_業務担当者シナリオ/README.md)

**08_開発体制との整合**

業務担当者はエンジニアではなくエンドユーザー。プログラミング不要の設計を tier3 担当者が担保し、tier2 担当者が業務不変条件を構造で保護する。人数はテナント規模・業務領域に比例して増減する。

- 緊急対応 step_up フロー（v1_emergency_step_up）が標準化され、手順書参照が不要になる
- partner federation 設定を管理 UI で自己完結でき、システム管理者依存がなくなる
- 規制証跡を自動エクスポートできるため、監査前準備コストがほぼゼロになる

- マスタ変更リードタイム：即時（< 5 分）
- 監査証跡収集所要時間：< 10 分
- 規制証跡準備の突貫作業件数：年 0 件
- partner 連携設定の自己完結率：100%

**主に踏むシナリオ**

**基本情報**

| 項目 | 内容 |

| 所属 | ○○監査法人 IT 監査部門 |
| 経験年数 | 公認会計士 15 年、IT 監査専門 7 年 |
| 場所 | 年次 1-2 回の訪問監査（リモート参加含む） |

**使用端末・環境**

- 監査法人支給 PC（セキュアブラウザ）
- Sigstore Rekor 独立検証ツール
- cosign CLI
- 読み取り専用 audit trail 閲覧 UI

**1 日の流れ（監査実施日）**

| 時間帯 | 業務 |
|--------|------|
| 朝 | audit trail の完全性確認・RFC 3161 タイムスタンプ検証 |
| 昼 | SLSA L3+ provenance の cosign verify・KEK ceremony 記録確認 |
| 夕方 / 夜 | chain-of-custody 形式の証拠保全・監査レポート草稿 |

**現状業務での痛み（k1s0 なし世界）**

- 証拠の真正性を被監査組織の提出書類に依存しており独立検証ができない
- audit trail の改竄可否が不明なため監査意見の根拠が脆弱になる
- build artifact の出所検証に専用ツールがなく属人的な手順が必要になる
- KEK ceremony を書類のみで確認するため実施事実の保証が困難になる
- 監査レポートの証拠保全が非形式的でチェーン・オブ・カストディが担保されない

**k1s0 でこう変わる**

- Sigstore Rekor / RFC 3161 タイムスタンプで被監査組織に依存せず独立検証できる
- WORM Object Lock（S3 互換）で audit trail の改竄不可能性を物理的に確認できる
- SLSA L3+ provenance を cosign verify コマンド一発で独立確認できる
- KEK shamir ceremony への観察者参加が制度化され、実施事実を直接証言できる
- chain-of-custody 形式の証拠保全が標準 API で自動生成され、監査レポートの証拠品質が向上する

**個人 KPI / 達成感**

- 独立検証成功率：100%（被監査組織非依存）
- WORM 確認所要時間：< 30 分
- cosign verify 成功率：100%（SLSA L3+）
- 証拠保全の chain-of-custody 完全性：100%

**主に踏むシナリオ**

- [09_外部監査人シナリオ](09_外部監査人シナリオ/README.md)

**08_開発体制との整合**

外部監査人は社内エンジニアではなく外部関係者。監査アクセスは読み取り専用の audit trail 閲覧 UI と外部公証 API に限定し、security 担当者（2-3 名）が監査アクセス制御を担保する。

**1 日の流れ**

| 時間帯 | 業務 |
|--------|------|
| 朝 | SLO burn rate 確認・on-call handoff |
| 昼 | runbook メンテ・Tekton pipeline 確認・toil 削減作業 |
| 夕方 / 夜 | incident 対応（on-call）・postmortem 執筆 |

**現状業務での痛み（k1s0 なし世界）**

- SLO 違反を文章アラートのみで検知するため burn rate の増大に気付くのが遅れる
- on-call rotation に gap が生じ、特定担当者に負荷が集中する
- postmortem が次 release をブロックしない文化が定着しておらず再発が繰り返される
- runbook が分散したドキュメントシステムに存在し陳腐化が進んでいる
- toil 削減が後回しにされ疲弊が蓄積する

**k1s0 でこう変わる**

- MWMBR alerting で SLO burn rate の早期検知が構造的に保証される
- on-call rotation の gap が 60 分 cap の auto cover で物理的にゼロになる
- postmortem PR merge が次 release の物理 prerequisite として CI で enforce される
- Backstage TechDocs に runbook が統合され常に最新状態が維持される
- SRE 50% rule が物理 enforce されることで toil ≤ 50% が保証される

**個人 KPI / 達成感**

- MWMBR alerting の burn rate 検知時間：< 5 分
- on-call rotation gap：0 件 / 月
- postmortem → アクション完了率：100%（次 release まで）
- toil 比率：≤ 50%（SRE 50% rule）

**主に踏むシナリオ**

- [10_ops担当者シナリオ](10_ops担当者シナリオ/README.md)

**08_開発体制との整合**

ops 軸はメタ専任・シニア級として定義。必須スキルは SRE 50% rule / SLO / MWMBR alerting / Argo Rollouts / Backstage TechDocs / Tekton。想定人数 3-5 名（24h on-call 3 階層 escalation に対応）。
