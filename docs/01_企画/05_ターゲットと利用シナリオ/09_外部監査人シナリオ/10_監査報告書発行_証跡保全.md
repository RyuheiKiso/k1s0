# 監査報告書発行_証跡保全

## 一文方針

監査報告書を発行し、chain-of-custody 形式の証拠保全を完結させる。

> 年次監査の最終フェーズ、外部監査人は 01〜09 のシナリオで収集した全証跡を chain-of-custody 形式で整理し、監査報告書を発行する。全証拠の hash 一覧表を作成し、監査報告書に添付する。監査で使用した short-term credential を無効化し、証跡ファイルの最終保管場所を確定させる。監査依頼者（業務管理者 / 経営層）に監査報告書を提出して監査手続きを完結させる。

## ペルソナ要約

主役: 外部監査人（公認会計士 / 監査法人スタッフ）、目的: 全監査手続きで収集した証跡を chain-of-custody 形式で保全し、監査依頼者と規制当局が使用できる品質の監査報告書を発行する

## 現状業務での痛み

- 監査で収集した証跡が複数の担当者のローカル環境に分散しており、報告書発行時に全証跡を一元整理するのに工数がかかる
- 証拠の chain-of-custody 記録が途中で途切れており、法的証拠効力が問われる場面で問題になることがある
- 監査完了後に short-term credential が無効化されたかどうかを確認する手順がない
- 監査報告書の形式が標準化されていないため、規制当局への提出時に書式の修正が必要になる

## k1s0 でこう変わる

- Backstage の外部監査人ポータルが監査期間中に収集した証跡の一元管理をサポートし、chain-of-custody 記録が自動生成される
- 監査完了時に短期 credential の自動無効化トリガーが設定されており、credential の残存リスクが排除される
- 監査報告書のテンプレートが規制当局向けの標準形式に準拠しており、追加修正なく提出できる
- 証拠の hash 一覧表が Backstage ポータルから自動生成され、報告書への添付作業が効率化される

## Trigger

監査手続き完了時（全シナリオの実施完了をトリガーとする）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 年次 1〜2 回
- 典型きっかけ: 「年次監査の全手続き完了に伴う報告書発行」「data breach 調査の完結に伴う調査報告書発行」

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 外部監査人（主役） | 外部専門家 | リモート | CLI 環境 + Backstage ポータル | 証跡整理・報告書作成・credential 無効化確認 |
| 業務管理者 / 経営層 | シニア〜経営陣 | 本社 / 事務所 | 監査報告書 | 報告書受領・不適合事項への対応 |
| security 担当者 | シニア | 開発拠点 | セキュリティダッシュボード | short-term credential の無効化 |

## 個人 KPI / 達成感

- chain-of-custody 記録の完全性（全収集証拠の記録が途切れなく存在すること）
- 監査報告書の発行所要時間（最終手続き完了から 5 営業日以内）
- short-term credential の監査完了後 24 時間以内の無効化確認
- 監査依頼者からの報告書受領確認（sign-off）の取得

## 工数 / 関与人数 / コスト感

- 証跡整理 + chain-of-custody 最終化: 4〜8 時間
- 監査報告書執筆: 1〜2 営業日
- 報告書 final review + sign-off: +半日
- 関与人数: 1〜2 名（外部監査人 + 必要に応じて補助者）

## 前提

- 01〜09 のシナリオで収集した全証跡が chain-of-custody ドキュメントに記録されている
- 監査期間中に使用した short-term credential の一覧が管理されている
- 監査報告書テンプレートが準備されている

## 流れ

1. 01〜09 のシナリオで収集した全証拠を確認し、chain-of-custody 記録の完全性を検証する
2. 証拠の hash 一覧表（証拠番号 / 証拠種別 / 取得日時 / SHA-256 hash）を作成する
3. 監査報告書を執筆する（監査手続き概要 / 実施項目 / 発見事項 / 結論 / 推奨事項）
4. 証拠の hash 一覧表を監査報告書に添付する
5. 監査報告書の draft を監査チーム内部でレビューし最終化する
6. security 担当者に short-term credential の無効化を依頼し、無効化確認を受け取る
7. 監査依頼者（業務管理者 / 経営層）に監査報告書を送付する
8. 監査依頼者から受領確認（sign-off）を受け取る
9. 全証跡ファイルと監査報告書を最終保管場所に移管し、保管期間を設定する

## 独立性宣言

外部監査人は本シナリオにおいても独立性宣言を確認済みであること。監査報告書の内容は外部監査人の独立した判断に基づいており、監査依頼者からの修正要求があっても事実認定の変更は行わない。

## 証拠保全 chain-of-custody（最終版）

監査完了時の最終 chain-of-custody 記録には以下を含む。

| 記録項目 | 内容 |
|---------|------|
| 証拠番号一覧 | EVD-001 から EVD-NNN まで全証拠の通し番号一覧 |
| 各証拠の SHA-256 hash | 取得時点での hash 値（改竄検知のベースライン） |
| 取得日時・取得者 | 各証拠の取得日時と取得者名 |
| 最終保管場所 | 各証拠ファイルの最終保管先（暗号化 USB / 安全なクラウドストレージ）|
| 保管期間 | 各証拠の保管期間（規制要件または監査契約による）|
| credential 無効化確認 | 使用した short-term credential の無効化確認日時 |

## 監査人側 tool セット

- 証拠 hash 一覧表生成スクリプト（全 EVD ファイルの SHA-256 を一括計算）
- 監査報告書テンプレート（ISO 9001 審査報告書形式 / GDPR 規制報告書形式）
- chain-of-custody 最終化フォーム
- credential 無効化確認フォーム

```bash
# 全証跡ファイルの SHA-256 hash 一覧生成
find ./evidence -type f | sort | xargs sha256sum > evidence_hash_manifest.txt

# manifest の hash を記録して改竄を検知できるようにする
sha256sum evidence_hash_manifest.txt > evidence_hash_manifest.txt.sha256
```

## 期待結果 / 観測指標 / 受入条件

- chain-of-custody 記録が監査開始から完了まで途切れなく存在している
- 全証拠の hash 一覧表が監査報告書に添付されている
- short-term credential が監査完了後 24 時間以内に無効化されていることが確認されている
- 監査依頼者から受領確認（sign-off）が得られている
- 受入条件: 監査報告書が法的証拠として使用できる品質であることを外部監査人が自己確認していること

## 失敗時の挙動 / escalation

- **chain-of-custody に gap が発見**: gap 以降の証跡の法的証拠効力が失われる可能性がある。gap の内容と影響範囲を監査報告書に明記し、監査依頼者に説明する
- **short-term credential の無効化が遅延**: security 担当者に Mattermost で escalation し、即座に無効化を実施する（SLA: 依頼後 2 時間以内）
- **監査依頼者が報告書の内容変更を要求**: 事実認定の変更は行わない。推奨事項の追加・表現の修正は可能だが、発見事項の削除・重大度の変更は拒否する

## 失敗パターン（3 例）

1. **証拠 hash 一覧表の作成を省略して監査報告書を発行する**: 証拠の完全性が監査報告書から証明できなくなる。hash 一覧表の添付を監査報告書発行の必須条件として手順書に明記する
2. **credential の無効化確認を security 担当者の口頭連絡だけで済ませる**: 後から「無効化されていなかった」という状況が発生しうる。無効化確認を書面（Mattermost / メール）で受け取り chain-of-custody に記録する
3. **監査完了後の証跡ファイルを外部監査人のローカル環境にのみ保管する**: 外部監査人のラップトップ紛失 / 故障で証跡が消失するリスクがある。暗号化された安全なクラウドストレージへのバックアップと監査依頼者への写しの提供を最終保管手順に含める
