# RFC3161_trusted_timestamp検証

## 一文方針

audit hash chain の RFC 3161 TSA 公開鍵による署名検証を独立に実施する。

> 年次監査の 2 日目、外部監査人は audit hash chain に付与された RFC 3161 タイムスタンプが信頼できる TSA（Timestamp Authority）によって署名されていることを独立に検証する。openssl ts コマンドで TSA の公開鍵を使った署名検証を実施し、タイムスタンプの時刻と audit レコードの記録時刻が一致していることを確認する。事後修正不在の証明を chain-of-custody に記録する。

## ペルソナ要約

主役: 外部監査人（公認会計士 / 監査法人スタッフ）、目的: audit hash chain のタイムスタンプが信頼できる第三者機関（TSA）によって署名されており、事後修正不在が証明できることを独立に確認する

## 現状業務での痛み

- システム内部のタイムスタンプは管理者が容易に改竄できるため、「いつ記録されたか」を内部関係者の主張だけで信頼することは監査の独立性を損なう
- RFC 3161 の技術的検証手順を知らない監査人が多く、タイムスタンプの有効性確認が形式的なチェックにとどまる
- TSA の信頼性（信頼できる認証局チェーンに属するか）を確認する手順が標準化されていない
- タイムスタンプ検証の結果を監査証拠として記録するフォーマットが定められていない

## k1s0 でこう変わる

- 全 audit レコードに RFC 3161 タイムスタンプが付与されており、TSA の公開鍵で独立検証できる
- 使用 TSA の証明書チェーンと公開鍵が公開ドキュメントとして提供されるため、外部監査人が信頼性を独立確認できる
- openssl ts コマンドによる標準的な検証手順が公開ドキュメントに記載されており、監査人が手順通りに実施できる
- タイムスタンプ検証結果が chain-of-custody に記録できる形式で出力される

## Trigger

タイムスタンプの信頼性独立検証時（年次監査手続きの一部として 01 の audit hash chain 検証と併せて実施）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 年次
- 典型きっかけ: 「DSAR 対応で提出した証跡のタイムスタンプが信頼できることを規制当局に証明する必要がある」「年次 ISO 9001 外部審査でプロセス記録の時刻信頼性を確認する」

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 外部監査人（主役） | 外部専門家 | 監査現場 / リモート | CLI 環境（openssl） | TSA 証明書確認・タイムスタンプ署名検証 |
| security 担当者 | シニア | 開発拠点 | セキュリティダッシュボード | TSA 情報提供・技術説明 |

## 個人 KPI / 達成感

- 対象 audit レコードのタイムスタンプ署名検証完了率（サンプリング方式でも可）
- TSA の信頼チェーン確認完了
- 検証完了から chain-of-custody 記録完了までの所要時間（目標: 半日以内）

## 工数 / 関与人数 / コスト感

- 標準的な検証（サンプリング 100〜500 件）: 2〜4 時間
- 全件検証（大規模テナント）: 半日
- 関与人数: 1 名（外部監査人のみ）

## 前提

- TSA の証明書チェーンと公開鍵が公開ドキュメントとして提供されている
- audit log export に RFC 3161 タイムスタンプ（.tsr ファイルまたは埋込み形式）が含まれている
- 外部監査人の環境に openssl が準備されている

## 流れ

1. k1s0 の公開ドキュメントから TSA の証明書チェーン（cacerts.pem）と公開鍵を取得する
2. TSA の認証局チェーンが信頼できる Root CA（DigiCert / GlobalSign 等）に連鎖していることを確認する
3. audit log export から RFC 3161 タイムスタンプを抽出する
4. openssl ts -verify コマンドで TSA の公開鍵による署名検証を実施する（サンプリング）
5. タイムスタンプの時刻と audit レコードの記録時刻が一致していることを確認する
6. 検証結果（全サンプル署名有効 / TSA 信頼チェーン確認）を chain-of-custody に記録する
7. 監査報告書に「RFC 3161 タイムスタンプの独立検証結果」を記載する

## 独立性宣言

外部監査人は本シナリオにおいても独立性宣言を確認済みであること。TSA 情報は k1s0 から提供されるが、TSA の信頼性確認（Root CA への連鎖）は外部監査人が独立に実施する。

## 証拠保全 chain-of-custody

| 証拠番号 | 証拠種別 | 取得日時 | 取得方法 | 保管場所 | 完全性確認 |
|---------|---------|---------|---------|---------|-----------|
| EVD-020 | TSA 証明書チェーン (PEM) | 取得日時を記録 | 公開ドキュメントから取得 | 監査人ラップトップ（暗号化） | SHA-256 hash を記録 |
| EVD-021 | openssl ts 検証結果ログ | 検証日時を記録 | CLI 出力 | 監査人ラップトップ（暗号化） | SHA-256 hash を記録 |

## 監査人側 tool セット

```bash
# TSA 証明書チェーンの Root CA 確認
openssl verify -CAfile trusted_roots.pem tsa_chain.pem

# RFC 3161 タイムスタンプ検証
openssl ts -verify \
  -in audit_record_0001.tsr \
  -data audit_record_0001.csv \
  -CAfile tsa_chain.pem

# 出力例:
# Verification: OK
```

## 期待結果 / 観測指標 / 受入条件

- 全サンプルのタイムスタンプ署名が「Verification: OK」であること
- TSA の証明書チェーンが信頼できる Root CA に連鎖していることを確認
- chain-of-custody に検証結果が記録されている
- 受入条件: 外部監査人が「タイムスタンプの信頼性」を独立に確認できたことを監査報告書に記載できること

## 失敗時の挙動 / escalation

- **署名検証失敗**: 外部監査人は即座に security 担当者に書面で通知し、監査手続きを一時中断する
- **TSA 証明書が期限切れ**: 期限切れの証明書では過去の署名が有効とみなせないため、security 担当者にタイムスタンプの再取得が必要かどうかを確認する

## 失敗パターン（3 例）

1. **TSA 証明書チェーンの Root CA 確認をスキップする**: 内部 PKI の自己署名 TSA が使われていた場合に気づかず、独立性のないタイムスタンプを有効と判定してしまう
2. **全件検証ではなくサンプリングを省略して 1 件のみ検証する**: サンプリングなしでは代表性がない。最低 100 件のランダムサンプリングを行う
3. **検証結果をスクリーンショットのみで保管する**: テキスト出力を chain-of-custody に記録することで後から検証可能な証跡にする
