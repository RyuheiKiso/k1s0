# data_breach発生時の独立調査

## 一文方針

data breach 発生時の independent investigator として audit chain を再構成し、breach の範囲と経路を独立確認する。

> 土曜深夜、k1s0 を運用する製造業テナントで data breach が発生した。規制当局への報告義務（GDPR 72 時間 / 個人情報保護法 3〜5 日）を遵守するため、外部監査人が independent investigator として緊急招集される。外部監査人は audit hash chain を再構成し、breach の発生時刻・影響範囲・アクセス経路を独立に特定する。内部関係者とは独立した調査結果が規制当局への報告書の根拠となる。

## ペルソナ要約

主役: 外部監査人（セキュリティ専門家 / フォレンジック対応経験者）、目的: data breach 発生時に内部関係者とは独立した調査を実施し、breach の範囲・経路・影響を技術的に証明する

## 現状業務での痛み

- data breach 発生時に内部関係者だけで調査すると、利益相反により調査結果の信頼性が損なわれる
- audit ログが改竄されている可能性がある場合に、改竄前の状態を独立に確認する手段がない
- breach の影響範囲を特定するために複数システムのログを突き合わせる作業が膨大で、規制当局への報告期限に間に合わないことがある
- independent investigator が迅速にアクセス可能な環境（credential / 手順書）が事前に準備されていない

## k1s0 でこう変わる

- external investigator 向けの緊急 credential 発行手順が事前に整備されており、招集後 30 分以内にアクセス可能
- audit hash chain の WORM 保存により、breach 発生後も audit ログが改竄されていないことが技術的に証明できる
- audit hash chain の再構成ツールが公開ドキュメントに記載されており、外部監査人が独立に調査を開始できる
- GDPR 72 時間 / 個人情報保護法の報告期限に対応した調査テンプレートが Backstage に準備されている

## Trigger

data breach 発生 / 疑義発生時（security 担当者からの緊急招集通知をトリガーとする）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: イベント駆動（希少だが重大）
- 典型きっかけ: 「不審なアクセスが検出され data breach の疑いがある」「個人情報を含むデータの外部流出が確認された」
- 頻度根拠: data breach は頻繁には発生しないが、発生時は72 時間以内の規制当局報告が義務付けられるため緊急性が高い

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 外部監査人（主役） | 外部専門家（フォレンジック） | リモート / 現場 | CLI 環境 + Backstage ポータル | audit chain 再構成・breach 範囲特定・報告書作成 |
| security 担当者 | シニア | 開発拠点 | セキュリティダッシュボード | 緊急 credential 発行・技術支援 |

## 個人 KPI / 達成感

- 招集後 2 時間以内に audit chain 再構成の初期結果を提出
- GDPR 72 時間期限 / 個人情報保護法 3〜5 日期限以内に調査報告書（初版）を法務部門に提出
- breach 発生時刻・影響範囲・アクセス経路の特定完了率
- 調査報告書が規制当局に受理されること

## 工数 / 関与人数 / コスト感

- 初期調査（audit chain 再構成 + 初期影響範囲特定）: 2〜6 時間
- 詳細調査（full scope）: 1〜3 営業日
- 調査報告書作成: +半日〜1 日
- 関与人数: 2〜5 名（外部監査人 + security 担当者 + data 担当者 + 法務担当）

## 前提

- external investigator 向けの緊急 credential 発行手順が事前に整備されている
- audit hash chain の再構成ツールが公開ドキュメントに準備されている
- WORM 保存により breach 発生後の audit ログが改竄されていないことが技術的に担保されている

## 流れ

1. security 担当者から緊急招集通知を受け、独立性宣言と調査範囲の合意を行う
2. 緊急 credential を受け取り、調査開始を chain-of-custody に記録する
3. audit hash chain の完全性を確認する（WORM 保存の確認 + hash 連鎖の検証）
4. 不審なアクセスが発生した時刻帯の audit レコードを中心に breach 発生時刻の特定を行う
5. 影響を受けた可能性のあるデータ範囲（テナント / PII フィールド / レコード数）を audit chain から特定する
6. アクセス経路（IP アドレス / 認証情報 / API エンドポイント）を audit レコードから追跡する
7. 初期調査結果（breach 発生時刻 / 影響範囲 / アクセス経路）を法務部門に提出する（招集後 2 時間以内）
8. 詳細調査を継続し、全容を解明する
9. 調査報告書を作成し法務部門に提出する（GDPR 72 時間期限前）

## 独立性宣言

外部監査人は本シナリオにおいても独立性宣言を確認済みであること。調査対象の内部関係者（security 担当者 / data 担当者 / 業務管理者）との利益相反がないことを確認し、独立した立場で調査結果を報告する。調査で取得した情報を調査目的以外に使用しないことを宣言する。

## 期待結果 / 観測指標 / 受入条件

- breach 発生時刻・影響範囲・アクセス経路が audit chain から技術的に特定されている
- GDPR 72 時間 / 個人情報保護法の報告期限以内に初期調査報告書が提出されている
- audit hash chain の完全性が確認されており、調査結果の信頼性が担保されている
- 受入条件: 調査報告書が規制当局への報告書の根拠資料として使用できること

## 失敗時の挙動 / escalation

- **audit hash chain に gap が発見（breach 後の改竄の可能性）**: 外部監査人は法務部門と security 担当者に即座に通知する。gap の有無を規制当局への報告書に明記する
- **GDPR 72 時間期限が迫っているが詳細不明**: 初期調査結果（既知の範囲）で規制当局に暫定報告し、詳細は後続報告とすることを法務部門に提案する
- **緊急 credential の発行に 30 分以上かかる**: 事前に緊急 credential 発行手順を演習して所要時間を把握しておく。発行遅延は調査開始の遅延につながるため事前準備が重要

## 失敗パターン（3 例）

1. **audit hash chain の完全性確認をスキップして調査を開始する**: breach 犯が audit ログを改竄していた場合、改竄後のログに基づいた誤った調査結果が規制当局に提出される。必ず hash chain 完全性確認を調査の最初のステップとする
2. **初期調査結果の提出を急いで不確かな情報を報告する**: 誤った影響範囲を報告した場合に後から修正報告が必要となり、規制当局の信頼が損なわれる。「現時点で確認できている範囲」を明記した暫定報告とし、確認済みの事実のみを記載する
3. **外部監査人が security 担当者と共同で調査シナリオを「合わせる」**: 独立性が失われる。外部監査人は内部関係者の調査結果を参照する前に独立調査を完了し、その後で比較する手順を守る
