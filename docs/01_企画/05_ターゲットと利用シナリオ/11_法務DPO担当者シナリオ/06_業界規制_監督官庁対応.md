# 業界規制_監督官庁対応

## 一文方針

業界規制監督官庁（PMDA / 厚生労働省 / 保健所）からの査察対応を法務 DPO 担当者として主導し、GMP / ISO 9001 / HACCP の適合証明と audit trail の提出を完了させる。

> 木曜午前 9 時、PMDA（医薬品医療機器総合機構）から「来月 XX 日に k1s0 を利用している医薬品製造テナントへの GMP 適合性査察を実施する」という通知が届く。法務 DPO 担当者は査察準備のチェックリストを開き、audit trail の完全性確認・GMP 適合 evidence パッケージの作成・系 quality システム整合性の確認を開始する。data 担当者に ClickHouse からの audit log 抽出を依頼し、security 担当者に改竄不可能性の証明書を要請する。

## ペルソナ要約

主役: 法務 DPO 担当者（シニア級）、目的: 監督官庁からの査察に対し、GMP / ISO 9001 / HACCP の適合 evidence を整備し査察対応を完了させる

## 現状業務での痛み

- 査察通知から準備期間が短く、audit trail の完全性を短期間で証明することが困難
- GMP / ISO 9001 / HACCP の適合 evidence が複数システムに分散しており、統合パッケージ作成に時間がかかる
- audit trail の改竄不可能性を技術的に証明する方法が確立されていない
- 過去の査察対応の手順が文書化されておらず、担当者交代後に対応品質が低下する

## k1s0 でこう変わる

- audit trail が ClickHouse に集約され、査察時に迅速に抽出・提出できる
- audit hash chain が改竄不可能性の技術的証明として機能し、監督官庁に提示できる evidence になる
- GMP / ISO 9001 / HACCP 査察準備チェックリストが Backstage TechDocs に整備され、準備の抜け漏れがなくなる
- 過去の査察対応記録が `compliance_audit.lock.yaml` に蓄積され、次回査察の準備が迅速化される

## Trigger

監督官庁査察通知受領時

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 年次〜不定期
- 典型きっかけ: 「PMDA から GMP 適合性査察の通知が届いた」「厚生労働省の食品安全査察（HACCP）の通知が届いた」
- 頻度根拠: 監督官庁査察は年次が典型。規制変更時は不定期で追加査察が入る

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 法務 DPO 担当者（主役） | シニア | 本社 / リモート | Mattermost / compliance_audit.lock.yaml | 査察準備主導・evidence パッケージ作成・当日査察対応 |
| data 担当者 | シニア | 本社 IT 室 / リモート | ClickHouse | audit trail 抽出・evidence データ提供 |
| security 担当者 | シニア | 本社 IT 室 / リモート | audit hash chain dashboard | 改竄不可能性証明書の発行 |
| 業務管理者 | シニア | テナント事業部 | Backstage admin UI | テナント固有の業務適合証明の確認 |

## 個人 KPI / 達成感

- 査察準備完了率（チェックリスト充足）: 100%
- 査察当日の evidence 提出完了: 100%
- 査察後の指摘事項数: 0 件が目標

## 工数 / 関与人数 / コスト感

- 査察準備: 3〜5 営業日
- evidence パッケージ作成: 1〜2 日
- 査察当日: 1〜2 日
- 関与人数: 4〜6 名（法務 DPO + data + security + 業務管理者 + 経営 + 外部コンサル）

## 前提

- audit trail が ClickHouse に蓄積されており、テナント単位で抽出可能
- audit hash chain の改竄不可能性証明が security 担当者から提供可能
- GMP / ISO 9001 / HACCP 査察準備チェックリストが Backstage TechDocs に整備されている

## 流れ

1. **査察通知受領 + 準備開始**: 査察日程・対象テナント・確認事項を確認し、`compliance_audit.lock.yaml` に記録する
2. **チェックリスト確認**: Backstage TechDocs の GMP / ISO 9001 / HACCP 査察準備チェックリストを開き、必要な準備を洗い出す
3. **audit trail 抽出（data 担当者と協働）**: ClickHouse から査察対象期間の audit trail を抽出し、テナント単位で整理する
4. **改竄不可能性証明書取得（security 担当者）**: audit hash chain の証明書を security 担当者から取得する
5. **GMP / ISO 9001 / HACCP 適合 evidence 整備**: 各規制の適合証明 evidence を整備する（SOP / バリデーション記録 / トレーサビリティ記録等）
6. **evidence パッケージ作成**: 査察担当者に提出する evidence パッケージを作成する
7. **事前ウォークスルー**: 査察前日に関係者でウォークスルーを実施し、想定質疑への回答を準備する
8. **当日査察対応**: 査察担当者の質疑に対応し、evidence を提示する
9. **査察結果記録 + follow-up**: 指摘事項を `compliance_audit.lock.yaml` に記録し、対応 action item を GitHub Issue 化する

## 通知 deadline timeline

- 通知 deadline は本シナリオには適用されない（監督官庁が査察日程を指定する）
- ただし指摘事項への是正対応には監督官庁が指定する期限がある（通常 30〜90 日）

## 監督官庁との接点

- **主な接点**: PMDA（医薬品製造テナント）/ 厚生労働省（食品製造テナント）/ 保健所（食品衛生法）
- **通知方法**: 査察結果の文書提出は監督官庁の指定フォームで行う
- **行政処分リスク**: 重大な GMP 違反は業務停止処分につながるリスクがある

## dual sign-off 規律

- 法務 DPO（法的適合確認）+ 業務管理者（テナント固有の業務適合確認）

## 関連適合仕様 / 関連 OSS

- security 強制機構（audit hash chain の改竄不可能性）
- 関連 OSS: ClickHouse（audit trail 抽出）/ Backstage TechDocs（準備チェックリスト）/ GitHub（action item 管理）

## 期待結果 / 観測指標

- 査察準備チェックリストが 100% 充足されている
- audit trail と改竄不可能性証明書が査察当日に提示できる
- 査察後の指摘事項が 0 件（または指定期限内に是正完了）

## 失敗時の挙動 / escalation

- **audit trail の抽出が査察日までに間に合わない**: data 担当者に L3 escalation し、tech lead が優先対応を指示する。必要に応じて監督官庁に準備状況を事前報告する
- **改竄不可能性証明書が発行できない（audit hash chain 障害）**: security 担当者が復旧を最優先で対応する。証明書なしで査察に臨む場合は外部公証（シナリオ 06-security）を活用する
- **査察で重大な指摘事項が出た**: 外部法務顧問と連携し、是正対応計画を経営と合意する

## 失敗パターン (anti-pattern)

1. **査察通知を受けてから準備を始める（通知直前）**: 査察準備は年次計画として事前に行う必要がある。`compliance_audit.lock.yaml` に年次査察スケジュールを事前登録する
2. **evidence パッケージを「とりあえず詰め込む」**: 查察担当者が必要な evidence を見つけられず、追加提出要求につながる。evidence は索引付きで整理する
3. **指摘事項の是正対応を後回しにする**: 是正期限超過は業務停止処分リスクがある
