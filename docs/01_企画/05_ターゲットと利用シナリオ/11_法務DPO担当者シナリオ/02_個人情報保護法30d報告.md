# 個人情報保護法30d報告

## 一文方針

日本 個人情報保護法 30d 報告（個人情報保護委員会への報告 + 本人通知）を法務 DPO 担当者として主導し、概算報告 30d / 確報 60d の deadline を厳守する。

> 水曜午後 3 時、日本テナント C の個人情報が外部からのアクセスで漏えいした可能性があることが security 担当者から通知される。法務 DPO 担当者は個人情報保護法第 26 条の報告義務を確認し、「漏えい等報告」の概算報告 30 日以内の deadline を記録する。security 担当者から技術詳細を収集しながら、個人情報保護委員会への報告フォームと本人通知文の draft を開始する。

## ペルソナ要約

主役: 法務 DPO 担当者（シニア級）、目的: 個人情報保護法に基づく概算報告 30d / 確報 60d の deadline を守り、個人情報保護委員会への報告と本人通知を完了する

## 現状業務での痛み

- GDPR と個人情報保護法の両方が並行して適用される場合、それぞれの deadline と要件の違いを正確に管理することが難しい
- 個人情報保護委員会への報告フォームの記載要件が複雑で、毎回確認に時間がかかる
- 本人通知の対象範囲（「速やかに」の解釈）が曖昧で、判断に迷うケースがある
- 概算報告後の確報（60d）の管理が後回しになり、期限超過が発生するリスクがある

## k1s0 でこう変わる

- `breach_notification.lock.yaml` が GDPR と個人情報保護法の両方の deadline を並行管理し、どちらの deadline も見逃さない
- 個人情報保護委員会への報告フォーム記載要件チェックリストが Backstage TechDocs に整備される
- 概算報告（30d）から確報（60d）への follow-up が `breach_notification.lock.yaml` で自動リマインドされる
- 本人通知の送信記録が data 層に保管され、委員会への完了報告に即座に活用できる

## Trigger

日本向け data breach 発生時（日本国内テナントの個人情報が漏えいした可能性がある時）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: イベント駆動（年 0〜2 件）
- 典型きっかけ: 「日本テナントの個人情報が外部アクセスで漏えいした可能性が security 担当者から通知された」
- 頻度根拠: 個人情報保護法の報告義務対象となる breach は設計上レアケース

## 個人 KPI / 達成感

- 概算報告 deadline（30d）遵守率: 100%
- 確報 deadline（60d）遵守率: 100%
- 本人通知完了率: affected 本人 100%

## 工数 / 関与人数 / コスト感

- 概算報告 draft + 送信: 4〜8 時間（breach 認識後 1 週間以内）
- 確報 draft + 送信: 4〜8 時間（breach 認識後 30〜60 日）
- 関与人数: 3〜4 名（法務 DPO + security + data + 経営承認）

## 前提

- 個人情報保護委員会への報告フォーム記載要件チェックリストが Backstage TechDocs に整備されている
- `breach_notification.lock.yaml` に個人情報保護法の deadline 管理機能が実装されている
- 日本テナントの個人情報取扱いが個人情報保護法の適用対象として特定されている

## 流れ

1. **breach 認識 T+0 記録**: 漏えい等の認識時刻を記録し、30d / 60d deadline を `breach_notification.lock.yaml` に設定する
2. **技術詳細収集（〜Day 3）**: security 担当者から技術詳細（漏えい経路 / affected テナント / データ種別）を収集する
3. **affected 本人数特定（〜Day 7）**: data 担当者が ClickHouse クエリで affected 本人数と個人情報カテゴリを特定する
4. **個人情報保護法第 26 条の報告要件確認**: 報告義務の対象判断（高い危険性があるかどうかの確認）を実施する
5. **概算報告 draft（〜Day 14）**: 個人情報保護委員会の報告フォームの記載事項を確認しながら概算報告を draft する。security 担当者との dual review を経て内容を確定する
6. **経営承認取得（〜Day 25）**: 概算報告の内容を経営に確認し、承認を取得する
7. **概算報告送信（〜Day 30）**: 個人情報保護委員会の電子報告システムで送信する。送信記録を `breach_notification.lock.yaml` に記録する
8. **本人通知実施**: 本人通知が必要と判断した場合、速やかに通知文を送付する
9. **確報 draft + 送信（〜Day 60）**: 追加調査結果を反映した確報を draft し、Day 60 の deadline 以内に委員会に送信する

## 通知 deadline timeline

| deadline | 内容 | 提出先 | 根拠条文 |
|----------|------|--------|--------|
| 概算報告: 漏えい認識後 30 日以内 | 速報（判明している範囲での報告）| 個人情報保護委員会 | 個人情報保護法 第 26 条 |
| 確報: 漏えい認識後 60 日以内 | 調査が完了した上での最終報告 | 個人情報保護委員会 | 個人情報保護法 第 26 条 |
| 本人通知: 速やかに（合理的期間） | 本人への通知（報告と並行）| breach 対象本人 | 個人情報保護法 第 26 条 |

## 監督官庁との接点

- **通知先**: 個人情報保護委員会（電子報告システム: https://www.ppc.go.jp/）
- **通知方法**: 個人情報保護委員会の電子申請ポータル（e-Gov 連携）
- **follow-up**: 委員会から追加情報要求が来た場合は指定期限内に回答する義務がある
- **行政処分リスク**: 報告義務違反は個人情報保護委員会による勧告・命令の対象

## dual sign-off 規律

- 法務 DPO（法的要件の充足確認）+ security 担当者（技術詳細の正確性確認）

## 関連適合仕様 / 関連 OSS

- security 強制機構（breach 技術詳細取得と連動）
- 関連 OSS: ClickHouse（affected 本人数特定）/ Backstage TechDocs（報告 template）/ Mattermost（通知チャネル）

## 期待結果 / 観測指標

- 概算報告が breach 認識から 30 日以内に個人情報保護委員会に送信されている
- 確報が breach 認識から 60 日以内に送信されている
- `breach_notification.lock.yaml` に概算報告・確報・本人通知の送信記録が存在する

## 失敗時の挙動 / escalation

- **Day 14 時点で技術詳細が収集できていない**: security 担当者に L3 escalation し、tech lead が優先対応を指示する
- **概算報告 deadline（Day 30）が迫っている（Day 25 時点で未 draft）**: 外部法務顧問に緊急連絡し、委員会への事前連絡（deadline 延長相談）を検討する
- **本人通知の対象範囲が確定できない**: data 担当者が ClickHouse クエリを複数パターンで実行し、保守的な（広い）範囲で本人通知を先行して実施する

## 失敗パターン (anti-pattern)

1. **概算報告と確報の deadline を混同する**: 概算報告は 30d、確報は 60d。`breach_notification.lock.yaml` で両方を別エントリで管理する
2. **GDPR 通知（01）と個人情報保護法報告（02）の対応を一本化しようとする**: 要件が異なる（deadline / 報告内容 / 通知先）ため、別々に管理する必要がある
3. **確報を概算報告後すぐに準備せず Day 50 から始める**: 確報は追加調査が必要なため、概算報告後から継続的に準備を進める
