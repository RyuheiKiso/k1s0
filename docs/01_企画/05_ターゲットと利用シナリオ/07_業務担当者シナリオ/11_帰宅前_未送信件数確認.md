# 帰宅前_未送信件数確認

## 一文方針

退社前に React SPA の Pending Queue (PQ) に残存する未送信件数 / 失敗件数を確認し、翌日の復帰 sync 計画を立てて帰宅する。

> 午後 5 時 45 分、勤務終了 15 分前。ライン担当者が iPad の SPA を開き、画面右上の PQ バッジを確認する。「未送信: 3 件」と表示されている。タップして詳細を見ると、午後の圏外区画作業で入力した検査結果が 3 件 Pending のままだ。担当者は「これは圏外区画のデータだ。明日の朝、事務所に戻れば自動で送れる」と判断し、PQ の詳細をスクリーンショットして備忘録にしておく。翌朝、事務所でネットワークに接続した瞬間、SPA が「3 件の送信が完了しました」とトーストを表示する。

## ペルソナ要約

主役: 業務担当者 (現場スタッフ級)、目的: 1 日の業務終了前に未送信データの残存状況を把握し、翌日の処理計画を立てて安心して帰宅する

## 現状業務での痛み

- 業務終了時に「今日の入力が全て送れたかどうか」を確認する手段がなく、翌日に記録漏れが発覚する
- 未送信データの件数・内容・失敗理由を一覧できる画面がなく、担当者が手探りで確認するしかない
- 帰宅後に管理者から「今日の検査データが品質 DB に未着」と連絡が来て対応できず、翌日まで持ち越しになる
- 未送信データを翌日まで放置するリスクについての認識が担当者間でばらつきがある

## k1s0 でこう変わる

- SPA の PQ バッジで未送信件数が常時表示されており、業務終了前の確認が 1 タップで完了する
- PQ 詳細画面で件数 / 内容 / 失敗理由 / 最終試行時刻が一覧表示され、翌日の対処計画を立てられる
- 翌朝のネットワーク復帰時に自動 resend が実行され、担当者の追加操作なく送信が完了する
- 管理者への事前報告機能で「今日 X 件が Pending のまま退社します」を Mattermost に 1 タップ送信できる

## Trigger

業務終了時 (退社前の最終確認フロー)

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 日次 (勤務日ごと)
- 典型きっかけ: 退社 15〜30 分前の端末確認
- 頻度根拠: 業務終了時の PQ 確認は全担当者が毎日実施する必要がある最終確認儀礼であり、未送信件数がゼロでも確認を省略しない

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 業務担当者 (主役) | 現場スタッフ | ライン / 事務所 | SPA PQ 詳細画面 | PQ 件数確認・内容確認・管理者報告 |
| 品質管理担当 | 品質管理スタッフ | 品質管理室 | 品質 DB ダッシュボード | 当日未着データの把握 |
| ライン管理者 | 現場リーダー | 事務所 | 管理ダッシュボード | Pending 件数の把握・翌日計画への反映 |

## 個人 KPI / 達成感

- 退社前 PQ 確認の実施率 (目標: 100%)
- PQ 件数ゼロで退社できた勤務日の割合 (目標: 週 3 日以上)
- 翌朝の自動 resend 成功率 (目標: 99% 以上)
- 管理者への Pending 報告実施率 (PQ 件数 1 以上の日の 100%)

## 工数 / 関与人数 / コスト感

- PQ ゼロ時の確認: 30 秒
- PQ あり・内容確認: 2〜3 分
- 管理者への Pending 報告: 追加 1 分
- 失敗時 (Pending の原因調査・即日送信試行): 5〜10 分
- 関与人数: 1〜2 名 (担当者 + 必要時に管理者)

## 前提

- SPA の PQ バッジが常時表示されており、タップで詳細画面に遷移できる
- PQ 詳細画面に件数 / 内容 / 失敗理由 / 最終試行時刻が一覧表示される
- 翌朝のネットワーク復帰時の自動 resend が Service Worker / Companion で有効化されている
- 管理者への Pending 報告ボタンが PQ 詳細画面に表示される

## 流れ

1. 退社 15〜30 分前に SPA の画面を開き、PQ バッジを確認する
2. PQ ゼロの場合: 「今日の送信は全て完了しています」メッセージを確認して終了
3. PQ あり (N 件) の場合: PQ バッジをタップして詳細画面を開く
4. 件名 / 記録時刻 / 失敗理由 / 最終試行時刻を確認する
5. 失敗理由を見て翌日の対処方針を判断する (圏外起因 → 翌朝自動 resend / 認証切れ → 翌朝ログイン後に手動 resend など)
6. 「管理者に報告する」ボタンをタップし、Mattermost に PQ 件数サマリーを送信する
7. 必要に応じて即座に送信試行 (「今すぐ再送」ボタン) を実施する
8. 即座に送信できなかった件は「翌日処理」として状態を確認し、帰宅する
9. 翌朝の出社後ネットワーク接続時に SPA が自動 resend を実行し、「3 件の送信が完了しました」トーストを表示する

- 照度: 事務所 300〜500 lux / ロッカー室 200〜300 lux

- 立位時間: 着席または立位で 1〜5 分の短時間操作

- 主端末: iPad / Windows tablet (ロッカーへの返却前に確認)
- SPA アクセス: Safari / Chrome または PWA
- 通知: Web プッシュ通知 / Mattermost
- PQ バッジ: アプリアイコン上のバッジ通知 (iOS / Android)

| SOP 条項 | k1s0 対応 |

| 社内情報管理規程 §8.2 未送信データの管理 | PQ 詳細画面での確認と管理者報告が未送信データ管理の公式手順となる |
| ISO 9001 §7.5.3 記録の管理 | PQ の翌日自動 resend により記録の完全性が維持される |

## 関連適合仕様 / 関連 OSS

- クライアント状態適合仕様 (Pending Queue / 自動 resend)
- 観測適合仕様 (PQ 件数メトリクスの管理者ダッシュボード可視化)
- Bidi 適合仕様 (翌朝 resend の at-least-once 保証)
- React (SPA フロントエンド)
- Service Worker (バックグラウンド自動 resend)

## 期待結果 / 観測指標 / 受入条件

- PQ 詳細画面が 1 秒以内に全件を表示する
- 管理者への Mattermost 報告が 10 秒以内に届く
- 翌朝の自動 resend が接続確立から 30 秒以内に開始される
- 自動 resend の at-least-once 保証で全件が品質 DB に記録される
- 受入条件: PQ 確認→退社→翌朝 resend の E2E テストが pass

## 失敗時の挙動 / escalation

- PQ 詳細画面が読み込めない: 「PQ 情報を取得できません。アプリを再起動してください」メッセージを表示
- 翌朝の自動 resend が 1 時間以内に完了しない: 端末に「未送信 N 件が残っています。手動で送信を試みてください」通知を送信
- 失敗件数が 10 件を超えて退社しようとした場合: 「未送信が 10 件以上あります。管理者への報告を推奨します」アラートを表示
- escalation: 前日の Pending が翌昼時点でも未解消の場合は品質管理担当と管理者に自動アラートを送信

## 失敗パターン (anti-pattern)

1. **PQ バッジが表示されていても確認せずに帰宅する**: 未送信データの放置が記録欠損につながる。SPA は退社時刻 (設定可能) の 15 分前に「今日の PQ 確認をしましたか？」バナーを表示して確認を促す
2. **PQ 詳細を確認せず「明日どうせ自動送信される」と思い込んで管理者報告をスキップする**: Idempotency-Key TTL 超過やネットワーク障害継続で翌日も送信できないケースがある。PQ あり退社時に管理者報告ボタンを必須フローに組み込む
3. **圏外起因と認証切れ起因を区別せずに「明日自動送信」と判断する**: 認証切れ起因の場合は翌朝ログイン前に自動 resend が失敗する。SPA は失敗理由を「圏外 / 認証切れ / tier2 エラー」の 3 種類に分類して表示し、それぞれの対処方針ガイダンスを表示する
