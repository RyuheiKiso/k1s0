# 発注承認_WebAuthn_step_up

## 一文方針

発注承認業務で v1_human_session + v1_emergency_step_up (WebAuthn) が発火し、Touch ID / セキュリティキー + PIN で認証し承認 audit emit まで完了する。

> 午後 3 時、購買担当の係長がデスクの Windows tablet で SPA を操作していると、「発注承認が必要です: 部品X 200 個 / 単価 ¥15,000 / 合計 ¥3,000,000」の承認依頼通知が届いた。合計金額が承認権限の閾値 (¥1,000,000) を超えているため、SPA が step_up 認証を要求する。係長は tablet のセキュリティキーを接続し、PIN を入力して Touch ID で追加認証を完了する。画面に「承認しました」と表示され、audit ログに承認記録が自動的に残る。

## ペルソナ要約

主役: 業務担当者 (購買係長 / 承認権限保有スタッフ級)、目的: WebAuthn step_up 認証を通じて発注承認を正確かつセキュアに完了する

## 現状業務での痛み

- 発注承認がメール / 紙の回覧で行われており、承認者の所在確認と物理的な回付に時間がかかる
- 承認記録が個人の受信フォルダや紙台帳に分散し、後から監査証跡を取り出しにくい
- 金額の大きい発注でも通常のパスワードと同じ強度の認証しかなく、不正承認のリスクがある
- 承認者が外出中の場合に業務が停滞し、発注リードタイムが伸びる

## k1s0 でこう変わる

- SPA で承認依頼が push 通知で届き、場所を問わず即座に承認できる
- 全承認アクションが audit log として自動記録され、監査証跡をいつでも検索できる
- 金額閾値超過時の WebAuthn step_up 認証により、不正承認リスクを強固に抑制する
- SPA から承認できるため、外出中でもリードタイム短縮が可能

## Trigger

発注承認が必要な業務 workflow が到達した時 (発注金額が承認権限閾値を超えた場合に step_up が発火)

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 日次〜週次 (発注業務の頻度に依存)
- 典型きっかけ: 購買担当からの発注依頼が回付された時 / 定期発注の承認タスクが到達した時
- 頻度根拠: 製造業の購買業務では日次〜週次で承認が発生し、金額閾値超過 (step_up 対象) は週次程度が標準的である

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 承認者 (主役) | 購買係長 / 権限保有スタッフ | 事務所 / 外出先 | SPA 承認タスク一覧 | step_up 認証・承認判断・承認実行 |
| 購買担当 | 購買スタッフ | 事務所 | SPA 発注フォーム | 発注依頼の起票・回付 |

## 個人 KPI / 達成感

- 承認タスクの処理所要時間 (目標: 受取から承認完了まで 5 分以内)
- step_up 認証の成功率 (目標: 99% 以上)
- 当日の承認待ちタスク消化率 (目標: 100%)
- 承認後の audit log 記録確認 (担当者自身が audit 画面で確認できる)

## 工数 / 関与人数 / コスト感

- 初回 (WebAuthn 登録含む): 10 分
- 平常 (step_up なし): 2〜3 分
- step_up あり: 3〜5 分 (Touch ID) / 5〜7 分 (セキュリティキー + PIN)
- 失敗時 (認証失敗・再試行): 10〜15 分
- 関与人数: 2〜3 名 (承認者 + 購買担当 + 必要時に業務管理者)

## 前提

- 承認者のアカウントに承認権限が付与されており、金額閾値が設定済みである
- WebAuthn デバイス (Touch ID / セキュリティキー) が SPA に登録済みである
- v1_human_session が有効で承認操作に人間の能動的アクションが必要である
- v1_emergency_step_up が閾値超過時に自動発火する設定が有効である

## 流れ

1. SPA に「承認依頼: 部品X 発注 ¥3,000,000」の push 通知が届く
2. 通知をタップして承認画面を開く
3. SPA が発注内容 (品目 / 数量 / 単価 / 合計 / 購買担当者) を表示する
4. 合計金額が閾値 (¥1,000,000) を超えているため、SPA が step_up 認証を要求するバナーを表示する
5. 「認証して承認する」ボタンをタップする
6. WebAuthn 認証ダイアログが起動する
7. Touch ID (または セキュリティキー接続 + PIN 入力) で追加認証を完了する
8. 認証成功後、SPA が承認内容の最終確認画面を表示する
9. 「承認する」ボタンをタップして承認を確定する
10. tier2 が承認を記録し、audit log に承認者 / 日時 / 認証手段 / 発注内容を emit する
11. SPA に「承認しました」トーストが表示され、購買担当に承認完了通知が届く

## 現場の物理環境

- 騒音: 事務所環境 (40〜60 dB)。外出先でも使用可能
- 照度: 事務所 300〜500 lux / 外出先は可変
- 防塵: 手袋なし。Touch ID は指の乾燥・汚れに注意
- 立位時間: 着席での操作が標準
- セキュリティキー携行: 社員証とセットで携行することが推奨される

## 使用デバイス・端末

- 主端末: Windows tablet / iPad / PC ブラウザ
- WebAuthn デバイス: Touch ID 内蔵 iPad / セキュリティキー (FIDO2 準拠) + PIN
- SPA アクセス: Safari / Chrome または PWA
- 通知: Mattermost モバイル通知 / Web プッシュ通知

## 業務手順書 (SOP) との対応

| SOP 条項 | k1s0 対応 |
|----------|----------|
| 社内購買規程 §6.1 承認権限と閾値 | 金額閾値を SPA 設定で管理し、閾値超過時の step_up 認証で準拠する |
| 社内情報セキュリティ規程 §9.3 重要操作の多要素認証 | WebAuthn step_up が「重要操作の MFA」要件を満たす |
| 内部統制 §4.2 承認証跡の保全 | audit log への自動 emit で承認証跡を電子的に保全する |

## 期待結果 / 観測指標 / 受入条件

- 金額閾値超過時に step_up 認証が必ず発火する
- Touch ID 認証が 3 秒以内に完了する
- 承認完了後に audit log に全必須フィールド (承認者 / 日時 / 認証手段 / 発注内容) が記録される
- 購買担当への承認完了通知が 10 秒以内に届く
- 受入条件: step_up 認証 E2E テストで上記 4 点が全て pass

## 失敗時の挙動 / escalation

- Touch ID 認証失敗 (3 回): セキュリティキー + PIN での代替認証を案内し、それも失敗した場合は「管理者に連絡してください」を表示
- セキュリティキー未持参: 「代替認証方法を選択してください」として SMS OTP (臨時) または管理者承認を案内
- step_up 認証タイムアウト (5 分): セッションを安全にクリアし、再度承認フローの最初から開始するよう案内
- escalation: 承認タスクが 24h 未処理の場合は業務管理者に Mattermost でエスカレーションアラートを送信

## 失敗パターン (anti-pattern)

1. **承認内容を確認せずに step_up 認証を完了して「承認する」をタップする**: 不正な発注や誤った金額の承認が発生するリスクがある。SPA は最終確認画面で発注内容の主要項目 (合計金額 / 品目 / 数量) を大きく表示し、確認チェックボックスを要求する
2. **セキュリティキーを机の引き出しに置いたまま外出する**: 外出先での step_up 認証ができなくなり、承認タスクが滞留する。SPA は前日に翌日の承認タスク予告通知を送り、セキュリティキー携行を促す
3. **step_up 認証の途中でブラウザを閉じる**: 認証フローが中断し、再度最初から操作が必要になる。SPA は認証途中でのブラウザ離脱を検出した場合、戻った際に「認証が中断されました。最初からやり直してください」の明確なメッセージを表示する
