# break_glass発火時の現場対応

## 一文方針

上長が緊急 break-glass (v1_emergency_step_up) を発火した際に、現場担当者が tier3 SPA の一時 freeze / 操作制限 / 業務管理者からの指示待ちを適切に対処する。

> 午後 3 時 20 分、工場内でセキュリティインシデントが疑われる事態が発生した。業務管理者が break-glass を発火し、全担当者の iPad に「緊急: セキュリティ対応中 - 操作が一時制限されます」のフルスクリーン通知が表示された。ライン担当者は手を止め、画面の指示に従って「確認しました」をタップする。SPA は読み取り専用モードに切り替わり、データの閲覧は可能だが送信・変更操作はすべてロックされる。担当者は Mattermost の指示チャネルを確認し、業務管理者からの安全確認完了の連絡を待つ。

## ペルソナ要約

主役: 業務担当者 (現場スタッフ級)、目的: break-glass 発火時の SPA 操作制限を正しく理解し、パニックにならず業務管理者の指示を待ちながら安全に待機する

## 現状業務での痛み

- セキュリティインシデント発生時に「何をしてよいか・してはいけないか」の連絡が口頭や電話で伝達されるため、情報が徐々にしか伝わらず混乱が生じる
- 緊急時にシステムが突然操作できなくなっても理由がわからず、担当者がパニックに陥る
- セキュリティ対応中に誰かが誤って重要データを操作・送信してしまうリスクがある
- 対応完了後の「業務再開可能」の通知が遅れ、担当者が長時間待機させられる

## k1s0 でこう変わる

- break-glass 発火と同時に全担当者の端末に理由と対処方法が明示されたフルスクリーン通知が届き、混乱を防ぐ
- SPA が自動的に読み取り専用モードに切り替わり、誤操作によるデータ漏洩・改ざんを防止する
- Mattermost の専用緊急チャネルで業務管理者からの指示がリアルタイムで届く
- 安全確認完了後に「業務再開」通知が全端末に届き、迅速に通常業務に戻れる

## Trigger

break-glass が発火した時 (上長 / 業務管理者が v1_emergency_step_up を有効化した時)

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 半年〜年次 (緊急時のみ)
- 典型きっかけ: セキュリティインシデントの疑い / 不正アクセス検出 / 内部不正の可能性 / 大規模障害発生時
- 頻度根拠: break-glass は最後の手段として設計されており、正常運用下では半年〜年次程度の発生が想定される稀なイベントである

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 業務担当者 (主役) | 現場スタッフ全員 | ライン / 事務所 / 倉庫 | SPA フルスクリーン通知 | 通知確認・操作停止・指示待ち |
| 業務管理者 | 管理者 | 管理事務所 | 管理ダッシュボード (特権) | break-glass 発火・担当者への指示・安全確認 |

## 個人 KPI / 達成感

- break-glass 通知受信から「確認しました」タップまでの所要時間 (目標: 1 分以内)
- 待機中の誤操作件数ゼロ (読み取り専用モードで操作ロックが有効)
- Mattermost 指示チャネルの確認率 (目標: 100%)
- 業務再開通知受信から通常業務再開までの所要時間 (目標: 3 分以内)

## 工数 / 関与人数 / コスト感

- 担当者側の対応: 2〜5 分 (通知確認・指示待ち)
- 待機時間: インシデント規模に依存 (15 分〜数時間)
- 業務再開後の確認: 5〜10 分 (PQ 確認・未完了操作の再実施)
- 関与人数: 全在籍担当者 + 業務管理者 + セキュリティ担当

## 前提

- 全担当者の端末に SPA の push 通知が有効化されている
- v1_emergency_step_up が業務管理者権限で発火できる状態
- Mattermost の緊急チャネルが全担当者に設定済みで通知が有効
- 業務管理者が break-glass 訓練を受けており、発火・解除手順を把握している

## 流れ

1. 業務管理者が管理ダッシュボードで break-glass を発火する (v1_emergency_step_up 有効化)
2. 全担当者の端末に「緊急: セキュリティ対応中 - 操作が一時制限されます」のフルスクリーン通知が表示される
3. 各担当者が画面を確認し「確認しました」ボタンをタップする
4. SPA が読み取り専用モードに切り替わり、送信・変更・削除操作が全てロックされる
5. 担当者は閲覧は可能なまま、Mattermost の緊急チャネルを開いて業務管理者からの指示を確認する
6. ライン管理者が現場担当者に口頭でも状況を説明し、パニックを防ぐ
7. セキュリティ担当がインシデント調査を完了し、業務管理者に「安全確認完了」を報告する
8. 業務管理者が break-glass を解除し、全担当者の端末に「業務再開可能」通知が届く
9. SPA が通常モードに復帰し、担当者が通常操作を再開する
10. 業務再開後に PQ を確認し、break-glass 中に保留された操作を必要に応じて実施する

## 業界 9 業務との紐付け

| 業務名 | 影響度 | 紐付き内容 |
|--------|--------|----------|
| 警報配信 | 高 | break-glass は最上位の緊急通知であり、警報配信インフラを使用して全担当者へ配信される |

| ライン稼働監視 | 中 | break-glass 解除後のライン稼働再開確認がライン稼働監視と連動する |

## 現場の物理環境

- 騒音: ライン稼働中は 80〜95 dB。break-glass 発生時もライン音が継続する可能性
- 照度: フロア上 200〜500 lux。フルスクリーン通知はどの照度でも視認できる設計
- 防塵: 手袋着用のままでの「確認しました」タップが必要
- 立位時間: 対応中は現地で待機 (立位 / 着席)
- 心理的プレッシャー: 突然の操作制限で担当者がパニックにならないよう、通知の文面と口頭説明が重要

## 使用デバイス・端末

- 主端末: iPad / Windows tablet / Windows PC (全端末が対象)
- SPA アクセス: Safari / Chrome / PWA (全ブラウザ・PWA が読み取り専用モードに移行)
- 通知: iOS / Android プッシュ通知 / Windows トースト通知 / Mattermost
- Mattermost: 緊急チャネルは専用チャネルで全担当者が強制参加済み

## 業務手順書 (SOP) との対応

| SOP 条項 | k1s0 対応 |
|----------|----------|
| 社内情報セキュリティ規程 §11.1 インシデント対応手順 | break-glass 発火・全担当者への通知・読み取り専用モードが公式のインシデント対応手順の一部 |
| 社内 BCP §6.3 緊急時のシステム操作制限 | v1_emergency_step_up が BCP における「システム操作制限」の公式手段として承認される |
| ISO 27001 §A.16.1 情報セキュリティインシデント管理 | break-glass の発火・解除・audit log が ISO 27001 のインシデント管理要件を満たす |

## 期待結果 / 観測指標 / 受入条件

- break-glass 発火から全担当者端末への通知まで 2 秒以内
- 全担当者の SPA が読み取り専用モードに切り替わり、送信・変更操作が完全にロックされる
- break-glass 解除から通常モード復帰まで 5 秒以内
- break-glass 発火・解除・全担当者の確認タップが audit log に全件記録される
- 受入条件: break-glass E2E テストで上記 4 点が全て pass

## 失敗時の挙動 / escalation

- 一部担当者端末に通知が届かない: 業務管理者が管理ダッシュボードで「未確認担当者」リストを確認し、ライン管理者を通じて口頭で通知する
- break-glass 中に担当者が「確認しました」をタップせず放置: 管理ダッシュボードで未確認リストが表示され、ライン管理者へ個別連絡依頼が送信される
- break-glass 解除後も一部端末が読み取り専用のままになる: SPA を再起動するよう案内し、それでも解除されない場合は IT 担当に報告
- escalation: break-glass が 2 時間以上継続する場合は工場長・本社の緊急対応チームへ自動エスカレーション

## 失敗パターン (anti-pattern)

1. **break-glass 中に「でも緊急の発注承認がある」と思い、SPA の読み取り専用モードを回避しようとする**: セキュリティ対応中の例外操作はリスクを拡大する可能性がある。SPA は読み取り専用モードのロックを担当者レベルでは解除できない設計にし、必要な場合は業務管理者が専用の override 手順 (別途 MFA) で対応する
2. **break-glass の理由がわからずパニックになり、Mattermost 緊急チャネルを確認しない**: 担当者が独自判断で行動してしまうリスクがある。フルスクリーン通知に「Mattermost の緊急チャネルで指示を確認してください」という明確な誘導文と Mattermost への直接リンクを含める
3. **break-glass 解除後に PQ 確認をスキップして業務を再開する**: break-glass 中に保留された操作 (送信待ちの検査結果など) が未処理のまま残る可能性がある。SPA は解除後の最初の画面に「break-glass 中に保留された操作: N 件があります。確認してください」バナーを自動表示する
