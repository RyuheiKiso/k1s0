# 業務エラー解析集計

## 一文方針

BusinessConflict 4 subtype（stale_write / lost_update / supersede / concurrent_edit）の月次発生集計を Backstage dashboard で確認し、頻度の高い subtype を tier3 担当者への改善要求として起票する。

> 月末金曜日、業務管理者は Backstage の業務エラー dashboard を開き、先月の BusinessConflict 発生件数を確認する。stale_write が前月比 +40% に増加しており、品質検査入力画面での発生が集中している。発生パターンと影響業務を整理し、tier3 担当者への改善要求チケットを起票する。解析結果を月次 review 会議の資料にまとめる。

## ペルソナ要約

主役: 業務管理者（シニア級）、目的: BusinessConflict の発生傾向を把握し、頻出パターンを tier3 担当者への改善要求に変換することで業務担当者の UX を改善する

## 現状業務での痛み

- 業務エラーの件数がシステムログに埋もれており、月次で傾向を把握するには手動で集計が必要
- stale_write / lost_update の区別がなく「エラーが多い」という認識にとどまり、根本原因の特定が困難
- 業務エラーの改善要求を tier3 担当者に伝える際に、どの画面・どの操作で発生しているかの情報が不足している
- 月次 review 会議の準備に都度 1〜2 日を要しており、担当者の工数を圧迫している

## k1s0 でこう変わる

- Backstage の業務エラー dashboard が BusinessConflict を 4 subtype 別に自動集計し、月次傾向をグラフで表示する
- 発生箇所（画面名 / 操作種別）が自動的にタグ付けされるため、根本原因の特定が数分でできる
- dashboard から直接 tier3 担当者への改善要求チケットを起票でき、発生パターン・件数・影響業務が自動添付される
- 月次 review 資料の骨格が dashboard の export で自動生成され、準備工数が大幅に削減される

## Trigger

月次 review 会議の前（前月分の集計確認）、または業務エラー頻度急増の通知受信時（dashboard のアラート閾値超過をトリガーとする）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 月次
- 典型きっかけ: 「月次 review 会議の 2 日前に dashboard 確認」「stale_write が前月比 2 倍の Mattermost アラートを受信した」「業務担当者から『競合エラーが多い』という問い合わせが増加した」
- 頻度根拠: BusinessConflict は日常的に発生しうるため月次の定点観測が有効

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|

## 個人 KPI / 達成感

- BusinessConflict の月次集計完了から改善要求起票完了までの所要時間（目標: 半日以内）
- 頻出 subtype の発生箇所特定率（発生件数上位 3 件について画面・操作を特定できること）
- tier3 担当者への改善要求起票件数 / 月（定量的フィードバックのループ確立）
- 改善要求を起票した発見件数のうち、翌四半期に tier3 が対応完了した件数の割合

## 工数 / 関与人数 / コスト感

- 平常（月次定点観測）: 1〜2 時間（dashboard 確認 + 分析 + 改善要求起票）
- 異常増加アラート発生時: 2〜4 時間（緊急の詳細分析 + tier3 担当者との協働調査）
- 月次 review 資料作成含む: 半日
- 関与人数: 2〜3 名（業務管理者 + tier3 担当者 + 業務担当者（ヒアリング））

## 前提

- Backstage の業務エラー dashboard が稼働しており、過去 3 ヶ月分の BusinessConflict データが集計されている
- 観測適合仕様に基づいて BusinessConflict の 4 subtype が正しく分類・記録されている
- tier3 担当者が改善要求チケットを受け付ける仕組みが整っている

## 流れ

1. Backstage の業務エラー dashboard を開き、当月の BusinessConflict 発生件数を subtype 別に確認する
2. 前月比・前年同月比のトレンドを確認し、異常増加している subtype を特定する
3. 発生箇所（画面名 / 操作種別）フィルタで、発生集中箇所を特定する
4. 上位 3 件の発生パターン（subtype × 発生箇所 × 影響業務）をメモにまとめる
5. 「改善要求起票」ボタンを押し、発生パターン・件数・影響業務を記載した tier3 担当者向けチケットを起票する
6. 月次 review 会議用の summary レポートを dashboard の export 機能で生成する
7. Mattermost `#business-error-review` に集計結果サマリを投稿する

## 業界 9 業務との紐付け

| 業務名 | 影響度 | 紐付き内容 |
|--------|--------|----------|
| 品質検査結果配信 | 高 | 検査結果入力画面での stale_write / lost_update が発生しやすく、改善優先度が高い |
| 計量装置連続データ | 高 | 連続データ送信中の concurrent_edit が計量記録の整合性に影響する |
| 在庫最新値 | 中 | 在庫更新処理でのスーパーバイズ競合が stale_write の一因になりやすい |

## Backstage プラグイン操作 UI

- **業務エラー dashboard**: BusinessConflict の subtype 別月次推移グラフ（stale_write / lost_update / supersede / concurrent_edit 別に色分け）
- **発生箇所フィルタ**: 画面名 / 操作種別 / テナント / 業務担当者 ID でドリルダウン可能
- **改善要求起票フォーム**: 発生パターン・件数・影響業務・優先度（高 / 中 / 低）を入力して tier3 担当者に送付
- **export 機能**: 選択期間の集計データと発生箇所ヒートマップを PDF / CSV で export

## 業務管理者の決定権限境界

- **実施可（単独で完結）**: dashboard 確認・分析・改善要求起票・月次 review 資料作成
- **escalation 必要（tier3 担当者）**: 改善実装の判断・実装・テスト（改善要求に応える実装作業）
- **escalation 必要（tier2 担当者）**: BusinessConflict の根本原因が tier2 の concurrency 制御にある場合の調査

## 期待結果 / 観測指標 / 受入条件

- BusinessConflict の 4 subtype 別集計が月次で正確に出力されている
- 発生上位 3 件の発生箇所（画面名 / 操作種別）が特定できている
- tier3 担当者への改善要求チケットが 1 件以上起票されている（発生パターンが確認された場合）
- 月次 review 用 summary レポートが export されている
- 受入条件: 上記 4 点が E2E テストで全て pass

## 失敗時の挙動 / escalation

- **dashboard のデータ欠損（観測適合仕様の gap）**: Backstage が「対象期間にデータ欠損があります」と警告バナーを表示。escalation 先: ops 担当者 Mattermost `#ops-incident`（SLA: 4 時間以内に調査）
- **改善要求チケット送信失敗**: Backstage が送信失敗を表示し、Mattermost `#tier3-support` へ手動で通知する
- **前月比 200% 以上のアラート閾値超過**: Mattermost `#business-error-review` にアラートが自動送付され、業務管理者に緊急の詳細分析を促す

## 失敗パターン（3 例）

1. **発生件数のみを確認して発生箇所を特定しない**: tier3 担当者への改善要求が「件数が多い」という曖昧な情報にとどまり、修正が困難になる。改善要求起票時に「画面名 / 操作種別」を必須フィールドとして設定する
2. **毎月起票するだけで tier3 の対応状況を追跡しない**: 改善要求が積み上がるだけで実際の改善が進まない。四半期ごとに起票済み改善要求の対応状況を tier3 担当者と確認する cadence を設ける
3. **BusinessConflict の急増を月次まで待って報告する**: 業務担当者が毎日エラーで操作を阻害されているにもかかわらず、月次まで改善が始まらない。dashboard のアラート閾値（前月比 +50% 超）を設定し、閾値超過時は即日確認する SOP とする
