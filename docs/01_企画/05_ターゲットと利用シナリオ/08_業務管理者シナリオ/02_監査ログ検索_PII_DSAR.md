# 監査ログ検索_PII_DSAR

## 一文方針

業務管理者が audit hash chain 検索 UI を通じて監査ログを横断検索し、GDPR DSAR / 個人情報保護法開示請求への証跡を export する。

> 金曜午後、業務管理者は法務部門から「GDPR DSAR（データ主体アクセス要求）が 30 日以内の回答期限で届いた」と連絡を受ける。Backstage プラグインの audit hash chain 検索 UI を開き、対象データ主体の識別子でフィルタをかける。検索結果を確認し、該当する audit レコードを選択して証跡 CSV を export する。export ファイルに hash 連鎖の整合性が確認できるシグネチャが付与されていることを確認して法務部門へ送付する。

## ペルソナ要約

主役: 業務管理者（シニア級）、目的: GDPR DSAR / 個人情報保護法開示請求に対して期限内に正確な audit 証跡を提出する

## 現状業務での痛み

- 監査ログが複数システムに分散しており、一件の DSAR 対応で 5〜10 システムを個別にアクセスして突き合わせる必要がある
- ログの改竄不在証明を人手で行わなければならず、規制当局への提出前に内部確認工数が膨大になる
- 個人情報に関連するレコードを識別子で横断検索する機能がなく、全ログを目視でスクリーニングする
- 30 日の DSAR 法的期限に対してログ収集だけで数日を要するため、回答文書の作成時間が圧迫される

## k1s0 でこう変わる

- audit hash chain 検索 UI により、データ主体識別子を 1 箇所に入力するだけで全テナントにまたがるログが横断検索できる
- hash 連鎖の整合性が export 時に自動検証され、改竄不在の証明書が証跡ファイルに添付される
- PII フィールドに対するアクセスログが自動的に監査対象として記録されており、スクリーニング不要
- 平均 DSAR 対応工数が半日以下になり、30 日期限に対して十分な余裕が確保される

## Trigger

DSAR 申請 / 内部調査 / 規制当局からの照会が来た時（法務部門または compliance 担当者からの依頼受信をトリガーとする）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 月次〜イベント駆動
- 典型きっかけ: 「EU の個人から GDPR DSAR が届いた（30 日期限）」「内部調査で特定ユーザの操作履歴が必要になった」「規制当局から特定期間の操作証跡の提出を求められた」
- 頻度根拠: GDPR / 個人情報保護法の対象テナントでは月次以上の頻度で DSAR や開示請求が発生しうる

## 個人 KPI / 達成感

- DSAR 受領から証跡 export 完了までの所要時間（目標: 4 時間以内）
- GDPR 30 日期限 / 個人情報保護法期限の遵守率 100%
- export 証跡の hash 整合性検証 pass 率（目標: 100%）
- 規制当局への提出書類で指摘なし件数 / 年

## 工数 / 関与人数 / コスト感

- 平常（識別子が明確な DSAR）: 2〜4 時間（検索 + 確認 + export + 法務送付）
- 複雑ケース（複数テナント + 長期間）: 0.5〜1 営業日
- 失敗時（hash 検証 fail）: +半日〜1 日（security 担当者と協働調査）
- 関与人数: 2〜4 名（業務管理者 + 法務担当 + 必要に応じて security / data 担当者）

## 前提

- 業務管理者が audit hash chain 検索 UI へのアクセス権を保有している
- audit_ingest_gap_monitor が正常稼働しており、ログ欠損がないことが確認されている
- 対象テナントの audit レコードが所定の保存期間内に存在する
- export 対象の識別子（個人 ID / メールアドレス等）が申請書に明記されている

## 流れ

1. 法務部門から DSAR 依頼（申請書 + 期限）を受領し、Backstage プラグインの audit hash chain 検索 UI を開く
2. 申請書に記載されたデータ主体の識別子（個人 ID / メールアドレス）と対象期間をフィルタに入力する
3. 検索を実行し、ヒットした audit レコードの一覧を確認する（レコード数・期間・操作種別の分布を把握）
4. 必要に応じてフィルタを絞り込み（操作種別 / テナント / 担当者）、対象レコードを選択する
5. 「証跡 export」ボタンを押下し、CSV + hash 整合性証明書（RFC 3161 タイムスタンプ付き）を取得する
6. export ファイルを開き、hash 整合性証明書のサマリを目視確認する（検証 pass の表示があること）
7. export ファイルと hash 整合性証明書を法務部門へ送付し、申請番号と期限を記録する
8. Mattermost `#compliance` チャンネルに対応完了を報告する

## Backstage プラグイン操作 UI

- **audit hash chain 検索 UI**: テナント横断の全文検索 + 識別子フィルタ + 操作種別フィルタ + 期間レンジ指定
- **レコード一覧ビュー**: ヒットレコードをタイムライン順に表示。各レコードに hash ポインタが付与されている
- **証跡 export パネル**: 選択したレコード範囲を CSV 形式で export し、hash 整合性証明書（RFC 3161 タイムスタンプ埋込み）を同梱して zip 出力する
- **hash 整合性サマリ**: export 後に画面上部に「hash 検証: pass / fail」のバナーを表示する

## 業務管理者の決定権限境界

- **実施可（単独で完結）**: audit hash chain 検索 / 証跡 export / 法務部門への送付
- **escalation 必要（security 担当者 + data 担当者）**: hash 検証 fail 時の調査 / audit_ingest_gap_monitor のアラート対応 / 法的証拠効力が問われる場合の詳細鑑定

## 期待結果 / 観測指標 / 受入条件

- 識別子フィルタで対象データ主体に関連する全 audit レコードが漏れなく検索できる
- export 証跡ファイルの hash 整合性証明書が「pass」を示している
- export 完了から法務部門への送付まで 1 時間以内
- DSAR 法的期限（GDPR: 30 日 / 個人情報保護法: 法令規定期限）を遵守している
- 受入条件: 上記 4 点が E2E テストで全て pass

## 失敗時の挙動 / escalation

- **hash 検証 fail**: Backstage が「hash 整合性エラー: 詳細を security 担当者に報告してください」と表示し、export を保留する。escalation 先: security 担当者 Mattermost `#security-incident`（SLA: 2 時間以内に調査着手）
- **audit_ingest_gap_monitor アラート（ログ欠損）**: 対象期間にログ欠損がある旨の警告が表示される。escalation 先: data 担当者 + security 担当者（SLA: DSAR 期限の 7 日前までに解消）
- **検索結果ゼロ（対象レコードが存在しない）**: Backstage が「対象期間にレコードが存在しません。保存期間設定を確認してください」と表示。escalation 先: data 担当者（保存期間ポリシー確認）
- **期限超過リスク検知**: DSAR 期限まで 7 日以内で対応が未完了の場合、Backstage が警告バナーを表示し、Mattermost `#compliance` にアラートを送付する

## 失敗パターン（3 例）

1. **識別子を不完全な状態で検索し、対象レコードの一部が漏れる**: DSAR 回答が不完全となり規制当局から不備を指摘される。申請書に記載された全識別子（メールアドレス / 個人 ID / 顧客番号）を全て入力してから検索することで防止する
2. **hash 整合性証明書の確認をスキップして法務部門へ送付する**: 証拠能力が問われる場面で後から問題が発覚する。export 後の hash サマリ画面を必ずスクリーンショット付きで確認する SOP とする
3. **DSAR 期限を法務部門に確認せずに自己判断で対応時間を見積もる**: 実際の法的期限よりも余裕があると誤解し、期限直前に対応開始してしまう。受領直後に法務部門から期限の書面確認を取ることを手順書に明記する
