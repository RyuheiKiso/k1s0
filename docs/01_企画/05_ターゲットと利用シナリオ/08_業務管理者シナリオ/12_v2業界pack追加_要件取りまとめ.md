# v2業界pack追加_要件取りまとめ

## 一文方針

v2 候補業界 pack（金融 / 医療 / サービス / 物流）への拡張を検討するにあたり、現行製造業 pack の業務管理者目線での要件 gap と拡張点を tier2 担当者へ提出する。

> 年度末、経営会議で「k1s0 の医療業界向け展開を来期検討したい」という方針が示された。業務管理者は製造業 pack で日常的に使っている機能と、医療業界の業務管理者が必要とする機能との gap を整理する。Backstage の要件取りまとめフォームに、現行 pack で充足している機能一覧と、医療業界固有の要件（薬機法 / 電子処方箋 / 患者 ID 管理など）を記載し、tier2 担当者への gap 分析資料として提出する。

## ペルソナ要約

主役: 業務管理者（シニア級）、目的: v2 業界 pack 検討の初期フェーズで現行 pack の強み・gap を業務管理者目線で整理し、tier2 担当者の技術的検討に貢献する

## 現状業務での痛み

- 現行製造業 pack の機能が他業界でも使えるかどうかを技術者視点で評価しており、業務管理者目線の評価が不足している
- 他業界の業務管理者がどのような機能を必要とするかを現行 pack のユーザが整理する機会がなく、拡張方針が開発者主導になりがち
- 業界固有の規制（金融: 金融商品取引法 / 医療: 薬機法 / 物流: 航空法など）と現行機能の対応関係が文書化されていない
- v2 pack の要件検討がトップダウンの経営判断だけで始まり、現場の業務管理者のインプットが反映されない

## k1s0 でこう変わる

- Backstage の要件取りまとめフォームが現行機能との gap 分析を構造化し、業務管理者が体系的に整理できる
- 現行製造業 pack で蓄積したシナリオ群（マスタ管理 / decision table override / 監査検索 / 緊急対応）が他業界展開の参照基盤として活用できる
- 業界固有の規制要件を business logic（decision table / 業界 pack）として分離する設計思想が v2 にも引き継がれる
- 業務管理者からの要件インプットが tier2 担当者の技術的検討に直接つながるループが確立される

## Trigger

経営判断で v2 業界 pack 検討が始まった時（経営会議での方針決定通知をトリガーとする）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 年次〜不定期
- 典型きっかけ: 「医療業界への拡張が経営判断で検討開始された」「物流会社からの引き合いで物流 pack の要件調査が必要になった」「金融業界 pack の PoC 検討が始まった」
- 頻度根拠: v2 業界 pack 検討は年次〜不定期の経営判断イベントに紐づく

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 業務管理者（主役） | シニア | 事務所 | Backstage プラグイン | 現行機能評価・他業界 gap 整理・要件書提出 |
| tier2 担当者 | シニア | 開発拠点 | GitHub PR list | 要件書の受領・技術的 gap 分析 |
| 経営層 / 事業企画 | マネージャ〜経営陣 | 本社 | 経営ダッシュボード | 拡張方針の意思決定 |
| 他業界の業務管理者候補 | — | 外部（潜在顧客） | — | ヒアリング対象（必要に応じて） |

## 個人 KPI / 達成感

- 要件書提出から tier2 担当者の gap 分析着手確認までの所要時間（目標: 1 営業日以内）
- 現行 pack で充足している機能と gap 機能の識別完了率（対象業界の主要業務ユースケースに対して）
- 業界固有の規制要件の列挙完了（対象業界の主要規制を 3 本以上識別）
- 提出した要件書が tier2 担当者から「着手可能な品質」として受け付けられた件数

## 工数 / 関与人数 / コスト感

- 要件取りまとめ（単一業界）: 1〜2 日（現行機能棚卸 + 他業界調査 + 要件書作成）
- 複数業界の比較分析: 2〜3 日
- 他業界業務管理者へのヒアリングが必要な場合: +2〜3 日
- 関与人数: 3〜5 名（業務管理者 + tier2 担当者 + 経営層 / 事業企画 + 必要に応じて外部ヒアリング対象者）

## 前提

- 経営会議での方針決定通知（検討対象業界・検討期間・PoC の有無）が文書化されている
- 業務管理者が現行製造業 pack の機能を十分に理解している（シナリオ 01〜11 の経験を有する）
- tier2 担当者が gap 分析資料を受け取れる状態である

## 流れ

1. 経営会議の方針決定通知（検討対象業界）を受領し、要件取りまとめ作業を開始する
2. 現行製造業 pack の機能一覧（マスタ管理 / decision table override / 監査検索 / 緊急対応 / partner 連携 / テナント管理 / schedule 管理 / 警報政策）を確認する
3. 検討対象業界（例: 医療）の主要業務フロー（患者管理 / 薬剤管理 / 処方箋管理 / 診療記録など）を列挙する
4. 現行機能と対象業界の業務フローを対比し、「充足」「部分充足」「gap」に分類する
5. 対象業界の主要規制（例: 薬機法 / 医療法 / 電子処方箋規制）と現行 audit / preservation 機能の対応関係を確認する
6. gap 機能の優先度（業務クリティカル / 規制必須 / あると望ましい）を整理する
7. Backstage の要件取りまとめフォームに上記内容を記載し、tier2 担当者へ提出する
8. tier2 担当者から受付確認を受け取り、gap 分析の次ステップを確認する

## Backstage プラグイン操作 UI

- **v2 業界 pack 要件取りまとめフォーム**: 現行機能棚卸 / 他業界業務フロー / gap 分類 / 規制対応分析 / 優先度の 5 セクションで構成
- **gap 分類アシスタント**: 現行機能一覧から選択した機能に対して「充足 / 部分充足 / gap」を入力すると、サマリ表が自動生成される
- **tier2 提出フォーム**: 完成した要件書を tier2 担当者へ送付。優先度 / PoC 期限 / 経営方針文書の参照を入力する

## 業務管理者の決定権限境界

- **実施可（単独で完結）**: 現行機能棚卸 / 他業界 gap 分析 / 要件書作成 / tier2 担当者への提出
- **escalation 必要（tier2 担当者）**: gap 機能の技術的実現可能性評価 / 実装工数見積もり / アーキテクチャ的な影響範囲評価
- **escalation 必要（経営層 / 事業企画）**: v2 業界 pack の PoC 投資判断 / 対象業界の顧客獲得可能性評価

## 関連適合仕様

- （業界横断）v2 業界 pack の要件が確定した後に適合仕様が定義される

## 期待結果 / 観測指標 / 受入条件

- 要件書に現行機能の充足 / gap 分類が全主要機能について記載されている
- 対象業界の主要規制が 3 本以上識別されており、現行機能との対応関係が記載されている
- gap 機能の優先度分類が完了している
- tier2 担当者から「着手可能な品質」として受付確認が得られている
- 受入条件: 上記 4 点が tier2 担当者の確認によって充足されている

## 失敗時の挙動 / escalation

- **tier2 担当者から「情報不足で着手できない」と差し戻される**: 不足情報（業界固有の業務フロー詳細 / 規制要件の出典）を補足して再提出する。必要な場合は他業界の業務管理者候補にヒアリングを依頼する
- **対象業界の規制を網羅できていない**: tier2 担当者の指摘を受けて規制一覧を補足する。法務部門または業界専門家へのヒアリングを検討する
- **経営方針が変更されて v2 検討が中断**: Backstage の要件書ステータスを「中断」に更新し、作成済み資料を保存しておく

## 失敗パターン（3 例）

1. **現行製造業 pack の機能を列挙せずに他業界要件だけを記載する**: tier2 担当者が現行機能の転用可能性を把握できず、一から開発するような工数見積もりになる。現行機能一覧を棚卸セクションで必ず記載することをフォームのガイダンスに明記する
2. **業界固有規制の調査を省略する**: 規制必須の gap 機能が識別されず、PoC 後に追加工数が発生する。規制対応分析セクションへの記載を必須フィールドとして設定する
3. **経営層の方針が確定する前に詳細な要件取りまとめに多大な工数をかける**: 方針が変更された場合に工数が無駄になる。まず 1〜2 日で概要レベルの要件書を作成して経営層に確認を取り、PoC 実施が確定してから詳細化する段階的アプローチを SOP に明記する
