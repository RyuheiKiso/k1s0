# マスタ更新_品目仕入先BOM

## 一文方針

業務管理者が Backstage プラグインから品目 / 仕入先 / BOM マスタを更新し、tier2 admin API 経由で変更を即時反映させる。schema migration を伴う変更は data 担当者へ escalation する。

> 火曜朝、事務所の業務管理者（シニア級）は品目マスタ変更申請の承認メールを受け取る。新規仕入先コードと対応 BOM 構成の追加だ。Backstage プラグインを開き、テナント別マスタ管理画面から対象レコードを検索し、差分を入力して申請番号を記録する。保存ボタンを押すと tier2 admin API が受け付け、audit ログが自動発行される。変更内容に schema 追加が含まれないことを確認した上でそのまま完了とする。

## ペルソナ要約

主役: 業務管理者（シニア級）、目的: マスタ変更申請に基づき品目 / 仕入先 / BOM マスタを正確に更新し audit 証跡を確保する

## 現状業務での痛み

- 品目マスタ更新がスプレッドシートで管理されており、複数担当者が同時編集した際に上書きが発生する
- 仕入先コードと BOM 構成の紐付けを手作業で確認しているため、入力ミスが気づかれずに流通してしまう
- 変更履歴が Excel シートの行として積み上がるだけで、誰がどの値を変更したか即座に特定できない
- schema 変更が必要なケースと値変更だけで済むケースの判断基準が文書化されておらず、担当者依存になっている

## k1s0 でこう変わる

- Backstage プラグインの排他ロック機構により、複数担当者の同時編集による上書きが構造的に防止される
- 仕入先コードと BOM 構成の整合性チェックが API 側で自動実行され、矛盾した登録が拒否される
- 全変更操作が audit hash chain に記録されるため、誰がいつ何を変更したか即座に検索・証跡提出できる
- schema migration が必要な変更は API が自動判定して data 担当者への escalation フローを起動し、境界が曖昧にならない

## Trigger

マスタ変更申請が承認された時（申請番号付きの承認通知を受信した時点で本シナリオ開始）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 週次
- 典型きっかけ: 「新規仕入先との契約締結に伴う仕入先コード追加」「生産ライン変更に伴う BOM 構成の改訂」「廃番品目の無効化申請が承認された」
- 頻度根拠: 製造業テナントでは週次で品目 / 仕入先の変動が発生するため、週次 cadence が標準

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 業務管理者（主役） | シニア | 事務所 | Backstage プラグイン | マスタ変更・整合性確認・申請番号記録 |
| 承認者（上位管理者） | シニア〜マネージャ | 事務所 | 承認ワークフロー画面 | 変更申請の承認 |
| data 担当者 | シニア | 開発拠点 | Backstage Catalog | schema migration escalation 受付 |
| tier2 担当者 | シニア | 開発拠点 | GitHub PR list | admin API の挙動確認（必要時のみ） |

## 個人 KPI / 達成感

- 承認申請書に記載された全フィールドが正確に反映されたことを確認（差分 review 画面で目視確認）
- 変更完了から audit ログ発行までの所要時間 3 秒以内
- schema migration escalation が必要な変更を自力で判定した件数 / 月（判断精度の自己評価）
- 翌日の業務担当者からの「マスタが反映されていない」問い合わせ件数がゼロ

## 工数 / 関与人数 / コスト感

- 平常（値変更のみ）: 15〜30 分（申請書確認 + 入力 + 確認）
- schema escalation 発生時: +1〜2 営業日（data 担当者対応待ち）
- 失敗時（API 拒否 / 整合性エラー）: +30 分〜1 時間（エラー内容確認 + 申請書照合）
- 関与人数: 2〜4 名（業務管理者 + 承認者 + 必要に応じて data 担当者）

## 前提

- テナントの Backstage プラグインへのアクセス権が業務管理者に付与されている
- マスタ変更申請が上位管理者に承認済みであり申請番号が発行されている
- tier2 admin API が正常稼働している
- 対象テナントの RLS 設定が正常であること

## 流れ

1. 承認メール（申請番号付き）を受信し、Backstage プラグインのテナント別マスタ管理画面を開く
2. 申請書に記載された品目コード / 仕入先コード / BOM 構成の変更内容を確認する
3. Backstage の検索フィルタで対象レコードを特定し、編集モードを開始する（排他ロック取得）
4. 申請書の差分を入力し、変更後の値と申請書の記載が一致することを差分プレビュー画面で確認する
5. 「変更種別」欄が「値変更のみ」であることを確認する（schema migration 不要と判定）
6. 申請番号を「変更理由」フィールドに記録し、保存ボタンを押下する
7. tier2 admin API がリクエストを受け付け、整合性チェックを実行する
8. 完了通知が Backstage 画面に表示され、audit ログ発行を確認する
9. Mattermost `#master-update` チャンネルに完了報告を投稿する

## Backstage プラグイン操作 UI

- **テナント別マスタ管理画面**: 品目 / 仕入先 / BOM の 3 タブ構成。テナント選択後にレコード一覧が表示される
- **差分プレビュー**: 変更前後の値を横並び比較で表示し、フィールド単位の変更箇所をハイライト
- **変更種別インジケータ**: API が自動判定した「値変更のみ」「schema migration 必要」を画面上部に表示
- **申請番号フィールド**: 変更理由欄に自由記述可能。audit ログにそのまま記録される
- **audit ログビューア**: 保存完了後に audit ログのリンクが表示され、クリックで当該レコードの変更履歴を参照できる

## 業務管理者の決定権限境界

- **実施可（単独で完結）**: 既存フィールドの値変更（文字列 / 数値 / フラグ）、レコードの有効 / 無効切替
- **escalation 必要（data 担当者）**: 新規カラム追加、型変更、外部キー制約の変更、RLS policy への影響がある変更
- 判断基準: Backstage の「変更種別インジケータ」が「schema migration 必要」と表示された場合は即座に data 担当者へ escalation する

## 期待結果 / 観測指標 / 受入条件

- 変更後のマスタレコードが申請書記載内容と完全一致している
- audit ログに申請番号 / 変更者 / 変更前後の値 / タイムスタンプが記録されている
- tier2 の整合性チェックが pass している（API レスポンスが 200 OK）
- 業務担当者の SPA 画面に変更が即時反映されている（反映遅延 < 5 秒）
- 受入条件: 上記 4 点が E2E テストで全て pass

## 失敗時の挙動 / escalation

- **整合性チェック失敗（仕入先コード未登録など）**: Backstage が具体的なエラー内容を表示し、変更を保存しない。業務管理者は申請書を照合し誤入力を修正する
- **排他ロック競合**: 別の業務管理者が同一レコードを編集中の場合、「○○が編集中（xx 分前から）」と表示し待機を促す。15 分以上継続する場合は Mattermost `#master-update` でロック解除を依頼する
- **schema migration 必要と判定**: API が 422 を返し、Backstage 画面に data 担当者 escalation フォームが表示される。SLA: 当日中に data 担当者へ escalation チケット起票
- **tier2 admin API 停止**: Backstage が「サービス停止中」バナーを表示。escalation 先: tier2 担当者 Mattermost `#tier2-incident`（SLA: 30 分以内に対応確認）

## 失敗パターン（3 例）

1. **変更種別の確認をスキップして保存する**: schema migration が必要な変更を見逃し、API が 422 を返してロールバックされる。Backstage の変更種別インジケータを必ず確認することで防止する
2. **申請番号を記録せずに保存する**: audit ログに根拠が残らず、後続の DSAR / 規制調査で変更理由を説明できなくなる。保存ボタン押下前に申請番号フィールドへの入力を必須バリデーションで強制する
3. **差分プレビューを確認せずに保存する**: 誤フィールドに値を入力していた場合に気づかないまま確定してしまう。差分プレビュー画面での目視確認を SOPとして手順書に明記する
