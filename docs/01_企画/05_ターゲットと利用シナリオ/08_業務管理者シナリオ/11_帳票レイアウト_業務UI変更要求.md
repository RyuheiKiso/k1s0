# 帳票レイアウト_業務UI変更要求

## 一文方針

業界規制変更に伴う帳票レイアウト変更 / 新業務画面追加を業務管理者が仕様書として取りまとめ、tier3 担当者への PR 依頼として発行する。

> 四半期末、業務管理者は新しい食品衛生法改正に伴う検査記録帳票の項目追加通知を受け取る。改正要件を確認し、現行の検査記録帳票と差分を整理する。Backstage の変更要求フォームに帳票変更の仕様（追加項目名 / データ型 / 配置位置 / 必須 / 任意）を記載し、tier3 担当者への PR 依頼を発行する。規制対応期限を記載し、優先度を「高」に設定して送付する。

## ペルソナ要約

主役: 業務管理者（シニア級）、目的: 規制改正 / 業務改善の要件を仕様書として整理し、tier3 担当者が実装着手できる品質の PR 依頼として発行する

## 現状業務での痛み

- 規制変更に伴う帳票変更の要件を業務管理者が整理する際に、どの情報を記載すればよいかの基準がなく、tier3 担当者との認識のずれが生じる
- 変更要求の発行から tier3 担当者の着手まで数週間かかり、規制対応期限に間に合わないことがある
- 業務担当者からの UI 改善要求が口頭で伝わるだけで仕様書化されず、実装内容が要求と乖離する
- 帳票変更が schema 変更を伴う場合と伴わない場合の判断が業務管理者に委ねられており、誤判断が発生する

## k1s0 でこう変わる

- Backstage の変更要求フォームに必須記載項目のガイダンスが組み込まれており、tier3 担当者が着手できる品質の仕様書が作成できる
- 規制対応期限が PR 依頼に明示されるため、tier3 担当者が優先度判断を明確に行える
- schema 変更が必要かどうかの判定を Backstage が補助し、必要な場合は data 担当者への escalation フローが自動的に起動する
- 変更要求の進捗が Backstage dashboard で可視化され、業務管理者が対応状況を追跡できる

## Trigger

規制改正通知受信 / 業務部門からの UI 改善要求発生時（規制改正通知メール受信または業務担当者から改善要求受領をトリガーとする）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 四半期〜年次
- 典型きっかけ: 「食品衛生法改正で検査記録帳票への追加項目が義務付けられた」「業務担当者から品質検査入力画面の操作性改善要求が蓄積した」「ISO 規格改訂でプロセス記録フォームの変更が必要になった」
- 頻度根拠: 製造業では四半期〜年次の規制改定と継続的な業務改善要求により帳票 / UI 変更が発生する

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 業務管理者（主役） | シニア | 事務所 | Backstage プラグイン | 要件整理・仕様書作成・PR 依頼発行 |
| tier3 担当者 | シニア | 開発拠点 | GitHub PR list | PR 依頼の受付・実装・テスト |
| data 担当者 | シニア | 開発拠点 | Backstage Catalog | schema 変更が必要な場合の対応 |
| 業務担当者 | 現場スタッフ | 工場フロア | SPA | 変更後の UI 受入確認 |

## 個人 KPI / 達成感

- PR 依頼発行から tier3 担当者の着手確認までの所要時間（目標: 2 営業日以内）
- 発行した PR 依頼のうち「仕様不明確による差し戻し」件数 / 年（目標: ゼロ）
- 規制対応期限を遵守した変更完了件数 / 年
- 業務担当者による変更後 UI の受入確認完了率（変更ごと）100%

## 工数 / 関与人数 / コスト感

- 規制対応の帳票変更（要件が明確）: 半日〜1 日（要件整理 + 仕様書作成 + PR 依頼発行）
- 業務改善の UI 変更（複数要求の統合）: 1〜2 日（業務担当者ヒアリング + 仕様整理 + 発行）
- schema 変更が必要と判定された場合: +1〜2 営業日（data 担当者 escalation 対応）
- 関与人数: 3〜5 名（業務管理者 + tier3 担当者 + 必要に応じて data 担当者 + 業務担当者）

## 前提

- 変更要求の根拠（規制改正通知 / 業務改善要求書）が文書として存在する
- 業務管理者が現行帳票 / UI の仕様を参照できる環境がある（Backstage の UI 仕様ドキュメント）
- tier3 担当者が新規 PR 依頼を受け付けられる状態である

## 流れ

1. 規制改正通知または業務改善要求書を受領し、変更内容を整理する
2. Backstage の変更要求フォームを開き、変更種別（帳票変更 / 新画面追加 / UI 改修）を選択する
3. 仕様書を記載する（変更対象画面 / 変更内容 / 追加 / 変更 / 削除フィールドの仕様 / データ型 / バリデーション / 規制根拠 / 対応期限）
4. 「schema 変更判定」を実行し、schema 変更の要否を確認する
5. schema 変更が「必要」の場合: data 担当者への escalation フォームを記入して送付する
6. schema 変更が「不要」の場合: 優先度（高 / 中 / 低）と対応期限を設定し、tier3 担当者への PR 依頼を発行する
7. tier3 担当者から受付確認を受け取る
8. 実装完了後、業務担当者に受入確認を依頼する

## Backstage プラグイン操作 UI

- **変更要求フォーム**: 変更種別 / 対象画面 / 仕様詳細 / 規制根拠 / 対応期限 / 優先度を入力する構造化フォーム
- **schema 変更判定アシスタント**: フォームの仕様内容から schema 変更の要否を自動判定し、結果を表示する
- **PR 依頼発行**: tier3 担当者への通知を Mattermost + Backstage の PR 依頼システムを通じて発行する
- **進捗 dashboard**: 発行済み PR 依頼の対応状況（受付済み / 着手中 / 完了 / 期限超過）を一覧表示

## 業務管理者の決定権限境界

- **実施可（単独で完結）**: 変更要求仕様書の作成 / PR 依頼発行 / 業務担当者への受入確認依頼
- **escalation 必要（tier3 担当者）**: 実際の UI 実装作業 / テスト / リリース
- **escalation 必要（data 担当者）**: schema 変更判定が「必要」となった場合の schema 設計・migration

## 期待結果 / 観測指標 / 受入条件

- PR 依頼に仕様書（変更対象 / 変更内容 / 規制根拠 / 対応期限）が明記されている
- tier3 担当者から受付確認が 1 営業日以内に届いている
- schema 変更判定が実施され、結果が PR 依頼に記録されている
- 業務担当者による受入確認が完了している
- 受入条件: 上記 4 点が E2E テストで全て pass

## 失敗時の挙動 / escalation

- **仕様書の不明確さで tier3 が着手できない**: tier3 担当者から「仕様不明確による差し戻し」通知が届く。業務管理者は不明点を補足して PR 依頼を更新する
- **schema 変更「必要」と判定されたのに escalation しない**: tier3 担当者が実装着手時に schema 変更が必要と気づき、着手遅延が発生する。Backstage のフォーム送信時に schema 変更「必要」の場合は data 担当者への escalation が完了するまで PR 依頼発行を保留する
- **規制対応期限が PR 依頼の tier3 対応完了予定を超えている**: 期限超過リスクが検知された場合、Backstage が業務管理者と tier3 担当者に警告通知を送付する

## 失敗パターン（3 例）

1. **規制根拠を仕様書に記載せずに PR 依頼を発行する**: tier3 担当者が変更の必要性を判断できず、優先度判定が誤る。変更要求フォームで「規制根拠」を必須フィールドにして記入なしでは送信できないようにする
2. **業務担当者ヒアリングなしで UI 変更仕様を一人で作成する**: 実際に操作する担当者の使いやすさを無視した UI になり、実装後に大幅な修正が必要になる。UI 変更要求は業務担当者 2 名以上へのヒアリング結果をフォームに添付することを SOP に明記する
3. **受入確認を業務管理者自身だけで行い現場担当者に確認させない**: 実際の操作環境（iPad / 工場フロア）での使いやすさが確認されないまま本番に適用される。受入確認は現場担当者 1 名以上が実際のデバイスで確認することを条件とする
