# 緊急対応_設備停止承認

## 一文方針

現場警報を受けた業務管理者が tier3 SPA の緊急対応 UI から WebAuthn step_up で設備停止を承認し、audit emit と後続 incident report 起票まで完了する。

> 水曜深夜、業務管理者のスマートフォンに工場の温度異常警報が届く。tier3 SPA の緊急対応 UI を開くと、現場担当者から「ライン B の制御盤が過熱しており設備停止の承認を求める」依頼が表示されている。WebAuthn step_up（FIDO2 セキュリティキー）で本人確認を完了させ、設備停止を承認する。承認直後に audit ログが発行され、SPA が incident report の下書きを自動生成する。業務管理者は内容を確認して起票し、Mattermost `#incident` チャンネルに報告する。

## ペルソナ要約

主役: 業務管理者（シニア級）、目的: 現場から届いた設備緊急停止依頼を安全に承認し、audit 証跡と incident report を確実に残す

## 現状業務での痛み

- 緊急停止の承認が電話口頭で行われ、誰がいつ承認したかの証跡が残らない
- 設備停止承認後の incident report 起票が翌朝まで放置され、原因調査が遅れる
- 夜間・休日の緊急対応時に承認担当者の連絡先が共有ドキュメントに分散しており、担当者特定に時間がかかる
- 承認権限のない担当者が現場判断で停止操作を実施してしまうケースが排除できていない

## k1s0 でこう変わる

- WebAuthn step_up により承認者の生体 / セキュリティキー認証が記録され、誰がいつ承認したかが audit hash chain に残る
- 設備停止承認と同時に audit ログが emit され、incident report の下書きが自動生成されるため、起票忘れが構造的に防止される
- 緊急対応 UI が警報 escalation 政策に基づいて承認担当者を自動特定し、1 タップで通知する
- 承認権限者（WebAuthn step_up 通過者）以外は停止承認ボタンが表示されない（RBAC 制御）

## Trigger

現場担当者から設備緊急停止の承認依頼が来た時（SPA の緊急対応 UI に承認依頼が表示された時点で本シナリオ開始）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 月次〜イベント駆動
- 典型きっかけ: 「制御盤の温度異常アラートが上限を超過し、現場担当者が設備停止の判断を業務管理者に委ねた」「設備の振動異常で生産継続リスクがあり緊急停止の承認が必要」
- 頻度根拠: 製造業では月次程度の頻度で設備異常が発生し、その一部が業務管理者承認を必要とする緊急停止に発展する

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 業務管理者（主役） | シニア | 事務所 / リモート | 警報通知 → SPA 緊急対応 UI | WebAuthn step_up 承認・audit 確認・incident 起票 |
| 現場担当者 | 現場スタッフ | 工場フロア | SPA ホーム（警報タイル） | 設備異常検知・停止承認依頼送信 |
| ライン管理者 | 現場リーダー | フロア / 事務所 | 管理ダッシュボード | incident 受理・現場対応指示 |
| ops 担当者 | シニア | 開発拠点 | ops ダッシュボード | 停止後の復旧 runbook 実行 |

## 個人 KPI / 達成感

- 承認依頼受信から WebAuthn step_up 承認完了までの所要時間（目標: 5 分以内）
- audit ログの自動発行成功率（目標: 100%）
- incident report 起票率（承認後 15 分以内）100%
- 承認後の設備停止確認（現場担当者からの停止完了通知受信まで）

## 工数 / 関与人数 / コスト感

- 平常（WebAuthn step_up 成功・即座に承認）: 5〜10 分
- step_up 失敗 / セキュリティキー紛失時: +15〜30 分（backup 認証フロー）
- incident report 起票まで含む総工数: 20〜30 分
- 関与人数: 3〜5 名（業務管理者 + 現場担当者 + ライン管理者 + 必要に応じて ops 担当者）

## 前提

- 業務管理者が WebAuthn step_up 認証（FIDO2 セキュリティキー）を登録済みである
- 緊急対応 UI の RBAC で業務管理者に設備停止承認権限が付与されている
- 警報 escalation 政策が最新の担当者情報で設定されている（シナリオ 08 が完了していること）
- tier2 の audit emit 機能が正常稼働している

## 流れ

1. スマートフォンに警報通知が届く（SPA プッシュ通知 / Mattermost 通知）
2. tier3 SPA の緊急対応 UI を開き、現場担当者からの設備停止承認依頼内容を確認する（設備名 / 異常内容 / 緊急度）
3. WebAuthn step_up 認証を開始する（FIDO2 セキュリティキー タップ または Touch ID）
4. step_up 認証が完了し、設備停止承認ボタンがアクティブになる
5. 承認内容（設備名 / 停止種別 / 緊急度）を最終確認し、承認ボタンを押下する
6. tier2 が設備停止コマンドを送信し、audit ログが即座に emit される
7. SPA が incident report の下書きを自動生成（発生時刻 / 設備名 / 承認者 / 停止理由）し、確認画面が表示される
8. 下書きに追記・修正を行い、incident report を起票する
9. Mattermost `#incident` に報告し、ライン管理者と ops 担当者へ通知する

## Backstage プラグイン操作 UI

- **緊急対応 UI**: 承認依頼一覧・設備名・異常内容・緊急度・現場担当者コメントを表示
- **WebAuthn step_up ダイアログ**: FIDO2 セキュリティキー / Touch ID による追加認証を要求するモーダル
- **承認確認パネル**: 承認内容（設備名 / 停止種別 / 影響範囲）を最終確認するレビュー画面。承認ボタンは step_up 完了後のみアクティブ
- **incident report 自動生成**: 承認完了直後に発生時刻 / 設備名 / 承認者 / 停止理由を自動入力したドラフトを生成。業務管理者が追記して起票する

## 業務管理者の決定権限境界

- **実施可（単独で完結）**: WebAuthn step_up 承認 / audit 確認 / incident report 起票 / Mattermost 報告
- **escalation 必要（ops 担当者）**: 停止後の復旧 runbook 実行 / 設備の再稼働承認
- **escalation 必要（security 担当者）**: WebAuthn step_up 認証の失敗が 3 回連続した場合のアカウントロック解除

## 期待結果 / 観測指標 / 受入条件

- WebAuthn step_up 認証完了から設備停止コマンド送信まで 10 秒以内
- audit ログが承認と同時に emit され、承認者 / タイムスタンプ / 設備名が記録されている
- incident report が承認後 15 分以内に起票されている
- Mattermost `#incident` にライン管理者 + ops 担当者への通知が届いている
- 受入条件: 上記 4 点が E2E テストで全て pass

## 失敗時の挙動 / escalation

- **WebAuthn step_up 失敗（セキュリティキー紛失）**: SPA が backup 認証フロー（TOTP + パスフレーズ）に切り替え。3 回失敗でアカウントロック。escalation 先: security 担当者 Mattermost `#security-incident`（SLA: 30 分以内）
- **tier2 接続不可（設備停止コマンド未送信）**: SPA が「通信エラー: 停止コマンドが送信できていません」を赤バナーで表示。業務管理者は現場担当者に電話で停止判断を直接連絡。escalation 先: ops 担当者（SLA: 10 分以内）
- **audit emit 失敗**: SPA が「audit ログ発行失敗: security 担当者に連絡してください」を表示。承認自体は有効だが audit 証跡が欠落するため緊急対応が必要。escalation 先: data 担当者 + security 担当者（SLA: 1 時間以内）

## 失敗パターン（3 例）

1. **承認依頼の内容確認をスキップして即座に承認する**: 誤った設備を停止してしまうリスクがある。承認パネルで設備名・停止種別・影響範囲を必ず目視確認してから承認ボタンを押す SOP とする
2. **incident report の起票を「後で」にして放置する**: 原因調査が遅延し、再発防止策の立案が遅れる。SPA は承認完了後 30 分以内に incident report が起票されない場合、Mattermost にリマインダーを送付する
3. **WebAuthn セキュリティキーを机の引き出しに入れて持ち歩かない**: 緊急対応時に step_up 認証ができず、backup フローへの切り替えで対応が遅延する。セキュリティキーの常時携帯を業務管理者の必携品として規程化する
