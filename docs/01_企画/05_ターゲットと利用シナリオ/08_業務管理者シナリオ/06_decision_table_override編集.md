# decision_table_override編集

## 一文方針

テナント固有の判定ルール（品質判定基準 / 在庫補充閾値 / 警報 severity マッピング）を Backstage の decision table override UI から変更し、tier2 override layer に適用する。

> 四半期初め、業務管理者は品質保証部門から「夏季の高温環境に合わせて品質判定の温度閾値を +2℃ 緩和してほしい」という変更依頼を受ける。Backstage プラグインの decision table override 編集画面を開き、対象テーブル（品質判定_温度基準）の夏季 override 行を特定する。変更前後の値を diff preview で確認し、変更理由欄に依頼番号を記録して保存する。tier2 override layer に即座に反映され、次回の品質判定から新しい閾値が適用されることを確認する。

## ペルソナ要約

主役: 業務管理者（シニア級）、目的: 業務ルール変更依頼に基づいてテナント固有の判定 override を正確に設定し、audit 証跡を確保する

## 現状業務での痛み

- 品質判定基準の変更が都度 IT 部門への依頼となり、実際に反映されるまで数日かかる
- 季節や製品ロットによる閾値調整がコード変更を伴うため、エンジニアの稼働を毎回消費する
- どの閾値がいつ誰の承認で変更されたかの履歴が散在しており、規制監査で変更根拠を説明できない
- 在庫補充閾値の変更が供給部門 / 製造部門 / 経営層で個別に管理されており、一致していないことがある

## k1s0 でこう変わる

- Backstage の decision table override UI から業務管理者が単独で閾値変更できるため、IT 部門への依頼が不要になる
- override 値がテナント固有の層として管理され、グローバル設定に影響せずテナント要件を反映できる
- 全 override 変更が audit hash chain に記録されるため、変更の根拠・承認者・タイムスタンプを即座に提出できる
- diff preview により変更前後の値と影響範囲を保存前に確認でき、誤変更が構造的に防止される

## Trigger

業務ルール変更 / 季節閾値調整 / 規制対応で判定ルール変更が必要な時（変更依頼書受領または季節変更の計画的スケジュールをトリガーとする）

## 想定頻度 / 典型きっかけ / 頻度根拠

- 想定頻度: 月次〜四半期
- 典型きっかけ: 「夏季の環境温度変化に合わせた品質判定閾値の調整」「在庫補充閾値を季節需要に合わせて見直す」「新規製品対応で警報 severity マッピングを追加する」
- 頻度根拠: 製造業では季節変動 / 新製品投入 / 規制改定に伴って月次〜四半期で判定ルールが変動する

## 主役 / 関与者

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|------|---|------------|----------------|----------------------|
| 業務管理者（主役） | シニア | 事務所 | Backstage プラグイン | override 値変更・diff 確認・audit 記録 |
| 品質保証 / 供給担当者 | — | 事務所 | 業務システム | 変更依頼の起点・変更後の動作確認 |

## 個人 KPI / 達成感

- 変更依頼受領から override 適用確認までの所要時間（目標: 30 分以内）
- diff preview 確認による誤変更防止件数 / 月（自己評価）
- 変更理由欄への依頼番号記録率（変更ごと）100%
- 閾値変更後に「意図しない動作変化」が報告された件数 / 月（目標: ゼロ）

## 工数 / 関与人数 / コスト感

- 平常（単一テーブルの値変更）: 20〜30 分
- 複数テーブルの関連変更: 30〜60 分
- 失敗時（tier2 反映エラー / 論理矛盾検出）: +30 分〜1 時間
- 関与人数: 2〜3 名（業務管理者 + 変更依頼者 + 必要に応じて tier2 担当者）

## 前提

- 業務管理者が Backstage の decision table override 編集画面へのアクセス権を保有している
- 変更対象のテーブルが tier2 override layer に存在している
- 変更依頼書（依頼番号付き）が承認されている
- グローバル（ベース）設定に override する方針であることが変更依頼書に明記されている

## 流れ

1. 変更依頼書（依頼番号 + 変更内容 + 有効日）を受領し、Backstage の decision table override 編集画面を開く
2. テナント別 override テーブル一覧から対象テーブルを選択する
3. 変更対象の行（条件 / 値のセット）を特定し、編集モードを開始する
4. 新しい override 値を入力し、diff preview を開く
5. 変更前後の値と適用条件が依頼書の内容と一致することを確認する
6. 「変更理由」フィールドに依頼番号を記録する
7. 保存ボタンを押下する
8. tier2 override layer への反映を確認する（反映 status が「適用済み」になること）
9. 変更依頼者（品質保証 / 供給担当者）に完了通知を送付する

## 業界 9 業務との紐付け

| 業務名 | 影響度 | 紐付き内容 |
|--------|--------|----------|
| 品質検査結果配信 | 高 | 品質判定基準 override が検査 pass / fail の判定に直結する |
| 在庫最新値 | 高 | 在庫補充閾値 override が補充発注タイミングに直接影響する |
| 警報配信 | 高 | 警報 severity マッピング override が警報の重要度分類を変える |
| 計量装置連続データ | 中 | 計量閾値 override が計量データの正常 / 異常判定に影響する |

## Backstage プラグイン操作 UI

- **decision table override 一覧**: テナント内の全 override テーブルを名前 / 最終変更日 / 変更者で一覧表示
- **行編集フォーム**: 条件列（適用条件）と値列（override 値）を編集できるインラインエディタ
- **diff preview パネル**: 変更前後の全行を比較表示。変更された行をハイライト。グローバル設定との差分も表示
- **反映 status バッジ**: 「保存中」→「tier2 適用済み」の status をリアルタイム更新

## 業務管理者の決定権限境界

- **実施可（単独で完結）**: 既存 override テーブルの値変更 / 行の有効 / 無効切替
- **escalation 必要（tier2 担当者）**: override テーブルの新規作成 / テーブル構造（列の追加 / 削除）の変更 / グローバル設定（ベース層）の変更
- **escalation 必要（data 担当者）**: override 値が参照する外部 lookup テーブルの schema 変更が必要な場合

## 期待結果 / 観測指標 / 受入条件

- tier2 override layer への反映が保存後 30 秒以内に完了する
- 次回の判定処理から新しい override 値が適用されている
- audit ログに変更者 / 依頼番号 / 変更前後の値が記録されている
- diff preview と実際の反映値が一致している
- 受入条件: 上記 4 点が E2E テストで全て pass

## 失敗時の挙動 / escalation

- **論理矛盾検出（override 値が下限 > 上限）**: Backstage が「論理矛盾が検出されました」と保存前にエラー表示。依頼書の記載を照合して修正する
- **tier2 反映エラー**: Backstage が反映失敗バナーを表示し retry ボタンを提示。3 回失敗後は escalation 先: tier2 担当者 Mattermost `#tier2-incident`（SLA: 30 分以内）
- **グローバル設定に影響する変更を誤って試みた場合**: Backstage が「グローバル設定への変更は tier2 担当者が必要です」と表示し、操作を拒否する

## 失敗パターン（3 例）

1. **diff preview を開かずに保存する**: 数値の桁や単位の誤りに気づかないまま override が適用され、品質判定や補充発注に意図しない影響が出る。diff preview での確認を保存の必須ステップとして SOP に明記する
2. **変更理由欄に依頼番号を記録せずに保存する**: 監査時に変更の正当性を説明できなくなる。依頼番号フィールドを必須バリデーションにする（API 側で空文字拒否）
3. **季節適用期間を誤入力して通年 override にしてしまう**: 夏季限定の閾値緩和が冬季にも適用され続けるリスクがある。変更の有効期間（開始日 / 終了日）を必須フィールドとして設定する
