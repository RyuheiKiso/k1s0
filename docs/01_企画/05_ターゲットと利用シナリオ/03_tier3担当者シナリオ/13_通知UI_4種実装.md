# 通知 UI 4 種実装

## 一文方針

tier3 担当者が業務イベントへのユーザー通知 UI（toast / banner / inline / browser notification の 4 種）を実装し、aria-live で screen reader 対応を確保する。製造業 pack の警報通知 / 承認依頼通知 / バッチ完了通知に対応する。

> 朝 9 時半、本社 IT 室の tier3 担当者（ジュニア級）が Mattermost `#tier3-dev` で「FA 設備異常検知 alert（v1_alert）の警報 UI 実装依頼」通知に気付き、警報 banner と browser notification の実装を開始する。手元には Bidi 適合仕様と Notification API のドキュメント、Mattermost 越しに tier2 担当者（通知イベントの contract 確認）と dual reviewer がいる。

## Trigger（発火条件）

tier2 担当者が新しい通知イベントを追加した時 / 業務担当者から「このイベントを画面で通知してほしい」という要求が来た時

## 想定頻度 / 典型きっかけ

想定頻度: 月次。典型きっかけ: 「FA 設備の異常検知 alert（v1_alert）が tier2 から届くようになり、低 lag の警報 UI（赤色 banner + browser notification）が必要になった」「受注承認待ちの案件が新着した際に toast 通知を表示してほしいという要求が業務担当から来た」

## 主役 / 関与者

- **主役**: tier3 担当者（ジュニア級）
- **関与**: tier2 担当者（通知イベントの contract 確認）
- **承認**: dual reviewer（tier3 担当者 1 名 + tier2 担当者 1 名）

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|---|---|---|---|---|
| 主役（tier3）| ジュニア | 本社 IT 室 / リモート | Mattermost `#tier3-dev` / Playwright CI | 通知種別選択 / コンポーネント実装 / aria-live 設定 / 重複防止 / E2E テスト |
| 関与（tier2）| 中堅 | 本社 IT 室 | Backstage Catalog | Domain Event contract の確認 / 通知イベントのスキーマ提供 / sign-off |
| 承認（dual reviewer）| 中堅〜シニア | 本社 IT 室 / リモート | GitHub PR | 4 種通知 + 重複防止 / aria-live 設定 / E2E green / sign-off |

- tier2 が通知イベントを Domain Event として発行済み。
- [リアルタイム更新 UX 方針](../../../03_概要設計/04_tier3設計方針/05_リアルタイム更新UX.md)（per-tab 16 subscription）が確立済み。
- （責務境界: [README 重要原則](./README.md#重要原則-tier3-が所有するもの--所有しないもの) を参照）

## 流れ

1. 通知イベントの重要度を 4 種類から選択する:
   - **toast**: 一時的な情報通知（バッチ完了 / 保存完了 / 軽微なエラー）。3〜5 秒後に自動消滅。`aria-live="polite"`
   - **banner**: 重要な持続的通知（システムメンテナンス / 緊急警報）。手動で閉じるまで表示。`aria-live="assertive"`
   - **inline**: フォームやデータ直近の文脈的通知（入力エラー / データ不整合）。該当要素の近くに表示。`role="alert"`
   - **browser notification**: バックグラウンド時の通知（警報 / 承認依頼）。Service Worker 経由。Notification API
2. tier2 generated stub の Domain Event インタフェースを確認する
3. 選択した通知種別に応じてコンポーネントを実装する（デザインシステムのトークンを使用）
4. browser notification の場合: Service Worker に push event handler を追加し、Notification Permission を適切に要求する（初回のみ、ユーザー操作後に要求）
5. aria-live の適切な設定を確認する（全 4 種でスクリーンリーダーが読み上げを確認）
6. 通知の重複表示を防ぐ（同一イベント ID の通知は 1 回のみ表示）
7. Playwright E2E test + axe-core a11y test を追加する
8. dual reviewer sign-off を取得する

## 業界 9 業務との紐付け

- **警報配信**: FA 設備の異常検知 alert を赤色 banner + browser notification で即時通知する実装が、警報配信の低レイテンシ要件を担う主要ユースケースとなる
- **FA 生産指示・設備操作**: 設備操作の承認依頼通知（toast / browser notification）により、FA 担当者が承認待ち状態をリアルタイムで把握できる

## 期待結果 / 観測指標

- ci: Playwright E2E test（4 種の通知表示 + 消滅 + 重複防止フロー）all green
- ci: axe-core a11y test all green（`aria-live` 設定が適切に機能していること）
- sign-off: dual reviewer（tier3 + tier2）sign-off 完了

## 失敗時の挙動 / escalation

- **browser notification の Permission が拒否されたケースで落ちる**: permission denied 時は banner に fallback する実装を追加（graceful degradation）。axe-core も permission denied ケースでテスト。
- **a11y 違反（aria-live 未設定 / role 不適切）**: merge 阻止。デザインシステム担当者に Mattermost `#design-review` で確認（**SLA: 48h 以内**）。
