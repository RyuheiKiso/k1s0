# 検索一覧 UX 実装

## 一文方針

tier3 担当者が tier2 の Read model API を消費する検索一覧 UX（cursor pagination + virtual scroll + filter）を実装し、製造業 pack の発注 / 検査 / 在庫照会等の基本一覧画面を提供する。

> 朝 9 時、本社 IT 室の tier3 担当者（ジュニア級）が GitHub PR で「FA 設備一覧画面に 3 軸フィルタ + virtual scroll の追加」レビュー依頼を受け、実装作業を開始する。手元には tier2 Read model API の generated stub と TanStack Virtual のドキュメント、Mattermost 越しに tier2 担当者（Read model API の確認）と dual reviewer がいる。

## ペルソナ要約

主役: tier3 担当者（ジュニア級）、目的: 検索一覧 UX を k1s0 の検索 UX 規約に従って一貫性ある実装にする

## 現状業務での痛み

- 検索 UX が各画面で独自実装されており、フィルター・ソート・ページネーションの挙動が画面ごとに異なる
- 検索パラメータが URL に同期されておらず、ブラウザバック時に検索状態が失われる
- 大量データ一覧のパフォーマンスが未最適化で、検索結果表示に時間がかかりユーザー体験を損なう

## k1s0 でこう変わる

- k1s0 の検索 UX コンポーネントが一貫したフィルター・ソート・ページネーションを提供し画面間の統一感が実現される
- 検索パラメータが URL search params に自動同期され、ブラウザバック時も検索状態が完全に復元される
- virtual scroll / infinite scroll が規約として組み込まれ、大量データでも Web Vitals 閾値内での表示が保証される

## Trigger（発火条件）

業務担当者から「大量レコードの一覧表示が必要」または「フィルタリング + ソートが必要な検索画面が必要」という要求が来た時

## 想定頻度 / 典型きっかけ

想定頻度: 月次。典型きっかけ: 「FA 設備一覧画面で拠点 / 状態 / 設備種別の 3 軸フィルタリング + 100 件以上の virtual scroll が必要になった。tier2-13 で追加した read model API を消費する実装を行う」「月次の受注一覧照会で cursor pagination が必要になった（全件 fetch による UX 劣化の改善）」

## 主役 / 関与者

- **主役**: tier3 担当者（ジュニア級）
- **関与**: tier2 担当者（Read model API の確認）
- **承認**: dual reviewer（tier3 担当者 1 名 + tier2 担当者 1 名）

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|---|---|---|---|---|
| 主役（tier3）| ジュニア | 本社 IT 室 / リモート | GitHub PR / Playwright CI | virtual scroll 実装 / filter UI / cursor pagination / URL query 保存 / E2E テスト |
| 関与（tier2）| 中堅 | 本社 IT 室 | Backstage Catalog | Read model API（cursor pagination 対応）の仕様確認 / cursor API 拡張対応 / sign-off |
| 承認（dual reviewer）| 中堅〜シニア | 本社 IT 室 / リモート | GitHub PR | E2E green / FID ≤ 100ms / a11y green / sign-off |

## 個人 KPI / 達成感

- 検索 UX 規約 compliance が CI で確認でき、画面間の一貫性達成を定量的に確認できる
- LCP ≤ 2.5s / INP ≤ 200ms の Web Vitals green で実装完了の達成感を得られる

## 工数 / 関与人数 / コスト感

- 工数: 1〜2 日（コンポーネント統合 4h + URL sync 実装 2h + パフォーマンスチューニング 4h）
- 関与人数: 2〜3 名（tier3・デザインシステム担当者・dual reviewer）
- コスト感: 低〜中。検索コンポーネントが規約として提供されているため個別実装は最小化される

## 前提

- tier2 担当者が Read model API（cursor pagination 対応）を提供済み（[tier2-13: 読取モデル_Projector追加](../02_tier2担当者シナリオ/13_読取モデル_Projector追加.md)）。tier2 generated stub が最新。
- （責務境界: [README 重要原則](./README.md#重要原則-tier3-が所有するもの--所有しないもの) を参照）

## 流れ

1. tier2 generated stub から Read model API のインタフェースを確認する（`GET /v1/{tenant_id}/read-models/{model_name}?cursor=&filter=&sort=` の形式）
2. virtual scroll コンポーネントを実装する（`TanStack Virtual` 等のライブラリを使用）
   - 画面内表示件数をレンダリング（全件 DOM マウント禁止）
   - スクロールに応じて cursor pagination で追加ページを fetch する
3. フィルタ UI を実装する（Select / DatePicker / TextInput 等）
   - フィルタ変更時は cursor をリセットして先頭から再取得
   - フィルタ条件を URL query string に保存（ブックマーク / ディープリンク対応）
4. ソート実装: テーブルヘッダのクリックで `sort=field:asc|desc` を API に渡す
5. 読込中の skeleton UI を実装する（a11y: `aria-busy="true"` を設定）
6. 空 result の empty state UI を実装する（0 件の場合は「該当データなし」と案内）
7. Playwright E2E test を追加する（filter → scroll → next page fetch → sort 変更のフロー）
8. axe-core a11y test が green であることを確認する
9. dual reviewer sign-off を取得する

## 業界 9 業務との紐付け

- **受注**: 受注一覧の cursor pagination + フィルタ（顧客 / 状態 / 日付）により、大量受注データを業務担当者が素早く検索・照会できる UX を提供する
- **在庫**: 在庫照会画面の virtual scroll により 1000 件超の在庫データを高速表示し、在庫確認作業の効率を高める
- **品質検査結果**: 検査結果一覧の拠点 / 製品 / 検査日 フィルタにより、品質担当者が特定条件の検査記録を即座に絞り込める

## 期待結果 / 観測指標

- ci: Playwright E2E test（filter / scroll / pagination フロー）all green
- ci: axe-core a11y test all green（WCAG 2.1 AA 違反 = 0 件）
- ux: 1000 件以上のリストで FID（First Input Delay）≤ 100ms（virtual scroll の効果）
- sign-off: dual reviewer（tier3 + tier2）sign-off 完了

## 失敗時の挙動 / escalation

- **Read model API が cursor pagination をサポートしていない**: tier2 担当者に Mattermost `#tier3-contract-fail` で連絡し API 拡張を依頼（**SLA: 24h 以内**）。API 拡張まで実装を保留。
- **virtual scroll で a11y 違反（screen reader が内容を読めない）**: デザインシステム担当者に Mattermost `#design-review` で確認（**SLA: 48h 以内**）。`aria-rowcount` / `aria-rowindex` の付与が必要な場合は修正して再テスト。

## 失敗パターン (anti-pattern)

- 独自検索 UI の実装: k1s0 検索コンポーネントを使わず自前実装すると UX 一貫性 CI が検知する
- URL sync なし: 検索状態を state のみで管理すると URL sync CI が違反を検知する
