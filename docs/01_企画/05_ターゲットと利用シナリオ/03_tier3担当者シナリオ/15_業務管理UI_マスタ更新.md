# Backstage 業務管理 UI マスタ更新

## 一文方針

業務管理者（tier3 業務管理 UI 利用者）が Backstage プラグイン経由で業務マスタ（製品コード / 工程マスタ / 取引先マスタ / 決定表）を更新し、tier3 担当者が実装した admin API を介してテナント別 DB に書き込まれ、audit hash chain に記録される一連の操作を、tier3 担当者が実装・保守する。

> 月曜朝 9 時、工場 IT 室の業務管理者が Backstage の「業務マスタ管理」プラグイン画面を開き、新しい製品コード「P-9042」の追加を行おうとする。tier3 担当者（ジュニア級）は先週実装した admin API に validation エラーが出ているという連絡を Mattermost `#tier3-bug` で受け取り、原因調査に入る。

## ペルソナ要約

主役: tier3 担当者（ジュニア級）、目的: 業務管理 UI をマスタ更新 API 経由で実装し DB 直接参照を排除する

## 現状業務での痛み

- 管理 UI が DB を直接参照し、スキーマ変更のたびに UI も変更が必要になる強い結合が生じる
- DB 直接参照により認可制御が UI 側に実装され、不正アクセスのリスクが高まる
- マスタデータの更新履歴が追跡できず、誰がいつ何を変更したかの audit trail がない

## k1s0 でこう変わる

- マスタ更新 API を通じてのみ DB にアクセスし、スキーマ変更の影響が API の contract 変更に限定される
- 認可制御が tier2 の API に集約され、管理 UI が認可ロジックを持たない設計が強制される
- API 経由の全更新が audit hash chain に記録され、マスタデータの完全な変更履歴が保証される

## Trigger（発火条件）

業務管理者からのマスタ追加・変更・無効化の申請（Backstage プラグイン経由）、または tier3 担当者が admin API の validation 実装・修正を行う必要が生じた時。

## 想定頻度 / 典型きっかけ

想定頻度: 週次〜月次（マスタ変更は業務部門が随時実施。tier3 担当者の保守は月次〜四半期）。典型きっかけ:「新工程「検査 Z ライン」が追加され、業務管理者が Backstage のマスタ管理画面から追加操作を行ったが、工程コードが重複エラーで登録できず tier3 担当者に validation ロジックの修正依頼が来た」

## 主役 / 関与者

- **主役**: tier3 担当者（ジュニア級、admin API と Backstage プラグイン実装の保守担当）
- **利用者**: 業務管理者（Backstage プラグイン側のマスタ更新操作者）
- **関与**: tier2 担当者（業務マスタの業務不変条件・RLS 設計の所有者）
- **承認**: dual reviewer

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|---|---|---|---|---|
| 主役（tier3）| ジュニア | 本社 IT 室 | Mattermost / GitHub PR | admin API validation 修正 / PR 提出 |
| 利用者（業務管理者）| — | 工場 IT 室 / 事務所 | Backstage 業務管理プラグイン | マスタ追加・変更・無効化操作 |
| 関与（tier2）| 中堅 | 本社 IT 室 | Backstage Software Catalog | 業務不変条件の確認・回答 |

## 個人 KPI / 達成感

- DB 直接参照 0 件を boundary check CI で確認でき、アーキテクチャ改善の達成感を得られる
- audit trail の全更新記録 green で compliance 完了を定量確認できる

## 工数 / 関与人数 / コスト感

- 工数: 1〜2 日（API 設計確認 2h + UI 実装 4h + audit trail 確認 2h + E2E 4h）
- 関与人数: 3 名（tier3・tier2・dual reviewer）
- コスト感: 低〜中。API 仕様が tier2 に定義されているため UI 実装に集中できる

## 前提

- Backstage Software Template で生成された tier3 admin API リポジトリが存在する
- 13 層強制機構 lint（tier3 強制機構）が CI に組込済みで、admin API が tier1 Library を直接 import していないことが保証されている
- テナント別 RLS（Row Level Security）が PostgreSQL に設定済みで、他テナントのマスタに誤って書き込めない構造になっている
- audit hash chain が稼働しており、マスタ更新操作の emit が保証されている

## 流れ

1. 業務管理者から Mattermost または Backstage のサポートチケットで問題報告を受け取る（validation エラー / 画面表示の不具合 / 新規マスタ種別追加依頼）
2. 問題の種別を判定する:
   - **validation エラー**: admin API の validation ロジックを修正する
   - **新規マスタ種別追加**: tier2 担当者に業務不変条件（unique 制約 / 文字種 / 桁数）を確認してから実装する
   - **権限エラー（RLS）**: tier2 担当者に RLS 設計を確認し、admin API のテナント context 付与を修正する
3. 修正 PR を作成する（13 層強制機構 lint を pass させること）
4. contract test で admin API ↔ tier2 業務 API の整合を確認する
5. staging 環境で業務管理者に動作確認してもらう
6. audit hash chain にマスタ更新操作が emit されることを確認する（staging での operation test）
7. Playwright E2E test を実行し、マスタ更新フローが全 green であることを確認する
8. dual reviewer sign-off を取得する

## 業界 9 業務との紐付け

- **FA 生産指示 / 進捗実績**: 工程マスタ・設備マスタの更新が生産指示の業務フローに直結する。工程コードが不正確だと FA 生産指示が誤ったラインに割り当てられる
- **品質検査結果**: 検査項目マスタ（検査コード / 判定基準）の更新。ISO 9001 / GMP の検査マスタは変更管理対象であるため audit 記録が必須
- **受注管理**: 取引先マスタ・製品コードの更新が受注登録に影響する。重複コードや無効コードでの受注は業務エラーに直結する

## 期待結果 / 観測指標

- ci: 13 層強制機構 lint が違反 0 件
- ci: contract test が all pass
- ci: Playwright E2E test が全 green（マスタ更新フロー + RLS 検証）
- audit: staging での operation test で audit hash chain に emit 済みを確認
- sign-off: dual reviewer 2 名 sign-off 完了

## 失敗時の挙動 / escalation

- **lint fail で merge 阻止**: 違反箇所を lint レポートから特定し、tier2 generated stub 経由に置換する（tier3-09 stub 経由 refactor シナリオを参照）
- **tier2 担当者が業務不変条件を回答できない**: tier2 担当者に Mattermost `#tier3-contract-fail` で確認依頼（**SLA: 24h 以内**）
- **RLS で他テナントデータが見えてしまう**: セキュリティ incident として security 担当者に即時 escalate（**SLA: 1h 以内**）。admin API のテナント context 付与の実装を緊急修正する

## 失敗パターン (anti-pattern)

- DB 直接参照: Prisma / Drizzle 等で DB に直接クエリを投げると boundary check CI が merge 阻止する
- 認可ロジックを UI に実装: ロール判定を UI で行うと security CI が認可 boundary 違反を検知する
