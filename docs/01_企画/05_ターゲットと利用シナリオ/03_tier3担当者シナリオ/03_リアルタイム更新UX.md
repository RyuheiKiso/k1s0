# リアルタイム更新 UX

## 一文方針

per-tab 16 subscription 上限と tier1 の適合仕様 pattern を厳守しながら、ラインライブ監視・警報配信などのリアルタイム更新 UX を tier1 Library の generated stub のみを通じて実装する。

> 朝 9 時半、本社 IT 室の tier3 担当者（ジュニア級）がライン監視画面の live tile コンポーネントで設備状態が更新されないことに気付く。手元には Bidi 適合仕様と tier1 generated stub の TypeScript 定義、Mattermost 越しに tier2 担当者（API 設計）と dual reviewer がいる。

## ペルソナ要約

主役: tier3 担当者（ジュニア級）、目的: WebSocket リアルタイム更新 UX を k1s0 の reconnect / replay 規約に従って実装する

## 現状業務での痛み

- WebSocket を自前実装して reconnect ロジックが不完全になり、切断後にリアルタイム更新が停止する
- replay 機能がなく再接続後に欠落したイベントが復元されないためデータ不整合が生じる
- 接続状態の UI フィードバックがなく、ユーザーがオフライン状態に気付かずに操作を続ける

## k1s0 でこう変わる

- k1s0 の WebSocket adapter が exponential backoff reconnect と replay offset を自動管理し欠落なし再接続を保証する
- Server-Sent Events fallback が自動で有効化され、proxy 環境でも接続が維持される
- 接続状態インジケーターが UX 規約として Template に組み込まれ、ユーザーが常に接続状況を認識できる

## Trigger（発火条件）

ラインライブ監視 / 警報配信など、リアルタイム更新 UX を要求する業務画面を実装する時。

## 想定頻度 / 典型きっかけ

想定頻度: 月次。典型きっかけ: 「工場ライン稼働監視画面が live tile（16 subscription）で設備状態をリアルタイム表示する要件が追加された」

## 主役 / 関与者

- **主役**: tier3 担当者（ジュニア級）
- **関与**: tier2 担当者（API 設計）/ dual reviewer

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|---|---|---|---|---|
| 主役（tier3）| ジュニア | 本社 IT 室 / リモート | GitHub PR / Jest CI | subscription pattern 実装 / live tile / replay 対応 / Playwright E2E |
| 関与（tier2）| 中堅 | 本社 IT 室 | Backstage Catalog | stream API 仕様確認 / per-tab 上限設計レビュー / sign-off |
| 承認（dual reviewer）| 中堅〜シニア | 本社 IT 室 / リモート | GitHub PR | subscription 数 / replay 整合 / E2E green 確認 / sign-off |

## 個人 KPI / 達成感

- reconnect 後の replay によるイベント欠落 0 件を E2E テストで定量確認できる
- 接続断 → 再接続までの UX フロー全件 green で実装完了の達成感を得られる

## 工数 / 関与人数 / コスト感

- 工数: 1〜2 日（adapter 統合 4h + replay 実装 4h + E2E 4h）
- 関与人数: 2〜3 名（tier3・tier2・dual reviewer）
- コスト感: 中。replay ロジックが adapter に集約されるため自前実装より大幅に削減される

## 前提

- [per-tab 16 subscription](../../../03_概要設計/04_tier3設計方針/05_リアルタイム更新UX.md) 上限（HTTP/2 multiplex 活用）
- v1_live_snapshot（latest-wins）/ v1_alert（低 lag + replay）の適合仕様が tier1 で定義済み
- tier1 Library の Bidi / SSE stream API（generated stub）が利用可能
- （責務境界: [README 重要原則](./README.md#重要原則-tier3-が所有するもの--所有しないもの) を参照）

## 流れ

1. 必要な subscription pattern（v1_live_snapshot / v1_event_feed / v1_alert / v1_interactive）を特定
2. per-tab subscription 数が 16 上限を超えないよう UI コンポーネント設計（super-position でまとめる等）
3. tier1 Library の Bidi / SSE stream API（generated stub）を使い、独自 WebSocket を張らない
4. live tile コンポーネント: latest-wins で stale indicator を表示（接続断 → gray-out）
5. replay 対応（v1_event_feed / v1_alert）: 復帰時の missed event を replay して整合性維持
6. Playwright E2E: subscription 確立 → data 受信 → live 更新 → 接続断 → 再接続 の全フローを網羅
7. dual reviewer sign-off

## Timeline

| T+ | actor | action | 通知例 |

| 1d+4h | dual reviewer | replay 動作と接続状態 UI を確認し sign-off | `sign-off 完了` |

## 業界 9 業務との紐付け

- **ライン稼働監視・進捗実績**: live tile（16 subscription）で各設備の稼働状態をリアルタイム表示することが本シナリオの主要ユースケースであり、ライン監視の即時性を直接支える
- **警報配信**: v1_alert pattern（低 lag + replay）を使った警報 UI 実装により、設備異常の検知から警報表示までのレイテンシを最小化する

## 期待結果 / 観測指標

- per-tab subscription 数 ≤ 16 を常時維持
- live tile の stale indicator が接続断 5 秒以内に gray-out
- replay 後のデータ整合性: missed event 0 件
- Playwright E2E: 全フロー green
- dual reviewer 2 名 sign-off 完了

## 失敗時の挙動 / escalation

- per-tab 16 超過を lint が検出 → merge 阻止。**escalate 先**: 設計担当者に Mattermost `#tier3-arch-review` で subscription 削減方針を相談（**SLA**: 48h 以内）。**runbook**: Backstage runbook `per-tab-subscription-cap` を参照
- 独自 WebSocket 実装を lint が検出 → merge 阻止、tier1 stub 経由に修正。**escalate 先**: tier1 担当者に Mattermost `#tier3-contract-fail` で stub 追加依頼（**SLA**: 24h 以内）
- replay 不整合が E2E で検出 → **escalate 先**: tier2 / tier1 担当者に Mattermost `#tier3-contract-fail` で replay 仕様確認を依頼（**SLA**: 24h 以内）

## 失敗パターン (anti-pattern)

- 自前 WebSocket 実装: adapter を使わずに直接 WebSocket を new すると reconnect / replay 規約が適用されず CI が検知する
- replay なしの再接続: offset を保存しない実装はイベント欠落を生み、E2E の再接続テストで fail する
