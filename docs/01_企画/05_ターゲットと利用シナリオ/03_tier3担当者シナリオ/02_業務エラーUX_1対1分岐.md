# 業務エラー UX 1 対 1 分岐

## 一文方針

tier2 が追加した BusinessConflict subtype の contract を受け取り、各 subtype に対して 1:1 の UI 分岐コンポーネントを実装することで、業務担当者が自力で状況を解決できる UX を提供する。

> 朝 9 時、本社 IT 室の tier3 担当者（ジュニア級）が Mattermost `#tier3-dev` で「`concurrent_edit` subtype が tier2 stub に追加された」通知に気付く。手元には tier2 generated stub の TypeScript 定義と Playwright、Mattermost 越しに tier2 担当者（subtype contract 宣言）と dual reviewer がいる。

## ペルソナ要約

主役: tier3 担当者（ジュニア級）、目的: tier2 が追加した BusinessConflict subtype に対して 1:1 の UI 分岐を実装する

## 現状業務での痛み

- BusinessConflict UX がファイルごとにバラバラで、subtype 追加のたびに実装方針を再検討する
- fallback UI が定義されておらず、未知 subtype で例外が発生しても CI では検知できない
- recovery_hints に PII が混入していても UI 側でレンダリングしてしまうリスクがある

## k1s0 でこう変わる

- generated stub の subtype 一覧を起点に 1:1 実装規約が定まり、ファイルごとのバラバラ実装がなくなる
- fallback UI を必須とする contract test が CI で強制され、未知 subtype の例外が merge 前に検知される
- tier2 が redaction 済みの recovery_hints のみが stub に公開されるため PII 混入を構造的に防ぐ

## Trigger（発火条件）

tier2 が BusinessConflict subtype を追加した通知を受け、tier3 側でその subtype に対応する 1:1 UI 分岐を実装する時。

## 想定頻度 / 典型きっかけ

想定頻度: 四半期（tier2 で新 subtype が追加された時）。典型きっかけ: 「並行受注編集で `concurrent_edit` subtype が追加され、presence indicator + user choice UI の実装依頼が来た」

## 主役 / 関与者

- **主役**: tier3 担当者（ジュニア級）
- **関与**: tier2 担当者（subtype contract 宣言）/ dual reviewer

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|---|---|---|---|---|
| 主役（tier3）| ジュニア | 本社 IT 室 / リモート | Mattermost `#tier3-dev` / Jest CI | subtype 確認 / 1:1 UI 分岐実装 / Playwright E2E / PR 提出 |
| 関与（tier2）| 中堅 | 本社 IT 室 | Backstage Catalog | BusinessConflict subtype contract 宣言 / recovery_hints 確認 / sign-off |
| 承認（dual reviewer）| 中堅〜シニア | 本社 IT 室 / リモート | GitHub PR | 全 subtype カバレッジ + fallback UI 確認 / sign-off |

## 個人 KPI / 達成感

- 全 BusinessConflict subtype に 1:1 UI 分岐が存在することを Playwright E2E で定量確認できる
- fallback UI green → merge 可能というゲートで実装完了の達成感を明確に得られる

## 工数 / 関与人数 / コスト感

- 工数: 0.5〜1 日（subtype 確認 1h + 分岐実装 4h + E2E 2h）
- 関与人数: 3 名（tier3・tier2・dual reviewer）
- コスト感: 低。subtype 一覧が stub に明示されているため調査コストが最小化される

## 前提

- tier2 が BusinessConflict subtype の contract（エラーコード / recovery_hints / PII redaction 済み）を宣言済み
- 対応する subtype の一覧が tier2 generated stub に含まれている
- （責務境界: [README 重要原則](./README.md#重要原則-tier3-が所有するもの--所有しないもの) を参照）

## 流れ

1. tier2 の BusinessConflict subtype 一覧（stale_write / lost_update / supersede / concurrent_edit + 新 subtype）を確認
2. 各 subtype に 1:1 の UI 分岐コンポーネントを実装
   - `stale_write` → field-level rebase UI
   - `lost_update` → 3-way merge UI
   - `supersede` → silent toast
   - `concurrent_edit` → presence indicator + user choice
3. recovery_hints を UI に表示（PII は既に tier2 で redaction 済みのため表示可能なものを使う）
4. subtype が未知の場合の fallback UI を定義（generic エラー + 再読み込み提案）
5. Playwright E2E test で全 subtype の UI 分岐を網羅
6. dual reviewer sign-off

## 業界 9 業務との紐付け

- **受注**: 並行受注編集による `concurrent_edit` / `stale_write` は受注業務で最も頻発するため、本シナリオの UI 分岐が受注競合時の業務継続性を直接支える
- **在庫**: 在庫引当の同時更新で `lost_update` が発生した際、3-way merge UI で業務担当者が在庫数を自己解決できる UX を提供する

## 期待結果 / 観測指標

- 全 BusinessConflict subtype に対して 1:1 の UI 分岐が存在する
- fallback UI が未知 subtype で正しく表示される
- Playwright E2E: 全 subtype カバレッジ green
- dual reviewer 2 名 sign-off 完了

## 失敗時の挙動 / escalation

- 未知 subtype が fallback なしで例外 → CI で uncaught error として検出 → merge 阻止。**escalate 先**: tier2 担当者に Mattermost `#tier3-contract-fail` で subtype 追加を通知（**SLA**: 24h 以内）
- recovery_hints に PII が混入 → **escalate 先**: tier2 担当者に Mattermost `#tier3-contract-fail` で redaction 修正を依頼（**SLA**: 24h 以内）。**runbook**: Backstage runbook `pii-redaction-check` を参照
- contract test fail → merge 阻止。**escalate 先**: tier2 担当者に Mattermost `#tier3-contract-fail` で連絡（**SLA**: 24h 以内）

## 失敗パターン (anti-pattern)

- switch/case で subtype を直書き: stub の型定義を無視した実装は contract test で検知されず drift が生じる
- fallback を省略: 未知 subtype でクラッシュするコードは CI の uncaught error check で merge 阻止される
