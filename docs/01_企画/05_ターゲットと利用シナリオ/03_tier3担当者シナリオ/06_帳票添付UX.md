# 帳票添付 UX

## 一文方針

tier2 の添付帳票 API（signed URL + envelope 暗号化）を通じてのみ upload / download を行い、virus scan 完了フラグ・retention policy 表示・a11y 通知を確立することで、業務担当者が安全に帳票を扱える UX を提供する。

> 朝 9 時半、本社 IT 室の tier3 担当者（ジュニア級）が GitHub PR の CI 結果で「virus scan 完了前に signed URL が露出」する E2E テストの fail に気付く。手元には tier2 添付帳票 API の generated stub と Playwright、Mattermost 越しに tier2 担当者（添付帳票 API）と dual reviewer がいる。

## ペルソナ要約

主役: tier3 担当者（ジュニア級）、目的: 帳票添付 UX を k1s0 の帳票レイアウト規約に従って実装する

## 現状業務での痛み

- 帳票レイアウトを hardcode で実装し、規制変更のたびに全帳票ファイルを手動修正する必要がある
- 帳票フォーマットが各画面で独自実装されており、法改正対応時に抜け漏れが発生する
- PDF 生成ロジックが UI コンポーネントに混在し、tier2 との責務境界が曖昧になる

## k1s0 でこう変わる

- 帳票レイアウトテンプレートが中央管理され、規制変更時は 1 箇所の更新で全帳票に反映される
- 帳票フォーマットが適合仕様に定義されており、法改正対応時の影響範囲が明確に特定できる
- PDF 生成が tier2 の帳票 API に委譲され、UI は帳票パラメータを渡すのみに責務が限定される

## Trigger（発火条件）

業務担当者が検査票 / 図面 / 受注書などを upload / download する帳票 UX を実装する時。

## 想定頻度 / 典型きっかけ

想定頻度: 月次。典型きっかけ: 「品質検査票の PDF 添付 / 閲覧機能が新設され、Object Storage 経由の signed URL 表示と virus scan 連携が必要になった」

## 主役 / 関与者

- **主役**: tier3 担当者（ジュニア級）
- **関与**: tier2 担当者（添付帳票 API）/ dual reviewer

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|---|---|---|---|---|
| 主役（tier3）| ジュニア | 本社 IT 室 / リモート | GitHub PR / Playwright CI | signed URL 取得 / chunk upload / sandbox iframe / aria-live 実装 / E2E テスト |
| 関与（tier2）| 中堅 | 本社 IT 室 | Backstage Catalog | 添付帳票 API 仕様提供 / virus scan pipeline 確認 / retention policy 確認 / sign-off |
| 承認（dual reviewer）| 中堅〜シニア | 本社 IT 室 / リモート | GitHub PR | 直接 upload 禁止 / scan 未完露出禁止 / a11y green 確認 / sign-off |

## 個人 KPI / 達成感

- 帳票フォーマット適合仕様 green が CI で確認でき、規制対応完了の達成感を定量的に得られる
- 全帳票の Playwright E2E green で実装完了を確認できる

## 工数 / 関与人数 / コスト感

- 工数: 1〜2 日（テンプレート統合 4h + パラメータ設計 2h + E2E 4h）
- 関与人数: 3 名（tier3・tier2・dual reviewer）
- コスト感: 低〜中。テンプレートが定型レイアウトを集約するため個別実装コストが大幅削減される

## 前提

- tier2 の添付帳票 API（Object Storage signed URL + envelope 暗号化）が利用可能
- Object Storage は Rook+Ceph で tier1 側に設定済み
- virus scan pipeline が tier2 側で自動実行される
- （責務境界: [README 重要原則](./README.md#重要原則-tier3-が所有するもの--所有しないもの) を参照）

## 流れ

1. tier2 の添付帳票 API（Object Storage signed URL + envelope 暗号化）から URL を取得
2. upload: browser の File API で chunk upload → tier2 API 経由で Object Storage（Rook+Ceph）に PUT（直接 upload 禁止）
3. download: signed URL を iframe sandbox 内で表示（ダウンロードリンクは `sandbox="allow-downloads"` 付き sandbox iframe）
4. virus scan 完了フラグ確認: tier2 が scan 済みにしてから URL が有効化されるため、scan 中は progress indicator を表示
5. PII 含むファイル: tier2 の retention policy（保持期間）を UI で表示
6. a11y: ファイル選択・進捗・完了 / エラーを aria-live で通知
7. Playwright E2E test: upload → scan 完了 → download / upload fail → retry
8. dual reviewer sign-off

| 0 | tier3 担当者 | 帳票テンプレート一覧を Backstage Catalog で確認し対象テンプレートを選択 | `帳票テンプレート選択完了 / 規制パラメータ確認` |
| 4h | tier3 担当者 | 帳票パラメータを tier2 API に渡す UI を実装 | `帳票 UI 実装完了 / パラメータ設計確定` |
| 1d | tier3 担当者 | E2E で帳票生成・ダウンロード・フォーマット検証を green にし PR 提出 | `帳票 E2E green / PR #NNN 提出` |
| 1d+4h | dual reviewer | 帳票フォーマットと適合仕様 green を確認し sign-off | `sign-off 完了` |

## 業界 9 業務との紐付け

- **品質検査結果**: 品質検査票 PDF の upload / download が主要ユースケースであり、virus scan + signed URL による安全な帳票取り扱い UX が検査結果の法的保全を支える
- **受注**: 受注書・出荷確認書などの帳票添付が受注業務の完結に必要であり、本シナリオの UX が受注フローに組み込まれる

## 期待結果 / 観測指標

- Object Storage への直接 upload が 0 件（全て tier2 API 経由）
- virus scan 完了前に signed URL が露出しない
- aria-live による a11y 通知が axe-core で green
- Playwright E2E: 全シナリオ green
- dual reviewer 2 名 sign-off 完了

## 失敗時の挙動 / escalation

- Object Storage への直接 upload を lint が検出 → merge 阻止。**escalate 先**: security 担当者に Mattermost `#security-review` で報告（**SLA**: 2h 以内）。**runbook**: Backstage runbook `direct-storage-upload-violation` を参照
- virus scan 未完了の URL 表示 → E2E で検出 → merge 阻止。**escalate 先**: tier2 担当者に Mattermost `#tier3-contract-fail` で virus scan pipeline 状態確認（**SLA**: 24h 以内）
- `unsafe-inline` で iframe が実行可能 → merge 阻止、CSP を強化。**escalate 先**: security 担当者に Mattermost `#security-review` で確認（**SLA**: 2h 以内）
- retention policy 未表示 → **escalate 先**: tier2 担当者に Mattermost `#tier3-contract-fail` で API レスポンス仕様確認を依頼（**SLA**: 24h 以内）

## 失敗パターン (anti-pattern)

- レイアウト hardcode: テンプレートを使わず CSS / HTML で帳票を直接実装すると帳票フォーマット CI が drift を検知する
- PDF 生成を UI に実装: PDF 生成ロジックを tier3 に持ち込むと boundary check CI が tier2 委譲違反を検知する
