# 新業務画面追加

## 一文方針

tier2 の新 API または業務担当者からの要求を起点に、Backstage Software Template を用いて新業務画面を追加し、contract test・a11y・Web Vitals の全 CI が green になるまで dual reviewer sign-off を受けない。

> 朝 9 時、本社 IT 室の tier3 担当者（ジュニア級）が GitHub PR ダッシュボードで「FA 生産指示画面の Backstage Template 生成完了」通知に気付く。手元には Backstage TechDocs と VSCode、Mattermost 越しに tier2 担当者（API 設計）と dual reviewer がいる。

## ペルソナ要約

主役: tier3 担当者（ジュニア級）、目的: 新業務画面を 13 層強制機構のガードレール下で追加する

## 現状業務での痛み

- 業務ロジックを UI コンポーネントに直書きしてモノリス化し、tier2 との責務境界が曖昧になる
- Backstage Template なしで手作りしたため、contract test・a11y テストが後から追加できず技術負債化する
- フォームバリデーションを client-side のみで実装し、server-side との二重管理が生じる
- 認証 token を tier3 自体が保持する設計になり、セキュリティホールが生まれる

## k1s0 でこう変わる

- Backstage Software Template が 13 層強制機構・contract test・a11y テストを自動組込みし、責務境界を物理強制する
- generated stub を通じて型安全に API クライアントを取得し、独自 type 定義が禁止されモノリス化を防ぐ
- client-side validation を UX 補助に限定し server-side が確定的判断を担う設計が Template で強制される
- BFF 経由で token を受け取る設計が Template に組み込まれ、tier3 が token を保持しないことを CI で検証する

## Trigger（発火条件）

業務担当者からの要求または tier2 新 API 追加を受けて新業務画面を実装する必要が生じた時。

## 想定頻度 / 典型きっかけ

想定頻度: 月次〜週次。典型きっかけ: 「製造ラインの FA 生産指示画面が新設され、Backstage Template から tier3 プロジェクトを生成して実装を開始した」

## 主役 / 関与者

- **主役**: tier3 担当者（ジュニア級）
- **関与**: tier2 担当者（API 設計）/ dual reviewer

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|---|---|---|---|---|
| 主役（tier3）| ジュニア | 本社 IT 室 / リモート | GitHub PR / Mattermost | Backstage Template 生成 / UI 実装 / Playwright E2E / PR 提出 |
| 関与（tier2）| 中堅 | 本社 IT 室 | Backstage Catalog | generated stub 提供 / contract 仕様確認 / sign-off |
| 承認（dual reviewer）| 中堅〜シニア | 本社 IT 室 / リモート | GitHub PR | contract test + a11y + Web Vitals 全 green 確認 / sign-off |

## 個人 KPI / 達成感

- contract test・a11y・Web Vitals の全 CI が green になるまで dual reviewer sign-off を取得できない → 品質ゲートが可視化される
- Backstage Template 生成から PR merge までの所要時間を計測でき、個人の実装速度が定量化される
- axe-core WCAG 2.1 AA 違反 0 件を達成することで a11y 対応の完了感を得られる

## 工数 / 関与人数 / コスト感

- 工数: 1〜3 日（Template 生成 1h + 実装 1〜2d + E2E test 4h）
- 関与人数: 3 名（tier3 担当者・tier2 担当者・dual reviewer）
- コスト感: 低〜中。Template が定型作業を自動化するためジュニアでも完結できる

## 前提

- Backstage Software Template で tier3 リポジトリ生成済み（[13 層強制機構](../../../04_詳細設計/02_強制機構/03_tier3強制機構.md) + contract test が自動組込済み）
- tier2 が対応 API の generated stub（TypeScript）を提供済み
- （責務境界: [README 重要原則](./README.md#重要原則-tier3-が所有するもの--所有しないもの) を参照）

## 流れ

1. Backstage Software Template から画面 template を生成（Section / Step / Wizard の 3 フォームレイアウトから選択）
2. tier2 generated stub（TypeScript）から API クライアントを取得し、独自 type 定義は禁止
3. フォームバリデーション: client-side は UX 補助のみ、server-side validation は tier2 が確定的
4. IME 対応 / a11y（WCAG 2.1 AA / axe-core / aria-label）を Backstage template のデフォルトで確保
5. 業務エラー（BusinessConflict subtype 等）の UX 分岐を `13_業務エラーUX.md` 規約に従って実装
6. 状態遷移 UI: tier2 が許可する遷移のみ button を activate、禁止遷移は deactivate（認可 cache 禁止）
7. [4 layer client state](../../../04_詳細設計/01_適合仕様/11_クライアント状態適合仕様.md) の Server Truth / Optimistic Local / Pending Queue / Draft を適切に使い分け
8. [BFF](../../../04_詳細設計/03_クロスカッティング適合仕様/06_BFF_auth_edge.md) 経由で認証 token を受け取り、tier3 が token を保持しないことを確認
9. Playwright E2E test + axe-core a11y test を追加し CI green
10. Web Vitals（LCP / INP / CLS）閾値確認
11. dual reviewer sign-off（契約 test + a11y + Web Vitals 全 green）

## 業界 9 業務との紐付け

- **FA 生産指示・設備操作**: 本シナリオで追加する FA 生産指示画面が、製造ラインへの生産指示操作の入力 UI を直接担う
- **ライン稼働監視・進捗実績**: 新画面に稼働状況サマリ widget を組み込む場合、ライン進捗をリアルタイムで可視化する起点となる
- **受注**: 受注確認 / 製造指示起票など、受注から製造への橋渡し画面として新業務画面が機能するケースが多い

## 期待結果 / 観測指標

- Playwright E2E: 全シナリオ green
- axe-core: WCAG 2.1 AA 違反 0 件
- Web Vitals: LCP ≤ 2.5s / INP ≤ 200ms / CLS ≤ 0.1
- contract test: tier2 API との contract 全 pass
- dual reviewer 2 名 sign-off 完了

## 失敗時の挙動 / escalation

- contract test fail → merge 阻止。**escalate 先**: tier2 担当者に Mattermost `#tier3-contract-fail` で連絡し API 修正依頼（**SLA**: 24h 以内）。merge 阻止は解除されない。**runbook**: Backstage runbook `contract-test-fail` を参照
- a11y 違反 → merge 阻止、`08_a11y_i18n修正.md` のフローに従い修正。**escalate 先**: デザインシステム担当者に Mattermost `#a11y-fail` で連絡（**SLA**: 24h 以内）
- CSP `unsafe-inline` 検出 → merge 阻止、nonce / hash 方式へ切り替え。**escalate 先**: security 担当者に `#security-review` で確認（**SLA**: 24h 以内）
- Web Vitals 閾値超過 → merge 阻止、ボトルネックを特定して最適化。**escalate 先**: tier2 / tier1 担当者に `#perf-review` で相談（**SLA**: 48h 以内）

## 失敗パターン (anti-pattern)

- 業務ロジックを UI に書く: tier2 generated stub を迂回して独自 type や fetch を実装すると contract test が検知し merge 阻止される
- token を tier3 で保持: BFF を迂回して token を localStorage に保存すると CSP / security CI が検知する
- a11y を後回しにする: axe-core が CI で必須のため後から一括修正すると工数が倍増する
