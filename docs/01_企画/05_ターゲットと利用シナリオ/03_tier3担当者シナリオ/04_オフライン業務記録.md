# オフライン業務記録

## 一文方針

工場現場など 25h オフライン業務を想定し、PWA + IndexedDB（AES-256-GCM 暗号化）と Pending Queue で操作を蓄積し、復帰後に BusinessConflict を正確に UI で提示することで業務担当者がデータ損失なく記録を完了できるようにする。

## Trigger（発火条件）

工場現場の検査担当など 25h オフライン業務が想定される場面でオフライン対応機能を実装する時。

## 想定頻度 / 典型きっかけ

想定頻度: 四半期〜年次。典型きっかけ: 「検査担当が工場地下（WiFi 圏外）で 5 件の品質検査を記録してから WiFi 復帰後に sync する運用が標準化された」

## 主役 / 関与者

- **主役**: tier3 担当者（ジュニア級）
- **関与**: tier2 担当者（Idempotency-Key TTL / conflict 仕様）/ dual reviewer

## 前提

- [4 layer client state](../../../04_詳細設計/01_適合仕様/11_クライアント状態適合仕様.md)（Server Truth / Optimistic Local / Pending Queue / Draft）が設計方針で確立済み
- IndexedDB encrypted（AES-256-GCM）/ PWA が設計方針で確立済み
- Idempotency-Key TTL は 24h（25h を超えてオフラインになると TTL 超過となる）が tier2 で規定済み
- （責務境界: [README 重要原則](./README.md#重要原則-tier3-が所有するもの--所有しないもの) を参照）

## 流れ

1. PWA service worker で offline fallback を設定（Cache API + Background Sync API）
2. Draft 状態を IndexedDB（AES-256-GCM 暗号化済み）に書き込む（PII を平文で localStorage / sessionStorage に保管しない）
3. Pending Queue で操作を蓄積し、Idempotency-Key を付与（TTL = 24h を超えて 25h オフラインになった場合に TTL 超過となるため user 確認フローを実装）
4. Idempotency-Key TTL 超過: user に「再送しますか / 破棄しますか」を確認してから新 key で resend
5. 復帰後の Server Truth との整合: stale_write 検出時は BusinessConflict UI を表示（`02_業務エラーUX_1対1分岐.md` のフロー適用）
6. Playwright E2E: offline → 5 件記録 → online 復帰 → 全件 sync → server 確認
7. dual reviewer sign-off

## 期待結果 / 観測指標

- オフライン中に Idempotency-Key TTL（24h）の範囲内で操作を Pending Queue に保持できる（25h を超えると TTL 超過となり user 確認が必要）
- 復帰後に全件 sync が完了し、server データと一致
- stale_write 発生時に BusinessConflict UI が正しく表示される
- Playwright E2E: 全フロー green
- dual reviewer 2 名 sign-off 完了

## 失敗時の挙動 / escalation

- IndexedDB 非暗号化のまま PII 書き込み → [13 層強制機構](../../../04_詳細設計/02_強制機構/03_tier3強制機構.md)で PII 保管禁止 lint fail → merge 阻止。**escalate 先**: security 担当者に Mattermost `#security-review` で報告（**SLA**: 2h 以内）。**runbook**: Backstage runbook `pii-storage-violation` を参照
- localStorage / sessionStorage への PII 書き込み → lint で検出 → merge 阻止。**escalate 先**: security 担当者に Mattermost `#security-review` で報告（**SLA**: 2h 以内）
- TTL 超過後の自動再送（user 確認なし）→ E2E で検出 → merge 阻止。**escalate 先**: tier2 担当者に Mattermost `#tier3-contract-fail` で TTL 仕様確認（**SLA**: 24h 以内）
