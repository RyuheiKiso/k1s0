# 業界中立性違反検出 是正

## 一文方針

CI の業界中立性 lint が fail した際、違反箇所を種別（型定義 / API 引数 / DB schema / Domain Event schema）に分類し、降格・抽象化昇格・隔離のいずれかで是正して stub conformance CI まで green にする。

> 朝 10 時、本社 IT 室の tier2 担当者（中堅級）が Mattermost `#tier2-ci-alert` で業界中立性 lint fail の自動通知に気付く。手元には lint レポート・GitHub PR、Mattermost 越しに dual reviewer の tier2 担当者がいる。

## ペルソナ要約

主役: tier2 担当者（中堅級）、目的: CI の業界中立性 lint fail を起点に違反箇所を種別分類し降格・抽象化昇格・隔離のいずれかで是正して stub conformance CI まで green にする

## 現状業務での痛み

- 業界固有概念が業界横断層に混入していても CI なしでは担当者の気付きに依存し、発覚が後の設計レビューか本番障害になる
- 是正方法（降格 / 抽象化昇格 / 隔離）の選択基準が明確でなく、担当者によって対処方針がブレる
- 是正 PR を出しても第二業界 stub conformance CI を確認しないままが merge されることがある
- 抽象化昇格による業界横断層 API の breaking change が見落とされて consumer に影響する

## k1s0 でこう変わる

- 業界中立性 lint が CI に組み込まれ、違反 PR を自動検出して `#tier2-ci-alert` に通知する
- 是正方法の選択基準（型定義 → 降格、API 引数 → 隔離、DB schema → expand-contract）が明文化される
- 第二業界 stub conformance CI が是正後の green を merge 条件として強制する
- Backstage runbook に是正手順が整備され、担当者が変わっても同一品質で対処できる

## Trigger（発火条件）

CI の業界中立性 lint が fail した（業界横断層に業界固有概念が混入した）時。

## 想定頻度 / 典型きっかけ

- 想定頻度: イベント駆動（CI fail 時）
- 典型きっかけ: 「'設備 ID' という製造業固有フィールドが業界横断の通知スキーマに混入し lint が fail した」
- 典型きっかけ 2: 「`CrossIndustryNotificationV1` proto に `equipment_id`（製造業固有）が混入し lint が fail した」

## 主役 / 関与者

- 主役: tier2 担当者（中堅級）
- 承認: dual reviewer（tier2 担当者 2 名、変更 PR の author 不可）

| 役割 | 級 | 主に居る場所 | 朝最初に見る画面 | このシナリオでの主要動作 |
|---|---|---|---|---|
| 主役（tier2）| 中堅 | 本社 IT 室 | Mattermost `#tier2-ci-alert` / GitHub PR | lint 違反特定 / 是正 PR 作成 / stub conformance 確認 |
| 承認（dual reviewer）| 中堅〜シニア | 本社 / リモート | GitHub PR | 是正内容レビュー / sign-off（author 不可） |

## 個人 KPI / 達成感

- 業界中立性 lint green（是正完了）
- stub conformance CI green（是正後の業界横断 API が第二業界 stub から消費可能）
- 業界固有 pack の contract test が是正後も引き続き green
- dual reviewer 応答時間 ≤ 24h

## 工数 / 関与人数 / コスト感

- 初回（単純な降格・隔離）: 2〜4h、関与 3 名（主役 + dual reviewer 2 名）
- 平常（抽象化昇格・DB schema 移動）: 1〜2 日、関与 3〜4 名（+ tier1 担当者 1 名）
- 失敗時（抽象化昇格で breaking change 発生）: +1 日、関与 4 名

## 前提

- 業界中立性 lint が CI に組み込まれていること
- 第二業界 stub（CI 専用）が存在し、業界横断層 API の消費テストに使用されていること
- 4 抽象化レベル（業界横断 / 業界共通 / 業界固有 / テナント固有）の定義が合意済みであること

## 流れ

1. lint レポートから違反箇所（どの型 / API / スキーマが業界固有概念を業界横断層に配置しているか）を特定する
2. 違反種別を分類する: 型定義 / API 引数 / DB schema / Domain Event schema のいずれか
3. 是正方法を選択する
   - a) 業界固有 Lv へ降格: 業界固有概念をそのまま業界固有 pack 内に移動する
   - b) 業界横断概念に抽象化して昇格: 業界を横断して成立する抽象概念に置き換えた上で業界横断層に配置する
   - c) 業界 pack 内に隔離: 業界横断層から参照を断ち切り業界 pack 内で完結させる
   - 型定義違反 → (a) 業界固有 Lv へ降格、または (b) 業界横断概念に抽象化昇格（同型 API が stub から消費可能か確認）
   - API 引数違反 → (c) 業界 pack 内に隔離（業界横断 API から業界固有フィールドを除去）
   - DB schema 違反 → (b) 業界横断テーブルから業界 pack テーブルに移動（expand-contract pattern 適用）
4. 是正 PR を作成し業界中立性 lint を再実行する
5. 第二業界 stub（CI 専用）でも変更後 API が消費可能であることを確認する
6. dual reviewer sign-off を得てから merge する

| T+ | actor | action | 通知例 |

## 業界 9 業務との紐付け

- **SCADA テレメトリ**: 業界横断通知スキーマに製造業固有フィールドが混入すると SCADA テレメトリ連携が他業界で動作しなくなるため、是正により業界中立性を回復する。
- **受注**: 受注 API の引数に製造業固有概念が混入した場合、是正により受注 API が他業界 pack でも利用可能になる。
- **図面 review**: 業界横断 Proto に製造業固有の図面フィールドが混入した際に隔離することで、他業界の図面 review フローへの影響を防ぐ。

## 期待結果 / 観測指標

- 業界中立性 lint が green になること
- stub conformance CI が green になること
- 業界横断層 API が第二業界 stub からも問題なく消費できること
- 是正後に業界固有 pack の contract test が引き続き green であること

## 失敗時の挙動 / escalation

- **CI 業界中立性 lint fail（是正なし merge 試行）**: 違反修正 PR が出るまで merge 不可。escalate 先: Mattermost `#tier2-ci-alert` に自動通知（SLA: 24h 以内に是正 PR を提出）。runbook: Backstage `industry-neutrality-fix`
- **抽象化昇格による業界横断層 API breaking change**: スキーマ進化適合仕様の手順に従い backward compatibility を確保する。escalate 先: Mattermost `#tier2-ci-alert`（SLA: 48h 以内に是正 PR 提出）。runbook: Backstage `industry-neutrality-violation-procedure`
- **第二業界 stub conformance fail（是正後）**: stub 側の API 同型性が未達と判断し tier2 担当者が API 設計を見直す。escalate 先: Mattermost `#tier2-ci-alert`（SLA: 48h 以内）。runbook: Backstage `industry-neutrality-violation-procedure`

## 失敗パターン (anti-pattern)

- **違反種別を特定せずに「とりあえず移動」**: 降格すべき概念を抽象化昇格してしまい、本来業界固有であった概念が誤って業界横断層に定着する。lint レポートから違反種別（型定義 / API 引数 / DB schema / Domain Event schema）を正確に分類してから是正方針を決定する。
- **是正後に stub conformance CI を確認しない**: 業界横断 API の変更が第二業界 stub から消費できない状態になっていても気付かずに merge される。stub conformance CI を是正 PR の必須 CI check として追加する。
- **抽象化昇格で consumer の breaking change を無視**: 業界横断層 API が変わって既存 consumer が壊れてから発覚する。抽象化昇格の場合はスキーマ進化適合仕様の手順に従い backward compatibility を担保してから is PR を作成する。
