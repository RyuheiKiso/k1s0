# 外部システム統合

## 一文方針

既存基幹システム（ERP / MES / SCADA / 検査機器）との新規連携を追加する際、連携方式の判定・External Proto 差分検査・Outbox 経由の内部 Domain Event 変換・circuit breaker 宣言・分散トレース伝播確認を全て通過させてから merge する。

> 朝 11 時、本社 IT 室の tier2 担当者（中堅級）が Backstage Software Catalog で SAP ERP 連携の新規要求チケットを開く。手元には External Proto 定義ファイル・Jaeger v2 ダッシュボード、Mattermost 越しに tier1 担当者がいる。

## ペルソナ要約

主役: tier2 担当者（中堅級）、目的: 基幹システム（ERP/MES/SCADA）との新規連携を External Proto 差分検査・Outbox 変換・circuit breaker 宣言・分散トレース伝播確認を全て通過させて merge する

## 現状業務での痛み

- 外部システムからのデータが Outbox を経由せず直接 DB に書き込まれ、Domain Event が発行されない経路が生まれる
- circuit breaker が設定されておらず外部システムの SLA 劣化が内部 SLO に直接波及する
- 外部システムの trace_id が内部トレースと切断され、障害時の end-to-end 追跡ができない
- 認証方式が外部システムごとに異なり、個別実装が散在して統一的な管理が困難になる

## k1s0 でこう変わる

- Outbox 経由の内部 Domain Event 変換を必須とし、外部システムからの直接 DB 書き込みを tier2 強制機構で物理拒否する
- circuit breaker / retry policy を tier1 Library 設定で宣言し、外部 SLA が内部 SLO に波及するリスクを構造的に排除する
- trace_id 伝播を Jaeger v2 で確認し、end-to-end の分散トレースを外部システム連携を超えて連続させる
- tier1 Auth Library が外部認証方式を吸収し、API Key / OAuth 2.0 / federated IdP の差異を統一的に管理する

## Trigger（発火条件）

既存基幹システム（ERP / MES / SCADA / 検査機器）との新規連携が要求された時。

## 想定頻度 / 典型きっかけ

- 想定頻度: 年次〜不定期
- 典型きっかけ: 「既存 ERP（SAP）との受注 sub 連携が新設され、External Proto の設計と Outbox 経由連携の実装が必要になった」
- 典型きっかけ 2: 「SAP ECC 6.0 の IDoc（ORDERS05）を External Proto に変換し、Outbox relay 経由で内部 Domain Event に変換する連携を追加した」

- 関与: tier1 担当者（Auth Library / circuit breaker / retry policy 設定の整合確認）
- 承認: dual reviewer（tier2 担当者 2 名、変更 PR の author 不可）

## 個人 KPI / 達成感

- External/Internal 二層差分検査 CI green
- 外部システムからのデータが Outbox 経由で内部 Domain Event に変換されること（直接 DB 書き込み 0 件）
- trace_id が Jaeger v2 で外部から内部まで一貫して伝播
- circuit breaker / retry policy が `slo_catalog.lock.yaml` に宣言済み

## 工数 / 関与人数 / コスト感

- 初回: 3〜5 日（連携方式判定・External Proto 追加・Outbox 変換実装・circuit breaker・Testcontainers）、関与 4〜5 名（主役 + tier1 担当者 + dual reviewer 2 名）
- 平常（既存連携への endpoint 追加）: 1〜2 日、関与 3〜4 名
- 失敗時（直接 DB 書き込み検出・circuit breaker 未設定による SLO 波及）: +1 日、関与 5 名（+ security 担当者）

## 前提

- External / Internal 二層の Proto 設計が確立済みであること
- Outbox relay（Sidecar）が稼働済みであること
- tier1 Auth Library が外部認証方式の吸収に対応していること
- 分散トレース基盤（Jaeger v2）が稼働済みであること

## 流れ

1. 連携方式を判定する: External Proto 経由 / Webhook / Companion Transport / token exchange（[v1_federated_exchange](../../../03_概要設計/07_security設計方針/README.md)）
2. External Proto を追加し、External / Internal 二層の差分検査 CI を通過させる
3. 外部システム側の認証方式（API Key / OAuth 2.0 client credentials / federated IdP）を確認し、tier1 Auth Library で吸収する
4. 外部システムからのデータは必ず Outbox を経由して内部 Domain Event に変換する（直接 DB 書き込み経路を持たない）
5. 外部システムの SLA（可用性 / latency）が internal SLO に影響するため、circuit breaker / retry policy を tier1 Library 設定で宣言する
   - tier1 Library の RPC カテゴリ設定（`k1s0_config.toml` or `appsettings.json`）で `circuit_breaker_threshold` と `retry_count` を指定
   - 外部システムの SLA（例: 99.0% / 500ms）を threshold として設定
   - tier1 Library の SLO カタログ（`slo_catalog.lock.yaml`）に外部 SLI を追記
6. 外部連携の trace_id が分散トレースに伝播することを Jaeger v2 で確認する
7. dual reviewer sign-off + Testcontainers green（外部システム stub 版）を確認してから merge する

## 業界 9 業務との紐付け

- **受注**: SAP ERP（ORDERS05 IDoc）との受注連携が Outbox 経由の内部 Domain Event に変換され、受注業務の自動化が実現する。
- **SCADA テレメトリ**: SCADA システムとの連携を External Proto 経由で追加することで、テレメトリデータがリアルタイムに内部 Domain Event へ変換される。
- **図面 review**: MES・CAD システムとの連携追加により、図面 review フローへの設計変更通知が自動化される。
- **品質検査結果**: 検査機器の測定データを External Proto で受信し、品質検査結果 aggregate に自動反映する。

## 失敗時の挙動 / escalation

- **External / Internal 差分検査 CI fail**: Proto の二層分離が不十分と判断し設計を見直す。escalate 先: Mattermost `#tier2-ci-alert`（SLA: 24h 以内に是正 PR 提出）。runbook: Backstage `external-system-integration-procedure`
- **外部システム直接 DB 書き込み経路検出**: tier2 強制機構違反として即時修正し security 担当に報告する。escalate 先: Mattermost `#security-incident`（SLA: 1h 以内に security 担当者へ連絡）。runbook: Backstage `external-system-integration-procedure`
- **Testcontainers fail**: stub との API 同型性または Outbox 変換ロジックの不備として tier2 担当者が修正する。escalate 先: Mattermost `#tier2-ci-alert`（SLA: 24h 以内に是正 PR 提出）。runbook: Backstage `external-system-integration-procedure`
- **circuit breaker 未宣言で外部 SLA 劣化が内部 SLO に波及**: tier1 担当者と連携して circuit breaker を即時追加する。escalate 先: Mattermost `#tier2-incident`（SLA: 即時対応、tier1 担当者と協働）。runbook: Backstage `external-system-integration-procedure`

## 失敗パターン (anti-pattern)

- **外部システムからのデータを直接 DB に書き込む**: Domain Event が発行されず、下流 aggregate / read model への伝播が断絶する。外部システムからのデータは必ず Outbox を経由して内部 Domain Event に変換することを tier2 強制機構で物理的に強制する。
- **circuit breaker なしで外部 API に直接接続**: 外部システムの SLA が劣化すると内部 SLO がそのまま影響を受け、tier2 全体の可用性が落ちる。外部連携追加時には circuit breaker / retry policy の `slo_catalog.lock.yaml` 宣言を merge の必須条件とする。
- **trace_id を外部システム境界で切断**: 障害時に外部システムと内部どちらで問題が起きているかを特定できなくなる。Jaeger v2 での trace_id 伝播確認を Testcontainers と並行して merge 条件に設定し、trace 連続性を担保する。
