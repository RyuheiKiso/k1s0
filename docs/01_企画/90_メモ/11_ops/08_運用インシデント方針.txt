============================================================
ops 運用インシデント方針
============================================================

■ 一文方針
  - 運用 incident（SLO 違反 / capacity 違反 / change 起因
    failure / dependency outage / drill failure 等の non-
    security incident）の lifecycle は incident_lifecycle.
    lock.yaml に build artifact として固定し、5 phase
    （detect / triage / mitigate / resolve / postmortem）
    全てに物理 action 経路と SLA を必須化、phase 不通過の
    incident は CI で覆面検出 + admission block する。

■ incident class（5 class、operational signal 別）
  - v1_slo_breach：
        - 13 SLO の error budget burn rate ≥ 6x（fast or
          slow window）で発火
        - 例：tier1 latency / data durability / replication
          lag / patch window compliance / topology drift
  - v1_capacity_breach：
        - per_tenant_volume / cluster headroom / partition
          capacity の hard threshold 違反
        - 例：CPU/memory headroom 0% / NodeNotReady / per-
          tenant noisy neighbor
  - v1_change_induced：
        - deploy / migration / canary / topology change
          直後の SLO 急変
        - 例：canary AnalysisTemplate fail / migration pair
          切替後の latency 急増
  - v1_dependency_outage：
        - 上位 / 下位 service / 外部 SaaS / IDP / DNS の
          unavailability
        - 例：Keycloak unreachable / external CA outage /
          Harbor pull failure
  - v1_drill_failure：
        - chaos drill / restore drill / red team drill で
          想定外 failure mode に到達
        - 例：restore RTO 越え / chaos zone partition 中の
          quorum loss

  - security incident（threat detect 由来）は 10_security/
    11_インシデント対応方針 が primary、ops は triage 後
    operational impact phase（containment 後の SLO 復旧 /
    capacity 再配分）の loop entry のみを bridge で受ける。

■ incident lifecycle（5 phase、SLA 付）
  - phase 1：detect
        - alert 発火 → Grafana OnCall page → primary
          on-call ack
        - SLA：page → ack ≤ 5 分（severity_freeze 時 ≤ 3 分）
        - 物理発火：Alertmanager → Grafana OnCall webhook
        - artifact：alert_event row in ClickHouse
  - phase 2：triage
        - on-call が ack 後 30 分以内に incident class
          確定 + Mattermost incident channel 起票 + IR
          ticket（incident.io OSS or GitHub Issue）作成
        - SLA：ack → triage 完了 ≤ 30 分
        - 物理発火：Mattermost slash command → incident.io
          OSS API → GitHub Issue
        - artifact：incident_event row（incident_id /
          class / severity / impacted_slo / impacted_
          tenant / suspected_cause）
  - phase 3：mitigate
        - 即時対処（auto rollback / manual rollback /
          throttle / freeze / runbook 起動）
        - SLA：triage → mitigation 開始 ≤ 5 分（severity
          freeze 時）、≤ 15 分（severity page 時）
        - 物理発火：Argo Rollouts auto rollback / Tekton
          Pipeline runbook / Kyverno freeze policy /
          break-glass token
        - artifact：mitigation_event row（action / actor
          / runbook_ref / outcome）
  - phase 4：resolve
        - SLO budget 復活 / capacity 平常化 / customer
          impact 終了の確認 → incident close
        - SLA：detect → resolve total（MTTR）SLO 別 target
          v1_mttr_slo_p95（class 別、v1_slo_breach は ≤ 2h
          / v1_capacity_breach ≤ 1h / v1_change_induced
          ≤ 30min auto rollback / v1_dependency_outage
          ≤ 4h / v1_drill_failure ≤ 1h）
        - 物理発火：incident.io OSS resolve / GitHub Issue
          close
        - artifact：resolve_event row（resolution_time /
          mttr / customer_impact_minutes）
  - phase 5：postmortem
        - resolve 後 72h 以内に postmortem PR 起票必須、
          merged まで関連 namespace の deploy が Kyverno
          で物理 block
        - SLA：resolve → postmortem PR open ≤ 72h、open
          → merged ≤ 14 日
        - 物理発火：09_ポストモーテム方針 と双方向 lock
        - artifact：postmortem PR + action_item issues

  - 各 phase の SLA 違反は CI で覆面検出（postmortem_
    pending / mitigation_overdue 等）、incident 関連 service
    の deploy は Kyverno で block。

■ incident command roles（4 役割）
  - incident commander（IC）：
        - on-call primary が default、複雑化時 ops lead が
          引継
        - decision authority、外部 communication 統制
  - communications lead（CL）：
        - Mattermost incident channel + status page
          （internal）の更新を統一
        - 30 分毎の status update を必須化（resolve まで）
  - subject matter expert（SME）：
        - 該当 service / 軸の domain expert（rotation 階層
          3）
        - 技術的 mitigation の意思決定支援
  - scribe：
        - timeline 記録（actions / decisions / hypotheses）
        - postmortem の primary author 候補

  - severity = freeze / security_bridge は 4 役割全員
    必須、page 級 incident は IC + scribe 最低 2 名必須、
    notify 級 ticket は IC のみで close 可能。

■ communication channel（separation of concerns）
  - public（社内）channel：
        - #ops-incident-<service>（Mattermost）：team
          内技術詳細の流通 channel
        - #ops-status-page（Mattermost）：customer 影響の
          ある incident のみ status update（外部公開向け
          internal mirror）
  - 機密 channel：
        - #ops-incident-confidential（Mattermost）：PII
          / security adjacency / legal sensitive な incident
          の内部 communication（10_security/11 と共有）
  - audit_event：
        - 全 channel の activity log は ClickHouse audit
          subject に shipping、retention は preservation_
          class 別に最低 7 年（security 11 と整合）

■ severity matrix（impact × urgency）
  - impact 軸（5 段階）：
        v1_individual_user：単一 user の操作失敗
        v1_tenant_partial：単一 tenant の partial
          functionality loss
        v1_tenant_full：単一 tenant の full outage
        v1_multi_tenant：複数 tenant の全 partial 以上
        v1_global：全 tenant outage / data loss
  - urgency 軸（3 段階）：
        v1_high：即時対応必須（SLO breach phase 4 以上）
        v1_medium：1h 以内対応（phase 3 SLO breach）
        v1_low：next-business-day 対応（informational
                ticket）
  - severity = (impact × urgency) で算出、severity 表は
    incident_severity_matrix.lock.yaml に build artifact
    化、手書き severity 上書きは禁止。

■ incident.io OSS の役割
  - incident.io OSS（minimal 経路）or GitHub Issue を
    primary IR ticket として固定。商用 incident.io 本体の
    SLA / on-call 機能は採用しない（Grafana OnCall で代替、
    04_採用OSS と整合）。
  - 全 incident は incident_id（incident.io OSS UUID or
    GitHub Issue 番号）を必須化、Mattermost channel 名 /
    PR タイトル / postmortem に bind。
  - GitHub Issue 経路（OSS minimal）：
        - Issue label：incident-class:<class> / severity:
          <severity> / status:<phase>
        - Project board：phase 別 column（detect / triage
          / mitigate / resolve / postmortem）
        - automation：Phase 遷移 trigger で関連 Action /
          Tekton Pipeline 起動

■ post-incident invariant
  - active incident（status != resolved）が存在する間、
    関連 namespace への自動 deploy は Argo CD sync wave で
    delay（phase 3 mitigate 中の deploy は break-glass
    のみ）。
  - postmortem PR 未 open（phase 4 resolved → 72h 経過）：
    Kyverno が関連 service の image deploy を block
    （feature flag toggle のみ allow、code change は
    block）。
  - postmortem PR open / unmerged 状態が 14 日以上：service
    全 deploy block（feature flag も含む）。

■ recurrence detection
  - incident.io OSS の similar_incident query で過去 30 日
    の同 incident_class 発生回数を集計、3 回以上は recurrent
    として escalate（quarterly review 必須 + action item
    elevated priority）。
  - recurrent incident の root cause が同一の場合は action
    item の implementation status を ship blocker として
    bind（次の同 cause incident 発生まで deploy block）。

■ 同型構造（13 軸 + meta + security との整合）
  - 6 yaml 単一の真：
        incident_classes.yaml（5 class enum）
        incident_severity_matrix.lock.yaml（build
          artifact、impact × urgency × severity）
        incident_lifecycle.lock.yaml（build artifact、
          5 phase × SLA × physical action）
        incident_role_assignments.lock.yaml（build
          artifact、role ↔ rotation の三項関係）
        incident_history.lock.yaml（build artifact、
          全 incident の 5 phase timestamp + outcome）
        recurrence_table.lock.yaml（build artifact、
          recurrent incident grouping）
  - 5 層 defense-in-depth：incident lifecycle は層 D / E
    に必ず物理 action を持つ（mitigation auto rollback /
    Kyverno freeze policy / postmortem PR block）。
  - CI 不変条件：lifecycle phase coverage / SLA within /
    role assignment full / postmortem ship blocker /
    recurrence action bound 等を CI で物理確認。

■ 採用しない方針
  - 文章 only の incident lifecycle：禁止、5 phase + SLA
    + physical action は build artifact 必須。
  - postmortem skip 経路：禁止、72h SLA + 14 日 merged
    SLA、違反は service deploy block。
  - severity の手動 override：禁止、severity matrix の
    機械算出のみ、override は audit_event 必須の break-
    glass 経路のみ。
  - mitigation の手動 default：auto rollback が default、
    手動 mitigation は break-glass。
  - communication channel の単一化：禁止、public / 機密
    の二系統必須（PII / legal sensitive 分離）。
  - 商用 incident management SaaS（PagerDuty / Opsgenie
    / Squadcast 等の有償 SLA）採用：採用しない、incident.
    io OSS + GitHub Issue + Grafana OnCall で完結。
  - recurrence の文章 only 集計：禁止、recurrence_table.
    lock.yaml が build artifact、3 回 threshold 違反は
    action item ship blocker。
  - incident close を SLO 復活前に行う：禁止、resolved
    判定は SLO budget 復活 + customer impact 終了の物理
    確認（Prometheus query）必須。
