============================================================
ops 位置づけ
============================================================

■ 5 階層 + 横断 layer 中の位置
  - tier1 : システム共通処理（Library / Server / 認証 /
            観測可能性）
  - tier2 : ドメイン業務共通化処理
  - tier3 : 個別業務の Web サイト / exe
  - infra : 物理 / 仮想基盤 + 制御平面
  - data  : データ層（保全 / lifecycle / 暗号化）
  - security : 全層を直交に貫く「脅威 ⊗ 軸 ⊗ 層」
              invariant の管掌 layer
  - ops   : 全層 + security を直交に貫く「loop ⊗ phase
            ⊗ 軸 ⊗ 層」 invariant の管掌 layer ← 本層

  - ops は tier1 / tier2 / tier3 / infra / data / security の
    上下左右に並列して存在するのではなく、6 階層 × 14 軸の
    grid を直交に貫く meta-layer として位置づく。ops は新しい
    責務を宣言するのではなく、既存軸の defense-in-depth 層
    A〜E から発信される全 operational signal が必ず運用 loop
    の closure に到達することを assert する。
  - security が「脅威 × 軸 × 層」の grid に mitigation を
    詰めるのに対し、ops は「signal × phase × 軸 × 層」の
    grid に action を詰める。両者は直交し、security 軸の
    incident（脅威 detect）も ops の loop に entry する。

■ 上下方向の関係
  - 上方向（5 階層 + security が ops に依存する経路）：
      - tier1 観測可能性（09）→ metric / log / trace の
            SoR を ops の alerting pipeline 入力として使用
      - tier1 SLO（13）→ error_budget.lock.yaml が ops
            の budget_action_bindings.lock.yaml に bind、
            burn rate 越え時の freeze / page を物理発火
      - tier1 認証（10）→ on-call rotation の identity
            assertion、step-up auth による break-glass の
            audit_event 経路
      - tier1 鍵管理（11）→ rotation overdue 時の page /
            freeze 経路を ops の alert routing に bind
      - tier1 OSS lifecycle（14）→ critical CVE / EoL の
            page を ops 経由で escalation
      - tier1 capacity（15）→ per_tenant_volume 超過の
            page → throttle runbook 起動を ops が管掌
      - tier2 RLS FORCE（32）→ tenant 越境 detect の
            security incident を ops loop に bridge
      - tier3 client（39）→ client crash rate / reconcile
            failure の operational signal を ops に flow
      - infra topology（infra01）→ topology change の
            change management（rolling drain / canary）を
            ops が管掌
      - data preservation（data01）→ restore_drill の
            cadence violation を ops が page / freeze
      - security（threat 14 軸）→ security incident
        （threat detect）の triage 後 operational
        impact phase は ops loop に entry

  - 下方向（ops が他層に依存する経路）：
      - 物理 enforcement の道具立て：
          - Kyverno admission policy（infra 14）
          - Argo Rollouts（infra 09 GitOps）
          - Argo CD sync wave（infra 09）
          - Perses（tier1/09 / data）
          - ClickHouse（data / tier1/09）
          - Tekton pipeline（infra 04）
          - OpenBao response wrapping（infra 04 + tier1/11）
        は全て他層が提供する。ops は「これらが運用 loop
        中の action 経路として bind されていること」を
        cross-axis assertion で保証するのみ。
      - operational_event の SoR：09 観測可能性 SoR
        （ClickHouse）+ audit_event subject を物理 store
        として共用、ops は ops_event subject schema の
        immutability 規律を宣言。

■ 横方向の関係（ops ↔ 各軸）
  - ops ↔ 07 transport：
      - bidi stream の接続失敗率 / handshake failure を
        SLI として alert、circuit-breaker 起動を runbook
        として codify。
  - ops ↔ 08 migration：
      - migration pair の旧版運用期間（compat window）
        を ops の change management に登録、window
        expiration の page → cutover runbook 起動。
  - ops ↔ 09 observability：
      - alert pipeline / metric ingestion lag を SLI
        として相互観測、ops 自身の visibility を循環
        破綻させない（自己観測 invariant）。
  - ops ↔ 10 auth：
      - login failure rate / token refresh failure rate
        を SLI として alert、credential stuffing detect は
        security に bridge、auth path の latency は ops
        が page。
  - ops ↔ 11 key：
      - rotation overdue / KMS API error rate を SLI、
        rotation 失敗の page → manual rotate runbook 起動。
  - ops ↔ 12 schema：
      - schema migration による backward incompat alert
        を ops の change management に登録、breaking
        判定が出た PR の merge を block。
  - ops ↔ 13 SLO：
      - error_budget.lock.yaml の全 SLO に対して budget_
        action_bindings.lock.yaml で運用 action を bind、
        burn rate threshold 超過時に freeze / page を
        物理発火。13 と本層が双方向 lock。
  - ops ↔ 14 OSS-lifecycle：
      - critical CVE / EoL window の page → patch /
        upgrade runbook 起動、pair_target 移行 progress
        を ops の change management に登録。
  - ops ↔ 15 capacity：
      - noisy neighbor / per_tenant_volume 超過の page →
        throttle / quarantine runbook 起動、capacity
        forecast の breach 予測も ops が page。
  - ops ↔ 32 data-tenant：
      - RLS FORCE bypass detect の security incident を
        ops loop に bridge、tenant 別 isolation breach
        は break-glass を経由して ops が postmortem
        起票必須化。
  - ops ↔ 39 client：
      - client crash rate / sync failure rate を SLI、
        client roll-forward / force-update の change
        management を ops が管掌。
  - ops ↔ infra01 topology：
      - cluster drain / node migration / control-plane
        upgrade の change management を ops が管掌、
        sync wave / rolling order を build artifact 化。
  - ops ↔ data01 preservation：
      - restore_drill / replication_lag の SLO breach を
        ops が page、failover runbook の Tekton job 化、
        crypto-erase の cadence violation も ops が
        freeze。
  - ops ↔ security（threat）：
      - security incident（threat detect）の triage 後
        operational impact phase（containment 後の
        SLO 復旧 / capacity 再配分）は ops loop に entry、
        postmortem は ops + security の二層で必ず merge
        済み（GitHub PR）。
  - ops ↔ security（build_provenance / 10_security/17）：
      - 10_security/17_build_provenance適合仕様 が emit する
        attestation_verify_failure / hermetic_egress_attempt /
        reproducibility_drift event は v1_threat_detect
        signal_class の sub-class `security.build_provenance
        .event` として ops loop に entry。oss.lifecycle.event
        と同型。5 phase（detect / respond / resolve / learn
        / prevent）closure を要求し、postmortem は ops +
        security build_provenance の二層 merge 済み。

■ 14 軸 + meta + security + ops 中の位置
  - ops は 15 軸目の候補として 00_軸登録適合仕様 の
    meta-registry に entry 追加される（cap v1=20 中 17 / 20、
    残 3 余地。ops 15 軸目 + test 16 軸目 + build_provenance
    17 軸目）。
  - 14 軸 + security + build_provenance が「層別 × 機能別 ×
    脅威別 × supply chain 別」軸であるのに対し、ops は
    「signal 別 × phase 別 × 時間軸」軸として直交方向に
    位置する。signal class（observed deviation / SLO breach
    / threat detect / capacity breach / change risk）を class
    軸として持ち、各 class が 5 phase（detect / respond /
    resolve / learn / prevent）の loop closure を要求する
    fan-out 構造を持つ。v1_threat_detect signal_class は
    10_security/17 の attestation_verify_failure event を
    sub-class として消費。
  - 00 meta（軸登録）の release_gate.lock.yaml AND-gate
    に、ops の ops_loop.lock.yaml の `closure_green` 状態
    と toil_reduction.lock.yaml の `monotonic_decrease`
    状態 + 10_security/17 の artifact_inventory.lock.yaml の
    `all_signed_green` + reproducibility_matrix.lock.yaml の
    `consensus_green` が入力される。全 signal class が 5
    phase 全 closure green でない限り、または build provenance
    chain が green でない限り 1.0.0 ship blocker。

■ 至高路線における位置づけの帰結
  - ops は「個別軸の規律を再宣言する layer」ではなく、
    「個別軸の規律から発生する全 operational signal が運用
    loop で必ず closure される」ことを機械検証する meta-
    layer。ops が新規物理機構を持ち込むことは原則しない
    （既存軸の機構を bind するのみ）。例外は alert
    pipeline / progressive delivery / runbook 実行 engine
    のような本質的に cross-axis な道具立てのみ。
  - 運用コスト度外視（CLAUDE.md 上位方針）の哲学に従い、
    operational signal coverage は最大化する。「現実には
    起こりにくいから loop に組み込まない」「page が増える
    から alert を間引く」判断は採らない。signal の重みは
    SLO budget や noise budget で表現するが、loop entry
    自体は省略しない。
  - 1.0.0 完璧 release：5 signal_class（observed deviation
    / SLO breach / threat detect / capacity breach /
    change risk）全てに対し全 14 軸の cross-axis
    operational closure（5 phase 全 green）、postmortem
    backlog ゼロ、toil monotonic decrease 維持、までを
    ship blocker とする。
