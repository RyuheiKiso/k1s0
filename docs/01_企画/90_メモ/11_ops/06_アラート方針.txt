============================================================
ops アラート方針
============================================================

■ 一文方針
  - 全 alert は alert_catalog.lock.yaml に build artifact と
    して固定し、severity / SLO bind / runbook pointer / auto-
    action pointer / noise budget の 5 attribute を必須化、
    page-level alert は actionable のみ、informational alert
    は cap 5% を CI で物理確認、noise budget 違反 alert は
    自動 silence + tuning ticket 化を物理 enforce する。

■ alert class（severity 5 段階、SLO budget action と整合）
  - v1_observe（severity = info）：
        - SLO budget 観測のみ、page しない、Mattermost
          投稿もしない。dashboard 上の status のみ。
        - 例：burn rate < 1x の SLO panel
  - v1_notify（severity = warning）：
        - Mattermost channel に informational 投稿、page
          しない。on-call は確認義務なし、ticket は任意。
        - 例：burn rate ∈ [1x, 6x)
  - v1_page（severity = critical）：
        - Grafana OnCall 経由で primary on-call へ page。
          ack window は 5 分、ack 無き場合 secondary へ
          escalate（07_オンコール方針 と整合）。
        - runbook pointer 必須（page-to-runbook 1:1）、
          runbook 不在 alert は CI fail。
        - 例：burn rate ∈ [6x, 14.4x)
  - v1_freeze（severity = critical-urgent）：
        - page + Kyverno admission policy が関連 namespace
          への deploy を block（除く emergency rollback）。
        - 例：burn rate ≥ 14.4x or budget 残 < 25%
  - v1_security_bridge（severity = critical-security）：
        - security incident（threat detect）の triage 後
          operational impact phase に bridge、ops + security
          の二系統 page。
        - 10_security/11_インシデント対応方針 と双方向 lock。

■ alertable / non-alertable の判定
  - alertable（page 候補）：
        - SLO budget burn rate（短窓 / 長窓 / 中窓）
        - critical infrastructure failure（cluster
          unreachable / control_plane_failure）
        - critical security signal（threat detect、security
          14 で生成、ops に bridge）
        - capacity hard breach（per_tenant_volume / cluster
          headroom 0%）
        - rotation overdue（鍵 / cert / secret）
        - postmortem PR overdue（active incident で 24h
          経過 unmerged）
        - drill cadence overdue（restore_drill / red_team
          / chaos_drill）
        - migration window overdue（compat window expired）
  - non-alertable（page 候補から除外、ticket 経路のみ）：
        - audit log generation（subject 観測 metric）
        - dashboard 自身の load latency
        - log shipping pipeline lag（< threshold 内）
        - single-host CPU spike（noisy neighbor、capacity
          軸が page 候補）
        - test environment failure（dev / stage namespace）

■ alert_catalog.lock.yaml（build artifact）
  - 1 row = (alert_id, severity, slo_bind, runbook_ref,
    auto_action_ref, noise_budget_ratio, mute_window_class,
    description)。
  - severity が v1_page / v1_freeze の場合、runbook_ref
    と auto_action_ref のいずれか必須（runbook なし auto-
    action のみは可、auto-action なし runbook のみは可、
    両方欠落は CI fail）。
  - noise_budget_ratio：30 日 window で false positive 率
    ≤ 5%（page level、informational は cap 不問）。違反は
    auto silence + tuning ticket。
  - mute_window_class：
        v1_no_mute        ：mute 不可（severity = security_
                            bridge / freeze は常時 alert）
        v1_business_hour  ：09:00-18:00 JST のみ alert
                            （batch job 失敗等）
        v1_planned_window ：planned maintenance 期間のみ
                            mute（change management で
                            artifact 化）
  - 文章 only mute（kind: textual）は禁止、CI fail。
    例外：rare exception の comment annotation のみ
    cap 0.5%。

■ noise budget（false positive / negative 抑制）
  - 全 page-level alert に対し 30 日 false positive ratio
    metric を Sloth で物化（page_count / actual_incident_
    count）。
  - threshold：≤ 5% false positive、≤ 1% false negative
    （後者は外部 chaos / red team 演習で計測）。
  - 違反時の処置：
        1. 自動 silence（alertmanager mute）24h
        2. tuning ticket 起票（alert_tuning_backlog.lock
          .yaml に entry 追加）
        3. 翌週の ops review で必須 tuning（threshold
          rebuild / SLO 再 tune / runbook 改善）
        4. 連続 4 週違反は alert を deprecate phase へ
          移行（alert_deprecation.lock.yaml entry）
  - false positive 率の集計は ClickHouse query baseline、
    Grafana dashboard で可視化。

■ alert routing（Alertmanager）
  - 全 alert は Alertmanager の routing tree で 4 層 tag
    分類：
        環境（v1_prod / v1_stage / v1_dev）
        severity（v1_observe〜v1_security_bridge）
        team（service owner、ownership_table.lock.yaml で
              管理）
        signal_class（slo_burn / capacity / rotation /
                      drill_overdue / postmortem_overdue
                      / security_bridge）
  - routing tree の yaml は build artifact、手書き routing
    は CI fail。
  - team ownership table は CODEOWNERS と双方向 lock、
    ownership 未宣言の alert は CI fail（service が deploy
    される前に owner 必須）。
  - silence は audit_event 必須、UI 上の silence は actor /
    reason / expected_duration を必須記録、無 reason silence
    は CI 後追い fail。

■ deduplication / inhibition
  - Alertmanager の inhibition rule で「上位 alert が active
    な間は下位 alert を mute」を build artifact 化。例：
    cluster_unreachable active → 全 service-level alert
    mute（root cause を特定するため）。
  - inhibition rule は ownership / signal_class の対応関係
    に従って generator が自動生成、手書きは cap 5%
    （cross-team complex case のみ）。
  - 同一 alert の重複 page は 5 分以内 1 件に dedup、5 分
    超過分は ack-pending として OnCall に集約 view 表示。

■ paging budget（個人 fatigue 抑制）
  - on-call 1 人あたりの 1 週間 page 数 ≤ 3 件 を SLO 化
    （v1_oncall_page_per_week ≤ 3）。
  - 違反は 07_オンコール方針 の fatigue budget と双方向
    lock、3 件超 1 週間継続は roster の rebalance + alert
    tuning ticket 起票。
  - paging budget は per-individual / per-team の二重
    metric、team budget も SLO 化（v1_team_page_per_week
    threshold は team サイズに比例）。

■ page-to-runbook の 1:1 対応
  - 全 page-level alert は runbook pointer 必須、runbook
    不在は CI fail。
  - runbook pointer は Tekton Pipeline 名 or Backstage
    TechDocs URL の二択、Markdown 単独は cap 5%
    （手作業 step 残存の例外のみ）。
  - 11_runbook方針 の runbook_catalog.lock.yaml と双方向
    lock、alert ⇔ runbook 1:1 で覆われていること。
  - 自動実行可能な runbook（Tekton Pipeline）の場合、
    Alertmanager webhook → Tekton Trigger で auto-
    invoke も併設（人間 ack と並行）。

■ alert lifecycle metric
  - 各 alert に対し以下 metric を ClickHouse に永続：
        firing_count（30d）
        ack_latency_p50/p95/p99（page → ack 時間）
        resolution_latency_p50/p95/p99（page → resolved）
        false_positive_count
        runbook_invocation_count
        auto_action_invocation_count
        postmortem_link_count
  - 上記 metric は 13 SLO の error_budget.lock.yaml に
    operational sub-SLO として登録。

■ 同型構造（13 軸 + meta + security との整合）
  - 6 yaml 単一の真：
        alert_classes.yaml（severity 5 enum）
        alert_catalog.lock.yaml（build artifact、catalog
          完全列挙）
        alert_routing.lock.yaml（build artifact、routing
          tree）
        ownership_table.lock.yaml（build artifact、team
          ↔ alert ↔ runbook 三項関係）
        alert_tuning_backlog.lock.yaml（build artifact、
          noise budget 違反の tuning queue）
        alert_deprecation.lock.yaml（build artifact、
          retire 中 alert の lifecycle）
  - 5 層 defense-in-depth：alert は層 D / E に必ず物理
    action を持つ（runbook / auto-action / freeze）。
  - CI 不変条件：catalog の coverage_full / page_runbook_
    1to1 / noise_budget_within / ownership_full / no_
    textual_only 等を CI で物理確認。

■ 採用しない方針
  - 単窓 alert：MWMBR 必須（05 SLO駆動運用方針 と整合）。
  - runbook なし page：禁止、CI fail。
  - 「とりあえず alert を増やす」運用：禁止、catalog
    entry 追加は noise budget impact 評価（過去 30d の
    類似 firing 履歴）と severity 査定を必須化。
  - 商用 alert SaaS（PagerDuty / VictorOps 商用）：採用
    しない、Alertmanager + Grafana OnCall で完結。
  - alert UI の personalization：禁止、共通 catalog のみ
    （個人別 view は browser 側 query parameter で対応）。
  - silence の無理由実行：禁止、audit_event 必須、reason
    欄空欄は CI 後追い fail。
  - alert を SLO 外で page 化：cap 10%（infrastructure
    例外のみ）、超過は CI fail。
  - false positive を放置：noise budget 違反は強制 tuning、
    放置経路ゼロ。
