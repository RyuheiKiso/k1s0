■ 一文定義
  - 運用ループ適合仕様は、5 signal_class × 5 phase の
    cross-product として完全列挙される ops_loop catalog
    の各 cell に対し、5 action_class のいずれかを必ず物理
    pointer として bind し、全 14 軸（13 軸 + meta + security）
    + 自軸の defense-in-depth 層 D / E に bind 済みであるこ
    とを 5 層 defense-in-depth + 17 項 CI 不変条件 + 15 件
    stress test pack で物理 enforce する meta-axis である。

■ 設計原則
  - signal_class は bundle である。
      yaml に書く ops.signal.* attribute のうち、signal
      _class 1 つの値が他 4 dimension（severity_default
      / window_class_default / paging_budget_weight /
      postmortem_class）を一意に導出する。Library 作者 /
      業務作者 / on-call が dimension を個別に override
      する経路は持たない。
  - dimension override は禁止する。
      「v1_slo_breach のうち paging_budget_weight を緩めた
      い」要望は新 class を切ることで表現する。class 数の
      爆発は意味論の規律として受け入れる。
  - dead spec を CI で殺す。
      classes.yaml に登録された全 class、ops_loop.lock.yaml
      に列挙された全 cell、runbook_catalog.lock.yaml に
      列挙された全 runbook、alert_catalog.lock.yaml に
      列挙された全 alert は、いずれも参照されなくなった
      時点で CI fail とする。service のうち ownership_
      table.lock.yaml に entry が無いものも CI fail
      （ownership 未宣言の deploy を deny by default）。
  - 5 種類 ops orchestrator を全 signal_class に必須化する。
      argo_rollouts_canary / kyverno_admission_block /
      tekton_runbook_pipeline / alertmanager_routing /
      self_escalation_engine の 5 orchestrator は、各
      class が必要とする層を宣言する。同一 signal は複数
      orchestrator に分散しないが、同一 service では複数
      class が複数 orchestrator を併用する。
  - drill cadence を物理 property とする。
      「runbook_drill_cadence_days 以内に必ず runbook を
      演習し、宣言された RTO 内に loop closure する」を
      Litmus chaos test + Tekton dry-run で必ず検証する。
      13 の v1_runbook_drill_compliance / v1_postmortem_
      sla_compliance / v1_oncall_paging_budget が cluster
      _label 付き metric で隣接 cluster を観測し、loop
      closure 破綻を即時 alert + admission block に流す。
  - defense-in-depth は 5 層で構成する。
      層 A : compile 時（PR の change_class 注釈必須、
              ops_loop.lock.yaml schema 通過）
      層 B : lint（catalog の coverage / SLA / runbook
              ref / ownership entry / blameless 文体）
      層 C : runbook_drill chaos test（Litmus + Tekton
              dry-run + chainsaw）
      層 D : runtime（5 orchestrator の実 deploy）
      層 E : physical（cosign signature / Kyverno
              admission webhook / Argo Rollouts pause /
              ops_event hash chain の物理層強制）
      任意の単層が破れても他層が必ず止める。物理 enforcement
      は最終 safety net。

■ phase（5 phase、signal の loop closure に対応）
  - phase_1_detect：
        signal の発火 → on-call ack
        SLA：page → ack ≤ 5 min（severity_freeze 時 ≤ 3
              min）
        primary action_class：alertmanager_routing /
              self_escalation_engine
  - phase_2_triage：
        incident class 確定 → IR ticket 起票 → Mattermost
        incident channel
        SLA：ack → triage 完了 ≤ 30 min
        primary action_class：tekton_runbook_pipeline
              （triage runbook）/ alertmanager_routing
  - phase_3_mitigate：
        即時対処（auto rollback / manual rollback /
        throttle / freeze / runbook 起動）
        SLA：triage → mitigation 開始 ≤ 5 min（severity_
              freeze 時）/ ≤ 15 min（severity_page 時）
        primary action_class：argo_rollouts_canary
              （auto rollback）/ kyverno_admission_block
              （freeze）/ tekton_runbook_pipeline
              （runbook 実行）
  - phase_4_resolve：
        SLO budget 復活 / capacity 平常化 / customer
        impact 終了の確認 → incident close
        SLA：detect → resolve total（MTTR）SLO 別 target
              （class 別、05_SLO駆動運用方針 と整合）
        primary action_class：tekton_runbook_pipeline
              （verification） / alertmanager_routing
              （resolve 通知）
  - phase_5_postmortem：
        resolve 後 72h 以内に postmortem PR 起票必須、
        merged まで関連 namespace の deploy が Kyverno で
        物理 block
        SLA：resolve → postmortem PR open ≤ 72h、open →
              merged ≤ 14 日
        primary action_class：kyverno_admission_block
              （deploy block）/ tekton_runbook_pipeline
              （postmortem template gen）

  - 5 phase × 5 signal_class = 25 cell が完全列挙、空欄は
    coverage gap として CI fail。

■ 単一の真（6 yaml、うち 5 が build artifact）
  - classes.yaml（軸 5 class enum + phase 5 enum +
    action 5 enum）
        signal_class / phase / action_class の 3 enum 軸
        を宣言。class 名は version prefix 固定（v1_xxx）、
        追加は purely additive。
  - ops_loop.lock.yaml（build artifact 1）
        生成器：ops-loop-builder
        input：classes.yaml + 各軸 spec の defense-in-
              depth 層 D / E + alert_catalog + runbook_
              catalog + ownership_table + budget_action_
              bindings
        出力：5 × 5 = 25 cell の row、各 cell に action
              pointer ≥ 1
        手書き禁止、CI fail。
  - budget_action_bindings.lock.yaml（build artifact 2）
        生成器：budget-action-binder
        input：error_budget.lock.yaml（13 SLO）+ ops_
              loop.lock.yaml + 5 段階 burn rate threshold
        出力：(slo_id × window_class × burn_rate_
              threshold × action_class × action_pointer)
              の row、観察 / 通知 / page / freeze /
              rollback の 5 段階 binding
        手書き禁止、CI fail。
  - alert_catalog.lock.yaml（build artifact 3、06_
    アラート方針 の primary key、ops_loop.lock.yaml の
    detect phase の primary key として参照される）
        生成器：alert-catalog-builder
        input：error_budget.lock.yaml + classes.yaml +
              各軸 spec の SLI 出力 + noise_budget_
              constraints
        出力：alert_id ↔ severity ↔ slo_bind ↔ runbook_
              ref ↔ auto_action_ref ↔ noise_budget_ratio
              ↔ mute_window_class の 7 項関係
  - runbook_catalog.lock.yaml（build artifact 4、11_
    runbook方針 の primary key、ops_loop.lock.yaml の
    全 phase の primary key として参照される）
        生成器：runbook-catalog-builder
        input：alert_catalog.lock.yaml + incident_
              classes.yaml + drill_progress.lock.yaml +
              break-glass_classes.yaml + change_classes.
              yaml
        出力：runbook_id ↔ class ↔ alert_ref ↔ incident
              _class_ref ↔ break_glass_ref ↔ drill_class
              _ref ↔ change_class_ref ↔ markdown_ref ↔
              pipeline_ref ↔ executable ↔ last_drill_at
              ↔ last_drill_outcome の 11 項関係
  - postmortem_progress.lock.yaml（build artifact 5、
    本層 + 09_ポストモーテム方針 + 10_security/11_インシ
    デント対応方針 が共有管掌、security 11 の incident
    postmortem と同型）
        生成器：postmortem-progress-builder（Tekton job）
        input：incident_history.lock.yaml + GitHub PR
              query + 6 必須 section schema
        出力：incident_id ↔ postmortem_pr_url ↔ phase
              （open / draft / review / merged）↔ sla
              _status（within / overdue）↔ action_item
              _ids ↔ blameless_lint_status の 6 項関係

  - 共通制約：
        - 全 yaml は CUE schema で type 検証
        - 全 yaml は cosign signed snapshot として periodic
          に publish（hash chain root とも整合）
        - drift 検出時は Argo CD が self-heal、build
          artifact ↔ runtime の divergence ゼロ

■ 5 層 defense-in-depth（運用ループ軸全体）
  - 層 A：compile
        - ops_loop.lock.yaml の cell = 5 × 5 = 25 で完全
          列挙（ビルド時に行数 check）
        - action pointer kind enum 検証（textual は cap
          5%、boundary section は cap 0%）
        - alert_catalog の page-level alert に runbook_
          ref 必須
        - runbook_catalog の executable enum 検証（v1_
          full_auto / v1_partial_auto / v1_human_only、
          後者は cap 5%）
        - CUE 型 check（class enum / pointer kind /
          severity enum / phase enum）
        - postmortem PR の 6 必須 section header 一致

  - 層 B：lint
        - Conftest custom rule（Rego）：
              - alert ↔ runbook 1:1 coverage
              - severity = page / freeze に runbook_ref
                必須
              - ownership_table 完全 coverage
              - rotation roster gap = 0
              - flag cleanup_due_at 期限内
              - postmortem PR SLA（72h open / 14d merged）
                内
              - change_calendar global freeze 内 PR の
                v1_emergency 注釈
              - automation backlog の P0 item に
                implementation owner 必須
              - toil quarterly target monotonic decrease
              - non-toil mis-classification ゼロ
              - alert ↔ ownership ↔ rotation の三項関係
                完整
        - Semgrep custom rule：
              - postmortem PR の blameless 文体 lint
              - blame keyword（"who failed" / "X person

        - Apicurio compatibility rule：phase_class_only_

  - 層 C：integration test
        - chainsaw / kuttl で全 admission policy（ops

■ 至高路線における判断（structural spec として）
  - 「page が増えると on-call が疲弊する」を理由に loop
    coverage を縮小しない。疲弊は paging budget metric
    で表現、coverage itself は省略しない。
  - 「postmortem の merge を待っていると速度が落ちる」を
    理由に postmortem ship blocker を緩めない。速度
    低下は短期的、loop closure 不能の蓄積は長期的に
    壊滅的。
  - 「商用 PagerDuty が便利だから入れたい」を理由に L1+
    単一深耕を緩めない。新 OSS は 14_OSSライフサイクル適合
    仕様 の pair_target 移行手続を経る。
  - 「toil monotonic decrease は厳しすぎる」を理由に
    cadence を緩めない。quarterly target は CI で物理
    enforce、未達は ship blocker（少なくとも次 quarter
    で挽回必須）。
  - 「SLO breach の auto rollback は怖い」を理由に手動
    rollback path を default にしない。Argo Rollouts の
    AnalysisTemplate による auto rollback を default、
    手動 rollback は break-glass。
  - 「runbook は Markdown だけで充分」を理由に Tekton
    job 化を skip しない。手作業 step が残る場合のみ
    Markdown allow（cap 5%）、それ以外は実行可能 runbook
    が ship blocker。
  - 「ops_event の hash chain は重複だから security 14
    の audit chain だけで充分」を理由に hash chain を
    skip しない。ops_event subject は別 schema、別
    immutability 規律で security audit_event と独立に
    chain 維持（subject 別の forgery resistance を物理
    enforce）。
