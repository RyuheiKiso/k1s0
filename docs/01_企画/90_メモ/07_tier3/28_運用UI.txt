============================================================
tier3 の運用 UI（業務 UI と業務管理 UI の境界遵守）
============================================================

■ 方針
  - 「06_tier2」各章で扱われる運用系機能の UI は大半が「業務
    管理 UI」スコープ（「26_業務管理UI境界」「06_tier2/23_管
    理境界」整合）であり、tier3 業務 UI から提供しない。
  - 本ファイルは「業務 UI 側で扱う運用観点」と「業務管理 UI
    へリダイレクトする観点」の二分を明示する。tier3 担当が
    UI を作る際の判断基準として用いる。
  - 業務 UI と業務管理 UI を混在させると、業務エンドユーザに
    本来見せるべきでない管理機能が露出し、認可境界 / 監査
    境界が崩れる（「06_tier2/22_権限モデル」「06_tier2/14_業
    務エラー監査コンプライアンス」整合）。

■ tier3 業務 UI で扱う運用観点
  - 自身が起動した LRO（long running operation）の進捗確認:
      - 自分が submit した bulk 処理 / 帳票生成の進捗を表示
        する（「15_非同期処理UX」整合）。
      - 進捗 polling / SSE 受信は tier2 業務 API 経由。
      - 他者が起動した LRO は本 UI から閲覧しない（業務管理
        UI スコープ）。
  - 自身に来た通知 / 承認待ち / 期限予告:
      - 通知センター（「17_通知UI」整合）の表示は業務 UI で
        扱う。
      - 自身宛て / 自身が関与する aggregate のみを表示する。
  - 自身が関与する Workflow の状態確認:
      - Workflow ステッパ / 承認段階の表示（「14_状態遷移UI」
        整合）。
      - 自身が関与しない Workflow の閲覧は業務管理 UI スコー
        プ。
  - quota 超過 / rate limit / SLO 違反のクライアント側 UX:
      - 429 相当のレスポンスを業務語彙で説明し、再試行誘導 /
        バックオフ表示を行う（「06_tier2/27_信頼性運用準備」
        整合）。
      - SLO 違反予兆（latency 上昇等）は業務 UI 側の
        gracefully degrade 表示で対応する。
  - 自身が起動した処理の失敗詳細とリトライ:
      - 失敗詳細を業務語彙で表示し、リトライ手段を業務 UI 上
        で提示する（「19_業務エラーUX」整合）。
      - 失敗の根本原因が業務管理者対応である場合は、その旨
        を表示し業務管理者への通知導線を提示する（業務管理
        UI への deep link）。
  - 接続断 / 復旧の表示:
      - 通信切断時のオフラインバナー / 復旧時の再同期表示
        （「16_リアルタイム更新UX」「22_端末オフラインデバ
        イス」整合）。

■ tier3 業務 UI に載せない運用機能（業務管理 UI へ deep link のみ）
  - schedule / 業務カレンダー編集:
      - cron / interval / calendar-based の schedule 編集は
        業務管理者領域（「06_tier2/20_スケジューラ・バッチ」
        整合）。
  - partner 連携設定:
      - subscription 登録 / mapping 編集 / partner credential
        管理（「06_tier2/25_外部システム統合」整合）。
  - 業務データ migration / dry-run / bulk 操作 / data export:
      - オンボーディング時の bulk import、テナント離脱時の
        data export（「06_tier2/29_データライフサイクル」
        整合）。
  - 失敗ジョブ手動再実行:
      - 業務管理者が監視する失敗ジョブの再実行は業務管理 UI
        スコープ。tier3 業務 UI からは「自身が起動した処理」
        の再実行のみ許容。
  - emergency_override 起動 / 解除:
      - time-bound の業務緊急対応は業務管理者領域（「06_tier
        2/22_権限モデル」緊急時の override 整合）。
  - 業務 entity の手動補償 / 手動完了:
      - 通常の業務 action では遷移できない状態への補償は
        業務管理 UI スコープ。
  - 監査検索:
      - 自身分の操作履歴閲覧は tier3 業務 UI で可（「14_状態
        遷移UI」監査履歴の閲覧 UI 節）。
      - テナント全体の監査検索は業務管理 UI スコープ
        （「06_tier2/14_業務エラー監査コンプライアンス」
        整合）。

■ quota / rate limit UX
  - 429 相当の表示:
      - 業務語彙でユーザに説明する。
      - 推奨対応（業務管理者への連絡 / 後で再試行 / 別経路
        の利用）を併記する。
      - 待ち時間（Retry-After ヘッダがある場合）を業務語彙
        で表示。
          例：「テナントの月次上限に達しました。次回リセッ
              ト：2026 年 6 月 1 日 00:00（JST）」
  - クライアント側 throttle:
      - 過剰送信を抑制するために、UI 側でも debounce / 押下
        後 disable を併用する（「14_状態遷移UI」二重押下防止
        整合）。
      - サーバ側 rate limit に依存せず、ユーザの誤操作で
        429 を発生させない設計。

■ SLO 違反予兆の表示
  - tier1 観測基盤からの通知（「33_観測可能性」整合）に基づ
    き、業務 UI 側で SLO 違反予兆を表示する。
      例：「現在、検査結果登録の応答が通常より遅延しており
          ます。確定処理に時間がかかる場合があります。」
  - 表示は控えめなバナーで、業務操作を阻害しない。

■ 障害時のフェイルオープン / フェイルクローズ
  - tier1 backend 全断時の業務 UI 挙動規約:
      - 認可判定が取得不能な場合は fail-close（操作を許可
        しない）を既定とする（「18_権限UI制御」整合）。
      - 参照系のキャッシュ表示は短期間に限り許容（「16_リ
        アルタイム更新UX」キャッシュ TTL 規約整合）。古い
        データである旨を明示する。
      - 書込系 API は無効化し、ユーザに明示する（「保存
        できません。サーバとの接続を確認してください」）。
  - 業務的に「障害時でもオフラインで処理を進めたい」要件
    （現場検査 / 倉庫操作）は「22_端末オフラインデバイス」
    整合の Outbox 機構で対応。

■ 業務管理 UI 連携
  - 業務管理 UI への deep link は、認可がある時のみ提示する
    （「18_権限UI制御」整合）。
  - 認可がない場合は deep link を表示せず、「業務管理者に
    連絡してください」の文言で対応する。
      例：「failed_jobs を再実行するには業務管理者権限が
          必要です。テナント管理者にお問い合わせください。」
  - deep link の URL は業務管理 UI 側で routing を所有
    （tier2 が管理）。tier3 はクエリパラメータとして関連
    aggregate ID を渡すだけにとどめる。
