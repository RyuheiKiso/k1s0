============================================================
tier3 の互換性ポリシー
============================================================

■ 1.0.0 完璧主義との整合
  - 「01_概要」「CLAUDE.md」記載の通り、本プラットフォームは
    1.0.0 を完璧として出す方針であり、段階的リリースを採ら
    ない。tier3 もこの方針に従う。
  - 1.0.0 までは外部互換性保証を行わない。1.0.0 リリース後
    から本ファイルの互換性ポリシーが発効する（「06_tier2/13_
    互換性ポリシー」と同枠）。

■ tier2 minor 追従
  - tier3 の業務コードは無変更で動作する。tier2 が拡張点
    contract を minor で破らない（「06_tier2/13_互換性ポリ
    シー」拡張点 contract の安定性節）以上、tier3 の業務
    コード / override は contract に従う限り動作する
    （「24_override実装規約」整合）。
  - tier3 SDK 更新は patch / minor リリースとして提供する。
    tier3 担当は SDK の bump を CI で受けるだけで済む。
  - minor 追従時の検証 :
      - contract test を新版 tier2 SDK で実行（「29_テスト
        方針」contract test 節整合）。
      - visual regression / accessibility test の再実行。

■ tier2 major 追従
  - 移行 toolchain（tier2 が提供、「06_tier2/13_互換性ポリ
    シー」tier2 移行コミットメント節）を使って override を
    修正する。
      例：拡張点 contract の差分リストに従い、override を
          機械的に書き換える。
  - 並行運用期間（最長 6 ヶ月）に新旧 tier2 SDK を共存させる
    方針:
      - 異なる tier3 が異なる tier2 SDK バージョンに依存する
        状況を許容する（「27_複数tier3連携」バージョン整合
        節整合）。
      - 期間内に全 tier3 を新 major に揃えることを目標に
        する。
  - tier3 SDK 更新は major リリースとして提供する。

■ tier3 自身の SemVer
  - patch :
      - バグ修正 / UI 微調整 / コピー文言の修正等。
      - ユーザの操作フローを変えない。
  - minor :
      - 機能追加（後方互換）。
      - 既存ユーザの操作フローを壊さない。
          例：新しい一覧フィルタの追加。
  - major :
      - UI フロー変更（多段化 / 単段化等）。
      - 認証フロー変更。
      - URL routing の破壊的変更（「11_画面遷移ルーティング」
        整合）。
      - tier3 利用者向けに移行ガイドを提供する。

■ ブラウザ更新追従
  - サポート対象 :
      - 主要モダンブラウザの最新版 + 1 つ前（Chromium /
        Firefox / WebKit / Edge）。
      - Internet Explorer / 旧 Edge は対象外。
  - Web 標準 API の deprecation 追従:
      - Chrome Platform Status / browser-compat-data を継続
        監視。
      - deprecated 通知を受けた API は計画的に置換する。
  - 旧ブラウザでの fallback :
      - Companion 経由レガシー（「36_レガシー資産統合」整合）
        の枠で別途対応する。tier3 業務 UI 自体に旧ブラウザ
        対応を埋め込まない。

■ bundle versioning / cache busting
  - immutable + content hash の URL 戦略を採る（「34_配布
    デプロイ運用」整合）。
      例：/static/main.<contenthash>.js
  - service worker 更新時のクライアント挙動 :
      - 新バージョン検知 → ユーザに「再読み込みで最新版を
        適用してください」のバナー表示。
      - 自動 reload は行わない（編集中フォームの破壊を避け
        るため）。
  - cache strategy は「22_端末オフラインデバイス」と整合。

■ データ移行影響
  - tier2 schema 変更時の表示崩れを生成型で防止する。
      - tier3 は tier2 の .proto 由来の生成型のみを使用
        する。独自型の宣言は禁止（「31_強制機構」層 8
        整合）。
      - tier2 schema が minor で前方互換変更された場合、
        生成型が更新されることで自動的に新フィールドを受
        けられる。
      - 旧フィールドが残る期間中は両方を受け取れる UI
        実装にしておく。

■ レガシー（Companion 経由）との並走
  - .NET Framework クライアントは Companion バージョンに依存
    する（「05_tier1/04_Library」Companion 節整合）。
  - tier3 業務 UI（Web）と Companion 経由レガシーが同居する
    場合、両者は別経路で tier2 と接続するため、互換性は別軸
    で管理する。
  - Companion 互換性ポリシーに従い、Companion の major 更新
    は tier1 整合下で進む。tier3 自身が Companion 互換性を
    持つわけではない。

■ API バージョニング
  - tier2 の URL path major / proto package major を明示
    指定する（「06_tier2/18_API設計規約」整合）。
      例：/v1/orders、tier2.manufacturing.v1
  - サーバ側自動 routing（バージョン解決を URL パスから
    省略する形）に頼らない。明示する。
  - major bumping 時は新 path / 新 package に切替える。

■ deprecation 対応
  - tier2 が deprecated とした API の Sunset 期日を遵守する。
    期日内に切替を完了させる（「06_tier2/13_互換性ポリ
    シー」整合）。
  - deprecated 通知は tier2 の release notes / Backstage の
    catalog 上で機械的に通知される（「31_強制機構」整合）。
  - tier3 の CI で deprecated API の利用箇所を検出し、警告
    として表示する。Sunset 期日が近い場合は CI fail に切替
    えて阻止する。

■ 1.0.0 出荷時の対応範囲
  - 上記すべての互換性枠を出荷時点で適用する。
  - tier2 / tier1 整合の上で、tier3 が「1.0.0 として完璧」
    の状態を担保する。
============================================================
