============================================================
tier3 のテスト方針
============================================================

■ 方針
  - tier3 は業務 UI を提供する以上、UI 表現 / UX / アクセシ
    ビリティ / パフォーマンス / contract 整合性の各軸を漏ら
    さずテストする。
  - テストは CI を merge 条件とし、運用後の例外申請に依存し
    ない（「06_tier2/15_テスト方針」と同枠、「31_強制機構」
    整合）。
  - tier1 / tier2 同様、Backstage Software Template に CI
    設定とともに同梱する。tier3 リポジトリ生成時点でテスト
    枠が組み込まれる。

■ テスト軸の全体像
  - 単体（コンポーネント / Application 層 / Domain 値オブ
    ジェクト）
  - 統合（tier2 SDK 含む）
  - E2E（Playwright によるユーザシナリオ全通し）
  - visual regression（デザインシステム整合）
  - accessibility（WCAG 2.1 AA）
  - contract（tier2 拡張点 / override 整合）
  - パフォーマンス（Web Vitals / 負荷）
  - 国際化 / オフライン / セキュリティ

■ 単体テスト
  - 対象 :
      - フレームワーク非依存のロジック（Application 層 /
        Domain 値オブジェクト、「07_内部アーキテクチャ」
        整合）
      - UI コンポーネント（Storybook + jest / vitest 等）
  - 方針 :
      - DI / 外部 IO / フレームワークに依存しないユニットを
        単体テスト対象とする。
      - 業務エラー taxonomy（「06_tier2/14_業務エラー監査コ
        ンプライアンス」）の各エラー型を UI 表現に正しく
        マップしているかを単体で網羅する（「19_業務エラー
        UX」整合）。
      - Storybook の各 story を視覚的単体ケースとして扱う。
          例：状態バッジの 6 状態（Draft / Confirmed /
              Cancelled / Modified / Expired / PendingApproval）
              の表示確認。

■ 統合テスト
  - 対象 :
      - tier2 SDK（Library 形態）/ tier2 Service（共有 Service
        形態）と接続した状態の業務処理。
  - 方針 :
      - Testcontainers で tier1 backend を起動（tier2 と
        同じ枠、「06_tier2/15_テスト方針」整合）。
      - tier2 Service を起動して tier3 から呼出し、業務 API
        の wire 整合 / Domain Event 受信を実機で検証する。
      - mock しない。tier1 が L1+ / L2* / L3 で深耕している
        OSS を起動して使う。

■ E2E テスト
  - フレームワーク : Playwright を既定とする。クロスブラウザ
    （Chromium / Firefox / WebKit）/ クロスデバイス（モバ
    イル / タブレット / デスクトップ）で並列実行する。
  - シナリオ :
      - 主要業務シナリオを golden path として網羅する。
          例：発注 Draft 起票 → 確定 → 取消、検査結果登録
              → 確定。
      - 認可違いのユーザロールでの分岐シナリオも含める
        （「18_権限UI制御」整合）。
  - 安定性 :
      - flaky test は merge 阻止対象。retry 前提のテストを
        作らない。
      - 外部依存は Testcontainers で固定する。

■ visual regression test
  - ツール : Chromatic / Percy 等のクラウド型、または
    Playwright の snapshot 機能を併用する。
  - スコープ :
      - Storybook の各 story
      - 主要画面の代表状態
  - デザインシステム（「09_デザインシステム」整合）の変更
    影響を検出する。テナント別ブランディング（「37_業務
    カスタマイズ粒度」整合）の各組合せも代表値で snapshot
    する。

■ accessibility test
  - ツール : axe-core / Pa11y を CI で実行する（「21_アク
    セシビリティ国際化」整合）。
  - 基準 :
      - WCAG 2.1 AA 違反は merge 阻止。
      - キーボード操作 / スクリーンリーダ読み上げは E2E で
        専用 step を設ける。
      - 色のみで状態を伝えていないことを CI で検査する
        （「14_状態遷移UI」状態バッジのデザインシステム節
        整合）。

■ contract test（tier3 → tier2 拡張点）
  - tier2 が提供する contract test suite を tier3 リポジトリ
    の CI で実行する（「24_override実装規約」「06_tier2/15_
    テスト方針」拡張点 contract 節整合）。
  - skip / 改変は CI で fail させる（「31_強制機構」層 9
    整合）。
  - 拡張点の入出力契約 / 呼び出しタイミング契約 / 不変条件
    保持を property based test 風に検査する。
  - tier2 minor version up 時、旧版 override 実装が新版
    tier2 上で contract test に green であることを CI で
    再検証する（「30_互換性ポリシー」整合）。

■ パフォーマンステスト
  - Web Vitals（LCP / FID / CLS / INP）の目標値を CI に組み
    込む（Lighthouse CI 統合）。
      - LCP : 2.5 秒以下
      - INP : 200ms 以下
      - CLS : 0.1 以下
  - 大量データ一覧の仮想スクロール検証（「13_検索一覧UX」
    整合）:
      - 数万件の表示時にフレームレートが落ちないことを E2E
        で検証する。
  - 負荷テスト :
      - 主要画面での同時操作（複数タブ / 複数ユーザ）での
        破綻が無いことを検証する。

■ 国際化 / 多言語テスト
  - pseudolocalization で文字長変動を検出する（「21_アクセ
    シビリティ国際化」整合）。
      例：英語 → 疑似ロケール（[!! Long string with
          accented characters !!]）でレイアウト崩れが無い
          ことを CI snapshot で検出。
  - TZ 切替（JST / UTC / Europe/Berlin 等）での日時表示
    検証。

■ オフラインテスト
  - PWA の offline shell 動作（「22_端末オフラインデバイス」
    整合）:
      - service worker による cache strategy の動作確認。
      - オフライン時の UI 表示と Outbox 動作を E2E で検証。

■ セキュリティテスト
  - ZAP / Burp の自動スキャンを CI に組み込む（「32_セキュ
    リティアーキテクチャ」整合）。
  - CSP / セキュリティヘッダ / SRI の設定を CI で検証する。
  - XSS / CSRF / clickjacking の代表攻撃ベクトルに対する
    回帰テストを保持。

■ Backstage Software Template での組込
  - tier3 リポジトリ生成時点で、上記すべての CI 設定が同梱
    される。テスト軸ごとに skip 設定が無いことを「31_強制
    機構」で機械的に検査する。
  - tier3 担当はテスト枠を新設する作業を行わない。テスト
    ケースの追加 / 拡張に集中する。
