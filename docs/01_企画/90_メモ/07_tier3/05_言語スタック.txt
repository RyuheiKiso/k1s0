============================================================
tier3 の言語スタック
============================================================

■ 基本方針
  - tier3 は tier1 / tier2 が対応する言語に揃える。tier1 / tier2
    が対応しない言語で tier3 を実装することは禁止する。理由 :
      - tier1 Library / tier2 Library が無い言語では、tier3 業務
        コードが tier2 を経由せず OSS や独自 HTTP クライアントを
        直接利用する経路を塞げない。
      - 公開 API snapshot / conformance test の整合性を全 tier3
        言語で維持できない（「31_強制機構」参照）。
  - tier1 / tier2 対応言語：Rust / C# (.NET 8+) / Go / TypeScript
    （「05_tier1/02_言語スタック」「06_tier2/12_言語スタック」
    参照）。

■ Library 直接組込言語
  - 対応言語：Rust / C# (.NET 8+) / Go / TypeScript（tier1 /
    tier2 と同集合）。
  - 各言語で tier2 Library を直接組み込み、業務 API を消費する。
    .proto / Schema 駆動で生成される型を消費するだけで、tier3 側
    で独自にコード生成は行わない（「06_tier2/11_表現手段」と整合）。

■ Companion 経由言語
  - 対応言語：.NET Framework 4.6.2+ のみ。
  - tier2 Library 直接組込が不可能な言語に対しては、tier1
    Companion（役割 A / 役割 B）と Gateway 経由 tier2 Service で
    消費する（「05_tier1/04_Library」Companion 節と整合）。
  - tier3 業務コードからは、tier2 Service の External Proto 由来
    の SDK と、Companion runtime のみが見える。OSS クライアント
    への直接アクセスは禁止する（「03_非提供スコープ」参照）。

■ アプリケーション形態別の主要言語
  - Web SPA :
      - 主要言語：TypeScript。
      - tier2 Library（npm package）を消費する。バンドル時の
        backend 専用依存混入は禁止（「06_UI技術スタック」参照）。
  - デスクトップ exe（クロスプラットフォーム） :
      - 主要言語：C# (.NET 8+) または Rust（Tauri）。
      - C# 採用時は tier2 Library（NuGet package）を消費する。
      - Rust + Tauri 採用時は tier2 Library（crate）を消費する。
        UI 部分は WebView 上で TypeScript を併用するため、複数
        言語混在の場合は API 表面を .proto / Schema 駆動で揃える
        （「06_tier2/12_言語スタック」業界 pack の言語選定指針節
        と整合）。
  - レガシー :
      - 主要言語：C# (.NET Framework 4.6.2+)。
      - tier2 Library 直接組込は不可。Companion + Gateway 経由
        tier2 Service を消費する（「04_アプリケーション形態」レ
        ガシー形態の固定方針節と整合）。

■ 言語間 API 表面整合性
  - tier3 は tier2 が公開する .proto / Schema 由来の型を「消費
    する側」である。tier3 側で独自にコード生成しない。
  - tier2 が言語ごとに提供する Library SDK / Service SDK の API
    表面は、tier2 の責務として整合性が担保される（「06_tier2/12_
    言語スタック」言語間 API 表面整合性節）。tier3 はこれをその
    まま使う。
  - tier3 業務コードが直接書く部分（UI 層 / 画面遷移 / フォーム
    バリデーション補助 / 通知 UI 等）の整合性は、tier3 横断の
    UI ライブラリ（「06_UI技術スタック」共通コンポーネントライ
    ブラリ節）で担保する。

■ 言語固有のイディオム差
  - 同一業務でも言語ごとに自然な API 形（async / 例外型 / null
    表現 等）が異なる。tier3 は tier2 が提供する SDK の上で言語
    イディオムに従って実装する :
      - Rust         : Result<T, E> / async fn
      - C# (.NET 8+) : ValueTask<T> / 業務例外型
      - Go           : (T, error) / context.Context
      - TypeScript   : Promise<T> / Result-like 型
  - 上記の差は tier1 Library core パッケージ（「05_tier1/04_
    Library」core 集約方針）と tier2 Library がイディオムを吸収
    する範囲で担保される。tier3 側でイディオム変換層を独自に
    持つことは禁止する。

■ 言語追加の手順
  - 1.0.0 出荷後に tier3 の対応言語を追加する場合、以下を満たす
    ことを要件とする :
      - tier1 Library がその言語に対応していること（先行条件。
        「05_tier1/02_言語スタック」と整合）。
      - tier2 Library / tier2 Service SDK がその言語に対応している
        こと（「06_tier2/12_言語スタック」言語追加の手順節と整合）。
      - 公開 API snapshot / conformance test を当該言語版で green
        にできること。
      - 当該言語向けの Backstage Software Template / 強制機構
        設定（「31_強制機構」）が整備されていること。
  - 上記が揃わない言語での tier3 実装は禁止する。「言語先行で
    tier1 / tier2 の対応を後追いする」ことは構造的に許容しない。

■ 1.0.0 出荷時の対応範囲
  - Library 直接組込言語：Rust / C# (.NET 8+) / Go / TypeScript。
  - Companion 経由言語：.NET Framework 4.6.2+。
  - その他言語（Swift / Kotlin / Python / Java 等）は 1.0.0 出荷
    対象外。
