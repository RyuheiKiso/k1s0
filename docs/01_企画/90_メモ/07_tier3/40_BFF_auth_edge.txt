============================================================
tier3 BFF auth-edge（v1）
============================================================

■ 位置づけ
  - tier3 が静的 SPA + SSR 不採用の前提を維持しながら、httpOnly
    cookie 保管 / Authorization header 自動付与 / silent renew /
    OIDC back-channel logout 受信を技術的に閉じるための横断
    コンポーネント。
  - 「07_tier3/06_UI技術スタック」「07_tier3/25_認証認可マルチテナント」
    「07_tier3/27_複数tier3連携」「07_tier3/34_配布デプロイ運用」
    「06_tier2/32_テナント分離適合仕様」と双方向 lock。
  - SSR 不採用の規律は維持する。本コンポーネントは HTML を生成
    せず、JSON / cookie / WebSocket（logout broadcast）のみを扱う
    auth/session edge であり SSR ではない（HTML 配信は CDN 静的
    ホスティングが継続して担う）。

■ 不可避性
  - SPA 単独配信では次のいずれも技術的に成立しない :
      (a) httpOnly cookie 中の access_token を JS から読み取って
          fetch の Authorization header に付与する経路（httpOnly
          仕様により JS 不可視）。
      (b) OIDC back-channel logout の HTTP POST 受信（CDN 静的
          ホスティングは listener を持たない）。
      (c) iframe + prompt=none による silent renew（Safari ITP /
          Firefox ETP / Chrome の third-party cookie 既定ブロック
          下で IdP cookie が抑止され interaction_required となる）。
  - これらを解消する唯一の現実解として、tier3 ごとに first-party
    な auth/session edge（本 BFF）を立てる。

■ 配置
  - 1 tier3 ごとに 1 Service を tier1 cluster 上に配置する（共有
    クラスタ内の sidecar 群）。tier3 業務ロジック（tier2 Library
    / Service）と同 cluster だが、責務は session/auth に限定する。
  - DNS レイアウト :
      auth.<tier3>.<tenant>.<root_domain>   → BFF
      app.<tier3>.<tenant>.<root_domain>    → SPA（CDN 静的）
    両者は同 root_domain 配下、SPA → BFF はブラウザから見て
    same-site（registrable domain 一致）として cookie 送出可能。
  - cookie scope は Domain=<tier3>.<tenant>.<root_domain>（tier3
    間の cookie 漏洩を構造的に遮断）。

■ 役割
  - 役割 BFF-A : session / cookie 管理
      - login 成功時に Keycloak から OIDC code flow + PKCE で取得
        した tokens を BFF process memory + Valkey に保管。
      - SPA に対しては httpOnly + Secure + SameSite=Lax +
        Path=/ + Domain=<tier3>.<tenant>.<root_domain> の
        session_id cookie のみを発行する（access_token 自体は
        SPA に渡さない）。SameSite は Lax 固定とする。Strict は
        Keycloak → BFF callback（OIDC code flow の cross-site
        top-level navigation）で BFF が事前に発行した state /
        PKCE / nonce cookie が落ち、code 検証が破綻するため採ら
        ない（07_tier3/25_認証認可マルチテナント の Lax 判断を
        BFF も継承）。CSRF は SameSite=Lax + Double-Submit
        Cookie + Origin/Referer 二重検査で担保する（後述 BFF-E）。
  - 役割 BFF-B : Authorization header 付与
      - SPA → BFF は fetch credentials:'include' で session_id
        cookie のみを送出。BFF は cookie から server-side state
        を引き当てて Authorization: Bearer <access_token> を
        backend（tier1 Gateway）向けに付与する。
      - 「access_token getter ゼロ」原則は強化される（SDK 公開
        API でも SPA 内 storage でも一切 access_token を露出
        しない）。
  - 役割 BFF-C : refresh_token rotation（silent renew 代替）
      - OAuth 2.1 RFC 6749 + RFC 8693 (token exchange) に従い、
        access_token の expiry を BFF が監視。サーバ間通信で
        refresh_token を回し、SPA は何も知らない（fetch 失敗時
        の暗黙再試行ですら BFF 内で透過完了する）。
      - 「iframe + prompt=none」を 25 から削除する根拠（2-D 解決）。
  - 役割 BFF-D : back-channel logout 受信
      - Keycloak から POST /logout（OIDC Back-Channel Logout 1.0）
        を受信できる HTTP listener を BFF が常時 expose。
      - logout を受けたら該当 session を Valkey から即時削除し、
        全 SPA タブに WebSocket / SSE で broadcast（SPA 側は
        受信して即座に画面遷移）。
  - 役割 BFF-E : CSRF / CORS 規律
      - SPA → BFF の全 mutation request に CSRF token 必須
        （Double-Submit Cookie pattern + Origin/Referer 二重検査、
        SameSite=Lax と二重持ち。SameSite=Lax は GET 以外の
        cross-site request を防ぐが POST 等 idempotent でない
        top-level navigation の余地が残るため、二重送信 CSRF
        token を fetch のカスタムヘッダ X-CSRF-Token で必須送出
        + サーバ側で Origin / Referer を二重検査する、
        25_認証認可マルチテナント / 32_セキュリティアーキテクチャ
        と整合）。
      - CORS は Origin allowlist を tier3 manifest から導出、
        wildcard 禁止、preflight cache 5 min 上限。

■ token 取扱の禁則（access_token getter ゼロ強化）
  - SPA 側 : access_token を window.* / localStorage / IndexedDB /
    sessionStorage / memory / Service Worker のいずれにも置かない。
    SPA 経由で BFF API に問合せても access_token は返らない（BFF は
    `/whoami` / `/session` などで claims subset と expiry のみ返す）。
  - SDK 公開 API : access_token getter は提供しない。CI で
    forbidden_export_symbols.lock.yaml の access_token 列を
    全 SDK に対して検査する（既存規律を継承）。

■ Valkey session スキーマ
  - key   : sess:<session_id>
  - value : { actor_id, tenant_id, access_token, refresh_token,
              id_token, expires_at, issued_at, csrf_token,
              ua_subclass }
  - TTL   : refresh_token の absolute_lifetime に従う（rotating
            refresh_token と同期）。
  - Encryption : AES-256-GCM (DEK は OpenBao Transit、KEK は
                 HSM-backed、tier3 ごと別 transit key path)。

■ 副作用と派生規律
  - tier3 数だけ cookie scope / CSRF / CORS / DNS レコードが増える。
    これらは tier3 manifest の `bff_auth_edge` セクションに集約し、
    Backstage Software Template で生成する（手書き禁止）。
  - sub-domain ごとの TLS 証明書を cert-manager + ACME で自動発行。
  - tier3 間の cookie 漏洩は cookie Domain scope
    （Domain=<tier3>.<tenant>.<root_domain>、別 tier3 sub-domain
    から構造的に到達不能）で遮断、追加で CI が `Set-Cookie
    Domain` のスコープ違反を検出。SameSite は OIDC redirect 整合
    のため Lax を採るが、tier3 間の遮断は Domain scope が担う
    ため SameSite 値に依存しない。
  - back-channel logout の Keycloak 側登録は Keycloak Realm
    Operator で Backstage から自動登録。

■ 整合
  - 整合 1 : 07_tier3/25_認証認可マルチテナント の「iframe +
            prompt=none」表記は本 BFF の refresh_token rotation
            に置換する（25 側で削除確定）。
  - 整合 2 : 07_tier3/27_複数tier3連携 の back-channel logout
            受信は本 BFF が単一の受信器として機能（27 側で参照）。
  - 整合 3 : 06_tier2/32_テナント分離適合仕様 の認証コンテキスト
            注入は BFF が Authorization header を tier1 に届け、
            tier1 Library が SET LOCAL に転写する経路で完成。
  - 整合 4 : 12_client/15_クライアントSDK配布適合仕様 の
            access_token getter ゼロ規律を BFF 経由で物理に
            強化（SDK は BFF cookie 経路のみを assume）。
  - 整合 5 : 11_ops/15_運用ループ適合仕様 の SLO に BFF の
            session_renew_latency_seconds（refresh_token
            rotation の P99 latency）を追加し、BFF 障害が
            業務 latency に化けないことを CI で確認。
  - 整合 6 : 07_tier3/25_認証認可マルチテナント の SameSite=Lax
            判断（Keycloak SSO redirect 戻りで Strict cookie が
            落ちる根拠）を BFF も継承。BFF が発行する全 cookie
            （session_id / state / PKCE / nonce / CSRF token）は
            SameSite=Lax 固定、CSRF は Double-Submit Cookie +
            Origin/Referer 二重検査で担保（BFF-E）。
            12_client/07_オフライン耐性方針 / 12_client/15_クラ
            イアントSDK配布適合仕様 の cookie SameSite 規約も
            本整合に従って Lax に揃える。
