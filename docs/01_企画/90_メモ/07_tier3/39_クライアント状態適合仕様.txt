============================================================
tier3 クライアント状態適合仕様（v1）
============================================================

■ 位置づけ
  - 「08_状態管理」「16_リアルタイム更新UX」「19_業務エラーUX」
    「22_端末オフラインデバイス」「24_override実装規約」が散在的
    に宣言する次の四つを、機械可読な単一の真として一箇所に固定
    する仕様書 :
      (a) Server Truth / Optimistic Local / Pending Queue / Draft
          の 4 layer 分離と各 layer の lineage
      (b) 4 layer 間の衝突解決 tree（決定論的）
      (c) BusinessConflict の subtype による UI 分岐の 1:1 固定化
      (d) 端末紛失 / 25h オフライン / PII 永続化での safety net
  - 本仕様は client 軸における defense-in-depth を 5 層で形式化し、
    各層の責務を分離して担保する。
  - 「05_tier1/07_Bidi適合仕様」が transport 軸、「06_tier2/32_
    テナント分離適合仕様」が data 軸の単一の真であるのと同型の
    枠組みを client 軸に転写したもの。dimension override 禁止 /
    dead spec 殺し / build artifact 化の規律はそのまま継承する。

■ 設計原則
  - クライアント状態は 4 layer に分割する。
      Server Truth (ST) / Optimistic Local (OL) / Pending Queue (PQ)
      / Draft (DR) の 4 つだけを許容する。これら以外の中間 layer
      （例：UI ローカルにしか存在しない aggregate cache）を作る
      ことを禁止する。1 つの値が「どの layer 由来か（lineage）」
      を必ず持つ。
  - 衝突解決 tree は決定論的である。
      4 layer × イベント（Domain Event 受信 / API 応答 / ユーザ
      操作 / ネットワーク復帰 / TTL 経過）の組合せで取るべき動作
      が一意に決まる。「実装者の判断」の余地を残さない。
  - BusinessConflict は 4 subtype に細分化する。
      tier2 BusinessConflict（「06_tier2/14_業務エラー監査コンプ
      ライアンス」）を stale_write / lost_update / supersede /
      concurrent_edit の 4 subtype に分割し、UI 分岐を 1:1 で固定
      する。subtype と UI 分岐の対応を override 禁止とする。
  - 永続化は WebCrypto + device_bound_key で encrypted at rest、
    PII は in-memory only。
      IndexedDB / localStorage に PII 平文を置かない。queue / draft
      は AES-GCM 暗号化、鍵は OS keychain（Tauri / native）または
      browser non-extractable CryptoKey。PII 列は enqueue 時に strip
      し、send 時に in-memory form state から attach する。
  - 5 層 defense-in-depth で構成する。
      層 A : Application 層 reducer（Adapter 集約）
      層 B : lint / 公開 API snapshot
      層 C : headless browser integration test
      層 D : runtime（WebCrypto / IndexedDB encryption / Idempotency-
             Key TTL enforce）
      層 E : 端末紛失時の rotation（refresh_token 失効で queue
             purge、device_bound_key は OS keychain 由来）
  - dead spec を CI で殺す（07 / 32 と同枠）。
      layers.yaml に登録された layer、conflict_tree.yaml に登録
      された event / branch、test_matrix.yaml に登録された scenario、
      いずれも参照されなくなった時点で CI fail。

■ v1 layer セット（4 layer）
  - クライアントが保持する全状態はいずれかの layer に属する。layer
    が決まれば lineage / 永続化 / PII 取り扱い / lifetime が決まる。

      layer             | source                       | persisted_in     | PII | lifetime
      ------------------+------------------------------+------------------+-----+--------------------------------
      server_truth      | domain_event_subscription /  | query cache      | NG  | session（logout で purge）
                        | api_response_2xx             | (in-memory)      |     |
      optimistic_local  | mutation_in_flight           | query cache      | NG  | until_ack_or_rollback
                        |                              | (overlay)        |     |
      pending_queue     | user_action（offline 含む）  | indexeddb        | 除外 | until_ack_or_user_discard
                        |                              | (encrypted)      |     |
      draft             | form_input                   | indexeddb        | 除外 | until_confirm_success
                        |                              | (encrypted)      |     | _or_user_discard

  - 各 layer の不変条件 :

      - server_truth (ST)
          - lineage : (server_truth, aggregate.version, trace_id, observed_at)
          - 真は常に tier2 atomic 三表書込（「06_tier2/32_テナント
            分離適合仕様」atomic 三表書込節）が確定した値。client
            は cache としてのみ保持する。
          - logout / token expiry で全 ST cache を purge。

      - optimistic_local (OL)
          - lineage : (optimistic_local, base_version, predicted_next_version,
                      idempotency_key, started_at)
          - mutation 開始時に作られ、ack で promote、reject で rollback。
          - 同一 aggregate に対し OL は同時 1 件まで（並行 OL 禁止）。

      - pending_queue (PQ)
          - lineage : (pending_queue, base_version, idempotency_key,
                      enqueued_at)
          - 永続化される唯一の mutation 経路。offline 中の操作 / 送信中
            の操作はすべて PQ に入る。
          - aggregate 単位で in-flight 1 件、enqueue 順を保つ。

      - draft (DR)
          - lineage : (draft, base_version, form_id, edited_at)
          - 編集中フォームの dirty state。confirm 成功 / 明示破棄で消滅。
          - aggregate に commit する前の値であり、ST / OL / PQ から
            独立に持つ。

  - 4 layer で v1 が covering する。新しい状態種別が 4 layer の
    いずれにも収まらないと判明した時点で、本仕様は v2 候補として
    layer 追加検討に入る（v2 拡張ルール参照）。

■ v1 conflict event カタログ（5 event、決定論的 tree）

  - 4 layer に対し以下の event が発火する。各 event の actions は
    一意に定まり、実装者の判断の余地を持たない。

      event_id                       | trigger                                     | when
      -------------------------------+---------------------------------------------+----------------------------------
      server_truth_advance           | domain_event_received | api_response         | server_truth.version 増加
                                     | _received                                   |
      optimistic_acknowledged        | api_response_2xx_for_in_flight_mutation     | OL 存在
      optimistic_rejected            | api_response_4xx_business_error             | OL 存在
      pending_queue_resume           | network_recovery | app_resume               | PQ 非空
      business_conflict_received     | api_response_409_with_subtype               | PQ または OL 存在

  - 各 event の actions :

      ── server_truth_advance
          - rollback_optimistic_if_present
          - update_server_truth (replace ST with new value)
          - re_evaluate_pending_queue
              （PQ に対し base_version との突合を行い、stale_write
                可能性を fire させる。実 send は次の resume で行う）

      ── optimistic_acknowledged
          - promote_optimistic_to_server_truth
              （OL の predicted_next_version が ack の version と一致
                すれば直接 promote、ずれていれば server 値で上書き）
          - delete_pending_queue_entry_by_idempotency_key

      ── optimistic_rejected
          - rollback_optimistic
          - present_business_error
              （「19_業務エラーUX」tier2 業務例外と UI presentation
                の対応表に委譲）
          - if BusinessConflict: dispatch_conflict_subtype（次の event）

      ── pending_queue_resume
          - send_queue_in_enqueue_order
          - per_aggregate_serialize (aggregate ID 単位で 1 in-flight)
          - 各 send で ack なら optimistic_acknowledged、4xx なら
            optimistic_rejected を fire

      ── business_conflict_received（subtype 分岐）
          branches:
            stale_write:
              - refetch_server_truth
              - rebase_pending_op_on_new_version (field-level)
              - if rebase_clean: auto_resend_with_new_idempotency_key
                _chained_to_original
                （rebase 後 payload は base_version が変わるため
                同 Idempotency-Key で送ると tier2 Idempotency
                cache の stored response と衝突する。新 key を
                発行し chain 親子関係（original_idempotency_key
                + chained_idempotency_key）を tier2 cache 側で
                dedup 判定する。「06_tier2/24_読み取りモデル方針」
                整合）
              - if rebase_dirty: present_3way_merge_ui + hold_queue
            lost_update:
              - refetch_server_truth
              - present_3way_merge_ui
              - hold_queue_until_user_decides
            supersede:
              - delete_queue_entry
              - notify_user_silent (toast 程度、「17_通知UI」整合)
            concurrent_edit:
              - update_presence_indicator
              - allow_user_to_continue_or_abort

  - tree が決定論的であることの含意 :
      ジュニア級チームが書く tier3 でも、conflict 事象が発生した
      ときに「どの分岐に入るか」は仕様で固定。実装側は branch ごと
      の UI コンポーネントを書くだけで済み、判断ロジックを散らさ
      ない。

■ v1 BusinessConflict subtype（tier2 への構造的拡張要求）
  - tier2 BusinessConflict（「06_tier2/14_業務エラー監査コンプラ
    イアンス」業務例外 taxonomy）を 4 subtype に分割する。これは
    tier2 リポジトリ抽象が aggregate.version mismatch 検出時に判定
    し、エラーレスポンスの拡張フィールド subtype として返却する。
  - subtype 判定ロジック（tier2 側 Library 内部、「06_tier2/32_
    テナント分離適合仕様」Repository abstraction で実装） :

      subtype          | 判定条件
      -----------------+--------------------------------------------------------
      stale_write      | base_version < ST.version, かつ field-level diff で
                       | client が触った field と他 actor が触った field の
                       | 集合が disjoint
      lost_update      | base_version < ST.version, かつ field-level diff で
                       | 集合が intersect
      supersede        | 同一 actor の後続 op が同 aggregate を既に更新済み
                       | （Idempotency-Key chain で検出）
      concurrent_edit  | 他 actor が presence で編集中宣言（「16_リアルタイム
                       | 更新UX」presence indicator 整合）+ 自身が send 試行

  - tier2 への要求 :
      - BusinessConflict.subtype フィールドを必須化。
      - field-level diff の算出を Repository abstraction 内で実施。
      - presence subscription 経由の concurrent_edit 通知を tier2
        Domain Event Hub に追加。
      - 上記は「06_tier2/14_業務エラー監査コンプライアンス」業務
        例外 taxonomy 節に反映する（本仕様と相互参照）。

■ 5 層 defense-in-depth

  ── 層 A : Application 層 reducer（Adapter 集約）
      - 4 layer + conflict tree を Application 層の単一 reducer に
        集約する。Presentation 層 / Adapter 層から layer state を
        直接書換える経路を持たない（「07_内部アーキテクチャ」整合）。
      - reducer は conflict_tree.yaml が宣言する event / actions を
        実装する純粋関数として書く。副作用（IndexedDB 書込 / network
        send）は中間 effect として表現し、Adapter 層が実行する。

  ── 層 B : lint / 公開 API snapshot
      - Presentation 層コンポーネントから IndexedDB / localStorage /
        sessionStorage への直接アクセスが現れたら CI fail。
          TypeScript : eslint-plugin-boundaries で UI 層からの
                       window.indexedDB / window.localStorage 利用を
                       deny。
          Blazor     : Roslyn analyzer で IJSRuntime 直接呼出の
                       Storage 系を deny。
      - tier3 公開 API snapshot に layer state を露出する getter が
        現れたら fail（layer は Adapter 経由でしか触らせない）。

  ── 層 C : headless browser integration test
      - test_matrix.yaml の全 scenario を Playwright + Testcontainers
        で自動実行する。tier2 側は実 PostgreSQL + 実 Outbox relay を
        立ち上げ、本物の atomic 三表書込（「06_tier2/32_テナント
        分離適合仕様」）と接続する。
      - network injection（offline / latency / 接続断）は Playwright
        の route interception + browser DevTools Protocol を組合せる。
      - merge 条件 : 全 scenario が green。skip された scenario が
        あれば fail。

  ── 層 D : runtime（WebCrypto / IndexedDB encryption / TTL）
      - IndexedDB に書込まれる pending_queue / draft は AES-GCM
        encrypted。鍵は device_bound_key として OS keychain (Tauri)
        または non-extractable CryptoKey (browser) に保管。
      - Idempotency-Key TTL（24h）超過の検出を Adapter 層で行い、
        durability.yaml の over_ttl_policy に従って動作する。
      - WebCrypto API 経由でのみ暗号化する。自製 crypto は禁止。

  ── 層 E : 端末紛失時の rotation
      - refresh_token 失効を検知すると pending_queue / draft / ST
        cache を即時 purge する。
      - device_bound_key は OS keychain から再生成。新規セッションは
        新しい key で encrypted storage を初期化、旧 storage は復号
        不可となる。
      - tenant_switch / actor_switch でも同様の purge を実行。
      - purge は監査 emit を伴う（「33_観測可能性」整合）。

■ tier2 atomic 三表書込との接合

  - 本仕様の pending_queue resume は tier2 32 仕様（atomic 三表書込）
    と次の対応関係で噛み合う :

      client (本仕様)                      | server (32 仕様)
      -------------------------------------+----------------------------------
      pending_queue.idempotency_key        | aggregate.version + outbox dedup
      pending_queue.base_version           | UPDATE WHERE version = ?
      optimistic_local.predicted_next      | aggregate.version + 1
      domain_event_received                | outbox relay → Kafka → tier3 sub
      api_response_2xx                     | atomic 三表 commit ack
      api_response_409 + subtype           | tier2 が version mismatch 検出時に
                                           | field-level diff から subtype 判定

  - tier2 atomic 三表書込により、ack を受領した時点で「state change /
    Outbox / audit_local の 3 表が同一 transaction で commit されて
    いる」ことが保証される（「06_tier2/32_テナント分離適合仕様」
    integrity property P1）。client 側は ack を受けた瞬間に OL を
    promote し PQ を delete してよい（後発の Domain Event 受信で
    再度 ST が更新されるが、optimistic_acknowledged がすでに promote
    済みのため idempotent）。

  - resume_token（「05_tier1/03_Server系」Resume / Replay 節）と
    本仕様の Domain Event subscription は同型 :
      tier1 transport が adapter 切替を跨いで session を継続するの
      と同様、tier3 client は network 復帰を跨いで pending_queue
      の send 順序を保つ。

■ CI 不変条件（4 ファイル + 5 層の関係性検査）
  - 違反は merge 不可。
      整合 1 : layers.yaml の全 layer が conflict_tree.yaml の
               actions のいずれかから書込まれる（dead layer 検出）。
      整合 2 : conflict_tree.yaml の全 event が test_matrix.yaml の
               少なくとも 1 scenario でカバーされる。
      整合 3 : business_conflict_received の全 subtype branch が
               test_matrix.yaml で個別 scenario によりカバーされる。
      整合 4 : Presentation 層から indexeddb / localStorage への
               直接アクセスが無い（公開 API snapshot 検査）。
      整合 5 : durability.yaml で encryption: AES-GCM が宣言された
               全 storage の実装が WebCrypto 経由である（静的検査）。
      整合 6 : pending_queue の PII strip / attach の対称性 property
               test が green（同じ form を strip して send すると
               元データに復元可能）。
      整合 7 : end-to-end PII 検査 : headless browser で全 scenario
               実行後、IndexedDB の物理 dump に PII 平文が含まれない
               ことを CI で自動検証。
      整合 8 : test_matrix.yaml の全 scenario が tier2 の実
               atomic 三表書込と接続して green を返す（mock では
               なく実 backend）。
      整合 9 : layers.yaml の lineage_fields が実装側の lineage 型
               定義と完全一致（codegen で同期、drift 検出）。
      整合 10: dead spec 検出 : 参照されない layer / event / branch /
               scenario は CI fail。

■ 製造業 pack stress test（v1 の正当性証跡）
  - 8 scenarios を v1 conflict tree に classify した結果、全て 5
    event × 4 subtype の枠で機構が成立する。

      # | 業務シナリオ                                          | event / subtype           | 主要 layer

■ v2 拡張ルール
  - 新 layer / 新 event / 新 subtype の追加は purely additive。
  - 既存 layer の lifetime / persistence 変更、event の actions 変更、
    subtype の UI 分岐変更はいずれも破壊的変更（major version up、
    「30_互換性ポリシー」と整合）。dual-write 移行 toolchain を
    tier1 / tier2 が成果物として提供する（「05_tier1/04_Library」
    L1+ 移行コミットメントと同型）。
  - 命名は layer / event / subtype ともに英小文字 snake_case 固定。
  - CRDT / 自動マージは v1 では採用しない。lost_update は常に 3way
    merge UI でユーザに判断を委ねる。CRDT 化は v2 以降の検討。

■ 長期収斂への作用
  - 本仕様の 4 ファイルに対し、新業務 / 新業界 pack の追加は purely
    additive な変更として進行する。test_matrix.yaml に scenario を
    足し、conflict_tree.yaml の既存 event / branch のみで覆える形を
    保つ。
  - 07（transport 軸）/ 32（data 軸）/ 本仕様（client 軸）の三軸が
    同型構造で固まったことにより、tier1 / tier2 / tier3 の単一の真
    が三軸独立に保たれ、軸間の接合は次の対応関係に閉じる :

      transport 軸 conformance_class    ↔  data 軸 transaction_unit
                                        ↔  client 軸 conflict event

      transport 軸 capability matrix    ↔  data 軸 RLS policy
                                        ↔  client 軸 durability policy

      transport 軸 scenario corpus      ↔  data 軸 stress test
                                        ↔  client 軸 test_matrix

  - 三軸の同型は「単一 OSS 深耕 + 移行コミットメント」（「05_tier1
    /04_Library」L1+）の哲学を data / client 軸にも転写したもの。
    各軸とも purely additive な拡張と決定論的な不変条件で成熟する。
