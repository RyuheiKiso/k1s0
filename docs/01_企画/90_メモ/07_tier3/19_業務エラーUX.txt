============================================================
tier3 の業務エラー UX
============================================================

■ 方針
  - tier2 の業務例外 taxonomy（「06_tier2/14_業務エラー監査
    コンプライアンス」）を UI に正しく presentation する規約を
    定める。tier3 は業務語彙でユーザに次アクションを示す責務を
    持つ。
  - 業務的失敗とシステム失敗を UI 上で明確に区別する。「すべて
    一律のエラー画面」のような扱いは禁止する。
  - エラー画面はエラーであっても業務遂行を支援する画面である。
    ユーザの入力を破棄しない、再試行 / 取下げ / サポート問合せ
    のいずれかが必ず提示されることを既定とする。

■ tier2 業務例外と UI presentation の対応表
  - DomainError（業務不変条件の違反、tier2 規約）:
      - 表示形態：モーダル + 業務的説明 + 推奨対応
        （recovery_hints）
      - 例：「在庫数がマイナスになる発注は確定できません」
      - 通常の form-level / field-level エラーとして扱わない
        （aggregate 状態に依存する判定のため）。
  - ValidationError（入力値の業務妥当性違反）:
      - 表示形態：field-level の赤色下線 + フィールド近傍の
        メッセージ（「12_フォーム設計規約」整合）
      - フォーム送信時の最終判定は tier2 が行うが、tier3 は軽量
        プリチェックで送信前に検出可能なものを表示する。
      - 複数 field のエラーは form 上部にサマリも表示する。
  - BusinessConflict（並行操作 / 別 actor との不整合）:
      - 表示形態：競合状況の業務的説明 + 再取得促し
      - 「16_リアルタイム更新UX」競合解決 UI と同型。version
        不一致 / 同 aggregate の二重承認等で発生。
      - 自動マージは行わない。
  - AuthorizationDenied（認可拒否）:
      - 表示形態：「18_権限UI制御」権限不足エラー節に従う。
      - 必要権限・委譲経路・申請手順を業務語彙で示す。

■ 業務的失敗とシステム失敗の区別
  - 業務的失敗:
      - tier2 が業務例外 taxonomy で返したもの。
      - 業務語彙で説明し、ユーザの次アクションを示す
        （修正 / 取下げ / 再取得）。
      - 業務管理者連絡導線は必ずしも提示しない（業務担当が
        自力で対応可能な範囲）。
  - システム失敗:
      - tier1 backend 障害 / ネットワーク障害 / 想定外例外。
      - 「一時的な問題が発生しています」と業務語彙で表示し、
        再試行 / サポート問合せ導線を提示する。
      - 業務語彙で説明できない技術詳細はユーザ向けには出さず、
        詳細展開でサポート向けに開示する（後述）。

■ recovery_hints の UI 表示
  - tier2 業務エラーの拡張フィールド recovery_hints
    （「06_tier2/18_API設計規約」エラーレスポンス節）を業務
    語彙でそのまま表示する。
  - hints は単一文字列ではなく構造化（推奨対応のリスト + 各
    対応への遷移リンク）として扱う。tier2 が提供する形式に
    準拠する。
  - hints が空の場合は汎用文言（「業務管理者にお問合せ
    ください」等）で fallback する。

■ エラーコードの表示
  - tier2 enum のエラーコード（error_code）はユーザ向けには
    既定で非表示とする（業務担当には冗長 / 誤誘導のため）。
  - サポート向けには「詳細」展開で開示する。trace_id とともに
    コピー可能とする。
  - エラーコード一覧の業務語彙対応は tier2 i18n 辞書から取得
    する（tier3 で勝手にラベル付けしない）。

■ 詳細エラーの収集（サポート連携）
  - エラー時に「サポートへ送信」ボタンを提示し、以下を tier2
    のサポート受付 API（または observability collector）に送信
    可能とする:
      - trace_id（tier1 trace context）
      - 操作再現手順（直近の画面遷移 / 入力値の概要）
      - エラーコード / business_outcome / 端末情報
      - スクリーンショット（ユーザ任意）
  - 「33_観測可能性」「35_開発者体験」整合。trace_id がサポート
    から開発まで一貫して辿れることを担保する。

■ PII を含むエラー詳細の取扱
  - tier2 はエラー詳細に PII を含めない方針（「06_tier2/14_業務
    エラー監査コンプライアンス」PII 節）。tier3 はそれを前提に
    表示する。
  - サポート送信時に画面入力値を添付する場合、tier3 側でも PII
    検出 hook を通し、含まれる場合は送信前にユーザに告知 +
    マスキング選択肢を提示する（「32_セキュリティアーキ
    テクチャ」整合）。
  - 自動的に PII を伏字化する経路を Adapter 層に集約する
    （「07_内部アーキテクチャ」整合）。

■ 多言語対応
  - エラーメッセージは tier2 提供の i18n 辞書を利用する。tier3
    で原文を改変しない。
  - locale 切替で過去エラーの表示も切替わる挙動を既定とする。
  - 数値 / 日時 / 通貨はフォーマッタを通す（「21_アクセシビ
    リティ国際化」整合）。

■ 部分失敗（複数操作の一部成功）の表示
  - bulk 系 API の応答が「N 件中 M 件成功 / N-M 件失敗」の場合:
      - 成功 / 失敗を業務語彙で要約表示。
      - 失敗分は理由 + recovery_hints を行ごとに表示。
      - 「失敗分のみ再試行」ボタンを提示する（idempotency-key
        は失敗分のみ再利用、成功分は新規発行しない。「15_
        非同期処理UX」整合）。
  - bulk 系自体は業務管理 UI スコープが多い（「26_業務管理UI
    境界」整合）。tier3 業務 UI で扱う bulk は限定的。

■ リトライ可能性の明示
  - 「同じ意図の再試行」ボタン:
      - Idempotency-Key を再利用する。tier2 サーバ側が cache
        した結果を再利用する。
      - 業務的失敗（DomainError）の修正リトライ、システム失敗
        の再試行のいずれにも適用される。
  - 「新しい操作として実行」ボタン:
      - Idempotency-Key を新規発行する。
      - 別意図として扱われ、二重実行のリスクがある旨を業務
        語彙で明示する。
  - ボタンは UI 上で明確に区別し、誤操作を防ぐ。

■ 業務エラーへの reaction（自動 undo / Draft 復帰）
  - 業務エラー発生時の自動アクション:
      - 確定操作（Draft → Confirmed）失敗時、フォームを Draft
        編集状態に自動復帰させる（入力値破棄なし）。
      - 楽観更新（「16_リアルタイム更新UX」）失敗時の自動
        rollback。
      - 一連の wizard で途中ステップが失敗した場合、可能な
        限り当該ステップに戻す。
  - これらの reaction は Application 層に集約し、Presentation
    層 / Adapter 層に分散させない（「07_内部アーキテクチャ」
    整合）。

■ エラー画面 / 状態の機械的担保
  - 全画面で以下を満たすことを CI / 静的検査で確認する
    （「31_強制機構」整合）:
      - tier2 業務エラーが presentation 対応表のいずれかに
        分類されて扱われていること
      - 失敗時にユーザ入力が破棄されないこと（自動 undo / Draft
        復帰のテスト）
      - 「サポートへ送信」導線が存在すること
      - 生のエラーコード / stack trace が UI に出ないこと
