============================================================
tier3 の通知 UI
============================================================

■ 方針
  - 通知の発信機構そのもの（メール / SMS / push の channel
    adapter）は tier2 が「業界横断 通知」（「06_tier2/10_提供
    機能カテゴリ」）として所有する。tier3 は通知の表示 /
    購読設定 / click 後の遷移に責務を絞る。
  - in-app 通知（toast / banner / 通知センター）は tier3 の
    Presentation 層実装、外部チャネル通知（メール / SMS /
    push）の購読設定 UI は tier3 が tier2 経由で提供する。
  - 通知の優先度は業務インパクトに応じて段階化し、ユーザを
    妨害しすぎない設計を既定とする。

■ in-app 通知の形態
  - トースト（一時表示）:
      - 数秒で自動消滅する軽量通知。操作の成功 / 軽微な情報
        伝達に用いる。
      - 画面操作を妨害しない位置（画面端）に表示する。
  - バナー（持続）:
      - 業務的に重要で確認・対応が必要な通知。手動で閉じる
        まで表示する。
      - 表示位置は画面上部または対応 entity 近接。
  - 通知センター（履歴）:
      - 全通知の履歴 + 既読 / 未読管理。アプリ全域からアクセス
        可能とする。
      - 件数バッジをグローバル navigation に表示。

■ Push 通知（外部チャネル）
  - Web Push API（PWA / ブラウザ）/ OS push（デスクトップ exe /
    モバイル）を tier2 経由で利用する。
  - tier3 は購読 token の取得・登録・解除 UI を提供する。
    送信そのものは tier2 channel adapter が行う。
  - tier1 直接利用は禁止する（「07_内部アーキテクチャ」）。

■ メール / SMS
  - tier2 の通知 channel adapter（「06_tier2/10_提供機能
    カテゴリ」業界横断 通知）経由で配信する。tier3 は購読設定
    UI（受信可否 / 受信宛先 / フォーマット選好）のみを提供する。
  - tier3 内でメール / SMS を直接送る経路は禁止する。

■ 通知優先度
  - tier2 の信頼性アラート階層（「06_tier2/27_信頼性運用準備」
    page / ticket / log only）と整合させ、業務通知の優先度に
    対応付ける:
      - page（最上位 / 妨害的）: モーダルまたは画面全幅バナー。
        例：emergency_override 中である旨、業務クリティカルな
        期限超過。
      - ticket（通常 / 通知センター）: 通知センターに溜まり、
        必要に応じてバナー / トーストでも気付かせる。例：
        承認待ち到着 / Workflow 完了 / 期限予告。
      - log only（履歴のみ）: 通知センター履歴に残るだけ。
        例：自身の操作の事後ログ的通知。
  - tier3 が独自に新たな優先度区分を発明しない。

■ 既読 / 未読管理
  - 既読 / 未読は subscriber（受信者）側で管理する。tier3 は
    tier2 経由で既読フラグを永続化する（端末を跨いで一致させる
    ため）。
  - グローバル navigation の未読バッジ件数は通知センターと
    一致させる。
  - 「すべて既読」操作はユーザ自身に許可するが、対応必須通知
    （page 級）の自動既読化は禁止する。

■ per-user 通知設定 UI
  - ユーザが per-user に通知の挙動を制御できる:
      - チャネル選択：in-app / Web Push / メール / SMS の
        on/off
      - 業務カテゴリ別 on/off：通知を業務カテゴリ（承認待ち /
        期限予告 / Workflow 完了 / 業務 KPI 警告 等）で
        on/off
      - 時間帯：通知を受け取りたい時間帯
      - おやすみモード：一時的な全通知抑制（緊急通知は除外）
  - tier3 はこの UI を提供し、tier2 の購読設定 API に保存する。
  - 通知必須カテゴリ（規制対応 / 監査対応で必達のもの）は
    off できないことを UI で明示する。

■ 緊急通知の優先表示
  - emergency_override 中（「06_tier2/22_権限モデル」「18_権限
    UI制御」整合）は、画面全域に警告バナーを表示し、操作内容の
    詳細監査が emit される旨を提示する。
  - 緊急通知（業務クリティカルな期限超過 / 承認失効間近 等）は
    おやすみモード中であっても表示する経路を持つ。
  - 緊急通知の閾値は tier2 が業務語彙で宣言したもののみを利用
    する（tier3 が独自に発明しない）。

■ 業務 KPI / Workflow 完了通知
  - LRO 完了通知:
      - 「15_非同期処理UX」と整合し、Operation の SUCCEEDED /
        FAILED / CANCELLED に対応する通知を発する。
      - click で対応 aggregate にディープリンクする。
  - 承認待ち通知:
      - 自分が承認段に到達した時点で通知を発する。
      - 期限が近づくと再通知（リマインド）する。閾値は tier2
        の Approval Workflow 設定に従う。
  - 期限切れ予告:
      - 「14_状態遷移UI」期限付き entity と連動する。残時間
        段階に応じて段階的に通知。

■ 通知の i18n
  - 通知文言は tier2 が業務語彙で宣言した messages を i18n
    辞書から取得する（tier3 が独自に翻訳しない）。
  - 数値 / 日時 / 通貨は「21_アクセシビリティ国際化」整合の
    フォーマッタを通す。
  - locale 切替時に既存通知履歴の表示文言も切替わることを
    既定とする（タイムスタンプは絶対時刻で保管）。

■ 通知 click action
  - 通知 click は対応 aggregate のディープリンクを開く
    （「11_画面遷移ルーティング」整合）。
  - 通知ペイロードに業務 ID（aggregate ID + 業務語彙の遷移
    意図）を含める。tier3 は受領した ID から URL を組み立てる。
  - リンク先で認可拒否される場合（権限変動 / Delegation 失効）
    は、適切な業務語彙のメッセージで誘導する（「18_権限UI制御」
    「19_業務エラーUX」整合）。

■ Push 同意管理
  - Web Push / OS push の取得は明示的なユーザ同意を取った
    うえで行う（ブラウザ / OS の同意 dialog）。
  - 同意状態 / 端末登録状態は通知設定画面から確認・解除可能
    とする。
  - push 同意取得時のテレメトリは「33_観測可能性」整合で、
    同意拒否率を計測しつつ PII を含めない（「32_セキュリティ
    アーキテクチャ」整合）。

■ 通知の retention
  - クライアント側 cache（通知センター履歴）は上限を設ける。
    既定は直近 90 日 または 1000 件、いずれか先に到達した方。
  - 上限超過分は古いものから破棄する（業務的真は tier2 側に
    あるため、クライアント側の歴は cache として扱う）。
  - tier2 が通知履歴の長期保管 API を提供する場合、過去履歴
    検索は通知センター内の追加読込で実現する。
