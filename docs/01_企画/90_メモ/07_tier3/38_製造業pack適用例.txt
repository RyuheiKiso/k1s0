============================================================
tier3 の製造業 pack 適用例（1.0.0 出荷代表 tier3）
============================================================

■ 方針
  - 1.0.0 出荷の業界 pack は製造業のみとする（「06_tier2/03_業
    界拡張モデル」「06_tier2/10_提供機能カテゴリ」整合）。
  - 本ファイルは代表 tier3 構成の参考設計を示す。tier3 担当が
    実装着手時に「どの形態 / どの API / どの override / どの
    UX 規約」を採用するかの出発点として用いる。
  - 業界 pack 追加時は本ファイルと同型の参考設計を当該業界に
    対しても整備する。

■ 1.0.0 出荷代表 tier3
  - 発注業務 tier3（procurement-app）:
      - 形態 : Web SPA。
      - 担当ドメイン : manufacturing/procurement（発注 / 検収）。
  - 検査業務 tier3（inspection-app）:
      - 形態 : タブレット PWA + デスクトップ exe（事務所）。
      - 担当ドメイン : manufacturing/inspection（検査計画 /
        実施 / 不良管理）。
  - FA 現場業務 tier3（fa-shopfloor-app）:
      - 形態 : 工場端末（堅牢タブレット）+ デスクトップ exe
        （班長 PC）。
      - 担当ドメイン : manufacturing/fa（生産指示 / 実績収集 /
        進捗管理）。
  - 業界横断業務 tier3（cross-industry-app）:
      - 形態 : Web SPA。
      - 担当 : 通知センター / 監査閲覧 / 帳票管理 / 業務
        カレンダー閲覧。

■ 発注業務 tier3
  - 形態 :
      - Web SPA（事務所 PC で利用）。
      - PWA 化は限定的（事務所は常時接続前提、「22_端末オフラ
        インデバイス」整合）。
  - 主要画面 :
      - 発注作成（フォーム）/ 発注一覧 / 発注詳細 / 承認 /
        検収 / 取消 / 修正。
      - 検索 / 一覧 UX は「13_検索一覧UX」整合。
  - 状態遷移 :
      - Draft → Confirmed → (Cancelled | Modified) の遷移を
        ステッパで表示（「14_状態遷移UI」整合）。
      - Confirmed 後は不変条件「過去確定発注の属性変更不可」を
        守る（「24_override実装規約」整合）。
  - tier2 消費 :
      - manufacturing/procurement の発注 / 検収 API。
      - cross_industry の承認 Workflow API。
      - cross_industry の通知 API。
      - 「23_tier2消費方針」整合の HTTP/JSON or gRPC 経路。
  - override :
      - 発注承認者解決ロジック（組織図に応じた解決）。
      - テナント別承認段数（テナント設定経由、「37_業務カス
        タマイズ粒度」整合）。
      - 承認金額閾値（テナント別、マスタ経由）。
  - 多言語 :
      - 取引先国に応じた切替（「21_アクセシビリティ国際化」
        整合）。
      - 帳票（注文書）も多言語生成（tier2 帳票 API、
        「20_添付帳票UX」整合）。

■ 検査業務 tier3
  - 形態 :
      - タブレット PWA（現場検査員）+ デスクトップ exe（事務所
        の検査管理）。
      - 工場 LAN の断続接続前提でオフライン対応必須。
  - 主要画面 :
      - 検査計画一覧 / 実施記録（写真添付）/ 確定 / 不良票 /
        集計閲覧。
      - 写真撮影 UX は「20_添付帳票UX」整合（getUserMedia 経由）。
  - 状態遷移 :
      - 計画 → 実施中 → 確定 / 不合格。
      - 確定後変更不可（不変条件、「24_override実装規約」整合）。
      - 不合格時は不良票を発行し、是正処置 Workflow を起動する。
  - tier2 消費 :
      - manufacturing/inspection の検査計画 / 検査実施 / 不良
        管理 API。
      - cross_industry の監査ログ API。
      - cross_industry の帳票生成 API（検査成績書 / 不良票）。
  - 添付 :
      - 検査写真 / 規制対応添付（hash chain）を保持する
        （「20_添付帳票UX」整合）。
      - PII / 機密保持の redact ルールを適用。
  - オフライン :
      - 現場の断続接続前提で IndexedDB queue 構成（「22_端末
        オフラインデバイス」整合）。
      - 検査記録は確定送信前まで queue に保持し、復帰時に順次
        送信。Idempotency-Key を付与。
  - override :
      - 規格内判定式（テナント / 顧客要件に応じた閾値設定）。
      - 不変条件「確定済み検査結果は再変更不可」は override
        不可。

■ FA 現場業務 tier3
  - 形態 :
      - 工場端末（堅牢タブレット / ハンドヘルド）+ デスクトッ
        プ exe（班長 PC）。
      - PWA + IndexedDB queue でオフライン耐性を持つ
        （「22_端末オフラインデバイス」整合）。
  - 主要画面 :
      - 生産指示一覧 / 進捗実績入力 / 設備実績閲覧 / 異常通知 /
        班別ダッシュボード。
  - tier2 消費 :
      - manufacturing/fa の生産指示 / 実績収集 / 進捗管理 API。
      - cross_industry の通知 API。
  - デバイス連携 :
      - バーコード / RFID リーダ : 進捗実績の入力で利用
        （「22_端末オフラインデバイス」整合）。
      - 設備からの実績取込 : IoT 機器経由で tier2 が外部システ
        ム統合として取込（緊急経路として tier3 直接取込も
        可能、emergency_override 相当）。
  - リアルタイム更新 :
      - 設備異常通知をリアルタイム表示（「16_リアルタイム更新
        UX」「17_通知UI」整合）。
      - server-streaming RPC を Companion 経由で受信
        （exe 形態のとき）。
  - キーボードショートカット :
      - 現場入力速度優先のショートカット（「12_フォーム設計規
        約」「10_UX原則」整合）。
      - 物理キーボード / ハンドヘルドの物理ボタンを active に
        マッピングする。
  - override :
      - 進捗実績の集計式（テナント別工程定義に応じた集計）。
      - 設備異常の閾値判定（マスタ経由）。

■ 業界横断業務 tier3
  - 形態 :
      - Web SPA（全業務担当者が共通利用）。
  - 主要画面 :
      - 通知センター（テナント全体の通知集約、「17_通知UI」
        「27_複数tier3連携」整合）。
      - 自身の操作監査閲覧（自身分のみ、「28_運用UI」整合）。
      - 帳票一覧（自身が生成 / 受領した帳票）。
      - 業務カレンダー閲覧（編集は業務管理 UI、「26_業務管理
        UI境界」整合）。
  - tier2 消費 :
      - cross_industry の通知 / 監査ログ / 帳票生成 / 業務カレ
        ンダー API。
      - 業界横断機能のみ消費し、業界 pack API は消費しない
        （業界中立性を tier3 側でも維持、「06_tier2/03_業界拡
        張モデル」整合）。
  - 全 tier3 から SSO で遷移可能 :
      - 通知 / 監査の閲覧経路として、業界 tier3（発注 / 検査 /
        FA）から deep link で遷移する（「27_複数tier3連携」
        整合）。
      - 通知 / 監査の発火元 tier3 と関連 aggregate ID を
        deep link に含める。

■ ハイブリッド構成例
  - 同一テナント内の同居 :
      - 事務所 PC（発注 / 業界横断 Web SPA）+ 現場タブレット
        （検査 / FA PWA）+ レガシー .NET Framework クライアン
        ト（既存資産）が同居。
      - 業務単位で適切な形態を選択する。1 テナント 1 アプリ
        ではない。
  - aggregate ID は業界 pack 横断で一意 :
      - 発注 ID / 検査 ID / 生産指示 ID は業界 pack 横断で一意
        （「27_複数tier3連携」整合）。
      - tier3 横断の deep link が機能する。
  - SSO で全アプリを跨ぐ :
      - Keycloak の SSO で全 tier3 を 1 度の認証で利用開始
        （「25_認証認可マルチテナント」「27_複数tier3連携」
        整合）。
  - レガシー連携 :
      - レガシー .NET Framework クライアントは Companion 経由
        で同一テナント / 同一 SSO に参加（「36_レガシー資産
        統合」整合）。

■ 統合シナリオ（業務横断フロー）
  - 発注確定 → 検収 → 入庫 :
      - 発注 tier3 で発注確定 → tier2 が OrderConfirmed Domain
        Event 発行 → 検収時に検査 tier3 / FA 現場 tier3 と連携。
      - tier3 同士が直接 API を呼ばない。Domain Event 経由で
        疎結合（「16_リアルタイム更新UX」「27_複数tier3連携」
        整合）。
  - 検査結果確定 → 不良票発行 → 是正処置 :
      - 検査 tier3 で確定 → tier2 が InspectionFinalized
        Domain Event 発行 → 不良判定なら不良票発行 Workflow
        起動。
      - 是正処置は FA 現場 tier3 / 発注 tier3（再発注）と連携。
  - 設備異常 → 生産指示再計画 :
      - FA 現場 tier3 で設備異常検出 → tier2 が EquipmentFault
        Domain Event 発行 → 生産指示再計画 Workflow 起動。
      - 関連する発注 / 検査への影響通知を業界横断 tier3 の
        通知センターに集約。
  - すべて Domain Event で疎結合 :
      - tier2 経由でテナント単位の Event Hub に publish され、
        tier3 ごとに subscribe。

■ 共通基盤の活用
  - デザインシステム共通 :
      - 全 tier3 で同一トークンを使用（「09_デザインシステム」
        整合）。
      - テナント別ブランディング（ロゴ / カラー / フォント）
        はトークンの override で表現。
  - 認証 SSO 共通 :
      - 全 tier3 で同一 Keycloak realm を使用（「25_認証認可
        マルチテナント」「27_複数tier3連携」整合）。
      - SSO / front-channel logout / back-channel logout を
        全 tier3 で連動。
  - 通知センター共通 :
      - 業界横断 tier3 が全 tier3 通知を集約する。tier3 個別の
        通知センターは作らない。
  - ランチャー UI 共通 :
      - tier1 / tier2 提供のシェルから利用可能 tier3 一覧を
        表示。認可で出し分け。

■ 業界 pack 追加時の取扱
  - 業界 pack 追加時の tier3 :
      - 追加業界の代表 tier3 を新規構築する（「37_業務カスタマ
        イズ粒度」業界 pack の追加整合）。
      - 既存製造業 tier3 は変更しない。業界横断 tier3 のみ
        テナント設定で利用可否を切替える。
  - 業界横断 tier3 :
      - 業界に依存しないため、業界 pack 追加で改修不要。

■ 1.0.0 出荷時の代表 tier3 範囲
  - 上記 4 本（procurement-app / inspection-app /
    fa-shopfloor-app / cross-industry-app）を 1.0.0 で出荷
    する。
  - 業界 pack 追加時に代表 tier3 を増やす（業界 pack 単位で
    別 tier3 を構築）。
