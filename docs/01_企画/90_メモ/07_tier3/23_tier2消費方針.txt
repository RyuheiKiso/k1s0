============================================================
tier3 の tier2 消費方針
============================================================

■ 方針
  - tier3 は業務処理を tier2 の API 経由でのみ行う（「02_位置づけ」
    tier2 への依存方針整合）。tier1 Library / Companion / OSS クライ
    アントへの直接呼出 / 業務処理での独自再実装は禁止する（「31_
    強制機構」整合）。
  - tier2 の API は Library 形態と Service 形態の両方で提供される
    （「06_tier2/02_位置づけ」「06_tier2/08_配布形態」）。tier3 は
    形態を選択できるが、業務コードは形態切替で再設計を伴わない
    （表面 API 対称性整合）。

■ 形態選択基準（Library / Service の選び方、「06_tier2/08_配布形態」整合）
  - Library 形態 :
      - tier3 が同一プロセス内で tier2 業務処理を完結させたい場合。
      - 低 latency が必須（ms オーダー）の業務操作。
      - tier3 が Library 直接組込可能な言語（Rust / C# .NET 8+ /
        Go / TypeScript）で実装される場合。
  - Service 形態 :
      - tier3 が Library 直接組込不可能な言語（.NET Framework 等、
        「36_レガシー資産統合」整合）で実装される場合。
      - 複数 tier3 アプリケーションで状態 / 振る舞いを共有する必要
        がある場合。
      - 集中管理が必要な業務（承認 Workflow / 通知集約 / 監査）。
      - tier3 のデプロイ独立性を高めたい場合。
  - 既定形態は tier3 アプリケーション形態（「04_アプリケーション
    形態」）に従う。同一機能のカテゴリ単位の既定は tier2 の「10_
    提供機能カテゴリ」を参照する。

■ API client
  - tier2 の .proto から派生する型 / クライアント生成物を使用する。
    tier3 は独自に proto を再定義 / 型生成しない。
      - gRPC : tier2 が配布する gRPC stub を import。
      - HTTP+JSON : tier2 が配布する OpenAPI 派生 SDK を import。
      - Companion 経由 : Companion runtime が transport 切替を吸収
        する（「05_tier1/04_Library」Companion 役割 B 整合）。
  - クライアント取得元は内部パッケージリポジトリ（「05_tier1/04_
    Library」強制機構層 3 整合）に固定する。外部 feed からの取得を
    禁止する。
  - 独自生成禁止 : tier3 リポジトリ内で .proto を所持・コード生成
    することを CI で禁止する（「31_強制機構」整合）。

■ 認可コンテキスト伝播
  - tenant_id / user_id を Authorization context のみで伝播する
    （「25_認証認可マルチテナント」「06_tier2/06_マルチテナント方針」
    識別子漏洩防止整合）。
  - tier3 業務コードがリクエスト引数 / body で tenant_id を送信
    する経路を持たない。Adapter 層で Authorization header のみ
    付与する。
  - request 一本ごとに、現在の actor と tenant が一致しているか
    Adapter 層で assert する（テナント切替直後の race を検出）。

■ リトライ / タイムアウト / 冪等性
  - tier2 の規約（「06_tier2/18_API設計規約」整合）に従う。
  - Idempotency-Key :
      - クライアント発行 UUID v4 を Adapter 層で付与する。
      - 再試行時は同一キーを保持する（mutation 単位で生成、retry
        ループ内では使い回す）。
      - キー TTL は 24 時間（tier2 と整合）。期限超過後の再送は
        新規 key を発行し、ユーザ確認を経る（「08_状態管理」整合）。
  - 取得系 RPC :
      - 冪等のため Idempotency-Key 不要。
  - リトライポリシー :
      - retryable : 5xx / network error / DEADLINE_EXCEEDED の一部。
      - non-retryable : 4xx 全般（業務エラー含む、「19_業務エラー
        UX」整合）。
      - exponential backoff + jitter を Adapter 層で実装する。
        max retry count を上限とし、それ以上は失敗としてユーザに
        提示する（silent な無限 retry を禁止）。
  - タイムアウト :
      - 同期 RPC は 30 秒を既定 deadline とする（業務カテゴリで
        上書き可）。
      - LRO は数分以上の処理を Operation オブジェクト経由で扱う
        （後述）。

■ エラーハンドリング
  - tier2 例外 taxonomy（「19_業務エラーUX」「06_tier2/14_業務エラー
    監査コンプライアンス」整合）を Adapter 層で型分類する。
      - DomainError → 業務エラー（再操作で解消可能）
      - ValidationError → フォーム入力エラー（「12_フォーム設計
        規約」整合）
      - BusinessConflict → 並行制御競合（後述）
      - AuthorizationDenied → 認可拒否（「18_権限UI制御」整合）
  - HTTP transcoded（Companion 経由）の RFC 7807 Problem Details
    から business_outcome / recovery_hints を抽出して UI に反映する。
  - PII を含むエラー詳細は表示しない（tier2 の規約整合、「32_セキュ
    リティアーキテクチャ」整合）。

■ 並行制御
  - optimistic locking（version 列）を tier2 が提供する。tier3 は
    UI 上で取得時の version を保持し、mutation 時に同梱する。
  - BusinessConflict 受信時の UX :
      - cache を rollback し、最新サーバ状態を refetch（「08_状態
        管理」「16_リアルタイム更新UX」整合）。
      - ユーザに「他者が先に更新した」旨と最新値の差分を提示。
      - 自動再送は禁止（silent な意味論変化を避ける）。
  - 物理的に競合し得ない読取系では version 検証を skip する。

■ 大量データ取得
  - cursor pagination のみ使用する（「06_tier2/18_API設計規約」
    pagination 整合）。
  - offset pagination は禁止（性能劣化 / 重複 / 欠落のため）。
  - cursor は opaque として扱い、内部形式（Base64 JSON 等）に依存
    したクライアント側パース / 加工を禁止する。
  - 一覧 UI では「次のページ」「全件取得」を Application 層で抽象化
    し、Presentation 層は無限スクロール / pager どちらも選べる
    （「13_検索一覧UX」整合）。

■ streaming
  - server-streaming（subscribe）は tier2 が許容したもののみ消費する。
      例：Domain Event subscription、監査ログ大量取得。
  - bidi-streaming は tier3 業務 API では使用しない（「06_tier2/18_
    API設計規約」整合）。tier3 が bidi を要求する業務シナリオは
    tier2 への新規 API 追加要求として扱う。
  - 切断 / 再接続は Companion 経由 / 直接接続のいずれでも resume_
    token で透過化される。tier3 は onMessage / send 形の API しか
    見えない（「08_状態管理」整合）。

■ LRO（Long-running Operation）
  - 数分以上の業務処理は Operation オブジェクト経由で扱う（「15_
    非同期処理UX」「06_tier2/18_API設計規約」LRO 整合）。
  - 起動 RPC が operation_id を返す。tier3 は :
      - polling : Get Operation で進捗 / 結果を取得。
      - Webhook : tier2 通知経由で完了通知を受領（「17_通知UI」整合）。
  - Cancel : ユーザの中断要求を Cancel Operation で送信。
  - 完了通知は別画面 / バックグラウンドで受領可能とし、UI 操作の
    継続を妨げない。

■ read model 利用
  - 厳密 consistency vs eventual consistency の判別を Application
    層で行う（「06_tier2/24_読み取りモデル方針」整合）。
  - 直近書込で即時 read が必要な場面では厳密 consistency 系 API を
    選択する（「08_状態管理」整合）。
  - 集計 / 検索が中心の場面では eventual consistency 系 read model
    を選択し、stale 表示インジケータを併記する。
  - tier3 が API 種別を画面ごとに使い分け、ユーザに整合性レベルを
    透過に表示する。

■ 集計 / 検索
  - tier2 が対応する集計 API / 検索 API のみを使用する。
  - tier3 がクライアント側で aggregate を跨いだ集計 / フィルタ /
    join を行うことを禁止する（業務処理の二重実装を避ける）。
  - 一覧 UI でのソート / フィルタは tier2 の対応 API パラメタに
    マップする（「13_検索一覧UX」整合）。

■ Library / Service 切替
  - 業務コードを変えずに DI 構成のみで切替可能とする（「07_内部
    アーキテクチャ」整合、「06_tier2/02_位置づけ」表面 API 対称性
    整合）。
      例：composition root で IOrderClient の具象を OrderLibraryClient
          → OrderGrpcClient に差替えるのみ。
  - 切替時の non-functional 差（latency / リトライ設定）は Adapter
    層の policy で吸収する。Application 層 / Presentation 層には
    形態差を漏らさない。

■ Library 専用機能 / Service 専用機能の存在禁止
  - tier3 から見える業務語彙は Library / Service 双方で等価である
    （「06_tier2/02_位置づけ」「06_tier2/08_配布形態」整合）。
  - tier3 が「Library 形態でしか使えない API」「Service 形態でしか
    使えない API」を呼ぶ実装をしない。tier2 が等価性を CI で証明
    した API のみを使用する。

■ tier2 SDK のバージョン整合
  - tier2 SDK のバージョンは「30_互換性ポリシー」整合の major /
    minor で管理する。
  - tier3 リポジトリは pinned バージョンで tier2 SDK を取得する
    （内部レジストリ経由）。
  - major version up 時は並行運用期間（最長 6 ヶ月、「06_tier2/13_
    互換性ポリシー」整合）の中で移行する。tier3 は新旧 SDK の併存を
    避け、ramp 切替を Adapter 層で行う。
  - SDK upgrade 時は contract test（「24_override実装規約」「29_
    テスト方針」整合）を CI で必須実行とする。
