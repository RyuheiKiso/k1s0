============================================================
tier3 の非提供スコープ
============================================================

■ tier1 / OSS の直接利用
  - tier3 は tier1 Library / Companion / Gateway / Server系 を
    直接消費しない。tier1 の横断的共通要素（自動計装 / 認証 token
    取得などの runtime）に乗ることだけは例外として許容する
    （「02_位置づけ」tier1 横断的共通要素への許容例外節を参照）。
  - infra 層の OSS / ミドルウェア（DB / Kafka / Temporal / Keycloak
    / Valkey / Object Storage / NATS / ClickHouse / Vector Search
    / Schema Registry 等）への直接接続は禁止する。
  - 強制機構は「31_強制機構」に従う。tier1 と同じ 3 層
    （依存導入レベル / 公開 API 表面レベル / 供給経路レベル）の
    多重防護を tier3 リポジトリにも適用する（「05_tier1/04_Library」
    強制機構節と整合）。

■ tier2 が提供する業務資産の独自再実装
  - 業務不変条件 / 整合性境界 / 認可規則の独自実装は禁止する。
  - Domain Event の独自発行は禁止する。tier3 は tier2 が公開する
    Domain Event を購読・参照するに留める。
  - Workflow / Saga 定義の独自記述は禁止する。tier3 は tier2 が
    提供する Workflow を起動 / 監視するに留める。Temporal SDK の
    直接利用は不可（「06_tier2/07_業務資産所有権」と整合）。
  - 決定表 / 業務ルールの独自実装は禁止する。決定表評価の入力 /
    出力を扱う UI 表現に責務を限定する。
  - 業務マスタ構造 / DB schema の独自定義は禁止する。tier3 が
    UI 表示用のキャッシュを持つことは「08_状態管理」「22_端末
    オフラインデバイス」の枠内で許容するが、永続データの正解は
    tier2 が所有する。

■ 業界固有概念の独自定義
  - 業界 pack の語彙（製造業であれば「設備」「ロット」「検査結果」
    等）は tier2 から借りる。tier3 が独自に新規語彙を定義し、
    画面に出すことは禁止する。
  - tier3 で発見された業界横断 / 業界共通の業務概念は、tier2 の
    業界 pack 拡張要求として扱う（「06_tier2/03_業界拡張モデル」
    参照）。

■ 業務管理機能
  - マスタ管理（マスタ CRUD / 履歴管理 / インポート / エクスポート）。
  - 監査検索（監査ログの全文検索 / フィルタ / エクスポート）。
  - 緊急対応（業務データの管理画面からの是正、Workflow の手動
    補償起動）。
  - schedule 編集（バッチ実行スケジュールの管理）。
  - partner 連携設定（外部システム接続先 / 認証情報の管理）。
  - これらは tier3 業務 UI に載せない。Backstage プラグインとして
    提供される業務管理 UI のスコープとする（「26_業務管理UI境界」
    参照）。

■ 開発体験 / 運用ツール
  - Backstage（開発者ポータル / Software Template）はプラットフォ
    ーム側で運用する。tier3 はその利用者として Software Template
    から生成される対象である（「35_開発者体験」参照）。
  - Testcontainers / Tilt（ローカル開発）、Helm / Kustomize
    （マニフェスト管理）、sqlx-cli（DB マイグレーション CLI）は
    tier3 の責務外（「05_tier1/06_非提供スコープ」「06_tier2/17_
    非提供スコープ」と整合）。
  - 可視化 UI（Perses / Apache Superset / Jaeger v2 UI（内蔵 CH storage））は
    プラットフォーム側で運用する。tier3 はダッシュボードを内蔵
    しない。

■ tier1 が抽象化していない OSS の利用
  - 「tier1 が抽象化していないが必要な機能」が発生した場合、
    tier1 への新規カテゴリとして提案する。tier3 内で OSS を直接
    ラップすることは禁止する（「06_tier2/02_位置づけ」tier1 への
    依存方針節と同じ哲学を tier3 にも適用する）。
  - tier3 は tier2 経由でしか OSS にアクセスできない構造のため、
    新規 OSS の提案は tier2 → tier1 のルートで上申する。

■ 業務イベント emit の抑制
  - tier2 の API を呼び出した結果として発火する Domain Event /
    監査ログ / 業務イベントの emit を tier3 が抑制することは禁止
    する（override 拡張点を通じた経路でも抑制不可。「06_tier2/07_
    業務資産所有権」override で禁止される範囲節と整合）。
  - 「ユーザに通知しない」「画面に表示しない」という UI 表現の
    抑制と、「業務イベントを発火させない」という業務制御は別物
    である。tier3 は前者のみを行える。

■ 認証 / 認可の独自実装
  - tier3 は認証フロー（OIDC / SAML 等）の独自実装を行わない。
    tier1 / tier2 が提供する認証 runtime に乗る（「25_認証認可
    マルチテナント」参照）。
  - 認可判定そのものを tier3 が独自に行うことは禁止する。tier3
    は tier2 から返された認可結果を UI に反映する責務に限定する
    （「18_権限UI制御」参照）。
  - tier3 が独自に「画面に表示しないことで権限制御の代替とする」
    実装は不可。サーバ側の認可が一次の真である。

■ レガシー基幹への直接接続
  - レガシー基幹システム（既存 ERP / 生産管理 等）への outbound
    統合は tier2 が「06_tier2/25_外部システム統合」で扱う。tier3
    は触らない。tier3 から SOAP / 古い WCF / 独自 TCP 等の経路で
    レガシー基幹に接続することは禁止する（「36_レガシー資産統合」
    参照）。

■ プラットフォーム横断の運用機能
  - 全社的な通知集約 / 全社的な監査集約 / 全社的なダッシュボード
    は tier3 のスコープ外。tier3 は自身の業務範囲の通知 UI / 監査
    UI を持つに留める（「17_通知UI」「28_運用UI」参照）。
