============================================================
tier3 の状態遷移 UI 規約
============================================================

■ 方針
  - tier2 の状態機械（「06_tier2/19_状態遷移パターン」）を、
    クライアント側でユーザに正しく提示するための規約を定める。
    UI 側で勝手な状態を増やさない（業務的な真は tier2 に集約
    される）。
  - 状態は型レベルで識別し、編集可能性 / 可能 action / 表示
    属性を状態ごとに定数化する。状態判定をベタな文字列比較で
    画面に散らさない（「07_内部アーキテクチャ」Application 層
    の責務とする）。
  - 状態遷移 action は必ず tier2 の業務 API を呼ぶ。クライアント
    がローカルで状態を進めることは禁止する（楽観更新は許容
    するが、サーバ確定で必ず差戻し可能とする。「16_リアルタイム
    更新UX」整合）。

■ 標準ライフサイクルと UI 表現
  - 標準ライフサイクル（tier2 既定）:
      Draft → Confirmed → (Cancelled | Modified)
  - Draft:
      - 編集可能なフォームを提示する（「12_フォーム設計規約」
        整合）。
      - 軽量 validation のみ表示し、業務不変条件のフルチェック
        結果は確定操作後に表示する。
      - バッジは「未確定」（業務語彙、i18n 対応）。
      - 「確定」ボタンを主アクションとして提示する。
  - Confirmed:
      - フォームをロック表示し、入力欄は read-only にする。
      - バッジは「確定済み」。
      - 編集 action は提示せず、業務 action（取消 / 修正連鎖
        開始）のみを提示する。
      - 確定者 / 確定時刻を業務語彙で表示する。
  - Cancelled:
      - 取消理由 / 取消者 / 取消時刻を表示する。
      - 編集 / 取消 action は提示しない。
      - バッジは「取消済み」。視覚的に減衰表示（薄色 / 取消線
        を含む扱い）として元 entity と区別する。
  - Modified:
      - 元 entity（modified_from）と新 entity（modified_to）の
        navigation を提示する（業務語彙で「修正前」「修正後」
        として双方向にリンク）。
      - 修正連鎖は監査追跡可能性のため辿れる UI（系譜表示）を
        既定とする。

■ 状態遷移 action のボタン規約
  - 配置:
      - 主アクション（次状態への正規遷移：Draft → Confirmed
        など）はフッタ右側または画面右上の固定位置に置く。
      - 副アクション（取消 / 修正開始 / 差戻し等）は主アクション
        の左、または「その他」メニューに集約する。
  - ラベル:
      - 業務語彙を用いる（「確定」「取消」「修正開始」等）。
      - 「保存」「OK」のような中立語は Draft 編集時のみ用いる。
  - 二重押下防止:
      - 押下中は disable + spinner。Idempotency-Key（tier2 規約）
        を再利用する形で再試行する（「15_非同期処理UX」整合）。
  - 危険 action（取消 / 削除相当）は確認ダイアログまたは入力
    確認（「ORDER-1234」を入力させる等）を要求する。

■ guard 違反のエラー表示
  - tier2 が DomainError として返す guard 違反は「19_業務エラー
    UX」DomainError 節に従ってモーダル + 業務的説明 + 推奨対応
    （recovery_hints）で表示する。
  - 例：「在庫がマイナスになる発注は確定できません」「確定済み
    検査結果は変更できません」。
  - guard 違反は ValidationError とは扱わない（field-level の
    赤字下線では表現しない）。

■ approval workflow（多段承認）の UI
  - tier2 の Approval Workflow（「06_tier2/10_提供機能カテゴリ」）
    を消費する画面では以下を表示する:
      - 承認段階（ステッパ表示。現在段 / 完了段 / 未到達段を
        視覚的に区別）
      - 自分のターンの強調（ヘッダバッジ + 通知センター連動。
        「17_通知UI」整合）
      - 差戻し履歴（差戻し者 / 理由 / 時刻）
      - 期限表示（残時間 / 期限超過時の赤色表示）
  - 自分のターンでは「承認」「差戻し」action を提示する。
    承認は確認なしで送信可、差戻しは理由必須とする。
  - 他者ターンの間は read-only 表示とし、進捗のみ更新する
    （「16_リアルタイム更新UX」subscription で受信）。

■ 期限付き entity（Expired 自動遷移）
  - tier2 が Workflow Timer で Expired 状態を発火する entity
    （「06_tier2/19_状態遷移パターン」）に対応する UI:
      - 一覧 / 詳細で期限を業務語彙で表示する（「あと 3 日」
        「本日中」等）。
      - 期限予告通知（残 N 日 / 残 N 時間）を「17_通知UI」経由で
        受信し、関連画面に bridge する。
      - Expired 遷移後は read-only 表示と「期限切れ」バッジ。

■ 修正連鎖の UI
  - tier2 規約上、修正は「取消 + 新規作成」で表現される
    （元 entity を直接編集しない）。UI も同じ表現を取る:
      - 確定済み entity に「修正」ボタンを置き、押下で
        Cancelled + 新規 Draft 起票（modified_from 連鎖あり）の
        flow に入る。
      - 新 Draft の入力欄には元 entity の値をプリフィル
        する。差分はハイライトで示す。
      - 元 entity 詳細には「修正後 → 新 entity」、新 entity
        詳細には「修正前 → 元 entity」の navigation を置く。

■ 状態バッジのデザインシステム
  - 状態バッジはデザインシステム（「09_デザインシステム」）の
    共通コンポーネントとして提供し、tier3 横断で同一見た目を
    保つ。
  - 既定の色トークン:
      - Draft        : 中立色（情報）
      - Confirmed    : 成功色（業務確定の安心感）
      - Cancelled    : 減衰色（操作不可の薄色）
      - Modified     : 中立色 + 「修正後」副ラベル
      - Expired      : 警告色
      - PendingApproval : アクセント色 + 段階数副ラベル
  - 色のみで状態を伝えない（アイコン + テキストを必須とし、
    アクセシビリティ要件を満たす。「21_アクセシビリティ国際化」
    整合）。

■ 監査履歴の閲覧 UI
  - tier3 業務 UI 上で閲覧可能なのは「自身が関与する aggregate
    の状態遷移履歴 / 自身の操作履歴」のみとする。
  - テナント全体の監査検索 / 他者操作の検索は業務管理 UI
    （「26_業務管理UI境界」）スコープとし、tier3 業務 UI には
    載せない。
  - 監査履歴の表示項目:
      - 業務イベント名（Domain Event 名と一致。tier2 規約）
      - 行為者（業務語彙：氏名・役職。PII 取扱は tier2 規約に
        従う）
      - 時刻（タイムゾーン表示は「21_アクセシビリティ国際化」
        整合）
      - 業務的結果（成功 / 業務的失敗 / システム失敗）
  - 監査エントリ自体の編集 / 削除は不可（規制要件）。
