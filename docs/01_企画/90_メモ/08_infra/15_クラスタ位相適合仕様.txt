■ 設計原則
  - topology_class は bundle である。
      yaml に書く infra.topology.* attribute のうち、topology_
      class 1 つの値が他 5 dimension（blast_radius / failover_
      mode / data_consistency / control_plane_locality / drill_
      cadence_days）を一意に導出する。Argo CD / Kustomize /
      Kyverno の作者が dimension を個別に override する経路は
      持たない。
  - dimension override は禁止する。
      「v1_multi_zone_per_cluster の data_consistency を
      synchronous_replicated に変えたい」要望は新 class を切る
      ことで表現する。class 数の爆発は意味論の規律として受け
      入れる。
  - dead spec を CI で殺す。
      classes.yaml に登録された全 class、scenarios.yaml に登録
      された全 assertion id、cluster_inventory.lock.yaml に列挙
      された全 cluster、failover_drill.lock.yaml に列挙された全
      drill record は、いずれも参照されなくなった時点で CI fail
      とする。Argo CD ApplicationSet のうち topology_class 注釈
      が無いものも CI fail（topology 未宣言の deploy を deny
      by default）。
  - 5 種類 failover orchestrator を全 topology_class に必須化
    する。
      kubernetes_pod_eviction / istio_locality_failover / metallb
      _bgp_failover / argo_rollouts_traffic_shift / external_dns
      _multi_region の 5 orchestrator は、各 class が必要とする
      層を宣言する。同一 failover は複数 orchestrator に分散
      しないが、同一 fleet では複数 class が複数 orchestrator
      を併用する。
  - failover_drill を物理 property とする。
      「drill_cadence_days 以内に必ず failover を実演し、宣言
      された RTO / RPO 内に収束する」を Litmus chaos test で必
      ず検証する。13 の v1_request_availability / v1_request_
      latency_p99 が region_label 付き metric で隣接 region を
      観測し、isolation 破綻を即時 alert + admission block に
      流す。
  - defense-in-depth は 5 層で構成する。
      層 A : compile 時（Argo CD ApplicationSet / Kustomize
              overlay / Helm chart の topology_class 注釈必須）
      層 B : lint（topology_class 注釈の存在 / 値域検査 /
              cluster_inventory.lock.yaml と整合）
      層 C : failover_drill chaos test（Litmus）
      層 D : runtime（5 orchestrator の実 deploy）
      層 E : physical（kube-apiserver multi-AZ etcd quorum /
              Ceph CRUSH map zone topology / Kafka rack
              awareness / CloudNativePG Replica Cluster の物
              理層強制）
      任意の単層が破れても他層が必ず止める。物理 enforcement
      は最終 safety net。

■ v1 topology_class セット（5 class）
  - yaml に書ける topology_class は次の 5 値のみ。各 cluster
    実体は cluster_inventory.lock.yaml の枝で classes.yaml の
    keys と照合する。

      class                              | blast_radius | failover_mode             | data_consistency        | control_plane_locality | drill_cadence_days
      -----------------------------------+--------------+---------------------------+-------------------------+------------------------+--------------------
      v1_single_zone                     | zone         | manual                    | strong_local            | single                 | 180
      v1_multi_zone_per_cluster          | cluster      | automatic_within_window   | strong_local            | single                 | 90
      v1_multi_cluster_active_active     | region       | automatic_continuous      | eventual_async          | federated              | 60
      v1_multi_region_active_passive     | region       | automatic_within_window   | synchronous_replicated (C-priority during partition) | federated              | 30
      v1_multi_region_active_active      | global       | automatic_continuous      | cell_partitioned_synchronous   | mesh                   | 14

  - 各 class の不変条件と典型用途：

      - v1_single_zone
          - 単一 AZ 内の単一 cluster。dev / stage / 検証用途。
            kube-vip + MetalLB の Layer2 mode で内部 VIP を提
            供。etcd quorum は zone 内で 3 ノード。
          - failover_mode：手動。zone 障害は zone 復旧待ち、
            cluster 障害は再構築（OpenTofu replay）。
          - data_consistency：strong_local（PostgreSQL synchronous_
            commit=on / Ceph zone_replica=3）。
          - drill：6 ヶ月に 1 回、cluster 全断 → OpenTofu 再構築
            の dry-run。
          - 典型：開発 namespace、PoC、internal tool。本番業務
            は採用しない（DR 不可能なため）。

      - v1_multi_zone_per_cluster
          - 単一 region 内の複数 AZ（≥ 3 zone）にまたがる単一
            cluster。本番業務の標準 default。kube-apiserver /
            etcd / control plane が AZ-quorum で配置される。
          - failover_mode：自動 / 検出窓 30 秒以内。zone 障害
            時 Kubernetes scheduler が他 zone に Pod 再配置、
            Istio locality failover が L7 で隣接 zone に切替。
          - data_consistency：strong_local（PostgreSQL synchronous_
            commit=remote_write、Ceph CRUSH map で zone_failure_
            domain、Kafka rack awareness で min.insync.replicas=2
            in different rack）。
          - drill：90 日に 1 回、Litmus で 1 zone を network
            partition、SLO 維持確認。
          - 典型：本番 production cluster の default 採用。
            tier2 業務 Service、tier1 Library、tier3 SPA backend。

      - v1_multi_cluster_active_active
          - 同 region 内の複数 cluster（≥ 2 cluster）が active-
            active で並走。Argo CD ApplicationSet が複数 cluster
            に同時 deploy、Istio multi-cluster mesh で L7 routing
            が cluster 間で連続。
          - failover_mode：自動 / 連続。1 cluster 完全断でも
            他 cluster が即時 traffic 全引受。MetalLB BGP mode
            で外部 LB が cluster 跨ぎ ECMP。
          - data_consistency：eventual_async。各 cluster が独立
            の primary を持ち、storage layer は cluster 横断
            replication（Kafka MirrorMaker2 / ClickHouse Replicated
            engine / CloudNativePG cluster-to-cluster streaming）。
          - drill：60 日に 1 回、Litmus で 1 cluster をネット
            ワーク隔離、SLO + data_lag 維持確認。
          - 典型：region 内 HA を最大化、計画 maintenance を
            online で実施。tier2 高 throughput Service、tier1
            transport mesh。

      - v1_multi_region_active_passive
          - 複数 region（primary + standby ≥ 1）。書き込みは
            primary region のみ、standby region は read-only
            replica（昇格前は書込不可、昇格後は新 primary）。
            region 障害時 Argo Events が standby を promote。
          - failover_mode：自動 / 検出窓 5 分以内（promotion
            手順は predefined runbook、Argo Events trigger で
            自動実行）。意味の厳密化：partition 検出 → primary
            側 write block window 開始 → 5 分以内に standby
            promote 完了 → write 再開。RTO ≤ 5 分は「write
            block window の cap」と解釈する。promote 時は旧
            primary を fence した上で standby が新 primary に
            なる（split-brain は CloudNativePG の fence 制御
            + 09 data レプリ方針の split-brain 防止節と双方向
            lock）。
          - data_consistency：synchronous_replicated（C-priority
            during partition）。書き込み点は単一 region に固定
            された active-passive 構造なので CAP 観点で C/A の
            両立可能（partition 発生時は (a) primary 側 write を
            physical block して C 維持、(b) standby 側を read-
            only に縮退、の双方を同時採用）。Postgres
            CloudNativePG Replica Cluster で WAL streaming
            （synchronous_commit=remote_apply）、Ceph multi-
            site sync、Kafka MirrorMaker2 strict ordering。
          - partition 中の不変条件：standby region 到達不能の
            窓では primary 側 write は physical block
            （synchronous_commit=remote_apply の native 挙動、
            quorum loss で commit 完了不能）。13 SLO の
            v1_request_availability は当該 window 中、partition
            window と同等の error budget を消費する（13 SLO の
            budget と双方向 lock）。RTO ≤ 5 分の cap で write
            block window が閉じる。
          - **RPO ≈ 0**（partition 中の primary write を block
            することで「ack 済 record の standby 到達率 100%」
            を保証。durability 保証であり可視性問題は別、未確定
            commit は commit-after-crash visibility fence で
            visibility-blocking 制御。09_data/15 fence 設計と
            双方向 lock）、RTO ≤ 5 分。commit latency は
            cross-region RTT（standby region への WAL apply ack
            往復）に支配される物理制約あり（業務 SLO 13
            v1_request_latency_p99 の region-pair latency budget
            と双方向 lock）。
          - drill：30 日に 1 回、Litmus で primary region を
            network partition、standby promote → traffic shift
            → primary 復旧 → fallback の full cycle。
          - 典型：規制要件で cross-region DR が必須な業務、
            data 軸の PII / monetary を扱う Service。

      - v1_multi_region_active_active
          - 複数 region（≥ 2）が active-active で並走。書き込み
            点は cell 単位で単一 region に固定し、tenant ↔ cell
            の affinity（cell_per_region）で cross-region write
            を物理発生させない。CAP 観点では全 region 同期書込
            みは原理不可能なので、本 class は「cell-partitioned
            による per-tenant 視点の synchronous」を採用する。
            CRDT 系の真の multi-master 路線は v1 では採用しない
            （現行 OSS で MergeTree ベース CRDT が存在しないため、
            v2 候補の v2_multi_region_crdt_active_active として
            別 class 化）。
          - failover_mode：自動 / 連続。意味の厳密化：未障害
            region の cell 視点では continuous（業務無影響）。
            障害 region を home とする cell のみ predefined
            fallback cell に automatic_within_window で再
            affinity（cell promote 中は当該 cell の writes が
            短時間 unavailable）。external_dns_multi_region は
            DNS TTL に律速されるため健全 cell には適用されず、
            被影響 tenant の DNS reassign が標準で 30〜60 秒。
          - data_consistency：cell_partitioned_synchronous。
            各 cell は per-region single-leader（PostgreSQL
            CloudNativePG synchronous_commit=remote_write、
            Kafka rack-aware ISR、ClickHouse Replicated MergeTree
            + region 内 keeper quorum）で per-cell synchronous
            local。cell 跨ぎ / region 跨ぎは eventual で、
            ClickHouse macro replicas / Kafka MirrorMaker2 /
            Ceph RGW multi-site bidirectional は cell-partitioned
            topic / cell-partitioned bucket prefix 前提の read-
            replication 経路として位置付ける（同一 partition /
            object key に複数 region から同時書込まない不変条件
            を 09 data 層と双方向 lock で保証）。
          - drill：14 日に 1 回、Litmus で 1 region を完全
            isolation、未障害 cell の業務継続 + 障害 cell の
            within_window 再 affinity + cell-partitioned 不変
            条件（cross-region 同 partition write が発生していな
            いこと）の維持確認。
          - 典型：global SaaS、per-tenant 視点 24/7 zero-downtime
            業務。本企画の 1.0.0 では「採用可能 class」として
            宣言、特定業務 pack（製造業 global SCM など）が選択
            する。「全 tenant 同時 zero-downtime」は cell
            migration window 中の被影響 tenant について保証
            しない（per-cell scope で zero-downtime）。

  - 上記 5 class で v1 が covering。製造業 pack 想定 8 業務シナ
    リオの stress test を本仕様末尾に示す。

■ dimension の根拠
  - blast_radius は障害局所化の単位：
        zone     → AZ 単一の同時障害が想定上限
        cluster  → cluster 単一断 / kube-apiserver 障害が上限
        region   → region 全断 / regional cloud outage が上限
        global   → 複数 region 同時 / 大陸障害が上限
    複数粒度を重ねた表現（zone+region 等）は class 内 fixed。
  - failover_mode は復旧の起動様式：
        manual                  → 人間オペレータが trigger
        automatic_within_window → Argo Events / k8s controller
                                   が一定 window 内に trigger
        automatic_continuous    → 常時 active で復旧 trigger 不要。
                                   v1_multi_region_active_active
                                   では「未障害 cell 視点で
                                   continuous」を意味し、障害
                                   region home の cell について
                                   は automatic_within_window で
                                   再 affinity される（per-cell
                                   scope の continuous）。
    混合は class 内 fixed。
  - data_consistency は storage layer の合意モデル：
        strong_local                  → 単一 cluster 内で
                                         synchronous
        eventual_async                → cluster 間で async
                                         replication
        synchronous_replicated        → 複数 region で synchronous
                                         commit。書き込み点は
                                         単一 region に固定（active-
                                         passive 構造）。standby
                                         region は read-only、
                                         commit latency は cross-
                                         region RTT に支配される。
        cell_partitioned_synchronous  → 複数 region で cell 単位
                                         の single-leader。tenant
                                         ↔ cell の affinity で
                                         cross-region write を
                                         物理排除し、per-cell は
                                         synchronous_local、cell
                                         間 / region 間は eventual。
                                         CAP 観点では「per-tenant
                                         視点で synchronous + per-
                                         cell partition で AP」
                                         の合成。CRDT 系 multi-
                                         master は v1 で採用しない
                                         （v2 候補）。
  - control_plane_locality は kube-apiserver / Istiod / Argo CD
    の所在：
        single    → 単一 cluster の単一 control plane
        federated → 複数 cluster で別 control plane、Argo CD
                    multi-cluster で federate
        mesh      → 複数 cluster の control plane が peer-to-peer
                    で双方向同期（Istio multi-primary mesh）
  - drill_cadence_days は failover_drill の最大 interval。class
    の risk profile が高いほど短い（multi_region_active_active
    が 14 日、single_zone が 180 日）。

■ derived dimension（per-cluster threshold）を独立次元にしない理由
  - per-cluster の閾値（v1_multi_zone_per_cluster の zone 数=3
    vs v1_multi_region_active_passive の primary_zone_count=3
    + standby_zone_count=3）は本来 dimension たり得るが、5 class
    それぞれで「同じ blast_radius / failover_mode / data_
    consistency / control_plane_locality / drill_cadence_days
    構造で閾値だけが instance 別」という同形操作になる。
  - 閾値は class instantiate 時の instance 属性として宣言し、
    build artifact が Argo CD ApplicationSet generator config /
    Kyverno admission policy / Litmus chaos experiment を生成
    する形に統一。
  - infra オペレータ / 業務側で迷う余地がないため、独立 dimension
    化する利得が乏しい。

■ 5 種類 failover orchestrator の責務分離（特殊機構）
  - orchestrator 1: kubernetes_pod_eviction
      - v1_multi_zone_per_cluster の主担当。Kubernetes scheduler
        + topology_spread_constraints + pod_disruption_budget
        + node_affinity で zone 障害時の Pod 再配置を駆動。
      - kubelet eviction / NodeNotReady taint / cordon が層 E
        の物理 trigger。

  - orchestrator 2: istio_locality_failover
      - v1_multi_zone_per_cluster / v1_multi_cluster_active_
        active の主担当。Istio destination rule の outlier_
        detection + locality_lb_setting で L7 routing を zone /
        cluster 跨ぎに自動切替。
      - 07 transport の messaging_bridge constraints と整合。

  - orchestrator 3: metallb_bgp_failover
      - v1_multi_cluster_active_active の主担当（外部 LB
        layer）。MetalLB BGP mode で複数 cluster からの ECMP
        announcement、外部 router が cluster 障害を BGP withdrawn
        で検出。
      - kube-vip は control plane VIP を担当し、data plane VIP
        は MetalLB が担う。

  - orchestrator 4: argo_rollouts_traffic_shift
      - v1_multi_cluster_active_active / v1_multi_region_
        active_passive の主担当（progressive delivery layer）。
        Argo Rollouts AnalysisTemplate で SLO ベース自動 rollback、
        Argo Events で region promotion を trigger。
      - 13 SLO 適合仕様の error budget freeze と直結。

  - orchestrator 5: external_dns_multi_region
      - v1_multi_region_active_passive / v1_multi_region_active_
        active の主担当（DNS layer）。external-dns が cluster
        endpoint を DNS provider に publish、failover 時に DNS
        weight / health check を切替。
      - cert-manager + DNS01 ACME challenge が region 跨ぎで
        証明書を維持。

  - 5 orchestrator は順次評価される（k8s scheduler → Istio →
    MetalLB → Argo Rollouts → external-dns）が、各 topology_
    class は 1 orchestrator を「主担当」として宣言。他層は補助
    的に協調動作（例：v1_multi_zone_per_cluster の主担当は
    kubernetes_pod_eviction だが、Istio locality failover が
    L7 で副担当）。

■ 5 層 defense-in-depth

  ── 層 A : compile 時（topology_class 注釈必須）
      - Argo CD ApplicationSet generator の generator config 全
        entry に `infra.topology.topology_class` 注釈が必須。
        注釈なしの ApplicationSet は build fail。
      - Kustomize overlay の root kustomization.yaml にも同注釈
        必須。Helm chart は values schema で topology_class を
        required field 化。
      - 注釈に書ける topology_class 値は classes.yaml の keys
        のみ。15 capacity の quota_class 注釈と同型。

  ── 層 B : lint
      - Conftest custom rule（Rego policy）：Argo CD / Kustomize
        / Helm に書かれた infra.topology.topology_class が
        classes.yaml に存在し、instance_attributes_required を
        満たす値が cluster_inventory.lock.yaml で declare されて
        いること。
      - kubeval / kubeconform snapshot に対し、topology_class
        注釈なしの manifest を fail。
      - 14 OSS lifecycle 適合仕様の oss_inventory.lock.yaml と
        本仕様の cluster_inventory.lock.yaml の Kubernetes /
        Istio / MetalLB / kube-vip / Argo CD / cert-manager /
        OpenBao バージョンが整合していること（cross-axis lint）。

  ── 層 C : failover_drill chaos test（Litmus）
      - 13 SLO 適合仕様の chaos_injection_validates_alert と同型
        に、本仕様は zone_partition / cluster_partition / region
        _partition_passive / region_partition_active の 4
        scenario を chaos test として実装。
      - シナリオ：Litmus が cluster の zone / cluster / region
        単位で network partition を注入し、5 orchestrator が
        正しく順次 trigger することを property test で検証。
        13 の v1_request_availability / v1_request_latency_p99
        / v1_event_freshness が SLO 違反しないことを観測。
      - 違反検出時は 13 の error budget freeze 経路と直結し、
        当該 region への deploy が物理的に block される（13 と
        infra01 の cross-axis 連動）。

  ── 層 D : runtime（5 orchestrator の実 deploy）
      - kubernetes_pod_eviction（topology_spread + PDB）/ istio_
        locality_failover / metallb_bgp_failover / argo_rollouts
        _traffic_shift / external_dns_multi_region の各 orchestrator
        が deploy されていることを Kyverno admission policy で
        確認。
      - cluster_inventory.lock.yaml の topology_class 宣言と
        異なる runtime config（topology_spread_constraints の
        欠落、Istio locality 設定の欠落、MetalLB BGP peers の
        欠落等）を持つ deploy は admission reject。
      - failover event は 09 audit signal sub-class
        `topology.failover.event` として ClickHouse に bulk
        insert。

  ── 層 E : 物理 enforcement（unbypassable な layer）
      - kube-apiserver multi-AZ etcd quorum：etcd raft 物理層
        で zone failure_domain を強制。Library bypass / 直接
        etcdctl 経路でも回避不能。
      - Ceph CRUSH map zone topology：Ceph OSD 物理層で zone /
        host failure_domain を強制。
      - Kafka rack awareness：Kafka broker process が partition
        replica を rack 跨ぎに配置。Library 経路に依存しない。
      - CloudNativePG Replica Cluster：PostgreSQL synchronous
        replication が WAL 物理層で強制される。
      - external-dns DNS provider：DNS provider 側 health check
        が region failure を物理検出、Argo CD / Kyverno の文
        章運用に頼らない。
      - 本層は文章運用に頼らず物理 enforcement に転写する最終
        safety net（13 / 14 / 15 と同型）。

■ failover_drill property（特殊機構）
  - 「drill_cadence_days 以内に必ず failover を実演し、宣言
    された RTO / RPO 内に収束する」を property test として CI
    で必ず green を返すことを必須化：
        ∀ cluster c with c.topology_class ≠ v1_single_zone:
          now() - c.last_green_at ≤ c.drill_cadence_days × 86400
          AND c.rto_observed ≤ c.rto_max
          AND c.rpo_observed ≤ c.rpo_max
        MUST hold

  - 検証手順：
      1. Litmus で cluster の topology_class に対応する scenario
         （zone_partition / cluster_partition / region_partition
         _passive / region_partition_active）を実演。
      2. 13 v1_request_availability / v1_request_latency_p99
         / v1_event_freshness の recording rule を観測。
      3. 観測 window（30s, 1m, 5m）で SLO target を維持して
         いること、RTO / RPO 内に収束していることを assertion。
      4. 違反検出は 13 alert + infra01 audit signal + 14 lifecycle
         signal（OSS の topology 性質起因の場合）を同時 emit。

  - property に違反した場合の対応：
      - drill 未実施 → admission block 発動、新規 deploy 停止、
        oncall 即時通知。
      - RTO / RPO 違反 → instance attribute の調整 PR（zone 数
        増加、replica 数増加 等）、または topology_class 変更
        PR（v1_multi_zone_per_cluster → v1_multi_cluster_active
        _active へ昇格）。
      - orchestrator bypass 経路発覚 → 層 D / E で塞ぐ admission
        policy 追加 PR。
      - OSS 固有の topology 機能不足 → 14 の v1_l1plus_pair_
        target への移行 trigger 候補（fork / pair_target
        reevaluation）。

■ Capability Negotiation との関係
  - 03 / 10 / 11 / 12 / 13 / 14 / 15 と並ぶ chosen_topology_
    backend を起動時に決める：
      1. 全 topology_class C を取得。
      2. cluster_inventory.lock.yaml で C を topology_class に

      3. constraints 節を満たさない cluster を B から除外。

         topology_backend を返却。

    build artifact、deploy 中に動的に書き換わらない。

■ v2 拡張ルール
  - 新 class の追加は purely additive：v1 class はそのまま残し、
    v2 で新規 class（例：v2_edge_cluster_at_factory_floor、v2_
    hybrid_onprem_cloud、v2_air_gapped_classified）を追加する。
  - 既存 class の dimension 値変更は破壊的変更（major version
    up）。
  - 命名は vN_<scope>_<failover_kind> 形式に固定。
  - dimension override 禁止の規律は v1 → v2 跨ぎでも維持する。
  - edge / on-prem / air-gapped 採用は v2 候補。v1 は cloud-
    native managed / unmanaged Kubernetes に固定。

■ 長期収斂への作用
  - 本仕様の 4 ファイル（classes / scenarios / cluster_inventory
    / failover_drill）に対し、新業界 pack / 新 cluster の追加
    は purely additive。tier1 / tier2 / tier3 / data アプリは
    Argo CD ApplicationSet に topology_class 注釈を書き、yaml
    に instance attribute（zone_ids / region_ids 等）を宣言
    すれば残りは機械的に降りる。
  - L1+「単一 OSS 深耕 + 移行コミットメント」の哲学を topology
    軸に転写したもの（単一 orchestrator 規律 + cluster topology
    移行コミットメント）。Kubernetes / Istio / MetalLB / kube-
    vip / Argo CD / Argo Rollouts / Argo Events / cert-manager
    / OpenBao / Kyverno / Litmus が L1+ primary、各々の
    lifecycle event は 14_OSSライフサイクル適合仕様で管理。
  - failover_drill property の機械検証により、運用上「机上の
    DR plan で実演されない」事故の物理的不可能化を 1.0.0 で
    確立する。これは至高路線の「文章運用ではなく物理
    enforcement」原則の transposed form として 13 軸の topology
    軸を担う。
  - 13 軸（07 transport / 08 migration / 09 observability / 10
    auth / 11 key / 12 schema / 13 SLO / 14 OSS lifecycle / 15
    capacity / 32 data-tenant / 39 client / infra01 topology /
    data01 preservation）が同型構造で結合し、tier1 / tier2 /
    tier3 / infra / data の責務分離と接合面が機械的に検証可能
    になる。本仕様 infra01 はその topology piece として、5
    階層全体の物理基盤の単一の真を担う。
