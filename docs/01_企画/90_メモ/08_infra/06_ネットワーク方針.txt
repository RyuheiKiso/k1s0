============================================================
infra ネットワーク方針
============================================================

■ 一文方針
  - L4 は MetalLB / kube-vip、L7 は Envoy Gateway / Istio で
    統一。multi-cluster / multi-region は Istio multi-primary
    mesh と external-dns で連結する。

■ CNI（Container Network Interface）
  - L1+ primary：Calico（BGP mode）。
  - rationale：
      - eBPF data plane を選択肢として持ちつつ（Calico eBPF
        mode）、kernel-routing も併用可能
      - NetworkPolicy 完全実装
      - MetalLB BGP mode との相性
  - v2 候補：Cilium（eBPF 専用、Istio ambient と組合せ）。
    14 OSS lifecycle 適合仕様の pair_target で評価。

■ MetalLB（data plane LB）
  - mode：本番 cluster で BGP mode 必須、開発で Layer2 mode
    許容。
  - BGP peer：cluster 外 router（ToR / spine / cloud BGP
    endpoint）と speaker Pod が peer。
  - IP プール：tier 別に分離（tier1-services / tier2-services
    / tier3-public / tier3-private / data-internal）。
  - v1_multi_cluster_active_active：複数 cluster からの ECMP
    announcement、外部 router が anycast で受信。

■ kube-vip（control plane VIP）
  - mode：BGP mode を default、Layer2 は dev のみ。
  - control plane の HA：kube-apiserver は port 6443 で
    listen、kube-vip が VIP を制御 plane node 間で float。

■ Istio service mesh
  - data plane：sidecar mode（v1）、ambient mode（v2 候補）。
  - mTLS：PERMISSIVE で開始、3 ヶ月以内に STRICT へ強制。
    Kyverno admission policy で STRICT 維持を validate。
  - locality_lb_setting：zone / cluster / region 距離に応じた
    failover を 15_クラスタ位相適合仕様 の topology_class
    に基づき自動設定。
  - root CA：cluster 単位の sub-CA、cluster 跨ぎ root は
    OpenBao が発行（11 鍵管理適合仕様）。
  - multi-cluster：multi-primary mesh、共通 root CA、cross-
    cluster service discovery は Istio が担う。

■ Envoy Gateway
  - role：tier1 Transport Adapter Layer の substrate。HTTP/2
    + gRPC / HTTP/3 + WebTransport / HTTP/1.1 Upgrade
    （WebSocket）/ HTTP/1.1 chunked + SSE（text/event-stream、
    tier1 Rust ハンドラが SSE フレーミングを直接生成、Envoy
    gRPC-JSON Transcoder は unary 専用）を同一 cluster で
    並立。詳細は 05_tier1/03_Server系「External Proto」server-
    streaming の項を参照。
  - rate limit：Local Rate Limit filter で 15_テナント容量
    適合仕様 の v1_per_tenant_qps を enforcement。cluster
    跨ぎ global rate limit は v2 候補。
  - JWT 認証：JWKS は Keycloak から取得、tenant_id を JWT
    claim から ingress filter で抽出。10 認証適合仕様 と
    整合。
  - TLS：cert-manager + Let's Encrypt / 内部 CA。TLS 1.3
    必須、TLS 1.2 は legacy 経路（.NET Framework Companion）
    のみ許容、deprecation timeline は 12 ヶ月。

■ DNS
  - cluster 内：CoreDNS（Kubernetes default）。
  - cluster 外：external-dns で cluster Service / Ingress
    を DNS provider（Route53 / Cloud DNS / 内部 BIND）に
    publish。
  - multi-region：external_dns_multi_region orchestrator が
    region 単位の health check + weight で routing。15_クラ
    スタ位相適合仕様 の v1_multi_region_active_passive /
    v1_multi_region_active_active で必須。

■ NetworkPolicy
  - default deny：全 namespace で default deny ingress /
    egress を Kyverno admission policy で強制。
  - 通信許可：
      - tier1 ↔ tier2 ↔ tier3 の許可される通信を Kustomize
        overlay で declarative に宣言
      - data 層への通信は data-stores namespace への egress
        許可で制限
      - infra-tools への通信は admin operator + Argo CD
        sync 経路のみ
  - cluster 間通信：Istio multi-primary mesh で mTLS、source
    cluster の identity を destination 側で validate。

■ HTTP/3 + WebTransport
  - Envoy Gateway HTTP/3 listener を本番 cluster で必須化。
  - QUIC は UDP/443、firewall で許可。
  - HTTP/3 fallback：クライアントが HTTP/3 を notiate しない
    場合は Alt-Svc header で advertise、HTTP/2 にも fall back
    可能。

■ WebSocket / Long-poll
  - Envoy Gateway HTTP/1.1 Upgrade で WebSocket、long-poll
    は HTTP/1.1 chunked。Istio L7 routing は WebSocket /
    long-poll connection の zone affinity を維持。

■ ingress / egress 監視
  - Kubeshark で API トラフィックの ad-hoc 監視。
  - Istio access log を OTel Collector 経由で ClickHouse
    に転送（09 観測可能性 SoR）。
  - eBPF + Pixie 等の追加 observer は 14 OSS lifecycle
    適合仕様の pair_target 候補（v2）。

■ failover orchestrator（network 層の責務）
  - istio_locality_failover：L7 routing の zone / cluster /
    region 跨ぎ自動切替。
  - metallb_bgp_failover：cluster 全断時の BGP withdrawn /
    ECMP shift。
  - external_dns_multi_region：region failover 時の DNS
    weight 切替。
  - 各 orchestrator の責務分離は 15_クラスタ位相適合仕様
    「5 種類 failover orchestrator」節を参照。
