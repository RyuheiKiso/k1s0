============================================================
infra 非提供スコープ
============================================================

■ 提供しない（明示的に out-of-scope）
  - ビジネスロジック / ドメイン業務処理
      → tier2 / tier3 の責務。
  - tier1 Library / Server 系の RPC / Repository 実装
      → 05_tier1 の責務。infra は kube-apiserver / Envoy
        Gateway の物理基盤までを提供。
  - 個別業務の SLI / SLO 定義値（latency target / availability
    target の数値）
      → 13_SLO適合仕様 + tier2 / tier3 の instance attribute。
  - テナント別 quota の閾値値（qps_limit / hot_byte_limit 等）
      → 15_テナント容量適合仕様 + tier2 / tier3 の instance
        attribute。infra は enforcement_layer の物理層を提供
        するだけ。
  - data の lifecycle 値（retention 日数 / archive_to_offline
    cadence 等）
      → 09_data の責務。infra は storage substrate のみ提供。
  - schema 進化の意味論（compatibility / breaking change の
    判定）
      → 12_スキーマ進化適合仕様 の責務。
  - 暗号鍵の rotation cadence / KEK / DEK の階層構造
      → 11_鍵管理適合仕様 の責務。infra は OpenBao 物理基盤
        と External Secrets 配信経路のみ提供。
  - 認証 issuer / JWT signing 鍵の発行
      → 10_認証適合仕様 + Keycloak。infra は cert-manager と
        OpenBao 物理基盤のみ提供。
  - tier3 SPA の UI コード / フォーム規約
      → 07_tier3 の責務。

■ 採用しない OSS / 技術
  - Grafana：AGPL のため。代替は Perses（02_採用OSS一覧 参照）。
  - OpenSearch：観測可能性 SoR は ClickHouse 一本。BM25 / 形態素
    解析は業務 SLO に持たない。
  - HashiCorp Vault：BUSL のため、シークレット管理は OpenBao
    （MPL 2.0 fork）。
  - Confluent Schema Registry v5+：Confluent Community License
    （OSI 非準拠）のため、代替は Apicurio Registry / Karapace。
  - クラウド固有 LB / managed Kubernetes：vendor lock-in を
    避けるため、cluster は素の Kubernetes（kubeadm / kops /
    cluster-api）+ MetalLB + kube-vip。クラウド managed K8s
    での動作は対応するが、 hard dependency は持たない。
  - service mesh の Linkerd / Cilium Service Mesh：Istio の
    L1+ 深耕のため、横並び mesh は採用しない（v2 候補は 14
    OSS lifecycle 適合仕様の pair_target で評価）。

■ 採用しないアーキテクチャ
  - hand-rolled cluster bootstrap：OpenTofu / kubeadm / cluster-
    api のいずれかに固定。手動 kubectl apply で cluster を
    bootstrap する経路は持たない。
  - 単一 zone での本番運用：v1_single_zone は dev/stage 専用。
    本番は最低 v1_multi_zone_per_cluster（zone ≥ 3）。
  - manual failover の本番採用：v1_single_zone を除く全 class
    は automatic failover_mode を必須化。runbook を人間が叩く
    だけの DR plan は採用しない（drill が機械的に検証不能な
    ため）。
  - GUI 操作による cluster 構築 / 廃棄：Headlamp / Backstage
    は読み取り / 限定的 trigger 専用。cluster 状態を変更する
    操作は GitOps（PR + Argo CD sync）経路のみ。
  - mixed-version cluster 長期運用：Kubernetes minor version
    の skew は ≤ 1 minor、かつ rolling upgrade window は ≤ 30
    日。長期 mixed-version 運用は dead spec として CI fail。

■ v2 候補（v1 で採用しないが将来検討）
  - edge cluster / on-prem hybrid（v2_edge_cluster_at_factory
    _floor、v2_hybrid_onprem_cloud）
  - air-gapped cluster（v2_air_gapped_classified）
  - cross-cluster global rate limit（Envoy Cluster External
    Rate Limit / gRPC RLS service） — 15 capacity の v2 と
    並走候補
  - serverless / Knative：本企画の Library 中心モデルと整合
    しないため v1 は不採用、v2 で必要性再評価。
  - cilium eBPF data plane / Cilium ServiceMesh：14 OSS
    lifecycle 適合仕様の pair_target 候補として v2 で評価。

■ 至高路線における判断
  - 「現実的に運用が楽」を理由に scope を縮小しない。
    drill cadence・supply chain 検証・admission policy 適用
    は最大化する。
  - 「業務が独自に kubectl で操作したい」を理由に GitOps
    経路を緩めない。drift は CI が必ず検出する。
  - 「採用 OSS を増やしたい」を理由に L1+ 単一深耕を緩めない。
    新 OSS は 14 OSS lifecycle 適合仕様の pair_target 移行
    手続を経る。
