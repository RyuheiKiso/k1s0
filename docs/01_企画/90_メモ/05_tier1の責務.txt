============================================================
tier1 の責務（infra 隠蔽）
============================================================

■ 方針
  - tier1 は、tier2 / tier3 に infra 層を意識させないことを使命とする。
  - infra 層の OSS / ミドルウェアへのアクセスは tier1 のファサードを
    経由させ、tier2 / tier3 から直接利用させない。
  - tier1 ファサードは Rust crate 群として自製

■ 背景・狙い
  - 例：tier2 が独自に Kafka を直接利用していた場合、Kafka がライセンス
    変更等で利用不可となり RabbitMQ への差し替えが必要になった際、
    変更箇所の特定に大きな工数を要する。
  - tier1 で infra をラップしておけば、差し替え時の影響範囲を tier1 に
    限定でき、tier2 / tier3 の改修を最小化できる。
  - tier2 / tier3 のエンジニアは OSS の動向やライセンスに必ずしも
    精通しているわけではないため、選定・追従の責務は tier1 に集約する。

■ Dapr 不採用の理由
  - 採用 OSS を決め打ちする方針のため、Dapr のような複数バックエンド
    対応の汎用 runtime は機能過剰であり、サイドカー運用コストに
    見合わない。
  - tier1 言語を Rust に絞る前提のため、Dapr のサイドカー型による
    多言語対応は本来要件ではない。
  - 外部 runtime 自体がライセンス変更・廃止された際の撤退コストを
    企画段階で消す。
  - tier1 を自製した場合でも、無償で利用できる Rust クライアント
    （rdkafka、redis-rs、sqlx、tonic など）の上に薄く乗せるため、
    Dapr クローンを作るような大規模実装にはならない。
