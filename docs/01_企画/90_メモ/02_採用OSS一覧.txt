[0] OSS license 規律
------------------------------------------------------------
  - 本企画の OSS 採用規律は次の階層で構成される（旧表現「全
    Apache 2.0 統一」は撤回し、本節 + linkage_model で精密化
    する）:

      (a) primary 許容 license（OSI-approved permissive）:
          Apache 2.0 / MIT / BSD-2/3 / MPL-2.0 / EPL-2.0 /
          ISC / PostgreSQL License / Unlicense / NCSA。
          静的 link / 動的 link / process boundary / network
          service のいずれの linkage でも採用可。
      (b) LGPL（LGPL-2.1 / LGPL-3.0）:
          dynamic linkage または network service / process
          boundary 経路でのみ採用可。静的 link 言語（Go /
          Rust）への組込は禁止。
      (c) GPL（GPL-2.0 / GPL-3.0）/ Affero GPL なき GPL:
          process boundary（subprocess 起動 / CLI / 別 binary
          配布）または network service 経路でのみ採用可。
          配布バイナリへの静的 / 動的リンク組込は禁止。
      (d) AGPL / SSPL / BSL / Confluent Community License /
          Elastic License v2 / その他 OSI 非準拠 commercial
          source-available license:
          採用禁止（既採用が判明した時点で 14_OSSライフ
          サイクル適合仕様 の代替探索 trigger 起動）。
      (e) 例外（OS provider native API） :
          **business core は OSS only** を貫くが、**escalation
          last-mile の OS provider native push（APNs : Apple
          Push Notification service、FCM : Firebase Cloud
          Messaging）は OS 仕様の必然的 dependency として明示
          例外** とする（iOS 上のバックグラウンド push は OS
          設計上 APNs を経由せざるを得ず、Android も Google
          Play Services 環境では FCM が事実上唯一の経路）。
          本例外は :
            - 適用範囲を **ops-edge escalation cluster の last-
              mile 通知経路に限定**。business core ワークロード
              は本例外の SLA に依存させない。
            - APNs / FCM の停止は escalation の delivery latency
              劣化に留まり、business core の SLO には影響させ
              ない設計（11_ops/16_ops_edge_cluster の degrade
              経路と整合）。
            - 「OSS のみ」原則の honest な書き換えとして本企画
              文言は「business core OSS only + last-mile OS
              native push 例外」と読む（08_infra/03_非提供スコープ
              の「クラウド固有 / 商用」全否定文言にも同等の honest
              化が施される、双方向 lock）。
            - APNs / FCM 例外は OSS 化代替を持たないため
              14_OSSライフサイクル適合仕様 の代替探索 trigger
              からは恒久的に除外（trigger を引かない）。

  - linkage_model 列の標準値（catalog 各エントリに導入）:
      - dynamic            : 動的リンク（共有ライブラリ / dlopen）
      - static             : 静的リンク（Go / Rust の compile-time
                             link）
      - process_boundary   : 別 process / 別 binary としての起動
                             （subprocess / CLI / sidecar）
      - network_service    : 独立 service として network 越しに
                             利用（HTTP / gRPC / SQL 経由）
  - 各 OSS catalog エントリは linkage_model を明示する責務を
    持つ。明示なき場合は static + dynamic 両許容を default と
    みなす（permissive 系のみ default 許容）。
  - linkage_model と license の整合性は CI で license-checker /
    cargo-deny / dotnet-licenses で物理検査する。違反 PR は
    GitHub Actions Required Status Check + Conftest（OPA Rego）
    で merge block する（**PR 段の merge gate**、check 名は
    `dcv_pr_blocks_license`）。さらに deploy 段の Kubernetes
    admission（Kyverno）でも image / manifest に license 違反
    artifact が混入していないことを物理検査し、admission reject
    で deploy を block する（**deploy 段の admission gate**、
    検査名は `dcv_kyverno_blocks_license`）。本企画では「Kyverno
    で merge block」の旧表現を「Conftest で PR merge block +
    Kyverno で admission deploy block」の二段に書き分ける規律と
    する（Kyverno は admission webhook であり PR merge を直接
    block する権限を持たないため。詳細は 08_infra/04_採用OSS の
    Kyverno 注記参照）。

  ※ Envoy Gateway は API ゲートウェイ用途に加え、tier1 の Transport
    Adapter Layer の substrate を担う。HTTP/2 + gRPC、HTTP/3 plain
    （QUIC + HTTP semantics、v1 必須）、HTTP/3 + WebTransport
    （`draft-ietf-webtrans-http3`（IETF Internet-Draft、RFC 化前
    段階）の extended-connect + RFC 9297 HTTP Datagrams、**v1 / v2
    ともに opt-in 扱い、Envoy native upstream の WebTransport 実装
    GA + draft-ietf-webtrans-http3 の RFC 化を migration_trigger と
    して 14_OSSライフサイクル適合仕様 の deprecation_clock に登録、
    本企画として v2 で必須化することは事前約束しない**）、
    HTTP/1.1 Upgrade（WebSocket）、HTTP/1.1
    + chunked SSE（text/event-stream）等の transport を同一クラスタ
    内で並立
    させる。本企画では Envoy Gateway（C++）が独立 upstream Pod の
    tier1 Rust SSE ハンドラへ HTTP/1.1 chunked で proxy し、Pod 間
    mTLS は Istio sidecar が担う。tier1 Rust ハンドラ Pod が
    server-streaming RPC を text/event-stream として直接生成し、
    Envoy gRPC-JSON Transcoder は unary の HTTP/1.1 + JSON 派生に
    限定する。**Envoy gRPC-JSON Transcoder 自体は server-streaming
    RPC を `stream_newline_delimited` option 等で NDJSON / JSON-array
    として派生可能であるが、SSE フレーミング (id: / event: / retry:)
    を持たないため Last-Event-ID resume を救えない**。本企画は
    resume_token を Last-Event-ID 標準に乗せる規律 + event: で
    制御情報を proto 外に正規搬送する規律を持つため、server-streaming
    の wire 派生は Transcoder ではなく **tier1 Rust ハンドラで SSE
    を直生成** する経路に固定する（Transcoder への SSE 派生 option
    (stream_sse_style_delimited 相当) は存在せず、本企画として上流
    寄稿はスコープ外、tier1 Rust ハンドラ内実装で SSE フレーミング
    規約を完全制御する）。SSE を採用するのは、id: フィールドが
    Last-Event-ID として標準化されており resume_token の wire 表現を
    実装独自に拡張せずに済む点と、event: / retry: により adapter 層が
    扱うべき制御情報を proto 外で正規に運べる点による（NDJSON では
    これらをヘッダや独自フィールドで再発明する必要がある）。bidi
    semantics は proto に宣言された意味論を単一の真とし、各 transport
    adapter が conformance proof で等価実装する。client-streaming は
    当面 External Proto に直接出さず unary 射影（resumable upload
    形式）で扱う。詳細は「05_tier1/03_Server系」Proto 二層化 /
    Transport Adapter Layer を参照。

  ※ Connect-RPC は Browser SPA capability_class=web の bidi
    primary として v1_l1plus_primary 採用するが、**fetch full-
    duplex streams の実装は UA 別に乖離している**（Chromium
    105+ 安定、Safari 17.4 / Firefox 安定 release は request
    body streaming 未対応）。本企画は ua_subclass 軸で primary
    を分割する :
      - chrome_edge / tauri_native : Connect-RPC over HTTP/2
        / HTTP/3、fetch full-duplex を要求する `connect_bidi_
        native` adapter を primary。
      - firefox_safari / dotnet_companion : `paired_post_sse`
        adapter（POST /open + SSE + POST /send + POST /close
        の 3 endpoint で半二重 emulation、12_client/17 で詳説）
        を **first-class 経路として併設**、bidi semantics は
        05_tier1/07_Bidi適合仕様 の bidi conformance class で
        property_axiom により完全等価を CI 検査。
    `requires_fetch_full_duplex_streams` は boolean ではなく
    `{chrome_edge: true, firefox_safari: false, dotnet_
    companion: false, tauri_native: true}` の ua_subclass 別
    map として capability_matrix.lock.yaml に登録する（client
    12 / 06 Transport 適応方針 / 12_client/15, 17 / tier1 07
    Bidi 適合仕様 と双方向 lock）。Envoy Gateway 内で gRPC-Web
    filter と並走させ、HTTP/2 over TLS / HTTP/3 over QUIC を
    wire とする。Connect-RPC と gRPC は同一 .proto から並走
    codegen され、SDK 内部で adapter として自動 negotiation
    される（アプリ作者は wire 種別を意識しない）。WebSocket-bidi
    （自製 protobuf binary frame）は v1 不採用（自製 frame
    protocol 禁止と整合）。

  -------------------------------+----------------------------------+-----------------------

  テレメトリパイプライン         | OpenTelemetry Collector          | Apache 2.0
  メトリクス                     | Prometheus                       | Apache 2.0
  ログ / トレース SoR            | ClickHouse                       | Apache 2.0
  ClickHouse Operator            | Altinity ClickHouse Operator     | Apache 2.0
  トレース UI                    | Jaeger v2 (v1.50+) 内蔵          | Apache 2.0
                                 |   ClickHouse storage             |
                                 |   (jaegertracing/jaeger,         |
                                 |    first-party)                  |
  ログ / ad-hoc 探索 UI          | Apache Superset                  | Apache 2.0
  Continuous Profiling           | Parca                            | Apache 2.0
  k8s 状態メトリクス             | kube-state-metrics               | Apache 2.0
  k8s Web UI                     | Headlamp                         | Apache 2.0
  API トラフィックビューア       | Kubeshark                        | Apache 2.0
  メトリクス可視化               | Perses                           | Apache 2.0

  ※ 観測可能性 SoR は **log / trace は ClickHouse、metric は
    Prometheus**（Prometheus exemplar 経由で trace_id を metric 上に
    連結、Perses で UI 統合）。log / trace を単一のカラムナストアに
    格納することで、trace_id を軸にした SQL JOIN や横断集計を
    可能にする。metric は時系列の supply / aggregation 特性が ClickHouse
    では非効率（cardinality 爆発、recording rule の semantics 不一致）
    であるため Prometheus を SoR として併存、両 SoR は exemplar /
    trace_id で連結する（「ClickHouse 一本」表現は log / trace に
    限定する honest 化）。OpenSearch は採用しない（観測可能性ワーク
    ロードは BM25 ランキングや形態素解析を業務 SLO に持たず、構造化
    集計が支配的なため、カラムナ OLAP のほうが構造的に最適）。
  ※ trace の SoR 化は **Jaeger v2 が内蔵する OTel Collector
    distribution（`jaeger-v2` 配布、Apache 2.0、active maintained）**
    を採用する。本 distribution は OTel Collector を Jaeger 公式の
    取込み経路として bundle するため、Collector → Jaeger 形式の
    変換は本 distribution が公式パスで担い、両者の中間 schema を
    本企画が独自にキャストする運用を回避する。
    ClickHouse 内のストレージ配置は :
      - `otel_traces` schema（OTel Collector の clickhouseexporter
        が出力する OTel native 形式、CNCF OTel Contrib、Apache 2.0）
      - `jaeger_*` schema（Jaeger v2 内蔵 ClickHouse storage が
        出力する Jaeger native 形式）
    の **2 schema を別 database に物理分離して併存** させる
    （単一の SoR テーブル invariant は維持できないため "2 schema
    別 database 併存" を honest に明示）。CI 整合検査は **同一
    trace_id が両 schema に同タイミングで存在することを property
    test で確認**（schema 互換性の物理確認は不可能、trace_id
    保持の equivalence 確認に意味論を絞る）。jaegertracing/jaeger-
    clickhouse community plugin（Jaeger v1 用 gRPC storage plugin）
    は 2023 年に archive 済かつ Jaeger v2 で plugin protocol 自体
    が廃止されたため、v1 採用候補から除外する。Jaeger UI はトレース
    調査専用 UI として位置付け、ad-hoc 解析は Apache Superset over
    ClickHouse（`otel_traces` schema 側）に寄せる。
  ※ メトリクス可視化は Perses（CNCF Sandbox、Apache 2.0）を標準採用する
    （Grafana の AGPL 回避方針は維持）。データソースは Prometheus 系に
    限定する。
  ※ ログ / トレースの ad-hoc 探索 UI は Apache Superset（Apache 2.0）
    を併用する（ClickHouse データソース）。tier3 が「テナント × エンド
    ポイント × latency」等を SQL ベースで探索する経路として位置付ける。
  ※ 全文検索（BM25・形態素解析）は観測可能性 SoR の業務要件に入らない
    ため、Library カテゴリには含めない。tier3 業務固有で必要な場合は
    Library 抽象の外で個別に検索エンジンを立てる。
  ※ ClickHouse の運用は Altinity ClickHouse Operator を採用する。
    Tiered storage（hot SSD + cold S3 = Ceph RGW）は MergeTree の
    disk_s3 で透過化する。tail-based sampling は OpenTelemetry
    Collector の tail_sampling processor で実施する（Library 表面には
    出さない）。
  ※ .NET Framework 向けには OpenTelemetry .NET Auto-Instrumentation
    （CLR Profiler アタッチ方式、Apache 2.0）を併用する。tier1 Library
    を直接組み込めない言語向けの Companion（観測可能性 + Transport
    Negotiation の二役割）の観測可能性役割の標準形態として位置付ける。
    Auto-Instrumentation 非対応環境（4.6.1 以前など）向けには NuGet
    参照型の Companion を補助的に提供する。CLR Profiler は HTTP/2 /
    HTTP/3 stack を持たない WinHTTP / HttpWebRequest の上に新たな
    wire protocol（WebSocket / SSE / HTTP/3）を生やせないため、
    Transport Negotiation 役割（役割 B）は OpenTelemetry
    Auto-Instrumentation の CLR Profiler 経路から独立した NuGet 参照
    （k1s0.Companion.NetFx、IL rewrite ではない通常のライブラリ参照）
    として配布する（詳細は「05_tier1/04_Library」Companion 節 役割
    A / 役割 B）。
