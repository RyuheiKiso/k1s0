============================================================
security 位置づけ
============================================================

■ 5 階層 + 横断 layer 中の位置
  - tier1 : システム共通処理（Library / Server / 認証 /
            観測可能性）
  - tier2 : ドメイン業務共通化処理
  - tier3 : 個別業務の Web サイト / exe
  - infra : 物理 / 仮想基盤 + 制御平面
  - data  : データ層（保全 / lifecycle / 暗号化）
  - security : 全層を直交に貫く「脅威 ⊗ 軸 ⊗ 層」 invariant
              の管掌 layer ← 本層

  - security は tier1 / tier2 / tier3 / infra / data の上下
    左右に並列して存在するのではなく、5 階層 × 13 軸の
    grid を直交に貫く meta-layer として位置づく。security
    は新しい責務を宣言するのではなく、既存軸の defense-in-
    depth 層 A〜E に「脅威モデル下で必須となる mitigation
    が cross-axis で重複なく漏れなく詰まっていること」を
    保証する。

■ 上下方向の関係
  - 上方向（5 階層が security に依存する経路）：
      - tier1 認証（10）→ session / token の compromise 経路
            を脅威モデルに登録、audit_event subject 経由で
            security に流れる
      - tier1 鍵管理（11）→ 鍵 exposure 時の crypto-erase
            経路を security の IR playbook に bind
      - tier1 観測可能性（09）→ audit_event subject の
            immutability を security が cross-axis lock
      - tier2 RLS FORCE（32）→ tenant ⊥ PII の交点を脅威
            モデルに register、PII class 列が tenant_id と
            必ず joint で扱われることを security が assert
      - tier3 client 状態（39）→ client-side cache / IndexedDB
            の PII 漏洩経路を脅威モデルに登録
      - infra topology（infra01）→ control-plane / supply-
            chain の trust boundary を security が定義
      - data preservation（data01）→ archive_to_offline /
            crypto_erase / WORM Object Lock の物理経路を
            security の脅威モデル mitigation として bind

  - 下方向（security が他層に依存する経路）：
      - 物理 enforcement の道具立て：
          - Kyverno admission policy（infra 14）
          - DB engine 物理機構（data 14）
          - 鍵階層（tier1/11）
          - 認証 token（tier1/10）
          - PII 暗号化（tier2/22 / 28）
        は全て他層が提供する。security は「これらが脅威
        モデル中の mitigation 経路として bind されている
        こと」を cross-axis assertion で保証するのみ。
      - audit_event の SoR：09 観測可能性 SoR（ClickHouse）
        を物理 store として共用、security は subject schema
        と immutability 規律を宣言。

■ 横方向の関係（security ↔ 各軸）
  - security ↔ 07 transport：
      - bidi stream の TLS / mTLS 必須を脅威モデルに登録、
        plaintext fallback 経路を CI block。
  - security ↔ 08 migration：
      - migration pair の脆弱性 window（旧版運用期間）を
        脅威モデルに登録、既知 CVE が pair の旧版で残存
        する場合は admission block。
  - security ↔ 09 observability：
      - audit_event subject の immutability を security が
        cross-axis lock、観測 signal の改竄を物理 block。
  - security ↔ 10 auth：
      - session / token の lifecycle 全脅威（hijack /
        replay / scope escalation）を脅威モデルに登録、
        各 mitigation が tier1/10 spec に bind 済であること
        を CI assert。
  - security ↔ 11 key：
      - 鍵 compromise 時の crypto-erase / re-encrypt 経路を
        IR playbook に bind、rotation overdue は security が
        admission block。
  - security ↔ 12 schema：
      - PII class 列を含む schema の breaking 判定で
        compatibility rule に「PII 残存」 axis を加え、PII
        column の rest 暗号化解除経路を CI block。
  - security ↔ 13 SLO：
      - audit_log_ingest_latency / patch_window_compliance /
        cve_open_critical_count を SLI として emit、error
        budget freeze と admission block を bind。
  - security ↔ 14 OSS-lifecycle：
      - 採用 OSS の CVE 状況を oss_inventory.lock.yaml に
        annotate、critical CVE 残存は本番経路で admission
        block。
  - security ↔ 15 capacity：
      - noisy neighbor → DoS 経路を脅威モデルに登録、
        per-tenant volume 超過は DoS class threat の
        physical mitigation として security が共有 lock。
  - security ↔ 32 data-tenant：
      - RLS FORCE bypass の全経路（superuser / break-
        glass / SECURITY DEFINER 関数）を脅威モデルに登録、
        tier2/32 が物理 enforce、security が cross-axis assert。
  - security ↔ 39 client：
      - client-side cache / device storage の compromise
        経路を脅威モデルに登録、reconcile_class 別の暗号化
        要件を security が cross-axis bind。
  - security ↔ infra01 topology：
      - control-plane（Argo CD / etcd / Kyverno）の trust
        boundary、supply chain（Harbor / cosign）の真正性
        境界、build-time（CI runner / Tekton）の compromise
        経路を脅威モデルに登録、infra 14 強制機構 が物理
        enforce。
  - security ↔ data01 preservation：
      - WORM Object Lock / cryptographic erasure / restore_
        drill green を脅威モデルの「data exfiltration」
        「data tampering」「data loss」 mitigation として
        bind、data 14 強制機構 が物理 enforce。

■ 13 軸 + meta + security 中の位置
  - security は 14 軸目の候補として 00_軸登録適合仕様 の
    meta-registry に entry 追加される（cap v1=20 中 14 / 20、
    残 6 余地）。
  - 13 軸が「層別 × 機能別」軸であるのに対し、security は
    「脅威別 × 軸横断」軸として直交方向に位置する。脅威
    モデル class（actor / capability / surface）を class
    軸として持ち、各 class が複数軸に mitigation を要求する
    fan-out 構造を持つ。
  - 00 meta（軸登録）の release_gate.lock.yaml AND-gate に、
    security の threat_model.lock.yaml の `coverage_green`
    状態が入力される。全 threat_class が mitigation green
    でない限り 1.0.0 ship blocker。

■ 至高路線における位置づけの帰結
  - security は「個別軸の規律を再宣言する layer」ではなく、
    「個別軸の規律が脅威モデル下で漏れなく重複なく組み
    合わさっていること」を機械検証する meta-layer。security
    が新規物理機構を持ち込むことは原則しない（既存軸の
    機構を bind するのみ）。例外は監査 SoR の immutability
    と SBOM/SLSA など本質的に cross-cut な道具立てのみ。
  - 運用コスト度外視（CLAUDE.md 上位方針）の哲学に従い、
    脅威モデル coverage は最大化する。「現実には起こり
    にくいから登録しない」「mitigation が高コストだから
    緩める」判断は採らない。脅威の重みは coverage 内で
    SLO や budget で表現するが、登録自体は省略しない。
  - 1.0.0 完璧 release：5 threat_class（actor 別）全てに
    対し全 13 軸の cross-axis mitigation が green、SBOM /
    cosign signed image / vulnerability admission policy
    完全適用、までを ship blocker とする。
