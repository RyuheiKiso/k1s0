============================================================
security 脆弱性管理方針
============================================================

■ 一文方針
  - 脆弱性（CVE / GHSA / RUSTSEC / GO-yyyy / 自社発見）
    は Trivy + Grype + 言語別 audit + Semgrep + IaC scan
    の 5 経路で完全列挙し、severity 別の patch SLO（critical
    72h / high 7 日 / medium 30 日 / low 90 日）を SLO 軸
    （13）と connect、SLO 違反時は本番 deploy を admission
    block で物理拒否する。

■ 5 検知経路
  - 経路 1：image vuln scan
        primary：Trivy（CI build 時 + Harbor scan-on-push
                + 日次再 scan）
        cross-check：Grype（同 image / 同 SBOM）
        severity 規律（10_security/04 と双方向 lock）：
          - 両 scanner が同 severity 一致 : 当該 severity の
            policy をそのまま適用（Critical 一致 → admission
            block）。
          - severity 不一致 : `max(severity_trivy, severity_grype)`
            に escalate して当該 severity の policy を適用、
            ticket 自動起票。一方のみ Critical の場合は High
            扱いで ticket 起票（admission block しない、両者
            Critical 一致時のみ block）。
          - 不一致は本来の vuln DB / matcher 実装差で常時発生
            するため、規律としては「false negative を二重化で
            潰す + false positive で本番停止しない」を基本姿勢
            とする。
        target：image base layer / OS package / language
                stdlib
  - 経路 2：language dep audit
        Rust：cargo-audit（cargo deny advisory も併用）
        Go：govulncheck
        Node：pnpm audit（npm audit / yarn audit は使用
              しない、pnpm 一本）
        Python（補助スクリプト）：pip-audit
  - 経路 3：SAST
        Semgrep（言語横断 OSS rules + 自社 ruleset、
                 ruleset は build artifact）
        言語別：cargo clippy / golangci-lint（infra 14
                と整合）
  - 経路 4：IaC scan
        Trivy IaC（OpenTofu / Helm / Kustomize / Dockerfile）
        Checkov（cross-check）
  - 経路 5：自社発見 / PenTest / red-team
        年次外部 PenTest 必須（v1）、四半期 internal red-
        team 演習（11_インシデント対応方針 と整合）。
        発見は CVE 風 ID で自社 catalog（vulns/ 配下）に
        登録、Trivy ignore list と統合管理。

■ severity / patch SLO
  - severity は CVSS v3.1 + EPSS（Exploit Prediction
    Scoring System）併用：
        critical：CVSS ≥ 9.0 OR EPSS ≥ 0.5 + CVSS ≥ 7.0
        high：CVSS ≥ 7.0
        medium：CVSS ≥ 4.0
        low：CVSS < 4.0
  - patch SLO（13_SLO適合仕様 と connect）：
        critical：discover → fix merged → deploy 完了 ≤ 72h
        high：≤ 7 日
        medium：≤ 30 日
        low：≤ 90 日
  - SLO 違反は error_budget.lock.yaml 消費、budget 0 は
    本番 deploy admission block（13 と整合）。

■ patch lifecycle
  - 検知（自動）→ Renovate / Dependabot 風の自動 PR 起票
    （依存更新は Renovate を default、infra 04 と共有）。
  - 仮締め経路：CVE が image base layer の場合は image
    rebuild（base image bump）、language dep の場合は
    cargo update / go get / pnpm update。
  - 本締め経路：CVE 修正版に向けた upstream PR（自社で
    修正できる場合は patch 提供）、tier1/14 OSS lifecycle
    の primary OSS は自社 fork も pair_target として保持。
  - 例外（仮締め不可能）：mitigating control（Kyverno
    rule / Falco rule / network policy）で active mitigate
    する経路を threat_model.lock.yaml に登録、SLO 違反は
    error_budget で表現。完全 unfixed のまま放置は禁止。

■ Trivy ignore list の規律
  - 全 ignore は build artifact（vulns/ignore.lock.yaml）
    として管理、手書き .trivyignore 禁止。
  - ignore entry は (CVE_ID, image_pattern, expires_at,
    reason, mitigation_pointer) を必須化、expires_at 超過
    は CI fail。
  - ignore reason = "false_positive" は upstream 報告 PR
    必須、reason = "wont_fix_with_mitigation" は mitigation
    pointer 必須（threat_model.lock.yaml に bind）。

■ admission block の経路
  - block-on-critical-cve-overdue：critical CVE が 72h
    超過で patch 未完了の場合、本番 cluster への新規
    deploy を block。
  - block-on-high-cve-overdue：high CVE が 7 日超過で
    block。
  - block-on-cve-budget-exhausted：error_budget.lock.yaml
    の cve_open_critical_count が target 超過で block。
  - block-unsigned-image：cosign verify 失敗の image
    deploy を block（infra 14 と整合）。
  - block-image-without-sbom：SBOM 添付なし image deploy
    を block。

■ SBOM の運用
  - 全 image build で Syft が SBOM 生成（SPDX +
    CycloneDX 両 format）、cosign で sign + Harbor に
    attach。
  - Trivy / Grype は SBOM 入力で再 scan（image なしでも
    SBOM のみで CVE 検出）。
  - SBOM は audit_event subject にも emit、過去 image
    の CVE 影響範囲を ClickHouse query で再評価可能。
  - SBOM lifecycle の retention / 監査 は 10_security/17_
    build_provenance適合仕様 の Build artifact retention /
    監査 lifecycle（hot Harbor 90 日 / cold Ceph RGW 7 年 /
    audit_event CDC 永続）に責務移譲。本仕様の SBOM 生成
    側 invariant（Syft + Cosign + Harbor attach）と 17 軸
    側の retention / consumer chain（spdx/v2.3 +
    cyclonedx/v1.5 predicate を Grype + reproducibility_
    consensus_verifier が consume）が双方向 lock。

■ 採用しない方針
  - 商用 vuln DB（Snyk / Black Duck）：採用しない、OSS
    DB（Trivy / Grype / OSV / GHSA / NVD）で完結。
  - 「次の sprint で patch」を理由に SLO を緩める：禁止、
    SLO は 13 で固定。緩和申請経路を持たない。
  - critical CVE の active ignore：禁止、必ず mitigation
    pointer を threat_model.lock.yaml に登録（active
    mitigate）か patch 完了。
  - 単一 scanner 依存：Trivy 単独運用は禁止、Grype cross-
    check 必須。
  - source repo に CVE detail を含む security advisory を
    publish しない：CVE detail は GHSA / 内部 audit log
    のみで管理、git commit message に詳細含めない（patch
    PR 経由で history 化）。
  - 未 scan image の本番 deploy：admission block で物理
    禁止。

■ 同型構造（13 軸との整合）
  - patch SLO は 13_SLO適合仕様 の v1_patch_window として
    bind、SLI = patch_lead_time_p95、target は severity
    別。
  - CVE catalog は 14_OSSライフサイクル適合仕様 の
    oss_inventory.lock.yaml と connect、各 OSS の cve_
    open_critical_count が version 別に annotate。
  - vuln scan の admission policy は infra 14 / data 14 /
    本層 14 で共通、build artifact 生成器 input に
    threat_model.lock.yaml と vulns/ignore.lock.yaml を
    持つ。
