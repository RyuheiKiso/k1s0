============================================================
client 配布 SemVer 方針
============================================================

■ 一文方針
  - 全言語 SDK は同一 major.minor を同時に release する
    （lockstep SemVer）。skew は patch のみ許容、major.minor
    skew は CI fail。

■ バージョン規約
  - 形式：MAJOR.MINOR.PATCH-PRERELEASE+BUILD（SemVer 2.0.0）。
  - 全言語 SDK で同一の MAJOR.MINOR を持つ。例：
      - k1s0.Library.Net8     1.0.0
      - io.k1s0:library-java  1.0.0
      - @k1s0/library-node    1.0.0
      - @k1s0/library-web     1.0.0
      - k1s0_library (Python) 1.0.0
      - k1s0-library (Ruby)   1.0.0
      - k1s0_library (Rust)   1.0.0
      - github.com/k1s0/library-go v1.0.0
      - k1s0.Companion.NetFx  1.0.0
      - 各 OTel Auto-Instrumentation distro    1.0.0

  - PATCH は言語別 hotfix のみで増えてよい（waterfall release
    許容）。例：
      - k1s0.Library.Net8     1.0.3
      - @k1s0/library-node    1.0.1
    のように skew が出てもよいが、MAJOR.MINOR は同期。

■ 1.0.0 完璧 release
  - CLAUDE.md「1.0.0 の時には完璧として出したいので段階的な
    リリースはしない」に従い：
      - 1.0.0 は 5 distribution_class 全てが conformance test
        green
      - 全 9 言語（.NET / Java / Node / Browser TS / Tauri /
        Rust / Python / Ruby / Go）が同 1.0.0 同時 release
      - 1.0.0 後の MINOR up は purely additive のみ。新 RPC /
        新 capability_class / 新 OTel SemConv 追加は MINOR で
        OK、既存 RPC の signature 変更 / capability_class 削除
        は MAJOR up。

■ MAJOR up（破壊的変更）の手続
  - tier1 14 OSS lifecycle 適合仕様の deprecation_window と
    同期。MAJOR up は次を満たす：
      - deprecation_window: 180 日（最低 6 ヶ月）
      - 1 LTS overlap：旧 MAJOR と新 MAJOR が 1 LTS 期間 並走
      - 移行 toolchain：tier1 が破壊的変更 1 つにつき 1 つの
        codemod / migration script を提供（codemod は SDK 言語
        ごと）
      - 14 軸 lifecycle_event_corpus に MAJOR up event を登録、
        signal_source_endpoint で外部監視
  - 旧 MAJOR の sunset：deprecation_window 経過後、Harbor 上
    の旧パッケージは pull 可能 / push 不可で永久保管（07_
    ストレージ方針 と同型）。

■ MINOR up（後方互換）の規約
  - purely additive のみ：
      - 新 RPC 追加（既存 RPC は変更不可）
      - 新 capability_class の追加（旧 class 削除は MAJOR）
      - 新 OTel SemConv 追加（旧 attribute は alias 維持）
      - 新 distribution_class の追加（旧は維持）
      - 新 オプション field（proto は optional / 新 reserved
        番号での追加）
  - MINOR up でも全言語同時 release。Buf の breaking change
    detection を CI gate として必須化。

■ PATCH（hotfix）の規約
  - 言語別 hotfix は purely バグ修正 / セキュリティパッチ
    のみ。public API 追加 / 削除 / 変更を含めない。
  - hotfix は waterfall release 許容、ただし sdk_inventory
    .lock.yaml に release timestamp を記録、14 軸 signal で
    監視。
  - hotfix waterfall は 30 日以内に他言語へ同等修正 propagate
    が必須（CI 不変条件で track）。

■ release lockstep の物理 enforce
  - 全 言語 SDK の release は同一 GitHub Actions workflow か
    Tekton pipeline で並列 trigger。各言語ごとの個別 workflow
    を持たない（drift 防止）。
  - sdk_inventory.lock.yaml に MAJOR.MINOR の skew が検出
    された場合、CI fail（後述 14_強制機構）。
  - tag は git に `v1.0.0` 1 つだけ、cosign signed。各言語
    package registry には同 version tag をそれぞれ push。

■ pre-release / canary
  - alpha / beta / rc は同 lockstep を維持。例：
      - 全言語 1.0.0-rc.3 を同時 release
  - canary は GitHub Actions で「main branch ごとに -alpha.N」
    を全言語同時に push。ユーザは pin して試用可能。

■ パッケージ命名と version 同期
  - 全 言語 registry で同一 base version。version mapping は
    sdk_inventory.lock.yaml に build artifact として固定：

      sdk_inventory:
        major_minor: "1.0"
        languages:
          - id: dotnet8
            registry: nuget
            package: k1s0.Library.Net8
            current_patch: 0
          - id: java21
            registry: maven
            coordinate: io.k1s0:library-java:1.0.0
            current_patch: 0
          - id: node20
            registry: npm
            package: "@k1s0/library-node"
            current_patch: 0
          - id: browser_ts
            registry: npm
            package: "@k1s0/library-web"
            current_patch: 0
          # ...全 9 言語
        last_release_at: "2026-05-09T00:00:00Z"
        cosign_attestation: harbor://k1s0/sdk-attestations/v1.0.0

■ 配信経路
  - 各言語 official registry（npm.org / nuget.org / maven
    central / pypi.org / rubygems.org / crates.io / proxy.
    golang.org）に push（公開 OSS のため）。
  - enterprise 利用は Harbor mirror（NuGet repo / Maven repo /
    PyPI repo / RubyGems repo / cargo mirror / Verdaccio /
    Athens）経由を強制。infra Kyverno admission policy が
    Harbor 以外の registry 参照を reject（08_infra/14 整合）。
  - 全 package は Cosign signed。npm は sigstore、PyPI は PEP
    740 sigstore signing、cargo は Harbor の Cosign signed
    blob として保管（cargo-sigstore 実験 v2）。

■ SBOM / 脆弱性スキャン
  - 全 release artifact について Syft で SBOM 生成、Grype で
    脆弱性スキャン CI 必須。critical/high CVE 検出は release
    block。
  - SBOM は sdk_inventory.lock.yaml の cosign_attestation に
    紐付け、in-toto attestation で chain of custody を記録
    （security15 threat-model 整合）。

■ deprecation 通知
  - SDK 起動時 / 周期的 health probe で server に SDK version
    を送信、server が「deprecated」と判定した場合 SDK は
    OnSdkDeprecated event を発火。
  - deprecation 警告は console.warn / .NET ILogger / SLF4J
    Warn に出力、deprecation_window 残日数を含む。
  - sunset 後の SDK は server から 426 Upgrade Required を
    受領、SDK は OnSdkRetired event を発火（RPC は失敗扱い）。

■ build reproducibility
  - 全言語 SDK の build は reproducible：
      - .NET: deterministic build flag + ContinuousIntegrationBuild
      - Java: maven-build-helper + reproducible-build-maven-plugin
      - Node: npm-shrinkwrap + node version pin
      - Rust: cargo deterministic build + lockfile
      - Go: GOFLAGS=-trimpath + lockfile
  - reproducibility check は CI で必須（同 input → 同 output
    bit hash）。

■ 採用しない選択肢
  - 言語別の独立 SemVer：禁止。
  - 言語別の release date skew（半年遅れの Python release 等）：
    禁止。
  - PATCH での API 追加：禁止（MINOR でのみ許容）。
  - GA 後の MAJOR 同時複数並走（v1 と v2 と v3）：v2 候補
    （現状は v1 → v2 で 1 LTS overlap のみ）。

■ 至高路線の整合
  - 「Python 版だけ release を遅らせる」を採らない。lockstep
    必須、全言語同時。
  - 「破壊的変更を入れたいから MINOR で済ませる」を採らない。
    破壊的変更は MAJOR up + 180 日 deprecation_window + codemod
    提供を経る。
