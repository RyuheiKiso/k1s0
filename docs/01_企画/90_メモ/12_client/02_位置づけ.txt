============================================================
client 位置づけ
============================================================

■ 5 階層中の位置
  - tier1 : システム共通処理（Library / Server / 認証 /
            観測可能性）
  - tier2 : ドメイン業務共通化処理
  - tier3 : 個別業務の Web サイト / exe
  - infra : 物理 / 仮想基盤 + 制御平面
  - data  : データ層（保全 / lifecycle / 暗号化）
  - client: 上記 5 階層が公開する規律を SDK / Companion /
            Auto-Instrumentation の組合せで同型投影する横断層
            ← 本層

  - client は 5 階層のいずれにも属さない「投影層」として位置
    づけられる。tier1 Library / tier2 Service の wire / tier3
    SPA や exe の前段 / infra cluster の OSS バージョン整合 /
    data 層の暗号 / key rotation の SDK 側挙動を、言語ごとに
    分岐させずに同型投影する。

■ 上下方向の関係
  - 上方向（client が tier1 / tier2 / tier3 / data / infra に
    依存する経路）：
      - tier1 Library 公開 API / .proto / Apicurio Registry
        を SDK の単一の真として import → tier1 が source of
        truth、client が investment surface
      - tier1 Transport Adapter Layer の capability matrix を
        SDK 側 capability_class として投影 → 07 transport 軸
        が source of truth、client が wire 投影
      - tier1 09 観測可能性 SoR の SemConv を SDK Auto-
        Instrumentation で emit → 09 観測軸が source of
        truth、client が emit 経路
      - tier1 10 認証適合仕様の AuthContext / SessionContext /
        token lifecycle を SDK 側で伝播 → 10 認証軸が source
        of truth、client が wire 投影
      - tier1 11 鍵管理適合仕様の DEK / KEK 階層を SDK 側
        device_bound_key で投影 → 11 鍵管理軸が source of
        truth、client が SDK 側投影
      - tier1 12 スキーマ進化適合仕様の compatibility 規約に
        従い codegen される proto / Apicurio schema を SDK
        Buf workflow で固定 → 12 schema 軸が source of truth
      - tier1 13 SLO 適合仕様の deadline propagation を SDK
        retry policy が尊重 → 13 SLO 軸が source of truth
      - tier1 14 OSS lifecycle 適合仕様の SDK 側 OSS（OTel
        Auto-Instrumentation 等）の v1_l1plus_primary 指定に
        従う → 14 OSS lifecycle が source of truth
      - tier1 15 テナント容量適合仕様の qps_limit / hot_byte_
        limit に SDK 側 retry budget が整合 → 15 capacity 軸
        が source of truth
      - tier2 32 テナント分離適合仕様の tenant_id / actor_id
        の wire 伝播形 → 32 軸が source of truth、client が
        wire 投影
      - tier3 39 クライアント状態適合仕様の 4 layer / conflict
        tree / BusinessConflict subtype を SDK 側で投影 → 39
        が source of truth、client が SDK 側 reducer / queue
        実装契約を提供
      - infra01 topology の region / cluster locality を SDK
        が探知して transport routing に反映 → infra01 が
        source of truth、client が routing 投影
      - data01 preservation の at-rest 暗号化方針を SDK 側
        WebCrypto / OS keychain で投影 → data01 が source of
        truth、client が SDK 側 at-rest 投影
      - security15 threat-model の SDK 面 attack surface 対策
        （Cosign signed パッケージ / SBOM 検証 / supply chain
        attestation）に従う → security15 が source of truth

  - 下方向（client が業務アプリ / レガシー資産 / SPA に対して
    提供する経路）：
      - 業務アプリ作者は client が公開する SDK パッケージを
        言語別 registry から install するだけで、上記全 13 軸
        の規律が default で動作する状態になる
      - レガシー資産（.NET Framework 4.6.2+ など）は OpenTelemetry
        .NET Auto-Instrumentation（CLR Profiler 方式、コード
        変更不要）+ Companion NuGet を組み合わせ、tier1 Library
        相当の規律を投影する
      - tier1 Library を直接組み込めない言語については、
        ビジネス API（Envoy Gateway 経由、unary は gRPC-JSON
        Transcoder / server-streaming は tier1 Rust ハンドラが
        直接生成する SSE）と Companion（観測 / 認証 / Transport
        Negotiation）の二点セットで投影する

■ 横方向の関係（client ↔ 各層）
  - client ↔ tier1：
      - tier1 が public な .proto / Library 公開 API / SemConv
        / AuthContext schema を「単一の真」として宣言、client
        が言語別 SDK にミラーする
      - tier1 04_Library の Companion 提供仕様（観測 / 認証 /
        Transport Negotiation）の言語別実装は client 12_コード
        生成方針で codify する
      - tier1 03_Server 系の Transport Adapter Layer と対をなす
        Companion 内 adapter は client 06_Transport適応方針で
        宣言する
  - client ↔ tier2：
      - tier2 BusinessConflict subtype（tier3/39 が拡張）を
        SDK 側でも同型 type として codify、UI 分岐の 1:1 を
        保つ
      - tier2 32 RLS の tenant_id / actor_id を SDK が token
        / metadata に必ず attach する（手書き禁止、SDK レベル
        で auto attach）
  - client ↔ tier3：
      - tier3 SPA は client が提供する TypeScript SDK + Browser
        Auto-Instrumentation で構築
      - tier3 exe（.NET Framework）は client が提供する
        Companion NuGet + .NET Auto-Instrumentation で構築
      - tier3 39 適合仕様の 4 layer reducer は client が SDK
        として提供する Adapter / Application 層 helper を使う
  - client ↔ infra：
      - SDK パッケージ自体は infra の Harbor mirror から配信
        （cargo / npm / NuGet / Maven の private mirror も
        Harbor + nexus 機能経由）。Cosign 署名 + Trivy / Grype
        スキャンを通った package のみが install 可能
      - infra01 topology_class が region / cluster locality を
        宣言、SDK が DNS / mTLS SAN から検知して closest
        endpoint へ routing
  - client ↔ data：
      - data01 preservation_class が at-rest 要件を宣言、SDK
        側オフライン storage（IndexedDB / OS keychain）が同等
        の暗号化要件を満たす（WebCrypto AES-GCM / device_
        bound_key）
  - client ↔ security：
      - security15 threat-model の SDK 攻撃面（依存パッケージ
        への supply chain 攻撃 / token theft / replay）への
        対策を SDK 側で codify

■ 13 軸 + meta + 14 軸（threat-model）の中の位置
  - 既存軸：07 transport / 08 migration / 09 observability /
    10 auth / 11 key / 12 schema / 13 SLO / 14 OSS lifecycle /
    15 capacity / 32 data-tenant / 39 client-state / infra01
    topology / data01 preservation / security15 threat-model
  - client は本層 spec（15_クライアントSDK配布適合仕様）で
    新たな軸（client-distribution）を追加する。distribution
    軸は state 軸（39）と直交する：39 が「client が保持する
    state の意味論」、本層 spec が「state を投影する SDK 配布
    と wire 規約」を担う。
  - 00 meta（軸登録）の release_gate.lock.yaml AND-gate に、
    client の sdk_conformance.lock.yaml が green 状態として
    入力される。

■ 至高路線における位置づけの帰結
  - client は「投影の単一の真」として、複数言語間の規律
    drift を物理的に発生させない層である。.NET 版だけ retry
    semantics が違う / TypeScript 版だけ idempotency-key を
    送らない / Python 版だけ tenant_id を attach し忘れる、
    といった drift は SDK 配布段階で物理 enforce で殺す。
  - 運用コスト度外視（CLAUDE.md）の哲学に従い、SDK 言語数
    を絞らない。.NET / Java / Node.js / Browser TypeScript /
    Browser+Tauri / Rust native / Python / Ruby / Go の全
    言語を 1.0.0 で同時 release する。「メンテが大変だから
    Python は v2」の妥協は採らない。
  - 1.0.0 完璧 release：5 distribution_class 全てが
    conformance test green、全 言語 SDK が SemVer lockstep、
    全 SDK が Cosign signed、までを ship blocker とする。
