■ 設計原則
  - sdk_distribution_class は bundle である。
      yaml に書く client.distribution.* attribute のうち、
      sdk_distribution_class 1 つの値が他 6 dimension（
      language_runtime / distribution_channel / transport_
      capability_class / auto_instrumentation_mode / companion
      _provision_mode / device_at_rest_encryption_mode /
      refresh_token_storage_mode）を一意に導出する。Buf
      workflow / Harbor admission policy / SDK init の作者
      が dimension を個別に override する経路は持たない。
      （※ 7 dimension あるが「他 6」と数えるのは class 自体が
       1 dimension であることに対する従属 dimension の数え方。）
  - dimension override は禁止する。
      「v1_browser_spa_typescript の refresh_token_storage_
      mode を localstorage に変えたい」要望は新 class を切る
      ことで表現する。class 数の爆発は意味論の規律として受
      け入れる。
  - dead spec を CI で殺す。
      classes.yaml に登録された全 class、scenarios.yaml に
      登録された全 assertion id、sdk_inventory.lock.yaml に
      列挙された全 SDK package、sdk_conformance.lock.yaml に
      列挙された全 conformance record は、いずれも参照され
      なくなった時点で CI fail とする。proto に含まれる全
      RPC method のうち annotation（retry / slo / quota /
      observability / capability）が 1 つでも欠けたものは
      buf lint で fail。
  - 5 種類 enforcement orchestrator を全 sdk_distribution_class
    に必須化する。
      buf_codegen_pipeline / cosign_supply_chain / language_
      lint_analyzer / pact_contract_test / property_based_
      test の 5 orchestrator は、各 class が必要とする層を
      宣言する。同一 enforcement は複数 orchestrator に分散
      しないが、同一 SDK では複数 class が複数 orchestrator
      を併用する。
  - sdk_conformance を物理 property とする。
      「conformance_cadence_days 以内に必ず 5 distribution_
      class 全てで全 conformance scenario を実演し、宣言された
      期待値内に収束する」を CI で必ず検証する。13 の v1_
      request_availability / v1_request_latency_p99 が SDK
      side OTel metric で隣接 region を観測し、isolation 破綻
      を即時 alert + admission block に流す。
  - defense-in-depth は 5 層で構成する。
      層 A : compile（codegen / 型 check）
      層 B : lint（規約 check）
      層 C : integration / contract test（Pact / Testcontainers
              / Playwright）
      層 D : runtime（SDK ランタイムの物理 enforcement、
              WebCrypto / OS keychain / DPAPI / 24h TTL /
              retry budget / circuit breaker）
      層 E : 物理（Cosign signed package / Kyverno admission
              policy / OS keychain / WebCrypto non-extractable
              CryptoKey / Browser CSP）
      任意の単層が破れても他層が必ず止める。物理 enforcement
      は最終 safety net。

■ dimension の根拠
  - language_runtime は SDK の宿主 ランタイム：
        dotnet8 / java21 / node20 / rust / go122 / python312
        / ruby33   → サーバ側 / 太い client
        dotnet_framework_4_6_2_plus → レガシー .NET FW
        browser    → SPA
        tauri      → デスクトップ Native
        any        → polyglot business API only
    複数粒度を重ねた表現（dotnet8 + dotnet_framework）は
    class 内 fixed。
  - distribution_channel は SDK の配布経路：
        各言語 official registry + Harbor mirror（enterprise）
        / OpenAPI yaml only / Tauri bundle 形式
    混合は class 内 fixed。
  - transport_capability_class は wire 能力：
        full / web / limited / business_api_only
        （06_Transport適応方針 と同型）
  - auto_instrumentation_mode は OTel Auto-Instrumentation
    の attach 方式：
        agent_attach / library_auto / clr_profiler_attach /
        dual / side_companion_proxy
        （11_観測Auto-Instrumentation方針 と同期）
  - companion_provision_mode は Companion 配布形態：
        optional / required / required(sidecar) /
        side_companion_proxy
  - device_at_rest_encryption_mode は SDK 側 offline storage
    の暗号化機構：
        os_native / dpapi / webcrypto_aes_gcm_non_extractable_
        cryptokey / webcrypto_aes_gcm_with_os_keychain_key_
        wrap / not_applicable
        （07_オフライン耐性方針 と同期）
  - refresh_token_storage_mode は refresh_token 永続化の物理
    保管：
        process_memory_only / dpapi_protected_blob / in_memory
        + httponly_cookie / os_keychain_secure_storage /
        not_applicable
        （08_認証コンテキスト伝播方針 と同期）

■ derived dimension（per-language threshold）を独立次元にしない理由
  - per-language の閾値（v1_full_native_with_companion 内の
    .NET 8 vs Java 21 vs Node.js 20 のそれぞれの runtime
    minor version、依存 NuGet / Maven / npm のバージョン）は
    本来 dimension たり得るが、5 class それぞれで「同じ
    transport_capability_class / auto_instrumentation_mode /
    companion_provision_mode / device_at_rest_encryption_mode
    / refresh_token_storage_mode 構造で言語と version だけが
    instance 別」という同形操作になる。
  - 閾値は class instantiate 時の instance 属性として宣言し、
    build artifact が Buf workflow generator config / Cosign
    signed package metadata / Kyverno admission policy 適用
    対象を生成する形に統一。
  - SDK 開発者 / 業務側で迷う余地がないため、独立 dimension
    化する利得が乏しい。

■ 5 種類 enforcement orchestrator の責務分離（特殊機構）
  - orchestrator 1: buf_codegen_pipeline
      - 全 class 共通の主担当。proto / Apicurio schema を input
        として全言語 SDK の RPC stub / type / SemConv helper /
        capability matrix / retry policy table / PII field map
        を 1 pipeline で生成（12_コード生成方針）。
      - generated code が compile できることが層 A の物理 trigger。

  - orchestrator 2: cosign_supply_chain
      - 全 class 共通の主担当。SDK package の Cosign signed +
        SBOM (Syft) + 脆弱性スキャン (Grype) + SLSA provenance
        attestation を物理 enforce（09_配布SemVer方針 / 14_
        強制機構）。
      - Harbor admission policy が unsigned package を物理
        reject する層 E。

  - orchestrator 3: language_lint_analyzer
      - 全 class が必要とする言語別 lint（Roslyn / SpotBugs /
        ESLint / clippy / pylint / rubocop / golangci-lint）。
        各 SDK 内 公開 API として「生 HTTP」「LocalStorage 直
        書込」「access_token getter」「自製 crypto」「dimension
        override」の存在を物理 reject（14_強制機構 整合 12）。

  - orchestrator 4: pact_contract_test
      - 全 capability_class について Pact provider / consumer
        contract test を実行（14_強制機構 整合 5 / 13_運用UI
        と開発者体験 contract test 節）。
      - SDK 利用者が tier1 Server 側 API と契約上整合している
        ことを 物理 verify。

  - orchestrator 5: property_based_test
      - 全 9 言語 SDK で property based test を実行：
        retry backoff の monotonicity / idempotency_key の
        uniqueness / capability negotiation の決定論性 / 4
        layer reducer の決定論性（39 conflict_tree.yaml の
        actions 投影）。
      - 言語別 property test ライブラリ（FsCheck / fast-check
        / Hypothesis / proptest 等）を統一 spec で駆動。

  - 5 orchestrator は順次評価される（codegen → contract →
    property → lint → cosign）が、各 sdk_distribution_class
    は 1 orchestrator を「主担当」として宣言。他層は補助的
    に協調動作（例：v1_browser_spa_typescript の主担当は
    pact_contract_test だが、property_based_test が capability
    negotiation を補助）。

■ 5 層 defense-in-depth

  ── 層 A : compile（codegen / 型 check）
      - protoc + Buf による単一 codegen pipeline（12_コード
        生成方針）。
      - 全 SDK の generated code が compile すること（言語別
        compiler／rustc／tsc／csc／javac／pyflakes／rubocop
        type-check）。
      - method annotation（retry_policy / slo_class /
        quota_class / observability_class / capability_class）
        が proto に必須化、buf lint で検出。
      - sdk_inventory.lock.yaml / capability_matrix.lock.yaml
        / sdk_conformance.lock.yaml は build artifact、手書き
        禁止。

  ── 層 B : lint（規約 check）
      - 言語別 lint / analyzer（14_強制機構 言語別 lint 一覧）。
      - SDK 公開 API として「生 HTTP」「LocalStorage 直書込」
        「access_token getter」「自製 crypto」が露出していない
        こと。
      - sdk_distribution_class 注釈の存在 / 値域検査 /
        sdk_inventory.lock.yaml と整合。
      - SDK 公開 API snapshot diff があれば release notes /
        codemod の存在を CI gate で要求。

  ── 層 C : integration test / contract test
      - Pact provider / consumer contract test（全 9 言語 ×
        全 capability_class）。
      - Testcontainers で tier1 Server + Companion Mock +
        tier2 atomic 三表書込 + Outbox + Keycloak + OpenBao
        を起動、SDK が round-trip。
      - Playwright で Browser SPA + Tauri SDK の E2E。
      - 39 適合仕様 8 製造業 pack stress test scenario の SDK
        投影テスト。
      - merge 条件：全 scenario が green。skip された scenario
        があれば fail。

  ── 層 D : runtime（SDK ランタイムの物理 enforcement）
      - WebCrypto / OS keychain / DPAPI による at-rest
        encryption（07_オフライン耐性方針）。
      - 24h Idempotency-Key TTL の SDK ランタイム enforcement。
      - retry budget の per-tenant / per-method / per-aggregate
        sliding window enforcement。
      - circuit breaker open/half-open/closed の状態遷移。
      - capability negotiation の決定論性（自動選択、override
        不能）。
      - OTel Auto-Instrumentation の attach（disable 不能、
        最小 sampling rate 0.001）。

  ── 層 E : 物理 enforcement（OS / Browser / Kubernetes 物理機構）
      - WebCrypto API の non-extractable CryptoKey は
        JavaScript が export 不能（browser engine 物理機構）。
      - OS keychain（macOS Keychain / Windows DPAPI / Linux
        SecretService）の secret 取出は OS user 認証必須。
      - Cosign signed package のみ install 可能（Harbor
        admission policy で unsigned reject、infra 14 と同期）。
      - Kyverno admission policy（infra 側、08_infra/14）：
        require-image-from-harbor / block-on-cve-backlog-
        threshold / require-cosign-signature / block-host-
        network-host-pid / require-tls-1.3-or-higher。
      - Browser engine の CSP（Content Security Policy）が
        default 'self' で SDK が外部 script eval 不能。
      - mTLS：Istio mesh STRICT、外向きは Envoy Gateway front
        の TLS 1.3 + cert-manager。

■ v2 拡張ルール
  - 新 class / 新 capability_class / 新 auto_instrumentation_
    mode の追加は purely additive。
  - 既存 class の dimension 変更（例：v1_browser_spa_typescript
    の refresh_token_storage_mode を localstorage に変更）は
    破壊的変更（major version up、09_配布SemVer方針 と整合）。
    dual-write 移行 toolchain を tier1 / client が成果物として
    提供する（codemod / migration script）。
  - 命名は class / capability / mode / channel ともに英小文字
    snake_case 固定。
  - WebGPU 利用の SDK 内 cryptographic acceleration（v2_
    webgpu_aead_offload）/ Service Worker background sync（v2
    _sw_background_sync）/ Connect-go Web 評価 / WASI 化 /
    eBPF user-space probe / .NET Native AOT / Cilium ServiceMesh
    協調観測 等は v2 候補。

■ 長期収斂への作用
  - 本仕様の 5 ファイル（classes / sdk_inventory.lock /
    capability_matrix.lock / sdk_conformance.lock / scenarios）
    に対し、新業務 / 新言語 / 新 OSS 採用は purely additive
    な変更として進行する。scenarios.yaml に scenario を足し、
    classes.yaml の既存 class のみで覆える形を保つ。
  - 14 軸（07 transport / 08 migration / 09 observability /
    10 auth / 11 key / 12 schema / 13 SLO / 14 OSS lifecycle /
    15 capacity / 32 data-tenant / 39 client-state / infra01
    topology / data01 preservation / security15 threat-model）
    + meta + client distribution（本仕様、15 軸目候補）が
    同型構造で固まったことにより、tier1 / tier2 / tier3 /
    infra / data / security / client の責務分離と接合面が
    機械的に検証可能になる。軸間の接合は次の対応関係に閉じる：

      transport 軸 conformance_class      ↔  client 軸 capability_class
      observability 軸 semconv_version    ↔  client 軸 auto_instrumentation_mode
      auth 軸 SessionContext              ↔  client 軸 refresh_token_storage_mode
      key 軸 device_bound_key             ↔  client 軸 device_at_rest_encryption_mode
      capacity 軸 noisy_neighbor_isolation ↔  client 軸 retry_budget
      schema 軸 compatibility             ↔  client 軸 buf workflow + breaking check
      threat-model 軸 supply chain        ↔  client 軸 cosign + sbom + slsa attestation
      data preservation 軸 at_rest        ↔  client 軸 device_at_rest_encryption_mode
      infra topology 軸 region locality   ↔  client 軸 preferred_locality routing
      client-state 軸 4 layer reducer     ↔  client 軸 SDK reducer/queue 実装契約

  - 15 軸の同型は「単一 OSS 深耕 + 移行コミットメント」（「05
    _tier1/04_Library」L1+）の哲学を全 layer に転写したもの。
    各軸とも purely additive な拡張と決定論的な不変条件で成熟
    する。00 meta-spec が「軸自体の追加削除を物理 enforce」
    （cosign signed tag + release_gate.lock.yaml AND-gate）
    する構造の中で、本仕様の sdk_conformance.lock.yaml が
    AND-gate の一入力として記録される。
