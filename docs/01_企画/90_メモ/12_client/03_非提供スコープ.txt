============================================================
client 非提供スコープ
============================================================

■ 提供しない（明示的に out-of-scope）
  - ビジネスロジック / ドメイン業務処理
      → tier2 / tier3 の責務。client は SDK / Companion /
        Auto-Instrumentation の投影のみを提供する。
  - tier1 Server 系の RPC / Repository 実装
      → 05_tier1 の責務。client は SDK 側 wire 規約を提供
        するだけで、server 側 RPC handler / Repository は
        持たない。
  - tier3 SPA / exe の UI コンポーネント / フォーム規約 /
    デザインシステム
      → 07_tier3 の責務。client は SDK 層までであり、UI 部品
        を提供しない。SDK はフレームワーク非依存（React /
        Blazor / WPF / Avalonia いずれでも組み込み可能）。
  - tier3 client-state の意味論（4 layer / conflict tree /
    BusinessConflict subtype）の定義変更
      → 07_tier3/39_クライアント状態適合仕様 の責務。client は
        この意味論を「言語横断 SDK で同型実装する」契約だけを
        持つ。layer / event / subtype の追加削除は 39 を改定
        してから client が追従する片方向 dependency。
  - 業務固有 SLI / SLO 値（latency target / availability target
    の数値）
      → 13_SLO適合仕様 + tier2 / tier3 の instance attribute。
        client は SDK 側 deadline propagation 経路と retry
        policy の枠組みのみを提供する。
  - テナント別 quota の閾値値（qps_limit / hot_byte_limit 等）
      → 15_テナント容量適合仕様。client は SDK 側 retry budget
        / circuit breaker 機構のみ提供。
  - data の lifecycle 値（retention 日数 / archive_to_offline
    cadence 等）
      → 09_data の責務。client は SDK 側 offline storage の
        TTL 強制（24h Idempotency-Key 等）のみ持つ。
  - schema 進化の compatibility 判定
      → 12_スキーマ進化適合仕様 の責務。client は Buf workflow
        を回す toolchain と SDK ロックファイルを提供するだけ。
  - 暗号鍵の rotation cadence / KEK / DEK の階層構造
      → 11_鍵管理適合仕様 の責務。client は SDK 側 device_
        bound_key 取扱いと WebCrypto / OS keychain ラッパーの
        提供のみ。
  - 認証 issuer / JWT signing 鍵の発行
      → 10_認証適合仕様 + Keycloak。client は SDK 側 token
        取扱い / refresh / propagation のみ持つ。
  - infra cluster の物理基盤
      → 08_infra の責務。client は Harbor mirror から SDK
        パッケージを pull する経路のみ持つ。
  - 観測可能性 SoR の storage 設計（ClickHouse / Jaeger Query
    + CH plugin）
      → tier1/09 観測適合仕様。client は SDK 側で OTel SDK
        を初期化し OTLP exporter で emit するまで。

■ 採用しない OSS / 技術
  - 言語別の独自テレメトリライブラリ（Application Insights
    SDK / NewRelic Agent / DataDog Agent）：OpenTelemetry .NET
    Auto-Instrumentation / OpenTelemetry Java Agent / OTel
    JS / OTel Python の L1+ 深耕のため、横並びの APM SDK
    は採用しない。
  - Connect-go / Connect-RPC を v2 候補から外し、v1
    primary に格上げ（Browser SPA capability_class=web の
    bidi primary。詳細は 04_採用OSS / 06_Transport適応方針）。
    gRPC 公式実装 + gRPC-Web は引き続き L1+ primary、Connect
    -RPC は Browser fetch full-duplex streams 上で bidi-
    streaming を成立させる役割を担い、いずれも同一 .proto
    から codegen される。
  - GraphQL Client（Apollo / Relay / urql）：tier1 RPC は
    .proto + Apicurio Registry を単一の真とするため、GraphQL
    層を SDK が提供することはない。tier3 が独自に採用する
    場合は client SDK 範囲外。
  - axios / superagent / requests（生 HTTP client）：SDK 内部
    では用途別 transport adapter（gRPC / gRPC-Web / WebSocket
    / WebTransport / SSE）を直接実装し、汎用 HTTP client
    library は SDK の公開 API として露出しない。アプリ作者は
    生 HTTP を直接使うことができない（Adapter 経由の強制）。
  - Redux / MobX / Recoil / Pinia / NgRx（state 管理ライブラリ
    の L1+ primary 化）：tier3/39 適合仕様の 4 layer reducer
    は client SDK が直接実装し、特定 state 管理 OSS への hard
    dependency を持たない。各 framework の adapter は
    Companion 経路で副次提供。
  - HashiCorp Vault SDK（クライアント側）：SDK 側秘密管理は
    OpenBao 連携の SDK 経路を持たず、infra 経由で External
    Secrets が配布した token を SDK が受領する設計に統一。
  - Auth0 / Okta SDK：認証は Keycloak 単一深耕、SDK が他
    OIDC provider を直接サポートする経路は持たない。
  - 自製 crypto 実装：SDK 内では WebCrypto API（Browser /
    Node.js）/ .NET System.Security.Cryptography / Java JCA
    / Rust ring or rustcrypto 等の標準暗号 API のみを使う。
    Pure JS 実装の crypto は採用しない。
  - npm-only build tool への hard dependency（webpack / vite
    のいずれかへの hard 結合）：SDK は ESM + CJS dual emit、
    bundler 非依存で配布する。

■ 採用しないアーキテクチャ
  - 言語別バージョン skew の長期許容：全言語 SDK の major.
    minor は lockstep。skew の最大許容は 1 patch（hotfix の
    waterfall release のみ）。長期 skew は dead spec として
    CI fail。
  - hand-rolled SDK：proto / Apicurio schema からの codegen が
    全 RPC / event / metric の唯一経路。手書きで RPC stub を
    書く経路は持たない。
  - SDK 外からの直接 wire 形成：アプリ作者が生 gRPC channel
    / 生 WebSocket / 生 fetch を立てて k1s0 platform endpoint
    に直接当てる経路は CI で検出（公開 API snapshot）。SDK
    経由のみ許容。
  - 「言語別の retry semantics 違い」の許容：全言語 SDK が
    同一 retry budget / 同一 jitter 戦略 / 同一 idempotency-
    key 生成規約を実装する。「.NET HttpClient は標準 retry を
    持つから SDK は薄く」のような言語固有の妥協は採らない。
  - 「Browser SDK は IndexedDB を選択肢にする」型の variability：
    Browser SDK の offline storage は IndexedDB + WebCrypto
    AES-GCM の固定組合せ。LocalStorage / SessionStorage は
    PII を含み得るため SDK 内で採用しない（lint で deny）。
  - SDK 自身が生 SQL / ORM 機能を提供する経路：tier2 が公開
    する Domain API のみが正規 entry。SDK が DB に直接接続
    する経路は持たない。

■ v2 候補（v1 で採用しないが将来検討）
  - WebGPU 利用の SDK 内 cryptographic acceleration（v2_
    webgpu_aead_offload）
  - Service Worker による background sync 自動化（v2_sw_
    background_sync）
  - WASI 化（Browser+WASI SDK の同型化、v2_wasi_unified_
    runtime）
  - eBPF user-space probe による uprobe-based Auto-
    Instrumentation（特定言語の compile 時注入が困難な場合
    の補完、v2_uprobe_auto_instrumentation）
  - .NET Native AOT / GraalVM Native Image での SDK サイズ
    削減と起動時間短縮（v2_aot_sdk_packaging）
  - Cilium ServiceMesh / Linkerd と SDK の協調観測（infra 軸
    と整合した v2 候補）

■ 至高路線における判断
  - 「SDK 言語数を絞れば運用が楽」を理由に scope を縮小
    しない。v1 で .NET / Java / Node.js / Browser TypeScript
    / Browser+Tauri / Rust native / Python / Ruby / Go の全
    9 言語を同時 release する。
  - 「アプリ作者が生 HTTP を直接書きたい」を理由に SDK
    bypass 経路を作らない。生 wire 利用は CI で物理 reject。
  - 「Auto-Instrumentation が大きい / 起動が遅い」を理由に
    観測機構を選択制にしない。1.0.0 では全 distribution_class
    で auto-instr デフォルト on。サイズ / 起動時間最適化は
    v2 で評価する。
  - 「言語別 SemVer tempo を分けたい」を理由に lockstep を
    緩めない。release は全言語同時、ただし hotfix patch のみ
    waterfall release を許容。
