■ 一文定義
  - 検証規律適合仕様は、5 verification_class × 5 phase の
    cross-product として完全列挙される verification_loop
    catalog の各 cell に対し、5 enforcement orchestrator の
    いずれかを必ず物理 pointer として bind し、全 15 軸
    （13 軸 + meta + security + ops）+ 自軸の defense-in-
    depth 層 C / D / E に bind 済みであることを 5 層
    defense-in-depth + 18 項 CI 不変条件 + 16 件 stress
    test pack で物理 enforce する meta-axis である。同時
    に 16 axis × 5 verification_class = 80 cell の
    coverage_matrix.lock.yaml の全 cell drill_state ∈
    {v1_baseline_green, v1_drill_red_handled} を 1.0.0
    ship blocker として 00 meta release_gate.lock.yaml の
    AND-gate に物理入力する（v1_drill_red_handled は ops
    の v1_drill_failure signal として起票済 + handling
    artifact pointer 保持の状態を表し、red 経路を構造化
    追跡することで red 容認と all-green 必須の概念衝突を
    解消する）。

■ 設計原則
  - verification_class は bundle である。
      yaml に書く test.verification.* attribute のうち、
      verification_class 1 つの値が他 5 dimension（
      cadence_class / artifact_class / orchestrator_
      preference / coverage_weight / regression_corpus_
      class）を一意に導出する。各軸 spec の作者 / 業務
      作者 / drill_owner が dimension を個別に override
      する経路は持たない。
  - dimension override は禁止する。
      「v1_property_axiom のうち cadence_class を緩めたい」
      要望は新 class を切ることで表現する。class 数の
      爆発は意味論の規律として受け入れる。
  - dead spec を CI で殺す。
      classes.yaml に登録された全 class、coverage_matrix
      .lock.yaml に列挙された全 cell、properties.yaml /
      pacts.yaml / scenarios.yaml / chaos_blueprints.lock
      .yaml / mutation_modules.yaml に列挙された全 entry、
      regression_corpus に保存された全 reproducer は、
      いずれも参照されなくなった時点で CI fail とする。
      service のうち test ownership_table.lock.yaml に
      4 軸 entry が無いものも CI fail（test ownership 未
      宣言の deploy を deny by default）。
  - 5 種類 enforcement orchestrator を全 verification_
    class に必須化する。
      pact_broker_pipeline / litmus_chaos_pipeline /
      mutation_pitest_pipeline / e2e_playwright_pipeline /
      coverage_gate_kyverno の 5 orchestrator は、各 class
      が必要とする層を宣言する。同一 verification は
      複数 orchestrator に分散しないが、同一 axis では
      複数 class が複数 orchestrator を併用する。
  - drill cadence を物理 property とする。
      「cell の cadence_days 以内に必ず該当 class の
      verification を実演し、宣言された閾値内に green
      する」を Tekton Pipeline + Litmus chaos workflow +
      Pact Broker webhook で必ず検証する。13 の v1_test_
      coverage_compliance / v1_mutation_score_compliance
      / v1_flaky_quarantine_compliance / v1_drill_cadence
      _compliance が cluster_label 付き metric で隣接
      cluster を観測し、cell green 破綻を即時 alert +
      admission block に流す。
  - defense-in-depth は 5 層で構成する。
      層 A : compile 時（PR の verification_class 注釈
              必須、coverage_matrix.lock.yaml schema
              通過）
      層 B : lint（catalog の coverage / cadence /
              ownership / regression_corpus / blameless
              文体）
      層 C : drill chaos test（Litmus + Tekton Pipeline
              + chainsaw + Playwright + Apache JMeter + Pact Broker）
      層 D : runtime（5 orchestrator の実 deploy）
      層 E : physical（cosign signature / Kyverno
              admission webhook / Ceph RGW Object Lock
              Compliance mode / test_event hash chain の
              物理層強制）
      任意の単層が破れても他層が必ず止める。物理
      enforcement は最終 safety net。

■ phase（5 phase、verification artifact の closure に対応）
  - phase_1_specify：
        各軸 spec が verification_claim entry を宣言する
        SLA：spec 追加 PR → coverage cell entry 追加 ≤
              same PR（同 commit）
        primary orchestrator：coverage_gate_kyverno
              （admission block）
  - phase_2_generate：
        Tekton Pipeline / generator が classes.yaml +
        spec entry から coverage_matrix.lock.yaml 等の
        build artifact を生成
        SLA：spec entry 追加 → artifact 生成 ≤ 5 min
        primary orchestrator：coverage_gate_kyverno
              （build trigger）
  - phase_3_execute：
        各 verification_class の test framework が
        artifact_pointer に対する test を実行
        SLA：artifact 生成 → first execution ≤ 30 min
              （v1_per_pr）/ ≤ 24h（v1_weekly）/ ≤ 7d
              （v1_biweekly）/ ≤ 30d（v1_monthly）
        primary orchestrator：5 orchestrator のいずれか
              （class ごと）
  - phase_4_triage：
        execution result red の場合 incident class 確定
        → ops の v1_drill_failure / v1_change_induced
        signal_class へ bridge → Mattermost incident
        channel
        SLA：red 検出 → triage 完了 ≤ 30 min
        primary orchestrator：litmus_chaos_pipeline /
              e2e_playwright_pipeline + ops alertmanager
              _routing
  - phase_5_learn：
        regression_corpus に entry 追加 → mutation_score
        baseline 更新 → flaky_quarantine 期限管理 →
        coverage cell の last_green_at 更新
        SLA：triage → corpus / baseline / cell 更新 ≤
              24h
        primary orchestrator：mutation_pitest_pipeline /
              coverage_gate_kyverno

  - 5 phase × 5 verification_class = 25 cell が完全列挙、
    空欄は coverage gap として CI fail。

■ 至高路線における判断（structural spec として）
  - 「test 実行時間が長い」を理由に coverage を縮小
    しない。実行時間は test_minutes_per_week noise
    budget で表現、coverage cell entry 自体は省略
    しない。
  - 「flaky の修正が間に合わない」を理由に quarantine
    cap を緩めない。14 day cap は物理規律、cap 越えは
    test 削除 + ownership escalation の自動経路で受
    ける。
  - 「mutation_score 引き上げが厳しすぎる」を理由に
    monotonic 規律を緩めない。引き下げは構造的に
    monotonic violation、release_gate AND-gate 物理
    fail。
  - 「chaos drill は怖い」を理由に cadence を緩め
    ない。v1_prod_gameday は break-glass + 二人承認
    + audit_event の経路で物理化、cadence は CI で
    enforce。
  - 「商用 test SaaS が便利だから入れたい」を理由に
    L1+ 単一深耕を緩めない。新 OSS は 14_OSSライフ
    サイクル適合仕様 の pair_target 移行手続を経る。
  - 「LLM で test を量産したい」を理由に注釈規律を
    緩めない。LLM-generated test は ai_generator_id /
    model_version / prompt_hash 注釈完備 + 人間
    reviewer ack 必須、merge gate は通常 test と同等。
  - 「property test の seed を random にしたい」を
    理由に deterministic 規律を緩めない。seed は
    必ず seed_pool / replay_corpus / pr_deterministic
    のいずれか、test runner ローカル random は禁止。
  - 「snapshot 自動更新で開発速度を上げたい」を理由
    に signed PR 規律を緩めない。snapshot 更新は drill
    _owner ack + diff artifact 必須。
  - 「test_event の hash chain は重複だから security
    14 / ops 14 の audit chain だけで充分」を理由に
    hash chain を skip しない。test_event subject は
    別 schema、別 immutability 規律で security audit
    _event / ops_event と独立に chain 維持（subject
    別の forgery resistance を物理 enforce）。
  - 「scenario_replay を production cluster で動かす
    のが効率的」を理由に shadow cluster 規律を緩めな
    い。production cluster での replay は admission
    block で物理拒否、性能 / capacity_forecast 検証も
    必ず shadow cluster。
  - 「contract test は両方向 verify が冗長」を理由に
    Pact + Buf-breaking double-bound を緩めない。両者
    は異なる semantic（実行時 contract / schema 静的
    contract）を担当、双方向 lock を物理 enforce。
  - 「regression_corpus が肥大化する」を理由に append
    -only 規律を緩めない。corpus 削除は dead spec
    検出時のみ、retention は v1_immutable_archive で
    365 day。
