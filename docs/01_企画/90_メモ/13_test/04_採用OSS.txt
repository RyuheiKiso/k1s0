============================================================
test 採用 OSS（test 層 subset）
============================================================

■ 位置づけ
  - 「02_採用OSS一覧」の grand catalog のうち、test 層が
    cross-axis に bind する OSS（unit / property / contract
    / e2e / chaos / mutation / load / fixture / coverage /
    fuzz）を抽出して整理したもの。tier1 / infra / data /
    security / ops が所有する OSS は cross 参照で明記する
    （test は使用面を宣言するのみ）。
  - 本ファイルの全 OSS は 05_tier1/14_OSSライフサイクル適合
    仕様 の oss_inventory.lock.yaml に v1_l1plus_primary と
    して登録される。

------------------------------------------------------------
[1] unit / framework（言語別 1 OSS L1+ 単一深耕）
------------------------------------------------------------
  カテゴリ                       | プロダクト             | ライセンス
  -------------------------------+------------------------+---------------
  Python unit                    | pytest                 | MIT
  TypeScript / JavaScript unit   | Vitest                 | MIT
  Go unit                        | testing (stdlib) +     | BSD-3
                                 | testify                | MIT
  Rust unit                      | cargo test (stdlib)    | Apache 2.0
  Java / Kotlin unit             | JUnit 5                | EPL-2.0
  C# / .NET unit                 | xUnit.net              | Apache 2.0

  - 各言語 1 unit framework のみ L1+ 単一深耕、横並び禁止
    （pytest と nose2 の両用 / Vitest と Jest の両用等は
    test 軸で禁止、buf workflow と同型の規律）。
  - 採用しない：unittest（stdlib）/ nose2 / Jest / Mocha /
    Jasmine / Ginkgo / NUnit / MSTest / Spock / TestNG。
  - L1+ 移行 commit は v1_l1plus_primary として oss_
    inventory.lock.yaml に登録、major version migration は
    test 軸の v1_scenario_replay drill として演習必須。

  -------------------------------+------------------------+---------------

  TypeScript property            | fast-check             | MIT

------------------------------------------------------------

  -------------------------------+------------------------+---------------

  Network fault injection        | Toxiproxy              | MIT

                                 | （Litmus と double-    |
                                 |  bound、blast radius   |
                                 |  小さい drill 用）     |

  - Litmus L1+ 単一深耕、ChaosBlade / PowerfulSeal / Pumba

    しない。
  - chaos blueprint は build artifact（chaos_blueprints.
    lock.yaml）として登録、prod gameday の blast radius は
    Kyverno admission policy で物理制限。

■ 採用しない（明示）
  - 商用 SaaS test platform（BrowserStack / Sauce Labs /
    LambdaTest / Applitools / Functionize / Mabl / TestRail）
  - 商用 chaos：Gremlin / AWS FIS / Harness Chaos
  - 商用 coverage：Codecov SaaS / Coveralls SaaS / SonarQube
    Server commercial edition

    generator 自体は採用 OSS 範囲で書き起こし、商用 SaaS
    依存は持たない。
  - 「test と prod を 1 cluster で混在させる shadow runner」
    の独自実装：採用しない、shadow は infra01 v1_multi_
    region_active_passive の passive 側 cluster に必ず
    bind（infra 15 + data 15 と整合）。

■ 軸間 bind
  - 14 OSS-lifecycle：本ファイル全 OSS は oss_inventory.
    lock.yaml に v1_l1plus_primary 登録、EoL window は
    test framework migration drill として演習。pair_target
    持つ OSS は test も migration drill を v1_scenario_
    replay class で claim。
  - 13 SLO：v1_test_coverage_compliance / v1_mutation_
    score_compliance / v1_flaky_quarantine_compliance /
    v1_drill_cadence_compliance の 4 SLO を登録。
  - 11 ops：drill_failure / drill_success の signal 経路、
    chaos drill の break-glass token 経路（OpenBao response
    wrapping）。
  - 10 security：fuzz / chaos の attacker simulation を
    threat 1:1 bind、cosign signed test artifact 物理 verify。
  - 09 data：test_event の SoR を ClickHouse、archive を
    Ceph RGW Object Lock Compliance mode で immutable。
  - 04_推奨の開発体制：各 OSS の deep know-how owner 配置
    は 4 軸 ownership 制（service / domain / framework /
    drill）として ownership_table.lock.yaml に登録。
