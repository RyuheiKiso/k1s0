■ 抽象化レベル（Lv）の意味
  - L3   : 業界標準 wire / protocol が存在する領域。OSS 中立。差し替え
           時、業務コードは無変更。
  - L2*  : 軽セマンティクスかつ真に互換性の高い OSS 族が存在する領域。
           差し替え時、業務コードは型置換 + 一部チューニングで済む
           （業務ロジックは不変）。族の外への差し替えは保証外。
  - L1+  : 高セマンティクス領域。単一 OSS への深耕を選ぶ代わり、OSS の
           全機能（拡張・運用機能を含む）を Library API として表現する。
           OSS ライフサイクルイベント時は tier1 が移行 toolchain を
           成果物として提供する（移行コミットメント）。差し替え時は
           当該カテゴリの業務コードに設計レベルの修正が入るが、tier1 が
           toolchain で支援する。
  - レベル定義および各レベルの受け入れ基準は「04_Library」を参照。

■ L1+ / L2* カテゴリで露出する代表的な OSS 概念（移行時影響箇所）
  - Profiling                              : profile 種別（cpu / heap / goroutine 等）、
                                             サンプリングレート、ラベル基数
  - Configuration / Feature Flag           : evaluation context、ターゲティング規則、
                                             セグメント定義
  - Schema Registry                        : 互換性モード、グループ / artifact 体系
  - Vector Search                          : インデックス種別 / 距離関数、再構築コスト
  - Messaging / EventBus                   : 分割キー、順序保証、consumer pool、
                                             再試行 / DLQ ポリシー、Outbox 設計、
                                             トランザクション送信
  - Relational Store / Single-leader       : トランザクション分離レベル、advisory lock、
                                             SQL 方言、接続プーリング制約、マイグレー
                                             ション形式、パーティション lifecycle、
                                             利用拡張（pg_trgm / PostGIS / pgvector 等）
  - Workflow / Long-running Saga           : Workflow / Activity 境界、WorkflowID 体系、
                                             補償処理の書き方、決定論実行の制約
  - Rule Engine                            : 決定表 DSL、ルール評価セマンティクス

■ L2* カテゴリの同族定義（差し替え保証対象範囲）
  - Profiling                      : pprof 族（Parca / Pyroscope）
  - Configuration / Feature Flag   : OpenFeature provider 族
                                     （flagd / GO Feature Flag / GrowthBook 等）
  - Schema Registry                : Confluent Schema Registry wire 互換族
                                     （Apicurio / Karapace）
  - Vector Search                  : k-NN 族
                                     （pgvector / Qdrant / Milvus、profile API 経由）
  族の外への差し替えは保証対象外。族の改廃自体は Library の破壊的変更
  （major version up）として扱う。

■ L3 カテゴリの wire 互換前提（業務コード無変更を成立させる根拠）
  - Logging / Tracing / Metrics    : OpenTelemetry SDK + OTLP
  - Authentication / Authorization : OIDC / OAuth 2.1
  - Secret Management              : External Secrets Operator 経由
                                     （Provider 差し替えに対し Library API 不変）
  - RPC / Gateway                  : gRPC（Library 経由言語向け） +
                                     Transport Adapter Layer による
                                     transport-neutral な External 公開
                                     （sse_paired / websocket / webhook /
                                      web_transport / long_poll /
                                      messaging_bridge を conformance
                                      proof で等価実装。詳細は
                                      「03_Server系」Transport Adapter
                                      Layer を参照）。
  - KeyValue / Cache               : RESP 族
                                     （Valkey / Dragonfly / KeyDB）
  - Object Storage                 : S3 API 族
                                     （Ceph RGW / MinIO / SeaweedFS）

■ L1+ カテゴリの本命 OSS と移行先候補
  - Relational Store / Single-leader  : 本命       PostgreSQL (CloudNativePG)
                                        移行先候補 別 PG operator
                                                   （StackGres / Crunchy PGO / EDB）、
                                                   Aurora PG、Neon
  - Relational Store / Distributed SQL: 将来カテゴリ。tier3 がアーキテクチャ
                                        設計時に Single-leader と排他選択する。
                                        本命 OSS は未定（CR / YB / TiDB /
                                        Spanner-API 等が候補）。実装着手は
                                        顧客要件発生時。
  - Messaging / EventBus              : 本命       Apache Kafka (Strimzi)
                                        移行先候補 RedPanda、AWS MSK、Confluent Cloud
  - Workflow / Long-running Saga      : 本命       Temporal
                                        移行先候補 Cadence、Temporal Cloud
  - Rule Engine                       : 本命       ZEN Engine
                                        移行先候補 自製 DSL、別 OSS
  L1+ では day-1 で複数 backend を並走させない。OSS ライフサイクル
  イベント時に tier1 が移行 toolchain を成果物として提供する
  （詳細は「04_Library」L1+ 移行コミットメント節を参照）。

■ RPC / Gateway カテゴリの追加次元（transport-neutral）
  - 本カテゴリは L3（OSS 中立）に加え、もう一つの中立性次元を持つ。
    Transport Adapter Layer により、bidi を含む全 RPC 形式は transport
    （wire 上の搬送方式）からも独立に表現される。
  - これは「異なる transport（HTTP/2 + gRPC / HTTP/3 + WebTransport /
    HTTP/1.1 + WebSocket / HTTP/1.1 + NDJSON / inbound webhook /
    cursor poll / messaging bridge 等）が同じ bidi semantics を等価
    実装する」ことを CI で証明する形で担保される。proto に宣言された
    意味論（ordering / half_close / resumable / max_msg_lag_ms /
    conformance_class）が単一の真であり、transport はその interpreter
    として複数並立する。
  - 受け入れ基準（業務コードへの影響）：
      - 新 transport の追加 : 業務コード無変更（adapter 追加のみ）。
      - 古い transport 退役 : 業務コード無変更（capability 宣言から
                              自動降格）。
      - transport 切替（例：SSE → WebSocket）: 業務コード無変更
                              （Companion / Library 内部で完結）。
  - 「OSS 中立」と「transport 中立」の二軸が成立することにより、本
    カテゴリは tier2 / tier3 から見た最も安定した抽象表面となる。
    External / Internal proto 二層化（「03_Server系」参照）も、本軸
    の成熟に伴い長期的には単層へ collapse する。
  - この発想は L1+「単一 OSS 深耕 + 移行コミットメント」の哲学を
    transport 軸に転写したもの（単一 transport 深耕ではなく、bidi
    semantics 深耕 + transport 移行コミットメント）として位置付ける。
