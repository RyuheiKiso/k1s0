============================================================
tier1 Library 設計方針
============================================================

■ 方針
  - tier1 Library は「機能カテゴリ単位の抽象 API」を tier2 / tier3 に提供
    する。現行採用 OSS は実装の詳細であり、Library の表面 API には漏らさ
    ない。
  - tier2 / tier3 は本 Library のみを通じて infra にアクセスする。OSS の
    クライアントライブラリを直接 import することは禁止する（機械的担保は
    本ファイル「強制機構」節を参照）。
  - Library を直接組み込めない言語（.NET Framework など）に対しては、
    ビジネス API と観測可能性を分けて提供する。
      - ビジネス API：tier1 提供のゲートウェイ経由でアクセスする。
        .proto を単一の真とし、HTTP/1.1 + JSON（unary）は Envoy
        Gateway の gRPC-JSON Transcoder で派生、HTTP/1.1 + SSE
        （text/event-stream、server-streaming）は tier1 Rust ハンドラ
        内で SSE フレーミングを直接生成する（streaming RPC の扱い
        詳細は「05_tier1/03_Server系」Proto 二層化 / RPC 形式の
        射影方針を参照）。
      - 観測可能性 / 認証コンテキスト伝播 / Transport Negotiation：
        Companion を別途提供する。観測可能性と認証コンテキスト伝播
        を役割 A、bidi を含む RPC の transport 選択と等価実装を
        役割 B として担う（詳細は本ファイル末尾「Companion」節を
        参照）。

■ パッケージ構成（frontend / backend 分離方針）
  - Library は core / frontend / backend の 3 パッケージで構成し、
    対象言語ごとにこの 3 パッケージを提供する。
  - 両者で重複する概念は core に集約し、frontend / backend は core
    に依存する形を取る。core に置く対象例：
      - 認証コンテキスト / テナント識別子の型と伝播ヘルパ
      - 構造化ログ / トレース / メトリクスの共通スキーマ
      - 共通エラー型、リトライ / タイムアウト等のポリシー定義
  - frontend パッケージにバックエンド専用の依存（DB ドライバ、Kafka
    クライアント、Temporal クライアント等）が混入することを禁止する。
    「提供機能カテゴリ」の「対象」列で frontend / backend / both を
    明示し、バンドル境界の検査基準とする。
  - 「対象」が both のカテゴリでも、具象 API は frontend / backend で
    異なって構わない（例：Authentication は frontend で OIDC PKCE
    クライアント、backend でトークン検証 / 認可ポリシー評価）。core
    が共有するのは型と概念であり、API 表面の完全一致は要求しない。

■ 抽象化レベルの方針
  - 機能カテゴリごとに到達可能な抽象化レベルが異なる。一律に「OSS 差し
    替えで業務コード無変更」を受け入れ基準として課すと、Messaging /
    Workflow / Saga / Rule Engine / Relational Store 等は「Library に
    乗らない」結論になり、かえって tier2 / tier3 が OSS を直接触る抜け
    穴を生む。これを避けるため、Library は次の 3 段階の抽象化レベル
    （Lv）を認め、カテゴリごとに到達目標を割り当てる。
  - 設計上の前提：
      - 「OSS 差し替え」は日常運用ではなく、ライフサイクルイベント
        （ライセンス変更・改廃・サポート終了等）として扱う。day-1 で
        複数 backend を並走させ続けるよりも、ライフサイクルイベント時
        に確実に移行できる toolchain を tier1 が用意する方が長期の
        価値が高い。これを「移行コミットメント」として L1+ カテゴリに
        適用する。
      - 高セマンティクス領域（Relational / Messaging / Workflow / Rule）
        では「型置換 + 一部チューニング」での差し替えは物理的に成立
        しない（トランザクション分離・採番・ロック・順序保証などの
        semantics 差が業務ロジックに染み出す）。L2 を無理に主張せず、
        L1+ で深耕する。

  - L3 : OSS 中立
      - 業界標準の wire / protocol（OIDC / OTLP / RESP / S3 / gRPC 等）
        が存在し、複数 OSS 実装が同じ表面を提供する領域に限定する。
      - OSS 固有の型 / 概念を API 表面に一切出さない。
      - 受け入れ基準 : OSS 差し替え時、業務コード（tier2 / tier3）は無変更。
      - 想定対象 : Logging / Tracing / Metrics / Authentication / Secret /
        RPC / KeyValue / Object Storage。

  - L2* : 軽セマンティクス + 真に互換性の高い OSS 族
      - 族の semantics 差が API 表面に出ても破壊的でない領域に限定する。
        高セマンティクス領域（トランザクション境界・ロック挙動・採番・
        順序保証等が業務ロジックに染み出す領域）には適用しない。
      - OSS 固有の語彙は Library 独自語彙に翻訳する。族内で意味を保てる
        範囲のチューニング概念（距離関数 / 互換性モード / evaluation
        context / プロファイル種別等）は API 表面に残す。
      - カテゴリごとに「同族」を明示列挙し、その範囲内での差し替えを
        保証対象とする。族の外への差し替えは保証外であり、族の改廃
        そのものを Library の破壊的変更（major version up）として扱う。
      - 受け入れ基準 : 族内差し替え時、業務コードは型置換 + 一部チュー
        ニング（パラメータ調整・索引再設計など）で済み、業務ロジック
        の再設計は不要。
      - 想定対象 : Profiling、Feature Flag、Schema Registry。
      - 同族の具体定義は「05_提供機能カテゴリ」を参照。

  - L1+ : 単一 OSS 深耕 + 移行コミットメント
      - 高セマンティクス領域で、OSS の semantics 差が業務ロジックに
        必然的に染み出す領域。複数 OSS 同時サポートを諦める代わりに、
        単一 OSS の全機能（拡張・運用機能を含む）を Library API として
        深く表現する。
      - Library の責務 :
          - 単一 OSS の全機能（拡張・運用機能を含む）を Library API
            として漏れなく表現する。L3 / L2* で要求される「OSS 概念の
            隠蔽」は意図的に放棄する。
          - 横断要素（認証コンテキスト伝播 / 自動計装 / リトライ・
            タイムアウト / マルチテナント識別子 / 共通エラー型 /
            ベストプラクティステンプレート）を強制する。
          - OSS バージョン跨ぎ（マイナー / メジャー）の互換維持と
            移行支援。
          - OSS ライフサイクルイベント時の移行 toolchain を成果物として
            継続保持（schema / state diff、双方向 ETL、dual-write 移行、
            observability の連続性確保。詳細は本ファイル「L1+ 移行
            コミットメント」節を参照）。
      - 受け入れ基準 : OSS クライアントを直接 import させない経路を
        Library として一本化し、ライフサイクルイベント時の影響範囲が
        「Library + 該当カテゴリの業務コード + tier1 が提供する移行
        toolchain」の三点に閉じること（全層に波及しない）。
      - 露出される OSS 概念は「05_提供機能カテゴリ」の露出概念一覧に
        明示する。OSS バージョンアップ / 移行時の影響範囲調査チェック
        リストとして使う。
      - 想定対象 : Relational Store / Single-leader、Messaging / EventBus、
        Workflow / Long-running Saga、Rule Engine、Vector Search。将来
        カテゴリとして Relational Store / Distributed SQL を予約（tier3
        がアーキテクチャ設計時に Single-leader と排他選択する位置付け）。
        Vector Search は pgvector 単独深耕（PostgreSQL extension として
        の transactional ANN / SQL JOIN 内 ANN を Library API に深く
        露出）、移行先候補は Qdrant / Milvus / Weaviate（standalone
        vector engine、L1+ 移行コミットメント枠で toolchain 提供）。

  - L1+ / L2* で API 表面に露出する OSS 概念は、カテゴリごとに「露出概念
    一覧」として Library 側ドキュメントに明示する。
  - 抽象化レベルが低いことを理由に Library から外さない。代わりに L1+ /
    L2* を選び、tier2 / tier3 が OSS を直接 import する経路を塞ぐことを
    優先する。

■ 横断的に Library が担う共通要素
  - 認証コンテキスト（誰が呼んでいるか）の伝播。
  - トレース / ログ / メトリクスへの自動計装。
  - リトライ / タイムアウト / サーキットブレーカ等のレジリエンス。
  - マルチテナント識別子の伝播と分離。

■ 強制機構（OSS 直接 import 禁止の機械的担保）
  - 「OSS クライアントを直接 import しない」方針を運用で空文化させない
    ため、以下 3 層を多重に設ける（defense-in-depth）。いずれの層も CI
    の必須チェックとして組み込み、後付け運用や例外申請に依存しない。
  - 層 1 ：依存導入レベル（tier2 / tier3 リポジトリ側）
      - 各言語の標準ツールで OSS クライアントの import 自体を機械的に
        禁止する。
          Rust         : cargo-deny の [bans] で Kafka / PostgreSQL /
                         Temporal / Valkey / Object Storage 等のクライ
                         アント crate を deny。
          C# (.NET 8+) : BannedApiAnalyzers の BannedSymbols.txt で OSS
                         の名前空間を禁止し、Central Package Management
                         で未承認パッケージの参照自体を弾く。
          Go           : golangci-lint の depguard で OSS クライアントの
                         import パスを deny。
          TypeScript   : eslint-plugin-import の no-restricted-imports と
                         eslint-plugin-boundaries で禁止と層越境を検出。
      - 上記設定は Backstage の Software Template に同梱し、tier2 /
        tier3 リポジトリ生成時点で組み込む。
  - 層 2 ：Library 公開 API 表面レベル（tier1 側）
      - Library が OSS 型を再エクスポート（Rust の pub use、C# の
        public 露出 等）すると、層 1 を満たしても業務コードが間接的に
        OSS 概念へ依存する。これを防ぐため、Library 公開 API を
        snapshot 化し差分を CI で検査する。
          Rust         : cargo public-api。
          C#           : Microsoft.CodeAnalysis.PublicApiAnalyzers
                         （PublicAPI.Shipped.txt 運用）。
          Go           : go-apidiff と自製 go/analysis を併用。
          TypeScript   : api-extractor の .d.ts rollup。
      - L3 / L2* カテゴリは公開シグネチャに OSS 型が現れたら CI fail
        とする。L1+ カテゴリは「05_提供機能カテゴリ」の露出概念一覧と
        allowlist 一致を検査する（一覧外の OSS 型が API 表面に出現
        したら fail）。
  - 層 3 ：供給経路レベル（内部パッケージリポジトリの一元化）
      - tier2 / tier3 のビルドが OSS クライアントを物理的に取得できな
        いよう、内部パッケージリポジトリを唯一の取得元に固定する。
          Rust         : 内部 cargo registry を [source.crates-io] で
                         置換。
          C#           : 内部 NuGet feed のみ nuget.config に登録。
          Go           : Athens 等の内部 module proxy を GOPROXY に固定。
          TypeScript   : Verdaccio 等の内部 npm registry に固定。
      - 内部リポジトリには Library と承認済み補助パッケージのみを公開
        し、Kafka / Temporal / PostgreSQL 系等の OSS クライアントは
        置かない。Library リポジトリの CI に限り、外部 feed を許可する。
      - 「02_採用OSS一覧」[6] サプライチェーン / セキュリティ の
        Harbor / Cosign / Trivy と整合する形で構築する。

■ L2* 同族保証の機械的担保
  - 「同族内 OSS 中立」を文書上の願望で終わらせないため、以下を CI と
    出荷物の両面で強制する。L2* に該当しないカテゴリ（高セマンティクス
    領域）は本節の対象外で、「L1+ 移行コミットメント」に従う。
  - 二バックエンド conformance（最重要）
      - 各 L2* カテゴリで、本命 OSS と同族内代替 OSS の最低 2 実装を
        Testcontainers で同時に立ち上げ、共通の統合テストを両方で green
        にすることを merge 条件とする。
      - 想定の組合せ：
          Profiling              : Parca + Pyroscope
          Feature Flag           : flagd + GO Feature Flag
          Schema Registry        : Apicurio + Karapace
      - 片側でしか通らないテストが発生した時点で「その API は L2* として
        適格でない」とみなし、API を族内ポータブル範囲まで縮める、
        または当該カテゴリを L1+ へ昇格させる（単一 OSS 深耕 + 移行
        コミットメントに切り替える）。
  - capability negotiation
      - Library の初期化 API で、業務コード側が要求する能力（互換性
        モード / 距離関数 / evaluation context 種別 / プロファイル種別
        など）を宣言させる。
      - backend が要求能力を満たさない場合、起動時に fail-fast する。
        本番投入後の差し替えで silent な意味論変化が起きるのを防ぐ。
  - 露出概念 / 禁止概念の機械可読宣言
      - 「05_提供機能カテゴリ」の露出概念一覧をカテゴリごとに YAML で
        宣言し、許可概念 / 禁止概念を明示する。
      - 公開 API snapshot（cargo public-api、PublicApiAnalyzers、
        api-extractor、go-apidiff）と CI で照合し、禁止概念に該当する
        語が API 表面に出現したら fail させる。
      - これは「強制機構」層 2 と同じ枠で動かす。

■ 出荷時のバックエンド方針
  - 抽象化レベルごとに方針を分ける。
  - L3 カテゴリ（wire 互換）：
      - 複数 OSS が wire 標準で互換のため、Library としてはどの実装でも
        利用可能。Backstage Software Template には初期オプションとして
        以下を含め、tier2 / tier3 が選択できる状態を維持する。
            KeyValue / Cache       : Valkey、Dragonfly
            Object Storage         : Ceph RGW、MinIO
      - L3 はライセンス事情の変化等で実装を増減させる際の影響が小さい。
        tier3 が複数の選択肢を持つこと自体を「wire 互換が機能している」
        生きた証跡として運用する。
  - L2* カテゴリ（同族）：
      - CI conformance で同族の 2 実装の green を merge 条件とする
        （前節「L2* 同族保証の機械的担保」）。日常運用で並走させるか
        どうかは別判断とし、Library 本体としては並走を強制しない。
      - tier2 / tier3 は本命 OSS を標準として運用し、族内代替の運用化
        が必要になった時点で Backstage template に追加する。
  - L1+ カテゴリ（深耕 + 移行コミットメント）：
      - 本命 OSS のみを Backstage template の標準として提供する。
        並走は行わない。
      - 移行は OSS ライフサイクルイベント発生時に tier1 が toolchain で
        支援する（次節「L1+ 移行コミットメント」）。
      - 並走しないことを「責任放棄」にしないため、移行 toolchain の
        年次 dry-run を実施し、移行可能性を継続的に検証する。

■ L1+ 移行コミットメント
  - 位置づけ：L1+ カテゴリは単一 OSS への深耕を選ぶ代わりに、OSS ライフ
    サイクルイベント（ライセンス変更・改廃・サポート終了等）で発生する
    移行作業を Library / tier1 が toolchain として成果物化する。day-1 で
    複数 backend を並走させる方式は採らない。
  - 移行 toolchain の成果物（カテゴリごとに整備）：
      - schema / state 差分検出
          DB なら schema diff、Workflow なら Workflow / Activity 定義の
          差分、Rule Engine なら決定表 DSL の差分、Messaging なら
          topic / consumer group / Schema Registry エントリの差分。
      - 双方向 ETL / replication
          Kafka なら MirrorMaker 2 系、PG なら logical replication /
          pg_dump、Temporal なら state export / replay。
      - dual-write 移行支援
          移行期間中、新旧 backend に二重書き込みするための Library
          抽象（書込 / 読取の正解 backend を ramp で切り替える）。
      - observability 連続性
          移行前後で span / metric の意味論を維持する Collector
          プロセッサ設定とゴールデン値テスト。
      - 業務コード移行ガイド
          露出概念一覧を起点に、tier2 / tier3 側の修正点を機械的に
          列挙したチェックリスト。
  - 維持責務：
      - 上記 toolchain は「ライフサイクルイベント時のみ作る」のではなく、
        Library 本体と同じリポジトリで継続的に維持する。Library のバー
        ジョンアップ時に toolchain も同時に CI で検証する。
      - 移行先候補（カテゴリごとに 1 つ以上）を文書化し、Testcontainers
        での dry-run 移行テストを年次で実施する。dry-run の green を
        Library リリース条件に含める。
  - 移行先候補（参考、確定ではない）：
      Relational Store / Single-leader : 別 PG operator（CNPG ↔ StackGres
                                          ↔ Crunchy PGO ↔ EDB Postgres）、
                                          Aurora PG、Neon
      Messaging / EventBus              : RedPanda、AWS MSK、Confluent Cloud
      Workflow / Long-running Saga      : Cadence、Temporal Cloud
      Rule Engine                       : 自製 DSL、別 OSS
      Vector Search                     : Qdrant、Milvus、Weaviate
                                          （standalone vector engine、
                                           transactional ANN / SQL JOIN
                                           を持たないため業務コードに
                                           設計レベルの修正が入る）
  - 移行先候補は ライフサイクル監視の対象であり、本命 OSS にライセンス
    変更等の予兆が出た時点で候補のうち 1 つを正式移行先として toolchain
    実装に進める。
  - 1.0.0 ship 前 dry-run green 必須 pair（4 カテゴリ × primary 1 pair）
    の確定形と、5 phase × assertion id matrix、dry_run.lock.yaml、
    cross-axis assertions（07 / 32 / 39 との接合）の機械可読仕様は
    本ディレクトリ「08_移行Pair適合仕様」に分離する。Testcontainers
    での dry-run と CI の release blocker 連動も同仕様に集約する。

■ Companion（Library 非対応言語向け追加提供）
  - 位置づけ：本 Library を組み込めない言語（.NET Framework など）に
    対し、二つの役割を担う薄物として提供する。
      役割 A : Observability / 認証コンテキスト伝播
      役割 B : Transport Negotiation Runtime（bidi を含む RPC の
               transport 選択と等価実装。tier1 Server系 の
               Transport Adapter Layer と対をなすクライアント実装）
  - 共通スコープ：ビジネス API 抽象（Messaging / Relational Store /
    Workflow など）は含まない。ビジネス API のスキーマ / セマンティ
    クスは引き続き Gateway 経由で .proto を真として利用する。
    Companion は「proto に書かれた意味論を、レガシー言語の HTTP / IO
    スタックの上で透過に実行する runtime」と位置付ける。

  ── 役割 A : Observability / 認証コンテキスト伝播
  - 標準形態：.NET Framework 4.6.2+ 向けに OpenTelemetry .NET
    Auto-Instrumentation を採用する。CLR Profiler によるアタッチ方式
    で、アプリケーションのソースコード変更を不要とする。HttpClient /
    ASP.NET / ADO.NET / WCF などを自動計装する。配布形態は環境変数 +
    DLL 配置 + 再起動で完結させる。
  - 補助形態：Auto-Instrumentation 非対応環境（4.6.1 以前など）向けに
    NuGet 参照型の Companion を提供する。HttpClient 用
    DelegatingHandler、Authorization / traceparent / テナント識別子の
    伝播ヘルパ、Logger 拡張のみを含む。
  - core スキーマとの整合：構造化ログ / span attribute 名は言語中立
    のスキーマ定義（YAML、OpenTelemetry Semantic Conventions 拡張
    形式）を単一の真とし、OpenTelemetry Weaver で各言語の定数コード
    を生成する。Companion は core 全体を取り込めないが、生成された
    定数のみを含む最小 NuGet を切り出して参照する形を取る。これに
    より人手による「複製実装」自体を排除する。
  - スキーマ持ち分の最小化：アプリ側で持つ組織固有スキーマは
    「テナント識別子・業務相関 ID・認証主体」等に絞り、HTTP / DB /
    RPC などの標準計装は OpenTelemetry Semantic Conventions に従う。
    属性のリネーム / 追加 / 削除は OpenTelemetry Collector のプロ
    セッサ（attributes / transform）で一元化し、Companion / 各言語
    Library 側に同等処理を持たせない。
  - CI 検証：定数文字列の一致確認に留めず、Testcontainers で
    OpenTelemetry Collector を起動し、Companion / 各言語 Library
    から実際に emit される span / log 属性をゴールデン値と比較する。
    スキーマ定義 → 生成定数 → 実行時出力の 3 点を CI で連結する。

  ── 役割 B : Transport Negotiation Runtime
  - 位置づけ：tier1 Server系 の Transport Adapter Layer
    （「03_Server系」参照）と対をなすクライアント実装。proto に
    宣言された bidi semantics（ordering / half_close / resumable /
    max_msg_lag_ms / conformance_class）を、レガシー言語上で
    transport 非依存に実行する責務を持つ。
  - 提供 API：bidi RPC に対しては言語ごとに統一インタフェース
    （C# 例：IBidiChannel<TReq, TResp>）を提供し、その裏で Gateway
    が選んだ chosen_transport に応じた adapter 実装が動作する。
    アプリ側は transport 種別を意識しない。server-streaming RPC も
    同様に統一 API（IServerStream<TResp>）で受ける。
  - 同梱 adapter（Companion 側受信実装）：
      sse_paired       : 既定。HttpClient.ResponseHeadersRead を用い
                         た SSE フレーミングパーサ（data: / id: /
                         event: / retry: を解釈）+ 送信用 unary POST。
                         event 消費・キャンセル・再接続を内蔵し、
                         resume_token は SSE 仕様の id: フィールドを
                         そのまま使う（Last-Event-ID リクエストヘッダ
                         で再接続時に server へ送出。.NET Framework に
                         EventSource ネイティブはないため、パーサは
                         Companion 内で実装する）。
      long_poll        : cursor 付き short poll の組合せ。長時間
                         接続を切る proxy 越えに用いる。
      webhook          : レガシー側で IIS / WCF / HttpListener が
                         利用可能な場合の opt-in。受信ハンドラ枠 +
                         認証検証を同梱。
      websocket        : ClientWebSocket ベース。.NET Framework
                         4.6.2+ で動作確認可能な範囲のみ提供する。
      web_transport    : .NET 8+ 等、QUIC / WebTransport クライアント
                         を持つ環境向け。.NET Framework Companion
                         には載せない。
      messaging_bridge : Kafka / AMQP の REST Proxy / 単純クライアント
                         越しに bidi メッセージを搬送する形態。
                         ネットワーク完全分離環境向け。
  - Conformance proof：各 adapter は tier1 Server系 の Transport
    Adapter Layer と同一の conformance scenario corpus
    （「03_Server系」Conformance Equivalence の機械的担保）に対して
    green を merge 条件とする。片側でしか通らない adapter はその
    時点で当該 conformance class の preferred transport から外す。
  - capability 宣言：Companion は起動時に自身が利用可能な adapter
    一覧 / TLS バージョン / inbound 可否 / max message size 等を
    Open RPC の client_capabilities として送出する。Gateway が選んだ
    chosen_transport を尊重する。アプリ側のコード変更は伴わない。
  - resume の透過化：bidi RPC が resumable: REQUIRED を持つ場合、
    Companion は transport 切替（例：SSE 切断 → 再接続、または
    websocket → sse_paired への降格）を跨いで session を継続する。
    アプリは onMessage / send の API しか見えず、再接続は Companion
    内部で完結する。
  - スコープ外：proto に書かれた意味論を実行することに留め、
    Library が提供する機能カテゴリ（Messaging / Relational Store /
    Workflow など）の抽象は持たない。Transport Negotiation も
    「proto 上の RPC を運ぶ」までの責務で、業務セマンティクスの
    解釈・補正は行わない。

  ── 長期収斂
  - tier1 側の Adapter Layer 退役（webhook / long_poll / sse_paired
    等の段階的廃止）に追随し、Companion 側 adapter も同期して退役
    する。Adapter の追加 / 退役はいずれもアプリのコード変更を伴わ
    ない（capability 宣言からの自動降格 / 自動採用で吸収する）。
  - レガシー言語そのものが対象 fleet から退役した時点で Companion
    自体の保守も終了する。その時点で Proto 二層化も単層へ collapse
    する（「03_Server系」Proto 二層化「長期方針」を参照）。
