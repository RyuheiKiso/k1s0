============================================================
tier1 Library 設計方針
============================================================

■ 方針
  - tier1 Library は「機能カテゴリ単位の抽象 API」を tier2 / tier3 に提供
    する。現行採用 OSS は実装の詳細であり、Library の表面 API には漏らさ
    ない。
  - tier2 / tier3 は本 Library のみを通じて infra にアクセスする。OSS の
    クライアントライブラリを直接 import することは禁止する（機械的担保は
    本ファイル「強制機構」節を参照）。
  - Library を直接組み込めない言語（.NET Framework など）に対しては、
    ビジネス API と観測可能性を分けて提供する。
      - ビジネス API：tier1 提供のゲートウェイ経由でアクセスする。
        .proto を単一の真とし、Envoy Gateway の gRPC-JSON Transcoder で
        HTTP/1.1 + JSON / NDJSON エンドポイントを派生させる
        （streaming RPC の扱い詳細は「05_tier1/03_Server系」Proto
        二層化 / RPC 形式の射影方針を参照）。
      - 観測可能性 / 認証コンテキスト伝播：Observability Companion を
        別途提供する（詳細は本ファイル末尾を参照）。

■ パッケージ構成（frontend / backend 分離方針）
  - Library は core / frontend / backend の 3 パッケージで構成し、
    対象言語ごとにこの 3 パッケージを提供する。
  - 両者で重複する概念は core に集約し、frontend / backend は core
    に依存する形を取る。core に置く対象例：
      - 認証コンテキスト / テナント識別子の型と伝播ヘルパ
      - 構造化ログ / トレース / メトリクスの共通スキーマ
      - 共通エラー型、リトライ / タイムアウト等のポリシー定義
  - frontend パッケージにバックエンド専用の依存（DB ドライバ、Kafka
    クライアント、Temporal クライアント等）が混入することを禁止する。
    「提供機能カテゴリ」の「対象」列で frontend / backend / both を
    明示し、バンドル境界の検査基準とする。
  - 「対象」が both のカテゴリでも、具象 API は frontend / backend で
    異なって構わない（例：Authentication は frontend で OIDC PKCE
    クライアント、backend でトークン検証 / 認可ポリシー評価）。core
    が共有するのは型と概念であり、API 表面の完全一致は要求しない。

■ 抽象化レベルの方針
  - 機能カテゴリごとに到達可能な抽象化レベルが異なる。一律に「OSS 差し
    替えで業務コード無変更」を受け入れ基準として課すと、Messaging /
    Workflow / Saga / Rule Engine 等は「Library に乗らない」結論になり、
    かえって tier2 / tier3 が OSS を直接触る抜け穴を生む。これを避ける
    ため、Library は次の 3 段階の抽象化レベル（Lv）を認め、カテゴリ
    ごとに到達目標を割り当てる。

  - L3 : OSS 中立
      - OSS 固有の型 / 概念を API 表面に一切出さない。
      - 受け入れ基準 : OSS 差し替え時、業務コード（tier2 / tier3）は無変更。
      - 前提 : 当該カテゴリの wire / プロトコル仕様が業界標準として
        確立しており、複数 OSS 実装が同じ表面を提供できること
        （例：S3 API、RESP、OpenTelemetry、OIDC、gRPC）。
      - 想定対象 : Logging / Tracing / Metrics / Authentication / Secret /
        RPC / KeyValue / Object Storage。

  - L2 : 同族内 OSS 中立
      - OSS 固有の語彙は Library 独自語彙に翻訳する。分割キー / 順序
        保証 / 再試行境界 / トランザクション境界 / インデックス種別
        などの概念は API 表面に残す。
      - カテゴリごとに「同族」を明示列挙し、その範囲内での差し替えを
        保証対象とする。族の外への差し替えは保証外であり、族の改廃
        そのものを Library の破壊的変更（major version up）として扱う。
      - 受け入れ基準 : 族内差し替え時、業務コードは型置換 + 一部チュー
        ニング（パラメータ調整・索引再設計など）で済み、業務ロジック
        の再設計は不要。
      - 想定対象 : Profiling、Feature Flag、Messaging / EventBus、
        Schema Registry、Relational Store、Vector Search。
      - 同族の具体定義は「05_提供機能カテゴリ」を参照。

  - L1 : 概念露出
      - OSS 固有の概念（Workflow / Activity 境界、補償処理の書き方、
        決定表 DSL 等）が API 表面に出る。Library の責務は OSS の隠蔽
        ではなく、以下の横断要素の強制に絞る。
          - 認証コンテキスト / テナント識別子の伝播
          - 構造化ログ / トレース / メトリクスの自動計装
          - 共通エラー型 / リトライ・タイムアウトポリシー
          - ベストプラクティスのテンプレート提供
      - 受け入れ基準 : OSS クライアントを直接 import させない経路を
        Library として一本化し、差し替え時の影響範囲が「Library + 該当
        カテゴリの業務コード」に限定できること（全層に波及しない）。
      - 想定対象 : Workflow / Long-running Saga、Rule Engine。

  - L1 / L2 で API 表面に露出する OSS 概念は、カテゴリごとに「露出概念
    一覧」として Library 側ドキュメントに明示する。OSS 差し替え時の影響
    範囲調査チェックリストとして使う。
  - L3 を狙えないことを理由に Library から外さない。代わりに L1 / L2
    を選び、tier2 / tier3 が OSS を直接 import する経路を塞ぐことを
    優先する。

■ 横断的に Library が担う共通要素
  - 認証コンテキスト（誰が呼んでいるか）の伝播。
  - トレース / ログ / メトリクスへの自動計装。
  - リトライ / タイムアウト / サーキットブレーカ等のレジリエンス。
  - マルチテナント識別子の伝播と分離。

■ 強制機構（OSS 直接 import 禁止の機械的担保）
  - 「OSS クライアントを直接 import しない」方針を運用で空文化させない
    ため、以下 3 層を多重に設ける（defense-in-depth）。いずれの層も CI
    の必須チェックとして組み込み、後付け運用や例外申請に依存しない。
  - 層 1 ：依存導入レベル（tier2 / tier3 リポジトリ側）
      - 各言語の標準ツールで OSS クライアントの import 自体を機械的に
        禁止する。
          Rust         : cargo-deny の [bans] で Kafka / PostgreSQL /
                         Temporal / Valkey / Object Storage 等のクライ
                         アント crate を deny。
          C# (.NET 8+) : BannedApiAnalyzers の BannedSymbols.txt で OSS
                         の名前空間を禁止し、Central Package Management
                         で未承認パッケージの参照自体を弾く。
          Go           : golangci-lint の depguard で OSS クライアントの
                         import パスを deny。
          TypeScript   : eslint-plugin-import の no-restricted-imports と
                         eslint-plugin-boundaries で禁止と層越境を検出。
      - 上記設定は Backstage の Software Template に同梱し、tier2 /
        tier3 リポジトリ生成時点で組み込む。
  - 層 2 ：Library 公開 API 表面レベル（tier1 側）
      - Library が OSS 型を再エクスポート（Rust の pub use、C# の
        public 露出 等）すると、層 1 を満たしても業務コードが間接的に
        OSS 概念へ依存する。これを防ぐため、Library 公開 API を
        snapshot 化し差分を CI で検査する。
          Rust         : cargo public-api。
          C#           : Microsoft.CodeAnalysis.PublicApiAnalyzers
                         （PublicAPI.Shipped.txt 運用）。
          Go           : go-apidiff と自製 go/analysis を併用。
          TypeScript   : api-extractor の .d.ts rollup。
      - L3 / L2 カテゴリは公開シグネチャに OSS 型が現れたら CI fail と
        する。L1 カテゴリは「05_提供機能カテゴリ」の露出概念一覧と
        allowlist 一致を検査する。
  - 層 3 ：供給経路レベル（内部パッケージリポジトリの一元化）
      - tier2 / tier3 のビルドが OSS クライアントを物理的に取得できな
        いよう、内部パッケージリポジトリを唯一の取得元に固定する。
          Rust         : 内部 cargo registry を [source.crates-io] で
                         置換。
          C#           : 内部 NuGet feed のみ nuget.config に登録。
          Go           : Athens 等の内部 module proxy を GOPROXY に固定。
          TypeScript   : Verdaccio 等の内部 npm registry に固定。
      - 内部リポジトリには Library と承認済み補助パッケージのみを公開
        し、Kafka / Temporal / PostgreSQL 系等の OSS クライアントは
        置かない。Library リポジトリの CI に限り、外部 feed を許可する。
      - 「02_採用OSS一覧」[6] サプライチェーン / セキュリティ の
        Harbor / Cosign / Trivy と整合する形で構築する。

■ L2 同族保証の機械的担保
  - 「同族内 OSS 中立」を文書上の願望で終わらせないため、以下を CI と
    出荷物の両面で強制する。
  - 二バックエンド conformance（最重要）
      - 各 L2 カテゴリで、本命 OSS と同族内代替 OSS の最低 2 実装を
        Testcontainers で同時に立ち上げ、共通の統合テストを両方で green
        にすることを merge 条件とする。
      - 想定の組合せ（例）：
          Messaging              : Kafka (Strimzi) + RedPanda
          Schema Registry        : Apicurio + Confluent SR (OSS)
          Relational Store       : PostgreSQL (CNPG) + CockroachDB
          Vector Search          : pgvector + Qdrant
          Profiling              : Parca + Pyroscope
          Feature Flag           : flagd + GO Feature Flag
      - 片側でしか通らないテストが発生した時点で「その API は L2 として
        適格でない」とみなし、API を族内ポータブル範囲まで縮める、
        または当該機能を L1 拡張へ降格する。
  - capability negotiation
      - Library の初期化 API で、業務コード側が要求する能力（配信保証 /
        順序保証 / トランザクション境界 / 距離関数など）を宣言させる。
      - backend が要求能力を満たさない場合、起動時に fail-fast する。
        本番投入後の差し替えで silent な意味論変化が起きるのを防ぐ。
  - 露出概念 / 禁止概念の機械可読宣言
      - 「05_提供機能カテゴリ」の露出概念一覧をカテゴリごとに YAML で
        宣言し、許可概念 / 禁止概念を明示する。
      - 公開 API snapshot（cargo public-api、PublicApiAnalyzers、
        api-extractor、go-apidiff）と CI で照合し、禁止概念に該当する
        語が API 表面に出現したら fail させる。
      - これは「強制機構」層 2 と同じ枠で動かす。

■ 出荷時の二バックエンド方針
  - L2 / L3 のうち、族内差し替えの実用可能性を継続的に保証したい
    カテゴリは、CI conformance に加えて出荷時から複数バックエンドを
    サポート対象として併走させる。
  - day-1 で複数バックエンドを併走させる初期対象（最低限）：
      Messaging              : Kafka + RedPanda
      KeyValue / Cache       : Valkey + Dragonfly
      Object Storage         : Ceph RGW + MinIO
  - tier2 / tier3 リポジトリは Backstage Software Template で backend
    を選択できる状態とし、テンプレート選択肢の存在自体を「族内差し替え
    が機能している」生きた証跡として運用する。
  - CI conformance のみだと運用 1 年で片側が腐るため、出荷物として
    並走させること自体を保証手段に含める。

■ Observability Companion（Library 非対応言語向け追加提供）
  - 位置づけ：本 Library を組み込めない言語（.NET Framework など）に
    対し、観測可能性 / 認証コンテキスト伝播 / streaming トランスポート
    の薄物を担う。ビジネス API 抽象は含まない（ビジネス API のスキーマ
    / セマンティクスは引き続き Gateway 経由で利用する）。
  - 標準形態：.NET Framework 4.6.2+ 向けに OpenTelemetry .NET
    Auto-Instrumentation を採用する。CLR Profiler によるアタッチ方式
    で、アプリケーションのソースコード変更を不要とする。HttpClient /
    ASP.NET / ADO.NET / WCF などを自動計装する。配布形態は環境変数 +
    DLL 配置 + 再起動で完結させる。
  - 補助形態：Auto-Instrumentation 非対応環境（4.6.1 以前など）向けに
    NuGet 参照型の Companion を提供する。HttpClient 用
    DelegatingHandler、Authorization / traceparent / テナント識別子の
    伝播ヘルパ、Logger 拡張のみを含む。
  - streaming トランスポートヘルパ：External Proto の server-streaming
    RPC を扱うため、NDJSON（application/x-ndjson）リーダを NuGet 参照
    型 Companion に同梱する。HttpClient.ResponseHeadersRead に基づく
    chunk 消費・キャンセル・再接続を内蔵し、レガシー側に streaming
    トランスポートの自製を要求しない。client-streaming /
    bidirectional streaming は Server系 側で unary 射影に変換済みの
    ため、本ヘルパの対象外とする（詳細は「05_tier1/03_Server系」
    RPC 形式の射影方針を参照）。
  - スコープ外：いずれの形態も Library が提供する機能カテゴリ
    （Messaging / Relational Store / Workflow など）の抽象は含まない。
    streaming トランスポートヘルパも proto 上の RPC 定義および NDJSON
    のデシリアライズ補助に留まり、業務セマンティクスの解釈は行わない。
  - core スキーマとの整合：構造化ログ / span attribute 名は言語中立
    のスキーマ定義（YAML、OpenTelemetry Semantic Conventions 拡張
    形式）を単一の真とし、OpenTelemetry Weaver で各言語の定数コード
    を生成する。Companion は core 全体を取り込めないが、生成された
    定数のみを含む最小 NuGet を切り出して参照する形を取る。これに
    より人手による「複製実装」自体を排除する。
  - スキーマ持ち分の最小化：アプリ側で持つ組織固有スキーマは
    「テナント識別子・業務相関 ID・認証主体」等に絞り、HTTP / DB /
    RPC などの標準計装は OpenTelemetry Semantic Conventions に従う。
    属性のリネーム / 追加 / 削除は OpenTelemetry Collector のプロ
    セッサ（attributes / transform）で一元化し、Companion / 各言語
    Library 側に同等処理を持たせない。
  - CI 検証：定数文字列の一致確認に留めず、Testcontainers で
    OpenTelemetry Collector を起動し、Companion / 各言語 Library
    から実際に emit される span / log 属性をゴールデン値と比較する。
    スキーマ定義 → 生成定数 → 実行時出力の 3 点を CI で連結する。
