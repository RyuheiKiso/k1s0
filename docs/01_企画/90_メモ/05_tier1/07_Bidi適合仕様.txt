============================================================
tier1 Bidi 適合仕様（v1）
============================================================

■ 位置づけ
  - 「03_Server系」Transport Adapter Layer の意味論的不変量宣言
    （tier1.bidi.* option）の規約と、conformance scenario corpus と、
    adapter capability matrix の三者を、機械可読な単一の真として
    一箇所に固定する仕様書。
  - 03_Server系 が「動く層」を定義するのに対し、本仕様は「層が等価に
    動いていることを CI で機械的に証明する規約」を定義する。
  - Buf custom lint、conformance test runner、Capability Negotiation
    のいずれも本仕様が宣言する 3 つの YAML を共通入力として参照する。

■ 設計原則
  - conformance_class は bundle である。
      proto に書く tier1.bidi.* option のうち、conformance_class 1 つ
      の値が他 4 option（ordering / half_close / resumable /
      max_msg_lag_ms）を一意に導出する。RPC 作者が dimension を個別に
      override する経路は持たない。
  - dimension override は禁止する。
      「v1_event_feed のうち lag だけ縮めたい」要望は新 class を切る
      ことで表現する。class 数の爆発は意味論の規律として受け入れる。
      実務上、業務 RPC の意味論パターンは数えられる粒度に収束する
      （本仕様 v1 では 5）。
  - dead spec を CI で殺す。
      classes.yaml に登録された全 class、scenarios.yaml に登録された
      全 assertion id、capabilities.lock.yaml に列挙された全 adapter
      は、いずれも参照されなくなった時点で CI fail とする。

■ v1 class セット（5 class）
  - proto に書ける conformance_class は次の 5 値のみ。Buf custom lint
    で classes.yaml の keys と照合する。

      class             | ordering        | half_close | resumable | lag(ms) | direction
      ------------------+-----------------+------------+-----------+---------+----------------
      v1_interactive    | SESSION_ORDERED | SUPPORTED  | REQUIRED  |    200  | bidirectional
      v1_alert          | SESSION_ORDERED | UNUSED     | REQUIRED  |    200  | server→client
      v1_event_feed     | SESSION_ORDERED | UNUSED     | REQUIRED  |   5000  | server→client
      v1_live_snapshot  | UNORDERED       | UNUSED     | NONE      |    500  | server→client
      v1_bulk_upload    | UNORDERED       | SUPPORTED  | NONE      |      0  | client→server

  - 各 class の不変条件（invariants）と典型用途：

      - v1_interactive
          - 双方向対話。順序 + half_close + resume + 低 lag を要する。
          - resume 跨ぎで at-most-once-effective（受信側 dedup を
            adapter が担保）。
          - 典型：設備リモート操作、collaborative editing、IME 補助。

      - v1_alert
          - server-driven の警報配信。低 lag と replay の両立。
          - resume 跨ぎで at-most-once-effective。
          - 典型：設備異常通知、SLA 違反通知、安全系 alarm。

      - v1_event_feed
          - server-driven のドメインイベント配信。順序保証 + replay。
          - lag は監査 / 業務通知の SLA として 5 秒に置く。
          - 典型：Domain Event sub、監査ログ tail、品質検査結果配信、
            受注 sub。

      - v1_live_snapshot
          - server-driven の最新値表示。順序不要、抜け許容。
          - delivery 性質は latest-wins。
          - 典型：feature flag 配信、ダッシュボード tile、ライブ KPI、
            在庫最新値。

      - v1_bulk_upload
          - client-driven の大量データ投入。
          - 配送性質は at-least-once、重複は受信側で idempotent に処理
            する。
          - 典型：metric / log / profile / IoT sensor / SCADA テレメトリ。

  - 上記 5 class で v1 が covering。製造業 pack 想定 RPC 10 件の stress
    test を本仕様末尾に示す。

■ dimension の根拠
  - ordering = SESSION_ORDERED の存在意義は resumable=REQUIRED と
    組む時に強く出る（順序保証 = 抜けの検出可能性 = resume の根拠）。
    SESSION_ORDERED + NONE は v1 では採らない。順序保証はあるが落ちたら
    抜ける、は業務的にレアな矛盾形のため。
  - UNORDERED + REQUIRED も v1 では採らない。順不同で resume は意味論
    として薄い。
  - half_close = SUPPORTED は client から終端を伝える局面が要る class
    にだけ付く（v1_interactive、v1_bulk_upload）。それ以外の server
    push 系（v1_alert、v1_event_feed、v1_live_snapshot）は UNUSED。
  - max_msg_lag_ms は数値だが、class 内では「class の SLA」として
    固定値を持つ。0 は best-effort（assertion から lag 検査を除外
    する宣言）。

■ delivery_guarantee を独立次元にしない理由
  - 配送回数の性質（at-most-once / at-least-once / exactly-once）は
    本来 ordering / resumable と直交する次元だが、v1 の 5 class それ
    ぞれに自然な配送性質が 1 つ決まる：
        v1_interactive / v1_alert / v1_event_feed → at-most-once-effective
        v1_live_snapshot                          → latest-wins（抜け許容）
        v1_bulk_upload                            → at-least-once（idempotent 受信）
  - 業務側で迷う余地がないため、proto option として明示的に dimension
    化する利得が乏しい。「class が暗黙の不変条件として保持する」形に
    留める。
  - v2 で「class の組合せが指数化する」ことが現実問題になった時点で、
    delivery_guarantee を独立次元に昇格する余地は残す（破壊的変更
    として major version up）。

■ spec の 3 ファイル構成（単一の真）

  ── tier1/conformance/classes.yaml
      - class bundle 定義。conformance_class 名 → 4 option + invariants
        の純粋関数テーブル。
      - スケッチ：
            classes:
              v1_interactive:
                options:
                  ordering: SESSION_ORDERED
                  half_close: SUPPORTED
                  resumable: REQUIRED
                  max_msg_lag_ms: 200
                invariants:
                  delivery_after_resume: at_most_once_effective
                  direction: bidirectional
              v1_alert:
                options:
                  ordering: SESSION_ORDERED
                  half_close: UNUSED
                  resumable: REQUIRED
                  max_msg_lag_ms: 200
                invariants:
                  delivery_after_resume: at_most_once_effective
                  direction: server_to_client
              v1_event_feed:    { ... }
              v1_live_snapshot: { ... }
              v1_bulk_upload:   { ... }

  ── tier1/conformance/scenarios.yaml
      - scenario × option 値 → assertion id のマトリクス。各 scenario
        がどの option 値の組合せで何を assert するかを宣言する。
      - assertion id は各言語の test runner が attribute / decorator で
        claim する索引。
      - スケッチ：
            scenarios:
              parallel_send:
                description: "並列送信した N メッセージの順序性 / 到達性"
                matrix:
                  - when: { ordering: SESSION_ORDERED }
                    assertions:
                      - pl_seq_monotonic_per_session
                      - pl_no_drop_under_well_formed
                  - when: { ordering: UNORDERED }
                    assertions:
                      - pl_no_drop_under_well_formed

              resume_after_disconnect:
                description: "TLS 切断後 resume_token で再接続"
                matrix:
                  - when: { resumable: REQUIRED }
                    assertions:
                      - rd_seq_continuous_across_resume
                      - rd_no_dup_within_resume_window
                  - when: { resumable: NONE }
                    assertions:
                      - rd_new_session_id_emitted

              slow_consumer_backpressure:
                description: "受信側の処理が遅い場合の lag / バッファ挙動"
                matrix:
                  - when: { max_msg_lag_ms: { gt: 0 } }
                    assertions:
                      - sc_p99_lag_within_budget
                      - sc_no_unbounded_buffering
                  - when: { max_msg_lag_ms: 0 }
                    assertions:
                      - sc_no_unbounded_buffering

              half_close_initiator:
                description: "half_close 後の両方向の挙動"
                matrix:
                  - when: { half_close: SUPPORTED }
                    assertions:
                      - hc_post_close_no_inbound
                      - hc_outbound_continues_until_eof
                  - when: { half_close: UNUSED }
                    assertions:
                      - hc_close_terminates_stream

              proxy_buffering_injection:  { ... }
              tls_disconnect:             { ... }
              large_message:              { ... }
              long_idle:                  { ... }

      - corpus 全体は 03_Server系 Conformance Equivalence 節と整合し、
        9 scenario を最小コーパスとする。

  ── tier1/adapters/capabilities.lock.yaml
      - 各 adapter crate の static 自己宣言（pub const
        ADAPTER_DECLARATION）を tier1 build script が集約して生成する
        build artifact。手書き禁止、PR レビュー対象は YAML diff だが
        書込みは自動。
      - スケッチ：
            # AUTO-GENERATED. DO NOT EDIT.
            adapters:
              grpc_native:
                supports: [v1_interactive, v1_alert, v1_event_feed,
                           v1_live_snapshot, v1_bulk_upload]
              web_transport:
                supports: [v1_interactive, v1_alert, v1_event_feed,
                           v1_live_snapshot, v1_bulk_upload]
              websocket:
                supports: [v1_interactive, v1_alert, v1_event_feed,
                           v1_live_snapshot, v1_bulk_upload]
              sse_paired:
                supports: [v1_alert, v1_event_feed, v1_live_snapshot,
                           v1_bulk_upload]
              long_poll:
                supports: [v1_event_feed]
              webhook:
                supports: [v1_alert, v1_event_feed, v1_live_snapshot]
              messaging_bridge:
                supports: [v1_event_feed, v1_live_snapshot, v1_bulk_upload]
                constraints:
                  v1_event_feed:
                    partition_key: session_id
                    max_concurrent_sessions: "<= partition_count"

      - constraints 節は、physical な substrate 制約を adapter が静的
        に宣言するための領域。Capability Negotiation は本制約を起動
        時に読み込み、宣言違反する fleet では当該 adapter × class を
        不採用とする。
      - 例：messaging_bridge は Kafka rebalance により SESSION_ORDERED
        を partition 単位でしか保証できない。そのため session_id を
        partition key に固定し、同時 session 数を partition 数以下に
        制約する宣言を必須とする。

■ Buf custom lint の責務（縮約）
  - 本仕様により Buf custom lint の仕事は次に縮約される：
      1. proto に書かれた conformance_class が classes.yaml の keys に
         存在すること。
      2. proto に他 tier1.bidi.* option が併記されている場合、その値が
         classes.yaml の bundle 値と一致すること（不一致は fail）。
      3. bidi RPC で conformance_class option が欠落していたら fail。
      4. 廃止予定 class（v2 で deprecated になる class 等）の使用に
         warn。
  - 「矛盾」の概念は本仕様により「テーブル不一致」に縮約される。
    これにより lint の判断主観が消える。

■ test runner と assertion id の連結
  - 各言語側 test runner は scenarios.yaml の assertion id を
    attribute / decorator で claim する。例：

        Rust:
            #[conformance_assert("pl_seq_monotonic_per_session")]
            fn check(events: &[Event]) -> Result<()> { ... }

        C# (Companion):
            [ConformanceAssert("pl_seq_monotonic_per_session")]
            public Task Check(IReadOnlyList<Event> events) { ... }

        TypeScript:
            export const check = conformanceAssert(
                "pl_seq_monotonic_per_session",
                (events: Event[]) => { ... }
            );

  - CI は次の関係性を全数検査する：
      - scenarios.yaml の全 assertion id について、対応 adapter ×
        対応言語で実装が存在し green を返す。
      - assertion id の typo / 未参照は fail。
      - adapter が claim する class について、scenarios.yaml が要求
        する全 assertion id を adapter 側 fixture が走らせる。
  - test runner の native 言語は Rust が一次。Companion は C# / TS で
    必要な範囲のみ。

■ Capability Negotiation との関係
  - 03_Server系 Capability Negotiation 節の chosen_transport 選択は、
    起動時に capabilities.lock.yaml を読み込んで実装される：
      1. proto の conformance_class C を取得。
      2. lock.yaml で C を supports に含む adapter 集合 A を抽出。
      3. constraints 節で fleet の物理条件を満たさない adapter を A
         から除外。
      4. クライアントが Open RPC で宣言した client_capabilities ∩ A
         を算出。
      5. サーバ側で定義された優先順位でソートして chosen_transport
         を返却。
  - lock.yaml は build artifact のため、サーバの起動とともに固定
    される。deploy 中に動的に書き換わらない。

■ CI 不変条件（3 ファイル間の関係性検査）
  - 以下を CI の必須チェックとして組み込む。違反は merge 不可。
      - 整合 1：classes.yaml の全 class が scenarios.yaml の matrix
        条件で少なくとも 1 scenario によりカバーされる
        （dead class 検出）。
      - 整合 2：scenarios.yaml の全 assertion id が、それを必要とする
        全 class × 全 adapter × 全対応言語で実装されている。
      - 整合 3：capabilities.lock.yaml で claim される class が
        classes.yaml に存在する（dangling reference 検出）。
      - 整合 4：classes.yaml に登録された class のうち、いずれの
        adapter からも supports されない class が存在しないこと
        （unreachable class 検出）。
      - 整合 5：proto に conformance_class フィールドが書かれた全
        RPC が、いずれかの adapter から到達可能であること
        （unreachable RPC 検出）。
      - 整合 6：capabilities.lock.yaml は手書き禁止のため、build
        script が生成した内容と git 上の内容が完全一致すること
        （generation drift 検出）。

■ 製造業 pack stress test（v1 の正当性証跡）
  - 以下の 10 RPC を v1 class に classify した結果、全て 5 class で
    覆える。class が漏れなく機能している証跡として保持する。

      # | RPC                                  | class             | 判定根拠
      --+--------------------------------------+-------------------+------------------------------
      1 | 設備リモート操作                     | v1_interactive    | 双方向 + 順序 + 低 lag + 瞬断耐性
      2 | ライン稼働監視 (live tile)           | v1_live_snapshot  | latest-wins、抜け許容
      3 | 品質検査結果配信                     | v1_event_feed     | 順序 + 監査目的の replay
      4 | SCADA テレメトリ収集                 | v1_bulk_upload    | client-driven 大量、idempotent
      5 | 図面 collaborative review            | v1_interactive    | 双方向
      6 | 在庫最新値表示                       | v1_live_snapshot  | latest-wins
      7 | 受注 sub (基幹 → 製造管理)           | v1_event_feed     | 順序 + replay
      8 | 警報配信                             | v1_alert          | server-driven + 低 lag + replay
      9 | 計量装置連続データ                   | v1_bulk_upload    | continuous push
     10 | 出荷指示双方向確認                   | v1_interactive    | 双方向

  - stress test 自体は Testcontainers で各 RPC のサンプル実装を 5
    class に対して走らせる形で CI に組み込む。新しい業務 RPC が v1
    のいずれの class にも収まらないと判明した時点で、本仕様は v2
    候補として class 追加検討に入る。

■ v2 拡張ルール
  - 新 class の追加は purely additive：v1 class はそのまま残し、v2 で
    新規 class（例：v2_realtime_strict、v2_event_feed_compact）を
    追加する。
  - 既存 class の dimension 値変更は破壊的変更（major version up）。
    例えば v1_event_feed の lag を 2000ms に縮めたい場合、新 class
    v2_event_feed を切り、移行 toolchain（04_Library L1+ 移行コミット
    メント節と同型）を tier1 が成果物として提供する。
  - 命名は vN_<usage> 形式に固定。N は本仕様のメジャー版数。usage は
    業務側の認識ラベル（interactive / alert / event_feed 等）。
  - dimension override 禁止の規律は v1 → v2 跨ぎでも維持する。
  - delivery_guarantee 等の独立次元昇格は v2 以降で検討する。昇格時
    は既存 class の不変条件を昇格次元の固定値として残し、新 class が
    昇格次元を可変にする形を取る。

■ 長期収斂への作用
  - 03_Server系 Proto 二層化の単層 collapse、Library 非対応言語の
    退役、古い adapter（webhook / long_poll / sse_paired）の段階的
    廃止は、いずれも本仕様の 3 ファイルに対する purely additive /
    purely subtractive 変更として進行する：
      - adapter 退役 = capabilities.lock.yaml から自動的に消える
        （crate 削除と連動）。
      - class 退役 = classes.yaml から removal、scenarios.yaml の
        該当 matrix 行が unreachable 検出により誘導的に整理される。
      - proto / 業務コードはいずれも無変更で遷移する。
  - 本仕様は「単一 OSS 深耕 + 移行コミットメント」（04_Library L1+）
    の哲学を transport 軸に転写したもの（単一 transport 深耕では
    なく、bidi semantics 深耕 + transport 移行コミットメント）の
    具体形である。
