============================================================
tier1 観測適合仕様（v1）
============================================================

■ 位置づけ
  - 「02_採用OSS一覧」が宣言する ClickHouse 一本化（log / trace の
    SoR）、「05_提供機能カテゴリ」Observability 系 4 カテゴリ
    （Logging / Tracing / Metrics / Profiling）、「04_Library」
    Companion 役割 A、「06_tier2/16_強制機構」層 8（観測可能性
    スキーマ整合）、「07_tier3/33_観測可能性」（cross-tier trace /
    RUM）、「06_tier2/14_業務エラー監査コンプライアンス」（監査
    エントリ schema）、「06_tier2/32_テナント分離適合仕様」
    （audit_local の trace_id 強制）が散在的に宣言する次の四つを、
    機械可読な単一の真として一箇所に固定する仕様書 :
      (a) 5 signal class（logs / metrics / traces / profiles / audit）
          の SoR / 派生関係 / retention / queryability
      (b) 4 dimension layer（core / tier1_ext / tier2_ext / tier3_ext）
          の namespace 所有権と合成順序
      (c) trace_id を primary key とする cross-signal cross-tier
          相関契約
      (d) PII redaction policies の単一の真と各 tier 実装の整合
  - 三軸（07 transport / 32 data / 39 client）と migration 軸（08）
    が「動く層」の真を担うのに対し、本仕様は「動いた事実の真」を
    担う対称軸として位置付ける。同型の枠組み（bundle 化 / dimension
    override 禁止 / dead spec 殺し / build artifact 化 / 5 層
    defense-in-depth / CI 不変条件）はそのまま継承する。

■ 設計原則
  - signal は 5 class で固定する。
      logs / metrics / traces / profiles / audit の 5 class のみ
      許容。「02_採用OSS一覧」が記述する OSS（ClickHouse / Prometheus
      / Jaeger v2 内蔵 CH storage / Parca）の選定はこの 5 class への
      1:N マップで決定する。新 signal の追加は破壊的変更（major version up）。
  - SoR と派生関係を一意に固定する。
      各 signal の SoR を 1 ストアに固定する（**logs / traces /
      profiles / audit は ClickHouse、metrics は Prometheus** の
      二 SoR 構成。「02_採用OSS一覧」のClickHouse 一本化方針は
      log / trace に限定した記述として読む）。派生 signal
      （exemplar / label 等）は SoR の query で再構成可能で
      あることを property test で保証する。Prometheus と
      ClickHouse は exemplar の trace_id label / span attribute を
      経路として相互参照（後述 metric_to_trace_link 契約）。
  - dimension は 4 layer の合成として宣言する。
      core（OTel Semantic Conventions）/ tier1_ext / tier2_ext /
      tier3_ext + Companion 拡張の 4 layer を OpenTelemetry Weaver
      で合成。各 layer の namespace 所有権を排他に固定し、跨 layer
      の rename / collision を CI で検出する。
  - trace_id を cross-signal cross-tier の primary key とする。
      W3C Trace Context が tier3 RUM → tier2 → tier1 backend を
      貫き、log / metric exemplar / trace / profile / audit の
      全 signal に統一注入される。注入箇所は各 signal の SoR 投入
      経路に固定し、「業務コードが trace_id を手動で扱う経路」を
      持たない。
  - PII redaction は単一の真 + Collector 強制。
      PII フィールドリストを redaction.yaml で 1 箇所に宣言し、
      OTel Collector のプロセッサ（attributes / transform）で物理
      的に削除する。Library / Companion / app code に同等処理を
      持たせない。ゴールデン値テストで「PII を含む input → 出力
      に PII が残らない」property を全 signal で検証する。
  - 5 層 defense-in-depth で構成する。
      層 A : signal / dimension 宣言（signals.yaml / dimensions.yaml）
      層 B : Weaver 生成 + lint（生成定数の使用強制）
      層 C : Testcontainers + Collector でのゴールデン値テスト
      層 D : runtime（Collector プロセッサが PII 物理削除 + trace_id
             統一注入）
      層 E : storage 層（ClickHouse の column-level access policy /
             Prometheus exemplar / 監査保管期間 enforcement）
  - dead spec を CI で殺す（07/08/32/39 と同枠）。
      signals.yaml に登録された signal、dimensions.yaml に登録
      された属性、redaction.yaml に登録された PII field、
      correlation.yaml に登録された propagation rule、test_matrix
      .yaml の各 scenario、いずれも参照されなくなった時点で CI
      fail。

■ v1 signal class セット（5 class）
  - 全テレメトリはいずれかの class に属する。class が決まれば
    SoR / derived 関係 / retention / queryability / redaction
    要件 が決まる。

      signal     | SoR                            | 投入経路                           | retention   | queryability             | redaction
      -----------+--------------------------------+------------------------------------+-------------+--------------------------+------------------
      logs       | ClickHouse logs table          | OTel SDK → Collector → ClickHouse  | 規制要件次第| Apache Superset (SQL)    | Collector で必須
      metrics    | Prometheus                     | OTel SDK → Collector → Prometheus  | 短期 + 月次 | Perses (PromQL)          | low cardinality
                 |                                |                                    | downsample  |                          | required
      traces     | ClickHouse traces table        | OTel SDK → DaemonSet Collector     | tail        | Jaeger v2 (内蔵 CH       | Collector で必須
                 | (clickhouseexporter 投入、     | → loadbalancingexporter           | sampled     |   storage, first-party)  |
                 |  Jaeger v2 first-party storage |   (routing_key: traceId)          |             |   + Apache Superset      |
                 |  で UI 提供、4-A)              | → tail-sampling Collector         |             |   (SQL JOIN with logs)   |
                 |                                |   Deployment (aggregator)         |             |                          |
                 |                                | → clickhouseexporter → ClickHouse |             |                          |
      profiles   | Parca                          | Parca agent (eBPF / native pull)   | 短期         | Parca UI                 | low cardinality
                 |                                |                                    |             |                          | required
      audit      | ClickHouse audit table         | PostgreSQL audit_local             | 規制要件次第| Apache Superset (SQL)    | PII 構造的不在
                 |                                | → Audit relay → ClickHouse         | (10 年 +)   |                          | (32 で担保)

  - 各 class の不変条件 :

      - logs
          - 構造化 JSON のみ。free-form text は許容しない。
          - trace_id を top-level field として持つ（attribute では
            なく、ClickHouse の indexed column）。
          - PII は redaction.yaml の rule で Collector が物理削除。
          - 「06_tier2/24_読み取りモデル方針」ad-hoc 探索 UI は
            Superset over ClickHouse。

      - metrics
          - 高 cardinality 属性（aggregate.id 等）の attribute 化
            禁止。aggregate 単位の指標は traces / logs から SQL で
            集計する経路に寄せる。
          - exemplar に trace_id を必須注入。
          - tier1 露出概念（「05_提供機能カテゴリ」L1+ 露出概念）
            に紐付く OSS-specific metric は dimensions.yaml の
            tier1_ext で attribute namespace を固定。

      - traces
          - W3C Trace Context 準拠。tier3 → tier2 → tier1 backend
            を貫く 1 trace に統合される。
          - tail-based sampling は OTel Collector の tail_sampling
            processor で実施（「02_採用OSS一覧」記載）。本 processor
            は同一 Collector プロセス内に trace の全 span を集約しな
            ければ動作しないため、観測 Collector 経路は 2 段で構成する
            （次節「観測 Collector の 2 段 pipeline」）。
          - span attribute は dimensions.yaml の合成スキーマに準拠。

■ 観測 Collector の 2 段 pipeline
  - 段 1（per-node DaemonSet, gateway role）
      - SDK OTLP を受信、basic filtering（早期 PII redaction の一部、
        trace_id 注入の検査）を実施。
      - 段 2 への転送は loadbalancingexporter（routing_key: traceId）
        で trace_id 単位に集約 Collector を選択する。consistent hashing
        必須（新 Pod 追加時の trace split を防ぐ）。
      - logs / metrics / profiles 経路は段 1 から直接 SoR（ClickHouse
        / Prometheus / Parca）へ送出（trace 集約を要しないため）。
  - 段 2（gateway-aggregator Deployment）
      - tail_sampling processor を実行する Collector。同一 trace の
        全 span が同一 Pod に集約されることを段 1 の routing_key で
        保証する。
      - 出口は clickhouseexporter（CNCF OTel Contrib）で ClickHouse
        traces table に投入。UI 経路は Jaeger v2（v1.50+、first-party、
        Apache 2.0）の内蔵 ClickHouse storage を採用（4-A、02_採用OSS
        一覧 [2] 参照）。jaegertracing/jaeger-clickhouse community plugin
        は archive 済 + Jaeger v2 で plugin protocol 廃止のため不採用。
      - HPA で水平 scale。loadbalancingexporter の hash ring が re-shape
        した際の trace split は consistent hashing で最小化、残余の
        部分集約 trace は dropped_partial_trace_count metric で記録。
  - 単段（DaemonSet 単体で tail_sampling を完結する構成）は trace
    split を防げないため不可。08_infra/04_採用OSS の OTel Collector
    配置記述および 12_client/11_観測Auto-Instrumentation方針 の
    exporter / collector 物理冗長は本 2 段構成と整合する。

      - profiles
          - Parca による Continuous Profiling。trace_id を Parca
            label として注入し、特定 trace 起点の hot path 解析を
            可能にする。
          - 業務識別子（tenant.id 等）の label 付与は low cardinality
            原則で制限。テナント別 hot path 解析が必要な場合は
            sampled subset で行う。

      - audit
          - 「06_tier2/14_業務エラー監査コンプライアンス」の業務
            観点監査エントリ。
          - 「06_tier2/32_テナント分離適合仕様」atomic 三表書込で
            audit_local に書込まれ、Audit relay が ClickHouse に
            転送する。relay の at-least-once + ReplacingMergeTree
            で idempotent。
          - hash chain（hash_prev / hash_self）が ClickHouse 側で
            再検証され、不整合は alert（「06_tier2/27_信頼性運用
            準備」アラート方針整合）。
          - PII は構造的に含まれない（32 audit_local schema 参照）。

  - 5 class で v1 を covering する。新 signal class（例：
    network_flow / browser_replay）が必要と判明した時点で v2 候補
    として class 追加検討に入る。

■ v1 dimension layer（4 layer の合成スキーマ）
  - OpenTelemetry Semantic Conventions の拡張を 4 layer 構成で
    宣言する。各 layer は排他的 namespace 所有権を持ち、跨 layer
    の rename / collision を CI で検出する。

      layer       | namespace prefix      | 所有 tier   | 例
      ------------+-----------------------+-------------+--------------------------------------
      core        | (OTel SC base)        | OTel 上流   | http.* / rpc.* / db.* / messaging.*
                  |                       |             |   / faas.*
      tier1_ext   | tier1.*               | tier1       | tier1.bidi.* / tier1.transport.* /
                  |                       |             |   tier1.oss.exposed.* (露出概念)
                  |                       |             | （tier1.transport.* の例：
                  |                       |             |   tier1.transport.tls_version /
                  |                       |             |   tier1.transport.cipher_suite /
                  |                       |             |   tier1.transport.alpn。これらは
                  |                       |             |   観測 SoR 専用の dimension で、
                  |                       |             |   07_Bidi適合仕様 scenarios.yaml
                  |                       |             |   の assertion 対象外。）
      tier2_ext   | tier2.*               | tier2       | tier2.tenant.id / tier2.aggregate.id
                  |                       |             |   / tier2.business_event /
                  |                       |             |   tier2.aggregate_class /
                  |                       |             |   tier2.purpose
      tier3_ext   | tier3.*               | tier3       | tier3.screen.id /
                  |                       |             |   tier3.interaction.kind /
                  |                       |             |   tier3.web_vitals.* /
                  |                       |             |   tier3.layer (39 layer)

  - layer 合成の不変条件 :
      - core 属性の rename / 削除を ext layer は行わない（OTel SC
        への準拠を破らない）。
      - tier2_ext は tier1_ext を参照する（aggregate.id は
        tier2.aggregate.id だが、aggregate_class が指す class は
        tier1.oss.exposed.* の概念）。
      - tier3_ext は tier2_ext を参照する（39 client 軸の layer /
        conflict_event）。
      - Companion 拡張は tier1_ext + tier2_ext のサブセットを
        生成定数として最小 NuGet で配布（「04_Library」Companion
        役割 A の核心、本仕様で機械化）。
      - 全 layer は OpenTelemetry Weaver で各言語の定数コードを
        生成。app code は生成定数のみを使い、文字列リテラル直書き
        を CI で禁止。

■ v1 correlation contract（cross-signal cross-tier）
  - primary key : trace_id（W3C traceparent の trace-id 部分、
    16 byte hex）。
  - 統一注入の原則 : 全 signal が trace context 内で emit される
    場合、trace_id を必須属性として保持する。注入箇所は signal
    別に固定 :

      signal     | trace_id 注入箇所
      -----------+----------------------------------------------------------
      logs       | ClickHouse logs.trace_id 列（top-level、indexed）
      metrics    | Prometheus exemplar の trace_id label
      traces     | OTel span の trace-id field（自然に存在）
      profiles   | Parca label "trace_id"
      audit      | audit_local.trace_id 列 → ClickHouse audit.trace_id 列

  - cross-tier propagation :
      - tier3 (Web SPA / Companion) で生成または継承された trace_id
        が tier2 業務 API / Companion Gateway / tier1 backend を
        貫く。
      - 「07_Bidi適合仕様」transport adapter は trace context を
        各 transport で機械的にマップ（HTTP/2 では traceparent
        header、HTTP/1.1 でも同、WebSocket では subprotocol、
        messaging_bridge では Kafka header）。
      - 「08_移行Pair適合仕様」の cutover 中も trace_id の連続性
        を保つ assertion を test_matrix.yaml に組む（co_observability
        _continuity）。

  - cross-signal join 契約 :
      - logs と traces の JOIN : ClickHouse 側で trace_id 列の
        equi-join。Apache Superset から両 table を結合する SQL
        を tier3 / 業務担当が直接書ける。
      - metrics と traces の JOIN : exemplar の trace_id を起点
        に Perses から該当 trace に drill-down。
      - profiles と traces の JOIN : Parca label の trace_id を
        起点に該当 trace の hot path を表示。
      - audit と logs/traces の JOIN : audit.trace_id で他 signal
        と相関。「14_業務エラー監査コンプライアンス」が要求する
        「いつ・誰が・何をした」の事後追跡を技術 telemetry と
        統一的に解析可能にする。

  - tier3 client 軸（39）との接続 :
      - 39 が宣言する 4 layer（ST / OL / PQ / DR）の各 lineage
        操作（rollback / promote / re-evaluate）に対応する span
        を tier3_ext で発行。trace_id が tier2 atomic 三表書込
        （32）まで貫通する。
      - 39 conflict_event の各分岐は span event として記録され、
        BusinessConflict subtype は span attribute として保持。

■ v1 PII redaction policies（単一の真）
  - PII field の宣言 :
      - 業務語彙で「PII フィールド」と分類された属性を
        redaction.yaml で 1 箇所に列挙する。
      - 列挙対象（例）: tier2.actor.email / tier2.actor.phone /
        tier2.actor.full_name / tier2.aggregate.address /
        tier3.form.input.value（業務マスタ参照経由で PII 化する
        可能性のある field）。
  - 適用箇所 :
      - 物理削除は OpenTelemetry Collector のプロセッサ
        （attributes processor の delete action / transform
        processor の delete_key statement）で実施。
      - Library / Companion / app code に同等処理を持たせない。
        「06_tier2/16_強制機構」層 8 / 「07_tier3/33_観測可能性」
        ログ・RUM への PII 漏洩防止節と整合。
  - actor 表現の固定 :
      - actor 識別子は Keycloak subject（不可逆 ID、sub claim）
        のみ。氏名 / メール / 電話 / 端末 ID は signal に出さない
        （「06_tier2/14_業務エラー監査コンプライアンス」PII 取り
        扱い節と整合）。
  - audit signal は構造的に PII 不在 :
      - audit_local の schema が PII 列を持たない（「06_tier2/
        32_テナント分離適合仕様」audit_local schema 参照）。
      - 「audit に PII を入れない」を runtime で守るのではなく
        schema レベルで物理的に不能にしている。本仕様の redaction
        layer は他 4 signal にのみ適用される。

■ 5 層 defense-in-depth

  ── 層 A : signal / dimension 宣言（signals.yaml / dimensions.yaml）
      - 5 signal を Rust enum と TypeScript / C# / Go の定数として
        生成。app code は生成物のみを参照可能。
      - 4 dimension layer の attribute 一覧を Weaver で各言語の
        定数コードに展開。

  ── 層 B : Weaver 生成 + lint
      - app code が attribute 文字列リテラル（"tier2.tenant.id"
        など）を直書きすることを CI fail。
          Rust         : Clippy lint + cargo public-api。
          C#           : Roslyn analyzer。
          Go           : go/analysis。
          TypeScript   : eslint-plugin で文字列リテラル attribute
                         検出。
          Companion    : 最小 NuGet パッケージのみ参照可能、それ
                         以外の attribute 名利用を BannedSymbols
                         で deny。

  ── 層 C : Testcontainers + Collector でのゴールデン値テスト
      - test_matrix.yaml の全 scenarios を Testcontainers で実行。
        OTel Collector + ClickHouse + Prometheus + Parca + Audit
        relay の本物を起動し、合成 workload を流して全 signal の
        ゴールデン値と比較。
      - merge 条件 : 全 scenarios green。skip 不可。

  ── 層 D : runtime（Collector プロセッサが PII 物理削除 + trace_id
             統一注入）
      - Collector の processors:
          - attributes / transform : redaction.yaml から自動生成
            される設定で PII を物理削除。
          - resource processor : trace_id を log records と
            metrics exemplar に補完注入。
          - tail_sampling : traces の retention を制御。
      - Collector 設定は手書き禁止。redaction.yaml + signals.yaml
        を入力として build artifact 化（次の lock）。

  ── 層 E : storage 層（最終 safety net）
      - ClickHouse audit table の schema が PII columns を物理的
        に持たない（「32_テナント分離適合仕様」audit_local schema
        と一致）。
      - ClickHouse logs / traces の retention policy は規制要件に
        従って TTL 設定で物理的に enforce。
      - Prometheus は cardinality budget を recording rule + alert
        で監視。budget 超過の metric は自動的に rate limited / 記録
        停止。

■ 三軸 + migration 軸との接合

  本仕様は 07 / 08 / 32 / 39 の上位レイヤとして、観測軸の不変条件
  を形式化する。

      transport (07) との接合 :
        - tier1.bidi.conformance_class を全 span の attribute と
          して必須注入。Capability Negotiation で chosen_transport
          が決まった瞬間に tier1.transport.chosen_adapter が span
          に記録される。
        - 07 の adapter ごとの trace_id propagation 機構は
          correlation.yaml の transport_adapters 節で機械可読化。

      data (32) との接合 :
        - audit_local.trace_id は本仕様 correlation contract により
          必須。Audit relay は ClickHouse audit table に trace_id
          列を持つ row として転送。
        - 32 atomic 三表書込の (P1)〜(P4) integrity property は、
          trace_id を起点にした log + audit JOIN で再検証可能。

      client (39) との接合 :
        - 39 の 4 layer + 5 conflict_event は tier3_ext の
          attribute として全数 enum 化。conflict subtype の UI 分岐
          も span event として記録され、事後解析で「どの subtype
          で何回起きたか」が ClickHouse SQL で可視。
        - 39 PII strip / attach の対称性 property test は本仕様の
          PII redaction property と同一の根拠で動作。

      migration (08) との接合 :
        - 08 の observability_continuity は本仕様の
          migration_cutover_observability_continuity scenario で
          自動検証。
        - 08 の dual_write_ramp 中の (P1)〜(P4) 両 backend 検証は
          本仕様の audit_log_join_with_traces を両 backend で同時
          実行する形で実現。

      clock_integrity (08_infra/16) との接合（cross-axis double-bound）:
        - span / log / audit_local / audit_event の全 emit に HLC
          tuple `(uint64 physical_ms, uint32 logical_counter, uint128
          node_id)` を必須包含。dimensions.yaml に `tier1.clock.hlc
          _physical_ms` / `tier1.clock.hlc_logical_counter` / `tier1
          .clock.hlc_node_id` の 3 attribute を tier1_ext namespace
          で追加。
        - audit hash chain hash 入力に HLC tuple を必須包含する
          ことで、wall-clock backwards step / clock skew 下でも
          因果性を保つ。08_infra/16 の causality_discipline =
          hlc_mandatory に整合。
        - redaction.yaml に hlc_physical_ms / hlc_logical_counter /
          hlc_node_id の 3 attribute を keep（PII でなく因果性
          証跡）として明示宣言、drop policy は適用しない。
        - 08_infra/16 の clock skew event は本仕様の audit signal
          sub-class `infra.clock_integrity.event` として ClickHouse
          に bulk insert、redaction policy は class / node_id /
          sync_protocol / skew_value を keep し、内部 HLC node_id
          の secret 部のみ drop（PII 不可達）。
        - 18 軸 cross-axis 双方向 lock として 08_infra/16 の clock
          _causality_proof.lock.yaml の green が本仕様 audit hash
          chain integrity の物理保証となる。

  これら接合点は test_matrix.yaml の各 scenario で
  cross_axis_assertions として明示し、CI で参照整合を検査する。

■ v2 拡張ルール
  - 新 signal class の追加（network_flow / browser_replay 等）は
    破壊的変更（major version up）。SoR / ingest_path / retention
    の宣言を必須とし、redaction policy も同時宣言。
  - 新 dimension layer の追加 / namespace prefix の変更は破壊的
    変更。命名衝突を CI で検出する規律は維持。
  - PII redaction の追加（新 PII field 検出）は purely additive。
  - 既存 signal の SoR 変更（例：traces の SoR を別実装に変更）
    は破壊的変更扱い。08 移行 toolchain と同型の dual-write 移行
    プロセスを経由する。

■ 長期収斂への作用
  - 5 軸（07 transport / 08 migration / 32 data / 39 client / 09
    observability）の同型構造で、tier1 / tier2 / tier3 / migration
    の真と「動いた事実の真」が独立に保たれ、軸間の接合は各 spec の
    test_matrix が cross_axis_assertions で担保する。
  - 観測 SoR は **ClickHouse (logs / traces / profiles / audit) +
    Prometheus (metrics) の 2 store 構成** で固定し、ClickHouse 側
    は SQL 直接照会で業務担当 / 監査 / インシデント分析が同じ query
    language で 4 signal を横断、Prometheus 側は PromQL で metric を
    照会、両者は exemplar trace_id 経路で相互参照する。OpenSearch /
    Loki / Tempo を採らないことの長期的優位を、本仕様の 5 ファイル
    が単一の真として保証する。
  - 5 軸の同型は「単一 OSS 深耕 + 移行コミットメント」（04_Library
    L1+）の哲学を観測軸にも転写したもの。ClickHouse 単一 OSS 深耕
    + 観測 SoR 移行 toolchain（08 の 5 番目の pair 候補として将来
    追加可能）を採る。
