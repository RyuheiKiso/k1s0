============================================================
tier1 SDK 設計方針
============================================================

■ 提供形態
  - Rust crate 群として tier1 SDK を提供する。
  - tier2 / tier3 の Rust コードからは crate 依存で直接利用する。
  - 非 Rust 言語向けには tier1 ゲートウェイサービス（Rust + tonic）
    を提供する。.proto を単一の真とし、Envoy Gateway の
    gRPC-JSON Transcoder で HTTP/1.1 + JSON エンドポイントを、
    gRPC-Web filter でブラウザ向けエンドポイントを派生させる。
    tier1 側で REST / gRPC-Web の独自実装は持たない。
  - クライアント別の経路:
      * Rust（tier2 / tier3）       : crate を直接利用
      * .NET 8+ / Java / Go 等      : gRPC（HTTP/2）で直接接続
      * .NET Framework / レガシー   : HTTP/1.1 + JSON
                                      （Envoy が gRPC へ転写）
      * ブラウザ                    : gRPC-Web（Envoy が gRPC へ転写）。
                                      双方向リアルタイム要件のみ
                                      WebSocket 経路を併用する。
  - 経路ごとのストリーミング可否は「ストリーミングの提供方針」を参照。
  - tier1 ゲートウェイは tier1 SDK と同一の API 形状を保ち、
    認証・トレーシングのコンテキスト伝播は tier1 が一元管理する。
    HTTP/1.1 経路では W3C traceparent / tracestate と
    Authorization ヘッダを Envoy が gRPC metadata に詰め替える。

■ crate 構成（初期）
  crate                     | 責務
  --------------------------+--------------------------------------------
  tier1-pubsub              | Kafka クライアントのラップ + CloudEvents
  tier1-state               | Valkey クライアントのラップ + etag / TTL
  tier1-db                  | sqlx + マイグレーション統合
  tier1-secrets             | OpenBao クライアント + キャッシュ
  tier1-otel                | OpenTelemetry 初期化 + 命名規約
  tier1-auth                | Keycloak OIDC クライアント + RBAC
  tier1-objstore            | S3 互換（Ceph RGW）のラップ + pre-signed URL 発行
  tier1-feature-flag        | OpenFeature SDK のラップ
  tier1-rpc                 | tonic + 共通 interceptor（Unary + WebSocket upgrade）
  tier1-stream              | Server / Bidirectional Streaming 用 interceptor
                            | （auth・trace 伝播・バックプレッシャー・ハートビート）

■ 設計上の制約宣言
  - 複数バックエンド対応は提供しない。
    例：Kafka を RabbitMQ に差し替える場合は、tier1-pubsub の実装ごと
    書き換える。これにより Dapr 的なコンポーネントモデルへの肥大化を
    予防する。
    ただし、tier2 / tier3 から見える API 形状は差し替え後も維持する
    （詳細は「バックエンド差し替えに対する API 安定性保証」を参照）。
  - Actor パターンは tier1 / tier2 で採用しない。
    長期 / 状態を持つフローは Temporal、軽量な非同期処理は Kafka に
    委ねる。Rust エコシステムでは Actor 専用 runtime の選択肢が
    乏しいため、依存を作らない。
  - tier1 SDK は最低 2 メジャーバージョンの併存を保証する。
    tier2 / tier3 が常に最新追従できない前提に立つ。
  - SDK で隠蔽するのは API 形状のみ。
    K8s マニフェスト、Operator のデプロイ順序、サイドカー構成などは
    infra / data チームの責務として残す。

■ ストリーミングの提供方針
  - サポート範囲は経路ごとに異なる。Unary 限定は HTTP/1.1 + JSON 経路に
    限定し、それ以外の経路ではストリーミング相当を選択肢として提供する。

    経路                              | サポート対象
    ----------------------------------+--------------------------------------
    Rust SDK（crate 直接）            | Unary / Server / Client / Bidirectional
    gRPC ネイティブ                   | Unary / Server / Client / Bidirectional
    （.NET 8+ / Java / Go 等）        |
    ブラウザ（gRPC-Web）              | Unary / Server Streaming のみ
                                      | （gRPC-Web 仕様上 Client / Bidi は不可）
    ブラウザ（WebSocket）             | 双方向リアルタイム要件のみ
                                      | （Envoy で upgrade、tier1-rpc が
                                      |  auth / trace を注入）
    HTTP/1.1 + JSON                   | Unary のみ
    （.NET Framework / レガシー）     |

  - ユースケース別の標準経路
    ユースケース                      | 推奨経路
    ----------------------------------+--------------------------------------
    サーバ→クライアントの push 通知   | gRPC Server Streaming
                                      | （HTTP/1.1 は SSE または webhook）
    双方向リアルタイム                | gRPC Bidirectional
    （チャット等）                    | （ブラウザは WebSocket で代替）
                                      | （HTTP/1.1 は対象外、pubsub へ）
    大容量ファイル転送                | tier1-objstore が pre-signed URL を
                                      | 発行し、クライアントが S3 互換へ直接
                                      | PUT / GET する。tier1 の RPC は
                                      | メタデータと URL のみ運ぶ
    長時間ジョブの進捗                | Temporal の signal / query を tier1 が
                                      | ラップ。短期間なら Server Streaming
    ライブダッシュボード              | gRPC Server Streaming
                                      | （HTTP/1.1 は long polling）

  - proto 設計時の判定フロー
    1. ペイロード > 1MB → object storage 経由を必須とし、RPC 化を禁止する。
    2. 1往復で完結する低レイテンシ要求 → Unary。
    3. サーバ→クライアントの push が要る → Server Streaming
       （HTTP/1.1 が必要なら SSE 派生を別途定義）。
    4. 双方向リアルタイムが要る → Bidirectional ＋ WebSocket 派生
       （HTTP/1.1 経路は提供しないと明示）。
    5. 進捗が分単位以上 → Temporal signal / query。

  - 設計レビューでの差し戻し基準
    - 上記マトリクスのいずれの代替経路にも適合しないストリーミング要件は
      差し戻す。
    - HTTP/1.1 経路に対する双方向ストリームの要望は無条件で差し戻す。

  - infra 隠蔽との関係
    - pre-signed URL 経路はクライアントが S3 互換に直接アクセスする構成と
      なるため、tier1 の隠蔽境界はメタデータ／URL 発行までとし、ペイロード
      転送経路は隠蔽対象外と明示する。
    - URL 発行時のバックエンド固有情報（バケット名、リージョン、署名方式）
      は tier1-objstore が抽象化し、tier2 / tier3 には URL のみを渡す。
    - WebSocket 経路の auth / trace 伝播は tier1-rpc に集約し、gRPC 経路と
      コードを二重化しない。

■ レガシー言語向け HTTP/1.1 + JSON 経路の仕様
  - 適用範囲
    - 対象は Rust SDK / Grpc.Net.Client を直接組み込めない言語
      （主に .NET Framework 4.x）。
    - 本経路は Unary RPC のみ提供する（「ストリーミングの提供方針」参照）。
      ストリーミング相当のユースケースは以下に振り分ける：
      ・サーバ→クライアント push 通知 : SSE または webhook
      ・長時間通知                     : pubsub（CloudEvents over Kafka）の
                                         ポーリング購読 or webhook 配信
      ・大容量ファイル転送             : tier1-objstore の pre-signed URL
    - 双方向ストリームの要望は無条件で差し戻す。

  - proto 規約
    - 公開対象 RPC には google.api.http アノテーションを必須化する。
    - buf lint のカスタムルールで「公開対象サービスの全 RPC に
      google.api.http が付与されている」ことを CI で強制する。
    - proto を単一ソースとし、JSON スキーマや OpenAPI を別管理しない
      （必要があれば proto から生成する）。

  - 冪等性
    - HTTP/1.1 経路は再送リスクが高まるため、Idempotency-Key
      ヘッダを必須化する。
    - Envoy が同ヘッダを gRPC metadata "x-idempotency-key" に詰め替え、
      tier1-rpc が共通 interceptor として受信・検証する。

  - エラー表現
    - 公開 API の tier1 独自エラー enum と HTTP ステータスの対応を
      固定テーブルとして定義する。
    - レスポンスボディは RFC 7807 problem+json に統一する
      （type / title / status / detail / instance に加え、
      tier1 エラーコードを拡張属性で含める）。

  - 認証・トレース伝播
    - Authorization: Bearer <OIDC トークン> を Keycloak で検証する。
    - W3C traceparent / tracestate を Envoy が gRPC metadata に
      詰め替え、tier1-otel が継続スパンを生成する。
    - テナント識別子はカスタムヘッダ（例：X-Tenant-Id）で運び、
      tier1-auth が認証主体と突き合わせる。

■ クライアント移行ストーリー
  - 現在 : .NET Framework は HTTP/1.1 + JSON 経路。
  - 中期 : .NET 8+ への移行時、同一 proto から Grpc.Net.Client へ
           切り替える。tier2 / tier3 の API 形状は不変。
  - 長期 : Envoy の transcoder filter は維持する。想定外のレガシー
           言語（Java 6 等）の連携が発生しても proto 共有のみで対応する。

■ バックエンド差し替えに対する API 安定性保証
  - 目的：infra 層の OSS（Kafka、Valkey、PostgreSQL、OpenBao 等）が
    ライセンス変更・廃止等で差し替えになった際、tier2 / tier3 の
    アプリケーションコードを無改修（再ビルドのみ）で追従可能に保つ。
    tier1 の存在意義の中核であるため、SDK の公開 API はこの要件を
    満たす抽象に対してのみ定義する。

  - 抽象化の境界（4 軸）
    1. メッセージ／ペイロードのエンベロープ
       - pubsub は CloudEvents 1.0 に準拠する。Kafka レコードヘッダ、
         RabbitMQ プロパティ等のバックエンド固有メタデータは
         tier1 が CloudEvents 属性へマッピングする。
       - tier2 / tier3 は CloudEvents 属性のみを参照する。
         バックエンド固有のヘッダ／プロパティは公開 API に出さない。
    2. 配信・整合性セマンティクス
       - 標準は at-least-once とする。tier1 SDK の API は配信保証を
         メソッド名・型で明示する（例：publish_at_least_once）。
       - 差し替え先のミドルウェアは「tier1 が宣言する保証を満たせる」
         ことを採用条件とする。満たせない場合は採用しない。
       - exactly-once 等の追加保証はオプトイン API として分離し、
         全バックエンドで提供する保証はしない。
    3. コンテキスト伝播
       - トレース（traceparent / tracestate）、認証主体、テナント識別子は
         CloudEvents 拡張属性および tier1-otel / tier1-auth が定める
         共通インターフェースで運ぶ。
       - バックエンド固有のヘッダ機構（Kafka headers、AMQP properties 等）
         には依存させない。
    4. エラー型
       - 公開 API のエラーは tier1 SDK 独自の enum で表現する。
       - rdkafka::error::KafkaError、redis::RedisError、sqlx::Error 等の
         バックエンド固有型は公開 API に露出させない（内部で
         tier1 エラー型へ変換する）。

  - 差し替え可能性の継続検証
    - tier1-pubsub / tier1-state / tier1-objstore など、抽象漏れが
      起きやすい crate には、Kafka / Valkey / Ceph 実装に加えて
      プロセス内モック実装（テスト専用）を必ず同梱する。
    - CI で「同一の公開 API に対して本実装とモックの双方が動作する」
      ことを継続検証する。複数バックエンド対応を提供する目的ではなく、
      抽象が漏れていないことを検出する手段として位置付ける。
    - モック実装で再現できない API は、バックエンド固有機能が公開 API
      に漏れている兆候とみなし、設計レビューで差し戻す。

  - 互換性ルール
    - 上記 4 軸を破る変更は tier1 SDK のメジャーバージョンアップとし、
      「最低 2 メジャーバージョン併存」ルールを適用する。
    - バックエンド差し替えに伴う実装変更でも、公開 API の破壊的変更を
      伴う場合は同ルールに従い、旧バージョンの crate を併存提供する。
    - 公開 API の破壊的変更は ADR（Architecture Decision Record）として
      Backstage 上に記録し、tier2 / tier3 への影響範囲と移行手順を
      添付する。

■ 自作によるリスクと緩和策
  リスク                          | 緩和策
  --------------------------------+--------------------------------------
  エッジケースのバグ              | 公式 Rust クライアント（rdkafka、
  （リバランス、再接続、          |  redis-rs、sqlx、tonic 等）の上に
   バックプレッシャー等）         |  薄く乗せ、自前実装範囲を最小化する
  --------------------------------+--------------------------------------
  メンテナンス工数                | tier1 にシニア級エンジニアを集約し
                                  | 専任 2 人体制を確保する
  --------------------------------+--------------------------------------
  採用候補者の学習コスト          | tier1 SDK のドキュメントを Backstage
                                  | 上で必須整備とする
  --------------------------------+--------------------------------------
  独自 SDK ゆえの社外知名度低下   | 標準 API（OpenTelemetry、OpenFeature、
                                  | CloudEvents、OIDC）への準拠で
                                  | 学習資産の流用性を担保する

■ 初期実装規模の見積もり
  - 初版（上記 10 crate）の実装：シニア 2 人 × 約 7〜8 か月。
    tier1-stream の追加と pre-signed URL 経路の整備により、
    当初見積もりから +1〜2 か月を見込む。
  - tier1 ゲートウェイ（tonic 直）+ Envoy transcoder / gRPC-Web /
    WebSocket upgrade 設定 + proto アノテーション規約整備：
    追加 1.5〜2 人月。
    （gRPC-JSON Transcoder / gRPC-Web filter / WebSocket upgrade は
     Envoy の既存機能を流用するため、独自実装は最小化される。）
