============================================================
tier2 の配布形態（Library と Service の両方）
============================================================

■ 方針
  - tier2 は機能カテゴリごとに Library 形態と Service 形態の
    両方を提供する。同一カテゴリを両形態で提供する場合、表面
    API はセマンティクス等価とし、tier3 が形態を選択しても
    業務コードの再設計を伴わないことを設計目標とする。
  - 両形態提供は tier1 の transport-neutral 哲学（「05_tier1/
    03_Server系」「05_tier1/05_提供機能カテゴリ」transport-
    neutral 節）の業務軸版と位置付ける。

■ 形態選定基準（カテゴリ単位の既定）
  - Library 寄り（カテゴリ既定が Library） :
      - tier3 プロセス内で完結し、外部状態共有が不要
      - 業務側 latency に敏感（ms オーダー）
      - 同一トランザクション境界に同居する必要がある
      - 例：ドメインモデル / バリデーション / 業務計算式 /
        軽量マスタ参照（読み取り中心）
  - Service 寄り（カテゴリ既定が Service） :
      - 複数 tier3 アプリケーションで状態 / 振る舞いを共有する
      - バックグラウンド処理（Workflow / Saga / バッチ等）を
        担う
      - 外部 IO の集約点として動く（通知配信 / 帳票生成 / 連携
        受発信）
      - 業界規制・コンプライアンスにより集中管理が必須
      - 例：承認 Workflow / 通知 / 監査集約 / マスタ管理 /
        業務ルール評価（決定表）
  - 両形態（カテゴリで Library / Service を併存提供） :
      - 上記境界が tenant / 業界で揺れるカテゴリ
      - tier3 の運用形態に応じて選択可能とする
      - 例：参照系の業務クエリ（Library で in-process /
        Service で集約 cache の二択）
  - 既定の選定は「10_提供機能カテゴリ」のカタログに記載する。

■ 同一機能を両形態で提供する場合の API 等価性
  - .proto を単一の真とし、Library 表面 API も Service 表面 API
    も同じ .proto から派生させる。Service 形態は tier1 の Envoy
    Gateway 経由で gRPC / HTTP+JSON / NDJSON を露出する
    （「05_tier1/03_Server系」Proto 二層化を参照）。
  - 等価性の機械的担保 :
      - Library 実装と Service 実装の双方に対し共通の
        conformance test suite を CI で実行する。両方 green を
        merge 条件とする。
      - 等価性が破れる API は両形態併存対象から外し、Library
        専用または Service 専用に明示分類する。
  - 形態切替時の業務コード影響 :
      - Library → Service / Service → Library の切替で、
        業務コードは無変更を目標とする（接続先 endpoint / DI
        構成の変更のみ）。
      - 切替時の latency 特性差は業務コードでなく非機能要件
        （SLO / リトライ設定等）の調整で吸収する。

■ Companion 経由クライアント（.NET Framework 等）への配慮
  - Library 直接組込が不可能な言語については、Service 形態を
    Gateway 経由で消費する。tier1 Companion（「05_tier1/04_
    Library」Companion 節）が transport / observability / 認証
    伝播を担う。
  - Library 専用に分類された機能（非同期 in-process API 等）
    は Companion 経由 tier3 から利用不可となるため、原則として
    Library 専用機能を恒常的に持たない方針とする（「02_位置
    づけ」表面 API 対称性節を参照）。

■ 配布物単位
  - Library :
      - Rust         : crate（複数 crate に分割、core /
                       frontend / backend の 3 段構成は tier1
                       と同枠）
      - C# (.NET 8+) : NuGet package
      - Go           : Go module
      - TypeScript   : npm package
  - Service :
      - 言語実装は Rust を主言語とする（tier1 Server系と同方
        針。詳細は「12_言語スタック」参照）
      - 配布形態は OCI image。tier1 のサプライチェーン
        （Harbor / Cosign / Trivy）に準拠する。
      - k8s への配置は「09_Service運用方針」を参照。

■ 配布物の供給経路
  - tier1 Library と同様、内部パッケージリポジトリを唯一の
    取得元に固定する（「05_tier1/04_Library」強制機構層 3 を
    参照）。tier2 配布物も同一の内部レジストリ経由で配布する。
  - 内部 OCI registry（Harbor）から tier2 Service image を配布
    する。

■ バージョニング
  - SemVer に従う。tier2 のバージョンは Library / Service を
    跨いで同一とする（同一機能の Library 版と Service 版が
    異なるバージョン番号を持たない）。
  - 互換性ポリシーは「13_互換性ポリシー」を参照。
