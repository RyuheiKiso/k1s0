============================================================
tier2 の業界拡張モデル
============================================================

■ 業界並立の前提
  - tier2 は単一業界専用の構造を取らない。業界 pack を並立
    させ、複数業界が同居しても tier2 構造が破綻しないことを
    設計の前提とする。
  - 1.0.0 出荷では製造業 pack のみを ship するが、本ファイルで
    定める業界拡張モデルは day-1 から有効とし、製造業 pack 自身
    も本モデルの規約に従って実装する。
  - 「業界 pack を 1 つしか持たないため業界横断層を曖昧にして
    おく」ことを許容しない。出荷物が 1 業界の時こそ、業界固有
    概念が業界横断層に漏れる圧力が最大であり、構造で塞ぐ必要
    が高い。

■ 業界 pack の定義
  - 業界 pack ：特定の業界（製造業 / サービス業 / 金融業 等）
    に特化した業務資産・業務語彙・ドメインモジュールの集合。
  - 業界 pack の単位 ：1 業界 = 1 pack を原則とする。業界内の
    ドメイン分割は pack 内で行う（製造業 pack の FA / 調達 /
    検査 等。詳細は「05_ドメイン分割方針」を参照）。
  - 業界 pack の境界 ：業界横断層に依存することは可、業界横断
    層への依存被参照は不可、別業界 pack への依存は不可。

■ 業界横断層と業界 pack の分離
  - 業界横断層 ：業界に依存しない業務語彙・業務資産（通知 /
    監査 / 承認 workflow / 帳票 / マスタ管理 等）。詳細は
    「04_抽象化レベル」「10_提供機能カテゴリ」を参照。
  - 業界 pack ：業界横断層を消費し、業界固有の業務資産を提供
    する。
  - 分離の方向は単方向（業界 pack → 業界横断層）に固定する。
    逆方向の依存（業界横断層 → 業界 pack）が発生したら、その
    時点で「業界横断層に業界固有概念が漏れている」とみなし、
    設計を見直す。

■ 業界中立性の機械的担保（3 種すべてを採用）
  - 業界並立を文書上の願望で終わらせないため、CI で以下 3 種の
    検査をすべて merge 条件とする。

  - (1) 命名禁則の機械検査
      - 業界横断層のシンボル名・ファイル名・モジュール名・
        Domain Event 名・テーブル名・proto message 名等に、
        業界固有語が出現したら CI fail とする。
      - 禁止語の例（製造業）：Manufacturing / Factory / Plant /
        Lot / Inspection / Equipment / 製造 / 工場 / ロット /
        検査 / 設備 / 調達 / 仕入先 等。
      - 禁止語リストは業界 pack ごとに YAML で宣言し、業界横断
        層の公開シンボル snapshot（「05_tier1/04_Library」強制
        機構と同枠：cargo public-api / PublicApiAnalyzers /
        api-extractor / go-apidiff）と CI で照合する。

  - (2) 依存方向の機械検査
      - 業界横断層 → 業界 pack の依存を機械的に禁止する。
          Rust         : cargo-deny の [bans] / workspace 構成
                         で業界横断 crate から業界 pack crate
                         を deny。
          C# (.NET 8+) : ProjectReference の方向検査と Roslyn
                         analyzer で業界横断 namespace から
                         業界 pack namespace への参照を fail。
          Go           : depguard で業界横断パッケージから業界
                         pack パッケージの import を deny。
          TypeScript   : eslint-plugin-boundaries で層境界を
                         宣言し逆方向参照を deny。
      - 業界 pack 間の相互依存も同様に禁止する。

  - (3) 第二業界 stub による抽象適格性証明
      - 1.0.0 では出荷業界が製造業のみのため、「2 業界
        conformance」は成立しない。これを補うため、サービス業
        を想定した最小 stub pack（仮称：service_industry_stub）
        を CI 専用で保持し、業界横断層の API が stub からも
        素直に消費できることを merge 条件とする。
      - stub は出荷物に含めない。Testcontainers / 単体テストで
        業界横断層 API を呼び出し、製造業 pack と同型のシナリオ
        が green になることを要求する。
      - stub で通らない業界横断 API が発生した時点で、その API
        は「業界横断層に適格でない」とみなし、業界横断層から
        業界 pack（製造業）に降格させる、または API を業界中立
        な形に縮める。
      - tier1 の L2* 「二バックエンド conformance」の業界軸版
        と位置付ける（詳細は「05_tier1/04_Library」を参照）。

■ 新業界 pack の追加手順
  - (1) 業界 pack の bounded context を「05_ドメイン分割方針」
        に従って設計し、業界横断層への依存のみで構成可能か
        検証する。
  - (2) 業界横断層に追加が必要な API があれば、業界中立な形で
        業界横断層に追加する（命名禁則・依存方向・stub 検査を
        満たす）。
  - (3) 業界 pack を独立 module として実装し、他業界 pack への
        依存がないことを CI で検査する。
  - (4) tier3 への提供形態（Library / Service）を「08_配布形態」
        に従って決定する。
  - (5) tier3 移行支援（既存 tier3 から新業界 pack への移行が
        発生する場合）を「13_互換性ポリシー」に従って整備する。

■ 第二業界 stub の維持
  - stub は CI 専用の生きた成果物として、業界横断層と同じリポ
    ジトリで継続的に維持する。業界横断層のバージョンアップ時に
    stub も同時に更新する。
  - 製造業 pack 以外の業界 pack が出荷された時点で、stub は
    当該業界 pack のテストハーネスへ移行統合する（出荷業界が
    複数になれば、本来の「2 業界 conformance」が成立する）。
