■ Lv 割付の根拠
  - 業界横断 Lv に置くカテゴリは、第二業界 stub（「03_業界拡張
    モデル」業界中立性の機械的担保 (3) 参照）でも素直に消費
    可能なものに限定する。stub で API が破綻するカテゴリは
    業界共通 Lv 以下に降格させる。
  - 業界共通 Lv は製造業 pack 内の複数ドメインから参照される
    語彙のみ。単一ドメインからしか参照されないものは業界固有
    Lv に置く。

■ 既定形態の根拠
  - Library+Svc（両形態）：tier3 が in-process で完結したい
    ケースと、複数 tier3 / Companion 経由 tier3 から共有したい
    ケースの両方が存在するカテゴリ。
  - Service のみ：tier1 Workflow / Messaging を内部で長時間
    保持するもの、または規制 / 監査で集中管理が必須のもの。
  - Library のみ（tier3-facing 公開 API として）：1.0.0 出荷時
    は採用せず（「02_位置づけ」表面 API 対称性節 / 「08_配布
    形態」Companion 配慮節と整合）。
  - 例外（Library*）: Domain Event Hub は Outbox + Kafka
    publisher が in-process トランザクション境界を必要とする
    ため Library 形態のみで提供する。ただしこれは tier2 実装
    内部から呼ばれるインフラであり、tier3 へは「業務 API で
    発行 → Hub が内部的に publish」「業務 API で subscribe
    登録 → tier2 内 subscriber が Hub から購読 → tier3 拡張点
    呼び出し」という間接利用となる（「24_読み取りモデル方針」
    Read model 更新の責務節 / 「07_業務資産所有権」「16_強制
    機構」参照）。Hub を tier3 から直接利用させる経路は
    提供しない。

■ 露出される tier1 概念（業務側に染み出す部分）
  - tier1 L1+ カテゴリの露出概念（「05_tier1/05_提供機能カテ
    ゴリ」L1+ 露出概念一覧）は tier2 の API 表面で業務語彙に
    翻訳する。翻訳できないものは業務語彙ではなく tier1 概念の
    まま露出する（無理な翻訳は業務不変条件の腐敗を招く）。
      - Workflow / Activity 境界、WorkflowID 体系
      - Outbox 連携、Domain Event の順序保証
      - トランザクション分離レベル（Repeatable Read 既定）
      - 決定表 DSL のセマンティクス
  - 翻訳の正解は「07_業務資産所有権」拡張点 / 不変条件 YAML
    宣言と同期させる（「16_強制機構」参照）。
