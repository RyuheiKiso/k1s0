============================================================
tier2 のセキュリティアーキテクチャ
============================================================

■ 方針
  - 個別文書（06 / 14 / 22 / 25）に散在するセキュリティ要素
    を本ファイルで全体像として束ねる。脅威モデル / attack
    surface / 防御層 / 運用面の責務を一つの参照点に集約する。
  - tier1 のセキュリティ機構（OIDC / mTLS / Secret 管理 /
    サプライチェーン）の上に tier2 固有の attack surface への
    対策を追加する。

■ 脅威モデル（Threat Model）の対象
  - tier2 固有の attack surface :
      (1) 業務 API（tier3 / Companion 経由 tier3 から呼ばれる）
      (2) 業務管理 API（業務管理者から呼ばれる、「23_管理境界」
          参照）
      (3) override 拡張点（tier3 が実装を差し込む、「07_業務
          資産所有権」参照）
      (4) 外部システム outbound（partner endpoint、「25_外部
          システム統合」参照）
      (5) Domain Event Hub（tier2 内部基盤、「10_提供機能
          カテゴリ」「24_読み取りモデル方針」参照）
      (6) 添付ファイル / 帳票生成（「31_業務添付帳票資産」
          参照）
  - 各 surface に対し、STRIDE 分類で脅威を列挙し、緩和策と
    残留リスクを明文化する。脅威モデル文書は tier2 リポジトリ
    で版管理する。

■ 主要脅威と緩和策
  - 越境テナントアクセス（Information Disclosure / Tampering）:
      - リポジトリ抽象による tenant_id 強制注入（「06_マルチ
        テナント方針」「16_強制機構」層 5 参照）
      - 公開 API での tenant_id 受付禁止 + CI 検査
      - 統合テストでの越境試行検証（「15_テスト方針」拡張）
  - override の悪用（Elevation of Privilege / Tampering）:
      - 拡張点 contract test で振る舞いを検査（「07_業務資産
        所有権」「15_テスト方針」）
      - 不変条件 / 認可 bypass / 監査 emit 抑制を override
        禁止範囲として明示
      - reflection 経由 private アクセスを言語別の analyzer
        で検出
  - 業務管理 API の不正利用（Elevation of Privilege）:
      - 別系統 role（tenant_admin / master.admin、「22_権限
        モデル」）必須
      - 全操作の詳細監査
      - emergency_override の time-bound + 事後レビュー
  - 外部システム outbound への成りすまし（Spoofing）:
      - HMAC 署名 / mTLS / OAuth 2.0 partner 認証
      - 認証情報の tier1 Secret 経由参照（直接埋込禁止、
        「25_外部システム統合」参照）
  - 添付ファイル経由の攻撃（malware upload / XSS）:
      - 受入時のウイルススキャン
      - Content-Type / マジックナンバー検証
      - ダウンロード時の安全な Content-Disposition
      - PDF 帳票生成時の template injection 検査（「31_業務
        添付帳票資産」参照）
  - サプライチェーン攻撃 :
      - Harbor / Cosign / Trivy / SBOM の tier1 整合
        （「16_強制機構」サプライチェーン節）
      - 内部レジストリ唯一化（「16_強制機構」層 6）
      - SBOM の継続検査と CVE 対応（後述）

■ 脆弱性管理
  - SBOM :
      - tier2 配布物（Library / Service image）すべてに SBOM
        を同梱（CycloneDX 形式）。
      - SBOM は OCI image / package metadata に attest する
        （Cosign で署名）。
  - CVE 対応 SLA :
      - Critical : 24 時間以内に評価開始、48 時間以内に修正
        deploy または mitigation。
      - High : 7 日以内に修正 deploy。
      - Medium : 30 日以内に修正 deploy。
      - Low : 次回計画 release で修正。
  - 継続検査 :
      - 内部レジストリの全 image / package を Trivy で日次
        スキャン。
      - 新規 CVE の自動検出 → アラート → ticket 起票
        （「27_信頼性運用準備」アラート方針と整合）。
  - 依存 OSS のライフサイクル監視 :
      - tier1 で監視している OSS 群と整合。tier2 が直接依存
        する OSS（言語ランタイム / 標準ライブラリ / ビルド
        ツール）は tier2 リポジトリで個別監視。

■ Secret rotation
  - tier2 が消費する Secret（DB credential、partner 認証情報、
    署名鍵、暗号鍵）の rotation cadence :
      - DB credential : 90 日
      - partner OAuth client secret / API Key : 180 日
        （partner 合意 / 契約に応じて短縮可）
      - partner mTLS 証明書 : 1 年（partner 標準）
      - HMAC 署名鍵 : 90 日（rolling、複数鍵を一定期間並走）
      - PGP 鍵（payload 暗号化用）: 1 年
  - 無停止切替 :
      - tier1 External Secrets Operator + OpenBao の機構
        （「05_tier1/05_提供機能カテゴリ」Secret Management）
        を活用。
      - tier2 は rotation 通知を subscribe し、無停止で新旧
        secret を並走させる（HMAC は鍵 ID 付きで複数鍵検証、
        partner OAuth は token 再取得）。
  - rotation 失敗時の取り扱い :
      - 失敗は page アラート（「27_信頼性運用準備」）。
      - 失効した secret での認証は fail-fast。
      - 失効猶予期間の延長は emergency_override 必須
        （「22_権限モデル」「23_管理境界」）。

■ 暗号アジリティ（Cryptographic Agility）
  - 利用アルゴリズムの定期見直し（年次）:
      - 署名 : HMAC-SHA256（既定）/ RSA-SHA256 / ECDSA-P256
      - 輸送暗号 : TLS 1.2 以上（partner 要求次第で TLS 1.3）
      - payload 暗号 : AES-256-GCM / ChaCha20-Poly1305
      - 鍵交換 : ECDHE / X25519
  - 危殆化（broken）時の移行 :
      - tier2 が「暗号スイート移行」runbook を保持。
      - 新スイートでの並走 → 旧スイート受付停止 → 旧スイート
        サポート終了 の段階を時限的に進める（major version
        up 相当の影響、「13_互換性ポリシー」整合）。
  - PQC（post-quantum cryptography）:
      - 1.0.0 出荷時点で PQC は導入しないが、移行可能性を
        本節で明記し、tier1 の TLS スタック更新に追従できる
        構造を維持する。

■ ペネトレーションテスト
  - 第三者監査 : 年 1 回、業界横断 / 業界 pack の主要 attack
    surface を対象。結果は tier2 のセキュリティロードマップに
    反映。
  - 内部 red team 演習 : 半期 1 回、tier2 開発チーム外のセキ
    ュリティ担当が実施。
  - bug bounty 等の外部報告窓口 : 1.0.0 出荷後の運用課題と
    して別途定義。

■ サポート用アクセス
  - サポートエンジニアがテナントデータをデバッグするための
    経路 :
      - 専用 role : support_engineer（プラットフォーム運営者
        の一形態）
      - 起動条件 : テナント側の明示的同意（チケット起票 +
        承認） + 期間限定（既定 4 時間、最大 24 時間）
      - 自動失効 : 期間到達 / テナント取消 / インシデント
        clear で失効
      - PII 露出 : 既定では PII を redact 表示（伏字 /
        ハッシュ）。PII 平文アクセスは追加承認 + emergency_
        override 相当の詳細監査（「22_権限モデル」緊急時の
        override と同枠）
      - 全アクセスは詳細監査エントリ emit、事後レビュー必須
        （「14_業務エラー監査コンプライアンス」「23_管理境界」
        と整合）
  - サポート用 UI :
      - 業務管理 UI（Backstage プラグイン、「23_管理境界」）
        とは別系統で提供。サポート専用ビューで PII redact 等
        を強制。

■ tier3 / テナントの拡張点
  - threat model に対するテナント固有の追加緩和策の宣言。
  - 追加 audit / 追加 alerting の hook。
  - サポートアクセス時の追加承認要件（テナント独自の承認
    workflow を override 拡張点で挿入）。
  - 不変条件（override 不可）:
      - SBOM / 継続検査 / CVE SLA を緩めない
      - サポートアクセスの監査要件を緩めない
      - emergency_override の time-bound 制約を緩めない

■ 1.0.0 出荷時の対応範囲
  - 脅威モデル文書を業界横断 + 製造業 pack に対し作成。
  - SBOM / CVE SLA / Secret rotation / 暗号アジリティの機構
    を 1.0.0 で実装。
  - ペネトレーションテストは 1.0.0 リリース前の最終確認と
    して実施。
