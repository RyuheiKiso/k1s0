============================================================
tier2 の開発者体験（DX / ローカル開発 / オンボーディング）
============================================================

■ 方針
  - tier2 が tier3 開発者（ジュニア級が中心、「04_推奨の開発
    体制」参照）から実際に使われるためには、ドキュメントの
    充実だけでは足りない。ローカル開発 / オンボーディング /
    starter / デバッグツールを 1.0.0 出荷時に揃える。
  - tier1 が「Backstage / Testcontainers / Tilt」をプラット
    フォーム標準として運用する（「05_tier1/06_非提供スコープ」
    開発体験 / 運用ツール 節）方針に乗る。tier2 はこれらに
    対応する tier2 / tier3 開発資産を提供する。

■ ローカル開発環境
  - 起動構成 :
      - tier1 backend（PostgreSQL / Kafka / Temporal /
        Keycloak / Valkey 等）を Testcontainers で起動。
      - tier2 Service を tier3 開発者の手元（または Tilt 経由
        で k8s ローカル）で起動。
      - tier3 アプリ自体は tier3 開発者の手元で起動。
  - 設定 :
      - tier3 リポジトリ生成時（Backstage Software Template）
        に Testcontainers + tier2 起動の docker-compose 同梱。
      - 必要な環境変数 / Secret は開発用ダミー値で初期化。
        本番 Secret 経路（OpenBao）は使わない。
  - 起動時間 :
      - tier1 backend 一式 + tier2 Service の起動を 5 分以内
        を目標とする。
      - 起動が遅い backend（Temporal 等）は profile 化して
        必要な機能だけ起動する選択肢を提供。

■ サンプルデータ
  - 業界横断サンプル :
      - 既定テナント / 既定ユーザー / 既定組織 / 既定マスタ
        の seed データを Backstage Software Template に同梱。
      - 監査ログ / 通知履歴の動作確認用サンプル。
  - 製造業 pack サンプル :
      - 品目 / 拠点 / BOM の代表例
      - 発注 → 検収の業務シナリオ（実行可能）
      - 検査計画 → 実施 → 不良 のフロー
  - サンプルデータ初期化 : ローカル起動時に自動投入する
    option を提供。

■ tier3 onboarding playbook
  - 初日 :
      - Backstage で新規 tier3 リポジトリ生成。Software
        Template が CI / 強制機構（「16_強制機構」）/ サン
        プル / docs を自動同梱。
      - ローカル環境起動。サンプルデータでの hello-world
        動作確認。
  - 1 週目 :
      - tier2 業務 API の利用方法学習（API ドキュメント /
        サンプルコード経由）。
      - 1 つの業務シナリオ（発注作成 → 承認 → 確定）を tier3
        で実装。
      - tier2 拡張点（「07_業務資産所有権」）の 1 つを override
        実装。
  - 2 週目 :
      - 認証 / 認可 / マルチテナント識別子伝播の理解と動作
        確認。
      - 拡張点 contract test / 業界中立性検査の CI 通過確認。
      - 統合テスト（Testcontainers 経由）の作成。
  - 1 ヶ月目 :
      - ステージング環境での動作確認、初回 deploy。
      - 業務管理 API の利用（マスタ編集等）を理解。
  - playbook は Backstage TechDocs で公開。各ステップに対応
    するサンプル PR / サンプルテストへのリンクを含む。

■ Starter template / hello-world
  - tier3 hello-world :
      - tier2 の通知 API を 1 回呼ぶだけのアプリ。
      - 認証 → 業務 API 呼出 → レスポンス受領 までのフルパス
        を最小コードで体験できる。
  - tier3 業界 pack starter :
      - 製造業 pack の代表シナリオ（発注 1 件 / 検査 1 件）を
        tier3 アプリとして実装した starter。
      - tier3 開発者がこれを fork して新規業務を作る出発点
        とする。
  - starter は tier2 と同じリポジトリ構造で配布し、tier2 の
    バージョンアップに合わせて更新する。

■ デバッグツール
  - 業務 API の呼出 :
      - curl / grpcurl 用のサンプル（認証 token 取得込み）を
        各 API ドキュメントに同梱。
      - Postman / Insomnia の collection を Backstage
        TechDocs からダウンロード可能。
  - Domain Event の inspect :
      - tier2 が Domain Event 履歴の検索 API を業務管理 API
        として提供（「23_管理境界」参照）。
      - 開発時はサンプル subscriber を tier3 starter に同梱
        して subscribe ログを確認可能とする。
  - Workflow の inspect :
      - tier1 Temporal Web UI で進行中 Workflow を確認できる
        （「27_信頼性運用準備」Workflow 可視化 と整合）。
      - 開発環境では Web UI を制限なく公開。
  - 認可結果の inspect :
      - tier2 が「この呼出はなぜ拒否されたか」を返す debug
        endpoint を提供（開発環境のみ有効）。
      - ABAC 判定式の評価結果 / 適用 role を返す。

■ Cross-tier trace correlation
  - tier3 → tier2 → tier1 を貫く trace を tier1 OpenTelemetry
    の標準で接続する（「05_tier1/04_Library」横断的共通要素
    / 「09_Service運用方針」観測可能性節と整合）。
  - 開発時のデバッグ手順 :
      - tier3 の特定リクエストで発火した trace ID を取得。
      - Jaeger v2 UI（tier1 のプラットフォーム標準 UI、「05_
        tier1/06_非提供スコープ」可視化 UI 節）で全 span を
        確認。
      - tier2 業務処理 / Domain Event 発行 / Workflow 起動 /
        tier1 backend 呼出 までを 1 trace で追える。
  - 業務 metric / 監査エントリへの紐付けは trace ID をキーに
    Apache Superset（tier1 標準 BI）で串刺し検索する。

■ ドキュメント生成 / 公開
  - tier2 が公開する全 API / Domain Event / マスタ schema /
    決定表のドキュメントを Backstage TechDocs で公開（「11_
    表現手段」ドキュメント生成節と整合）。
  - 各ページに :
      - 業務語彙の説明（「何を意味するか」「いつ使うか」）
      - 利用例コード（4 言語：Rust / C# / Go / TS）
      - 試行用 curl / grpcurl サンプル
      - 関連する拡張点 / contract test
      - 関連する SLO / quota 情報
  - ドキュメントの版管理 : tier2 のバージョンと同期。古い
    バージョンも参照可能。

■ tier2 開発者の体験（dogfooding）
  - tier2 自身を開発する tier1 担当 / tier2 担当も同じ
    Backstage Software Template の派生で開発する。第二業界
    stub（「03_業界拡張モデル」「15_テスト方針」）を tier2
    開発者が日常的に動かすことで、業界中立性が空文化しない
    ことを保つ。

■ 1.0.0 出荷時の対応範囲
  - ローカル開発環境 / サンプル / starter / playbook /
    デバッグツール / cross-tier trace 連携 / ドキュメント生成
    を 1.0.0 で揃える。
  - 開発体験の継続改善は出荷後の DX チーム責務（tier1 と協働）。
