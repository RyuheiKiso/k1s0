============================================================
tier2 の業務エラー / 監査 / コンプライアンス
============================================================

■ 方針
  - tier1 が提供する共通エラー型 / 監査基盤 / Secret 管理の上
    で、tier2 は業務観点のエラー taxonomy / 監査エントリ /
    PII 取り扱いを規定する。
  - tier1 のシステム観点と tier2 の業務観点を二重に持たない。
    tier1 の機構を業務語彙でラップして提供する。

■ 業務例外 taxonomy
  - 大分類（4 種）:
      - DomainError              : 業務不変条件の違反。例：
                                   「在庫数がマイナスになる発注」
                                   「確定済み検査結果の改変」。
      - ValidationError          : 入力値の業務妥当性違反。例：
                                   品番フォーマット違反、金額の
                                   桁超過。
      - BusinessConflict         : 並行操作 / 別 actor の操作と
                                   の業務上の不整合。例：「他者
                                   が先に承認した発注の再承認」。
                                   subtype フィールドを必須とし、
                                   stale_write / lost_update /
                                   supersede / concurrent_edit の
                                   4 値で UI 分岐を 1:1 固定する
                                   （詳細は「07_tier3/39_クライ
                                    アント状態適合仕様」BusinessConflict
                                    subtype 節 / Repository
                                    abstraction での判定ロジック
                                    は「32_テナント分離適合仕様」
                                    との整合）。
      - AuthorizationDenied      : 認可拒否（tier1 認可結果を
                                   業務語彙で表現）。例：「他
                                   テナント resource への参照」。
  - 各エラーは tier1 の共通エラー型を実装し、業務語彙のフィー
    ルド（aggregate ID / 業務的な原因コード / 推奨対応）を持つ。
  - エラーコードは tier2 が一元管理する enum / 定数として提供
    し、Schema 駆動（「11_表現手段」参照）で多言語生成する。
    tier3 が独自にエラーコードを付与することは禁止する。

■ ドメインエラーと validation エラーの境界
  - ValidationError : 業務的な「入力受付」段階で検出可能なもの。
    aggregate に到達する前に reject される。
  - DomainError : aggregate 内部で業務不変条件を評価して検出
    されるもの。aggregate の状態に依存する判定（在庫 / 進捗 /
    承認段数 等）はここに分類する。
  - tier2 は両者を区別して emit する。tier3 は UI 側で異なる
    presentation（form 検証 / モーダルでの業務エラー表示）を
    取れるようにする。

■ 監査ログ（業務観点）
  - tier1 Logging（OpenTelemetry → ClickHouse）の上で、tier2
    が業務観点の監査エントリ schema を定義する。
  - 監査エントリの必須属性 :
      - tenant_id（テナント識別子）
      - actor (誰が)
      - business_event (何をした：業務語彙で命名)
      - target (どの aggregate に対して)
      - business_outcome (成功 / 業務的失敗 / システム失敗)
      - timestamp
  - 監査専用 sink :
      - 通常の構造化ログとは別の専用 ClickHouse テーブルに蓄積
        する。保持期間は規制要件で定める。
      - 監査エントリは改竄検知（hash chain / 外部公証）をオプ
        ションで提供する（規制要件次第）。
  - 監査ログに含めない情報 :
      - PII（後述）
      - 機密業務データの本体（識別子と業務イベント名のみ残す）

■ PII の取り扱い
  - 識別子最小化 :
      - 監査ログ / 構造化ログ / span attribute に PII（氏名 /
        メールアドレス / 電話番号 / 住所 等）を含めない。
      - actor 表現には Keycloak の subject（不可逆 ID）を使用
        し、氏名等は監査ログに残さない。
      - PII を扱う必要のある業務処理は、PII を tier1 Secret
        管理の延長線上に置き、参照時の監査を残す。
  - PII の保管 :
      - PII を含むテーブルは専用 schema に分離し、アクセスログ
        を DB レベルで取得する（tier1 PostgreSQL の audit 拡張
        等）。
      - PII への変更（更新 / 削除）は監査エントリに業務イベン
        トとして残す。変更内容そのものは残さない（差分は規制
        要件次第）。
  - 削除（GDPR 等）:
      - テナント / ユーザー削除時には PII の物理削除を行う
        （「06_マルチテナント方針」テナントライフサイクル節と
        整合）。
      - 削除完了の証跡を監査エントリとして残す。

■ コンプライアンス境界
  - 業界規制 :
      - 製造業の業界規制（例：医療機器・自動車・食品の品質管理
        規制）への対応は、業界 pack 内のドメイン（特に検査ドメ
        イン）が責任を持つ。
      - 規制対応の業務不変条件（「確定済み検査結果は変更不可」
        等）は tier2 が override 不可の不変条件として保持する
        （「07_業務資産所有権」参照）。
  - 地理的データ局所性 :
      - データ局所性が必要な場合、専用 Service / 専用 DB に昇格
        する（「06_マルチテナント方針」「09_Service運用方針」
        参照）。
      - tier2 はテナント識別子に紐付くデータ配置情報を持ち、
        データ書込時に配置先を選択する責務を持つ。
  - 規制対応のバージョニング :
      - 規制要件の変更に伴う業務不変条件の更新は、major version
        up として扱う（「13_互換性ポリシー」参照）。

■ 業務イベント emit の必須化
  - 業務的に意味のある操作（aggregate 状態変更）には必ず Domain
    Event を emit する。emit を抑制する経路を作ることは禁止
    （「07_業務資産所有権」override 禁止範囲節と整合）。
  - 監査エントリと Domain Event は別物として扱う :
      - Domain Event : 業務通信のための一次手段（subscribe 側
        が後続処理を実行）。
      - 監査エントリ : 「誰が何をした」の事後追跡のための痕跡。
        後続処理を駆動しない。
  - 両者を物理的に分離して管理する（混在させると、subscribe
    失敗時に監査も欠落する事故が起きる）。
  - 物理分離の懸念（subscribe 失敗時の監査欠落）は、State change /
    Outbox / Audit を同一 DB トランザクションで書く atomic 三表
    書込により構造的に解消する。具体機構と integrity property
    (P1)〜(P4) の CI 検証は「32_テナント分離適合仕様」atomic 三表
    書込節を参照。
