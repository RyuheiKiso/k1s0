============================================================
tier2 の外部システム統合（outbound）
============================================================

■ 方針
  - tier1 Companion は inbound（外部から本プラットフォームへ
    の流入）を主に扱う（「05_tier1/04_Library」Companion 役割
    A / B 参照）。outbound（本プラットフォームから外部システム
    への流出）は tier2 が業務語彙でラップして提供する。
  - 外部システム例 : 取引先 EDI、顧客 ERP、公的機関への報告、
    BI / DWH 連携、SaaS 通知（Slack / Teams 等）。

■ outbound の形態
  - HTTP webhook : 外部システムへの POST。POST body は .proto
    から派生する JSON が既定。署名は HMAC-SHA256 を既定。
  - EDI : X12 / EDIFACT 等の業界標準フォーマット。tier2 が
    業務語彙 → EDI message への変換を担う。配送は SFTP / VAN
    / AS2 等の partner-specific チャネル。
  - ファイル転送 : SFTP / S3 互換 storage 経由。tier1 Object
    Storage（S3 API 族）を使用（「05_tier1/05_提供機能カテゴ
    リ」参照）。
  - メッセージング bridge : 外部 Kafka / AMQP への bridge。
    tier1 Companion 役割 B の messaging_bridge と対称
    （「05_tier1/04_Library」Companion 参照）。

■ subscription model
  - 外部宛て配信は subscription として tier2 に登録する :
      - subscription 単位 : (tenant_id, partner_id, event_
        type, delivery_form, endpoint, credential_ref,
        retry_policy)
      - event_type : Domain Event 名 または 業務 API のレスポ
        ンス。
      - delivery_form : webhook / edi / sftp / messaging_
        bridge
      - endpoint : URL / SFTP path / Kafka topic 等
      - credential_ref : tier1 Secret Management（OpenBao）
        への参照
  - subscription 管理 API は業務管理 API surface（「23_管理
    境界」参照）として提供。

■ 信頼性 / 配送保証
  - at-least-once 配送を既定とする。受信側で冪等性を担保する
    必要があることを契約として明示する :
      - HTTP webhook : Idempotency-Key を tier2 が発行
        （「18_API設計規約」冪等性節と同枠）。
      - EDI / ファイル : 業務固有のメッセージ識別子（EDI の
        Interchange Control Number 等）で重複検出。
  - リトライ : 失敗時は exponential backoff で最大 24 時間
    リトライ。最終失敗は DLQ 相当の outbound_failed テーブル
    に記録し、業務管理者向けに再送 API を提供（「23_管理境界」
    緊急対応経路と整合）。

■ 認証 / 暗号化 / 署名
  - 認証 : partner ごとに認証情報を tier1 Secret Management
    に保管。HTTP webhook は OAuth 2.0 / API Key / mTLS から
    選択。EDI / SFTP は SSH 鍵 / クライアント証明書。
  - 輸送暗号化 : TLS 1.2 以上を必須。partner が要求する場合
    TLS 1.3。
  - payload 署名 : HTTP webhook は HMAC-SHA256 署名を既定。
    EDI は X12/EDIFACT の標準制御セグメントに従う。
  - payload 暗号化 : partner 契約で要求された場合のみ。tier2
    が PGP / partner 公開鍵での暗号化を提供する hook を持つ。

■ 業務語彙との対応
  - tier2 が出力する outbound payload は、内部 Domain Event /
    業務 entity から partner-specific 形式へのマッピングで
    構成する。
  - マッピング定義 :
      - 業界横断 mapping（共通 webhook payload 等）は tier2
        が提供。
      - partner-specific mapping（特定取引先 EDI 仕様）は
        tenant 運用責任とし、tier2 は mapping DSL（「11_表現
        手段」DSL 節と同枠）と registration API を提供する。
  - mapping は override 拡張点として tier3 が拡張可能（「07_
    業務資産所有権」参照）。

■ inbound との対称性
  - tier1 Companion 役割 B（inbound transport）と tier2
    outbound は対称概念であり、protocol / transport の選択
    ロジックを共有する。両者の adapter 実装は機械的に等価性
    検査する（tier1 の transport-neutral conformance proof と
    整合）。

■ 監査 / observability
  - 全 outbound 試行は監査エントリとして記録（送信先 / 内容
    ハッシュ / 結果。「14_業務エラー監査コンプライアンス」
    参照）。PII を含む payload の場合は内容ハッシュのみ記録、
    内容自体は記録しない。
  - metric : per-partner 配送成功率 / リトライ回数 / 配送遅延
    （「09_Service運用方針」観測可能性節と整合）。

■ tier3 の拡張点
  - mapping DSL の override（partner 固有のフォーマット拡張）。
  - subscription 追加（tier3 主導の業務連携）。
  - 配送前 hook（追加バリデーション / 業務的承認等）。
  - 不変条件（override 不可）:
      - 監査エントリ emit
      - retry 上限 / DLQ 記録
      - 認証情報の Secret 経由参照（直接埋込禁止）

■ 1.0.0 出荷時の対応範囲
  - HTTP webhook（HMAC 署名 / OAuth 2.0 / API Key）と
    SFTP ファイル転送を 1.0.0 で提供。
  - EDI（X12 / EDIFACT）/ messaging bridge は 1.0.0 では
    proto / mapping DSL の枠組みを定義し、partner adapter は
    需要発生時に追加する形とする。
