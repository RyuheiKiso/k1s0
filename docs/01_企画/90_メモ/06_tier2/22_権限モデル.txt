============================================================
tier2 の権限モデル（RBAC + ABAC）
============================================================

■ 方針
  - tier2 は ABAC（Attribute-Based Access Control）を採用
    する。判定属性 : tenant_id、user_id、role 集合、resource_
    type、resource_id、action、業務的属性（aggregate の状態
    / 担当組織 等）。
  - 単純な RBAC（role による許可）は ABAC のサブセットとして
    成立する。tier2 は両者を統一して扱う。
  - 判定機構は tier1 Authentication / Authorization（Keycloak
    認可ポリシー）を使用する（「05_tier1/05_提供機能カテゴリ」
    参照）。tier2 は判定属性の供給と業務語彙の role / scope
    を定義する責務を持つ。

■ ロール命名規約
  - 形式 : <pack>.<domain>.<resource>.<action>
      pack     : cross_industry / manufacturing 等
      domain   : 業界横断は省略可、業界 pack は fa /
                 procurement / inspection / common 等
      resource : 業務 entity 名（purchase_order /
                 inspection_result / equipment 等）
      action   : read / write / approve / cancel / admin
  - 例 :
      - cross_industry.notification.read
      - cross_industry.audit.read
      - manufacturing.procurement.purchase_order.approve
      - manufacturing.inspection.inspection_result.cancel
      - manufacturing.fa.equipment.admin
  - tier2 が組み込みロールを定義し、tier3 / テナントが組合せ
    て role に bind する。

■ 標準 action（scope）
  - read     : 取得 / 検索 / 一覧
  - write    : 作成 / 更新（Draft 状態への変更）
  - confirm  : Draft → Confirmed への遷移（「19_状態遷移
              パターン」参照）
  - approve  : 多段承認 workflow での承認
  - cancel   : Confirmed → Cancelled への遷移
  - admin    : マスタ / 設定の管理操作（全権限）
  - 業務 entity / API カテゴリごとに、サポートする action
    集合を YAML 宣言する。CI で実装と照合（「16_強制機構」
    参照）。

■ 業務的属性による判定（ABAC 部分）
  - role による判定だけでは不足する場合（例：「自分が起票
    した発注のみ取消可能」「自工場の検査結果のみ参照可能」）
    に属性ベース判定を行う。
  - 判定属性の供給 :
      - tier2 が aggregate からの属性抽出を Authorization
        context に同梱する hook を提供。
      - 例 : aggregate の created_by、tenant_org_id（所属
        組織）、equipment_location（拠点） 等。
  - 判定式は Keycloak 認可ポリシー（JS / Rego 等）で記述
    する。式の所有権は tier2（業界横断 / 業界 pack それぞれ
    が既定式を提供）、tier3 が override 拡張点で差し替え可能。

■ 権限委譲（Delegation）
  - 製造業の業務（承認 workflow / シフト交代 等）では「上司
    の代理で承認」「シフト交代時の権限引き継ぎ」が頻発する。
  - tier2 は明示的な Delegation API を提供する :
      - 委譲元 user / 委譲先 user / 対象権限（role 集合または
        scope 集合）/ 期間 / 委譲理由 を必須項目とする。
      - 委譲は監査エントリを emit（「14_業務エラー監査コンプ
        ライアンス」参照）。
      - 期間終了で自動失効。
  - 委譲された権限を行使した操作も別の監査エントリで記録
    （行為者 + 委譲元 user の両方を記録）。

■ 緊急時の override（Emergency Override）
  - 業務的な緊急対応（規制対応 / インシデント対応）で一時的
    に通常権限ルールを bypass する経路を提供する :
      - 専用 role : emergency_override（テナント管理者のみが
        付与可能）
      - 起動条件 : 明示的な「emergency mode」宣言 + 理由 +
        最大 1 時間の time-bound
      - 自動失効 : 期間到達 / 明示的な解除 / インシデント
        clear で失効
      - 監査 : emergency mode 宣言 / 期間中の全操作 / 解除を
        詳細に監査エントリ emit。事後レビュー必須。
  - 詳細は「23_管理境界」緊急対応経路節を参照。

■ tier2 が提供する組み込みロール
  - 業界横断 :
      - cross_industry.tenant_admin     : テナント管理者
      - cross_industry.audit.read       : 監査閲覧者
      - cross_industry.master.admin     : マスタ管理者
      - cross_industry.notification.send: 通知発信者
  - 製造業 :
      - manufacturing.fa.operator       : FA 現場担当
      - manufacturing.fa.supervisor     : FA 班長
      - manufacturing.procurement.buyer : 調達担当
      - manufacturing.procurement.approver : 調達承認者
      - manufacturing.inspection.inspector : 検査員
      - manufacturing.inspection.qa_manager : 品質管理者
  - 上記は出発点。テナントは Keycloak で組合せロール / カス
    タムロールを作成可能。

■ tier3 / テナントの拡張点
  - 既定 role の集合に追加（テナント固有の役職に対応）。
  - ABAC の判定式に追加条件を override 拡張点経由で挿入。
  - Delegation の追加要件（追加承認等）を hook で挿入。
  - 上記すべて「07_業務資産所有権」override 契約に準拠。
  - 不変条件（override 不可）:
      - 監査エントリ emit
      - emergency_override の time-bound 制約
      - tenant_id 越境の禁止（別テナント resource アクセス
        禁止）

■ 機械的担保
  - role 命名規約違反を CI で fail（「16_強制機構」と同枠）。
  - tier2 公開 API の各 endpoint に必要な action / role 集合
    を .proto annotation または YAML で宣言。実装での認可
    呼び出しと CI 照合。
  - 認可 bypass 経路を tier2 公開 API に置くことを禁止
    （tenant_id 引数受付禁止と同じ枠：「16_強制機構」層 5）。
