============================================================
data 位置づけ
============================================================

■ 5 階層中の位置
  - tier1 : システム共通処理（Library / Server / 認証 /
            観測可能性）
  - tier2 : ドメイン業務共通化処理
  - tier3 : 個別業務の Web サイト / exe
  - infra : 物理 / 仮想基盤 + 制御平面
  - data  : データ層（保全 / lifecycle / 暗号化）← 本層

  - data は tier1 / tier2 / tier3 全てが「永続化される」
    全てのバイトを所有する。tier1 / tier2 / tier3 の各 spec
    が「永続化された後にも壊れない」と書く defense-in-depth
    層 E は data 層の engine 物理機構で実 enforcement される。
  - infra との関係：data 層の instance は infra が提供する
    Operator 基盤（CloudNativePG / Strimzi / Altinity） /
    PV substrate（Longhorn / Ceph）/ object storage（Ceph
    RGW）の上で動作する。data 層は instance の所有者で
    あって、Operator 自体や PV 物理層は持たない。

■ 上下方向の関係
  - 上方向（tier1 / tier2 / tier3 が data に依存する経路）：
      - tier1 Library Repository →
            CloudNativePG instance（PostgreSQL）
            Apicurio Registry instance（schema fetch）
            Valkey instance（cache）
      - tier1 観測可能性 SoR →
            ClickHouse instance（signal SoR、tier1 が論理所有
              するが instance 運用は data 層）
      - tier2 Service Outbox / audit_local →
            CloudNativePG instance（同 schema 内 outbox table、
              06_スキーマ運用方針 で table 命名固定）
            Kafka instance（CDC / Outbox publisher 経由）
      - tier3 SPA backend / 業務 entity →
            CloudNativePG instance、Valkey instance（session）
      - tier1 Server 系 messaging_bridge →
            Kafka instance（07 transport の messaging_bridge
              constraints が partition_count / retention で
              data に降りる）

  - 下方向（data が infra に依存する経路）：
      - PV：Longhorn（block）/ Ceph RGW（object）の物理層
        を infra が提供。data は PVC / S3 endpoint を消費。
      - Operator：CloudNativePG / Strimzi / Altinity / Apicurio
        Operator は infra が GitOps 配信。
      - Secret：CloudNativePG superuser / Kafka SCRAM 認証 /
        TLS 証明書 は External Secrets 経由で OpenBao から
        配信。鍵は 11 鍵管理適合仕様 の v1_kek 階層から下る。
      - cluster topology：preservation_class が要求する物理
        topology（multi-zone PV / multi-region replication）
        は infra topology_class と preservation_substrates
        .lock.yaml で双方向 lock。

■ 横方向の関係（data ↔ tier 各層）
  - data ↔ tier1：
      - tier1 Repository は CloudNativePG / Valkey / Kafka /
        ClickHouse 実装を直接行う。data 層は instance
        substrate と schema migration 物理実行を提供。
      - tier1/12 schema 進化適合仕様 が compatibility 判定
        を行い、data 層が sqlx-cli で物理 migration を実行。
      - tier1/13 SLO 適合仕様 の v1_data_durability /
        v1_replication_lag は data 層の preservation 軸 SLI
        を emit して評価される。
      - tier1/15 capacity 適合仕様 の v1_per_tenant_volume の
        enforcement_layer = storage_layer_quota は data 層の
        bucket / namespace / topic 単位で物理 enforce。
  - data ↔ tier2：
      - tier2/32 テナント分離適合仕様 の RLS FORCE は
        CloudNativePG instance に descend、data 層が物理
        FORCE_RLS / RESET ROLE 規律を運用。
      - tier2 Outbox / audit_local table の table_naming /
        partition_strategy は data 層 06_スキーマ運用方針 に
        従う（tier2 側で coding 自由度を持たない）。
      - tier2 Service の write は Outbox（同 transaction 内）
        を経由、Kafka publisher は data 層が運用。
  - data ↔ tier3：
      - tier3/22 端末オフラインデバイス で IndexedDB に
        rest した copy は logical replication の対象であり、
        data 層は server 側の sync endpoint（Kafka topic /
        Postgres logical replication slot）を提供。
      - tier3/39 client 状態適合仕様 の reconcile_class が
        要求する server 側 read consistency は data 層の
        synchronous_commit 設定で物理 enforce。
  - data ↔ infra：
      - infra topology_class と data preservation_class は
        preservation_substrates.lock.yaml で双方向 lock。
        どちらか一方だけ宣言する経路は admission block。
      - infra 14_強制機構 の require-encrypted-pv / Kyverno
        admission policy が data 層 PVC に対して LUKS 強制。
      - infra 15_クラスタ位相適合仕様 の cross_axis_data_
        preservation scenario が data01 と integration assertion
        を共有。

■ 13 軸 + meta 中の位置
  - 13 軸：07 transport / 08 migration / 09 observability /
    10 auth / 11 key / 12 schema / 13 SLO / 14 OSS lifecycle /
    15 capacity / 32 data-tenant / 39 client / infra01
    topology / data01 preservation（本層）
  - data は 13 軸の 1 軸（preservation）の保有層であると
    同時に、全 13 軸の defense-in-depth 層 E（物理 enforcement）
    のうち永続化に関わる物理基盤を提供する基盤層という
    二重の役割を持つ。
  - 00 meta（軸登録）の release_gate.lock.yaml AND-gate に、
    data01 の restore_drill.lock.yaml が green 状態として
    入力される。failover_drill（infra01）と restore_drill
    （data01）は別 artifact だが AND-gate で同時 green が
    1.0.0 ship blocker。

■ 至高路線における位置づけの帰結
  - data は「物理 enforcement のうち永続化に責任を持つ最終
    layer」として、文章運用に依らず必ず守られる規律を担う。
  - 運用コスト度外視（CLAUDE.md 上位方針）の哲学に従い、
    cross-region replication の同期度・restore_drill cadence・
    application-layer 暗号化適用範囲は最大化する。「運用が
    大変だから cadence を緩める」「PII column を平文に
    戻す」判断は採らない。
  - 1.0.0 完璧 release：5 preservation_class（v1_local_only
    を除く 4 class）全てで restore_drill green、5 採用 OSS
    全てが L1+ primary として oss_inventory.lock.yaml に登録、
    Kyverno admission policy 完全適用、までを ship blocker
    とする。
