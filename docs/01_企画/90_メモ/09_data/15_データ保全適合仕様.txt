■ 設計原則
  - preservation_class は bundle である。
      yaml に書く data.preservation.* attribute のうち、
      preservation_class 1 つの値が他 5 dimension（durability
      / replication_topology / encryption_layer / restore_
      window_seconds / drill_cadence_days）を一意に導出する。
      Library 作者 / 業務作者 / DBA が dimension を個別に
      override する経路は持たない。
  - dimension override は禁止する。
      「v1_zone_replicated のうち encryption_layer を at-
      rest-only に弱めたい」要望は新 class を切ることで表現
      する。class 数の爆発は意味論の規律として受け入れる。
  - dead spec を CI で殺す。
      classes.yaml に登録された全 class、scenarios.yaml に
      登録された全 assertion id、preservation_substrates.
      lock.yaml に列挙された全 substrate、restore_drill.
      lock.yaml に列挙された全 drill record は、いずれも
      参照されなくなった時点で CI fail とする。CR のうち
      preservation_class 注釈が無いものも CI fail（preservation
      未宣言の persistence を deny by default）。
  - 5 種類 preservation orchestrator を全 preservation_class
    に必須化する。
      postgres_wal_streaming / kafka_replication_quorum /
      clickhouse_keeper_replication / ceph_multi_site /
      object_lock_compliance の 5 orchestrator は、各 class
      が必要とする層を宣言する。同一 preservation は複数
      orchestrator に分散しないが、同一 instance では複数
      class が複数 orchestrator を併用する。
  - restore_drill を物理 property とする。
      「drill_cadence_days 以内に必ず restore を実演し、
      宣言された RPO / RTO 内に収束する」を Litmus chaos
      test で必ず検証する。13 の v1_data_durability /
      v1_replication_lag が cluster_label 付き metric で
      隣接 cluster を観測し、保全破綻を即時 alert + admission
      block に流す。
  - defense-in-depth は 5 層で構成する。
      層 A : compile 時（CR / migration ファイルの preservation
              _class 注釈必須、sqlx prepare 通過）
      層 B : lint（preservation_class 注釈の存在 / 値域検査 /
              preservation_substrates.lock.yaml と整合）
      層 C : restore_drill chaos test（Litmus）
      層 D : runtime（5 orchestrator の実 deploy）
      層 E : physical（CloudNativePG synchronous_commit /
              Kafka min.insync.replicas / clickhouse-keeper
              Raft / Ceph CRUSH zone failure_domain / Longhorn
              LUKS の物理層強制）
      任意の単層が破れても他層が必ず止める。物理 enforcement
      は最終 safety net。

■ v1 preservation_class セット（5 class）
  - yaml に書ける preservation_class は次の 5 値のみ。各
    instance 実体は preservation_substrates.lock.yaml の枝で
    classes.yaml の keys と照合する。

      class                          | durability       | replication_topology       | encryption_layer            | restore_window_seconds | drill_cadence_days
      -------------------------------+------------------+----------------------------+-----------------------------+------------------------+--------------------
      v1_local_only                  | local            | none                       | at_rest_only                | 14400 (4 h)            | 180
      v1_zone_replicated             | zone_quorum      | sync_within_cluster        | at_rest + column_envelope   | 60                     | 90
      v1_cluster_replicated          | cluster_quorum   | async_cross_cluster        | at_rest + column_envelope   | 300 (5 min)            | 60
      v1_cross_region_replicated     | region_quorum    | sync_cross_region          | at_rest + column_envelope + | 300 (5 min)            | 30
                                     | (C-priority      |                            |   topic_payload_envelope    |                        |
                                     |  during          |                            |                             |                        |
                                     |  partition)      |                            |                             |                        |
      v1_global_replicated           | global_quorum    | cell_partitioned_multi_region | at_rest + column_envelope + | 0 (per-cell continuous) | 14
                                     |                  |                               |   topic_payload_envelope +  |                         |
                                     |                  |                               |   archive_triple_wrap       |                         |

  - 各 class の不変条件と典型用途：

      - v1_local_only
          - 単一 zone 内の単一 instance。dev / stage / 検証
            用途。CloudNativePG 1 primary（standby なし）、
            Kafka RF=1、ClickHouse 1 replica。
          - durability：local（fsync 完了で commit 確定、
            zone 障害で永続喪失の可能性）。
          - replication_topology：none（cross-zone 同期なし）。
          - encryption_layer：at_rest_only（PV LUKS のみ、
            column-level envelope は適用 optional だが推奨）。
          - restore_window：4 時間（manual restore、PITR
            base backup + WAL）。
          - drill：6 ヶ月に 1 回、full restore の dry-run。
          - 典型：開発 namespace、PoC、internal tool。本番
            業務は採用しない（DR 不可能なため、infra topology
            v1_single_zone とのみ整合）。

      - v1_zone_replicated
          - 単一 region 内の複数 AZ（≥ 3 zone）にまたがる
            単一 cluster。本番業務の標準 default。CloudNativePG
            1 primary + 2 sync standby（zone 分散）、Kafka
            RF=3 ISR=2 rack 跨ぎ、ClickHouse 1 shard × 3
            replica（zone 分散）、Apicurio HA pod。
          - durability：zone_quorum（zone failure 時 quorum
            維持で書き込み継続）。
          - replication_topology：sync_within_cluster
            （synchronous_commit=remote_write、min.insync.
            replicas=2 rack 跨ぎ）。
          - encryption_layer：at_rest（Longhorn LUKS）+
            column_envelope（PII / monetary 列）。
          - restore_window：60 秒（automatic recovery、新
            primary 昇格）。
          - drill：90 日に 1 回、Litmus で 1 zone を network
            partition、SLO 維持確認。
          - 典型：本番 production 業務の default 採用。tier2
            業務 entity、tier1 Library Repository、tier1/09
            観測 SoR。

      - v1_cluster_replicated
          - 同 region 内の複数 cluster（≥ 2 cluster）が
            active-active。CloudNativePG 内 zone_replicated
            + 別 cluster に async standby、Kafka MirrorMaker2
            cross-cluster mirror、ClickHouse 別 cluster の
            Distributed table 経由 async push、Apicurio
            cross-cluster sync。
          - durability：cluster_quorum（1 cluster 完全断
            でも他 cluster が即時 traffic 引受、async lag
            分の data loss は容認）。
          - replication_topology：async_cross_cluster
            （cluster 跨ぎは eventual consistency）。
          - encryption_layer：v1_zone_replicated と同等。
          - restore_window：5 分（automatic、cluster 跨ぎ
            failover）。
          - drill：60 日に 1 回、Litmus で 1 cluster を
            network partition、SLO + data lag 維持確認。
          - 典型：region 内 HA を最大化、計画 maintenance を
            online で実施。tier2 高 throughput Service、
            tier1 transport mesh の messaging_bridge。

      - v1_cross_region_replicated
          - 複数 region（primary + standby ≥ 1）。standby
            region は読み取り可能だが書き込みは primary のみ。
            CloudNativePG Replica Cluster で WAL streaming
            sync、Kafka MM2 strict-ordering、ClickHouse macro
            replicas、Ceph multi-site。
          - durability：region_quorum（region 障害でも
            standby が同期受信済の WAL を持つ、RPO=0。
            partition 中の primary write を block することで
            保証＝永続書込が ack された record は 100% standby
            に到達済みを意味）。commit latency は cross-region
            RTT（standby region への WAL apply ack 往復）に
            支配される物理制約あり（infra01/15 v1_multi_region
            _active_passive と双方向 lock）。
          - 対応する SLO latency class：本 preservation_class
            配下の write 経路は 13_SLO 適合仕様 の
            v1_request_latency_p99_cross_region に bind 必須
            （threshold_ms 典型 1500ms、primary↔standby region
            RTT に応じて instance 別宣言）。13_SLO 整合 14 の
            双方向 lock により、intra-region 想定の
            v1_request_latency_p99 を本 preservation_class の
            write 経路に適用することは admission block。
          - replication_topology：sync_cross_region
            （synchronous_commit=remote_apply）。書き込み点は
            単一 region に固定された active-passive 構造で、
            CAP 観点では C/A の両立が可能（partition 発生時
            は (a) primary 側 write を physical block して C
            維持、(b) standby 側を read-only に縮退、の双方を
            同時採用）。
          - partition 中の不変条件：standby region 到達不能の
            窓では primary 側 write は physical block
            （synchronous_commit=remote_apply の native 挙動、
            quorum loss で commit 完了不能）。restore_window
            5 分は「write block window の cap = standby promote
            完了までの上限」と解釈する。13 SLO の v1_request_
            availability は当該 window 中、partition window と
            同等の error budget を消費する（13 SLO の budget と
            双方向 lock）。
          - encryption_layer：at_rest + column_envelope +
            topic_payload_envelope（Kafka payload にも
            envelope）。
          - restore_window：5 分（Argo Events trigger で
            standby promote、write block window cap）。
          - drill：30 日に 1 回、Litmus で primary region を
            network partition、standby promote → traffic
            shift → fallback の full cycle。
          - 典型：規制要件で cross-region DR が必須な業務、
            data 軸の PII / monetary を扱う Service、tier2
            の業務 SoR。

      - v1_global_replicated
          - 複数 region（≥ 2）が cell-partitioned active-
            active。CloudNativePG は cell 単位の per-region
            single-leader（v1_zone_replicated と同型を per-
            cell で配置）、tenant ↔ cell の affinity で
            cross-region write を物理排除。Kafka は cell-
            partitioned topic で partition key を cell_id に
            固定、MM2 双方向 mirror は read-replication 用途。
            ClickHouse macro replicas は per-region replicated
            （cross-region eventual）、Ceph RGW multi-site
            bidirectional は object key prefix で write owner
            を home region に固定。
          - durability：global_quorum（per-cell 視点では
            region_quorum、cell 集合視点で global）。region
            障害時、未障害 region の cell は無影響、障害
            region home の cell のみ predefined fallback cell
            に automatic_within_window で再 affinity される。
            external_dns_multi_region は健全 cell には適用
            されず、被影響 tenant の DNS reassign は DNS TTL
            に律速（標準で 30〜60 秒）。
          - replication_topology：cell_partitioned_multi_
            region。per-tenant region affinity で cross-region
            write を物理発生させない（true multi-master /
            CRDT は v1 で採用しない、v2 候補）。
          - 対応する SLO latency class：本 preservation_class
            配下の write 経路は 13_SLO 適合仕様 の
            v1_request_latency_p99_cross_region に bind 必須。
            unaffected cell 内の per-cell write は per-cell
            scope の zone_replicated 相当 commit semantics を
            持つが、cell promote / cross-region archive 経路を
            含む経路は cross-region RTT 律速のため統一して本
            class を採用する。13_SLO 整合 14 の双方向 lock により
            intra-region 想定の v1_request_latency_p99 を採用
            することは admission block。
          - encryption_layer：at_rest + column_envelope +
            topic_payload_envelope + archive_triple_wrap
            （archive_to_offline で 3 重 wrap）。
          - restore_window：0（per-cell continuous、未障害
            cell は常時書込可能）。障害 region home cell の
            tenant 視点では cell promote 中に短時間 unavailable
            （RTO は cell promote window 内）。
          - drill：14 日に 1 回、Litmus で 1 region を完全
            isolation、未障害 cell 業務継続 + 障害 cell の
            within_window 再 affinity + cross-region 同 partition
            write が発生していない不変条件 + data divergence
            なしを確認。
          - 典型：global SaaS、per-tenant 視点 24/7 zero-
            downtime 業務。本企画の 1.0.0 では「採用可能 class」
            として宣言、特定業務 pack（製造業 global SCM など）
            が選択する。「全 tenant 同時 zero-downtime」は cell
            migration window 中の被影響 tenant について保証
            しない（per-cell scope の zero-downtime）。

  - 上記 5 class で v1 が covering。製造業 pack 想定 8 業務
    シナリオの stress test を本仕様末尾に示す。

■ dimension の根拠
  - durability は喪失時の単位：
        local            → fsync 完了 / 単一 disk 喪失で全失
        zone_quorum      → zone 単一断 / AZ 障害が想定上限
        cluster_quorum   → cluster 単一断が上限
        region_quorum    → region 全断 / regional outage が
                           上限
        global_quorum    → 複数 region 同時 / 大陸障害が
                           上限
    複数粒度を重ねた表現（zone+region 等）は class 内 fixed。
  - replication_topology は同期 model：
        none                            → 単一 instance のみ
        sync_within_cluster             → cluster 内 sync
        async_cross_cluster             → cluster 跨ぎ async
        sync_cross_region               → region 跨ぎ sync。
                                           書き込み点は単一
                                           region に固定（active-
                                           passive）、commit
                                           latency は cross-region
                                           RTT に支配される。
        cell_partitioned_multi_region   → 複数 region で cell
                                           単位の single-leader、
                                           tenant ↔ cell affinity
                                           で cross-region write
                                           を物理排除。per-cell
                                           は sync_within_cluster
                                           相当、cell 間 / region
                                           間は eventual。CRDT
                                           系 multi-master は v1
                                           不採用（v2 候補）。
    混合は class 内 fixed。
  - encryption_layer は暗号化の depth：
        at_rest_only                          → PV LUKS のみ
        at_rest + column_envelope             → 加えて
                                                 column-level
                                                 envelope
        at_rest + column_envelope +           → 加えて Kafka
          topic_payload_envelope                payload envelope
        at_rest + column_envelope +           → 加えて archive
          topic_payload_envelope +              の 3 重 wrap
          archive_triple_wrap
  - restore_window_seconds は復旧の時間 SLA：
        14400 → 4 時間（manual）
        300   → 5 分（automatic, region failover 含む）
        60    → 60 秒（automatic within zone）
        0     → continuous。v1_global_replicated では per-cell
                 continuous（未障害 cell は常時書込可能）の意味
                 で、障害 region home cell の tenant 視点では
                 cell promote window 中に短時間 unavailable に
                 なり得る。
    class の risk profile が低いほど短い。
  - drill_cadence_days は restore_drill の最大 interval。
    class の risk profile が高いほど短い（global_replicated
    が 14 日、local_only が 180 日）。

■ derived dimension（per-instance threshold）を独立次元に
  しない理由
  - per-instance の閾値（v1_zone_replicated の zone 数=3
    vs v1_cross_region_replicated の primary_zone_count=3
    + standby_region_count=1）は本来 dimension たり得るが、
    5 class それぞれで「同じ durability / replication_topology
    / encryption_layer / restore_window_seconds / drill_
    cadence_days 構造で閾値だけが instance 別」という同形
    操作になる。
  - 閾値は class instantiate 時の instance attribute として
    宣言し、build artifact が CloudNativePG Cluster CR /
    KafkaTopic CR / Kyverno admission policy / Litmus chaos
    experiment を生成する形に統一。
  - data オペレータ / 業務側で迷う余地がないため、独立
    dimension 化する利得が乏しい。

■ 5 種類 preservation orchestrator の責務分離（特殊機構）
  - orchestrator 1: postgres_wal_streaming
      - v1_zone_replicated 以上の主担当。CloudNativePG の
        synchronous_commit + Replica Cluster で WAL streaming、
        commit 確定を OS fsync 物理層で強制。
      - synchronous_standby_names が層 E の物理 trigger。

  - orchestrator 2: kafka_replication_quorum
      - v1_zone_replicated 以上の主担当。Strimzi Kafka の
        replication.factor + min.insync.replicas + rack
        awareness + unclean.leader.election=false で broker
        層に物理 enforce。
      - 07 transport の messaging_bridge constraints と整合。

  - orchestrator 3: clickhouse_keeper_replication
      - v1_zone_replicated 以上の主担当。Replicated MergeTree
        + clickhouse-keeper の Raft quorum で part metadata
        を全 replica 同期、leader election quorum で物理
        保証。

  - orchestrator 4: ceph_multi_site
      - v1_cross_region_replicated 以上の主担当。Rook+Ceph
        RGW の master / secondary zone 双方向同期（v1_global
        _replicated）または master → secondary 単方向同期
        （v1_cross_region_replicated）で、object 単位の
        eventual consistency を保証。
      - object lock は両 zone 同一適用。

  - orchestrator 5: object_lock_compliance
      - 全 preservation_class（v1_local_only を除く）の archive
        担当。Ceph RGW Object Lock の Compliance mode で、
        retention 期限内の物理 delete を不可能化する。
        crypto-erase（DEK 破壊）以外で対象 object に手を出せ
        ない。
      - 11 鍵管理適合仕様 の rotation cadence と双方向 lock。

  - 5 orchestrator は順次評価される（postgres_wal → kafka_
    replication → clickhouse_keeper → ceph_multi_site →
    object_lock）が、各 preservation_class は 1 instance 種
    に対して該当 orchestrator を「主担当」として宣言。他
    instance 種は補助的に協調動作（例：v1_zone_replicated
    の主担当は postgres_wal_streaming だが、同 instance に
    kafka_replication_quorum が併用される）。

■ defense-in-depth の各層（重複の物理意味）
  - 層 A（compile）：Cluster CR / KafkaTopic CR / migration
    ファイル / Avro/Proto schema が compile 時に preservation
    _class 注釈を必須化。sqlx prepare で query type を check、
    Apicurio CLI で compatibility verify。
  - 層 B（lint）：Rego policy で classes.yaml と整合性
    check、preservation_substrates.lock.yaml と CR の双方向
    確認、Kyverno policy build artifact の整合確認。
  - 層 C（restore_drill chaos test）：Litmus で per-class
    drill scenario を起動、assertion id の機械的 evaluation、
    restore_drill.lock.yaml の自動 update。drill 失敗で
    admission block 発火。
  - 層 D（runtime）：5 orchestrator の deploy 状態を Argo
    CD reconciliation で常時確認。drift は self-heal、
    手動変更は drift として reset。
  - 層 E（physical）：CloudNativePG の synchronous_commit
    が OS fsync で確定するまで commit を返さない、Kafka
    broker が min.insync.replicas を満たさなければ produce
    を NOT_ENOUGH_REPLICAS で reject、ClickHouse keeper の
    Raft majority がなければ part 確定しない、Ceph CRUSH
    map で zone failure_domain が違反すれば PG mapping 拒否、
    Object Lock Compliance mode で retention 期限内 delete
    physical block。

■ build artifact の双方向 lock
  - infra topology_class と data preservation_class の対応表
    （preservation_substrates.lock.yaml の topology_class
    フィールド）が双方向 lock：
        - v1_local_only        ↔ v1_single_zone のみ
        - v1_zone_replicated   ↔ v1_multi_zone_per_cluster
                                 （同一 cluster 内）
        - v1_cluster_replicated↔ v1_multi_cluster_active_active
                                 （同 region 複数 cluster）
        - v1_cross_region_repl.↔ v1_multi_region_active_passive
        - v1_global_replicated ↔ v1_multi_region_active_active
  - 片方だけ宣言：admission block。両方が一致しない：admission
    block。例：preservation_class=v1_cross_region_replicated
    で topology_class=v1_multi_zone_per_cluster は physical
    に sync replication 不可能なので CI fail。
