# 番号体系規約

## 一文方針
- フォルダ / ファイル名の先頭 2 桁番号は安定 ID として扱う。番号は付与順 = 軸登録順 = 適合仕様 entry 順であり、リネーム / 詰め直し / 振り直しは禁止。新項目は既存番号の末尾追加で対応する。

## 至高路線における原則
- 番号は読者向けの目次順序ではなく、**機械的に安定した参照キー**である。リネームは下流の link / `depends_on` / `id` を全て破壊する操作であり、削除と新規追加を同時にやる行為に等しい。
- 連番に「欠番」が出ても良い。詰め直すことで安定 ID を破壊する方が損失が大きい。
- 番号付与は単調増加 (monotonic increase)。これは git log / build artifact 化された軸登録 (`axis_registry.lock.yaml`、メモ層 `00_軸登録適合仕様` 相当) と同型。

## 番号の桁数

| 階層 | 桁数 | 例 |
|---|---|---|
| フェーズ | 2 桁 | `01_企画/` `02_要件定義/` `03_概要設計/` `04_詳細設計/` `00_format/` |
| フェーズ内サブカテゴリ | 2 桁 | `01_スコープ/` `02_機能要件/` `03_非機能要件/` |
| サブカテゴリ内ファイル | 2 桁 | `01_提供スコープ.md` `02_非提供スコープ.md` |
| 軸別フォルダ（概要設計） | 2 桁 | `02_tier1設計方針/` ... `11_formal設計方針/` |

- すべて 2 桁ゼロパディング。`1_` ではなく `01_`。
- 99 を超える項目が出た場合は階層を分割する（フォルダ追加）。

## 番号付与順序の規約

- 軸番号:
  - `tier1=05`, `tier2=06`, `tier3=07`, `infra=08`, `data=09`, `security=10`, `ops=11`, `client=12`, `test=13`, `formal=14`
  - 概要設計フォルダ内では `02_tier1〜11_formal` に再番号化（フェーズ内連番として）。これは元の `05〜14` をそのまま使うと `01_アーキテクチャ概観` の後 `02〜10` を空けることになるため、フェーズ内連番に整える。
  - 適合仕様フォルダ (`04_詳細設計/01_適合仕様/`) は **適合仕様 entry 順**で `00_軸登録`〜`20_形式検証` を付与。
- 軸内のサブ項目の番号順:
  - `01_責務` / `02_位置づけ` / `03_非提供スコープ` / `04_採用OSS` / `05〜XX_方針` / `XX_運用UIと開発者体験` / `XX_強制機構` / `XX_適合仕様`
- フェーズ内サブカテゴリは **要件定義 / 概要設計 / 詳細設計のプラン本文ツリー**に従う。

## 軸番号体系

各軸の項目は以下の固定構造で正式層に配置される:

| 項目種別 | 配置先 |
|---|---|
| 責務 | `02_要件定義/01_スコープ/01_提供スコープ.md` (集約) + `03_概要設計/<軸>設計方針/README.md` (軸 index) |
| 位置づけ | `03_概要設計/<軸>設計方針/README.md` (軸 index 内) |
| 非提供スコープ | `02_要件定義/01_スコープ/02_非提供スコープ.md` (集約) |
| 採用 OSS | `02_要件定義/04_技術選定/01_OSS採用一覧.md` (集約) |
| 各方針 | `03_概要設計/<軸>設計方針/<連番>_<同名>.md` (1:1) |
| 運用 UI と開発者体験 | `04_詳細設計/04_運用UI開発者体験/<軸番号>_<軸>運用UI.md` (1:1、tier1/2/3 は 08_開発者体験統合.md に集約) |
| 強制機構 | `04_詳細設計/02_強制機構/<軸番号>_<軸>強制機構.md` (1:1) |
| 軸別適合仕様 | `04_詳細設計/01_適合仕様/<連番>_<同名>.md` (1:1、連番付与) |
| クロスカッティング適合仕様 | `04_詳細設計/03_クロスカッティング適合仕様/<連番>_<同名>.md` (1:1、連番付与) |

## コンテキスト別番号対照表

同一軸に対して、フォルダ / ファイルの番号付けが **4 つのコンテキスト**で異なる。これは「安定 ID（05-14）」と「各フォルダ内の phase-local 連番」の設計上の使い分けによる。リネームは禁止であり、本表がその全コンテキストを単一の真として集約する。

| 軸 | 安定 cross-repo ID | 概要設計フォルダ # | 強制機構 # | 運用UI # | env 構築フォルダ # |
|---|---|---|---|---|---|
| tier1 | 05 | 02 | 01 | 統合(08) | 01 |
| tier2 | 06 | 03 | 02 | 統合(08) | 02 |
| tier3 | 07 | 04 | 03 | 統合(08) | 03 |
| infra | 08 | 05 | 04 | 01 | 04 |
| data | 09 | 06 | 05 | 02 | 05 |
| security | 10 | 07 | 06 | 03 | 06 |
| ops | 11 | 08 | 07 | 04 | 07 |
| client | 12 | 09 | 08 | 05 | 08 |
| test | 13 | 10 | 09 | 06 | 09 |
| formal | 14 | 11 | 10 | 07 | 10 |

**表の読み方**:
- **安定 cross-repo ID**: `axis_registry.lock.yaml` / `id` frontmatter / cross-repo 参照に使う固定識別番号
- **概要設計フォルダ #**: `03_概要設計/<NN>_<軸>設計方針/` のフォルダ先頭番号（01_アーキテクチャ概観 が既存のため 02 から開始）
- **強制機構 #**: `04_詳細設計/02_強制機構/<NN>_<軸>強制機構.md` の先頭番号（10 軸を 01-10 で通番）
- **運用UI #**: `04_詳細設計/04_運用UI開発者体験/<NN>_<軸>運用UI.md` の先頭番号。tier1/2/3 は `08_開発者体験統合.md` に集約のため個別ファイルなし（統合=08）
- **env 構築フォルダ #**: `05_環境構築/<NN>_<軸>/` のフォルダ先頭番号（`00_k1s0作者` の後 01-10 に tier1〜formal を連番）

**なぜコンテキストごとに番号が異なるか**: 各フォルダはそれぞれ独自の先行コンテンツ（`01_アーキテクチャ概観` 等）を持つため、フォルダ内の phase-local 連番は安定 ID と一致しない。番号リネームは `depends_on` / `id` を全破壊するため禁止。本表でコンテキスト間の対応を明示し、ナビゲーションの曖昧さを排除する。

## 番号の追加 / 削除規約

- **追加**: 既存番号の末尾に追加。途中の欠番を埋め直さない。
- **削除**: 物理削除はせず、frontmatter `status: deleted` で論理削除する経路を持つ（Phase 5 で lint 規約として確定）。
- **リネーム**: 番号 / ファイル名のリネームは禁止。意味が変わった場合は新番号で新規作成し、旧 file は `status: deprecated` に変更（Phase 5）。

## archive 領域の番号規約

`docs/90_archive/` 配下のフォルダ / ファイル番号は本流の安定 ID 規約から除外される。

- 新規 archive 追加時は本流の番号体系を侵さず、archive 内で独立に連番管理する
- `status: archived` frontmatter を必須とする
- lint の対象外（`EXCLUDE_PATTERNS` に `90_archive` を追加済み）
- `00_format/` の lint 設定は `90_archive` を除外対象として設定済み
