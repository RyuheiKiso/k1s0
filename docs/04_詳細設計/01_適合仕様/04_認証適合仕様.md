# tier1 認証適合仕様（v1）

## 一文定義
- 認証適合仕様は、5 auth_class × 5 dimension（subject_kind / token_type / lifetime_class / refresh_policy / step_up_required）の cross-product として宣言される subject identity catalog の各 instance に対し、Envoy + Keycloak + DPoP / mTLS の 5 層 defense-in-depth で物理 enforce し、tier2 / tier3 / Companion から「生 access_token 文字列」を扱う経路を物理拒否する meta-axis である。

## 位置づけ
- 04_提供機能カテゴリ Authentication / Authorization、02_採用 OSS 一覧 Keycloak、01_Server 系 Backend-for-Library / Capability Negotiation、02_Library Companion 認証コンテキスト伝播、tier2 / tier3 認証関連が散在的に宣言する subject identity / token lifetime / refresh / step-up / federation / impersonation を、機械可読な単一の真として一箇所に固定
- 01_Bidi 適合仕様 が transport 軸、tier2/32 適合仕様 が data 軸の単一の真であるのと同型の枠組みを auth 軸に転写
- tier1 が物理的に唯一の認証 facade として振る舞う

## 設計原則
- **auth_class は bundle**: class 1 値が他 5 dimension（`subject_kind` / `token_type` / `lifetime_class` / `refresh_policy` / `step_up_required`）を一意に導出
- **dimension override 禁止**: 「`v1_workload_jwt` のうち lifetime だけ伸ばしたい」要望は新 class を切る
- **dead spec を CI で殺す**: classes / scenarios / IdP adapter のいずれも参照消失で CI fail
- **delegation / impersonation / purpose は AuthContext attribute**: auth_class は subject の本質を決め、`delegation_chain` / `purpose` は session attribute として 32 適合仕様の `session_context` と直交
- **defense-in-depth は 5 層**: compile（AuthContext 必須引数化、生 token 不可視）/ lint / cross-class integration test / runtime（Envoy + Keycloak + DPoP / mTLS）/ token validation 全数監査

## v1 auth_class セット（5 class）

| class | subject_kind | token_type | lifetime | refresh | step_up |
|---|---|---|---|---|---|
| `v1_human_session` | human | dpop_bound_jwt | medium (<1h) | rotating | on_high_risk |
| `v1_workload_jwt` | workload | jwt_short | short (<5m) | not_applicable | never |
| `v1_device_attest` | device | jwt_attested | long (<24h) | one_shot | on_first_use |
| `v1_federated_exchange` | external_subject | exchange_jwt | short (<5m) | not_applicable | never |
| `v1_emergency_step_up` | human | dpop_bound_jwt | very_short (<10m) | not_applicable | always |

### 各 class の不変条件と典型用途
- `v1_human_session`: 業務担当者の SPA セッション。OIDC code flow + DPoP 鍵束縛（RFC 9449）。rotating refresh（replay 検出で session 全消滅）。step_up: 高リスク action 直前に WebAuthn / FIDO2 / TOTP で再認証。tier3 業務 SPA / 運用 console / tier2 admin UI
- `v1_workload_jwt`: K8s ServiceAccount projection or SPIFFE/SPIRE 由来 SVID。短 TTL の JWT。自動 renew は workload runtime（kubelet projected volume / spire-agent）が担う。tier2 Service 間 RPC、tier1 Sidecar、Outbox relay、CI/CD deploy
- `v1_device_attest`: 工場端末・KIOSK・現場ハンドヘルド。TPM / 専用 HSM / WebAuthn platform authenticator による device cert を根拠に、長 TTL token を 1 度発行（one_shot refresh）。on_first_use step_up: 初回登録時のみ管理者承認 + device attestation chain 検証。期限切れは再 attestation を要求（自動 refresh 不可）
- `v1_federated_exchange`: 親会社 IdP / 取引先 IdP / 別 SaaS から token exchange（RFC 8693）で audience-restricted な短命 JWT を取得。`audience` claim によりアクセス可能な resource server を機械的に絞る
- `v1_emergency_step_up`: 業務停滞 / 障害対応 / コンプライアンス監査の break-glass。always step_up: 取得時に必ず WebAuthn 等で再認証 + 理由文記入。発動は audit signal に強制 emit。lifetime <10 分、refresh 不可、自動 revoke。`purpose='emergency'` を必ず claim に含み、32 の `app.purpose` と直結

## dimension の根拠
- `subject_kind` は token validation の鍵検索 path を分ける（human / workload / device / external_subject はそれぞれ異なる JWKS / SVID bundle / device cert chain / federation issuer と紐付く）
- `token_type` は wire 上の検証アルゴリズムを決める（`dpop_bound_jwt` は proof-of-possession 必須、`jwt_short` は通常 JWT、`jwt_attested` は attestation chain verify、`exchange_jwt` は `act` / `may_act` claim、audience-restricted）
- `lifetime_class` は revocation 戦略を決める（very_short / short は revocation list を持たず期限切れに任せる、medium / long は Keycloak revocation API + JWKS rotation で revoke）
- `refresh_policy = rotating` は OIDC 推奨パターン。`one_shot` は device 初期登録時のみ、`not_applicable` は workload / federated / emergency
- `step_up_required` は high-risk action 前の再認証要求の発動条件（never / on_first_use / on_high_risk / always の 4 段階）

## delivery dimension（impersonation / delegation）を独立次元にしない理由
- `impersonation_policy` / `delegation_chain` は本来 dimension たり得るが、5 class それぞれに自然な値が 1 つ決まる:
  - `v1_human_session` / `v1_workload_jwt` / `v1_device_attest` / `v1_emergency_step_up` → impersonation forbidden
  - `v1_federated_exchange` → impersonation scoped（`act` / `may_act` claim）
- delegation（admin が user を代行する Delegation: tier2/22）は auth_class とは直交し、`AuthContext.delegation_chain` attribute として表現する。32 の `app.delegation_chain` と同期
- impersonation を class dimension に昇格する余地は残す（v2 で需要が出た場合の major version up）

## AuthContext スキーマ（32 session_context の拡張・同型）
tier1 Library が transaction 開始時に SET LOCAL する GUC を、32 の `session_context` に対し追加宣言:

| field | type | 用途 |
|---|---|---|
| `app.auth_class` | text | `v1_human_session` 等 |
| `app.subject_id` | text | canonical subject（Keycloak `sub`） |
| `app.subject_kind` | text | `human` / `workload` / `device` / `external_subject` |
| `app.token_id` | text | `jti`（revocation tracking） |
| `app.session_id` | text | human / device の session 識別 |
| `app.audience` | text | token `aud`（federated に必須） |
| `app.scopes` | text[] | OAuth scopes |
| `app.dpop_jkt` | text | DPoP key thumbprint（`dpop_bound_jwt` のみ） |
| `app.attestation_level` | text | device attestation level（`jwt_attested` のみ） |
| `app.step_up_proven_at` | timestamptz | 最終 step_up challenge 時刻 |

- 32 で既に存在する `app.tenant_id` / `app.actor_id` / `app.purpose` / `app.delegation_chain` と組合せて、AuthContext + TenantContext は一つの `session_context` として PostgreSQL transaction に提示
- 設定漏れの transaction で auth-bound table を SELECT すると、32 の RLS により 0 行（fail-safe default）
- `app.auth_class` の値は 32 の `app.purpose` 評価と組み合わさる:
  - `v1_emergency_step_up` は `purpose='emergency'` を必ず取り、`v1_federated_exchange` / `v1_device_attest` は `purpose='business_op'` のみ許容、`v1_workload_jwt` は `purpose='business_op'` / `migration`、`v1_human_session` は `business_op` / `support` / `export` / `migration` / `emergency`（emergency 化は `v1_emergency_step_up` に格上げ取得が必須）
- 上の制約は `table_classes.yaml` と同型の純粋関数テーブルとして `classes.yaml` の `allowed_purpose` 節で機械化

## 単一の真（3 ファイル構成）

### `classes.yaml`（軸 auth_class enum）
- class bundle 定義。auth_class 名 → 5 dimension + 不変条件 + `allowed_purpose` の純粋関数テーブル

### `scenarios.yaml`（軸 catalog）
- scenario × auth_class / dimension 値 → assertion id のマトリクス
- 主要 scenario: `token_validation` / `refresh_rotation` / `step_up_challenge` / `revocation_propagation` / `mtls_handshake` / `dpop_proof_replay` / `federation_audience_check` / `emergency_break_glass`

### `idp_capabilities.lock.yaml`（build artifact）
- 各 IdP adapter（Keycloak / SPIRE / federated IdP）の static 自己宣言を tier1 build script が集約して生成。手書き禁止
- 各 adapter の `supports`（class 集合）と `constraints`（federation_protocol / discovery endpoint / revocation API capabilities）を宣言

## 5 層 defense-in-depth
- 層 A: compile（`AuthContext` 必須引数化、生 token 文字列の不可視化、SDK 公開 API として `getAccessToken()` 不在）
- 層 B: lint / 公開 API snapshot（言語別 analyzer + cargo public-api / api-extractor で `Authorization` header 直書きを deny）
- 層 C: cross-class integration test（Testcontainers で Keycloak + SPIRE + federated IdP mock を起動、5 class 全 scenario 実行）
- 層 D: runtime（Envoy `jwt_authn` filter + Keycloak token introspection + DPoP / mTLS）
- 層 E: token validation 全数監査（→ 09 audit signal）

## CI 不変条件（merge 不可）
- 整合 1: `classes.yaml` の全 class が `scenarios.yaml` の matrix 条件で少なくとも 1 scenario によりカバーされる
- 整合 2: `scenarios.yaml` の全 assertion id が、それを必要とする全 class × 全 IdP adapter で実装されている
- 整合 3: `idp_capabilities.lock.yaml` で claim される class が `classes.yaml` に存在
- 整合 4: `classes.yaml` の `allowed_purpose` が 32 適合仕様の `purpose` enum と完全整合
- 整合 5: SDK 公開 API として `getAccessToken()` / 生 `Authorization` header 露出ゼロ
- 整合 6: 全 token 検証経路が audit signal を強制 emit
- 整合 7: `idp_capabilities.lock.yaml` は手書き禁止、build artifact と git の差分検出
- 整合 8: dead spec 検出（参照されない class / scenario / adapter / assertion id は CI fail）

## 1.0.0 ship blocker
- 5 auth_class × 全 IdP adapter の完全 conformance green
- DPoP proof replay 攻撃の property test green
- federation token exchange の audience restriction property test green
- emergency break-glass の audit signal emit が 100% 検証

## 製造業 pack stress test（v1 の正当性証跡、8 業務シナリオ）
1. 業務担当 SPA login + step_up → 発注承認（`v1_human_session` + step_up）
2. tier2 Service が tier1 Backend-for-Library に SVID で RPC（`v1_workload_jwt`）
3. ライン端末（24h 連続稼働）が device cert で long token を取得（`v1_device_attest`）
4. 親会社 IdP federation で取引先パートナーアクセス（`v1_federated_exchange`）
5. 障害対応 break-glass で本番 DB cluster-admin 取得（`v1_emergency_step_up`）
6. CI/CD pipeline が SPIRE SVID で deploy（`v1_workload_jwt`）
7. 取引先 SaaS から token exchange で audience-restricted JWT 取得 + audit emit（`v1_federated_exchange`）
8. refresh_token replay 検出 → session 全消滅 + audit emit（`v1_human_session`）

## v2 拡張ルール
- 新 class の追加は purely additive、既存 class の dimension 値変更は破壊的変更
- impersonation を class dimension に昇格する余地は残す（v2 major version up）
- 命名は `vN_<usage>` 形式に固定

## 採用しない設計
- 生 access_token 文字列の SDK 公開 API 露出
- auth_class dimension override
- impersonation を SDK ユーザが能動的に開始
- ROPC（Resource Owner Password Credentials）
- step_up なしでの high-risk action
- emergency break-glass の audit emit 省略
