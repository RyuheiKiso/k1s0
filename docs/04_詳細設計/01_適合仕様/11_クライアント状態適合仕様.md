# tier3 クライアント状態適合仕様（v1）

## 一文定義
- クライアント状態適合仕様は、4 layer（Server Truth / Optimistic Local / Pending Queue / Draft）× 5 conflict event × 4 BusinessConflict subtype の cross-product として宣言される client state catalog の各 instance に対し、Application 層 reducer + lint + headless browser integration test + WebCrypto / IndexedDB encryption + 端末紛失時 rotation の 5 層 defense-in-depth で物理 enforce する meta-axis である。

## 位置づけ
- 04_状態管理 / 05_リアルタイム更新 UX / 19_業務エラー UX / 22_端末オフラインデバイス / 24_override 実装規約 が散在的に宣言する次の四つを、機械可読な単一の真として固定:
  1. Server Truth / Optimistic Local / Pending Queue / Draft の 4 layer 分離と各 layer の lineage
  2. 4 layer 間の衝突解決 tree（決定論的）
  3. BusinessConflict の subtype による UI 分岐の 1:1 固定化
  4. 端末紛失 / 25h オフライン / PII 永続化での safety net
- 01_Bidi 適合仕様 が transport 軸、10_テナント分離適合仕様 が data 軸の単一の真であるのと同型の枠組みを client 軸に転写

## 設計原則
- **クライアント状態は 4 layer に分割**: ST / OL / PQ / DR の 4 つだけを許容。これら以外の中間 layer を作ることを禁止。1 つの値が「どの layer 由来か（lineage）」を必ず持つ
- **衝突解決 tree は決定論的**: 4 layer × イベント（Domain Event 受信 / API 応答 / ユーザ操作 / ネットワーク復帰 / TTL 経過）の組合せで取るべき動作が一意に決まる
- **BusinessConflict は 4 subtype に細分化**: tier2 BusinessConflict を `stale_write` / `lost_update` / `supersede` / `concurrent_edit` に分割し UI 分岐を 1:1 で固定。subtype と UI 分岐の対応を override 禁止
- **永続化は WebCrypto + device_bound_key で encrypted at rest、PII は in-memory only**
- **defense-in-depth は 5 層**
- **dead spec を CI で殺す**

## v1 layer セット（4 layer）

| layer | source | persisted_in | PII | lifetime |
|---|---|---|---|---|
| `server_truth` (ST) | domain_event_subscription / api_response_2xx | query cache（in-memory） | NG | session（logout で purge） |
| `optimistic_local` (OL) | mutation_in_flight | query cache（overlay） | NG | until_ack_or_rollback |
| `pending_queue` (PQ) | user_action（offline 含む） | indexeddb（encrypted） | 除外 | until_ack_or_user_discard |
| `draft` (DR) | form_input | indexeddb（encrypted） | 除外 | until_confirm_success_or_user_discard |

### 各 layer の不変条件
- `server_truth (ST)`:
  - lineage: `(server_truth, aggregate.version, trace_id, observed_at)`
  - 真は常に tier2 atomic 三表書込が確定した値、client は cache としてのみ保持
  - logout / token expiry で全 ST cache を purge
- `optimistic_local (OL)`:
  - lineage: `(optimistic_local, base_version, predicted_next_version, idempotency_key, started_at)`
  - mutation 開始時に作られ、ack で promote、reject で rollback
  - 同一 aggregate に対し OL は同時 1 件まで（並行 OL 禁止）
- `pending_queue (PQ)`:
  - lineage: `(pending_queue, base_version, idempotency_key, enqueued_at)`
  - 永続化される唯一の mutation 経路。offline 中の操作 / 送信中の操作はすべて PQ に入る
  - aggregate 単位で in-flight 1 件、enqueue 順を保つ
- `draft (DR)`:
  - lineage: `(draft, base_version, form_id, edited_at)`
  - 編集中フォームの dirty state。confirm 成功 / 明示破棄で消滅
  - aggregate に commit する前の値であり、ST / OL / PQ から独立に持つ

## v1 conflict event カタログ（5 event、決定論的 tree）

| event_id | trigger | when |
|---|---|---|
| `server_truth_advance` | domain_event_received / api_response_received | server_truth.version 増加 |
| `optimistic_acknowledged` | api_response_2xx_for_in_flight_mutation | OL 存在 |
| `optimistic_rejected` | api_response_4xx_business_error | OL 存在 |
| `pending_queue_resume` | network_recovery / app_resume | PQ 非空 |
| `business_conflict_received` | api_response_409_with_subtype | PQ または OL 存在 |

### 各 event の actions
- `server_truth_advance`: rollback_optimistic_if_present / update_server_truth / re_evaluate_pending_queue
- `optimistic_acknowledged`: promote_optimistic_to_server_truth / delete_pending_queue_entry_by_idempotency_key
- `optimistic_rejected`: rollback_optimistic / present_business_error / if BusinessConflict: dispatch_conflict_subtype
- `pending_queue_resume`: send_queue_in_enqueue_order / per_aggregate_serialize / 各 send で ack なら optimistic_acknowledged、4xx なら optimistic_rejected を fire
- `business_conflict_received`（subtype 分岐、後述）

## v1 BusinessConflict subtype（4 種、UI 分岐 1:1 固定）

### tier2 への構造的拡張要求
- `BusinessConflict.subtype` フィールドを必須化
- field-level diff の算出を Repository abstraction 内で実施

### subtype 判定ロジック（tier2 側 Library 内部）

| subtype | 判定条件 |
|---|---|
| `stale_write` | base_version < ST.version、かつ field-level diff で client が触った field と他 actor が触った field の集合が disjoint |
| `lost_update` | base_version < ST.version、かつ field-level diff で集合が intersect |
| `supersede` | 同一 actor の後続 op が同 aggregate を既に更新済み（Idempotency-Key chain で検出） |
| `concurrent_edit` | 他 actor が presence で編集中宣言 + 自身が send 試行 |

### subtype branches（business_conflict_received）
- `stale_write`:
  - refetch_server_truth
  - rebase_pending_op_on_new_version (field-level)
  - if rebase_clean: auto_resend_with_new_idempotency_key_chained_to_original（rebase 後 payload は base_version が変わるため同 Idempotency-Key で送ると tier2 Idempotency cache の stored response と衝突する。新 key を発行し chain 親子関係を tier2 cache 側で dedup 判定）
  - if rebase_dirty: present_3way_merge_ui + hold_queue
- `lost_update`:
  - refetch_server_truth
  - present_3way_merge_ui
  - hold_queue_until_user_decides
- `supersede`:
  - delete_queue_entry
  - notify_user_silent (toast 程度)
- `concurrent_edit`:
  - update_presence_indicator
  - allow_user_to_continue_or_abort

tree が決定論的であることの含意: ジュニア級チームが書く tier3 でも、conflict 事象が発生したときに「どの分岐に入るか」は仕様で固定。実装側は branch ごとの UI コンポーネントを書くだけで済み、判断ロジックを散らさない。

## 単一の真（3 ファイル構成）

### `layers.yaml`（軸 layer enum）
- 4 layer の bundle 定義: layer 名 → source / persisted_in / PII / lifetime / lineage の純粋関数テーブル

### `conflict_tree.lock.yaml`（build artifact）
- 5 event × 4 subtype の actions matrix。Application 層 reducer の codegen 入力
- 手書き禁止、build artifact

### `test_matrix.yaml`（軸 catalog）
- headless browser integration test scenarios。製造業 pack stress test 8 シナリオ（offline 25h / lost_update 3way merge / supersede silent / concurrent_edit presence 等）

## 5 層 defense-in-depth
- 層 A: Application 層 reducer（Adapter 集約）— 4 layer reducer / store helper / Adapter 層 effect 実行器を SDK が提供
- 層 B: lint / 公開 API snapshot — layer 種類 / event 追加 / subtype 追加を SDK 公開 API として deny
- 層 C: headless browser integration test — Playwright で 4 layer の lineage / conflict tree / subtype 分岐を property test
- 層 D: runtime（WebCrypto / IndexedDB encryption / Idempotency-Key TTL enforce）— at-rest encryption + 24h TTL の物理 enforcement
- 層 E: 端末紛失時の rotation — refresh_token 失効で queue purge、device_bound_key は OS keychain 由来

## CI 不変条件（merge 不可）
- 整合 1: `layers.yaml` の 4 layer 全てが SDK reducer で実装される
- 整合 2: `conflict_tree.lock.yaml` の 5 event × 4 subtype の actions が SDK で実装される
- 整合 3: `conflict_tree.lock.yaml` は手書き禁止、build artifact と git の差分検出
- 整合 4: `test_matrix.yaml` の全 scenario が Playwright で green
- 整合 5: BusinessConflict subtype と UI 分岐の対応が override 禁止（override 検出は CI fail）
- 整合 6: PII を含むまま PQ / DR に enqueue する経路ゼロ（field_pii annotation で識別、enqueue 時 strip）
- 整合 7: Idempotency-Key 24h TTL の SDK runtime enforcement
- 整合 8: localStorage / SessionStorage / cookie への PII 平文書込ゼロ（headless browser で IndexedDB dump 検査）
- 整合 9: dead spec 検出

- 製造業 pack 8 stress test scenario 全 green（offline 25h / lost_update 3way merge / supersede silent / concurrent_edit presence 等）
- IndexedDB encrypted at rest property test green

## 製造業 pack stress test（v1 の正当性証跡、8 scenarios）
1. 業務担当 SPA で発注承認 → atomic 三表書込ack → ST advance
2. 工場現場の検査担当が 5 件 offline 記録 → 復帰時に PQ resume → 全 ack
3. 同 React SPA で 25h オフライン → Idempotency-Key TTL 超過 → user 確認 → 新 key で resend
4. 並行編集（actor A: 数量 / actor B: 納期）→ stale_write 検出 → field-level rebase → auto resend
5. 並行編集（actor A: 数量 / actor B: 数量）→ lost_update 検出 → 3way merge UI
6. 同 actor が同 aggregate を 2 回更新 → supersede 検出 → silent toast
7. presence indicator 表示中の編集衝突 → concurrent_edit → user choice
8. logout → 4 layer 全 purge + audit emit + device_bound_key rotate

## v2 拡張ルール
- 新 layer の追加は破壊的変更（major version up）
- conflict event の追加は purely additive
- BusinessConflict subtype の追加は purely additive、tier2 / tier3 の対応 UI が必要

## 採用しない設計
- 4 layer 以外の中間 layer
- conflict event の override
- BusinessConflict subtype と UI 分岐の override
- localStorage / SessionStorage への PII 平文書込
- 自製 crypto
- per-aggregate write の concurrent in-flight 複数
