# tier2 テナント分離適合仕様（v1）

## 一文定義
- テナント分離適合仕様は、4 テーブル class（tenant_scoped / tenant_master / platform_global / pii_segregated）× session_context（4 GUC）× transaction_unit（state_change / master_update / pii_access / cross_tenant_admin）の cross-product として宣言される data 分離 catalog の各 instance に対し、Repository abstraction + sqlx-cli plugin + Buf custom lint + cross-tenant integration test + PostgreSQL Row Level Security + pgaudit の 5 層 defense-in-depth で物理 enforce する meta-axis である。

## 位置づけ
- 05_マルチテナント方針 / 08_業務エラー監査コンプライアンス / tier2 強制機構 / 09_権限モデル / 読み取りモデル方針 が散在的に宣言する次の四つを、機械可読な単一の真として一箇所に固定:
  1. `tenant_id` 強制注入の static / runtime 二重防御
  2. 生 SQL 経路の Library 境界での完全封鎖
  3. State change / Outbox / Audit の同一トランザクション書込
  4. PII 隔離と DB layer audit の機構接続
- 01_Bidi 適合仕様 が transport 軸の単一の真であるのと同型の枠組みを data 軸に転写

## 設計原則
- **テーブル分類は migration 時に確定**: 実行時に「このテーブルは tenant 越境を許すか」を判定するのではなく、テーブルを「何の class か」で migration 時点に固定し、class が RLS policy / 必須列 / 監査要件 / Outbox 要件 / TTL を一意に導出。class カタログは 4 種に絞る
- **生 SQL は Library 境界で完全封鎖**: tier2 アプリ層から SQL 文字列を渡せる経路を一切提供しない。Library 内部の Repository abstraction だけが SQL を組み立て、その時点で session GUC（`app.tenant_id` 等）が必ず設定済み。sqlx の `query!` / `query_as!` 系 macro は Library crate 内部のみから呼べる workspace 構造
- **State change / Outbox / Audit は同一 DB トランザクションで書く**: 3 表 atomic に書込み、async 配信は別レイヤ。subscribe 失敗で audit が欠落する事故を構造的に不可能化
- **defense-in-depth は 5 層**: compile（Repository abstraction）/ lint / cross-tenant integration test / runtime（PostgreSQL RLS）/ DB layer audit（pgaudit）
- **dead spec を CI で殺す**: `table_classes.yaml` の class、`transaction_units.yaml` の unit、`migration.lock.yaml` の table、いずれも参照消失で CI fail

## v1 テーブル class セット（4 class）

| class | tenant_id 列 | RLS | 監査要件 | Outbox 要件 | 典型用途 |
|---|---|---|---|---|---|
| `tenant_scoped` | 必須 | `tenant_id = current_setting('app.tenant_id')::uuid` | 業務操作で audit_local | aggregate 変更で outbox | 業務 entity / aggregate / RM |
| `tenant_master` | 必須 | 同上 | 変更で audit_local | 任意（class で宣言） | テナント所有マスタ |
| `platform_global` | 不在 | RLS 無効（tenant 全員 read 可） | 変更で全テナント横断 audit | platform-wide outbox | 通貨 / 国 / 業界共通分類 |
| `pii_segregated` | 必須 | tenant_id + 専用 role check | pgaudit + audit_local | redact 後 outbox | PII を含む user / partner |

### 各 class の不変条件

#### tenant_scoped
- 必須列: `id`, `tenant_id`, `created_at`, `updated_at`, `version`
- RLS: USING / WITH CHECK ともに `tenant_id` 一致
- 監査: INSERT / UPDATE / DELETE で `audit_local` emit を強制
- Outbox: 状態変化 → Domain Event を outbox 表に同 txn で挿入

#### tenant_master
- 必須列: 同上
- RLS: tenant_scoped と同様
- 監査: 変更操作で `audit_local` emit、role 制限（`master.admin`）
- Outbox: マスタ class が要求する場合のみ emit

#### platform_global
- 必須列: `id`, `created_at`, `updated_at`, `version`（`tenant_id` 無し）
- RLS: 無効（tenant 全員 read 可、書込は `platform_admin` role）
- 監査: 変更時に platform-wide audit（tenant 識別子無しで全テナント可視の sink に emit）
- Outbox: platform-wide topic に emit

#### pii_segregated
- 必須列: `id`, `tenant_id`, `created_at`, `updated_at`, `version`、さらに各 PII 列ごとの暗号化済み別表参照
- RLS: `tenant_id` 一致 + 専用 role（`support_engineer` 等）check
- 監査: `audit_local` emit に加え pgaudit による全アクセス DB log
- Outbox: redact 済み payload で emit（PII 平文を outbox に乗せない）

4 class で v1 covering。新業務テーブルが 4 class のいずれにも収まらないと判明した時点で、v2 候補として class 追加検討。

## session_context スキーマ（PostgreSQL session GUC）
tier1 Library が transaction 開始時に SET LOCAL する GUC:

| field | type | 内容 |
|---|---|---|
| `app.tenant_id` | uuid | Authorization context から導出 |
| `app.actor_id` | text | Keycloak subject |
| `app.purpose` | text | `business_op` / `support` / `export` / `migration` / `emergency` |
| `app.delegation_chain` | text[] | 委譲元 user の配列（空は通常操作） |

- GUC が SET されていない transaction で `tenant_scoped` / `tenant_master` / `pii_segregated` を SELECT すると RLS により 0 行が返る（fail-safe default）
- `app.purpose` は 09_権限モデル の Delegation / Emergency Override / セキュリティアーキテクチャ のサポートアクセスと連動。`pii_segregated` の RLS / pgaudit は `app.purpose` の値で挙動を変える

## 単一の真（3 ファイル構成）

### `table_classes.yaml`（軸 table class enum）
- class カタログ。class 名 → 必須列 / RLS policy / 監査要件 / Outbox 要件 の純粋関数テーブル

### `transaction_units.yaml`（軸 catalog）
- transaction unit カタログ。業務操作カテゴリ → 必須参加 table / 必須 GUC / atomic 制約 のマトリクス
- 主要 unit: `state_change` / `master_update` / `pii_access` / `cross_tenant_admin`

### `migration.lock.yaml`（build artifact）
- sqlx-cli migration が生成する build artifact。手書き禁止
- 各 migration ファイルの先頭ヘッダを集約

## 5 層 defense-in-depth
- 層 A: compile 時（Repository abstraction）— sqlx の `query!` / `query_as!` 系 macro が Library crate 内部のみから呼べる workspace 構造
- 層 B: lint / 公開 API snapshot — tier2 アプリ層から SQL 文字列を渡せる API が公開シグネチャに現れたら CI fail
- 層 C: cross-tenant integration test — Testcontainers で tenant A の context で tenant B のデータが取得できないことを property test
- 層 D: runtime（PostgreSQL Row Level Security）— USING / WITH CHECK policy が物理 enforce
- 層 E: DB layer audit（pgaudit）— `pii_segregated` の全アクセスを DB layer で audit

## CI 不変条件（merge 不可）
- 整合 1: `table_classes.yaml` の全 class が `transaction_units.yaml` の少なくとも 1 unit でカバーされる
- 整合 2: `transaction_units.yaml` の全 unit が Repository abstraction で実装される
- 整合 3: `migration.lock.yaml` は手書き禁止、build artifact と git の差分検出
- 整合 4: 全 migration ファイルに class 注釈必須、`tenant_id` 列の存在 / RLS 有効化 / 必須列の充足を CI で検査
- 整合 5: 公開 API snapshot に SQL 文字列受付 API が現れたら CI fail
- 整合 6: cross-tenant integration test で tenant 越境取得ゼロを property test green
- 整合 7: PostgreSQL RLS が `tenant_scoped` / `tenant_master` / `pii_segregated` table で `FORCE` flag 付きで有効化
- 整合 8: pgaudit が `pii_segregated` table で全アクセス log
- 整合 9: atomic 三表書込（State change + Outbox + Audit）の同一トランザクション property test green
- 整合 10: dead spec 検出

## 1.0.0 ship blocker
- 4 テーブル class × 全 transaction unit の完全 conformance green
- cross-tenant integration test で tenant 越境取得ゼロ
- 認証適合仕様 04 の `app.purpose` enum と `table_classes.yaml` の `allowed_purpose` が完全整合
- atomic 三表書込 property (P1)〜(P4) green

## P1〜P4 atomic 三表書込 invariant
- P1: aggregate 状態変更時、必ず Outbox + Audit が同一トランザクションに書込まれる
- P2: Outbox 投入失敗時、aggregate 状態変更も rollback
- P3: tenant_id が GUC と aggregate 行で一致しない場合、INSERT / UPDATE は WITH CHECK で reject
- P4: pgaudit が `pii_segregated` の全 SELECT / INSERT / UPDATE / DELETE を捕捉、欠落ゼロ

## 採用しない設計
- 実行時の tenant 越境判定（migration 時に class で確定）
- tier2 アプリ層への raw SQL 露出
- State change / Outbox / Audit の別トランザクション分割
- `pii_segregated` schema への PII 平文列追加
- table class dimension override
- audit_event の sampling / logical delete
