# tier1 鍵管理適合仕様（v1）

## 一文定義
- 鍵管理適合仕様は、5 key_class × 5 dimension（purpose / rotation_cadence / scope / backend / destruction_method）の cross-product として宣言される key catalog の各 instance に対し、KeyHandle 抽象 + HSM PKCS#11 + SPIRE + OpenBao audit log + 外部公証 attestation の 5 層 defense-in-depth で物理 enforce し、tier2 / tier3 / Companion から「生 key bytes」「Secret 文字列」を扱う経路を物理拒否する meta-axis である。

## 位置づけ
- 02_採用 OSS 一覧 OpenBao / cert-manager / Cosign / SPIRE、04_提供機能カテゴリ Cryptography / Secrets、tier2 audit / data 保持 / セキュリティアーキテクチャ / data lifecycle / テナント分離適合仕様、tier3 セキュリティアーキテクチャ（client device_bound_key）が散在的に宣言する key purpose / rotation cadence / destruction proof / scope / backend を、機械可読な単一の真として固定
- 01_Bidi 適合仕様 / 04_認証適合仕様 と同型の枠組みを key 軸に転写
- tier1 が物理的に唯一の key facade として振る舞う

## 設計原則
- **key_class は bundle**: class 1 値が他 5 dimension（`purpose` / `rotation_cadence` / `scope` / `backend` / `destruction_method`）を一意に導出
- **dimension override 禁止**
- **dead spec を CI で殺す**
- **envelope encryption を data 軸の規範形とする**: pii_segregated（32）の column 暗号は DEK で行い、DEK は KEK で wrap して at-rest に置く。crypto-shred は KEK destroy で全 DEK を不可逆に失効
- **destruction proof は外部公証で物理担保**: audit hash chain の root（tenant 別年次 root）は外部公証（RFC 3161 trusted timestamp / Cosign transparency log）で attest
- **defense-in-depth は 5 層**: compile（KeyHandle 必須引数化、生 key bytes 不可視）/ lint / cross-class integration test / runtime（HSM PKCS#11 / SPIRE / OpenBao audit log）/ 外部公証 attestation

## v1 key_class セット（5 class）

| class | purpose | rotation_cadence | scope | backend | destruction_method |
|---|---|---|---|---|---|
| `v1_data_dek` | data_encryption | days_90 | per_tenant | software_kms_wrapped | crypto_shred (KEK 削除) |
| `v1_data_kek` | kek_wrapping | years_1 | per_tenant_or_platform | hsm_pkcs11_shamir_distributed (M-of-N、N region 独立 HSM) | hsm_zeroize_all_shares |
| `v1_token_signing` | signing_jwt | days_90 | platform | hsm_pkcs11 | jwks_revoke |
| `v1_audit_root_signing` | signing_audit_root | years_1 | per_tenant | hsm_pkcs11 | external_notary_attest |
| `v1_mtls_workload` | mtls_identity | hours_6 | per_workload | spire | spire_revoke |

### 各 class の不変条件と典型用途
- `v1_data_dek`: column-level 暗号化用の DEK。1 KEK で N 個の DEK を wrap、wrapped DEK は AAD で紐付けて pii_segregated table の専用 KMS column に保存。rotation 90 日で background batch 再暗号化、当該 tenant の KEK 削除で全 PII 列が物理的に読めなくなる（crypto-shred）
- `v1_data_kek`: DEK を wrap する KEK。per_tenant or platform。rotation 1 年で全 wrapped DEK を re-wrap（data 再暗号化不要）。HSM PKCS#11 destroy command で全 region の share を zeroize、外部公証で削除を attest。cross-region 物理保証: KEK material は単一 region の単一 HSM partition に物理存在しない、N region の独立 HSM partition が share を 1 個ずつ保持し、KEK の物理復元は M region 健全時の閾値 ceremony によってのみ成立（OpenBao OSS は Vault Enterprise の Performance/DR Replica 機能を持たないため、この cross-region 保証経路で代替）
- `v1_token_signing`: Keycloak JWT 署名鍵（OIDC / OAuth / DPoP / token exchange の発行側）。rotation 90 日で新鍵、JWKS endpoint で 30 日 overlap 期間
- `v1_audit_root_signing`: tier2 audit_local hash chain の年次 root に署名する key。tenant 別、年次。各 tenant の年次 audit hash root を本鍵で署名し、外部公証（RFC 3161 trusted timestamp + Sigstore transparency log）に提出
- `v1_mtls_workload`: K8s pod 間 mTLS / SPIRE SVID（X.509 SVID）。rotation 6 時間で新証明書、SPIRE workload API が kubelet 経由で pod 内に automatic rotation

## dimension の根拠
- `purpose` は backend selection の鍵となる（data_encryption は KEK + DEK の二段、signing 系は HSM 内に private key を留め public key だけを export、mtls_identity は SPIRE が第一級扱い）
- `rotation_cadence` は revocation 戦略を決める（短い rotation は revocation list を持たず期限切れに任せる、長い rotation は明示的 revoke API + 公証）
- `scope` は crypto-shred / blast radius を分ける単位（per_tenant は GDPR 物理削除の単位、platform は cross-tenant resource、per_workload は workload 単位の compromise 局所化）
- `backend` は physical layer の確度を決める（`software_kms_wrapped` は速い / 弱い、`hsm_pkcs11` は遅い / 強い、`spire` は workload bootstrap 専用）
- `destruction_method` は「削除した」の証跡形を決める

## derived dimension（key_use / wrapping_relation）を独立次元にしない理由
- key の用途（encrypt / sign / verify）は `purpose` dimension に自然に従属
- wrapping relation（DEK is wrapped by KEK）は class 間の関係として `classes.yaml` の `wrapped_by` 節で表現

## KeyHandle / KeyMaterial の言語横断型
tier1 Library が公開する KeyHandle は opaque newtype で、生 key bytes を保持しない:
- Rust: `pub struct KeyHandle { class: KeyClass, alias: KeyAlias, /* private */ }`、`encrypt` / `decrypt` / `sign` / `verify` method
- C# / Go / TypeScript も同型 API（Library 公開 API snapshot で生 key bytes 露出を deny）

## 単一の真（3 ファイル構成）

### `classes.yaml`（軸 key_class enum）
- class bundle 定義。class 名 → 5 dimension + `wrapped_by` 関係 + 不変条件 の純粋関数テーブル

### `scenarios.yaml`（軸 catalog）
- scenario × key_class / dimension 値 → assertion id のマトリクス
- 主要 scenario: `key_generation` / `rotation_cycle` / `crypto_shred_proves_unread` / `revocation_propagation` / `external_notary_attestation_chain` / `hsm_zeroize_audit` / `dpop_proof_of_possession` / `kek_threshold_ceremony`

### `backends.lock.yaml`（build artifact）
- 各 backend（OpenBao / HSM PKCS#11 / SPIRE / Cosign）の static 自己宣言を tier1 build script が集約して生成。手書き禁止
- 各 backend の `supports`（class 集合）と `constraints`（HSM partition / cluster topology / shamir threshold M-of-N）を宣言

## 5 層 defense-in-depth
- 層 A: compile（KeyHandle 必須引数化、生 key bytes 不可視）
- 層 B: lint / 公開 API snapshot
- 層 C: cross-class integration test（rotation / destruction）
- 層 D: runtime（HSM PKCS#11 / SPIRE / OpenBao audit log）
- 層 E: 外部公証 attestation（tamper evidence、HSM の audit event を独立 SoR に流す）

## CI 不変条件（merge 不可）
- 整合 1: `classes.yaml` の全 class が `scenarios.yaml` の matrix で覆われる
- 整合 2: `scenarios.yaml` の全 assertion id が、それを必要とする全 class × 全 backend で実装
- 整合 3: `backends.lock.yaml` で claim される class が `classes.yaml` に存在
- 整合 4: SDK / Library 公開 API として KeyHandle 以外の生 key bytes 露出ゼロ
- 整合 5: 全 audit hash chain root が外部公証 attestation を持つ
- 整合 6: KEK shamir threshold M-of-N が backends.lock.yaml と詳細仕様（[KEK Shamir 分散](../03_クロスカッティング適合仕様/02_KEK_shamir_distribution.md)）で双方向 lock
- 整合 7: dead spec 検出

## 1.0.0 ship blocker
- 5 key_class × 全 backend の完全 conformance green
- KEK shamir threshold ceremony の dry-run green
- 外部公証 attestation の chain of custody green
- crypto-shred の物理 unread property test green

## 採用しない設計
- 生 key bytes の SDK 公開 API 露出
- Secret 文字列の業務コード直接保持
- key_class dimension override
- HSM 単一 region 配置（KEK shamir M-of-N 必須）
- 自製 crypto（HSM PKCS#11 / WebCrypto / OS keychain の物理機構のみ）
- Vault BUSL（OpenBao MPL 2.0 のみ）
