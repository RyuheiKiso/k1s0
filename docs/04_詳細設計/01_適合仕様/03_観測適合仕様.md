# tier1 観測適合仕様（v1）

## 一文定義
- 観測適合仕様は、5 signal class（logs / metrics / traces / profiles / audit）× 4 dimension layer（core / tier1_ext / tier2_ext / tier3_ext）× trace_id を primary key とする cross-signal cross-tier 相関契約 + PII redaction policies の cross-product を機械可読な単一の真として固定し、OTel Collector + Weaver で物理 enforce する meta-axis である。

## 位置づけ
- 02_採用 OSS 一覧 が宣言する ClickHouse 一本化（log / trace の SoR）、04_提供機能カテゴリ Observability 系 4 カテゴリ、04_Library Companion 役割 A、tier2 / tier3 観測関連の規律が散在的に宣言する次の四つを、機械可読な単一の真として一箇所に固定:
  1. 5 signal class（logs / metrics / traces / profiles / audit）の SoR / 派生関係 / retention / queryability
  2. 4 dimension layer（core / tier1_ext / tier2_ext / tier3_ext）の namespace 所有権と合成順序
  3. trace_id を primary key とする cross-signal cross-tier 相関契約
  4. PII redaction policies の単一の真と各 tier 実装の整合
- 三軸（07 transport / 32 data / 39 client）と migration 軸（08）が「動く層」の真を担うのに対し、本仕様は「動いた事実の真」を担う対称軸

## 設計原則
- **signal は 5 class で固定**: logs / metrics / traces / profiles / audit のみ許容、新 signal の追加は破壊的変更
- **SoR と派生関係を一意に固定**: logs / traces / profiles / audit は ClickHouse、metrics は Prometheus の二 SoR 構成。派生 signal（exemplar / label 等）は SoR の query で再構成可能であることを property test で保証
- **dimension は 4 layer の合成として宣言**: core（OTel SC base）/ tier1_ext / tier2_ext / tier3_ext + Companion 拡張。OpenTelemetry Weaver で合成
- **trace_id を cross-signal cross-tier の primary key とする**: 業務コードが trace_id を手動で扱う経路を持たない
- **PII redaction は単一の真 + Collector 強制**: PII フィールドリストを `redaction.yaml` で 1 箇所に宣言、OTel Collector のプロセッサで物理削除
- **defense-in-depth は 5 層**: signal 宣言 / Weaver 生成 / Testcontainers ゴールデン値 / runtime（PII 物理削除 + trace_id 統一注入）/ storage 層 enforcement

## v1 signal class セット（5 class）

| signal | SoR | 投入経路 | retention | queryability | redaction |
|---|---|---|---|---|---|
| `logs` | ClickHouse `logs` table | OTel SDK → Collector → ClickHouse | 規制要件次第 | Apache Superset (SQL) | Collector で必須 |
| `metrics` | Prometheus | OTel SDK → Collector → Prometheus | 短期 + 月次 downsample | Perses (PromQL) | low cardinality required |
| `traces` | ClickHouse `traces` table（clickhouseexporter 投入、Jaeger v2 first-party storage で UI 提供） | OTel SDK → DaemonSet Collector → loadbalancingexporter（routing_key: traceId）→ tail-sampling Collector Deployment → clickhouseexporter | tail sampled | Jaeger v2（内蔵 CH storage、first-party）+ Apache Superset（SQL JOIN with logs） | Collector で必須 |
| `profiles` | Parca | Parca agent（eBPF / native pull） | 短期 | Parca UI | low cardinality required |
| `audit` | ClickHouse `audit` table | PostgreSQL `audit_local` → Audit relay → ClickHouse | 規制要件次第（10 年+） | Apache Superset (SQL) | PII 構造的不在（32 で担保） |

### 各 class の不変条件
- `logs`: 構造化 JSON のみ、`trace_id` を top-level field として持つ（attribute ではなく ClickHouse の indexed column）。PII は `redaction.yaml` rule で Collector が物理削除
- `metrics`: 高 cardinality 属性（`aggregate.id` 等）の attribute 化禁止。aggregate 単位の指標は traces / logs から SQL で集計。exemplar に `trace_id` 必須注入
- `traces`: W3C Trace Context 準拠。tier3 → tier2 → tier1 backend を貫く 1 trace に統合。tail-based sampling は OTel Collector の `tail_sampling` processor で実施
- `profiles`: Parca による Continuous Profiling。`trace_id` を Parca label として注入、特定 trace 起点の hot path 解析を可能にする
- `audit`: tier2 atomic 三表書込で `audit_local` に書込まれ、Audit relay が ClickHouse に転送（at-least-once + ReplacingMergeTree で idempotent）。hash chain（`hash_prev` / `hash_self`）が ClickHouse 側で再検証

## 観測 Collector の 2 段 pipeline

### 段 1（per-node DaemonSet, gateway role）
- SDK OTLP を受信、basic filtering（早期 PII redaction の一部、`trace_id` 注入の検査）
- 段 2 への転送は `loadbalancingexporter`（`routing_key: traceId`）で `trace_id` 単位に集約 Collector を選択（consistent hashing 必須）
- logs / metrics / profiles 経路は段 1 から直接 SoR（ClickHouse / Prometheus / Parca）へ送出

### 段 2（gateway-aggregator Deployment）
- `tail_sampling` processor を実行する Collector。同一 trace の全 span が同一 Pod に集約されることを段 1 の `routing_key` で保証
- 出口は `clickhouseexporter`（CNCF OTel Contrib）で ClickHouse `traces` table に投入。UI 経路は Jaeger v2（v1.50+、first-party、Apache 2.0）の内蔵 ClickHouse storage を採用
- HPA で水平 scale。`loadbalancingexporter` の hash ring re-shape 時の trace split は consistent hashing で最小化、残余の部分集約 trace は `dropped_partial_trace_count` metric で記録

単段（DaemonSet 単体で `tail_sampling` を完結する構成）は trace split を防げないため不可。

## v1 dimension layer（4 layer の合成スキーマ）

| layer | namespace prefix | 所有 tier | 例 |
|---|---|---|---|
| core | (OTel SC base) | OTel 上流 | `http.*` / `rpc.*` / `db.*` / `messaging.*` / `faas.*` |
| tier1_ext | `tier1.*` | tier1 | `tier1.bidi.*` / `tier1.transport.*`（`tls_version` / `cipher_suite` / `alpn`、Bidi 適合仕様 assertion 対象外）/ `tier1.oss.exposed.*` |
| tier2_ext | `tier2.*` | tier2 | `tier2.tenant.id` / `tier2.aggregate.id` / `tier2.business_event` / `tier2.aggregate_class` / `tier2.purpose` |
| tier3_ext | `tier3.*` | tier3 | `tier3.screen.id` / `tier3.interaction.kind` / `tier3.web_vitals.*` / `tier3.layer`（39 layer） |

### layer 合成の不変条件
- core 属性の rename / 削除を ext layer は行わない（OTel SC への準拠を破らない）
- tier2_ext は tier1_ext を参照、tier3_ext は tier2_ext を参照
- Companion 拡張は tier1_ext + tier2_ext のサブセットを生成定数として最小 NuGet で配布
- 全 layer は OpenTelemetry Weaver で各言語の定数コードを生成。app code は生成定数のみを使い、文字列リテラル直書きを CI で禁止

## v1 correlation contract（cross-signal cross-tier）
- primary key: `trace_id`（W3C `traceparent` の trace-id 部分、16 byte hex）
- 統一注入の原則: 全 signal が trace context 内で emit される場合、`trace_id` を必須属性として保持

| signal | trace_id 注入箇所 |
|---|---|
| `logs` | ClickHouse `logs.trace_id` 列（top-level、indexed） |
| `metrics` | Prometheus exemplar の `trace_id` label |
| `traces` | OTel span の `trace-id` field（自然に存在） |
| `profiles` | Parca label `"trace_id"` |
| `audit` | `audit_local.trace_id` 列 → ClickHouse `audit.trace_id` 列 |

### cross-tier propagation
- tier3（Web SPA / Companion）で生成または継承された `trace_id` が tier2 業務 API / Companion Gateway / tier1 backend を貫く
- 07_Bidi 適合仕様 transport adapter は trace context を各 transport で機械的にマップ
- 08_移行 Pair 適合仕様 の cutover 中も `trace_id` の連続性を保つ assertion を `test_matrix.yaml` に組む（`co_observability_continuity`）

### cross-signal join 契約
- logs と traces の JOIN: ClickHouse 側で `trace_id` 列の equi-join。Apache Superset から両 table を結合する SQL を tier3 / 業務担当が直接書ける
- metrics と traces の JOIN: exemplar の `trace_id` を起点に Perses から該当 trace に drill-down
- profiles と traces の JOIN: Parca label の `trace_id` を起点に該当 trace の hot path を表示
- audit と logs/traces の JOIN: `audit.trace_id` で他 signal と相関

### tier3 client 軸（39）との接続
- 39 が宣言する 4 layer（ST / OL / PQ / DR）の各 lineage 操作（rollback / promote / re-evaluate）に対応する span を tier3_ext で発行。`trace_id` が tier2 atomic 三表書込（32）まで貫通
- 39 `conflict_event` の各分岐は span event として記録され、BusinessConflict subtype は span attribute として保持

## v1 PII redaction policies（単一の真）

### PII field の宣言
- 業務語彙で「PII フィールド」と分類された属性を `redaction.yaml` で 1 箇所に列挙
- 列挙対象（例）: `tier2.actor.email` / `tier2.actor.phone` / `tier2.actor.full_name` / `tier2.aggregate.address` / `tier3.form.input.value`

### 適用箇所
- 物理削除は OpenTelemetry Collector のプロセッサ（`attributes` processor の `delete` action / `transform` processor の `delete_key` statement）で実施
- Library / Companion / app code に同等処理を持たせない

### actor 表現の固定
- actor 識別子は Keycloak subject（不可逆 ID、`sub` claim）のみ。氏名 / メール / 電話 / 端末 ID は signal に出さない

### audit signal は構造的に PII 不在
- `audit_local` の schema が PII 列を持たない（32 適合仕様 audit_local schema 参照）
- 「audit に PII を入れない」を runtime で守るのではなく schema レベルで物理的に不能にしている。本仕様の redaction layer は他 4 signal にのみ適用される

## 単一の真（5 ファイル構成）
- `signals.yaml`: signal class カタログ。signal_id → SoR / 投入経路 / retention / queryability / redaction の純粋関数テーブル
- `dimensions.yaml`: 4 layer の合成スキーマ宣言。layer × namespace × 所有 tier × 属性一覧
- `correlation.yaml`: cross-signal cross-tier propagation rule。`trace_id` 注入箇所 / cross-tier propagation rule / cross-signal join 契約
- `redaction.yaml`: PII field の単一列挙 + Collector processor 設定への射影
- `test_matrix.yaml`: Testcontainers + Collector でのゴールデン値 scenario カタログ

## 5 層 defense-in-depth
- 層 A: signal / dimension 宣言（`signals.yaml` / `dimensions.yaml`）
- 層 B: Weaver 生成 + lint（生成定数の使用強制、文字列リテラル直書き禁止）
- 層 C: Testcontainers + Collector でのゴールデン値テスト（`test_matrix.yaml`）
- 層 D: runtime（Collector プロセッサが PII 物理削除 + `trace_id` 統一注入）
- 層 E: storage 層（ClickHouse の column-level access policy / Prometheus exemplar / 監査保管期間 enforcement）

## CI 不変条件（merge 不可）
- 整合 1: `signals.yaml` / `dimensions.yaml` / `correlation.yaml` / `redaction.yaml` / `test_matrix.yaml` の参照整合（dangling 検出）
- 整合 2: SemConv attribute 名が OTel 公式 + tier1_ext / tier2_ext / tier3_ext の 4 layer namespace 内で衝突しない
- 整合 3: 全 signal で `trace_id` が必須注入経路を持つ
- 整合 4: 全 PII field が `redaction.yaml` に列挙され、Collector processor が delete を物理実行
- 整合 5: ゴールデン値テストで「PII を含む input → 出力に PII が残らない」property を全 signal で検証
- 整合 6: 文字列リテラル直書き（生成定数を使わない attribute 名）の検出は CI fail
- 整合 7: dead spec 検出（参照されない signal / dimension / propagation rule / PII field / scenario は CI fail）

## 1.0.0 ship blocker
- 5 signal class × 4 dimension layer の完全 coverage
- PII redaction property test 全 signal green
- 観測 Collector 2 段 pipeline の HPA + consistent hashing が production load で green
- `release_gate.lock.yaml` の observability cells 全 green

## 採用しない設計
- 単段 Collector（DaemonSet 単体で `tail_sampling` を完結する構成）
- 文字列リテラル直書きの attribute 名
- Library / Companion / app code に redaction 処理を分散
- 高 cardinality attribute（`aggregate.id` 等）を metric 化
- `audit` schema に PII 列を追加（schema レベルで物理拒否）
- Grafana / Tempo / Loki（AGPL-3）
- jaegertracing/jaeger-clickhouse community plugin（archive 済 + Jaeger v2 で plugin protocol 廃止）
