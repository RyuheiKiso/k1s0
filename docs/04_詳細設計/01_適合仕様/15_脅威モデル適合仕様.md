# 脅威モデル適合仕様（v1）

## 一文定義
- 脅威モデル適合仕様は、5 actor × 5 capability × 5 surface × 5 asset の cross-product として完全列挙される threat catalog の各 cell に対し、5 mitigation class のいずれかを必ず物理 pointer として bind し、全 13 軸 + meta + 自軸の defense-in-depth 層 D / E に bind 済みであることを 5 層 defense-in-depth + 13 項 CI 不変条件 + 13 件製造業 pack stress test で物理 enforce する meta-axis である。

## 位置づけ
- 13 軸 + meta（00 軸登録）の 14 軸目として、本仕様が tier1 / tier2 / tier3 / infra / data の各軸の defense-in-depth 層 D / E が宣言する物理 mitigation 機構（RLS FORCE / Kyverno admission / mTLS / cosign verify / cryptographic erasure 等）を threat model 下で cross-axis に集約する。
- canonical axis 06 (security) の 2 spec の一つ（脅威モデル = spec 15）。cap v1=20 中 19 / 20、残 1 スロット。
- 13 軸が「層別 × 機能別」軸であるのに対し、security は「脅威別 × 軸横断」軸として直交方向に位置する。

## 軸 class（5 class、actor 軸を primary key として採用）

| class | 対応する drill_class | primary defense_layers | 最低限の cross-axis | active mitigation 数 (v1 cap) |
|---|---|---|---|---|
| `v1_external_unauth` | red_team_table_top / external_pen_test | authn / boundary / WAF / supply_chain | tier1/10 / 06 / 14 | ≥ 30 |
| `v1_external_auth` | red_team_table_top | authz / RLS FORCE / rate limit / audit | tier2/32 / tier1/10 / 09 | ≥ 35 |
| `v1_insider_application` | red_team_live / chaos_failure_drill | mTLS / SPIFFE ID / capability scope / audit | 07 / 06 / 09 | ≥ 40 |
| `v1_insider_operator` | red_team_live / secret_compromise_drill | break-glass + audit / control-plane mTLS / step-up auth | infra01 / 11 / 09 | ≥ 35 |
| `v1_supply_chain` | supply_chain_drill / external_pen_test | cosign / SBOM / Tekton Chains / Trivy + Grype double-bound / build_provenance_class enum | 14 / 08 / infra01 / 17 / 11 | ≥ 30 |

- 全 5 actor class の active mitigation 総数 ≥ 170（v1）、cap 上限は v2 で +50 拡張

## 単一の真（5 yaml、うち 2 が build artifact）

### `classes.yaml`（軸 5 class enum、security/conformance/ 配下）
- actor / capability / surface / asset / mitigation の 5 enum 軸を宣言
- class 名は version prefix 固定（`v1_xxx`）、追加は purely additive

### `threat_model.lock.yaml`（build artifact 1）
- 生成器: `threat-catalog-builder`
- input: `classes.yaml` + 各軸 spec の defense-in-depth 層 D / E + `boundary_mitigation` section
- 出力: 5⁴ = 625 cell の row（unreachable cell の `explicit_unreachable=true` marking 含む）、各 cell に mitigation pointer ≥ 1
- 手書き禁止、CI fail

### `mitigation_bindings.lock.yaml`（build artifact 2）
- 生成器: `mitigation-binder`
- input: `threat_model.lock.yaml` + 13 軸 + meta の全 spec の build artifact + boundary_mitigation
- 出力: mitigation pointer ⇔ 物理 artifact の双方向 lock 表（`pointer_kind` / `ref` / `source_axis` / `source_layer`）
- 手書き禁止、CI fail

### `pii_classification.lock.yaml`（build artifact、本層管掌）
- 生成器: `pii-classifier`
- input: Apicurio Registry の全 subject + 各 column の `pii_class` 注釈 + tier2/22 / 28 / 06_tier2 の pii_class 規律
- 出力: column ↔ pii_class ↔ DEK class の三項関係

### `drill_progress.lock.yaml`（build artifact、本層 + インシデント対応 + 訓練が共有管掌）
- 生成器: `drill-runner`（Tekton job）
- input: `scenario_catalog.lock.yaml` + drill 実行ログ + audit_event の `v1_ir` fact
- 出力: drill_class 別 `last_green_at` / `next_due_at` / `cadence_status`

### 共通制約
- 全 yaml は CUE schema で type 検証
- 全 yaml は cosign signed snapshot として periodic に publish（hash chain root とも整合）
- drift 検出時は Argo CD が self-heal、build artifact ↔ runtime の divergence ゼロ

## 5 層 defense-in-depth（脅威モデル軸全体）

### 層 A: compile
- `threat_model.lock.yaml` の cell = 5⁴ で完全列挙（ビルド時に行数 check）
- mitigation pointer kind enum 検証（textual は cap 5%、boundary section は cap 0%）
- PII column の DEK class binding が tier1/11 階層内に存在
- scenario_catalog の全 threat_class coverage
- CUE 型 check（class enum / pointer kind / weight enum）

### 層 B: lint
- Conftest custom rule（Rego）: mitigation pointer の重複禁止 / textual cap / 軸別最低 mitigation 数 / coverage gap の zero-tolerance
- Semgrep meta-rule: threat_class が schema / policy に登場するときの命名整合
- Apicurio compatibility rule: `pii_class_only_strengthens`（PII class の弱化を breaking 判定）

### 層 C: integration test
- chainsaw / kuttl で全 admission policy（security 担当 23 policy）が intended state を block / pass
- Testcontainers で OpenBao + ClickHouse + Kafka + CloudNativePG を local 起動、PII access path の audit_event emit を end-to-end で確認
- hash chain divergence 試験（人為的 row 改竄 → CI 検出 verify）
- drill scenario の自動 replay（`red_team_table_top` 全 scenario）

### 層 D: runtime（cluster 上の actual enforcement）
- Kyverno admission webhook（25+ policy、[security 強制機構](../02_強制機構/06_security強制機構.md) 参照）
- Falco / Tetragon の常駐 detection
- cosign verify in admission（unsigned image deploy block）
- ClickHouse mutation block（audit_event UPDATE / DELETE 物理拒否）
- cert-manager / OpenBao の auto rotation
- Vector pipeline の PII redaction
- audit_event hash chain の online 検証（行 insert 時 prev hash 一致 check、ClickHouse MV）
- audit_ingest_gap_monitor（[09_audit_ingest_gap_monitor](../03_クロスカッティング適合仕様/09_audit_ingest_gap_monitor.md)）の常駐

### 層 E: 物理 enforcement
- cosign signature の cryptographic verification（Sigstore 標準、公開鍵の真正性）
- Ceph RGW Object Lock Compliance mode（root 権限でも archive 物理 delete 不可）
- OpenBao Transit + HSM-backed KEK（鍵 export 物理不可）
- audit chain hash の cryptographic forgery impossibility（SHA-256 / Blake3 等、ただし ingest gap は別経路で補完）
- mTLS / TLS 1.3 cipher suite OS 強制（weakcipher handshake reject）
- ClickHouse Replicated MergeTree + Keeper Raft（audit data の replication consistency 物理保証）

| stress 4 | `v1_insider_operator × v1_write × v1_control_plane × v1_audit_log`: cluster-admin 取得 → audit_event 改竄試行 → mutation block + hash chain divergence 検出 + on-call page |
| stress 5 | `v1_supply_chain × v1_write × v1_supply_chain_surface × v1_business_data`: compromised image push → cosign verify fail / Trivy critical detect → admission block + Harbor quarantine |
| stress 6 | secret_compromise_drill: 意図的に commit された secret → gitleaks pre-commit block / 万一 push されても trufflehog + Trivy secret + Falco の三重検知 → OpenBao revoke 完了 ≤ 30 分 |
