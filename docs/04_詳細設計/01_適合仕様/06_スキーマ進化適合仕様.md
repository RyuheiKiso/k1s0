# tier1 スキーマ進化適合仕様（v1）

## 一文定義
- スキーマ進化適合仕様は、6 schema_class × 5 dimension（schema_kind / compatibility_mode / deprecation_period / breaking_change_policy / registry_backend）の cross-product として宣言される schema catalog の各 instance に対し、proto / Avro / DDL / yaml / SemConv の 4+1 軸を `aggregate_qualified_name` 名前空間で束ね、cross-axis schema sync property を物理 enforce する meta-axis である。

## 位置づけ
- 02_採用 OSS 一覧 Buf / Apicurio Registry / Karapace / sqlx-cli / OpenTelemetry Weaver、01_Server 系 Proto 二層化、04_提供機能カテゴリ Schema Registry / Domain Event、tier2 表現手段 / 互換性ポリシー / 強制機構 / テナント分離適合仕様 / tier3 互換性ポリシーが散在的に宣言する schema_kind / 互換性 mode / deprecation lifecycle / breaking change policy / registry backend を、機械可読な単一の真として固定
- 「同 aggregate を表す proto / event / DB column / SemConv 属性が drift しない」cross-axis schema sync property を本仕様が単一所有

## 設計原則
- **schema_class は bundle**: class 1 値が他 4 dimension（`compatibility_mode` / `deprecation_period` / `breaking_change_policy` / `registry_backend`）を一意に導出
- **dimension override 禁止**
- **dead spec を CI で殺す**: classes / scenarios / registry backend、aggregate_qualified_name registry に登録された aggregate が 4 軸の少なくとも 1 軸からも参照されない場合も dead 扱い
- **単一の真は「位置」ではなく「導出関係」で守る**: 各軸が同名で同型の declaration を持つことを invariant とする
- **codegen 出力は build artifact とし手書き禁止**
- **defense-in-depth は 5 層**

## v1 schema_class セット（6 class）

| class | schema_kind | compatibility_mode | deprecation_period | breaking_change_policy | registry_backend |
|---|---|---|---|---|---|
| `v1_external_proto` | proto_external | BACKWARD | months_12 | major_only | buf_bsr |
| `v1_internal_proto` | proto_internal | NONE | not_applicable | additive_with_migration | buf_bsr_internal |
| `v1_event_avro` | event_avro | FULL | months_24 | major_with_dual_write | apicurio |
| `v1_db_ddl` | db_ddl | forward_backward_via_migration | not_applicable | additive_with_migration | sqlx_migrations |
| `v1_config_yaml` | config_yaml | BACKWARD | months_6 | additive_only | yaml_in_repo |
| `v1_otel_semconv` | otel_semconv | FULL | months_12 | additive_only | weaver |

### 各 class の不変条件と典型用途
- `v1_external_proto`: 01_Server 系 二層化の External 層 RPC / message。Companion 経由 .NET Framework や第三者 client が消費する wire 互換契約。BACKWARD（新 server が旧 client を破らない）、deprecation 12 ヶ月、breaking change は major version up のみ
- `v1_internal_proto`: 01_Server 系 二層化の Internal 層 RPC / message。tier1 内 / Backend-for-Library 内 / tier2 Service 間で消費。互換性は NONE（同期 deploy 前提、Argo Rollouts 連動）
- `v1_event_avro`: tier2 Domain Event の Apicurio Registry 上 Avro schema。FULL（双方向互換）、deprecation 24 ヶ月、breaking は major + dual_write
- `v1_db_ddl`: tier2/32 migration 由来 DDL。sqlx-cli + 32 の migration ヘッダで管理。`forward_backward_via_migration`（rolling upgrade window 互換性、NOT NULL 列追加は default 必須、column rename は二段階）
- `v1_config_yaml`: tier1 / tier2 / tier3 の config yaml（feature flag / quota / SLO / 業界 pack 定義 / route_atlas 等）。BACKWARD、deprecation 6 ヶ月
- `v1_otel_semconv`: 02_OSS OpenTelemetry Weaver で管理する SemConv tier1 拡張（業界 attribute / 業務 attribute 命名）。FULL、deprecation 12 ヶ月

## dimension の根拠
- `schema_kind` は backend dispatcher として最上位（proto は Buf BSR、Avro は Apicurio、DDL は sqlx migrations、yaml は repo 内、SemConv は Weaver）
- `compatibility_mode` は consumer の挙動を機械的に決める（BACKWARD / FORWARD / FULL / NONE / forward_backward_via_migration）
- `deprecation_period` は consumer の更新猶予を決める（external は長め、internal は短め、event は最長）
- `breaking_change_policy` は major version up の発動条件と migration toolchain の有無を決める
- `registry_backend` は schema の物理保管先と検証経路を決める

## derived dimension（field-level invariant）を独立次元にしない理由
- field-level の不変条件は class が定める `compatibility_mode` に従属
- field-level rule を独立 dimension にすると class 数が指数化するため、class が暗黙の不変条件として保持

## aggregate_qualified_name 名前空間（cross-axis 同型の鍵）
- 4 軸（5 軸）に跨る aggregate を表す共通名前空間: `<industry>.<domain>.<aggregate>`（例: `manufacturing.procurement.purchase_order`）
- 4 + 1 軸での declaration 形式:
  - proto: `package manufacturing.procurement.v1`
  - Avro subject: `manufacturing.procurement.purchase_order-value`
  - DDL: schema `manufacturing_procurement`、table `purchase_order`
  - yaml: ネスト key `manufacturing.procurement.purchase_order`
  - SemConv: attribute prefix `manufacturing.procurement.purchase_order.*`
- 4 軸の同 aggregate 名で field / type 同形を CI で検証

## 単一の真（3 ファイル構成）

### `classes.yaml`（軸 schema_class enum）
- class bundle 定義

### `scenarios.yaml`（軸 catalog）
- scenario × schema_class / dimension 値 → assertion id のマトリクス
- 主要 scenario: `breaking_change_detection` / `n_minus_1_compat_runtime` / `aggregate_qualified_name_sync` / `field_default_for_avro_full` / `migration_dual_write_window` / `semconv_deprecation_window` / `weaver_codegen_drift`

### `registries.lock.yaml`（build artifact）
- 各 registry backend（Buf BSR / Apicurio / Karapace / sqlx migrations / yaml repo / Weaver）の static 自己宣言

## 5 層 defense-in-depth
- 層 A: compile 時（codegen 出力のみ消費、生 schema 文字列なし）
- 層 B: lint（Buf breaking / Apicurio compat API / sqlx-cli plugin / Weaver validate / yaml schema validation）
- 層 C: cross-version integration test（n-1 / n+1 互換性）
- 層 D: registry runtime（Apicurio が違反 schema を reject）
- 層 E: cross-axis sync property（proto + DB + event + SemConv の同 aggregate 名で field / type 同形）

## CI 不変条件（merge 不可）
- 整合 1: `classes.yaml` の全 class が `scenarios.yaml` の matrix で覆われる
- 整合 2: `scenarios.yaml` の全 assertion id が registry backend ごとに実装
- 整合 3: `registries.lock.yaml` で claim される class が `classes.yaml` に存在
- 整合 4: aggregate_qualified_name の 4 軸（proto / event / DB / SemConv）同期 property green
- 整合 5: codegen 出力（proto → 各言語 stub、proto → Avro、proto → DDL ヘッダ、proto → SemConv schema）が build artifact、手書き diff は CI fail
- 整合 6: dead aggregate 検出（registry に登録された aggregate が 4 軸の 1 軸からも参照されない）
- 整合 7: dead spec 検出

## 1.0.0 ship blocker
- 6 schema_class × 全 registry backend の完全 conformance green
- aggregate_qualified_name 4 軸同期 property test green
- breaking change detection（buf breaking / Apicurio compat API）green
- Apicurio GitOps SoT（Argo CD reconcile）green（[apicurio_gitops_sot](../03_クロスカッティング適合仕様/03_apicurio_gitops_sot.md)）

## 採用しない設計
- 同 aggregate を真とする「片寄せ」（proto を権威、DDL を権威 のような）
- schema_class dimension override
- 手書き codegen 出力
- BACKWARD でない外部 wire（External Proto は BACKWARD 必須）
- breaking change の deprecation window 省略
