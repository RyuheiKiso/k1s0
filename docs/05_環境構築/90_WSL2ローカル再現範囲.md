# WSL2 ローカル再現範囲

## 一文方針

- WSL2 + kind + Docker Compose で本番スタックの 65–70% を再現できる。届かない壁は multi-region 冗長性 / Rook+Ceph raw block device / Yubikey KEK ceremony / 常駐 on-call プロセスの 4 点であり、これらは専用 Linux サーバなしに代替できない。

> **pre-P0 注記**: `src/` は P10 deliverable（pre-P0 時点で実体ゼロ）。src/ 依存手順は P10 完了後に有効。

## 再現できないこと

### 1. Multi-zone / multi-region 冗長性

**理由**: kind は1台の Linux ホスト上で Docker コンテナを node として起動する。物理的な zone / region 分離がなく、ネットワーク partition や zone 障害のシミュレーションが本番等価でない。

**ローカル近似**: kubefed または Argo CD multi-cluster で複数 kind cluster を擬似 federation できるが、IP routing が Docker ネットワーク内に閉じているため外部 BGP peering は不可。

**本番に必要なもの**: 別 AZ / 別リージョンのクラウドノード、または bare metal × 複数 DC。

### 2. Rook+Ceph（raw block device）

**理由**: Rook+Ceph は `/dev/sdX` 等の raw block device を要求する。WSL2 の仮想ディスクは loop device として見えるが Ceph OSD に割り当てると WSL2 の vhd layer との相性で I/O が不安定になる。

**ローカル近似**: MinIO（S3 互換）を Docker で起動し、backup 先ストレージとして使う。プライマリストレージには hostPath volume で代替。

**本番に必要なもの**: bare metal またはクラウドの block storage（AWS EBS / GCP PD）に Rook を直当て。

### 3. Yubikey PIV / KEK ceremony

**理由**: KEK shamir M-of-N ceremony は Yubikey PIV スロットへの書き込みを伴う。WSL2 から Yubikey へアクセスするには `usbipd-win` 経由の USB passthrough が必要だが、PIV 操作中の接続断でキーが破損するリスクがあり production 運用には不適。

**ローカル近似**: OpenBao `-dev` モードで shamir 手順の rehearsal（key share 生成 → unseal フロー）は体得可能。production KEK の生成は専用 air-gapped Linux マシン + Yubikey で実施。

**本番に必要なもの**: Windows から独立した Linux マシン + USB Yubikey（PIV 対応）。

### 4. 常駐 on-call プロセス

**理由**: WSL2 は Windows 再起動または `wsl --shutdown` で全プロセスが終了する。Alertmanager / Grafana / Backstage / SPIRE agent 等の常駐を前提とするサービスは、セッション切断で停止し SLO 監視の継続性が担保できない。

**ローカル近似**: 開発中の手順確認には `docker compose up` で都度起動すれば十分。

**本番に必要なもの**: systemd 管理下で常時稼働する専用 Linux サーバ（または Kubernetes + restart policy）。

## 代替手段早見表

| 本番要素 | ローカル近似 | 限界 |
|---|---|---|
| multi-region k8s | kind × 2 cluster（Argo CD multi-cluster） | BGP peering 不可 |
| Rook+Ceph | MinIO (docker) | オブジェクトストレージのみ |
| Yubikey KEK ceremony | OpenBao `-dev` で rehearsal | 本番鍵の生成は不可 |
| 常駐 Alertmanager | `docker compose up` 都度起動 | シャットダウンで失われる |
| MetalLB (LoadBalancer) | NodePort + port-forward で代替 | 外部 IP 割当なし |
| Calico BGP | Calico VXLAN mode | BGP peering なし |
| SPIRE (production mode) | SPIRE ローカル（join_token） | 外部 CA chain なし |

## 本番移行のパス

ローカル検証が green になった後、以下の順で本番スタックへ段階的に移行する。

1. **infra 軸**: cloud provider（AWS / GCP / Azure）または bare metal に Ubuntu 22.04 を展開し、kind の代わりに kubeadm または managed k8s（EKS / GKE / AKS）を使う
2. **data 軸**: Docker Compose の 5 サービスをそのまま k8s StatefulSet に変換し、Rook+Ceph または cloud block storage をバックエンドに切り替える
3. **security 軸**: air-gapped Linux マシンで Yubikey PIV への KEK shamir 書き込みを実施。cosign 鍵は hardware-backed に昇格
4. **ops 軸**: Alertmanager / Grafana を systemd または k8s Deployment として常駐化し、外部 DNS + LoadBalancer を割り当てる
5. **release**: `release_gate.lock.yaml` の全 98 cell が green になった後、cosign signed tag で 1.0.0 を打つ
