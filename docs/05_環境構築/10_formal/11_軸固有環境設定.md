# 軸固有環境設定

## 一文方針

- formal 軸固有の環境設定として、95 cell（proof_matrix 基底）proof_matrix の雛形 YAML 生成 / 5 proof_class それぞれ 1 spec の検証 / dual reviewer sign-off 演習（2 名でのレビューフロー確認）の 3 演習を完走することを必須とする。

## 演習 1: proof_matrix 雛形 YAML 生成

5 proof_class × 19 軸 = 95 cell（proof_matrix 基底）の proof_matrix 雛形を生成する。

```yaml
# proof_matrix_template.yaml
proof_matrix:
  version: "1.0"
  axes:
    - id: axis_07_bidi
      proof_classes:
        tla_plus: red
        dafny: red
        lean4: red
        kani: red
        cbmc: red
    - id: axis_08_migration_pair
      proof_classes:
        tla_plus: red
        dafny: red
        lean4: red
        kani: red
        cbmc: red
    # ... 残り 17 軸（19 軸全てを列挙する）
```

上記 YAML をスクリプトで生成する場合の例:

```bash
python3 -c "
axes = [
  'axis_07_bidi', 'axis_08_migration_pair', 'axis_09_observation',
  'axis_10_auth', 'axis_11_key_mgmt', 'axis_12_schema_evolution',
  'axis_13_slo', 'axis_14_oss_lifecycle', 'axis_15_tenant_capacity',
  'axis_32_tenant_isolation', 'axis_39_client_state',
  'infra01_cluster_topology', 'data01_data_integrity',
  'security15_threat_model', 'security16_build_provenance',
  'client15_sdk_distribution', 'ops15_ops_loop',
  'test15_test_discipline', 'formal15_formal_verification'
]
proof_classes = ['tla_plus', 'dafny', 'lean4', 'kani', 'cbmc']
print('proof_matrix:')
print('  axes:')
for ax in axes:
    print(f'    - id: {ax}')
    print('      proof_classes:')
    for pc in proof_classes:
        print(f'        {pc}: red')
" > proof_matrix_template.yaml
wc -l proof_matrix_template.yaml
```

## 演習 2: 5 proof_class の 1 spec 検証

各 proof_class につき 1 つの sample spec を検証し、全て pass することを確認する。

```bash
# TLA+（tlc）
tlc HelloSpec.tla -deadlock 2>&1 | grep -E "No error|error"

# Dafny
dafny verify Sample.dfy 2>&1 | tail -3

# Lean 4
lean Sample.lean 2>&1

# Kani
cargo kani 2>&1 | tail -3

# CBMC
cbmc cbmc_sample.c --bounds-check 2>&1 | tail -3
```

## 演習 3: dual reviewer sign-off 演習

proof_matrix の 1 cell を yellow → green に変更する際の dual reviewer フローを演習する。

1. 担当者 A（formal 軸エンジニア）が spec を検証し、pass を確認する
2. 担当者 A が PR を作成し、proof_matrix.yaml の該当 cell を `yellow` に変更する
3. 担当者 B（domain expert または別の formal 軸エンジニア）がレビューし、正当性を確認する
4. 担当者 B が PR を approve し、`green` に変更して merge する

演習では実際に GitHub の PR review 機能を使い、2 名の approve を確認する。LLM 単独での approve は禁止。
