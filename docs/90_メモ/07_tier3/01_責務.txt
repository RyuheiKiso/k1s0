============================================================
tier3 の責務（個別業務 UI と業務シナリオ所有）
============================================================

■ 1.0.0 出荷スコープ
  - 1.0.0 で出荷する tier3 群：製造業 pack（「06_tier2/01_責務」
    1.0.0 出荷スコープ節）を消費する代表 tier3 群（発注 / 検査 /
    FA など）。
  - 業界 pack の追加は tier2 が「06_tier2/03_業界拡張モデル」に
    従って行う。tier3 は対応する業界 pack の出荷後に新規 tier3 を
    追加する。
  - 1.0.0 段階で「業界横断専用の tier3」「業界 pack を跨ぐ汎用
    tier3」は出荷しない。tier3 は業界 pack を一つ消費する形態を
    既定とする。

■ 方針
  - tier3 は個別業務に特化した Web サイト・exe を提供する。
    プラットフォーム構成（「03_プラットフォーム構成」）における
    最上位の業務アプリケーション層に位置する。
  - tier3 は tier2 を一次消費し、業界横断 / 業界 pack の業務 API /
    業務資産（Domain Event / Workflow / 決定表 / 業務マスタ /
    DB schema）を、ユーザに対し業務語彙で表現する。
  - tier3 は tier1 Library / Companion / OSS クライアントを直接
    利用しない。tier1 が抽象化していない機能であっても、tier3 が
    独自に OSS をラップすることは禁止する（強制機構は「31_強制
    機構」を参照）。
  - tier3 は業務不変条件・整合性境界・認可規則を所有しない。これら
    は tier2 が所有し、tier3 は tier2 の override 拡張点を通じて
    UI 層の業務固有差分のみを表現する（「06_tier2/07_業務資産
    所有権」と整合）。

■ tier3 が所有するもの
  - 画面遷移シナリオ（業務シナリオ単位の画面フロー / wizard /
    多画面トランザクション境界）。
  - フォームレイアウト（入力欄 / グルーピング / バリデーション
    表示位置 / キーボード移動順 / 補助入力）。
  - 業務エラーの UI 表現（tier2 が返す業務エラー型を、ユーザが
    取れるアクションとして表現する）。
  - 帳票のレイアウト（PDF / 印刷向けレイアウト、明細・集計の
    可視配置。集計値そのものは tier2 が提供する）。
  - 業務イベントへのユーザ通知 UI（toast / banner / 一覧の差分
    強調）。発火条件は tier2 の Domain Event に従う。
  - UI 上のキーボード操作 / ショートカット / IME 補助 / アクセシ
    ビリティ補助。
  - UI 認可結果の反映（活性 / 非活性 / 表示 / 非表示の制御。認可
    判定そのものは tier2 / tier1 が行う）。

■ tier3 が所有しないもの
  - 業務資産 :
      - Domain Event の schema 定義 / 発行責務
      - Workflow / Saga 定義 / 補償処理
      - 決定表 / 業務ルール
      - 業務マスタ構造
      - DB schema
      - API 振る舞い（バリデーション / 業務不変条件 / 認可規則）
      - これらは「06_tier2/07_業務資産所有権」に従い tier2 が所有
        する。
  - infra への直接アクセス :
      - DB / Kafka / Temporal / Keycloak / Valkey / Object
        Storage 等への直接接続は禁止する。
      - tier3 はすべて tier2 の API（Library / Service）経由で
        アクセスする（「23_tier2消費方針」参照）。
  - tier1 Library / Companion / Gateway の直接消費 :
      - tier3 は tier1 を直接消費しない。tier1 の横断的共通要素
        （自動計装 / 認証 token 取得などの runtime）に乗ることだけ
        は許容する（「02_位置づけ」参照）。
  - 業界横断概念 / 業界 pack 概念の独自定義 :
      - 業務語彙は tier2 から借りる。tier3 が独自の業務語彙を
        作って画面に出すことは禁止する（「03_非提供スコープ」参照）。

■ 背景・狙い
  - tier3 担当はジュニア級エンジニア（「04_推奨の開発体制」）。
    業務不変条件 / 整合性境界 / セキュリティ制御を tier2 が守り、
    tier3 は表現に集中することで、業務品質を構造的に底上げする。
  - tier3 が業務資産を所有すると、別の tier3 が同じ業務を別の
    実装で扱うことになり、整合性 / 監査 / 規制対応が破綻する
    （「06_tier2/01_責務」背景・狙い節と整合）。
  - 業務処理の正解は一つに集約し、tier3 は「同じ業務処理を異なる
    操作シナリオで表現する場」とする。

■ 抽象化レベル別 影響範囲
  - tier2 の業務抽象化レベル（「06_tier2/04_抽象化レベル」）に応じ
    て、tier3 が追従する範囲が異なる。
      - Lv 業界横断 : tier2 が提供する横断業務 API（通知 / 監査 /
        承認 / 帳票 / マスタ管理 等）の UI 表現。tier2 のマイナー
        変更時、tier3 は override 部の追従のみで済む。
      - Lv 業界共通 : 業界 pack 内で共通する業務語彙（製造業で
        あれば「設備」「ロット」「検査結果」等）の UI 表現。tier3
        は override 部 + 該当ドメイン参照部のみ追従。
      - Lv 業界固有 : 業界 pack 内ドメイン固有の業務語彙（FA /
        調達 / 検査 各ドメイン）の UI 表現。tier3 は当該ドメイン
        利用部の追従のみで済む。
      - Lv テナント固有 : テナント差分は tier2 の override / 設定
        で吸収される。tier3 のコード変更を伴わない（マスタ・ルール・
        権限の差分のみ）。
  - tier3 の追従責務は「tier2 が提供した拡張点に対する UI 表現の
    更新」に限定する。業務不変条件側に踏み込む追従は禁止する。

■ 業務管理機能との分離
  - マスタ管理 / 監査検索 / 緊急対応 / schedule 編集 / partner
    連携設定などの業務管理機能は tier3 業務 UI に載せない。
    Backstage プラグインとして提供される業務管理 UI に分離する
    （詳細は「26_業務管理UI境界」参照）。
  - tier3 は「日々の業務操作」のための UI に責務を絞る。

■ 非責務
  - 詳細は「03_非提供スコープ」を参照。
