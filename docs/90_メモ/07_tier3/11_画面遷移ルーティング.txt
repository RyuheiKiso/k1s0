============================================================
tier3 の画面遷移とルーティング
============================================================

■ 方針
  - tier3 は SPA / native アプリのいずれであってもルーティング
    規約を統一する。bounded context に対応する path 構造とし、
    deep-link / 認証認可ガード / 未保存変更警告 / アプリ間遷移を
    既定で扱う。
  - ルーティング規約はデザインシステムと同様に tier3 横断で配布
    する。アプリごとに独自実装しない（「31_強制機構」整合）。

■ SPA routing 規約
  - path 構造 : `/<bounded-context>/<resource>/<id>` を既定とする。
      例：/procurement/purchase-orders/123e4567-...
          /fa/production-instructions/abcdef-...
          /inspection/inspection-results/uuid
  - bounded-context は tier2 のドメイン分割（「06_tier2/05_ドメイン
    分割方針」）と一致させる。
      製造業 pack : fa / procurement / inspection / common
  - resource は tier2 の aggregate 名のケバブケース複数形。
  - id は aggregate ID（UUID v4 既定）。「06_tier2/18_API設計規約」
    整合。
  - sub-resource :
      - 一覧 : /<bounded-context>/<resource>
      - 新規 : /<bounded-context>/<resource>/new
      - 詳細 : /<bounded-context>/<resource>/<id>
      - 編集 : /<bounded-context>/<resource>/<id>/edit
      - 関連 action : /<bounded-context>/<resource>/<id>/<action>
        例：/procurement/purchase-orders/<id>/cancel
  - クエリパラメタは検索 / フィルタ / ソート / pagination cursor
    （「13_検索一覧UX」整合）に限定する。状態遷移を query で表現
    しない（戻るボタンの挙動を予測可能にするため）。

■ 認証ガード
  - 未ログインで保護 route にアクセスした場合は認証フローへ
    redirect する（「25_認証認可マルチテナント」整合）。
  - redirect 後の元 path を query に保持し、認証完了後に復元する
    （ディープリンク到達性を維持）。
  - 認証 token 失効 : Adapter 層が 401 を検出したら現在 path を
    保持して認証 flow へ。フォーム dirty 状態は IndexedDB 下書き
    に保存（「08_状態管理」「12_フォーム設計規約」整合）。

■ 認可ガード
  - 各 route に「必要 capability」を宣言する。Application 層の
    ルート定義に capability メタデータを持たせる。
  - tier2 の ABAC 結果（「06_tier2/22_権限モデル」「18_権限UI制御」
    整合）で capability を満たさない場合 :
      - 進入禁止画面へ遷移し、業務語彙で拒否理由を提示。
      - 単純な 403 ページにせず、関連する操作（権限申請 / 戻る）
        への導線を提示する。
  - 認可結果 cache : tier2 の policy 評価結果を short-TTL（例 60s）
    で cache。テナント切替 / actor 切替で即時 purge。
  - tenant 切替 : Authorization context の tenant_id 切替時は全
    cache を purge し、現 path を tenant_id に対する認可で再評価
    （別テナントで invalid なら top へ）。

■ ディープリンク
  - aggregate ID 直接アクセスを既定でサポートする。URL を共有
    すれば他者が同じ aggregate を開ける（認可 OK の場合）。
  - eventual consistency 中の挙動 :
      - 直近作成された aggregate ID が read model に未反映の場合、
        書込モデル直接取得 API（「06_tier2/24_読み取りモデル方針」
        厳密 consistency 整合）にフォールバックする。
      - それでも未存在なら「読み取りモデル反映待ち」を業務語彙で
        表示し、自動再試行（exponential backoff）。 5 回失敗後に
        404 扱い（「16_リアルタイム更新UX」整合）。
  - 404 vs 403 の区別 :
      - 認可上見えない aggregate は 404 として扱う（存在情報の
        漏洩防止、「32_セキュリティアーキテクチャ」整合）。
      - 自テナントで存在しない aggregate も 404。

■ 未保存変更の破棄警告
  - dirty form を持つ画面から離脱しようとする場合は確認モーダルを
    表示する（「12_フォーム設計規約」整合）。
  - 確認モーダルの選択肢 :
      - 「下書きを保存して移動」（IndexedDB へ保存、「08_状態管理」
        整合）
      - 「破棄して移動」
      - 「キャンセル」（既定フォーカス）
  - ブラウザの beforeunload にも hook して、タブ閉じ / リロード
    でも警告を表示する。
  - 自動保存が完了していれば警告を出さずに移動する選択肢を
    Application 層の dirty 判定に組み込む。

■ 履歴 / 戻るボタン
  - history に積むのは「業務的に意味のある進行」のみ :
      - 一覧 → 詳細 → 編集 のような業務フローは積む。
      - フィルタ条件変更 / ソート変更 / pagination は積まない
        （連打で history を埋めない、replace を既定）。
  - モーダル / ドロワー / popover は履歴に積まない（既定）。
    Esc / 背景クリック / 戻るボタンで閉じる挙動を統一する。
      - 例外 : full-screen モーダルとして表現する大きな業務フォー
        ム（添付プレビュー / 業務帳票編集等）は履歴に積む。
  - tab / accordion 切替も履歴に積まない（軽量な情報切替）。
  - 戻るボタンで dirty form 警告を出すか否かはアプリ側で宣言。
    既定は「警告を出す」。

■ ブレッドクラム
  - bounded context 内の階層を表示する。
      例：調達 > 発注 > 発注番号 PO-2025-0001
  - bounded context 名 / resource 名は tier2 業務語彙の i18n キー
    から取得（「21_アクセシビリティ国際化」整合）。
  - 各セグメントを click すると一覧画面へ遷移。最終セグメント
    （現在画面）は click 不可。
  - aggregate ID は人間可読な業務識別子（発注番号等）に置換して
    表示する。tier2 の表示用 alias を使用。

■ アプリ間遷移
  - tier3 アプリ間（同一テナント内の業務アプリ間）の遷移は
    「27_複数tier3連携」と整合させる。
  - SSO : tier1 Keycloak のセッションを共有し、再ログインを
    要求しない。
  - aggregate ID 共通 : 別 tier3 アプリへの遷移時は同一 aggregate
    ID を path で渡す。
      例：tier3 procurement-app の発注詳細から
          tier3 inspection-app の検査結果一覧へ
          /inspection/inspection-results?purchase-order-id=...
  - アプリ起動 :
      - Web 同士 : 同一 origin であれば SPA 内遷移、別 origin なら
        full page navigation（authentication context は cookie /
        token 渡し）。
      - native（Tauri / WPF）⇄ Web : custom URL scheme で起動 +
        deep-link 渡し。
  - 認証コンテキストの伝播は tier1 認証コンテキスト伝播の枠組み
    （「05_tier1/04_Library」横断的共通要素整合）に従う。

■ バージョン違いへの対応
  - tier3 バンドル更新時の遷移挙動 :
      - 古いバンドルを長時間開いているユーザーは server から最新
        version 情報を inactive 中に取得し、ナビゲーションタイミ
        ングで「新しいバージョンが利用可能」を非 blocking に提示。
      - 強制更新が必要な場合（破壊的 schema 変更等）は遷移時に
        フルリロード。dirty form は IndexedDB に保存してから更新。
  - tier2 SDK の major version 切替期間中は両方を呼べる Adapter
    層実装で対応（「07_内部アーキテクチャ」DI / 注入経路整合）。
  - サーバ側 410 Gone（旧 major 退役）を検出したら強制更新画面へ
    遷移し、ユーザーに対応バージョンへの切替を案内する。

■ ルーティングのテスト方針
  - 単体 :
      - route 定義と必要 capability の宣言整合性をテスト。
      - 認証ガード / 認可ガードの redirect 先を fake adapter で
        検証。
  - 統合（Playwright 等） :
      - 主要 route のディープリンク到達性。
      - dirty form での破棄警告動作。
      - tenant 切替時の cache purge と再認可。
      - eventual consistency 中の 404 への自動再試行。
  - visual regression : 進入禁止画面 / 404 / バージョン不一致
    画面のスクリーンショット差分。
  - 詳細は「29_テスト方針」整合。
