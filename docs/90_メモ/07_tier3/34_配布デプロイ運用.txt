============================================================
tier3 の配布 / デプロイ / 運用
============================================================

■ 方針
  - tier3 は Web SPA / デスクトップ exe / レガシー（.NET
    Framework + Companion）の 3 形態を 1.0.0 で出荷対象とする
    （「04_アプリケーション形態」整合）。それぞれの配布 /
    デプロイ / 運用方式を本ファイルで定める。
  - tier3 の配布 / デプロイは tier1 / tier2 と同じ GitOps 経路
    に乗せ、ロールバック / 監視 / サプライチェーン保全を共通
    の基盤で扱う。tier3 個別の運用基盤を作らない。
  - 1.0.0 出荷では「Web ホスティング / exe 自動更新 / レガシー
    配布 / バンドル CI 検査 / GitOps」を全面に揃える。

■ Web SPA の配信
  - 静的ホスティング :
      - tier1 が運用する内部 CDN / オブジェクトストレージ
        （Ceph RGW / MinIO、「05_tier1/04_Library」L3 Object
        Storage 整合）に静的アセットを配置する。
      - HTML / JS / CSS / 画像はすべて静的アセットとして配信
        し、SSR は採用しない（「07_内部アーキテクチャ」整合）。
  - immutable assets + content hash :
      - JS / CSS のファイル名に content hash を付与し
        （app.[hash].js）、Cache-Control: immutable を付ける。
      - HTML は no-cache（SPA 起動エントリ）。
      - cache busting を URL レベルで行い、互換性ポリシー
        （「30_互換性ポリシー」整合）の参照側 stale 問題を
        構造で塞ぐ。
  - service worker による更新管理 :
      - PWA 対応端末では service worker 経由でアセット cache
        を制御する（「22_端末オフラインデバイス」整合）。
      - 更新検出時は skipWaiting + clientsClaim を Adapter 層
        で制御し、業務操作中に強制リロードしない。
      - 新版検出は通知 UI（「17_通知UI」「22_端末オフライン
        デバイス」整合）でユーザに reload を促す。
  - feature flag / カナリアリリース（任意）:
      - flagd / GO Feature Flag（「05_tier1/04_Library」L2*
        Feature Flag 整合）で機能ごとの roll-out を制御する。
      - テナント別 / ユーザ群別の段階的 roll-out が可能。
      - 1.0.0 出荷時の必須機能ではないが、利用経路を template
        に含める。

■ デスクトップ exe 配布
  - インストーラ署名 :
      - Windows : コードサイニング証明書（cert-manager
        運用、「02_採用OSS一覧」整合）で署名。
      - macOS : 必要に応じて Apple Developer ID で署名 +
        notarize。
      - 署名なし配布は 1.0.0 出荷では許容しない。
  - 自動更新 :
      - Tauri は自前 update endpoint + Ed25519 署名を使う。
        Electron 系を採用する場合は Squirrel / electron-
        updater を使う（「05_言語スタック」整合）。
      - 差分配布（delta update）でダウンロード量を削減。
      - 自動更新の検証は内部レジストリの署名済みアセットに
        対して行う。
  - サイドバイサイド更新 :
      - 業務中断回避のため、業務操作中の強制再起動は禁止。
      - 新版を別パスに展開し、次回起動時に切替える。
      - 切替前後で IndexedDB / Outbox queue のスキーマ互換性
        を保持する（「30_互換性ポリシー」整合）。
  - OS 別配布チャネル :
      - 内部配布のみ。Microsoft Store / Mac App Store 等の
        公的 store を使わない（企業内利用前提、「02_位置づけ」
        整合）。
      - 配布経路はテナントの内部レジストリ経由で行う。

■ レガシー（.NET Framework）配布
  - 形式 :
      - ClickOnce / MSI のいずれか。テナント運用に応じて選択。
      - 内部配布のみ（公的 store 配布なし）。
  - Companion 同梱 :
      - OpenTelemetry .NET Auto-Instrumentation（CLR Profiler
        アタッチ）+ Companion runtime を MSI に同梱する
        （「36_レガシー資産統合」整合）。
      - 環境変数 / DLL 配置は MSI が自動設定する。
  - 自動更新 :
      - ClickOnce 経由は ClickOnce 更新機構。
      - MSI 経由は Group Policy / 内部配信ツール（SCCM /
        Intune 等、テナント運用に依存）。
      - 自動更新の有無は テナント運用責任、tier3 側からは
        update 検出 banner を提示する経路を提供する。

■ バンドル戦略
  - code splitting / lazy load :
      - route 単位の chunk 分割を既定とする（「11_画面遷移
        ルーティング」整合）。
      - 業務 pack 単位 / 大型コンポーネント（PDF viewer 等）
        は dynamic import で遅延読込。
  - Web Vitals 目標値 :
      - LCP < 2.5s（事務所 PC + 工場 LAN 想定）。
      - INP < 200ms。
      - CLS < 0.1。
      - 目標未達の画面は roll-out を保留する。
  - bundle size budget :
      - 初回 JS bundle は gzip 後 250 KB 以内を目標とする。
      - 累積 JS は gzip 後 1 MB 以内。
      - Web Vitals + size budget の CI 検査を merge 条件と
        する（「31_強制機構」整合）。
  - tree-shaking :
      - tier2 SDK の不要部分を含めない。barrel export 経由の
        過剰依存を ESLint で禁止する。

■ バージョン整合
  - tier2 SDK バージョンとの整合 :
      - tier3 が依存する tier2 SDK の minor バージョンは、
        tier2 互換ポリシー（「06_tier2/13_互換性ポリシー」
        整合）に従って互換維持される。
      - tier3 は SDK の minor をいつでも更新できる。
  - メジャー違いの並走 :
      - tier2 が major 跨ぎの場合、新 / 旧 SDK の並走は最長
        6 ヶ月（「30_互換性ポリシー」整合）。
      - 同一テナント内で複数 tier3 が異なる SDK major で動作
        することは、並走期間内に限り許容（「27_複数tier3連携」
        整合）。
  - tier1 Library / Companion :
      - Web SPA は tier1 frontend Library のバージョン整合性
        を維持。Companion はレガシー側で同等。

■ ロールバック
  - Web SPA :
      - 内部 CDN 上の旧バージョンを即時切戻し可能とする
        （URL の content hash により旧版が残っているため）。
      - ロールバック判断は監視（次節）で自動誘発するか、
        運用者が手動誘発する。
  - デスクトップ exe :
      - 自動更新サーバから前 stable を再配信する経路を維持。
      - クライアント側にも 1 つ前のバージョンを保持し、即時
        切戻し可能にする（インストーラ）。
  - レガシー :
      - ClickOnce / MSI ともに前バージョンを内部レジストリに
        保持し、再インストールでロールバック可能にする。

■ GitOps
  - tier1 / tier2 と整合 :
      - Argo CD（または同等 Operator）で manifest をロールア
        ウトする（「06_tier2/09_Service運用方針」ライフサイ
        クル節整合）。
      - tier3 manifest は Web SPA 配信用 ConfigMap、デスク
        トップ exe 自動更新サーバ ConfigMap、レガシー配信用
        manifest を含む。
  - リポジトリ構成 :
      - アプリリポジトリと manifest リポジトリを分離（GitOps
        標準構成）。
      - manifest リポジトリは Backstage Software Template
        （「35_開発者体験」整合）から自動生成する。

■ 環境別配布
  - 開発 / ステージング / 本番 :
      - 各環境別に CDN / 自動更新サーバ / レガシー配信元を
        分離する。
      - 環境識別はビルド時に埋め込み、起動時に差し替え不可
        （誤接続事故の防止）。
  - デバッグ機能の本番無効化 :
      - 認可 debug endpoint（「35_開発者体験」整合）/ 開発時
        の RUM 全量送信 / debug ログ等は本番ビルドから物理的
        に除去する（dead code elimination）。
      - 本番ビルドが debug 機能を含んでいないことを CI で
        検査する（「31_強制機構」整合）。

■ 監視 / アラート
  - ロールアウト中の監視 :
      - クラッシュ率 / Web Vitals 異常 / RUM 異常を tier1
        観測基盤で監視（「33_観測可能性」整合）。
      - 監視メトリクスが閾値超過した場合、Argo CD の
        progressive roll-out 機構で自動 pause / 自動 rollback。
  - アラート :
      - ロールアウト中の異常検出は page アラートとして
        オンコール（「06_tier2/27_信頼性運用準備」アラート
        方針整合）。
  - 配布先別の異常 :
      - Web SPA / exe / レガシーで異なる失敗パターンを
        識別可能にする（version 属性 + 配布形態 attribute）。

■ 配布物の供給経路
  - 内部レジストリ唯一化 :
      - tier3 の Web SPA アセット / exe インストーラ /
        レガシー MSI を内部レジストリ（Harbor / 内部 CDN）
        にのみ配置する（「31_強制機構」整合）。
      - 開発者個別端末から外部経路で配布されることを物理
        遮断する。
  - レジストリの認可 :
      - tier3 配布物は Keycloak の認可で取得経路を制御。
        テナント別の取得制限を可能にする。

■ サプライチェーン
  - Cosign 署名 :
      - すべての配布物（Web SPA bundle / exe / MSI）に対して
        Cosign 署名を付与する。
      - 配布時の検証で署名不一致は配信を拒否する。
  - Trivy / SBOM :
      - 配布物の SBOM（CycloneDX）を生成し、配布物と同梱。
      - Trivy で脆弱性スキャンを CI で実施し、Critical /
        High 検出は merge / release を block する。
      - 「02_採用OSS一覧」[6] サプライチェーン / セキュリ
        ティ整合。

■ 1.0.0 出荷時の対応範囲
  - Web ホスティング / exe 自動更新 / レガシー配布 / バンドル
    CI 検査 / GitOps / Cosign 署名 / SBOM / 監視 / 環境別配布 /
    ロールバックを 1.0.0 で揃える。
  - feature flag / カナリアの運用化は出荷後の DX / 運用チーム
    が継続改善する。
