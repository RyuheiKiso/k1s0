============================================================
tier3 の業務カスタマイズ粒度（テナント別カスタマイズの境界）
============================================================

■ 方針
  - テナント別 / 業界別 / ユーザ別の差分は、tier2 の override /
    設定 / マスタ機構を経由して表現する（「06_tier2/04_抽象化
    レベル」「06_tier2/07_業務資産所有権」整合）。tier3 のコード
    分岐 / branch を増やす方法は禁止とする。
  - 差分表現を tier3 のコードに散らせると、テナント追加 / 業界
    pack 追加で tier3 の保守コストが線形に増え、互換性ポリシー
    （「30_互換性ポリシー」）の責任分界が崩壊する。差分は構造
    で受ける。
  - 1.0.0 出荷物として「階層別差分の表現手段の固定」を強制機構
    （「31_強制機構」整合）で担保する。

■ 階層別の差分表現手段
  - 業界横断 → 業界共通 :
      - tier2 業務 API の差そのもの。
      - tier3 は業界 pack 別に実装する（製造業 pack 用 tier3 と
        他業界 pack 用 tier3 を別アプリとして構築、「06_tier2/
        03_業界拡張モデル」整合）。
      - 同一 tier3 で複数業界をスイッチ表示する設計は禁止。
  - 業界共通 → 業界固有 :
      - tier2 のドメイン別 API の差。
      - tier3 はドメイン別 module で実装する（「07_内部アーキ
        テクチャ」整合）。FA / 調達 / 検査の差は同一 tier3 内
        の module 分割で吸収。
  - 業界固有 → テナント固有 :
      - tier2 の拡張点 override / マスタ / 設定で表現
        （「06_tier2/04_抽象化レベル」テナント固有 Lv 整合）。
      - tier3 は override 実装と UI 表現のみを担当。
  - テナント固有 → ユーザ固有 :
      - クライアント側設定 / preferences で表現
        （「08_状態管理」整合）。
      - 言語 / タイムゾーン / 通知設定 / 表示密度 / 既定タブ等。
      - ユーザ固有差分が業務不変条件に影響しないことを担保する。

■ 表現手段の選択
  - コード分岐（if tenant == X）:
      - 禁止する。CI で検出する（「31_強制機構」整合）。
      - tenant_id によるコード分岐は不変条件を腐敗させ、互換
        性ポリシーの保証範囲を崩す。
  - 設定（テナント設定）:
      - 業務 UI からは編集不可。業務管理 UI から編集する
        （「26_業務管理UI境界」整合）。
      - 設定値はテナントマスタとして tier2 が保持する。
  - マスタ（業務マスタ）:
      - tier2 マスタ管理 API で CRUD する（「06_tier2/10_提供
        機能カテゴリ」マスタ管理整合）。
      - テナント別に CRUD された値が業務 API の振る舞いに
        反映される。
  - override（拡張点）:
      - tier2 拡張点を tier3 が override 実装する（「24_override
        実装規約」整合）。
      - 不変条件は override 不可。

■ ブランディング / テーマ
  - ロゴ / カラー / 略称 :
      - デザイントークンの override で表現（「09_デザインシス
        テム」整合）。
      - tier3 が独自テーマを class / inline style で書かない。
        tokens を override する形で行う。
  - 機能 ON/OFF :
      - テナント設定 + 認可（「18_権限UI制御」整合）の組合せで
        表現する。
      - 機能 OFF の状態は UI から該当ボタン / メニュー / 画面を
        非表示にする（disable 表示は禁止、誤解の温床）。
  - 業務語彙 :
      - テナント別の用語差（例：「発注」を「発注書」と呼ぶ等）
        は i18n の resource override で表現する（「21_アクセシ
        ビリティ国際化」整合）。

■ 業務 entity 拡張
  - schema 拡張 :
      - tier2 が base schema を提供し、tier3 が override schema
        を提供する形態（「06_tier2/07_業務資産所有権」整合）。
      - 既存属性の削除 / 型変更は不可（不変条件、override 不可）。
      - 追加属性は前方互換に限る。
  - 追加バリデーション :
      - tier2 拡張点で表現する（「24_override実装規約」整合）。
      - 業務不変条件を緩める方向の override は禁止。
  - 追加表示フィールド :
      - tier3 UI で表示する。カスタムフィールドの動的レンダリ
        ング機構を tier3 共通 UI コンポーネントとして提供する
        （「09_デザインシステム」整合）。
      - フィールドの順序 / グループ化はテナント設定で制御する。

■ ワークフロー差分
  - 承認ルート / 通知先 / 補償 Activity :
      - tier2 拡張点 override で表現（「06_tier2/07_業務資産
        所有権」整合）。
      - tier3 は override 実装と UI 表現のみを担当する。
      - Workflow 骨格 / 補償処理の不変条件は override 不可。
  - 承認段数 :
      - テナント設定として表現。tier3 は段数に応じて段階表示
        を生成する（「14_状態遷移UI」承認段階表示整合）。
  - 通知先解決 :
      - 組織図に応じた通知先解決ロジックを override する。

■ 業界 pack の追加
  - 新業界 pack の tier3 :
      - tier2 が業界 pack を追加した時、tier3 は当該業界の業務
        UI を「新規 tier3」として構築する。
      - 既存 tier3 を改造して新業界対応するのではなく、業界
        pack 単位で別 tier3 を立てる（「27_複数tier3連携」整合）。
  - 既存 tier3 への影響 :
      - 既存業界 tier3 は業界 pack 追加によって変更されない。
        業界横断層の API が業界中立性（「06_tier2/03_業界拡張
        モデル」整合）を保つことが前提。

■ override で表現できない差分
  - 設計不足とみなす :
      - override で表現できない差分は「tier2 拡張点の設計不足」
        とみなし、tier2 拡張点を再設計する。
      - tier3 でコード分岐を増やして吸収しない。
  - 再設計の手順 :
      - tier3 担当が tier2 担当に拡張点追加 / 改修を要求する。
      - tier2 が拡張点を追加した上で、tier3 が override 実装
        する（互換性ポリシーに従い major / minor を判断、
        「06_tier2/13_互換性ポリシー」整合）。
  - 緊急回避 :
      - 業務影響が即時の場合の緊急回避は emergency_override
        （「06_tier2/22_権限モデル」整合）で対応する。回避後は
        正規の拡張点に戻すことを必須とする。

■ カスタマイズの ABI / API 安定性
  - tier2 minor 上げで silently 壊れない :
      - tier3 の override 実装が tier2 minor バージョンアップ
        で動作不能になることを防ぐ（「30_互換性ポリシー」
        「06_tier2/07_業務資産所有権」契約 test 整合）。
      - 拡張点の公開シグネチャ snapshot を tier2 が CI で守る。
  - tier3 の override 実装の互換性 :
      - tier3 が拡張点規約に従って override している限り、
        minor 上げでの silent 破壊は禁止。tier2 が違反を検出
        した場合、tier2 側で互換 shim を提供する。
  - major 跨ぎ :
      - tier2 major 跨ぎは override 移行 toolchain（「06_tier2
        /13_互換性ポリシー」整合）で支援する。
      - tier3 は移行期間中に override 実装を更新する。

■ カスタマイズと監査
  - 全カスタマイズは監査対象 :
      - テナント設定変更 / マスタ編集 / override 実装 deploy
        は監査ログ（「06_tier2/14_業務エラー監査コンプライア
        ンス」整合）に記録する。
      - 「誰がいつ何を変えたか」が業務管理 UI から検索可能。
  - tier3 が監査ログを抑制しない :
      - override 実装で監査ログ emit を skip するのは禁止
        （「06_tier2/07_業務資産所有権」override 禁止範囲整合）。

■ 1.0.0 出荷時の対応範囲
  - 階層別差分表現手段の固定 / コード分岐の禁止検査 / ブラン
    ディング override / schema 拡張 / Workflow 差分 / 業界 pack
    追加手順 / 設計不足の正規ルート / ABI 安定性 を 1.0.0 で
    揃える。
