============================================================
tier3 の非同期処理 UX
============================================================

■ 方針
  - tier2 の API 形態（「06_tier2/18_API設計規約」LRO 節）に対応
    して、所要時間ごとに UX を分ける。tier3 が独自に長時間処理を
    sync で待たせる経路は禁止する（ブラウザ deadline / モバイル
    スリープで容易に破綻するため）。
  - 業務的に重要な完了は通知として届ける（「17_通知UI」整合）。
    画面に張り付かなくても結果が届くことを既定とする。
  - 失敗時の再実行 / キャンセル経路は必ず提示する。「黙って
    再試行」「黙って失敗」は業務 UI として許容しない。

■ 所要時間別 UX
  - 同期 RPC（数秒以内）:
      - スピナー + ボタン disable で完了まで待つ。
      - 200ms 未満で確定するなら spinner 表示自体を抑制する
        （ちらつき防止）。
      - timeout は tier2 SLO（p99 < 500ms）+ ネットワーク余裕
        を加味し、UI 側 deadline を 5 秒〜10 秒程度で設定する。
  - 中時間（数秒〜数分）:
      - 進捗バー（determinate 可なら %、不可なら indeterminate）
        + cancel ボタン。
      - tier2 が同期 RPC で Workflow 起動 + 結果待ちを受け持つ
        ケース（「06_tier2/18_API設計規約」LRO 中時間ケース）に
        対応する。
      - 画面遷移は許容しつつ、進行中ジョブを通知センター
        （バックグラウンドタスク表示）に登録する。
  - 長時間（数分以上）:
      - tier2 の非同期 LRO パターンを利用する。Operation
        オブジェクトを subscribe（Server-Streaming）または
        polling で追跡する。
      - 画面に張り付かなくても完了通知が届く前提とする
        （「17_通知UI」連動）。

■ 進捗の表示
  - 進捗率（progress %）:
      - tier2 の Operation が percent_complete を返す場合のみ
        表示する。返さない場合は indeterminate に倒し、勝手に
        % を捏造しない。
  - 推定残り時間（ETA）:
      - tier2 から返る場合のみ表示する。
      - クライアント側で経過時間から推定して表示するのは禁止
        （業務 UI では誤誘導になりやすい）。
  - 段階表示:
      - 多段の Workflow（「発注確定 → 与信確認 → 在庫引当 →
        出荷指示」等）では現在段を示す。
      - 段階情報は tier2 が Operation の中で宣言したものに
        限る（tier3 が独自に段階を発明しない）。

■ ページ遷移しても継続
  - 進行中ジョブはアプリ全域の通知センター（または
    バックグラウンドタスク表示エリア）に登録する。
  - ページ遷移しても subscription は中断せず、関連画面に戻った
    時に最新進捗を再表示する。
  - 完了した過去ジョブは一定数（または一定時間）保持し、結果
    詳細を再閲覧できるようにする。

■ 完了通知
  - in-app 通知（toast / banner）で完了を知らせる。重要度は
    「17_通知UI」優先度に従う。
  - 業務 UI 上の状態（「14_状態遷移UI」）も自動更新する
    （subscription 受信または明示的 refetch）。
  - 通知 click で関連 aggregate にディープリンクする
    （「11_画面遷移ルーティング」整合）。

■ 失敗時の再実行 UI
  - tier2 失敗レスポンスの分類（「19_業務エラーUX」）に従って
    分岐する:
      - 業務的失敗（DomainError / ValidationError /
        BusinessConflict）: 修正のうえ再実行 / 操作を取下げる
        の二択を提示。
      - システム失敗（一時的）: 再試行ボタンを提示する。
  - idempotency-key の扱い:
      - 同一意図の再試行 → 同じ Idempotency-Key を再利用する
        （tier2 サーバ側で結果が cache されている。「06_tier2/
        18_API設計規約」冪等性節）。
      - 別意図の新規発行 → 新しい Idempotency-Key（UUID v4）を
        払い出す。
      - UI 上は「同じ操作を再試行」と「新しい操作として実行」を
        ボタン文言で区別する。

■ ユーザによるキャンセル
  - tier2 LRO の Cancel エンドポイント（Workflow cancel、tier1
    Temporal 経由）を呼ぶ。
  - キャンセル送信後の状態は「キャンセル要求中」を経て、tier2
    から CANCELLED 確定が返ってから「キャンセル済み」表示に
    遷移する（即時 CANCELLED 表示は禁止する）。
  - キャンセル不能な段階（補償処理中等）に到達済みの場合は
    その旨を業務語彙で表示し、業務管理者連絡導線を提示する。

■ 長時間 Workflow の状態確認 UI
  - tier3 業務 UI で確認可能なのは「自身が起動した Workflow」
    に限定する。テナント全体の Workflow 一覧 / 他者起動分の
    検索は業務管理 UI スコープ（「26_業務管理UI境界」）。
  - 自身関与の進行中 Workflow は通知センター / マイページ的な
    集約画面で一覧表示する。
  - Workflow の手動 signal / 手動補償（tier1 Temporal 機構）も
    業務管理 UI スコープであり、tier3 業務 UI からは利用させ
    ない（「06_tier2/27_信頼性運用準備」Workflow 運用節と整合）。

■ バッチ処理（複数 entity 一括処理）
  - 複数 entity の bulk 起動 / bulk 補償等のバッチ処理は業務
    管理 UI スコープ（「03_非提供スコープ」「26_業務管理UI境界」
    「28_運用UI」整合）。
  - tier3 業務 UI は単発の業務操作のみを扱う。例外的に bulk が
    必要な場合（自身の Draft 一括破棄等）に限り、tier2 が宣言
    した bulk API を消費する形で提供する。

■ 失敗詳細表示と支援情報
  - tier2 のエラーレスポンスから recovery_hints を取り出し、
    業務語彙で次アクションを提示する（「19_業務エラーUX」整合）。
  - 詳細 / trace_id 等は折り畳みで提示し、サポート問合せに
    そのまま添付できるようにする。
  - 失敗時のフォーム入力値は失わない。再入力させない
    （「12_フォーム設計規約」整合）。

■ 再開（resume）のクライアント取扱
  - 長時間 streaming（subscription / 大量結果）の再接続には
    tier2 の resume_token を利用する（「06_tier2/18_API設計規約」
    Streaming resumable 節）。
  - 接続断検知 → 自動再接続 → resume_token で取り溢れ防止、を
    Adapter 層に集約する（「07_内部アーキテクチャ」整合）。
  - 再接続中は UI に「接続再確立中」表示を出し、ユーザに状態を
    伝える（「16_リアルタイム更新UX」整合）。

■ deadline / timeout の業務語彙化
  - サーバ deadline 超過は「処理に時間がかかっています」など
    業務語彙で表示する（生の deadline_exceeded / 504 を見せない）。
  - 該当 Operation はバックグラウンドで継続している可能性が
    あるため、通知センターで結果到達を待つ導線を提示する。
