============================================================
tier3 のセキュリティアーキテクチャ
============================================================

■ 方針
  - tier1 / tier2 のセキュリティ機構（OIDC / mTLS / Secret
    管理 / サプライチェーン / WAF / CSP）の上で、tier3 固有
    のクライアントサイド attack surface への対策を本ファイル
    で束ねる。
  - 個別文書（「18_権限UI制御」「20_添付帳票UX」「22_端末
    オフラインデバイス」「25_認証認可マルチテナント」「31_
    強制機構」「33_観測可能性」「36_レガシー資産統合」）に
    散在するセキュリティ要素を、本ファイルで全体像として
    集約する。
  - tier3 は業務エンドユーザのブラウザ / 端末に最も近い層で
    あり、攻撃者が直接到達しうる surface を多数持つ。本ファ
    イルはそれを脅威モデルとして列挙する。

■ 脅威モデル（クライアント側 surface）
  - (1) ブラウザに表示されるすべての UI（XSS / clickjacking
    / UI redress）
  - (2) クライアント側ストレージ（localStorage / IndexedDB /
    cookie / OS keychain）
  - (3) third-party script / SBOM（依存パッケージ）
  - (4) postMessage / BroadcastChannel / 拡張機能との境界
  - (5) アップロード / ダウンロード（添付、「20_添付帳票UX」
    整合）
  - (6) WebUSB / Web Bluetooth / Web Serial 等のデバイス
    API
  - (7) Companion 経由レガシー（「36_レガシー資産統合」整合）
  - 各 surface に対し、STRIDE 分類で脅威を列挙し、緩和策と
    残留リスクを明文化する（tier2 と同枠、「06_tier2/28_セ
    キュリティアーキテクチャ」整合）。

■ 主要脅威と緩和策
  - XSS（Cross-Site Scripting）:
      - フレームワーク既定の自動 escape を有効に保つ。
      - innerHTML / dangerouslySetInnerHTML の使用を lint
        で禁止。
      - テンプレート injection 検査（「20_添付帳票UX」整合）。
      - ユーザ生成コンテンツは sanitize ライブラリで通す
        （DOMPurify 等）。
  - CSRF（Cross-Site Request Forgery）:
      - SameSite=Lax cookie の利用（SameSite=Strict は Keycloak
        SSO redirect 戻りで session cookie が落ちるため不採用、
        「25_認証認可マルチテナント」整合）。
      - custom header X-CSRF-Token（fetch のカスタムヘッダ送出）
        を必須化。
      - double-submit token を併用。
      - サーバ側で Origin / Referer の二重検査必須（許可された
        Origin / Referer 以外は 403 reject、Envoy Gateway / tier1
        Server で物理 enforce）。
  - CSP（Content Security Policy）:
      - strict CSP（nonce / hash ベース）を採用。
      - unsafe-inline / unsafe-eval は禁止（「31_強制機構」
        層 11 整合）。
  - clickjacking:
      - X-Frame-Options DENY を設定。
      - frame-ancestors 'none' を CSP で宣言。
  - subresource integrity:
      - 第三者 CDN を使う場合は SRI 必須。
      - 既定では内部 CDN のみを使用する。
  - postMessage:
      - origin 検証を必須とする。
      - target を明示し、'*' を使わない（「27_複数tier3連携」
        shared state の取扱節整合）。
  - 開いた window / target=_blank:
      - rel="noopener noreferrer" を必須化。
      - 別タブから opener にアクセスされる経路を防ぐ。

■ クライアント側 Secret
  - API Key を bundle に直接埋込まない。クライアントに送出
    する secret は持たない設計を既定とする。
  - OAuth token は httpOnly cookie / OS keychain に保管する
    （「25_認証認可マルチテナント」整合）。
  - localStorage に PII / token を置かない（「31_強制機構」
    層 5 整合）。
  - 一時的な操作 token（CSRF token 等）は sessionStorage に
    限り許容するが、ライフサイクルを最短化する。

■ ブラウザ拡張機能との境界
  - 業務 UI が拡張機能の DOM 改変前提で動作することを想定
    しない。
  - 拡張機能による DOM 注入を検出した場合の挙動は規定しな
    い（拡張機能はユーザ起動の責任）。
  - 業務 UI 自身は拡張機能 API（chrome.*, browser.*）を
    呼ばない。

■ 添付ファイル攻撃面
  - Content-Disposition / Content-Type 検査:
      - アップロード時に MIME / マジックナンバーを検査
        （tier2 受入時のウイルススキャンと整合、「06_tier2/
        28_セキュリティアーキテクチャ」整合）。
      - SVG / HTML inline 表示を禁止（「20_添付帳票UX」整合）。
  - ダウンロード時:
      - URL 署名 + 期限を必須化。
      - 認可確認をダウンロード直前にも実施（直リンクからの
        漏洩を防ぐ）。
      - Content-Disposition: attachment で開かせる。

■ third-party 依存管理
  - SBOM 必須（CycloneDX 形式、「31_強制機構」層 13 整合）。
  - Cosign 署名 / Trivy 継続スキャン / 内部レジストリ唯一化
    （「31_強制機構」層 12 / 13 整合）。
  - CVE SLA :
      - tier2 と整合（Critical 48h / High 7d / Medium 30d /
        Low 次回計画 release）。
      - 「06_tier2/28_セキュリティアーキテクチャ」CVE 対応
        SLA 節整合。
  - 依存 OSS のライフサイクル監視 :
      - tier3 が直接依存する OSS（UI フレームワーク / lint /
        build ツール）は tier3 リポジトリで個別監視。

■ セッション固定 / セッション切替
  - ログイン後の session ID を再発行する（セッション固定
    攻撃の防御）。
  - ロール切替 / テナント切替時にもセッションを再発行する。
  - 一定時間のアイドル後に自動ログアウトする（テナント設定
    で時間を調整可能、「25_認証認可マルチテナント」整合）。

■ ログ / RUM への PII 漏洩防止
  - クライアント側で発生する error / RUM 情報に PII を含め
    ない（「33_観測可能性」整合）。
  - エラーメッセージを送信する前にクライアント側で redact
    する（フィールド名のみ送信、値は伏字）。
  - URL / referrer に PII が含まれる場合は送信前に scrub
    する。

■ 同意管理 / GDPR cookie consent
  - RUM / 解析 cookie の利用にはユーザ同意を取得する
    （「33_観測可能性」整合）。
  - 同意管理 UI はテナント別ブランディングで提供する
    （「09_デザインシステム」整合）。
  - 同意拒否時は RUM / 解析 cookie を発行しない。業務遂行に
    必須な技術的 cookie のみを発行する。

■ ペネトレーションテスト
  - 1.0.0 リリース前の最終確認として実施する（tier2 と同枠、
    「06_tier2/28_セキュリティアーキテクチャ」ペネトレーシ
    ョンテスト節整合）。
  - 年 1 回の第三者監査を継続する。
  - 内部 red team 演習（半期 1 回）を tier3 開発チーム外の
    セキュリティ担当が実施。

■ emergency_override 中の追加保護
  - emergency_override 中の業務 UI 表示は「18_権限UI制御」
    整合の追加バナー / 操作監査を行う。
  - 期間内の全操作は詳細監査エントリ emit 対象。
  - emergency_override 起動 / 解除自体は業務管理 UI 経由
    （「28_運用UI」整合）であり、tier3 業務 UI からは行わ
    ない。

■ 暗号アジリティ
  - tier1 / tier2 の TLS / 署名スイートに追従する
    （「06_tier2/28_セキュリティアーキテクチャ」暗号アジリ
    ティ節整合）。
  - クライアント側で暗号スイートを固定しない。ブラウザ /
    OS の TLS スタックに任せる。
  - PQC（post-quantum cryptography）への移行可能性を維持
    する設計。

■ セキュリティヘッダの強制
  - CSP（strict、nonce / hash）
  - HSTS（max-age=31536000; includeSubDomains; preload）
  - X-Content-Type-Options: nosniff
  - Referrer-Policy: strict-origin-when-cross-origin
  - Permissions-Policy（不要な API を明示無効化、camera /
    microphone / geolocation 等）
  - X-Frame-Options: DENY
  - 上記は tier3 配信レイヤで強制し、CI で検査する
    （「31_強制機構」層 11 整合）。
