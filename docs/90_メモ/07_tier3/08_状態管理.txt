============================================================
tier3 のクライアント状態管理
============================================================

■ 方針
  - tier3 のクライアント状態管理は「サーバ状態とクライアント状態
    の分離」を最上位原則とする。両者を区別せずに 1 つのストアに
    押し込む実装は禁止する（cache invalidation / 楽観更新 / リア
    ルタイム更新の責務が混線するため）。
  - サーバ状態は tier2 業務 API レスポンス / Domain Event
    subscription / 集計 read model（「06_tier2/24_読み取りモデル
    方針」整合）に由来する。クライアントは「サーバ状態の cache」
    として扱い、真は常に tier2 側にあるとする。
  - クライアント状態は UI ローカルな揮発状態（フォーム編集中 /
    モーダル開閉 / 選択範囲 / ウィザード進行 / アンドゥスタック）
    に限定する。
  - 本ファイルは方針定義に留め、Server Truth / Optimistic Local /
    Pending Queue / Draft の 4 layer 分離、決定論的衝突解決 tree、
    BusinessConflict subtype による UI 分岐の 1:1 固定、永続化と
    PII 取扱の機械可読仕様は「39_クライアント状態適合仕様」に分離
    する。Application 層 reducer・lint・headless browser test・
    WebCrypto runtime のいずれも 39 が宣言する 4 つの YAML を共通
    入力とする。

■ サーバ状態管理
  - 推奨ライブラリ :
      TypeScript : TanStack Query
      C# Blazor  : 同等の query キャッシュライブラリ（または独自
                   wrapper を Adapter 層に持ち、TanStack Query の
                   API 形に揃える）
      Rust       : 同等の async cache（leptos query 等）
  - キャッシュキー : tier2 業務 API の RPC 名 + tenant_id +
    aggregate ID + クエリパラメタ。tenant_id をキー先頭に含めて
    テナント間混線を機械的に防ぐ（「25_認証認可マルチテナント」
    整合）。
  - stale-while-revalidate を既定とする。stale 中は古い値を表示
    しつつバックグラウンドで再フェッチ。
  - eventual consistency 中の挙動 : 直近の書込で即時 read 必要な
    場面は「06_tier2/24_読み取りモデル方針」厳密 consistency に
    該当する API を選択する。tier3 は API 種別を Application 層
    で使い分ける。
  - エラーハンドリング :
      - DomainError / ValidationError / BusinessConflict /
        AuthorizationDenied を区別して保持（「06_tier2/14_業務
        エラー監査コンプライアンス」業務例外 taxonomy 整合）。
      - retry はネットワーク / 5xx に限定。業務エラーは retry
        しない（「19_業務エラーUX」整合）。

■ クライアント状態管理
  - 推奨ライブラリ : 軽量グローバルストア（Zustand / Jotai /
    Pinia / 各言語等価物）。Redux 等の重量フローも禁止しない。
  - ストアは feature 単位で分割する（features/<domain>/store/）。
    グローバル単一ストアは禁止しない（「グローバル vs ローカルの
    判断基準」節参照）。
  - クライアント状態に該当する例 :
      - フォーム編集中の dirty state（「12_フォーム設計規約」整合）
      - モーダル / ドロワー / ポップオーバの開閉
      - 一覧画面の選択範囲 / ソート / フィルタ条件
      - ウィザード / 多段ステップの進行位置
      - アンドゥ / リドゥスタック
      - 一時的な UI hint（tooltip 表示位置等）

■ 楽観更新
  - 状態変更 RPC（POST / PUT / DELETE 相当、「06_tier2/18_API
    設計規約」整合）に対し、ユーザー応答性を上げるため楽観更新
    を既定とする（「16_リアルタイム更新UX」整合）。
  - 手順 :
      - mutation 開始時に query cache に楽観値を反映。
      - tier2 へ送信。Idempotency-Key を付与（「06_tier2/18_API
        設計規約」冪等性節整合）。
      - 成功 : サーバ確定値で cache を上書き。Domain Event 由来
        の最終値が後追いで届いたら再上書きされる。
      - 失敗 : cache を rollback。エラーは「19_業務エラーUX」に
        従って presentation。
  - BusinessConflict 検出 : tier2 が version 不一致で
    BusinessConflict を返した場合（「06_tier2/24_読み取りモデル
    方針」並行制御整合）、楽観値を rollback し、最新サーバ状態を
    refetch、ユーザーに「他者が先に更新した」旨を提示する。
    自動再送は行わない（silent な意味論変化を避ける）。

■ リアルタイム更新と cache invalidation
  - tier2 が Server-Streaming で配信する Domain Event を tier3 が
    subscribe し（「06_tier2/18_API設計規約」Streaming 節整合）、
    該当 query を invalidate する。
  - invalidation のキー対応 :
      - <Aggregate>Created    : 一覧 query を invalidate
      - <Aggregate>Confirmed  : 該当 ID の詳細 + 一覧を invalidate
      - <Aggregate>Cancelled  : 該当 ID の詳細 + 一覧を invalidate
      - <Aggregate>Modified   : 旧 ID + 新 ID + 一覧を invalidate
        （modified_from / modified_to 連鎖、「06_tier2/19_状態
        遷移パターン」整合）
  - subscribe は Application 層に集約する。Presentation 層が
    直接 subscribe することは禁止する（unmount でリーク発生
    回避）。
  - 切断 / 再接続 : Companion 経由クライアントでは tier1 Companion
    の resume_token で透過的に再開（「05_tier1/04_Library」
    Companion 役割 B 整合）。tier3 アプリは onMessage / send 形の
    API しか見えない。

■ 永続化
  - 用途別の使い分け :
      - localStorage : UI 設定（テーマ / 言語 / 一覧の列順 /
        ソート条件）。サイズ小・同期 API・PII 不可。
      - IndexedDB : フォーム下書き / オフラインキャッシュ /
        添付ファイル一時保管。サイズ中〜大・非同期 API・PII 不可。
      - OS keychain（Tauri / native） : リフレッシュトークン /
        デバイスバインド token のみ。アプリで生成する Secret は
        ここに置かない（tier1 OpenBao 経由を原則とする、「32_
        セキュリティアーキテクチャ」整合）。
  - PII 不可の例外なし : 氏名 / メール / 電話 / 住所等の PII を
    クライアントストレージに永続化することは禁止する（「06_tier2
    /14_業務エラー監査コンプライアンス」PII 取り扱い整合）。
  - 暗号化 : IndexedDB / localStorage の保存値は WebCrypto + デバ
    イスバインド鍵で暗号化する。鍵は OS keychain に保持。
  - 期限切れ : 認証 token 失効と同時に永続化された業務データを
    purge する hook を Application 層に置く。

■ フォーム下書き保存
  - 編集中フォームを定期的に IndexedDB に保存し、再起動 / クラッ
    シュ後に復元可能とする（「12_フォーム設計規約」自動保存節
    整合）。
  - 保存粒度 : aggregate ID + form_id + tenant_id + actor_id を
    キーとする。tenant 切替 / actor 切替で別空間として扱う。
  - 競合解消 : 復元時にサーバ状態の version と保存時 version を
    比較し、ずれていたら復元 / 破棄をユーザーに選択させる。
    silent な上書きは行わない。
  - 保存データの purge :
      - Confirmed 遷移成功時に該当 form の下書きを purge。
      - Idempotency-Key の TTL（24 時間、「06_tier2/18_API設計
        規約」冪等性整合）超過後は警告表示の上で破棄。

■ グローバル vs ローカルの判断基準
  - グローバルストアに置くもの :
      - 認証 / 認可状態（current actor / tenant_id / role）
      - テーマ / 言語 / アクセシビリティ設定
      - グローバル通知（toast queue、「17_通知UI」整合）
      - リアルタイム接続状態（接続中 / 再接続中 / 切断）
  - ローカル（component / hook）に閉じるもの :
      - 単一画面のフォーム編集状態
      - 単一一覧の選択 / フィルタ
      - モーダル / ドロワーの開閉
  - 判断基準 : 「他の画面 / コンポーネントから参照される必要が
    あるか」。なければ component-local を既定とする。グローバル
    に置くと test と reasoning の負担が増えるため、必要最小限に
    留める。

■ tier3 内部の状態管理 override 拡張点
  - 業界 pack / テナント別の override は features/<domain>/store/
    内の slice 拡張点で表現する（「24_override実装規約」整合）。
  - 楽観更新の有効 / 無効、永続化対象、cache invalidation キーの
    既定値は tier3 SDK 側で固定し、override は features ごとの
    挙動差分に限定する（silent な挙動変化防止）。
