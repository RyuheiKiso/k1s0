============================================================
tier3 業務 UI と業務管理 UI の境界
============================================================

■ 方針
  - 「06_tier2/23_管理境界」のクライアント側境界規約を tier3 側で
    定める。tier3 業務 UI と業務管理 UI を明確に分離し、両者は別
    API surface / 別 UI として扱う。
  - tier3 は「日々の業務操作」のための UI に責務を絞る（「01_責務」
    業務管理機能との分離整合）。マスタ管理 / 監査検索 / 緊急対応 /
    schedule 編集 / partner 連携設定などの業務管理機能は Backstage
    プラグインとして提供される業務管理 UI に分離する。

■ 業務 UI と業務管理 UI の責務分担
  - 業務 UI = tier3 が提供 :
      - 業務エンドユーザー向けの日常操作（発注 / 検査記録 / 進捗
        確認 / 通知受領 等）。
      - 業界 pack ごとに固有の業務シナリオ UI を tier3 が実装する。
  - 業務管理 UI = tier2 が Backstage プラグインとして提供 :
      - 業務管理者向けのマスタ / ルール / Workflow 設定 / 監査検索 /
        緊急対応 UI（「06_tier2/23_管理境界」運用 UI 整合）。
      - tier2 が業界横断 / 業界 pack ごとに Backstage プラグインを
        配布する。

■ 二系統の API surface
  - 業務 API :
      - tier3 が消費する。proto package は tier2.<pack>.<domain>.v1
        等。
      - 路径 : /v1/...（「06_tier2/18_API設計規約」整合）。
      - tier3 業務 UI からのみ呼出する。
  - 業務管理 API :
      - 業務管理 UI（Backstage プラグイン）から消費される。
      - proto package は tier2.<pack>.admin.v1（「06_tier2/23_管理
        境界」管理 API の分離整合）。
      - 路径 : /admin/v1/...。
      - tier3 業務 UI からは呼ばない（後述、CI で禁止）。

■ tier3 業務 UI に載せない機能
  - マスタ編集（参照は可、後述）
  - 決定表編集
  - Workflow 設定（cron / 承認ルート）
  - 監査検索（業務管理者がテナント全体の監査エントリを検索する経路）
  - 通知履歴一覧（自身分は可、テナント全体は不可、後述）
  - 失敗ジョブ再実行
  - 緊急対応（emergency_override 起動 / 解除、Workflow 手動補償、
    マスタ緊急更新 等）
  - partner 連携設定（外部システム統合 endpoint / 認証情報設定）
  - schedule 編集（cron / バッチタイミング）
  - これらは「06_tier2/23_管理境界」運用 UI 節と整合し、Backstage
    プラグイン側に配置する。

■ マスタ参照と編集の境界
  - 業務 UI では :
      - マスタ参照は可（業務操作で必要な品目 / 仕入先 / 拠点 等の
        マスタ情報の表示・選択）。
      - マスタ編集は不可（テナント運用責任の編集は業務管理 UI で
        実施）。
  - 業務 UI から「マスタ編集」を要求する経路を提示する場合、deep
    link で業務管理 UI に遷移させる（後述）。
  - 業務 UI 内に inline マスタ編集ダイアログを置かない（境界違反
    のため、CI で禁止）。

■ 業務管理 UI への deep link
  - tier3 業務 UI から業務管理 UI へのリンク提示は許容する（権限
    あり時のみ表示）。
      例：「この品目マスタを編集する」リンクを Backstage プラグ
          インの該当画面に飛ばす。
  - リンクは tier3 SDK で抽象化された URL ビルダ経由で生成する
    （業務管理 UI のルート / バージョンを tier3 が直接知らない）。
  - 権限なしの user には deep link を非表示とする（「18_権限UI
    制御」整合）。

■ ロール体系の分離（「18_権限UI制御」「06_tier2/22_権限モデル」整合）
  - 業務 API ロール（tier3 業務 UI 用）:
      例 : manufacturing.procurement.buyer /
           manufacturing.inspection.inspector
  - 業務管理 API ロール（業務管理 UI 用）:
      例 : cross_industry.tenant_admin /
           cross_industry.master.admin /
           cross_industry.audit.read
  - 両系統は別ロールとして管理され、同一ユーザに両系統が付与される
    こともあるが、UI 上の操作可否は系統別に判定される。
  - tier3 業務 UI は業務 API ロールに基づいて活性 / 非活性を判定
    する。業務管理 API ロールの有無で業務 UI の操作可否を変えない
    （業務管理 API ロールを持つユーザでも業務 UI 上は通常ユーザと
    同等の操作可能範囲とする）。

■ 通知履歴の取扱
  - 自身分の通知履歴 : tier3 業務 UI で表示可（「17_通知UI」整合）。
      例 : 自分が受信した toast / banner / 業務通知の履歴一覧。
  - テナント全体の通知履歴 : 業務管理 UI 側に分離する。
      例 : テナント内全 user への通知配信統計 / 失敗履歴。
  - 「自身分」の判定は actor_id == request.actor_id を tier2 が
    フィルタする。tier3 がクライアント側で全件取得して絞り込む
    実装は禁止する（「23_tier2消費方針」整合）。

■ 業界 pack 別の業務管理 UI 拡張
  - tier2 が業界 pack ごとに Backstage プラグインを提供する（製造業
    pack / 将来の業界 pack）。
  - tier3 はそこに業界固有 UI を追加しない（業界固有の業務管理 UI
    は tier2 業界 pack の責務）。
  - tier3 が業務管理 UI を独自に作る経路を持たない（Backstage
    プラグインを tier3 が提供することを禁止する）。

■ プラットフォーム運営者と業務管理者の境界
  - プラットフォーム運営者（tier1 / インフラ運用責任者）:
      - tier1 backend の運用、Cluster 管理、tier2 Service の deploy
        / upgrade を担当（「06_tier2/23_管理境界」整合）。
      - 個別テナントの業務データには触れない。
  - 業務管理者（テナント / 業界 pack の運用責任者）:
      - マスタ / ルール / Workflow 設定 / 監査検索 / 緊急対応を
        担当。
      - tier1 backend には触れない（tier2 業務管理 API のみ使用）。
  - tier3 はどちらの境界も触らない :
      - tier3 業務 UI から tier1 backend / Cluster 設定にアクセス
        する経路を持たない。
      - tier3 業務 UI から業務管理 API にアクセスする経路を持た
        ない。

■ 出荷時の境界整合 CI
  - tier3 リポジトリで業務管理 API への参照を import 禁止する強制
    機構を持つ（「31_強制機構」整合、「06_tier2/16_強制機構」と同枠）。
  - 検査内容 :
      - tier3 アプリの SDK import で tier2.<pack>.admin.v1 系の
        proto / SDK パッケージが含まれていないか。
      - HTTP path として /admin/v1/ への呼出が含まれていないか。
      - 業務管理 UI と同等の機能（マスタ編集 / 監査検索 / 緊急
        対応 等）の UI コードが tier3 リポジトリに存在しないか。
  - Backstage Software Template 由来の CI 設定で組み込み、後付け
    運用に依存しない。

■ 業務 UI から見た業務管理 UI の利用導線
  - 業務 UI ヘッダ / ユーザメニューに「業務管理 UI を開く」リンクを
    配置する（権限あり時のみ）。
      例 : Backstage の該当ポータル URL を新タブで開く。
  - 業務 UI 内の操作経路から業務管理 UI に飛ぶ deep link は前述の
    URL ビルダ経由で生成する。
  - 業務管理 UI に遷移する際、現在の tenant_id / actor / language
    が SSO で引き継がれる（「25_認証認可マルチテナント」SSO 連動
    整合）。

■ 境界の例外と禁止
  - 例外なし : 「業務 UI から少しだけ管理操作」を許容する例外は
    設けない。境界違反は ad-hoc な業務管理機能の業務 UI 流入を
    招くため、CI で機械的に禁止する（前述）。
  - tier3 が業務管理 API を呼ぶ正当な業務シナリオが発生した場合、
    その機能は業務管理 UI 側に移すか、tier2 へ業務 API として新規
    追加する（「23_tier2消費方針」「06_tier2/17_非提供スコープ」
    整合）。

■ 1.0.0 出荷時の境界
  - 1.0.0 で tier3 業務 UI を提供する代表アプリ群（発注 / 検査 /
    FA、「01_責務」1.0.0 出荷スコープ整合）と、tier2 が提供する
    業務管理 UI（Backstage プラグイン）の境界を CI で固定する。
  - 1.0.0 出荷後の機能追加で境界が揺らぐことがないよう、境界違反
    検出ルールを定期的に更新する（「30_互換性ポリシー」整合）。
