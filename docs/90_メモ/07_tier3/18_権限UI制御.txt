============================================================
tier3 の権限 UI 制御
============================================================

■ 方針
  - tier2 が ABAC（「06_tier2/22_権限モデル」）で認可判定を
    行う。tier3 はその判定結果を受けて、UI 上の表示 / 活性 /
    操作可否を反映する責務を持つ。
  - 認可の真は常にサーバ側にある。クライアント側 UI 制御は
    UX ヒントに留め、認可 bypass の根拠にしない。
  - 業務 UI では「権限がないこと」を業務担当が理解できる
    ように見せる方針を既定とする（hide ではなく explain を
    既定とする）。

■ ABAC 判定結果の UI 反映
  - tier2 から各画面 / action に対する許可状態を取得する経路:
      - 画面 mount 時にまとめて取得する「画面別 allowed actions」
        API を tier2 が提供する。tier3 はこれを呼んで UI 制御に
        反映する。
      - action 実行時の二重チェック（サーバ側）も必ず行われる。
        UI 制御は事前ヒントに過ぎない（「12_フォーム設計規約」
        validation 多段防御と同型）。
  - 判定属性（tenant_id / user_id / role 集合 / aggregate 状態
    / 担当組織等）は tier2 が Authorization context として供給
    する。tier3 はそのまま受け、独自属性を付加しない。

■ 三つの選択肢
  - hide:
      - 権限のない機能を完全に非表示にする。
      - 採用条件：機能の存在自体を業務的に知らせる必要がない
        場合（他テナント / 他組織機能等、知らせると識別子漏洩
        の懸念がある場合）。
  - disable:
      - 機能の存在を示しつつ操作不可（grayed out / 非活性）。
      - 採用条件：必要だが付与されていない、と業務担当に伝える
        必要がある場合。
  - explain:
      - disable + 理由 / 委譲経路 / 申請手順を表示。
      - 採用条件：業務担当が必要な権限の取得方法を理解して
        ロールアップ / 委譲依頼できるようにする場合。

■ 既定方針
  - 業務 UI では「explain」を既定とする。業務担当が業務遂行
    のために必要な権限を理解できることを優先する。
  - 「hide」を採用するのは、別テナント・別組織の identifier 等を
    画面に出すこと自体が認可越境のリスクとなる場合に限る。
  - 「disable のみ」は、explain にする情報源（理由 / 経路）が
    業務的に意味を持たない場合の妥協選択とする。
  - 既定方針は features 単位で宣言し、画面ごとに散らさない
    （「07_内部アーキテクチャ」整合）。

■ ロール別 navigation
  - サイドバー / メニュー項目 / 初期画面はロール / 許可状態に
    基づいて出し分ける。
      - 例：manufacturing.fa.operator は FA 進捗画面を初期表示、
        manufacturing.procurement.buyer は調達画面を初期表示。
  - メニュー項目の存否は前述の hide / disable / explain 方針に
    従う。
  - 初期画面の決定ルールはユーザ設定で上書き可能とする
    （業務担当の好みを尊重）。

■ 委譲権限（Delegation）の UI 表示
  - tier2 の Delegation API（「06_tier2/22_権限モデル」）で
    委譲が成立している間、UI 上に「○○の代理として操作中」
    バッジを常時表示する。
  - 表示要素:
      - 委譲元 user（業務語彙：氏名・役職）
      - 委譲対象権限の業務語彙ラベル
      - 委譲期間（残時間）
  - 委譲下で実行された操作は監査エントリに行為者 + 委譲元 user
    の両方が残る旨を、初回利用時にユーザに告知する。

■ emergency_override 中の警告バナー
  - emergency_override（「06_tier2/22_権限モデル」緊急時 override
    節）が起動している間、画面全幅の警告バナーを表示する。
  - 表示要素:
      - 「現在 emergency_override 中」の業務語彙メッセージ
      - 起動者 / 開始時刻 / 残時間
      - 「全操作の詳細監査が emit される」旨の注意
      - 解除導線（権限を持つ者向け）
  - 通知優先度は page 級として扱う（「17_通知UI」整合）。

■ ABAC 判定式の debug endpoint 利用
  - 開発環境のみ、tier2 の ABAC 判定 debug endpoint
    （「06_tier2/30_開発者体験」）を利用して「なぜ拒否されたか」
    を表示する。判定式 / 不足属性 / 関連 role を業務語彙で表示。
  - 本番環境では debug 表示を禁止する（攻撃者への情報供与を
    避ける。「32_セキュリティアーキテクチャ」整合）。
  - 環境判定はビルド時に固定し、runtime フラグで切替えない
    （誤って本番で開放される事故を防ぐ）。

■ 認可結果のクライアント cache 禁止
  - 認可結果をクライアントで cache し、cache に基づいて action
    を実行することは禁止する。必ずサーバ判定を経由する。
  - 画面 mount 時の許可状態取得結果は UI ヒント目的の短期 cache
    に留め、TTL を短く設定する（既定 60 秒程度）。
  - 権限変動（Delegation 開始 / 終了 / role 変更）は subscription
    で受信し、即時 invalidate する経路を持つ（「16_リアルタイム
    更新UX」整合）。

■ 権限不足エラーの表示
  - tier2 が AuthorizationDenied（「06_tier2/14_業務エラー監査
    コンプライアンス」）を返した場合、「19_業務エラーUX」の
    AuthorizationDenied 規約に従って表示する。
  - 表示内容:
      - 業務語彙の説明（生のエラーコードは出さない）
      - 必要権限の業務語彙ラベル
      - 委譲経路 / 申請手順（explain 方針が成立する範囲）
      - 緊急時の業務管理者連絡導線（emergency_override 経路は
        UI から直接起動させない。「26_業務管理UI境界」整合）

■ ロール命名規約の UI 表現
  - tier2 のロール命名（<pack>.<domain>.<resource>.<action>、
    「06_tier2/22_権限モデル」）はシステム側 ID であり、ユーザ
    向けには業務語彙ラベルへ翻訳して表示する。
  - 翻訳辞書は tier2 が i18n リソースとして提供する。tier3 が
    独自にラベル翻訳を行わない（業務語彙の真は tier2 にある）。
  - 開発者向け詳細表示（「ロール ID 表示」トグル）は開発環境
    のみ提供する。

■ tier3 内の機械的担保
  - 認可関連の UI 制御は Application 層 + Adapter 層に集約し、
    Presentation 層に直接認可ロジックを書かない（「07_内部
    アーキテクチャ」整合）。
  - allowed actions の取得 / cache invalidation を一元化する
    DI コンポーネントを features 横断で共有する。
  - 認可関連 hook の使用箇所と allowed action 名の整合は CI
    で照合する（「31_強制機構」整合）。
