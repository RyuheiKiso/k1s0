============================================================
tier3 アプリケーション間の連携
============================================================

■ 方針
  - 同一テナント内に複数 tier3 アプリが同居する前提を取る。
    1.0.0 出荷時の製造業 pack だけでも発注 / 検査 / FA など
    複数の tier3 が並走する（「01_責務」1.0.0 出荷スコープ
    節と整合）。
  - 複数 tier3 はテナント識別子と業務語彙を tier2 経由で
    共有する。tier3 同士が直接 API を呼び合わない。すべての
    業務処理は tier2 を経由する（「23_tier2消費方針」整合）。
  - 連携の体験単位は「ユーザがテナント内の業務を一気通貫で
    扱える」こと。具体的には SSO / 横断 navigation / 横断
    通知 / aggregate ID の deep link / 共通ブランディングで
    構成する。

■ SSO 体験
  - 認証は tier1 Authentication（Keycloak）の SSO で全 tier3
    を跨ぐ。一度認証すれば、テナント内のすべての tier3 で
    再認証なしに業務 UI を開始できる（「25_認証認可マルチ
    テナント」整合）。
  - 認証 token は OIDC の標準フローで取得し、httpOnly cookie
    または OS keychain に保持する（「32_セキュリティアーキ
    テクチャ」クライアント側 Secret 節整合）。
  - tier3 が独自の認証画面を作らない。Keycloak の認証画面に
    redirect する形を既定とする。
      例：「ログイン」ボタンは tier1 認証エンドポイントへの
          redirect のみを行う。

■ ログアウト連動
  - OIDC の front-channel logout / back-channel logout に
    対応し、テナント内のいずれか一つの tier3 でログアウト
    すると、全 tier3 から一斉にログアウトする。
  - 単一 tier3 だけのログアウト経路は提供しない。業務監査
    上、誰がいつどこからログアウトしたかが分散すると追跡
    不能になる（「06_tier2/14_業務エラー監査コンプライアン
    ス」整合）。
  - back-channel logout 受信時は、画面で開かれている業務
    操作を一旦 hold し、未保存の Draft はサーバ側に保存
    試行（save-on-logout）。

■ アプリ間遷移（deep link）
  - aggregate ID は業界 pack 横断で一意（tier2 既定）。
    あるアプリで参照した発注 ID を別アプリで開く deep link
    が機能する。
      例：発注 tier3 から「この発注に紐づく検査結果を開く」
          リンクを踏むと、検査 tier3 の詳細画面に直接遷移。
  - deep link の URL 形式は tier3 横断で統一（「11_画面遷移
    ルーティング」整合）。tier3 ごとの routing 規約に揺れを
    持たせない。
  - 認可がない aggregate への deep link は、遷移先で
    AuthorizationDenied を表示する（「18_権限UI制御」整合）。

■ アプリ間 navigation
  - ランチャー UI を tier1 / tier2 提供のシェルとして用意
    する。テナント内で利用可能な tier3 一覧を、認可で出し
    分けて表示する（業務管理 UI の menu と整合、「26_業務
    管理UI境界」整合）。
  - ランチャー UI は tier3 業務 UI のヘッダから常時起動
    可能。tier3 ごとに独自のグローバルナビを作って分散
    させない。
  - tier3 アプリ追加時は、テナント設定で利用可否を切替
    できる（「37_業務カスタマイズ粒度」整合）。

■ shared state の取扱
  - 状態の物理共有はしない。業務状態の真は tier2 にある
    （「08_状態管理」整合）。
  - クライアント間の軽量な UX 連携（例：別タブで開いた
    同一 aggregate の編集ロック表示）は BroadcastChannel /
    postMessage を限定的に許容する（「32_セキュリティアー
    キテクチャ」postMessage 節整合）。
  - 共有してよいのは UI ヒント（hover 状態 / 同時編集の警告）
    のみ。業務データを直接共有しない。

■ 異なる tier3 間の Domain Event 反映
  - 各 tier3 は必要な Domain Event を独自に subscribe する
    （「16_リアルタイム更新UX」整合）。tier3 間で event を
    直接渡さない。
  - subscribe は tier2 経由でテナント単位の Event Hub に
    接続。tier3 ごとに subscription を持つ。
      例：発注 tier3 で発行された OrderConfirmed を、検査
          tier3 が独自 subscribe して通知する。発注 tier3 が
          検査 tier3 を直接呼ぶことは禁止。
  - subscription の重複（同じ event を複数 tier3 で扱う）は
    既定で許容。各 tier3 はその event のうち自身の業務に
    関わる部分だけを表示する。

■ アプリ間 cookie / token 共有
  - 同一 origin の場合は cookie 共有で透過的に SSO 動作
    する。
  - 異 origin の場合は OIDC のリフレッシュフローで token を
    再取得する。token を URL fragment / query string で
    渡さない（「32_セキュリティアーキテクチャ」セキュリ
    ティヘッダ節整合）。
  - Companion 経由レガシー（「36_レガシー資産統合」整合）
    との SSO は Companion の transport 経由で別途行う。

■ バージョン整合
  - 複数 tier3 が異なる tier2 SDK バージョンに依存しても
    共存できる前提とする。tier2 が minor 互換性を保つこと
    で、tier3 ごとの SDK バージョンが minor で乖離しても
    動作する（「30_互換性ポリシー」「06_tier2/13_互換性
    ポリシー」整合）。
  - major 跨ぎは並行運用期間（最長 6 ヶ月、tier2 規約）に
    限り許容。期間内に全 tier3 を新 major に揃える。

■ ブランディング統一
  - テナント設定によりロゴ / カラー / フォントを共通化する
    （「09_デザインシステム」「37_業務カスタマイズ粒度」
    整合）。
  - tier3 ごとに独自テーマを実装しない。テナント全体での
    一貫した見た目を維持する。
  - ランチャー UI / 業務管理 UI / 各 tier3 業務 UI で
    ブランディングが揃う。

■ 通知の統合
  - 通知センター（「17_通知UI」）はテナント内の全 tier3 通知
    を集約する。tier3 ごとに別の通知センターを持たない。
  - 通知の発火元 tier3 / 関連 aggregate ID / 推奨アクション
    は通知エントリに含め、別 tier3 から開く deep link を
    生成する。
      例：検査 tier3 から「対応する発注を開く」リンクで
          発注 tier3 に遷移。
  - 未読件数のバッジはテナント全体での累計を表示する。

■ iframe 埋込
  - 原則禁止。tier3 を別 tier3 に iframe で埋め込まない。
    CSP / 認可境界 / clickjacking 防御の崩壊を避ける
    （「32_セキュリティアーキテクチャ」CSP 節整合）。
  - 業務上どうしても埋込が必要な場合は、tier2 経由で組成
    された専用の埋込ビュー（読み取り専用 / 認可制限済み）を
    用意する経路に限る。
