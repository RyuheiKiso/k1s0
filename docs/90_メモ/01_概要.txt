============================================================
企画メモ
============================================================

■ 概要
  - OSS として開発・公開する。
  - 企業内に構築するプラットフォームを提供する。
  - 無料利用可能な OSS（Kubernetes、Istio など）を最大限活用する。
  - マイクロサービスの構築を支援する基盤を提供する。

■ ターゲット
  - 企業の情報システム部門。

■ 既存資産への配慮
  - レガシー資産（.NET Framework など）も最小限のカスタマイズで
    プラットフォームの恩恵を受けられるようにする。
  - tier1 Library を直接組み込めない言語については、ビジネス API と
    観測可能性を分けて提供する。
      - ビジネス API：tier1 が提供するゲートウェイ経由で infra に
        アクセスさせる。.proto を単一の真とし、HTTP/1.1 + JSON
        （unary）は Envoy Gateway の gRPC-JSON Transcoder で派生、
        HTTP/1.1 + SSE（text/event-stream、server-streaming）は
        tier1 Rust ハンドラ内で SSE フレーミングを直接生成する
        （streaming RPC の扱い詳細は「05_tier1/03_Server系」Proto
        二層化 / RPC 形式の射影方針を参照）。
      - 観測可能性（役割 A）：
          Companion 役割 A として提供する。.NET Framework 4.6.2+ では
          OpenTelemetry .NET Auto-Instrumentation（CLR Profiler アタッチ
          方式、Apache 2.0、コード変更不要）を観測可能性の標準形態
          とする。Auto-Instrumentation 非対応環境（4.6.1 以前など）
          向けには NuGet 参照型の Companion を補助的に提供する。
          役割 A は span / log / metric の自動生成のみを担い、
          ビジネスコードへの明示参照は不要。ただし tenant / subject
          の attribute 注入は OTel .NET Auto-Instrumentation の標準
          計装範囲外であり（CLR Profiler は HTTP / ADO.NET / WCF 等の
          既知 instrumentation point に対する自動 span 生成までを
          担い、Authorization header 中の JWT claim を decode して
          attribute に注入する経路は持たない）、Companion OTel
          拡張 NuGet（k1s0.Companion.NetFx.OTelExt、splunk-otel-
          dotnet fork）の **CLR Profiler 初期化 (`ICorProfilerCallback`
          経由 IL rewrite) で登録される k1s0 processor** が
          JWT claim → OTel attribute 変換を補完する（4.6.1 以前
          は Application_Start / Main 起動直後の手動初期化に
          degrade、用語上 .NET Framework に "startup hook"
          (`DOTNET_STARTUP_HOOKS`) は存在しない、詳細は
          05_tier1/04_Library Companion 役割 A / 12_client/16_
          companion_otel_extension）。さらに defense-in-depth として OTel
          Collector の attributes processor でも tenant / subject を
          span enrichment する二重持ち（注入経路の片肺障害でも全
          span に attribute が必ず乗る）。
      - Transport Negotiation（役割 B）：
          Companion 役割 B として、bidi を含む全 RPC を tier1
          Transport Adapter Layer と対をなす Companion 内 adapter で
          transport 非依存に実行する。役割 B は CLR Profiler 経由
          ではなく、明示的な NuGet 参照（k1s0.Companion.NetFx
          パッケージ、IL rewrite ではない通常のライブラリ参照）
          として配布する。CLR Profiler は HttpWebRequest（h2 非対応
          stack）と、Windows 10 1607 / Server 2016 未満ホスト OS の
          WinHTTP（OS 側 WinHTTP API が h2 を実装しない版数）の上に
          WebSocket / SSE / HTTP/3 を生やすことはできないため、
          Transport Negotiation を観測可能性と同経路で自動化する
          ことはできず、別 NuGet で生やす。.NET Framework Companion
          の bidi 経路は WinHttpHandler の HTTP/2 ALPN がホスト OS
          側 WinHTTP の h2 対応版数（Windows 10 1607+ / Server
          2016+）に依存し、かつ WinHttpHandler 自体に client-
          streaming / bidi の構造的制約があるため Connect-RPC bidi
          を採用せず、引き続き sse_paired（HTTP/1.1 chunked + SSE
          + 自製パーサ）を既定とする。Browser SPA の bidi primary は
          ua_subclass 別に分割して採用する：**chrome_edge / tauri_
          native は Connect-RPC (`connect_bidi` adapter)** が primary、
          **firefox_safari / dotnet_companion は `paired_post_sse`
          adapter**（POST /open + SSE + POST /send + POST /close の
          半二重 emulation、05_tier1/07_Bidi適合仕様 の bidi conformance
          class で property_axiom により connect_bidi との完全等価を
          CI 検査）が first-class 経路として併設される。本経路は
          .NET Framework Companion の bidi 実装と直交し、Browser SPA
          側で UA を検出して経路選択する（詳細は「05_tier1/03_Server系」
          Transport Adapter Layer /「05_tier1/04_Library」Companion 役割
          A / 役割 B /「12_client/06_Transport適応方針」「12_client/17_
          UA_aware_adapter」を参照）。
      - 認証コンテキスト伝播：
          役割 A の一部として、生成された span / log / metric に
          tenant / subject / trace_id を統一注入する（注入経路は
          Companion OTel 拡張 NuGet の CLR Profiler 経由 IL
          rewrite で登録される k1s0 processor + OTel Collector
          attributes processor の二重持ち、上記の役割 A 注記参照）。
    （詳細は「05_tier1」配下の各方針メモを参照）
