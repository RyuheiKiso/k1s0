============================================================
formal 責務
============================================================

■ 一文定義
  - formal は、tier1 / tier2 / tier3 / infra / data / security
    / ops / test の各層が宣言した個別軸の規律（transport /
    migration / observability / auth / key / schema / SLO /
    OSS-lifecycle / capacity / data-tenant / client-state /
    infra-topology / data-preservation / threat-model / build-
    provenance / clock-integrity / client-distribution / ops-
    loop / verification）の中で「コード経路に依存せず数学的
    に証明されるべき不変式」を、temporal_safety_proof →
    temporal_liveness_proof → refinement_proof → program_
    correctness_proof → runtime_modelcheck_proof の 5
    proof_class の格子で完全に埋め、proof artifact が必ず
    物理経路（TLA+ / Apalache / P language / Stainless /
    Dafny / Lean 4 / Kani / CBMC のいずれかで生成された
    machine-checkable certificate）に bind されることを
    meta-layer として保証する責務を持つ。test 軸が「実行
    ベース検証 artifact の cell 化」を担うのに対し、formal
    は「数学的証明 artifact の cell 化」を担い、両者は同型
    だが直交する。

■ 責務の境界
  - formal が責務を持つ：
      - 証明 lifecycle（temporal_safety_proof / temporal_
        liveness_proof / refinement_proof / program_
        correctness_proof / runtime_modelcheck_proof の 5
        proof_class）の宣言的真
      - axis × proof_class の coverage matrix（19 軸 × 5
        proof_class = 95 cell）の build artifact 化、欠損
        cell ゼロかつ全 cell の proof_status ∈ {verified,
        accepted_with_assumption} を 1.0.0 ship blocker
        として CI 不変条件化
      - critical_invariant catalog（proof_inventory.lock
        .yaml）の単一の真：各軸が「証明されるべき不変式」
        を theorem 名 + tool + statement_hash で claim し、
        formal がそれを集約・査読・enforce
      - proof artifact の immutable archive：TLA+ TLC trace /
        Apalache trace / P trace / Stainless certificate /
        Dafny .dfy + verification log / Lean .olean + mathlib
        revision pin / Kani report / CBMC .json の単一の真
      - counter-example の物理 closure：model checker が
        検出した反例（counter_example.lock.yaml）は close_
        kind ∈ {fixed_in_code, fixed_in_spec, accepted_as_
        bug, scope_narrowed} のいずれかで必ず closure、文章
        only での「重要でない」処理は禁止
      - proof artifact の build artifact 化：proof は「PR
        で書き加える」のではなく「proof_inventory.yaml /
        formal_classes.yaml / 各 axis の formal_obligations
        から導出される build artifact として生成 + 検証
        される」形を採る
      - formal proof の cadence enforcement（proof_status
        .lock.yaml の last_verified_at が cadence_days 以内、
        cadence 違反は admission policy で deploy block）
      - 証明 toolchain の L1+ 単一深耕（TLA+ + Apalache /
        P language / Stainless / Dafny / Lean 4 / Kani /
        CBMC を 1 機能カテゴリ 1 OSS で固定、横並び禁止）
      - 証明 loop の各 phase（specify → model → prove →
        review → archive）が空欄でないことの cross-axis
        operational coverage の CI assertion
      - test 軸（13_test/15）との bind：formal の各 cell が
        verified された場合、test 軸の対応 cell（同 axis ×
        v1_property_axiom）の property は formal proof の
        instantiation として regression corpus に物理転写
        され、property test の seed pool に追加される

  - formal が責務を持たない：
      - 個別 OSS の選択（→ 02_採用OSS一覧 / 各層 04_採用
        OSS、formal は L1+ 単一深耕の規律を踏襲するのみ）
      - SLI / SLO target 値の意味論
        （→ 05_tier1/13_SLO適合仕様、formal は v1_proof_
          coverage_compliance / v1_proof_freshness_compliance
          / v1_counter_example_closure_compliance を SLO に
          登録するのみで target 値自体の意味論は持たない）
      - 観測可能性 SoR の物理運用
        （→ 05_tier1/09_観測適合仕様 / 09_data、formal は
          proof execution の OTel trace / ClickHouse 保存を
          SoR に従属させる側）
      - 脅威モデルの宣言
        （→ 10_security/15_脅威モデル適合仕様、formal は
          threat の「攻撃者視点 invariant 否定」を temporal
          _safety_proof の 1 obligation として転写するのみ、
          threat 自体は宣言しない）
      - migration pair の compatibility 判定
        （→ 05_tier1/08_マイグレーション適合仕様、formal は
          dual-write の linearizability theorem を proof_
          inventory に持つのみ、pair の意味論は migration 軸
          の所有）
      - 運用 loop の宣言
        （→ 11_ops/15_運用ループ適合仕様、formal は
          idempotency / progress theorem を持つのみ）
      - test execution の意味論
        （→ 13_test/15_検証規律適合仕様、formal は test
          軸の v1_property_axiom と双方向 lock するのみで、
          test cell の意味論は test 軸の所有）
      - proof obligation の意味論そのもの
        （→ 各軸 spec、formal は obligation を集約・enforce
          するのみ、obligation の中身は各軸 spec の所有）

■ 至高路線における立ち位置
  - formal は 18 軸 + meta + security + ops + test の更に
    上位に立つ「数学的真理 invariant」の管掌者である。
    test が「実行ベース検証 artifact」を coverage matrix に
    詰めるのに対し、formal は「machine-checkable proof
    certificate」を proof matrix に詰める。両者は同型だが
    直交：test の v1_property_axiom（実行で反例 0 を観測）
    の上層に formal の temporal_safety_proof（数学的に反例
    が存在しないことを証明）が居る。
  - formal は 5 層 defense-in-depth の最上層に「数学的
    enforcement」を追加する：
        層 A : compile（type check）
        層 B : lint（policy check）
        層 C : integration test（実行検証）
        層 D : runtime（admission webhook + drill）
        層 E : 物理（cosign / Kyverno / Object Lock）
        層 F : 数学的（proof certificate） ← 本層
    層 F は「実行で検出されない潜在反例」を数学的に
    impossible にする。Amazon S3 / DynamoDB / TigerBeetle /
    CockroachDB が運用している路線の OSS 投影。
  - formal は「文章運用に頼らず物理 enforcement に転写
    する」という infra / data / security / ops / test の
    哲学を、証明次元（proof_class ⊥ axis ⊥ phase）で
    再保証する meta-meta-layer である。「proof は完成が
    難しいから後回し」「critical invariant の証明は v2
    で良い」を全て禁止し、proof_status.lock.yaml の
    `all_critical_verified` を 1.0.0 ship blocker とする。
  - 各層の spec が「cross-axis assertion」「cross-threat
    assertion」「cross-loop assertion」「cross-class
    assertion」を持つように、formal は「cross-proof
    assertion」を持ち、proof_class ⊗ axis ⊗ phase ⊗ 層
    の四次元 grid の全 cell に machine-checkable
    certificate が宣言済みであることを CI で物理 enforce
    する。

■ 至高路線における原則
  - 証明 matrix の単一の真：proof_matrix.lock.yaml が
    build artifact、手書き禁止。各軸 spec の formal_
    obligations 宣言と各 proof_class の verification result
    から生成される。
  - artifact の物理転写：全 proof claim（safety / liveness /
    refinement / program / runtime）は TLA+ / Apalache /
    P / Stainless / Dafny / Lean 4 / Kani / CBMC のいずれ
    かに必ず物理転写される。「文章のみで証明済み」「論文
    引用のみ」は禁止、CI fail。
  - last_verified_at の物理 enforcement：全 (axis ×
    proof_class) cell は last_verified_at を持ち、cadence
    越え cell が 1 つでもあれば関連 service deploy を
    Kyverno で物理 block。文章のみで「次回証明する」は
    禁止。
  - proof artifact の不可逆性：verified された proof は
    statement_hash + tool_version + mathlib_revision +
    certificate_hash で fingerprint され、回帰（statement
    変更 + 再証明なし）は CI fail。「invariant を緩めた」
    操作は新 theorem を切ることでのみ表現可能。
  - counter-example の物理 closure：model checker が反例
    を出した場合、close_kind ∈ {fixed_in_code, fixed_in_
    spec, accepted_as_bug, scope_narrowed} のいずれかで
    14 day 以内に物理 closure。文章で「そのうち直す」は
    禁止、期限後は admission block で関連 service deploy
    block。
  - 単一 OSS 深耕（formal 道具立て）：1 機能カテゴリ
    （temporal logic / state machine code-gen / program
    logic / proof assistant / runtime model check）に対し
    L1+ 単一深耕。横並びは持たない。具体的には TLA+ +
    Apalache（temporal logic）/ P（state machine）/
    Stainless（Scala program logic）/ Dafny（multi-lang
    program logic）/ Lean 4 + mathlib（proof assistant）/
    Kani（Rust runtime model check）/ CBMC（C/C++ runtime
    model check）の 7 OSS を v1_l1plus_primary として
    14 OSS-lifecycle に登録、major version migration 演習
    必須。
  - 段階的 release 禁止：1.0.0 時点で 5 proof_class 全てが
    19 軸全 cell で proof_status ∈ {verified, accepted_
    with_assumption} であること。証明不能な (axis ×
    class) cell が 1 つでも残っていれば ship blocker。
    accepted_with_assumption は assumption の文書化 +
    軽減策 + revisit 期限の 3 点 set で artifact_lock 化、
    文章 only の例外は禁止。
  - formal の物理計測：proof execution は proof_minutes_
    per_quarter / verified_theorem_count / counter_
    example_open_count / proof_artifact_size_bytes
    metric として 13 SLO に登録、四半期で必ず（verified_
    theorem_count 単調増加 + counter_example_open_count
    単調減少 + accepted_with_assumption_count 単調減少）
    する artifact 化された target を持つ。文章で「formal
    を充実させたい」は禁止、必ず proof_matrix_target.lock
    .yaml の backlog entry として物理化。
  - test 軸との双方向 lock：formal の v1_temporal_safety_
    proof / v1_program_correctness_proof で verified された
    invariant は test 軸の v1_property_axiom の seed pool
    に物理転写、test 軸の v1_property_axiom で flake なし
    に green 維持された property は formal の proof_
    candidate.lock.yaml に backlog として登録。両者の
    drift は CI fail。
