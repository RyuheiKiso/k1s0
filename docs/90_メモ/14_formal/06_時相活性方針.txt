============================================================
formal 時相活性方針（v1_temporal_liveness_proof）
============================================================

■ 一文方針
  - v1_temporal_liveness_proof は、各軸の「いつかは必ず
    成り立つべき liveness property（"good thing eventually
    happens"）」を TLA+ + Apalache で weak / strong
    fairness 仮定下に machine-checkable に証明する proof_
    class であり、progress 不能（livelock / starvation）の
    存在不可能性を 19 軸の主 obligation に対し物理 enforce
    する。

■ 担当 proof_class
  - v1_temporal_liveness_proof：
      - 意味論：「temporal logic の formula `<>(P)` または
        `[]<>(P)`（eventually P / always eventually P）」、
        即ち全 fair execution path で P が無限回 / いつか
        成り立つ
      - artifact：TLA+ .tla + Apalache liveness check log
        + counterexample loop（livelock cycle）
      - cadence_class：v1_per_axis_change_or_biweekly、
        cadence_days = 14（liveness check は state
        explosion で重い、weekly より緩める）
      - artifact_class：v1_apalache_liveness_certificate
      - orchestrator_preference：tlaplus_apalache_pipeline
      - coverage_weight：1.2
      - 対応する drill_class：apalache_liveness_drill /
        fairness_assumption_review_drill
      - primary defense_layers：tlaplus_apalache_pipeline /
        proof_gate_kyverno
      - 最低限の cross-axis：08 migration / 10 auth / 11 key
        / 39 client / infra01 / data01 / ops15 loop
      - active cell 数（v1 cap）：12（全軸ではなく liveness
        が意味を持つ軸のみ。残 7 軸は v1_temporal_safety_
        proof のみで cover）

■ Liveness vs Safety
  - safety property：「bad thing never happens」、`[](P)`
    形式、有限 trace で反例検出可能
  - liveness property：「good thing eventually happens」、
    `<>(P)` 形式、無限 trace（lasso shape）で反例検出
    （livelock / starvation cycle）
  - liveness は safety より state explosion が深刻：
    Apalache は bounded liveness check が中心、unbounded
    liveness は別途 TLA+ TLC の exhaustive enumeration を
    補助で使う。

■ Fairness 仮定の規律
  - 全 liveness property は fairness 仮定（weak fairness
    WF / strong fairness SF）を陽に宣言。fairness 仮定が
    過大な liveness proof は受け入れない（fairness の
    abuse は accepted_with_assumption に強制 downgrade）。
  - fairness 仮定の文書化：
        - WF_v(A)：action A が必ず実行可能であり続ければ、
          いずれ実行される（weak fairness）
        - SF_v(A)：action A が無限回 enabled になれば、
          いずれ実行される（strong fairness）
  - 各 liveness obligation の fairness 仮定は proof_
    inventory.lock.yaml の fairness_assumption 段落に
    自然言語 + TLA+ 表現で artifact 化。assumption.lock
    .yaml の cap=20 件に算入。

■ 各軸の代表 liveness obligation

  - 08 migration：
      - LiveCutoverProgress：cutover phase が必ず終了
        （livelock なし）、SF 仮定下
      - LivePostCleanupProgress：post phase の cleanup が
        必ず終了

  - 10 auth：
      - LiveTokenRefreshProgress：refresh request が必ず
        いずれか（成功 / 失敗）で終了
      - LiveStepUpProgress：step-up challenge が必ず
        timeout または成功で終了

  - 11 key：
      - LiveRotationProgress：key rotation が cadence 内に
        必ず終了
      - LiveKMSAvailability：KMS API outage 後に必ず
        recovery（infra01 failover と co-bound）

  - 39 client：
      - LiveReconcileTermination：dirty state から
        reconciled state に必ず到達（fairness 仮定下）

  - infra01 topology：
      - LiveLeaderElection：leader 喪失後に必ず新 leader
        選出（partition 解消 + SF 仮定下）
      - LiveDrainCompletion：drain 操作が必ず終了

  - infra16 clock：
      - LiveClockResync：clock skew 越え後に PTP / chrony
        による resync が必ず収束

  - data01 preservation：
      - LiveRestoreCompletion：restore 操作が必ず終了
        （lossless であることは v1_temporal_safety_proof
        側で保証）
      - LiveReplicationCatchUp：replication lag が必ず
        bound 以内に収束

  - security15 threat：
      - 各 threat の incident response runbook が必ず
        終了することを LiveIncidentResponse_<id> として
        claim

  - ops15 loop：
      - 5 signal_class 全ての runbook が必ず終了する
        progress property
      - LiveDrillFailureClosure：drill_failure signal が
        必ず closure に到達

  - test15 verification：
      - LiveDrillCadenceClosure：cadence 越え cell が必ず
        新 verification round で再 green に到達

  - formal（自軸）：
      - LiveCounterExampleClosure：counter-example が
        close_due_at 以内に必ず close_kind のいずれかで
        closure

■ workflow
  - specify：軸 spec の formal_obligations 段落で liveness
    obligation を `liveness:` 副段落として宣言、fairness
    仮定を併記
  - model：TLA+ spec の Spec definition に fairness 条件
    （`Spec == Init /\ [][Next]_v /\ WF_v(A) /\ SF_v(B)`）
    を陽に書く
  - prove：Apalache の liveness check（experimental, depth
    bound、Buchi automaton）または TLC の exhaustive
    liveness check で verified
  - review：fairness 仮定の合理性 review、過大な fairness
    は accepted_with_assumption に downgrade
  - archive：verified liveness certificate + fairness
    statement を proof_status.lock.yaml に fingerprint

■ Liveness proof の特殊性
  - state explosion が深刻：Apalache の liveness check は
    bounded、unbounded は TLC enumeration が必要。bound
    parameter は tla_apalache_pin.lock.yaml で固定。
  - fairness 仮定の文書化が必須：fairness なしで liveness
    が証明できる場合は要 review（過剰に強い property の
    可能性）
  - 反例（livelock cycle / starvation pattern）は trace
    形式で counter_example.lock.yaml に登録、close_kind
    で closure

■ 採用しない設計
  - fairness 仮定なしの liveness 証明（単純 termination
    のみ）は v1_program_correctness_proof の termination
    proof 側で実施、本軸とは別 obligation。
  - 「実用上はほぼ起きない」を理由とする liveness 省略
    禁止。obligation を取り下げる場合は新 statement_hash
    + scope_narrowed として artifact_lock。
  - real-time bound（時間制約付き liveness）は infra16
    clock の HLC bound と co-bind、本軸単独では time-
    independent な liveness のみ。

■ CI 不変条件（v1_temporal_liveness_proof 担当部分）
  - 整合 1：proof_inventory.lock.yaml の全 v1_temporal_
    liveness_proof entry が theorem_name + fairness_
    assumption + statement_hash 完備
  - 整合 2：全 v1_temporal_liveness_proof cell の last_
    verified_at が cadence_days=14 以内
  - 整合 3：counter_example.lock.yaml の v1_temporal_
    liveness_proof entry（livelock / starvation pattern）
    が close_due_at 以内に closure
  - 整合 4：fairness_assumption の cap が assumption.lock
    .yaml の v1=20 件以内
  - 整合 5：generator output と手書き drift = 0
