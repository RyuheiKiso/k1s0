============================================================
tier1 L1+ 移行 Pair 適合仕様（v1）
============================================================

■ 位置づけ
  - 「04_Library」L1+ 移行コミットメント節が宣言する「移行先候補
    （カテゴリごとに 1 つ以上）を文書化し、Testcontainers での
    dry-run 移行テストを年次で実施する。dry-run の green を Library
    リリース条件に含める」を、機械可読な単一の真として一箇所に
    固定する仕様書。
  - 04_Library が候補を複数列挙する一方で、1.0.0 ship blocker と
    なる「dry-run green 必須 pair」が確定していなかった。本仕様
    でこれを 4 pair に固定し、各 pair × phase × assertion を全数
    機械検証可能な形で組む。
  - 「07_Bidi適合仕様」が transport 軸、「06_tier2/32_テナント分離
    適合仕様」が data 軸、「07_tier3/39_クライアント状態適合仕様」
    が client 軸の単一の真であるのと同型の枠組みを migration 軸に
    転写したもの。dimension override 禁止 / dead spec 殺し / build
    artifact 化の規律はそのまま継承する。

■ 設計原則
  - 1 カテゴリ = 1 primary pair。
      L1+ カテゴリ（Relational Store / Single-leader、Messaging /
      EventBus、Workflow / Long-running Saga、Rule Engine）の各々
      に対し、1.0.0 ship 前に dry-run green を要件とする primary
      pair を 1 つだけ確定する。複数候補の並走は採らない。
      （L1+「単一 OSS 深耕 + 移行コミットメント」の哲学を migration
        toolchain にも転写。pair の数を絞ることで toolchain の
        作り込み深度を最大化する。）
  - 移行 phase は 5 段階で固定する。
      schema_diff / state_replicate / dual_write_ramp / cutover /
      rollback の 5 phase に分割し、各 phase の assertion id を
      決定論的に matrix 化する。phase の追加 / 順序変更は破壊的
      変更（major version up）。
  - dry-run は 1.0.0 ship 前と年次。
      1.0.0 ship 前に少なくとも 1 度の全 pair × 全 phase green を
      必須とする（ship blocker）。1.0.0 以降は年次で同 dry-run を
      実施し、green 維持を Library リリース条件とする。
  - pure OSS 内移行を 1.0.0 で証明する。
      cloud lock-in 想定（Aurora / Neon / AWS MSK / Confluent Cloud
      / Temporal Cloud 等）への移行は dry-run primary pair から
      除外する。OSS 方針との整合を保つため、1.0.0 では同 wire /
      同 engine 系の pair で移行可能性を証明する。
  - 5 層 defense-in-depth で構成する。
      層 A : pair 宣言（pairs.yaml）
      層 B : phase / assertion 宣言（phases.yaml）
      層 C : Testcontainers での dry-run 自動実行（test_matrix.yaml）
      層 D : runtime（露出概念一覧との整合検査）
      層 E : 物理層（年次 cadence の自動 schedule、release blocker）
  - dead spec を CI で殺す（07/32/39 と同枠）。
      pairs.yaml に登録された pair、phases.yaml に登録された phase
      / assertion、test_matrix.yaml に登録された scenario、いずれも
      参照されなくなった時点で CI fail。

■ v1 primary pair セット（4 pair）
  - 1.0.0 ship 前 dry-run green 必須。pair 名は 04_Library のカテゴリ
    名と整合する。

      pair_id              | from (本命)                    | to (移行先 primary)        | wire 互換
      ---------------------+--------------------------------+----------------------------+-----------
      relational_pg_pair   | PostgreSQL (CloudNativePG)     | PostgreSQL (StackGres)     | 完全
                           |                                |                            | (同 engine)
      messaging_kafka_pair | Apache Kafka (Strimzi)         | RedPanda                   | wire 完全
                           |                                |                            | (Kafka API)
      workflow_pair        | Temporal                       | Cadence                    | 部分
                           |                                |                            | (state model)
      rule_engine_pair     | ZEN Engine                     | 自製 DSL backend           | DSL 真として
                           |                                | (Rust 実装)                | 同一表現

  - 各 pair の不変条件と pair 選定理由 :

      ── relational_pg_pair (CloudNativePG → StackGres)
          - 同じ PostgreSQL engine、Kubernetes Operator 差のみ。
          - pg_dump / pg_restore / logical replication が両方で動く。
            pg_partman / pgvector の拡張も両方で対応。
          - 移行の難所は Operator 周辺（backup CR / monitoring CR /
            postgres role 系 CR の差）に縮約され、業務コードへの
            影響は extension の availability に絞られる。
          - 至高選択の根拠：pure OSS 内 + 同 engine + 同 wire の
            最小移行 pair。1.0.0 で証明する難度が現実的かつ意味的
            に十分。

      ── messaging_kafka_pair (Apache Kafka → RedPanda)
          - Kafka wire 完全互換（KIP / Schema Registry wire 互換も）。
          - MirrorMaker 2 が両方で動く。Schema Registry は既に
            Apicurio + Karapace の L2* 同族で対応済み（「04_Library」
            L2* 同族保証参照）。
          - 移行の難所は partition 配置 / topic config 差 / consumer
            group rebalance 戦略差に縮約される。
          - 至高選択の根拠：pure OSS + Kafka wire 互換 + 別実装
            （C++ vs JVM）で、wire 互換の真価が現れる pair。

      ── workflow_pair (Temporal → Cadence)
          - 元々同一プロジェクト由来。state model / Workflow /
            Activity の境界概念が近い。state export / replay が
            ほぼ parallel。
          - Workflow definition の API（SDK 形）は完全互換ではなく、
            tier2 業務コードに修正が入る。露出概念一覧（「05_提供
            機能カテゴリ」L1+ 露出概念）の WorkflowID 体系 / 補償
            処理の書き方 / 決定論実行制約 で差が出る。
          - 至高選択の根拠：業務コード影響の最も大きい pair。
            これを 1.0.0 で覆うことが移行コミットメントの中核。

      ── rule_engine_pair (ZEN Engine → 自製 DSL backend)
          - ZEN Engine の決定表 DSL を真として、評価エンジンを
            Rust で再実装する dry-run。tier1 Library が ZEN の DSL
            semantics を内部表現として完全把握していることを証明
            する。
          - 1.0.0 後の Drools / Camunda DMN 等への将来移行は、本
            内部表現を起点に書ける。
          - 至高選択の根拠：DSL を真として握ることが ZEN ライセンス
            変更時の即応性を担保する。

  - 4 pair で v1 を covering する。新 L1+ カテゴリ（Distributed SQL
    予約カテゴリ等）が確定した時点で、本仕様は v2 候補として pair
    追加検討に入る。

■ v1 移行 phase セット（5 phase、決定論的順序）
  - 全 pair に共通する 5 phase。順序は固定。phase ごとに pair 別の
    assertion id matrix を持つ。

      phase_id          | 入力                          | 出力                         | 業務影響
      ------------------+-------------------------------+------------------------------+------------------
      schema_diff       | 旧 backend の schema / state  | 差分レポート + tier2 露出   | なし（読取のみ）
                        | 定義                          | 概念影響箇所一覧            |
      state_replicate   | 旧 backend の状態スナップ    | 新 backend の同期状態        | なし（旧側継続）
                        | ショット                      |                              |
      dual_write_ramp   | 業務トラフィック             | 旧 / 新両方への二重書込、    | 読取は旧 100% →
                        |                              | 読取 ramp 切替              | 新 100% へ ramp
      cutover           | dual_write 完了状態          | 新 backend が単独動作        | 短時間の write
                        |                              |                              | freeze
      rollback          | cutover 後 24h 以内の異常検知| 旧 backend への切戻し        | 短時間の write
                        |                              |                              | freeze

  - 各 phase の不変条件 :

      - schema_diff
          - 旧 / 新の schema / state 定義を機械的に diff し、業務
            コード影響箇所を「05_提供機能カテゴリ」露出概念一覧に
            射影してチェックリスト化する。
          - tier2 / tier3 への影響度を「無修正 / 設定変更 / コード
            修正」の 3 段階で分類。
          - business outcome に影響する差分（Workflow ID 体系変更、
            ロック挙動差、SQL 方言差 等）は赤線扱い。

      - state_replicate
          - 旧 backend の現在状態を新 backend に複製。完了後に
            状態整合（行数 / hash / sequence / consumer group offset
            等）を assertion で検証。
          - 業務 traffic は旧 backend に流れ続ける。

      - dual_write_ramp
          - tier1 Library 抽象が dual-write 経路を持ち、書込は両
            backend、読取は旧 → 新へ ramp で切替（0% / 5% / 25% /
            50% / 75% / 100%）。
          - 各 ramp 段階で「06_tier2/32_テナント分離適合仕様」の
            integrity property (P1)〜(P4) が両 backend で満たさ
            れることを assertion で検証。
          - 「07_tier3/39_クライアント状態適合仕様」の Domain Event
            subscription が中断しないことを resume_token（「03_
            Server系」）で透過化する。

      - cutover
          - 短時間の write freeze（数秒〜数十秒）で書込を新 backend
            のみに切替。tier1 Library の dual-write を新側 only に
            切替える。
          - cutover 直前 / 直後の business outcome の連続性を
            observability connection（trace_id / span 名）で検証。

      - rollback
          - cutover 後 24h 以内の異常検知で旧 backend に切戻す経路。
          - cutover 中に新 backend が受けた書込は、rollback 時に
            旧 backend に再生する（reverse replication）。
          - 24h 以降の rollback は新規移行扱い（再 dual_write_ramp）。

■ 5 層 defense-in-depth

  ── 層 A : pair 宣言（pairs.yaml）
      - pair_id を tier1 内部の Rust crate と enum で claim する。
        pairs.yaml に登録されない pair は Library 内部で参照不能。
      - exposed_concepts_affected は「05_提供機能カテゴリ」露出
        概念一覧と CI 照合する（drift 検出）。

  ── 層 B : phase / assertion 宣言（phases.yaml）
      - 全 assertion id を Rust test runner が attribute claim
        （07/32/39 と同型）:
            #[migration_assert("sr_logical_replication_lag_under_threshold")]
            fn check(...) -> Result<()> { ... }
      - 未参照 assertion id / 未実装 assertion id は CI fail。

  ── 層 C : Testcontainers での dry-run 自動実行（test_matrix.yaml）
      - 4 pair × 5 phase の全 scenario を Testcontainers で並列
        実行。各 pair で旧 backend + 新 backend を実コンテナで
        立ち上げ、合成 workload を流す。
      - 障害注入 scenario（replication lag / network partition /
        disk full / clock skew）も同 matrix に含める。
      - merge 条件 : 全 scenario green。skip 不可。

  ── 層 D : runtime（露出概念整合検査）
      - 04_Library 露出概念一覧と pairs.yaml の exposed_concepts_
        affected を CI で照合する。
      - tier2 業務コード移行ガイド（04_Library L1+ 移行コミットメ
        ント節）は exposed_concepts_affected を起点に機械的に生成
        する。手書き diff があれば fail。

  ── 層 E : 物理層（年次 cadence + release blocker）
      - dry_run.lock.yaml の last_green_at が 365 日を超えた pair
        があれば、Library のリリース pipeline を物理的に block する
        （CI で自動）。
      - 1.0.0 ship 前は initial dry-run（4 pair すべて green）が
        ship blocker。これを満たすまで release tag を作成しない。

■ 三軸との接合

  本仕様は三軸（07 / 32 / 39）の上位レイヤとして、移行軸の不変条件
  を形式化する。dual_write_ramp / cutover / rollback の各 phase 中
  でも三軸の不変条件は保たれる必要がある :

      relational_pg_pair の dual_write_ramp / cutover :
        - 32 atomic 三表書込 (P1)〜(P4) が両 backend で同時に成立
          （dwr_atomic_three_table_property_p1_p4_both_sides）。
        - 32 RLS が両 backend で同一 policy 適用される
          （schema_diff で row level security 設定差分を検証）。

      messaging_kafka_pair の dual_write_ramp / cutover :
        - 07 conformance_class（v1_event_feed の SESSION_ORDERED
          + REQUIRED + 5000ms）が両 backend で満たされる。
        - 07 messaging_bridge adapter の constraints（partition_key
          = session_id）が両 backend で同等に物理的成立する。

      workflow_pair の cutover :
        - 39 client conflict tree の resume_token / Idempotency-Key
          が cutover 前後で連続性を保つ。
        - 39 pending_queue resume が cutover 中の write_freeze 区間
          で正しく hold され、解除後に新 backend に流れる。

      rule_engine_pair の dual_write_ramp :
        - 32 atomic 三表書込内で rule evaluation が両 backend で
          同一結果を返すことを assert。

  これら接合 assertion は test_matrix.yaml の各 scenario で
  cross_axis_assertions として claim する。

■ CI 不変条件（4 ファイル + 5 層 + 三軸接合の関係性検査）
  - 違反は merge 不可。
      整合 1 : pairs.yaml の全 pair が phases.yaml の全 phase に
               assertion を持つ（4 pair × 5 phase で 20 cell すべて
               非空、unreachable cell 検出）。
      整合 2 : phases.yaml の全 assertion id が Rust test runner で
               実装され、test_matrix.yaml の少なくとも 1 scenario
               でカバーされる。
      整合 3 : test_matrix.yaml の各 pair について full_dry_run +
               障害注入 scenario が両方存在する。
      整合 4 : pairs.yaml の exposed_concepts_affected が 05_提供
               機能カテゴリ 露出概念一覧と完全整合（drift 検出）。
      整合 5 : dry_run.lock.yaml は手書き禁止、build artifact と git
               の差分検出。
      整合 6 : 三軸接合 cross_axis_assertions が 07 / 32 / 39 の
               不変条件 id と参照整合（dangling 検出）。
      整合 7 : 1.0.0 ship 前 release は 4 pair の last_green_at
               すべて存在することを ship blocker として要件化。
      整合 8 : 1.0.0 後の release は 4 pair の last_green_at が
               365 日以内であることを release blocker として要件化。
      整合 9 : pairs.yaml に from / to の version_pin が記録されて
               おり、本命 OSS の version up と toolchain 整合が
               年次で再検証される。
      整合 10: dead spec 検出 : 参照されない pair / phase /
               assertion / scenario は CI fail。

■ 製造業 pack stress test（v1 の正当性証跡）
  - 4 pair × 5 phase × 製造業 workload を組合せた dry-run scenarios
    を v1 spec で覆える。新 L1+ カテゴリが確定した時点で v2 候補
    として pair 追加検討に入る。

      # | dry-run scenario                                 | pair                | 主要 phase

■ v2 拡張ルール
  - 新 pair の追加は purely additive。Distributed SQL カテゴリ
    （「05_提供機能カテゴリ」予約カテゴリ）が確定した時点で
    distributed_sql_pair を追加する。Vector Search カテゴリ
    （L1+、本命 pgvector）の primary pair も v2 候補として予約する
    （pgvector → Qdrant / Milvus / Weaviate、14_OSSライフサイクル
    適合仕様 vector_search_pair と整合）。primary 移行先確定の
    trigger は pgvector のライフサイクルイベント or adoption_demand。
  - 新 phase の追加は破壊的変更（major version up、「13_互換性
    ポリシー」と整合）。既存 4 pair × N phase の全 cell に対する
    assertion 追加が必須となる。
  - 既存 pair の primary 移行先変更（StackGres → Crunchy PGO 等）は
    破壊的変更扱い。dry-run の lock を refresh + 移行 toolchain の
    再実装。
  - cloud lock-in 移行先（Aurora / Neon / AWS MSK / Confluent Cloud
    / Temporal Cloud）への対応は v2 以降。本仕様の primary pair に
    は採用しない。

■ 1.0.0 ship blocker としての位置づけ
  - 04_Library が「dry-run の green を Library リリース条件に含める」
    と書く一方、何 pair × 何 phase かが未確定であった点は本仕様で
    解消する。
  - 1.0.0 ship 前の必須 :
      - pairs.yaml に 4 pair が登録され、phases.yaml に 5 phase ×
        4 pair = 20 cell すべて非空であること
      - test_matrix.yaml の 10 scenarios（4 full + 6 障害注入）が
        Testcontainers で全 green
      - dry_run.lock.yaml に 4 pair の last_green_at が記録されて
        いること
  - 上記が満たされない限り 1.0.0 release tag は作成しない。CI が
    物理的に block する。
  - 「運用コスト度外視」（CLAUDE.md）と整合し、1.0.0 完璧主義の
    具体形として本仕様が ship blocker を担う。

■ 長期収斂への作用
  - 三軸（07 / 32 / 39）と本仕様（08）の四つを同型構造で固めた
    ことで、tier1 / tier2 / tier3 / migration の単一の真が独立に
    保たれ、軸間の接合は test_matrix.yaml の cross_axis_assertions
    に集約される。
  - OSS lifecycle event（ライセンス変更 / 改廃 / サポート終了）が
    検知された時点で、既に green を維持している pair から正式移行
    先を選び、toolchain は本仕様の 4 ファイルを起点に運用に移す。
    「day-1 で並走」せず「常時 dry-run で待機」する哲学（04_Library
    L1+）の機械的具体形である。
  - L1+「単一 OSS 深耕 + 移行コミットメント」を migration 軸に
    完全転写したもの。pair 数を絞ることで toolchain 深度を最大化、
    purely additive な拡張で v2 以降に伸ばす。
