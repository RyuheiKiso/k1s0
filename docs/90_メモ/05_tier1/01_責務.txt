============================================================
tier1 の責務（infra 隠蔽）
============================================================

■ 方針
  - tier1 は、tier2 / tier3 に infra 層を意識させないことを使命とする。
  - infra 層の OSS / ミドルウェアへのアクセスは tier1 のファサードを
    経由させ、tier2 / tier3 から直接利用させない。
  - 設計の詳細は本ディレクトリ配下の各方針メモを参照。

■ 背景・狙い
  - 例：tier2 が独自に Kafka を直接利用していた場合、Kafka がライセンス
    変更等で利用不可となり RabbitMQ への差し替えが必要になった際、
    変更箇所の特定に大きな工数を要する。
  - tier1 で infra をラップしておけば、差し替え時の影響範囲を tier1 に
    限定でき、tier2 / tier3 の改修を最小化できる。
  - tier2 / tier3 のエンジニアは OSS の動向やライセンスに必ずしも
    精通しているわけではないため、選定・追従の責務は tier1 に集約する。

■ tier2 / tier3 への影響範囲（抽象化レベル別）
  - 「改修を最小化」の中身は Library の抽象化レベル（Lv）ごとに異なる。
    どこまで影響が及ぶかを事前に見積もれるよう、Lv ごとに以下を保証する。
      - L3 カテゴリ : 業界標準 wire / protocol（OIDC / OTLP / RESP / S3
        等）が支える領域。差し替え時、tier2 / tier3 のコードは無変更
        （再ビルド + 再デプロイのみ）。
      - L2* カテゴリ : 真に互換性の高い OSS 族が存在し、Library API が
        族の semantics 差を吸収できる領域に限定する。差し替え時、影響は
        「同族 OSS 内」に限定される。設定値・型・チューニング層に修正
        が入るが、業務ロジックは無変更。族の外への差し替えは保証外。
      - L1+ カテゴリ : 高セマンティクス領域。OSS の semantics 差が業務
        ロジックに必然的に染み出すため、複数 OSS 同時サポートを諦める
        代わりに単一 OSS の全機能を Library API として深く表現する。
        差し替えは日常運用ではなく OSS ライフサイクルイベント
        （ライセンス変更・改廃・サポート終了等）として扱い、その時には
        tier1 が移行 toolchain を成果物として提供する（移行コミットメ
        ント）。差し替え時、tier2 / tier3 の業務コードには設計レベルの
        修正が入るが、tier1 が toolchain でサポートする。
  - レベル定義および各カテゴリの割付・同族の具体定義は「04_Library」
    および「05_提供機能カテゴリ」を参照。
