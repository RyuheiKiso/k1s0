============================================================
test 位置づけ
============================================================

■ 5 階層 + 横断 layer 中の位置
  - tier1 : システム共通処理（Library / Server / 認証 /
            観測可能性）
  - tier2 : ドメイン業務共通化処理
  - tier3 : 個別業務の Web サイト / exe
  - infra : 物理 / 仮想基盤 + 制御平面
  - data  : データ層（保全 / lifecycle / 暗号化）
  - security : 全層を直交に貫く「脅威 ⊗ 軸 ⊗ 層」
              invariant の管掌 layer
  - ops   : 全層 + security を直交に貫く「loop ⊗ phase
            ⊗ 軸 ⊗ 層」 invariant の管掌 layer
  - test  : 全層 + security + ops を直交に貫く
            「verification_class ⊗ axis ⊗ phase ⊗ 層」
            invariant の管掌 layer ← 本層

  - test は tier1 / tier2 / tier3 / infra / data / security
    / ops の上下左右に並列して存在するのではなく、7 階層 ×
    16 軸の grid を直交に貫く meta-layer として位置づく。
    test は新しい責務を宣言するのではなく、既存軸の defense
    -in-depth 層 A〜E から発信される全 verification claim
    が必ず coverage matrix の cell に bind され、cell ごとの
    last_green_at が cadence 内に維持されることを assert
    する。
  - security が「脅威 × 軸 × 層」の grid に mitigation を、
    ops が「signal × phase × 軸 × 層」の grid に action を
    詰めるのに対し、test は「verification_class × axis ×
    phase × 層」の grid に artifact を詰める。三者は直交し、
    互いの incident / signal / verification を相互に bridge
    する：
      - test の v1_fault_chaos drill が想定外 mode に到達
        → ops の v1_drill_failure signal_class へ bridge
      - test の v1_contract_pair の breaking が PR に出現
        → ops の v1_change_induced へ bridge かつ Kyverno
          で deploy block
      - security の脅威 detect が新たな「攻撃者視点 fault
        injection」blueprint を必要とする → test の
        v1_fault_chaos の new scenario として追加

■ 上下方向の関係
  - 上方向（5 階層 + security + ops が test に依存する経路）：
      - tier1 transport（07）→ bidi stream / handshake /
        backoff の type_invariant + property_axiom +
        contract_pair が test 軸の matrix cell に登録、
        green が deploy 前提
      - tier1 migration（08）→ 4 phase の dry_run.lock
        .yaml は test 軸の Tekton Pipeline で生成、
        last_green_at の cadence 違反は deploy block
      - tier1 観測可能性（09）→ SemConv の type_invariant
        と OTel emit の scenario_replay を matrix cell
        として claim
      - tier1 SLO（13）→ v1_test_coverage_compliance /
        v1_mutation_score_compliance / v1_flaky_quarantine
        _compliance を SLO として登録、burn rate 越えは
        ops 経由で freeze
      - tier1 OSS lifecycle（14）→ pytest / hypothesis /
        Playwright / Pact / Litmus / pitest / Apache JMeter の
        v1_l1plus_primary 登録、EoL window は test の
        framework migration drill として演習
      - tier1 capacity（15）→ noisy_neighbor_isolation の
        property test を v1_property_axiom で claim
      - tier2 RLS FORCE（32）→ tenant 越境の attempt を
        v1_property_axiom（generative）と v1_fault_chaos
        （bypass attempt simulation）の双方で claim
      - tier3 client（39）→ client 4-state machine の
        v1_property_axiom（state transition closure）と
        v1_scenario_replay（offline → reconcile）を必須
      - infra topology（infra01）→ failover_drill / zone
        partition を v1_fault_chaos の blueprint として
        claim、last_green_at が 90 日以内
      - data preservation（data01）→ restore_drill を v1_
        scenario_replay の blueprint として claim、
        last_green_at が class.restore_drill_cadence_days
        以内
      - security threat（10_security/15）→ 各 threat に
        対する attacker simulation を v1_fault_chaos の
        blueprint として 1:1 bind
      - client distribution（12_client/15）→ 5 distribution
        _class 全てに対する v1_contract_pair（pact）と
        v1_scenario_replay（Playwright）を必須
      - ops loop（11_ops/15）→ 5 signal_class 全てに対する
        runbook の v1_scenario_replay drill を必須

  - 下方向（test が他層に依存する経路）：
      - 物理 enforcement の道具立て：
          - Kyverno admission policy（infra 14）：coverage
            cell の last_green_at cadence 違反 deploy block
          - Argo CD sync wave（infra 09）：test artifact
            生成 → 各層 spec への入力の同期
          - Tekton Pipeline（infra 04）：generative test の
            実行 + chaos drill 実行
          - ClickHouse（data / tier1/09）：test execution
            result の SoR
          - Perses（tier1/09 / data）：coverage matrix UI
          - OpenBao response wrapping（infra 04 + tier1/11）：
            chaos drill の break-glass token
        は全て他層が提供する。test は「これらが verification
        artifact 経路として bind されていること」を cross-
        axis assertion で保証するのみ。
      - verification_event の SoR：09 観測可能性 SoR
        （ClickHouse）+ test_event subject を物理 store と
        して共用、test は test_event subject schema の
        immutability 規律を宣言。

■ 横方向の関係（test ↔ 各軸）
  - test ↔ 07 transport：
      - bidi handshake / backoff jitter / circuit-breaker
        threshold を v1_property_axiom で claim、frame
        decoder を v1_fault_chaos で破壊性 input 注入。
  - test ↔ 08 migration：
      - 4 phase の dry_run（pre / dual / cutover / post）を
        v1_scenario_replay で順序付き journey として claim、
        cutover 失敗を v1_fault_chaos で chaos drill。
  - test ↔ 09 observability：
      - SemConv の type_invariant と OTel emit chain の
        scenario_replay を必須、span loss / sampling
        boundary を v1_property_axiom で claim。
  - test ↔ 10 auth：
      - login flow / token refresh / step-up を v1_
        scenario_replay、credential stuffing を v1_fault_
        chaos の attacker simulation として claim。
  - test ↔ 11 key：
      - rotation cadence の v1_scenario_replay drill、
        KMS API outage を v1_fault_chaos で注入、key
        envelope の type_invariant を claim。
  - test ↔ 12 schema：
      - schema migration の forward / backward compatibility
        を v1_property_axiom + v1_contract_pair で claim、
        breaking detection を Buf-breaking で物理 enforce。
  - test ↔ 13 SLO：
      - v1_test_coverage_compliance / v1_mutation_score_

  - test ↔ 14 OSS-lifecycle：
      - test framework 自体の v1_l1plus_primary 登録、

  - test ↔ 15 capacity：
      - per_tenant_volume の overflow を v1_property_axiom

  - test ↔ 32 data-tenant：
      - RLS FORCE bypass の attempt を v1_property_axiom
        の generative + v1_fault_chaos の attacker
        simulation で双方 claim。
  - test ↔ 39 client：
      - 4-state machine（fresh / dirty / syncing /
        reconciled）の transition closure を v1_property_
        axiom（stateful）で claim、offline → reconcile を
        v1_scenario_replay の journey で claim。
  - test ↔ infra01 topology：
      - failover / drain / migration を v1_fault_chaos の
        blueprint として claim、last_green_at が cadence
        内であることを Kyverno で deploy block 物理 enforce。
  - test ↔ data01 preservation：
      - restore_drill / replication_lag breach を v1_
        scenario_replay + v1_fault_chaos で claim、crypto

  - test ↔ security15 threat：
      - 全 threat 1 件に対し v1_fault_chaos の attacker

  - test ↔ client15 SDK distribution：
      - 5 distribution_class 全てに対し v1_contract_pair
        （pact）と v1_scenario_replay（Playwright）を
        必須、conformance_cadence_days 以内に演習。

      - 5 signal_class 全ての runbook を v1_scenario_replay

        postmortem を test 軸の v1_fault_chaos の corpus

■ 14 軸 + meta + security + ops + test + build_provenance 中の位置
  - test は 16 軸目の候補として 00_軸登録適合仕様 の
    meta-registry に entry 追加される（cap v1=20 中 18 / 20、
    残 2 余地。ops が 15 軸目、test が 16 軸目、build_
    provenance が 17 軸目、clock_integrity（08_infra/16）が
    18 軸目で全 18 軸が同 cap 内に登録される）。
  - 14 軸 + security + ops + build_provenance + clock_
    integrity が「層別 × 機能別 × 脅威別 × signal 別 ×
    supply chain 別 × 時刻 / 因果性別」軸であるのに対し、
    test は「verification_class 別 × axis 別 × phase 別」
    軸として直交方向に位置する。
    verification_class（type_invariant / property_axiom /
    contract_pair / scenario_replay / fault_chaos）を class
    軸として持ち、各 class が 5 phase（specify / generate /
    execute / triage / learn）の closure を要求する fan-
    out 構造を持つ。test 軸 coverage_matrix.lock.yaml の
    cell 数は 18 axis × 5 verification_class = 90 cell。
  - 00 meta（軸登録）の release_gate.lock.yaml AND-gate
    に、test の coverage_matrix.lock.yaml の `all_cells_
    green` 状態と mutation_score.lock.yaml の `monotonic_
    increase` 状態 + 10_security/17 の artifact_inventory
    .lock.yaml の `all_signed_green` + reproducibility_
    matrix.lock.yaml の `consensus_green` が入力される。
    全 (axis × verification_class) cell が green でない限り、
    または build provenance chain が green でない限り 1.0.0
    ship blocker。

■ 至高路線における位置づけの帰結
  - test は「個別軸の規律を再宣言する layer」ではなく、
    「個別軸の規律から発生する全 verification claim が
    coverage matrix で必ず closure される」ことを機械検証
    する meta-layer。test が新規物理機構を持ち込むことは
    原則しない（既存軸の verification 機構を bind するの
    み）。例外は coverage matrix generator / mutation
    score baseline / flaky quarantine engine / pact
    broker のような本質的に cross-axis な道具立てのみ。
  - 運用コスト度外視（CLAUDE.md 上位方針）の哲学に従い、
    verification coverage は最大化する。「現実には起こり
    にくいから property test を書かない」「test 実行時間
    が長いから coverage を間引く」判断は採らない。test の
    重みは test_minutes_per_week noise budget で表現する
    が、coverage cell entry 自体は省略しない。
  - 1.0.0 完璧 release：5 verification_class 全てに対し
    全 16 軸の cross-axis verification closure（5 phase
    全 green）、coverage matrix 全 cell green、mutation
    score quarterly monotonic increase 維持、flaky
    quarantine ゼロ、までを ship blocker とする。
