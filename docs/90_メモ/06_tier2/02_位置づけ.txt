============================================================
tier2 の位置づけ（tier1 / tier3 / Companion との境界）
============================================================

■ 階層関係
  - tier1 : システム共通処理（infra 隠蔽）。tier2 はこれを消費
    する。
  - tier2 : ドメイン業務共通化処理。本ディレクトリ。
  - tier3 : 個別業務に特化した Web サイト・exe。tier2 を消費
    する。
  - 詳細は「03_プラットフォーム構成」を参照。

■ tier1 への依存方針
  - tier2 は tier1 Library / Companion / Gateway 経由でのみ
    infra にアクセスする。tier1 が抽象化していない OSS / ミドル
    ウェアを tier2 が直接利用することは禁止する。
  - tier2 で「tier1 が抽象化していないが必要な機能」が発生した
    場合、その機能は tier1 に新規カテゴリとして提案する。tier2
    内で独自に OSS をラップして抽象化することは禁止する（強制
    機構は「16_強制機構」を参照）。
  - tier1 の抽象化レベル（L1+ / L2* / L3）の差は tier2 の業務
    コードに伝播する場合がある。tier2 は L1+ カテゴリの露出
    概念一覧（「05_tier1/05_提供機能カテゴリ」参照）を承知の
    上で、業務語彙に翻訳して tier3 に再露出する。

■ tier3 への提供方針
  - tier2 は API（Library 関数 / Service エンドポイント）と
    業務資産（Domain Event / Workflow 定義 / 決定表 / 業務
    マスタ / DB schema）を tier3 に提供する。
  - 提供形態は Library と Service の両方をサポートする
    （詳細は「08_配布形態」「09_Service運用方針」を参照）。
  - tier3 は tier2 の override 拡張点を通じて業務固有の差分を
    表現する。override 不可の不変条件は tier2 が contract test
    で守る（詳細は「07_業務資産所有権」を参照）。

■ Companion 経由クライアント（.NET Framework 等）への配慮
  - 「01_概要」および「05_tier1/04_Library」記載の通り、
    Library を直接組み込めない言語については tier1 が Gateway +
    Companion の枠を提供する。tier2 はこの枠の上で動作する
    tier3 も第一級の顧客として扱う。
  - tier2 が Library 形態で提供する API は、同等のセマンティクス
    で Service 形態（Gateway 経由 HTTP/1.1 + JSON unary /
    HTTP/1.1 + SSE server-streaming）でも提供する。Library
    専用機能・Service 専用機能を恒常的に持たない。
  - .proto を単一の真とする tier1 の方針に従い、tier2 が Service
    形態で提供する API も .proto を起点とする（External Proto に
    対応する形で派生させる。詳細は「08_配布形態」を参照）。

■ 表面 API の対称性
  - 同一機能を Library / Service の両形態で提供する以上、両者の
    表面 API はセマンティクス等価でなければならない。形態切替
    を業務コードの再設計を伴わずに行えることを設計目標とする。
  - 等価性は CI で証明する（詳細は「15_テスト方針」「16_強制
    機構」を参照）。
