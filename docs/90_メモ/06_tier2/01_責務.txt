============================================================
tier2 の責務（ドメイン業務共通化）
============================================================

■ 1.0.0 出荷スコープ
  - 1.0.0 で出荷する業界 pack：製造業のみ。
  - 本ディレクトリの全文書で扱う「業界横断」「業界 pack」「業界
    拡張」は tier2 の構造的前提であり、製造業以外の pack は後続
    バージョンで「03_業界拡張モデル」に従って追加する。
  - 製造業固有概念を業界横断層に置くことは禁止する（強制機構は
    「16_強制機構」を参照）。

■ 方針
  - tier2 は、tier3 にドメイン業務の共通化処理を提供する責務を
    持つ。
  - tier3 から見える業務の語彙（製造業であれば「設備」「ロット」
    「検査結果」等）を tier2 に集約し、業界 / ドメイン横断で
    再利用される業務資産（Domain Event / Workflow 定義 / 決定表 /
    業務マスタ / DB schema 等）を所有する。
  - tier3 は tier2 の提供する API / Service 経由でのみ業務資産に
    アクセスする。tier2 を迂回して tier1 Library を直接組み合わせ、
    業務処理を独自に再実装することは禁止する（強制機構は「16_
    強制機構」を参照）。
  - tier1 の OSS / ミドルウェアへの直接アクセスは禁止する。tier2
    内部の infra 接続はすべて tier1 Library 経由とする。

■ 背景・狙い
  - 例：tier3 が独自に「検査結果の確定」Workflow を Temporal で
    実装した場合、別の tier3 が同じ業務を別の Workflow で実装し、
    検査結果の確定基準・補償処理・通知タイミング等が乖離する。
    監査・規制対応・業務連携の各局面で破綻する。
  - tier2 で業務資産を所有しておけば、業界 / ドメイン横断の整合
    性を tier2 で担保でき、tier3 は業務固有の差分のみを表現すれば
    よい。
  - tier3 担当（ジュニア級）が業務不変条件を踏み抜く経路を構造で
    塞ぐ。

■ tier3 への提供方針
  - 業務資産の既定実装は tier2 が所有し、tier3 は本ディレクトリ
    「07_業務資産所有権」に従って override で業務固有の差分を
    表現する。
  - override の拡張点は contract test で守られ、tier2 のバージョン
    アップで silently 壊れない（詳細は「07_業務資産所有権」「15_
    テスト方針」を参照）。

■ tier3 への影響範囲（抽象化レベル別）
  - 「改修を最小化」の中身は tier2 の業務抽象化レベル（Lv）ごと
    に異なる。レベル定義は「04_抽象化レベル」を参照。
      - Lv 業界横断 : 業界に依存しない業務語彙（通知 / 監査 /
        承認 / 帳票 / マスタ管理 等）。tier2 の API 変更時、
        tier3 は override 部のみ追従。
      - Lv 業界共通 : 業界 pack 内で共通する業務語彙（製造業で
        あれば「設備」「ロット」等）。tier3 は override 部 +
        該当ドメイン参照部のみ追従。
      - Lv 業界固有 : 業界 pack 内ドメイン固有の業務語彙
        （FA / 調達 / 検査 各ドメイン）。tier3 は当該ドメイン
        利用部を追従。
      - Lv テナント固有 : テナントごとの差分は override / 設定
        で吸収。tier2 / tier3 のコード変更は伴わない（マスタ・
        ルール・権限の差分のみ）。

■ 非責務
  - 詳細は「17_非提供スコープ」を参照。
