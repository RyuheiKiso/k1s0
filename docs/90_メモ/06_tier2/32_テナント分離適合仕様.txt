============================================================
tier2 テナント分離適合仕様（v1）
============================================================

■ 位置づけ
  - 「06_マルチテナント方針」「14_業務エラー監査コンプライアンス」
    「16_強制機構」「22_権限モデル」「24_読み取りモデル方針」が
    散在的に宣言する次の四つを、機械可読な単一の真として一箇所に
    固定する仕様書 :
      (a) tenant_id 強制注入の static / runtime 二重防御
      (b) 生 SQL 経路の Library 境界での完全封鎖
      (c) State change / Outbox / Audit の同一トランザクション書込
      (d) PII 隔離と DB layer audit の機構接続
  - 本仕様は data 軸における defense-in-depth を 5 層で形式化し、
    各層の責務を分離して担保する。
  - 「07_tier1/07_Bidi適合仕様」が transport 軸の単一の真であるのと
    同型の枠組みを data 軸に転写したもの。dimension override 禁止 /
    dead spec 殺し / build artifact 化の規律はそのまま継承する。

■ 設計原則
  - テーブル分類は migration 時に確定する。
      実行時に「このテーブルは tenant 越境を許すか」を判定するのでは
      なく、テーブルを「何の class か」で migration 時点に固定し、
      class が RLS policy / 必須列 / 監査要件 / Outbox 要件 / TTL を
      一意に導出する。class カタログは 4 種に絞る（後述）。
  - 生 SQL は Library 境界で完全封鎖する。
      tier2 アプリ層から SQL 文字列を渡せる経路を一切提供しない。
      Library 内部の Repository abstraction だけが SQL を組み立て、
      その時点で session GUC（app.tenant_id 等）が必ず設定済みである。
      sqlx の query! / query_as! 系 macro は Library crate 内部のみ
      から呼べる workspace 構造とする。
  - State change / Outbox / Audit は同一 DB トランザクションで書く。
      3 表 atomic に書込み、async 配信は別レイヤ。subscribe 失敗で
      audit が欠落する事故を構造的に不可能にする。
      （「14_業務エラー監査コンプライアンス」業務イベント emit 必須化
        節が懸念する subscribe 失敗事故を、本仕様は構造的に解消する。）
  - defense-in-depth は 5 層で構成する。
      層 A : compile 時（Repository abstraction）
      層 B : lint / 公開 API snapshot
      層 C : cross-tenant integration test
      層 D : runtime（PostgreSQL Row Level Security）
      層 E : DB layer audit（pgaudit）
      任意の単層が破れても他層が必ず止める。RLS は最終 safety net。
  - dead spec を CI で殺す（07 と同枠）。
      table_classes.yaml に登録された class、transaction_units.yaml に
      登録された unit、migration.lock.yaml に列挙された table、いずれ
      も参照されなくなった時点で CI fail。

■ v1 テーブル class セット（4 class）
  - migration 時に各テーブルがいずれかの class に分類される。class が
    決まれば必須列 / RLS policy / 監査要件 / Outbox 要件が決まる。

      class            | tenant_id 列 | RLS                                   | 監査要件               | Outbox 要件        | 典型用途
      -----------------+--------------+---------------------------------------+------------------------+--------------------+---------------------------------
      tenant_scoped    | 必須         | tenant_id = current_setting(...)::uuid| 業務操作で audit_local | aggregate 変更で   | 業務 entity / aggregate / RM
                       |              |                                       |                        | outbox             |
      tenant_master    | 必須         | tenant_id = current_setting(...)::uuid| 変更で audit_local     | 任意（class で宣言）| テナント所有マスタ
      platform_global  | 不在         | RLS 無効（tenant 全員 read 可）      | 変更で全テナント横断   | platform-wide      | 通貨 / 国 / 業界共通分類
                       |              |                                       | audit                  | outbox             |
      pii_segregated   | 必須         | tenant_id + 専用 role check           | pgaudit + audit_local  | redact 後 outbox   | PII を含む user / partner

  - 各 class の不変条件 :

      - tenant_scoped
          - 必須列 : id, tenant_id, created_at, updated_at, version
          - RLS    : USING / WITH CHECK ともに tenant_id 一致
          - 監査    : INSERT / UPDATE / DELETE で audit_local emit を強制
          - Outbox  : 状態変化 → Domain Event を outbox 表に同 txn で挿入

      - tenant_master
          - 必須列 : id, tenant_id, created_at, updated_at, version
          - RLS    : tenant_scoped と同様
          - 監査    : 変更操作で audit_local emit、role 制限（master.admin）
          - Outbox  : マスタ class が要求する場合のみ emit

      - platform_global
          - 必須列 : id, created_at, updated_at, version（tenant_id 無し）
          - RLS    : 無効（tenant 全員 read 可、書込は platform_admin role）
          - 監査    : 変更時に platform-wide audit（tenant 識別子無しで全
                     テナント可視の sink に emit）
          - Outbox  : platform-wide topic に emit

      - pii_segregated
          - 必須列 : id, tenant_id, created_at, updated_at, version、
                     さらに各 PII 列ごとの暗号化済み別表参照
          - RLS    : tenant_id 一致 + 専用 role（support_engineer 等）
                     check
          - 監査    : audit_local emit に加え pgaudit による全アクセス
                     DB log
          - Outbox  : redact 済み payload で emit（PII 平文を outbox に
                     乗せない）

  - 4 class で v1 を covering する。新業務テーブルが 4 class のいずれ
    にも収まらないと判明した時点で、本仕様は v2 候補として class 追加
    検討に入る（v2 拡張ルール参照）。

■ session_context スキーマ（PostgreSQL session GUC）
  - tier1 Library が transaction 開始時に SET LOCAL する GUC を以下に
    固定する。Repository abstraction の transaction begin path で必ず
    設定され、業務コードからは設定経路を持たない。

      app.tenant_id         : uuid       Authorization context から導出
      app.actor_id          : text       Keycloak subject
      app.purpose           : text       business_op | support | export
                                         | migration | emergency
      app.delegation_chain  : text[]     委譲元 user の配列
                                         （空は通常操作）

  - GUC が SET されていない transaction で tenant_scoped /
    tenant_master / pii_segregated を SELECT すると RLS により 0 行
    が返る（fail-safe default）。
  - app.purpose は 22_権限モデル の Delegation / Emergency Override /
    28_セキュリティアーキテクチャ のサポートアクセスと連動する識別子。
    pii_segregated の RLS / pgaudit は app.purpose の値で挙動を変える。

■ 5 層 defense-in-depth

  ── 層 A : compile 時（Repository abstraction）
      - tier1 Library の Repository<T> trait は &TenantContext を
        必須引数として受ける。SQL は Library 内部で組立て、生 SQL
        を渡す経路を提供しない。
      - sqlx 系 macro は Library crate 内部からのみ呼べる workspace
        構造とする。tier2 アプリ層は Repository / UnitOfWork 抽象
        だけが見える。
      - 状態変更系の API は repo.persist_with_event(agg, event,
        audit_entry) のような unit 単位で公開し、3 表 atomic 書込
        を Library 内部で実施する。

  ── 層 B : lint / 公開 API snapshot
      - 「16_強制機構」層 5 と整合。Repository / UnitOfWork 公開 API
        に String 型 SQL 引数が現れたら CI fail。
      - app.tenant_id を SET しない経路から Repository を初期化する
        コードを言語別 analyzer で検出（Rust feature flag、C# Roslyn
        analyzer、Go go/analysis、TS ESLint rule）。
      - tier2 公開 API スナップショット（cargo public-api 等）に対し、
        tenant_id を引数で受ける関数が現れたら fail（成りすまし防止、
        「06_マルチテナント方針」テナント識別子の漏洩防止節と整合）。

  ── 層 C : cross-tenant integration test
      - Testcontainers で PostgreSQL を立ち上げ、二つの tenant_id で
        同時に書込・読込を実行。
      - 全 tier2 公開 API について「テナント A の context で B の
        resource にアクセス」を試行し、必ず DomainNotFound または
        AuthorizationDenied を返すことを検証。
      - contract test を「16_強制機構」層 1（tier3 リポジトリ側）にも
        同枠で展開し、tier3 が tier2 経由で書いたコードでも越境が
        起きないことを CI 必須とする。

  ── 層 D : runtime（PostgreSQL Row Level Security）
      - 全 tenant_scoped / tenant_master / pii_segregated table で
        ALTER TABLE ... ENABLE ROW LEVEL SECURITY および FORCE ROW
        LEVEL SECURITY を migration 時に適用。
      - app.tenant_id GUC が SET されていない transaction では RLS
        により 0 行 → fail-safe default。
      - Library 接続専用 role（tier2_app_user）は SUPERUSER でなく
        BYPASSRLS 属性も持たない。RLS bypass を物理的に不能とする。
      - 層 A〜C のいずれもが破れた最悪シナリオでも、層 D が必ず
        止める。これが本仕様の最終 safety net。

  ── 層 E : DB layer audit（pgaudit）
      - pii_segregated class の table は pgaudit で SELECT / UPDATE /
        DELETE を全数 DB log。
      - DB log は tier1 Logging（OpenTelemetry → ClickHouse、
        「05_tier1/05_提供機能カテゴリ」Observability / Logging）に
        bulk import し、tier2 の audit_local と相関 (trace_id 同期)。
      - sample 率 0%（全数）。pii_segregated 以外の class には適用
        せず、性能影響を最小限に抑える。

■ State change + Outbox + Audit の atomic 三表書込

  - 機構 :
      tier1 Library が提供する infrastructure tables :

          CREATE TABLE outbox (
            seq          bigserial PRIMARY KEY,
            tenant_id    uuid NOT NULL,
            aggregate_id uuid NOT NULL,
            event_type   text NOT NULL,
            payload      jsonb NOT NULL,
            created_at   timestamptz NOT NULL DEFAULT now(),
            trace_id     text,
            relay_status text NOT NULL DEFAULT 'pending',
            relayed_at   timestamptz
          );

          CREATE TABLE audit_local (
            seq                 bigserial PRIMARY KEY,
            tenant_id           uuid NOT NULL,
            actor_id            text NOT NULL,
            purpose             text NOT NULL,
            delegation_chain    text[] NOT NULL DEFAULT '{}',
            business_event      text NOT NULL,
            target_aggregate_id uuid,
            business_outcome    text NOT NULL,
            hash_prev           bytea,
            hash_self           bytea,
            created_at          timestamptz NOT NULL DEFAULT now(),
            relay_status        text NOT NULL DEFAULT 'pending',
            relayed_at          timestamptz,
            trace_id            text
          );

      上記 2 表は「14_業務エラー監査コンプライアンス」が要求する
      物理分離を保ちつつ、書込時点で同一 transaction に入る形を取る。

  - Library が強制する書込パターン :
        repo.persist_with_event(
            &aggregate,
            DomainEvent::PurchaseOrderConfirmed { ... },
            AuditEntry { business_event: "purchase_order.confirm", ... },
        )
      Library 内部 :
        BEGIN;
          UPDATE aggregate
            SET ...
            WHERE id = $1
              AND tenant_id = current_setting('app.tenant_id')::uuid
              AND version  = $2;             -- optimistic lock
          INSERT INTO outbox       ( ... );
          INSERT INTO audit_local  ( ... );  -- hash chain で hash_prev を計算
        COMMIT;
      - aggregate UPDATE が version mismatch → BusinessConflict、3 表
        まとめて rollback。
      - INSERT outbox / audit_local の失敗は Library bug 扱い、CI で
        property test により検出する。

  - async relay :
      - Outbox relay（tier1 Sidecar / Agent、「05_tier1/03_Server系」
        Sidecar / Agent 節）: outbox.seq の cursor 保持 → Kafka に
        publish → ack 後に relay_status='relayed' に更新。
      - Audit relay : audit_local.seq の cursor 保持 → ClickHouse に
        bulk insert（ReplacingMergeTree で idempotent）→ relay_status
        更新。hash chain は ClickHouse 側で再検証、定期 reconciliation
        job が hash 不整合を検出し alert（「27_信頼性運用準備」と整合）。
      - 両 relay は at-least-once、idempotent insert。
      - 欠落検出 : relay_status='pending' AND created_at < now() -
        interval '5 min' の row 数を Prometheus に emit、threshold 超
        で alert。

  - integrity property（CI 検証対象）:
      (P1) state change が durable に commit されたなら、対応する
           outbox row と audit_local row も同 transaction で commit
           されている（atomicity）。
      (P2) state change が rollback したなら、outbox / audit_local
           にも row は存在しない（atomicity）。
      (P3) outbox.aggregate_id と audit_local.target_aggregate_id は
           同一 transaction の seq 範囲で 1:1 対応する（reconciliation
           可能性）。
      (P4) async relay の停止中に state change が継続しても、3 表は
           DB に蓄積され続け、relay 復旧後に順次配信される（durability）。
      property test で commit 中の kill / kill -9 を注入し、(P1)〜(P4)
      が成立することを CI で検証する。

  - 元の論点解消 : 「14_業務エラー監査コンプライアンス」業務イベント
    emit の必須化節が懸念する subscribe 失敗事故（Domain Event 発行
    済みで監査未記録）は、本仕様の atomic 三表書込により発生し得ない。
    subscribe 側の失敗は relay の retry で吸収され、3 表の整合は
    transaction 境界で保証される。

■ Buf custom lint と migration tool の責務

  - sqlx-cli migration plugin の責務（縮約） :
      1. migration ファイルのヘッダ（@table_class / @audit_emitter /
         @outbox_emitter）を読み、table_classes.yaml と整合検査。
      2. 必須列の欠落、RLS 未有効、外部キー先 class の不整合（例：
         tenant_scoped から platform_global を参照する FK は許容、
         逆向きは禁止）で fail。
      3. migration.lock.yaml を生成。手書き diff があれば fail。

  - Buf custom lint（proto 側 / Domain Event）の責務 :
      1. Domain Event proto に必須 option :
            tier2.event.aggregate_class  : "manufacturing.purchase_order"
            tier2.event.tenant_id_field  : "tenant_id"
      2. aggregate_class が migration.lock.yaml に存在し、かつ
         tenant_scoped / tenant_master / pii_segregated いずれかで
         あること（platform_global は別 lint で平面 audit 経路）。
      3. pii_segregated の event は redaction marker（field option
         tier2.event.pii_redacted = true）が付与されていることを
         確認。

■ Capability negotiation との関係（07 との同期）
  - 07_Bidi適合仕様 の Capability Negotiation は transport を選ぶが、
    本仕様は data 軸で「app.purpose による RLS 挙動の切替」を行う。
    両者は orthogonal だが、span attribute / 監査 attribute の整合
    は OpenTelemetry Semantic Conventions の tier2 拡張（「16_強制
    機構」層 8）が共通の真として担保する。
  - 例：app.purpose='support' で発行された全 query は trace に
    purpose=support として記録され、ClickHouse 側で監査と相関可能。

■ 既存軸との接続関係（08_infra/16_時刻整合適合仕様 cross-axis double-bound）
  - tenant policy cache TTL の clock source は CLOCK_MONOTONIC_RAW
    必須化（wall-clock 依存禁止）。本仕様 session_context（app.tenant
    _id / app.actor_id / app.purpose / app.delegation_chain）の cache
    invalidation 判定で SystemTime / time.Now / DateTime.UtcNow を
    使う経路は 08_infra/16 dcv_pr_blocks_wall_clock_for_ttl により
    PR merge block。
  - RLS FORCE 状態の cache invalidation timestamp に HLC tuple を
    必須包含し、cross-region replication 下で因果性を保つ
    （08_infra/16 v1_application_hlc_only causality_discipline =
    hlc_mandatory に整合）。
  - atomic 三表書込（state change / Outbox / audit_local）の audit
    _local emit に HLC tuple を必須包含、wall-clock backwards step
    下でも 09 audit hash chain integrity が保たれる。
  - 18 軸 cross-axis 双方向 lock として 08_infra/16 の clock_
    causality_proof.lock.yaml の green が本仕様 atomic 三表書込
    integrity property P1〜P4 の物理保証となる。

■ CI 不変条件（3 ファイル + 5 層の関係性検査）

               class を持つ（unclassified table 検出）。

      整合 5 : pgaudit の対象 schema が pii_segregated の全 table を
               カバー（pg_catalog 照合）。
      整合 6 : migration.lock.yaml は手書き禁止、build artifact と git
               の差分検出。
      整合 7 : cross-tenant integration test の cell が全

      整合 8 : property test (P1)〜(P4) が全 aggregate × 全 unit に

               の少なくとも 1 メソッドから呼ばれる（dead unit 検出）。

■ 製造業 pack stress test（v1 の正当性証跡）
  - 8 操作を v1 unit / class に classify し、全て v1 の枠で機構が
    成立することを確認。

      # | 操作                              | unit                | 主要 class       | 検証ポイント
      --+-----------------------------------+---------------------+------------------+----------------------------------------
      1 | 発注確定 (Draft → Confirmed)      | state_change        | tenant_scoped    | 別テナント発注書 SELECT で 0 行 (RLS)
      2 | 検査結果改竄試行 (override)       | state_change        | tenant_scoped    | DomainError + audit_local emit
      3 | 仕入先マスタ追加                  | master_update       | tenant_master    | 別テナント仕入先 不可視
      4 | サポートエンジニアの PII 閲覧     | pii_access          | pii_segregated   | pgaudit + audit_local 同時 emit
      5 | テナント削除 (data export 後)     | cross_tenant_admin  | tenant_scoped × 全| platform_admin role + purpose=migration
      6 | 通貨コード platform-wide 更新     | cross_tenant_admin  | platform_global  | RLS 無し、admin role 検査
      7 | bulk import (29_データライフサイクル)| state_change × N | tenant_scoped    | dry-run context で commit せず、RLS 全適用

  - stress test は Testcontainers で PostgreSQL + relay を立ち上げ、
    全 8 操作を property test として実装する。新業務操作が unit に
    収まらないと判明した時点で、本仕様は v2 候補として unit / class
    追加検討に入る。

■ v2 拡張ルール
  - 新 class / 新 unit の追加は purely additive。
  - 既存 class の RLS policy 変更 / required column 変更 / unit の
    must_touch 変更は破壊的変更（major version up、「13_互換性
    ポリシー」と整合）。dual-write 移行 toolchain を tier1 が成果物
    として提供する（「05_tier1/04_Library」L1+ 移行コミットメント
    と同型）。
  - 命名は table class / unit ともに英小文字 snake_case 固定。
  - Distributed SQL カテゴリ（「05_tier1/05_提供機能カテゴリ」予約
    カテゴリ）が確定した時点で、本仕様の RLS 機構を Distributed SQL
    の row-level access policy（CockroachDB / Spanner-API 等）に
    マップする移行 toolchain を v2 で定義する。Single-leader と
    Distributed SQL の選択は tier3 アーキテクチャ設計時に排他選択
    される（「05_提供機能カテゴリ」記載）。

■ 長期収斂への作用
  - 本仕様の 3 ファイルに対し、新業務 entity / 新業界 pack の追加は
    purely additive な変更として進行する。migration ヘッダと proto
    option を書けば残りは機械的に降りる。
  - pii_segregated class は将来的に「独立 schema → 独立 DB →
    tenant 別暗号化キー」への段階的強化が可能。purely additive で
    進行する。
  - L1+ 「単一 OSS 深耕 + 移行コミットメント」（「05_tier1/04_Library」）
    の哲学を data 軸に転写したもの。単一 RDBMS（PostgreSQL）深耕 +
    Distributed SQL への移行コミットメントを採る。
