============================================================
tier2 のデータ保持 / アーカイブポリシー
============================================================

■ 方針
  - tier2 が扱うデータ（業務データ / Domain Event / 監査
    ログ / PII）はそれぞれ retention 要件が異なる。tier2 は
    カテゴリごとに retention policy を宣言し、機械的に強制
    する。
  - 規制要件が最優先。製造業の業界規制（医療機器 / 自動車 /
    食品 / 一般工業）で長期保管が要求される場合があり、
    tier2 はテナント別 / 業界 pack 別に policy を宣言できる
    構造とする。

■ カテゴリ別 retention の既定値
  - 業務データ（aggregate / entity の本体）:
      - 既定 : テナントとの契約期間 + 規制保管期間（製造業
        既定 10 年）。
      - 規制要件で延長 : 医療機器 / 自動車安全関連は最長
        30 年。
      - テナント運用が再構成可能（テナント設定で延長 / 短縮
        指定）。
  - Domain Event（Kafka）:
      - 既定 : 30 日間 retention（hot tier）。
      - その後はアーカイブ（cold tier）へ移送。
      - Schema Registry エントリは event 自体より長期保持。
  - 監査ログ :
      - 既定 : 7 年（多くの業界規制で最低要件）。
      - 規制要件で延長 : 製造業の品質関連は 10 年。
      - 監査ログは hash chain で改竄検知（オプション、規制
        次第。「14_業務エラー監査コンプライアンス」監査専用
        sink 節 参照）。
  - PII :
      - 既定 : 関係終了後 6 ヶ月で物理削除（GDPR 要件）。
      - 規制要件で短縮 : 業界 / 国によっては関係終了即削除。
      - 削除完了は監査エントリで記録（「06_マルチテナント
        方針」テナントライフサイクル節と整合）。

■ アーカイブ階層（hot / warm / cold）
  - hot（< 1 年）:
      - tier1 Relational Store（PostgreSQL）/ tier1 Messaging
        （Kafka） に保持。
      - 全 read API がリアルタイムで応答可能。
  - warm（1 〜 3 年）:
      - 業務データは PostgreSQL のパーティション切り出し
        （pg_partman、tier1 露出概念）で warm パーティション
        へ移送。read は同 API でアクセス可能だが latency
        増加を許容。
      - Domain Event は Kafka tiered storage / 別 retention
        policy のトピックへ。
      - 監査ログは ClickHouse の TTL 階層管理。
  - cold（3 年 〜 規制保管期間終了）:
      - tier1 Object Storage（Ceph RGW）にアーカイブ。
      - read は archive 専用 API（同期では応答せず、Long-
        running Operation として 結果を返却。「18_API設計
        規約」LRO 節と整合）。
      - 業務管理者向けの監査検索（「23_管理境界」参照）と
        コンプライアンス対応に用いる。

■ パーティション lifecycle と tier1 PostgreSQL
  - tier1 Relational Store / Single-leader の露出概念
    （「05_tier1/05_提供機能カテゴリ」L1+ 露出概念一覧）に
    パーティション lifecycle が含まれる。tier2 が業務カテゴリ
    ごとに「パーティション境界」「パーティション粒度（月 /
    四半期）」「移送タイミング」を宣言する。
  - tenant_id をパーティションキーに含める運用は性能影響と
    切替容易性のトレードオフで決定する。1.0.0 出荷時の既定は
    時系列パーティション（月 partition）で、tenant_id は索引
    のみ。

■ 削除のライフサイクル
  - 段階削除 :
      - soft delete : deleted_at 列を持つ。read API は除外、
        admin API は閲覧可能。grace period（既定 30 日）。
      - hard delete : grace period 終了でレコード物理削除。
        Domain Event「Deleted」を emit。
      - PII は physical erasure : hard delete + 関連する全
        backup / archive の対象 partition 再生成（GDPR 対応）。
  - 削除権限 : 業務管理者の master.admin / tenant_admin
    （「22_権限モデル」組み込みロール参照）に限定。緊急対応
    での削除は emergency_override 必須。

■ Backup と retention の関係
  - backup : 障害復旧（DR）のための短期コピー（既定 30 日
    rolling）。retention とは別の運用。
  - retention は「業務的に何年保持するか」、backup は「事故
    時に何時間前まで戻せるか」。混同しない。
  - PII の物理削除実行時、backup から物理削除前の状態を復元
    することは禁止する（規制違反になる場合があるため）。
    backup 保持期間の延長で PII が間接的に長期残存しないよう、
    PII テーブルは backup 対象から分離する設計を既定とする。

■ retention policy YAML 宣言
  - 全 retention policy をカテゴリごとに YAML で宣言する :
      - カテゴリ名、データ種別（業務データ / Domain Event /
        監査ログ / PII）、既定期間、最大期間、規制延長条件、
        アーカイブ階層、削除種別。
  - 宣言と実装（DB schema / Kafka 設定 / archive job）の整合
    を CI で検査する（「16_強制機構」と同枠）。

■ tier3 の拡張点
  - retention 期間の延長 / 短縮（tenant 設定 / 業界 pack
    設定）。
  - アーカイブ後の archive 検索 hook（業務固有の検索条件）。
  - 削除前 hook（追加業務承認 / 連携先への通知）。
  - 不変条件（override 不可）:
      - 規制要件で定められた最低保管期間の短縮
      - PII の規制要件最大期間の延長
      - 削除アクションの監査エントリ emit
      - hash chain 監査ログの改竄検知無効化

■ 1.0.0 出荷時の対応範囲
  - hot / warm / cold の 3 階層構造を提供。
  - 既定 retention policy を業界横断 + 製造業 pack に対し
    設定。
  - パーティション lifecycle 運用（pg_partman 経由）を tier2
    実装に組込み。
  - PII 物理削除フローを業界横断機能として提供。
