============================================================
tier2 業務 entity の状態遷移パターン
============================================================

■ 方針
  - 業務 entity（aggregate root）は明示的な state machine と
    して実装する。状態 / 遷移 / guard を proto で宣言し、
    Library / Service 双方で同一実装を生成する。
  - 状態遷移の標準パターンを tier2 が提供し、ドメインごとに
    バラバラな実装を防ぐ。

■ 標準ライフサイクル
  - 製造業の業務 entity の多くは以下のライフサイクルを取る :
      Draft → Confirmed → (Cancelled | Modified)
  - Draft :
      - 編集可能。aggregate 不変条件のうち軽量なもののみ
        チェック。
      - 業務的に「正式な記録」ではないため監査エントリは詳細
        を残さない（操作の存在のみ記録）。
  - Confirmed :
      - 業務不変条件をフルチェック。確定後は immutable。
      - Domain Event を emit して subscribe 側の処理を駆動。
      - 監査エントリに詳細を残す。
  - Cancelled :
      - 確定済み entity の取消。元 entity は変更せず取消済み
        フラグ + 取消理由 + 取消者 + 取消時刻 を記録。
      - 補償処理（後続業務の取消）を Workflow / Saga で実行。
  - Modified :
      - 確定済み entity の修正は「取消 + 新規作成」で表現
        する。元 entity を直接編集しない。
      - 元 entity と新 entity を業務的にリンク（modified_from
        / modified_to）。
      - 修正履歴は Domain Event の連鎖で表現可能。

■ 状態機械の実装規約
  - 状態 enum は proto / Schema 駆動で定義（「11_表現手段」
    参照）。
  - 遷移は明示的なメソッドとして提供（command パターン）。
    型レベルで状態遷移を表現する（型による不正遷移防止）。
    例：DraftOrder.confirm() → ConfirmedOrder のように、
        confirmed な型に対して再 confirm できないことを
        コンパイル時に保証する。
  - guard 条件 :
      - 業務不変条件を satisfy できなければ DomainError を
        返す（「14_業務エラー監査コンプライアンス」業務例外
        taxonomy 参照）。
      - guard は決定論的に実装する（外部 IO を guard 内で
        行わない）。

■ Domain Event 命名標準
  - 状態遷移に対応する Domain Event を必ず emit する :
      Created   : Draft 作成時
      Confirmed : Draft → Confirmed
      Cancelled : Confirmed → Cancelled
      Modified  : 修正連鎖の通知（modified_from / modified_to
                  を含む）
  - イベント名は <Aggregate><Verb> パターンを既定とする
    （例：PurchaseOrderConfirmed、InspectionResultCancelled）。
  - schema は tier1 Schema Registry に登録。互換性モードは
    BACKWARD_TRANSITIVE（「11_表現手段」参照）。

■ 監査履歴の残し方
  - 状態遷移ごとに監査エントリを 1 件 emit する（「14_業務
    エラー監査コンプライアンス」監査ログ節と整合）。
  - 監査エントリの business_event 名は Domain Event 名と
    一致させる（追跡可能性のため）。
  - 修正履歴は監査エントリの連鎖で再構成可能（DB の差分
    テーブルを別途持たない）。

■ 補償処理（Saga / Workflow）
  - Cancelled / Modified に伴う補償処理は tier1 Workflow
    （Temporal）の補償アクティビティで実装する（「07_業務資産
    所有権」参照）。補償処理の Workflow 定義は tier2 が所有
    し、tier3 は override 拡張点で補償アクションを差し替える。
  - 補償処理の冪等性は「18_API設計規約」冪等性節に従う。

■ 状態遷移の override 拡張点
  - tier3 が業務固有の差分を表現する位置 :
      - guard 条件の追加（不変条件は override 不可、追加
        チェックは可）
      - 状態遷移時の追加 hook（通知先、追加 Domain Event
        発行）
      - 補償処理の Activity 実装
  - override 不可 :
      - 状態の追加 / 削除（state machine の定義そのもの）
      - 既存遷移の削除
      - Domain Event の必須属性

■ 製造業 pack の適用例
  - PurchaseOrder（発注）: Draft → Confirmed → (Cancelled |
    Modified)。Confirmed で発注確定 Domain Event を emit、
    調達 workflow を駆動。
  - InspectionResult（検査結果）: Draft → Confirmed →
    Cancelled。「確定後は変更不可」を不変条件として強制
    （「07_業務資産所有権」override 利用例 参照）。修正は
    Cancelled + 新規 Confirmed で表現。
  - ProductionInstruction（生産指示）: Draft → Confirmed →
    (Cancelled | Modified)。実績収集との整合性を Domain Event
    で確保。

■ 状態遷移以外のパターン
  - Approval Workflow を伴う entity（多段承認）: 上記 Draft /
    Confirmed の間に PendingApproval state を挟む。承認 step
    は tier1 Workflow で表現。
  - 期限付き entity（時限）: Confirmed 後に Expired state に
    自動遷移。期限到達時の Domain Event を tier1 Workflow
    Timer で emit。
