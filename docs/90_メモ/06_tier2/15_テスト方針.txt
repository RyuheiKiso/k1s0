============================================================
tier2 のテスト方針
============================================================

■ 方針
  - tier2 は業務不変条件 / 業界中立性 / 拡張点 contract / 互換
    性の 4 軸でテストを構成する。
  - tier1 同様、CI を merge 条件とし、運用後の例外申請に依存
    しない。

■ 単体テスト
  - 対象 : ドメイン層（aggregate / entity / value object /
    domain service）。
  - 方針 :
      - フレームワーク非依存で実行可能（DI / DB / 外部 IO に
        依存しない）。
      - 業務不変条件をテストケースとして網羅する。「確定済み
        検査結果の改変が DomainError になる」等。
      - 業務例外 taxonomy（「14_業務エラー監査コンプライアン
        ス」参照）の各エラー型を発生させるケースをすべて含め
        る。
  - tier3 への要求 :
      - tier3 は override したドメインロジックの単体テストを
        必須とする。

■ 統合テスト（tier1 Library を含む）
  - 対象 : tier2 のリポジトリ / Domain Event 発行 / Workflow /
    決定表評価。
  - 方針 :
      - Testcontainers で tier1 backend（PostgreSQL / Kafka /
        Temporal / Keycloak / Valkey 等）を起動。tier1 が L1+
        / L2* / L3 で深耕している現行 OSS の本物を起動する
        （mock しない）。
      - tier2 リポジトリの強制注入（tenant_id 述語）が業務
        コードから回避不可能であることを統合テストで検証する。
      - Outbox + Domain Event 発行の atomic 性を実機で検証
        する。
  - tier3 への要求 :
      - tier3 が tier2 経由で業務処理を行う統合テストを推奨
        する（必須化はしない）。

■ Contract テスト（tier3 との API 契約 / override 拡張点）
  - tier2 公開 API の contract :
      - .proto / Schema 駆動の API について、wire 互換 / 振る
        舞い互換を Pact 系または同等の contract test で検証
        する。
      - 拡張点 contract は別 suite として用意し、tier3 リポジ
        トリの CI で実行することを Backstage Software Template
        で強制する（「16_強制機構」参照）。
  - 拡張点 contract の中身 :
      - 拡張点メソッドの入出力契約（型 / null 許容 / 例外型）
      - 拡張点呼び出しタイミングの契約（「override は同一
        トランザクション内で評価される」「副作用 emit を含む
        か」等）
      - 不変条件の保持 : tier3 の override 実装が業務不変条件
        を破らないことを property based test 風に検査する。

■ 業界中立性 conformance テスト
  - 第二業界 stub による検査（「03_業界拡張モデル」業界中立性
    の機械的担保 (3) と同枠） :
      - サービス業を想定した最小 stub pack を CI 専用で保持し、
        業界横断層の API が stub からも素直に消費できることを
        merge 条件とする。
      - stub は 1.0.0 出荷物に含めない。
  - 命名禁則 / 依存方向の検査 :
      - 業界横断層の公開シンボル snapshot に対し、業界固有語
        （「03_業界拡張モデル」(1) 参照）の出現を CI で fail
        させる。
      - 業界横断層 → 業界 pack の依存を CI で fail させる
        （「03_業界拡張モデル」(2) 参照）。

■ 互換性テスト（バージョン跨ぎ）
  - minor version up :
      - 公開 API snapshot の差分検査（後方互換のみ許可）。
      - Domain Event schema の互換性検査（tier1 Schema Registry
        の BACKWARD_TRANSITIVE モード）。
      - 拡張点 contract の不変性検査（「07_業務資産所有権」
        参照）。
      - 旧版 override 実装が新版 tier2 上で contract test に
        green であることを CI で検証。
  - major version up :
      - 移行 toolchain の dry-run（「13_互換性ポリシー」tier2
        移行コミットメント節と同枠）。
      - 旧版 → 新版 schema migration のゴールデン値検証。
      - 互換性 shim の有効期間内に旧版 API が新版 backend で
        動作することを検証。

■ 観測可能性のゴールデン値テスト
  - tier2 が emit する span / metric / 監査エントリの属性を
    ゴールデン値（YAML / JSON）と CI で照合する（tier1 Companion
    スキーマ整合方針と同枠：「05_tier1/04_Library」Companion
    役割 A 節を参照）。
  - 業務 metric（業務イベント発行件数 / Workflow 完了率 等）の
    semantic conventions 拡張についても同様に検査する
    （「09_Service運用方針」観測可能性節と整合）。

■ Library / Service の表面 API 等価性テスト
  - 同一機能を Library / Service の両形態で提供するカテゴリは、
    共通の conformance test suite を両形態で実行する
    （「08_配布形態」API 等価性節）。
  - 等価性破れを検出した API は両形態併存対象から除外し、
    Library 専用または Service 専用に明示分類する。

■ 性能 / 負荷テスト
  - 共有 Service の per-tenant 隔離特性（rate limiter /
    concurrency limiter）を負荷テストで検証する
    （「09_Service運用方針」リソース isolation 節と整合）。
  - tier1 Workflow / Messaging を含む end-to-end の SLO 達成を
    継続テストで検証する。

■ Backstage Software Template での組込
  - tier2 リポジトリ生成時、上記テスト枠を CI 設定とともに同梱
    する。tier3 リポジトリ生成時には、拡張点 contract test と
    業界中立性検査が CI に組み込まれる。
