============================================================
tier2 の互換性ポリシーと移行コミットメント
============================================================

■ 1.0.0 完璧主義との整合
  - 「01_概要」「CLAUDE.md」記載の通り、本プラットフォームは
    1.0.0 を完璧として出す方針であり、段階的リリースを採らない。
    tier2 もこの方針に従う。
  - 1.0.0 までは内部ベータ等を経ても外部 API としての互換性
    保証を行わない。1.0.0 リリース後から本ファイルの互換性
    ポリシーが発効する。

■ SemVer の運用
  - tier2 のバージョンは Library / Service を跨いで同一とする
    （「08_配布形態」バージョニング節）。
  - patch バージョン : バグ修正 / 内部実装改善 / observability
    強化等、tier3 の業務コード / override に影響しない変更。
  - minor バージョン : 拡張点 contract を保ちつつ、API 追加 /
    Domain Event 追加 / マスタ構造の前方互換変更等。tier3 の
    業務コードは無変更、override は無変更で動作することを保証
    する。
  - major バージョン : 拡張点 contract を変更する / 不変条件を
    変更する / 業界横断 API を業界共通 Lv に降格する等の破壊的
    変更。tier2 移行コミットメント（後述）が発効する。

■ 並行バージョン提供
  - 原則として並行提供しない（「08_配布形態」「09_Service運用
    方針」共有運用方針と整合）。複数バージョンの tier2 が共存
    すると、業務不変条件 / 規制対応 / 監査の整合性を維持できな
    くなる。
  - 例外として major version up の移行期間に限り、新旧 2 バー
    ジョンの並行運用を時限的に許容する。移行期間は最長 6 ヶ月
    とし、終了時点で旧バージョンを撤去する。

■ tier2 移行コミットメント（major version up 時）
  - tier1 が L1+ カテゴリで提供する「移行コミットメント」
    （「05_tier1/04_Library」L1+ 移行コミットメント節）の業務
    軸版として、tier2 も major version up 時に移行 toolchain を
    成果物として提供する。
  - 移行 toolchain の成果物（major 上げごとに整備） :
      - schema 差分検出 :
          DB schema、Domain Event schema、業務マスタ schema、
          .proto API の機械的 diff。
      - dual-write 移行支援 :
          移行期間中、新旧 schema / 新旧 Domain Event に二重
          書き込みする tier2 抽象。書込 / 読取の正解を ramp で
          切り替える（tier1 Outbox + Schema Registry 互換モード
          を活用）。
      - 業務データ migration :
          DB の logical migration（必要なら tier1 PostgreSQL
          logical replication を活用）。Domain Event の旧
          schema → 新 schema 変換ジョブ。
      - override 移行ガイド :
          拡張点 contract の差分を機械的に列挙し、tier3 側の
          override 修正点をチェックリストとして提供する。
      - observability 連続性 :
          移行前後で span / metric の意味論を維持する Collector
          プロセッサ設定とゴールデン値テスト（tier1 Companion
          スキーマ整合方針と同枠）。
      - 互換性 shim :
          tier3 が新版 API へ段階的に移行できるよう、旧 API を
          薄い shim として一定期間維持する（major +1 期間内
          のみ）。
  - 維持責務 :
      - 上記 toolchain は major version up 時のみに作るのでなく、
        tier2 本体と同じリポジトリで継続的に維持する。tier2 の
        minor version up 時にも toolchain を CI で回す。
      - 「次の major で何を変えるか」を継続的に candidate list
        として保持する（候補 list に対する dry-run 移行テストを
        年次で実施）。

■ 業界横断 Lv の降格 / 業界 pack 統合 / 削除
  - 業界横断 Lv の API を業界共通 Lv に降格する場合（第二業界
    stub conformance を満たさなくなった場合等）、major version
    up として扱う。tier3 移行ガイドで降格内容と影響範囲を明示
    する（「03_業界拡張モデル」「04_抽象化レベル」参照）。
  - 業界 pack の統合 / 削除は major version up として扱う。
    1.0.0 出荷時点で業界 pack の削除を計画していないが、業界
    そのものが対象 fleet から退役する場合に発生する。

■ 拡張点 contract の安定性
  - 拡張点（override 可の API / Schema / Workflow / 決定表）の
    contract は minor version up で破らない。
  - tier2 の公開 API snapshot に拡張点 contract を含め、CI 検査
    で minor version での破壊を検出（「16_強制機構」参照）。
  - tier3 が override で踏み抜いている領域（contract 範囲外）
    の互換性は本保証の対象外（「07_業務資産所有権」override
    後の互換性責務節）。

■ tier1 のバージョン追従
  - tier2 は tier1 Library のメジャーバージョンに追従する。
    tier1 の major version up 時は tier1 の移行 toolchain
    （「05_tier1/04_Library」L1+ 移行コミットメント節）を
    使って tier2 を移行し、tier2 の API 表面に tier1 の major
    変更が業務語彙レベルで漏れないことを保証する。
  - tier2 の minor version up で tier1 の minor 上げを取り込む
    場合、tier3 の業務コード / override に影響しないことを CI
    で検証する。

■ 監査 / コンプライアンス観点での bumping 制約
  - 規制要件に関わる業務不変条件の変更は major version up に
    限定する。minor / patch では実施しない（変更履歴の追跡
    可能性を担保するため。詳細は「14_業務エラー監査コンプライ
    アンス」参照）。
