============================================================
tier2 の管理境界（業務管理 API / 運用画面 / 緊急対応）
============================================================

■ 方針
  - tier2 が業務資産（マスタ / ルール / 決定表 / Workflow /
    監査）を所有する以上、その管理経路（編集 / レビュー /
    承認 / 監査検索 / 緊急対応）も tier2 が提供する責務を
    持つ。
  - tier3（業務エンドユーザー向けアプリ）と業務管理経路を
    明確に分離する。両者は別 API surface / 別 UI として扱う。

■ 管理 API の分離
  - tier2 は二系統の API surface を提供する :
      - 業務 API : tier3 のエンドユーザーが操作する。発注
        作成 / 検査記録 / 進捗確認 等。
      - 業務管理 API : 業務管理者が操作する。マスタ編集 /
        決定表編集 / Workflow 設定 / 監査検索 等。
  - 業務管理 API は別 path（/admin/v1/...）/ 別 proto
    package（tier2.<pack>.admin.v1）で分離する。
  - 業務管理 API のロール（「22_権限モデル」組み込みロール
    参照）は業務 API のロールと別系統（tenant_admin /
    master.admin 等）。

■ 運用 UI（Backstage プラグイン）
  - 業務管理 UI は Backstage のプラグインとして tier2 が提供
    する。
  - スコープ :
      - マスタ編集（CRUD UI、テナント別）
      - 決定表編集（DSL エディタ + テスト実行）
      - Workflow 設定（cron / 承認ルート）
      - 監査検索（business_event / actor / target で検索）
      - 通知履歴 / 失敗ジョブ再実行
  - tier3 のエンドユーザー向け UI は対象外（「17_非提供
    スコープ」UI 節と整合）。

■ マスタ編集の workflow
  - マスタ編集は「編集 → レビュー → 承認 → アクティベー
    ション」の workflow を経る :
      - 編集 : Draft 状態でマスタを変更（業務 entity の状態
        遷移パターンと同じ。「19_状態遷移パターン」参照）。
      - レビュー : 別ユーザーが内容確認。
      - 承認 : 業界横断「承認 Workflow」（「10_提供機能
        カテゴリ」参照）に乗せる。
      - アクティベーション : 承認後にマスタ反映。
  - 規制対応マスタ（業界規制 / コンプライアンス関連）は承認
    必須。一般マスタ（テナント運用上の値）は workflow を
    skip 可能（テナント設定で選択）。

■ 決定表編集の workflow
  - 決定表編集も同様に「編集 → テスト → レビュー → 承認 →
    アクティベーション」の workflow を経る :
      - テスト : 編集中の決定表に対し、過去ケース / golden
        ケースでの評価結果を確認できる UI を提供。
      - 承認 : 業界横断「承認 Workflow」に乗せる。
      - アクティベーション : 承認後に ZEN Engine の評価
        チェーンへ反映。
  - tier3 の override 拡張点経由で挿入する「上書き決定表」
    も同様の workflow を経る（「07_業務資産所有権」決定表
    override と整合）。

■ 監査検索 API
  - 業務管理 API の一部として、監査エントリ検索を提供 :
      - 検索条件 : tenant_id / actor / business_event /
        target / 期間。
      - レスポンス : 監査エントリの一覧（pagination は
        「18_API設計規約」参照）。
      - 結果は監査ログ専用 ClickHouse テーブル（「14_業務
        エラー監査コンプライアンス」参照）から取得。
  - 監査検索行為自体も監査対象（誰が何を検索したかを別の
    監査エントリに残す）。
  - 規制対応の長期監査検索は別系統（archive 層への問合せ）
    になる場合がある（「26_データ保持」と整合）。

■ 緊急対応の経路
  - インシデント発生時の緊急対応（規制対応 / 業務影響回避）
    の経路を業務管理 API として提供する :
      - emergency_override 起動 / 解除（「22_権限モデル」
        緊急時の override 節参照）。
      - 失敗ジョブの手動再実行（「20_スケジューラ・バッチ」
        参照）。
      - Workflow の手動補償実行（事故発生 entity の業務的
        取消 + 補償実行）。
      - マスタの緊急更新（承認 workflow を skip するモード、
        emergency_override 必須）。
  - 緊急対応 API はすべて詳細監査 + 事後レビュー必須。

■ プラットフォーム運営者と業務管理者の境界
  - プラットフォーム運営者（tier1 / インフラ運用責任者）:
      - tier1 backend の運用、Cluster 管理、tier2 Service
        の deploy / upgrade。
      - 個別テナントの業務データには触れない。
  - 業務管理者（テナント / 業界 pack の運用責任者）:
      - マスタ / ルール / Workflow 設定 / 監査検索 / 緊急
        対応。
      - tier1 backend には触れない（tier2 業務管理 API の
        み使用）。
  - 両者の境界は role / scope で機械的に区別する。プラット
    フォーム運営者の特権（cluster admin 等）と業務管理者の
    特権（業務管理 API admin）は別系統。

■ tier3 の拡張点
  - 業務管理 UI に tier3 固有の管理機能を追加（Backstage
    プラグイン拡張）。
  - マスタ workflow にテナント固有の追加承認 step を override
    で挿入。
  - 緊急対応の事後レビュー hook を override で実装。
  - 上記すべて「07_業務資産所有権」override 契約に準拠。
  - 不変条件（override 不可）:
      - 監査検索行為自体の監査
      - emergency_override の time-bound / 詳細監査要件
      - 規制対応マスタの承認必須化
