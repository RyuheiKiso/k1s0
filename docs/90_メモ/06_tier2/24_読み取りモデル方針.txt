============================================================
tier2 の読み取りモデル方針（CQRS / read model / 検索 / 集計）
============================================================

■ 方針
  - tier2 は CRUD + Outbox event を既定とする（純粋な event
    sourcing は採用しない）。理由 :
      - tier1 Relational Store（PostgreSQL）の機能（トラン
        ザクション / 制約 / 索引）を業務不変条件の担保に直接
        活用できる。
      - 業務担当 / 監査 / 規制対応で「現在状態の SQL 直接
        照会」を維持できる。
      - event sourcing 固有の運用コスト（snapshot / replay /
        rebuild）を業界 pack 開発で常時負担する必要がない。
  - 一方で、Domain Event は同等に重視する。aggregate の状態
    変更は必ず Domain Event を emit（Outbox 経由）し、
    subscriber 側で派生処理 / 派生モデルを維持する（「14_業務
    エラー監査コンプライアンス」業務イベント emit の必須化 /
    「07_業務資産所有権」と整合）。

■ 書込モデルと読込モデルの境界
  - 書込モデル : aggregate root と関連 entity / value object。
    tier1 PostgreSQL の正規化テーブル。
  - 読込モデル :
      - 単純な read（aggregate ID で取得 / 単純条件検索）:
        書込モデルから直接取得。専用 read model を作らない。
      - 跨 aggregate / 跨 context の read（業務サマリ / 進捗
        ダッシュボード等）: 専用 read model を作る。書込
        モデルの join では性能が出ない / context 越境を避け
        たい場合に該当。

■ Read model 更新の責務
  - Domain Event subscriber が read model を更新する。
    subscriber は tier2 Service 内に閉じる（tier3 が独自に
    subscribe する経路は禁止。「07_業務資産所有権」「16_強制
    機構」参照）。
  - Domain Event Hub（「10_提供機能カテゴリ」参照）は tier2
    内部基盤として subscribe を仲介する（tier3 直接利用なし）。
  - 更新の冪等性 : Domain Event は at-least-once 配送のため、
    subscriber は冪等に実装する（event ID + processed_at
    テーブルで重複検出）。
  - 順序保証 : 同一 aggregate 内の event 順序は Kafka
    partition で保証（aggregate ID を partition key に使用）。

■ Eventual consistency と業務的影響
  - 書込確定から read model 反映までの遅延（通常 < 1 秒）が
    存在する。業務 API 設計時に以下を区別する :
      - 厳密な consistency が必要な read（「自分が直前に
        作成した entity を即時取得」等）: 書込モデルから直接
        取得（書込トランザクションと同じ DB session で）。
      - eventual consistency で十分な read（業務サマリ /
        ダッシュボード等）: 専用 read model から取得。

■ 検索（Search）
  - 単純文字列検索 : tier1 PostgreSQL pg_trgm 拡張による部分
    一致 / 類似度検索（「05_tier1/05_提供機能カテゴリ」露出
    概念一覧 参照）。
  - 全文検索（業務文書 / コメント等）: tier1 PostgreSQL の
    全文検索（tsvector）を既定。専用全文検索 OSS は tier1 に
    新規カテゴリとして提案する経路に限定（「02_位置づけ」
    参照）。
  - 意味検索（Vector Search）: tier1 Vector Search カテゴリ
    （pgvector）を tier2 が業務語彙でラップして提供。1.0.0
    出荷時の用途は「品目の類似検索」「不良票の類似事例検索」
    等に限定。

■ 集計（Aggregation）
  - リアルタイム集計（業務 KPI / 進捗ダッシュボード）:
      - Domain Event subscriber が集計テーブル（read model
        の一種）を更新する。
      - 集計テーブルは時系列の append-only 構造を既定とし、
        過去値の改竄を防ぐ（監査追跡可能性）。
  - ad-hoc 集計（業務分析 / レポート）:
      - 既定では tier1 のプラットフォーム標準 BI（Apache
        Superset over ClickHouse、「05_tier1/06_非提供
        スコープ」可視化 UI 参照）に Domain Event / 監査ログ
        を流して使う。
      - tier2 自体は ad-hoc 集計用 API を提供しない（「17_
        非提供スコープ」業務固有の長期データ分析 節と整合）。

■ Cache（tier1 Valkey の業務側活用）
  - tier1 KeyValue / Cache（Valkey）を tier2 が業務語彙で
    wrap し、以下の用途に限定して使用する :
      - 高頻度参照のマスタ（業務カレンダー / 為替レート /
        単位換算係数 等）の cache。TTL + Domain Event 駆動の
        invalidation で整合維持。
      - per-tenant rate limiter / concurrency limiter の
        counter store（「09_Service運用方針」リソース
        isolation 節と整合）。
      - Idempotency-Key の結果キャッシュ（「18_API設計規約」
        冪等性節と整合）。tier3 client の rebase 後 retry では
        新キーが発行され元キーと chain 関係（original_idempotency
        _key + chained_idempotency_key）を持つ（「07_tier3/39_
        クライアント状態適合仕様」整合）。tier2 Idempotency
        cache は chain 親子関係を含めて dedup 判定し、chain 内
        で同一 base_version + 同一 actor の op は同一結果を返す
        （rebase 後 payload 不一致による stored response 衝突
        を防ぐ）。chain メタデータは結果キャッシュ entry に
        付与、TTL は元キーと chain 全体で同一（24h）。
      - 分散ロック（OptimisticLock で表現できないケースの
        み）。
  - 業務 entity の状態 cache は禁止する（cache が真と DB が
    真の乖離で業務不変条件を踏み抜くため）。

■ 並行制御
  - 既定は optimistic locking（version 列）。aggregate root
    に version 列を必須とし、UPDATE 時に WHERE version = ?
    で検出する。version 不一致は BusinessConflict エラー
    （「14_業務エラー監査コンプライアンス」参照）として
    返す。
  - pessimistic locking（SELECT FOR UPDATE）は限定使用 :
      - 連番採番 / 在庫引当 等の競合が確実な処理に限定。
      - tier1 PostgreSQL の advisory lock 露出概念
        （「05_tier1/05_提供機能カテゴリ」L1+ 露出概念一覧）
        を tier2 が業務語彙でラップ。
  - tier3 の override では、上記方針を逸脱しないこと。

■ tier3 の拡張点
  - 業界横断 / 業界 pack に追加の read model を tier3 が必要
    とする場合 :
      - 既存 Domain Event を subscribe する追加 subscriber を
        tier3 が tier2 経由（業務 API でなく拡張点経由）で
        登録できる仕組みを tier2 が提供する。
      - tier3 が独自に Kafka を直接 subscribe する経路は禁止
        （「07_業務資産所有権」「16_強制機構」参照）。
  - キャッシュ追加 / 集計 read model 追加も tier2 拡張点
    経由。

■ 1.0.0 出荷時の read model
  - 業界横断 read model :
      - 通知配信履歴 / 監査エントリ集計 / 承認 workflow 進捗
        サマリ
  - 製造業 pack read model :
      - 生産進捗ダッシュボード（FA）
      - 発注 → 検収進捗（調達）
      - 検査結果集計 / 不良率推移（検査）
