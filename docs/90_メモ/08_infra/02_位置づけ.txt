============================================================
infra 位置づけ
============================================================

■ 5 階層中の位置
  - tier1 : システム共通処理（Library / Server / 認証 /
            観測可能性）
  - tier2 : ドメイン業務共通化処理
  - tier3 : 個別業務の Web サイト / exe
  - infra : 物理 / 仮想基盤 + 制御平面 ← 本層
  - data  : データ層（保全 / lifecycle / 暗号化）

  - infra は tier1 / tier2 / tier3 / data 全てが動作する
    物理基盤を提供する。tier1 / tier2 / tier3 / data の各
    spec が「物理層で強制」と書く defense-in-depth 層 E は
    全て infra の責務として降りる。

■ 上下方向の関係
  - 上方向（tier1 / tier2 / tier3 が infra に依存する経路）：
      - tier1 Server 系は Envoy Gateway / Istio mesh の上で
        動作する → infra が substrate 提供
      - tier1 Library は kube-apiserver の Service / Pod
        topology を前提に AuthContext を伝播 → infra が
        topology を保証
      - tier2 Service は CloudNativePG / Kafka / Valkey /
        ClickHouse の上で動作する → infra が storage substrate
        提供
      - tier3 SPA / exe は Argo CD ApplicationSet で配信 →
        infra が GitOps 制御平面を提供

  - 下方向（infra が data 層に対して提供する経路）：
      - data 層の v1_cross_region_replicated は infra の
        v1_multi_region_active_passive / v1_multi_region_
        active_active topology 上でしか動作不能 → infra が
        topology の物理基盤を提供、data が論理保全を担う
      - data 層の暗号化 at rest は OpenBao + 11 鍵管理適合
        仕様の鍵を、infra の Secrets 配信経路（External
        Secrets）で配布

■ 横方向の関係（infra ↔ tier 各層）
  - infra ↔ tier1：
      - tier1 の Transport Adapter Layer の substrate は
        Envoy Gateway（infra 提供）。bidi semantics は
        tier1 が定義し、transport 物理は infra が提供。
      - tier1 09 観測可能性 SoR の ClickHouse は infra の
        Altinity Operator 上で動作。
  - infra ↔ tier2：
      - tier2 Service の Pod は infra の Kubernetes 上で
        動作、Argo CD ApplicationSet 経由で配信。
      - tier2 32 テナント分離（RLS FORCE）の物理基盤は
        infra の CloudNativePG。
  - infra ↔ tier3：
      - tier3 SPA は Argo CD で CDN / S3 経由配信、または
        infra 上の static service として serve。
      - tier3 exe（.NET Framework）の更新は infra の Argo
        Rollouts traffic shift で段階配信。
  - infra ↔ data：
      - infra topology_class（v1_multi_region_active_*）と
        data preservation_class（v1_cross_region_replicated）
        が preservation_substrates.lock.yaml で双方向 lock。
        どちらか一方だけ宣言する経路は admission block。

■ 13 軸 + meta 中の位置
  - 13 軸：07 transport / 08 migration / 09 observability /
    10 auth / 11 key / 12 schema / 13 SLO / 14 OSS lifecycle
    / 15 capacity / 32 data-tenant / 39 client / infra01
    topology（本層）/ data01 preservation
  - infra は 13 軸の 1 軸（topology）の保有層であると同時に、
    全 13 軸の defense-in-depth 層 E（物理 enforcement）を
    実装する基盤層という二重の役割を持つ。
  - 00 meta（軸登録）の release_gate.lock.yaml AND-gate に、
    infra01 の failover_drill.lock.yaml が green 状態として
    入力される。

■ 至高路線における位置づけの帰結
  - infra は「物理 enforcement の最終 layer」として、文章
    運用に依らず必ず守られる規律を担う層である。
  - 運用コスト度外視（CLAUDE.md 上位方針）の哲学に従い、
    cluster の冗長度・drill 頻度・supply chain 検証は最大
    化する。「運用が大変だから drill cadence を緩める」
    判断は採らない。
  - 1.0.0 完璧 release：5 topology_class（v1_single_zone を
    除く 4 class）全てで drill green、全 OSS が L1+ primary
    として oss_inventory.lock.yaml に登録、Kyverno admission
    policy 完全適用、までを ship blocker とする。
