============================================================
data マイグレーション方針
============================================================

■ 一文方針
  - 全 schema 変更は expand-contract pattern で online 適用、
    rolling migration / dual-write / dual-read を経て
    breaking 変更を実質的に non-breaking に変換する。
    forward-only migration、phantom write、Outbox pattern
    を物理 enforce、preservation_class の RPO / RTO を
    migration 中も崩さない。schema 進化の意味論は 05_tier1
    /12 が決め、data 層は物理実行を責任分担する。

■ migration の 3 フェーズ
  - フェーズ A：expand（追加のみ）
      - 新 column / 新 table / 新 index / 新 enum value /
        新 topic / 新 schema subject を追加
      - 旧 schema は破壊しない、新旧同時 read 可能
      - tier1 Library が新 schema を fetch、application は
        新 path を実装するが旧 path も維持
      - 物理：sqlx-cli で `ADD COLUMN ... DEFAULT NULL` の
        ように non-blocking、`CREATE INDEX CONCURRENTLY`
        を必須化（Postgres）
  - フェーズ B：dual-write / dual-read
      - application 側 release で「新 column / topic にも
        書く」「新 column を読む（旧から fallback）」を
        段階適用
      - data 層は backfill job（過去行を新 column に埋める）
        を Argo CD CronJob で発火
      - dual 期間は preservation_class 別 minimum：
            v1_local_only           : 1 d
            v1_zone_replicated      : 7 d
            v1_cluster_replicated   : 14 d
            v1_cross_region_repl.   : 30 d
            v1_global_replicated    : 60 d
  - フェーズ C：contract（旧除去）
      - 全 row が新 column に値を持つことを確認、旧 column
        / topic / subject を deprecate
      - dual 期間経過後、別 PR で旧除去 migration 発火
      - 物理：`DROP COLUMN`、Kafka topic 削除、Apicurio
        subject archive

■ phase ごとの CI gate
  - フェーズ A の PR：
        - expand-only か、breaking 検出時 fail
        - 新 column に NOT NULL を最初から付与する PR は fail
          （DEFAULT 後に backfill して contract で NOT NULL
          化が正しい順序）
        - CREATE INDEX が CONCURRENTLY 付きか確認（large
          table）
  - フェーズ B の PR：
        - dual-write 期間が preservation_class min を満たす
        - backfill job の dryrun が成功
        - Apicurio compatibility rule 適合
  - フェーズ C の PR：
        - 全 row backfill 完了 SLI green
        - dual 期間経過確認
        - 旧 column / topic 参照ゼロ（grep + ClickHouse
          access log で検証）

■ expand-contract の rolling migration（PostgreSQL）
  - sqlx-cli の migration は forward-only、reverse 禁止。
  - destructive DDL（DROP COLUMN / DROP TABLE / DROP NOT
    NULL constraint） は contract phase の専用 migration
    として独立 PR 化。
  - rename column の代わり：
        1. expand：new_column_name 追加 + trigger（旧 ↔ 新
          を sync）
        2. dual：application が新 column を read/write
        3. contract：trigger 削除 → 旧 column 削除
  - 大規模 backfill：partition 単位で chunk 化、各 chunk
    で `BEGIN; UPDATE ... LIMIT N; COMMIT;` で MVCC bloat
    制御。

■ Kafka topic / subject migration
  - topic 増設：新 partition を追加（Strimzi KafkaTopic CR
    の partitions 増加、reduce は禁止）。
  - schema evolve（subject）：
        - BACKWARD compat：新 field optional 追加 OK
        - FORWARD compat：旧 reader が新 schema を読める
        - FULL compat：両方
        - breaking change：別 subject（`-v2` suffix）として
          expand → consumer 側 dual subscribe → 旧 subject
          archive
  - retention.ms 変更：preservation_class 切替を伴うので、
    KafkaTopic CR では直接変更不可（class instance を
    新 class に再作成、message を MM2 で copy）。

■ ClickHouse migration
  - go-migrate で `ALTER TABLE ... ADD COLUMN` は ON
    CLUSTER で全 replica 同期。
  - reorganize（ORDER BY / PARTITION BY 変更）：destructive、
    新 table を別名で作成 → INSERT INTO ... SELECT で copy
    → atomic RENAME（v1.4+）→ 旧 table archive。
  - distributed table の DDL：mutations は keeper で
    sequential 実行、長時間 mutation は分割。

■ Outbox pattern（再掲、12 で物理化）
  - tier2 業務 Service の write は次の手順で行う：
        BEGIN;
          INSERT INTO entity_v1 ...;
          INSERT INTO outbox_<context>_v<n> (id, payload, ...)
            VALUES (uuid_v7(), '<event>', ...);
        COMMIT;
  - Debezium が outbox table の WAL を tail、Kafka topic
    に publish、published_at 列を update。
  - tier1 Library Repository は Outbox table を呼び出し時
    に必ず touch する（同 transaction 必須）、抜け道なし。
  - migration 中の Outbox：dual-write phase で旧 schema /
    新 schema 両方の Outbox event を生成、consumer が両方
    handle。

■ logical migration（cell-based 分割への移行）
  - cell 単位での migration：tenant_id ↔ cell_id mapping を
    application 側で持ち、migration job で per-tenant に
    新 cell（別 region cluster）に rows を copy。
  - 期間中は dual-read（旧 cell ↔ 新 cell の両方読む）、
    完了後 旧 cell を archive。
  - cell migration は preservation_class 切替を伴う場合が
    多く、12_マイグレーション方針 + 13_運用UI（migration
    progress dashboard）で進行管理。

■ migration 中の RPO / RTO 維持
  - migration 中も preservation_class 規律は不変：
        - synchronous_commit / min.insync.replicas を緩めない
        - WAL streaming を停止しない
        - chaos drill cadence を delay しない
  - 大規模 backfill は throttling（per-tenant rate limit）
    で primary に過負荷をかけない。
  - migration が SLO error budget を burn し過ぎる場合、
    migration job を pause、resume は次の budget cycle で。

■ schema 進化軸（tier1/12）との分担
  - tier1/12 が決定：
        - schema_class（v1_strict_backward / v1_full_compat）
        - compatibility 判定 / breaking change 検出
        - migration plan の expand / contract phase 区切り
        - dual-write / dual-read 期間 minimum
  - 09_data（本層）が決定：
        - migration tool（sqlx-cli / go-migrate / Apicurio）
          の物理 lifecycle
        - DDL apply の admission（lock / drift 検出）
        - phantom write / Outbox table の物理生成
        - backfill job の物理 throttling
        - migration の実行順序（CloudNativePG primary →
          standby は streaming で同期、ON CLUSTER で
          ClickHouse 同期）

■ migration の admission gate
  - Kyverno admission policy：
        - require-migration-pr-link：migration 適用 Job CR
          の annotation に migration ファイル一覧と PR URL
          必須
        - block-non-forward-migration：down migration 検出
          で block
        - require-expand-contract-phase-id：destructive DDL
          の Job は contract phase id 必須、対応する expand
          PR が merge されていることを確認
  - migration 実行履歴は 09 観測 SoR（ClickHouse）に記録、
    audit signal として永続。

■ 採用しないマイグレーション機構
  - down migration（reverse）：forward-only。rollback は
    新 forward migration（compensate）で表現。
  - hot rename（同 transaction で expand+contract）：禁止、
    必ず dual phase を挟む。
  - schema-on-read のみで進化：JSONB 列にも check
    constraint / Validator を必須、schema-less 化はしない。
  - migration の手動 apply：本番経路では admission block。
  - 「migration 中は SLO を緩める」：禁止、preservation_
    class 規律は migration 中も不変。
