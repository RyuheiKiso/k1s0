# tier2 業務資産所有権

## 一文方針
- 業務資産（Domain Event / Workflow 定義 / 決定表 / 業務マスタ / DB schema 等）の既定実装は tier2 が所有する。tier3 は事前に宣言された拡張点を通じて override で業務固有の差分を表現する。tier2 のバージョンアップで silently 壊れない contract を CI で物理 enforce する。

## 既定実装と override
- tier2 が既定実装（業界横断 / 業界共通 / 業界固有 Lv）を所有
- tier3 は [抽象化レベル](03_抽象化レベル.md) の override 許容範囲に従って業務固有の差分を表現:
  - 業界横断 / 業界共通 Lv の不変条件: override 不可
  - 業界固有 / テナント固有 Lv: override 可

## 拡張点の宣言形式
- 拡張点は YAML で宣言: `extension_points.yaml`
- 各拡張点は次を持つ:
  - `id`: 拡張点識別子
  - `lv`: 抽象化レベル（業界固有 / テナント固有）
  - `signature`: 拡張可能な API のシグネチャ（proto FQN）
  - `invariants`: override 後も保たれるべき invariant の宣言
  - `contract_test`: 拡張点の contract test fixture

## contract test
- tier3 が override した拡張点に対し、tier2 が宣言した invariants を満たすことを CI で機械検査
- contract test は Pact + property based test の組合せ
- tier3 リポジトリの CI で必須実行、skip / 改変は CI fail

## tier2 バージョンアップの互換性
- 拡張点 signature の追加は purely additive
- 拡張点 signature の変更 / 削除は 24 ヶ月 deprecation + 移行 codemod 必須
- invariants の強化（追加）は tier3 側 contract test fail で検出 → tier3 修正が必須
- invariants の緩和（削除）は purely additive

## 業務マスタの所有
- **プラットフォーム提供**: 業界横断 / 業界共通 Lv マスタ（通貨 / 国 / カレンダー / 業界共通分類）
- **テナント所有**: 業界固有 / テナント固有 Lv マスタ（個別品目 / 個別仕入先 / 個別検査基準）
- マスタ格納機構は tier2 が提供、内容はテナントが運用

## 公開 API snapshot
- tier2 公開 API は cargo public-api / PublicApiAnalyzers / api-extractor / go-apidiff で snapshot 化
- 拡張点 / invariants 宣言と公開 API snapshot を CI で照合し、宣言と実装の乖離を fail
