# tier2 業界拡張モデル

## 一文方針
- tier2 は単一業界専用の構造を取らない。業界 pack を並立させ、複数業界が同居しても tier2 構造が破綻しないことを設計の前提とする。1.0.0 出荷では製造業 pack のみを ship するが、業界拡張モデルは day-1 から有効、製造業 pack 自身も本モデルの規約に従って実装する。

## 業界並立の前提
- 「業界 pack を 1 つしか持たないため業界横断層を曖昧にしておく」ことを許容しない
- 出荷物が 1 業界の時こそ、業界固有概念が業界横断層に漏れる圧力が最大であり、構造で塞ぐ必要が高い

## 業界 pack の定義
- 業界 pack: 特定の業界（製造業 / サービス業 / 金融業 等）に特化した業務資産・業務語彙・ドメインモジュールの集合
- 業界 pack の単位: 1 業界 = 1 pack を原則とする。業界内のドメイン分割は pack 内で行う（製造業 pack の FA / 調達 / 検査 等。詳細は [ドメイン分割方針](04_ドメイン分割方針.md) を参照）
- 業界 pack の境界: 業界横断層に依存することは可、業界横断層への依存被参照は不可、別業界 pack への依存は不可

## 業界横断層と業界 pack の分離
- 業界横断層: 業界に依存しない業務語彙・業務資産（通知 / 監査 / 承認 workflow / 帳票 / マスタ管理 等）
- 業界 pack: 業界横断層を消費し、業界固有の業務資産を提供
- 分離の方向は単方向（業界 pack → 業界横断層）に固定。逆方向の依存（業界横断層 → 業界 pack）が発生したら、その時点で「業界横断層に業界固有概念が漏れている」とみなし設計を見直す

## 業界中立性の機械的担保（3 種すべてを採用）

### (1) 命名禁則の機械検査
- 業界横断層のシンボル名・ファイル名・モジュール名・Domain Event 名・テーブル名・proto message 名等に、業界固有語が出現したら CI fail
- 禁止語の例（製造業）: Manufacturing / Factory / Plant / Lot / Inspection / Equipment / 製造 / 工場 / ロット / 検査 / 設備 / 調達 / 仕入先 等
- 禁止語リストは業界 pack ごとに YAML で宣言し、業界横断層の公開シンボル snapshot（cargo public-api / PublicApiAnalyzers / api-extractor / go-apidiff）と CI で照合

### (2) 依存方向の機械検査
- 業界横断層 → 業界 pack の依存を機械的に禁止:
  - Rust: cargo-deny の `[bans]` / workspace 構成で業界横断 crate から業界 pack crate を deny
  - C# (.NET 8+): ProjectReference の方向検査と Roslyn analyzer
  - Go: depguard で業界横断パッケージから業界 pack パッケージの import を deny
  - TypeScript: eslint-plugin-boundaries で層境界を宣言し逆方向参照を deny
- 業界 pack 間の相互依存も同様に禁止

### (3) 第二業界 stub による抽象適格性証明
- 1.0.0 では出荷業界が製造業のみのため、「2 業界 conformance」は成立しない。これを補うため、サービス業を想定した最小 stub pack（仮称: `service_industry_stub`）を CI 専用で保持し、業界横断層の API が stub からも素直に消費できることを merge 条件
- stub は出荷物に含めない。Testcontainers / 単体テストで業界横断層 API を呼び出し、製造業 pack と同型のシナリオが green になることを要求
- stub で通らない業界横断 API が発生した時点で、その API は「業界横断層に適格でない」とみなし、業界横断層から業界 pack（製造業）に降格させる、または API を業界中立な形に縮める
- tier1 の L2\* 「二バックエンド conformance」の業界軸版と位置付ける

## `forbidden_industry_terms.yaml` 語彙集合

`src/tier2/forbidden_industry_terms.yaml` は業界横断層の公開 API に混入を禁じる業界固有語の機械検査リスト。CI lint がこのファイルを参照して公開シンボル snapshot と照合する。

| 業界語 | 英語識別子 | 許可スコープ |
|---|---|---|
| 設備 | `equipment` | `pack/manufacturing` |
| ロット | `lot` | `pack/manufacturing` |
| 品目 | `item` | `pack/manufacturing` |
| 拠点 | `site` | `pack/manufacturing` |
| BOM | `bill_of_materials` | `pack/manufacturing` |
| ManufacturingOrder | `manufacturing_order` | `pack/manufacturing` |

- リストに挙げた語が業界横断層の公開 API / 公開型名 / テーブル名 / proto message 名に出現すると CI fail
- 業界 pack 内部（`pack/manufacturing` 配下）での使用は許可
- 業界 pack が公開する API は `manufacturing/vocabulary.yaml` の `neutral_term`（`ResourceUnit` / `ProductionBatch` / `ItemSpecification` / `OperationSite` / `SpecificationTree` 等）を使用する

## `pack/manufacturing/` サブディレクトリ構成

製造業 pack は以下の 6 サブディレクトリ（+ `domain/`）で構成する。各サブディレクトリの責務:

| サブディレクトリ | 責務 |
|---|---|
| `domain/` | 製造業共通の aggregate / entity（`ResourceUnit` / `ProductionBatch` / `ItemSpecification` 等）。複数サブドメイン（FA / 調達 / 検査）が共有するドメインオブジェクトを配置する |
| `fa/` | FA（Factory Automation）サブドメイン。設備稼働・工程実績・製造指示の aggregate と domain event を保持する。`ep_resource_lifecycle` / `ep_batch_lifecycle` extension point の実装を含む |
| `regulations/` | 業界規制・規格準拠ルールの宣言（ISO 9001 等）。YAML 形式で規制要件を宣言し、enforcement は compile / lint / test で担保する。`regulations/iso9001.yaml` が SoT |
| `reports/` | 業務帳票テンプレート（FA 日報 / 調達発注書 / 品質検査報告書等）の YAML 宣言。帳票フォーマットの変更は本ディレクトリのみを変更することで tier2 全体を無影響にする |
| `stress_test/` | 製造業固有の負荷試験シナリオ（FA 操作バースト / マルチテナント同時アクセス / ドメインイベントバースト等）。Rust crate として独立しており、`cargo test --package tier2-manufacturing-stress` で実行する |
| `usecase/` | 製造業ユースケース層。`production_start.rs` / `quality_inspect.rs` 等のアプリケーションサービスを配置する。tier2 業界横断 Library の Repository abstraction を消費し、製造業 domain event を emit する |

- `vocabulary.yaml`: 業界固有語 → 公開 API 業界中立語のマッピング SoT。命名禁則 CI lint が参照する
- `extension_points.yaml`: tier2 業界中立層が業界 pack に公開する extension point の一覧（`ep_resource_lifecycle` / `ep_batch_lifecycle` / `ep_inspection_result_policy` / `ep_procurement_approval_policy` 等）

## `pack/_stub_service/` の責務と契約

`src/tier2/pack/_stub_service/` は製造業以外の業界（サービス業想定）の最小 stub pack。**出荷物には含まれない**（CI 専用の生きた成果物）。

責務:
- 業界横断層の API が製造業以外の業界からも素直に消費できることを実証する（業界中立性の証明）
- `pack/manufacturing` との API diff を継続的に検証し、業界横断 API の抽象適格性を保証する
- stub で通らない業界横断 API が発生した時点で、「業界横断層に適格でない」とみなし設計を見直す

必要な契約（stub が満たすべき条件）:
- **製造業固有語の禁止**: `stub.rs` / `usecase.rs` / `lib.rs` の公開 API に設備 / ロット / 品目 / 拠点 / BOM / ManufacturingOrder 等の製造業固有語が出現しないこと（CI fail 条件）
- **業界中立語のみ使用**: 公開型名は `ServiceOrder` / `ResourceManager` 等の業界中立語を使用する
- **manufacturing との同型構造**: stub は manufacturing と同型の API surface（usecase / domain / ResourceManager trait 等）を持ち、業界横断 Library の同一 API を消費できること
- **CI green 維持**: 業界横断層のバージョンアップ時に stub も同時に更新し、`diff_stub_vs_manufacturing.sh` による diff 検証が green を保つこと

出荷業界が複数になった時点で stub は当該業界 pack のテストハーネスへ移行統合する（[§第二業界 stub の維持](#第二業界-stub-の維持) 参照）。

## 新業界 pack の追加手順
1. 業界 pack の bounded context を [ドメイン分割方針](04_ドメイン分割方針.md) に従って設計し、業界横断層への依存のみで構成可能か検証
2. 業界横断層に追加が必要な API があれば、業界中立な形で業界横断層に追加（命名禁則・依存方向・stub 検査を満たす）
3. 業界 pack を独立 module として実装し、他業界 pack への依存がないことを CI で検査
4. tier3 への提供形態（Library / Service）を [Service 運用方針](07_Service運用方針.md) に従って決定
5. tier3 移行支援（既存 tier3 から新業界 pack への移行が発生する場合）を互換性ポリシーに従って整備

## 第二業界 stub の維持
- stub は CI 専用の生きた成果物として、業界横断層と同じリポジトリで継続的に維持。業界横断層のバージョンアップ時に stub も同時に更新
- 製造業 pack 以外の業界 pack が出荷された時点で、stub は当該業界 pack のテストハーネスへ移行統合する（出荷業界が複数になれば、本来の「2 業界 conformance」が成立する）
