# tier2 データ保持 / アーカイブポリシー

## 一文方針
- カテゴリ別 retention（業務 entity / 監査 / read model / Outbox / PII）を YAML 宣言で固定し、hot / warm / cold の 3 階層 + crypto-shred で物理 enforce。GDPR 物理削除は KEK destroy で wrapped DEK を不可逆に失効させる経路（[鍵管理適合仕様](../../04_詳細設計/01_適合仕様/05_鍵管理適合仕様.md) `v1_data_dek`）。

## カテゴリ別 retention の既定値

| カテゴリ | retention | 物理 storage | 備考 |
|---|---|---|---|
| 業務 entity（aggregate） | 7 年 + 規制要件次第 | hot PostgreSQL → cold Ceph RGW | テナント解約後も保持 |
| audit_local / audit_event | 10 年（規制要件） | hot PostgreSQL → cold Ceph RGW Object Lock WORM | hash chain + 外部公証 |
| read model | 同 aggregate retention | hot PostgreSQL | 再構築可能 |
| Outbox / Kafka topic | 30 日（再送 buffer） | Kafka log | 配信完了後 GC |
| Domain Event archive | 7 年 + 規制要件次第 | cold Ceph RGW | 過去 event の re-projection 用 |
| PII（pii_segregated） | テナント運用責任 + GDPR 削除 | hot PostgreSQL（envelope encryption） | KEK destroy で crypto-shred |
| RUM / observability | 90 日 | hot ClickHouse | 集計後 sampled |
| trace | tail sampled、30 日 | hot ClickHouse | tail_sampling processor |

## アーカイブ階層（hot / warm / cold）
- **hot**: PostgreSQL（CloudNativePG）、SSD、即時 query 可
- **warm**: ClickHouse（OLAP query 用）、SSD、集計向け
- **cold**: Ceph RGW（Object Storage）、HDD、batch restore のみ
- 階層遷移は age / access pattern で自動（pg_partman + tier2 lifecycle workflow）

## パーティション lifecycle と tier1 PostgreSQL
- 大量データ table（業務 entity / Outbox / audit_local）は pg_partman で時間 partition
- partition の hot → warm → cold 遷移は tier2 lifecycle workflow で declarative
- partition drop は cold archive 完了後

## 削除のライフサイクル
- 通常削除: logical delete（`deleted_at` 列、RLS で隠蔽）
- GDPR 物理削除: KEK destroy で当該 tenant の wrapped DEK を不可逆失効（crypto-shred）
- audit / Outbox は logical delete も crypto-shred も対象外（10 年保持）

## Backup と retention の関係
- Backup（CloudNativePG WAL streaming + barman + Ceph RGW Object Lock）は別経路
- Backup retention は disaster recovery 目的、GDPR 削除とは独立
- crypto-shred で削除された data は Backup からも復元不能（KEK 不在）

## retention policy YAML 宣言
- カテゴリ別 retention は `retention_policy.yaml` で宣言
- table 単位 / event 単位の retention を機械可読に固定
- Argo Workflows + Backstage で lifecycle workflow を declarative 実行

## tier3 の拡張点
- tier3 / テナントは category 別 retention を override 不可（tier2 が所有）
- ただし業界固有 / テナント固有のカテゴリ追加は extension point 経由

## 1.0.0 出荷時の対応範囲
- 製造業 pack の業務 entity / 監査 / read model / Outbox / PII の retention
- 規制対応（製造業: ISO 9001 / 医薬品 GMP 等）の retention 要件は業界 pack 単位で宣言

## 採用しない設計
- retention の文章運用（必ず YAML + lifecycle workflow）
- 物理削除の logical delete 代替（GDPR 削除は crypto-shred）
- Backup 経由での GDPR 削除済 data 復元
- 業務 entity の retention 短縮（10 年 minimum、規制要件次第で延長）
