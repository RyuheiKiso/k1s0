# tier2 マルチテナント方針

## 一文方針
- tier2 が tier3 に提供する Service は複数テナントが同居するプラットフォーム共有運用形態を採る。tier1 が提供する「テナント識別子の伝播」は最低限のキャリア機能で、tier2 はそれを業務マスタ / ルール / 権限 / データの分離にまで具体化する責務を持つ。

## テナント識別子
- tier2 / tier3 共通のテナント識別子型を tier1 Library core パッケージで提供する
- 識別子は Authorization context に含めて伝播する。tier2 の Library / Service API はすべて識別子の存在を要求し、欠落時は fail-fast
- tier2 内部処理（Workflow / バックグラウンドジョブ等）でも識別子を伝播する。tier1 の自動計装で識別子が span attribute として emit されることを Companion 節で定義したスキーマと整合させる

## テナント別資産の分離
- **業務マスタ**: テナント別に値を保持。テーブルレベルでは行単位 `tenant_id` 列で分離。マスタ参照 API は識別子を必須引数とする
- **ルール / 決定表**: テナント別に決定表を保持できる構造。既定はプラットフォーム共通決定表、テナント差分は override レイヤで吸収。tier1 Rule Engine（ZEN Engine）の決定表 DSL を tier2 が業務語彙でラップして提供
- **権限ロール**: テナント別にロール定義を保持。tier1 Authentication / Authorization（Keycloak）の認可ポリシーにテナント識別子を含めて評価
- **業務データ**: aggregate / entity の保持に行レベル `tenant_id` 列を必須とする。tier2 のリポジトリ抽象は識別子を強制注入する（業務コードからの省略を不可能にする）

## 共有 Service でのテナント分離（行レベル）
- 既定の分離方式は行レベル `tenant_id` 列。共有 DB / 共有 Pod 上で複数テナントが同居
- 検索クエリには `tenant_id` 述語を必ず含める。tier2 のリポジトリ抽象が `tenant_id` 述語を強制注入し、業務コードからの省略・別テナント参照を不可能にする
- 強制注入の機械的担保は [tier2 強制機構](../../04_詳細設計/02_強制機構/02_tier2強制機構.md) を参照
- 本節は方針定義に留め、`tenant_scoped` / `tenant_master` / `platform_global` / `pii_segregated` の class カタログ、PostgreSQL Row Level Security の policy 定義、5 層 defense-in-depth の機械可読仕様は [テナント分離適合仕様](../../04_詳細設計/01_適合仕様/10_テナント分離適合仕様.md) に分離

## 専用 Service への昇格条件
既定は共有 Pod / 共有 DB だが、特定テナントが以下のいずれかに該当する場合は専用 Service / 専用 DB への昇格を許容:
- 規制要件（業界規制・地理的データ局所性 等）でデータ分離が法的に要求される場合
- 単一テナントの負荷が共有運用の SLO を恒常的に逼迫させる場合

昇格時にも業務コードは無変更を維持する（リポジトリ抽象が接続先を切り替える）。

詳細は [SLO protection layers](../../04_詳細設計/03_クロスカッティング適合仕様/05_SLO_protection_layers.md) の自動昇格 trigger を参照。

## マスタ / ルールの所有
- **プラットフォーム提供のマスタ**: 業界横断 / 業界共通 Lv のマスタ（通貨コード / 国コード / カレンダー / 業界共通の品目分類 等）。tier2 が提供し、テナント間で共有
- **テナント所有のマスタ**: 業界固有 / テナント固有 Lv のマスタ（個別品目 / 個別仕入先 / 個別検査基準 等）。tier2 はマスタ格納機構を提供、内容はテナントが運用
- **tier3 override**: tier3 アプリケーションが必要に応じてマスタを override 拡張点経由で拡張

## テナントライフサイクル
- **追加**: テナント識別子発番 → 必須マスタ初期化 → 権限ロール初期化 → 既定 Workflow / Rule の deploy。tier2 はこの一連の手順を Onboarding Workflow として Library / Service で提供
- **削除**: 業務データ消去（GDPR 等の規制対応含む）。tier2 は削除 Workflow を提供し、tier1 の Object Storage / DB / Vector Search / Messaging の各カテゴリで識別子に紐付くデータを完全削除
- 削除には監査ログを残すが、ログ自体に PII を含めない（詳細は [業務エラー監査コンプライアンス](08_業務エラー監査コンプライアンス.md) を参照）

## テナント識別子の漏洩防止
- 識別子は強制注入と CI 検査で漏洩を防ぐ
- クライアント側から任意のテナント識別子を引数で受け付ける API（成りすまし可能な API）を tier2 公開 API に置くことを禁止
- 識別子は必ず Authorization context から取得（CI 検査機構は [tier2 強制機構](../../04_詳細設計/02_強制機構/02_tier2強制機構.md) 参照）
