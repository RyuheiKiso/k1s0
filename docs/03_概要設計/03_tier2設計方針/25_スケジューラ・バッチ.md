# tier2 スケジューラ・バッチ

## 一文方針
- 定期実行 / batch 処理は Argo Workflows CronWorkflow + Temporal Workflow（tier1 Workflow Library 経由）で declarative 実行する。手動 batch 実行は Backstage プラグインからのみ、audit emit + dual sign-off 必須。

## スケジューラ
- **Argo Workflows CronWorkflow**: cron 形式の定期実行（業務 batch、データ移行、retention 管理）
- **Temporal Workflow**: 業務的に意味のある long-running batch（multi-aggregate / multi-service にまたがる）
- **KEDA ScaledObject**: イベント駆動 trigger（Kafka topic depth / DB row count）

## 定期実行 use case
- 業務 batch（夜間 close / 月次集計 / 年次 archive）
- データ移行 batch（migration era の dual-write、cold storage 移行）
- retention 管理（pg_partman + lifecycle workflow）
- audit hash chain root の年次外部公証 attestation
- L1+ 移行 pair の年次 dry_run

## 手動 batch 実行
- Backstage プラグインから admin API 経由
- audit emit 必須（actor_id / purpose='migration' or 'business_op'）
- dual sign-off 必須（business 重大度に応じて）

## batch 処理の規律
- 必ず Workflow（Temporal）または CronWorkflow（Argo）で declarative
- 手動 SQL 実行禁止（[tier2 強制機構](../../04_詳細設計/02_強制機構/02_tier2強制機構.md)）
- batch 進捗は OTel span として emit、trace_id で全層 stitch
- batch failure は incident response runbook に従う

## bulk 操作
- bulk import / update / delete は admin API（[管理境界](14_管理境界.md)）
- bulk 操作は Workflow で long-running operation として表現（Start RPC → cursor 付き GetStatus）
- bulk audit emit は per-record

## 受入条件
- 全 batch が Argo CronWorkflow / Temporal Workflow で declarative
- 手動 batch 実行は Backstage プラグイン + audit emit + dual sign-off
- batch failure の incident response runbook 配備

## Temporal Workflow 5 仕様

`src/tier2/temporal/src/` に実装された 5 つの Temporal Workflow の仕様。

### monthly_aggregation — 月次集計

| 項目 | 内容 |
|---|---|
| スケジュール | Argo CronWorkflow から月次 trigger（月初 0:00 UTC） |
| タイムアウト | Temporal Workflow timeout（デフォルト: なし、Activity タイムアウトで制御） |
| 業務目的 | 月次受注総額・出荷件数の集計サマリーを生成する |

**入力（`MonthlyAggregationInput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `tenant_id` | UUID | 集計対象テナント識別子 |
| `year_month` | 文字列 | 集計対象年月（`"YYYY-MM"` 形式） |
| `actor_id` | 文字列 | バッチ操作のアクター識別子（Keycloak subject 相当） |

**出力（`MonthlyAggregationOutput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `total_order_amount_jpy` | int64 | 月次受注総額（円） |
| `total_items_shipped` | int64 | 月次出荷件数 |
| `aggregation_id` | UUID | 集計結果の識別子 |

**べき等性**: `k1s0.order_monthly_summary` に `ON CONFLICT (tenant_id, year_month) DO UPDATE` で UPSERT するため複数回実行しても安全。`atomic_triple_write` で Outbox + Audit を同一 txn に書込。

---

### nightly_close — 夜間 close バッチ

| 項目 | 内容 |
|---|---|
| スケジュール | Argo CronWorkflow から毎日深夜 trigger |
| 業務目的 | 当日の `open` 受注を `closed` に変更し、在庫を `confirmed` に確定、翌営業日フラグを更新する |

**入力（`NightlyCloseInput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `tenant_id` | UUID | 処理対象テナント識別子 |
| `business_date` | 文字列 | close する業務日（`"YYYY-MM-DD"` 形式） |
| `close_timeout_secs` | uint64 | close 処理タイムアウト秒数（デフォルト: 1800） |
| `actor_id` | 文字列 | バッチアクター識別子 |

**出力（`NightlyCloseOutput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `closed_orders_count` | int64 | close した受注件数 |
| `closed_inventory_count` | int64 | close した在庫件数 |
| `audit_event_id` | UUID | close 完了を記録した audit_event の ID |
| `next_business_date` | 文字列 | 翌営業日（`"YYYY-MM-DD"` 形式） |

**ステップシーケンス**: open 受注 close → 在庫確定 → 翌営業日計算 → audit_event emit（全ステップ atomic_triple_write）

---

### saga_long_running — Saga 長時間 Workflow

| 項目 | 内容 |
|---|---|
| スケジュール | 業務 use case から on-demand 起動（注文確定・在庫更新等の multi-step 業務 transaction） |
| 業務目的 | 複数 aggregate / サービスにまたがる長時間業務 transaction を Saga compensation pattern で実行する |

**入力（`SagaWorkflowInput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `workflow_id` | 文字列 | Temporal Workflow ID（重複実行防止に使用） |
| `tenant_id` | UUID | 対象テナント識別子 |
| `steps` | `Vec<SagaStep>` | 実行する Saga ステップのリスト（`step_id` / `step_name` / `compensation_step_id`） |
| `payload` | JSON | ステップ間で共有されるペイロード |
| `max_compensation_retry` | uint32 | 補償 transaction の最大リトライ回数 |

**出力（`SagaWorkflowOutput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `completed_steps` | `Vec<String>` | 正常完了したステップ ID リスト |
| `compensated_steps` | `Vec<String>` | 補償実行したステップ ID リスト（失敗時のみ） |
| `success` | bool | 全ステップが正常完了した場合 `true` |
| `final_payload` | JSON | 最終ペイロード |

**補償設計**: `SagaContext` がステップ完了スタック（LIFO）を管理し、失敗時に逆順で補償 transaction を実行。`compensation_step_id` が未設定のステップはスキップ。

### yearly_archive — 年次 archive

| 項目 | 内容 |
|---|---|
| スケジュール | Argo CronWorkflow から年次 trigger（年初 UTC） |
| 業務目的 | `retention_policy.yaml §business_event`（365 日）を超えた `closed` レコードを S3（MinIO）に archive し、本番 DB から削除する |

**入力（`YearlyArchiveInput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `tenant_id` | UUID | archive 対象テナント識別子 |
| `archive_year` | int32 | archive する年（例: `2023`） |
| `retention_years` | uint32 | 本番 DB に保持する年数 |
| `actor_id` | 文字列 | バッチアクター識別子 |
| `s3_bucket` | 文字列 | archive 先 S3 バケット名 |

**出力（`YearlyArchiveOutput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `archived_records_count` | int64 | archive したレコード件数 |
| `archive_location` | 文字列 | archive 先パス（`s3://bucket/year/tenant_xxx/year_xxx/` 形式） |
| `archive_id` | UUID | archive 処理の識別子 |

**Object Lock**: S3 PUT 時に `x-amz-object-lock-mode: COMPLIANCE` + `x-amz-object-lock-retain-until-date`（HLC wall_ms + `AUDIT_RETENTION_DAYS` = 2555 日）を付与。`atomic_triple_write` で削除 + Outbox + Audit を同一 txn に書込。

---

### yearly_dry_run — L1+ migration pair 年次 dry_run

| 項目 | 内容 |
|---|---|
| スケジュール | Argo CronWorkflow から年次 trigger（`dry_run.lock.yaml §last_green_at` を 365 日以内に保つため） |
| 業務目的 | L1+ migration pair の 5 フェーズ dry_run を実行し、新旧スキーマ間の差分を検証する |

**入力（`MigrationPairDryRunInput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `pair_id` | 文字列 | `dry_run.lock.yaml` の `pair_id` と一致する識別子 |
| `tenant_id` | UUID | dry_run を実行するテナント識別子 |
| `target_phase` | `DryRunPhase` | 到達する目標フェーズ（`Shadow` / `DualRead` / `Cutover` / `Cleanup` / `Complete`） |
| `sample_size` | uint64 | 処理するサンプルデータ件数 |
| `actor_id` | 文字列 | バッチアクター識別子 |
| `shadow_schema` | 文字列 | shadow DB のスキーマ名（デフォルト: `"k1s0_shadow"`） |
| `envoy_configmap_name` | 文字列 | Cutover フェーズで更新する Envoy ConfigMap 名 |
| `dry_run_input_path` | 文字列 | `complete` フェーズで更新する `dry_run_input.yaml` のパス |

**5 フェーズ定義（`DryRunPhase`）**

| フェーズ | 内容 |
|---|---|
| `Shadow` | 本番 DB を読み取りのみ参照し、shadow スキーマに UPSERT する |
| `DualRead` | 本番と shadow の値を EXCEPT で差分検出し、`divergence_count` を記録する |
| `Cutover` | Envoy ConfigMap を Kubernetes PATCH して `db_schema` を shadow に切り替え |
| `Cleanup` | 旧本番スキーマを archive スキーマに RENAME、shadow を `k1s0` に昇格（atomic_triple_write） |
| `Complete` | `dry_run_input.yaml` の `last_green_at` を HLC derived RFC3339 文字列で更新 |

**出力（`MigrationPairDryRunOutput`）**

| フィールド | 型 | 説明 |
|---|---|---|
| `pair_id` | 文字列 | dry_run した migration pair の識別子 |
| `reached_phase` | `DryRunPhase` | 実際に到達したフェーズ |
| `processed_records` | uint64 | 処理したサンプルレコード件数 |
| `divergence_count` | uint64 | 新旧スキーマ間の差異件数（0 の場合のみ `success=true`） |
| `dry_run_id` | UUID | dry_run 実行の識別子 |
| `success` | bool | `divergence_count == 0` の場合 `true` |

**dry-run 設計**: `target_phase` を `Shadow` に設定することで本番スキーマを変更せずに shadow 書込のみ確認できる。`Cutover` 以降は Envoy ConfigMap を実際に更新するため、dry-run 的な実行は `Shadow` / `DualRead` フェーズ止まりで行う。

## KEDA ScaledObject 仕様と data_retention_worker 連動

### KEDA trigger 仕様

`src/tier2/scheduler/keda/tenant_scaledobject.yaml` で定義する ScaledObject。

| フィールド | 値 | 説明 |
|---|---|---|
| `scaleTargetRef.name` | `tier2-event-consumer` | スケール対象 Deployment |
| `pollingInterval` | 15 秒 | スケールアウト判定のポーリング間隔 |
| `cooldownPeriod` | 60 秒 | スケールインまでの安定化ウィンドウ |
| `minReplicaCount` | 1 | 最小レプリカ数（ゼロスケール無効） |
| `maxReplicaCount` | 20 | 最大レプリカ数（テナント数に応じて調整） |

**Kafka トリガー仕様**

| フィールド | 値 | 説明 |
|---|---|---|
| `type` | `kafka` | トリガー種別 |
| `bootstrapServers` | `kafka.k1s0-infra.svc.cluster.local:9092` | Kafka ブローカーアドレス |
| `consumerGroup` | `tier2-event-consumer-group` | 監視対象コンシューマーグループ |
| `topic` | `k1s0.tier2.domain_events` | 監視対象トピック |
| `lagThreshold` | `"100"` | 1 レプリカあたりの目標ラグ数（超過時にスケールアウト） |
| `offsetResetPolicy` | `earliest` | 未コミットメッセージからの処理開始 |

**スケールアウト計算**: `desired_replicas = ceil(total_lag / lagThreshold)`。ラグが `100 × current_replicas` を超えるとスケールアウト発動。

**quota_class との関係**: `v1_per_tenant_compute` quota class の `oss_native_quota` enforcement 層（階層 3）として機能。`classes.yaml §v1_per_tenant_compute.enforcement_layer: oss_native_quota` の具体実装。

### data_retention_worker との連動

`retention_policy.yaml` で宣言されたカテゴリ別 retention を適用する `data_retention_worker` は以下の仕組みで KEDA とリンクする。

| retention カテゴリ | デフォルト保持日数 | 対応する purge トリガー |
|---|---|---|
| `audit` | 3650 日 | 年次 archive workflow が Kafka に `retention.audit.purge_needed` event を投入 |
| `business_event` | 365 日 | `yearly_archive` Temporal Workflow が purge 対象を検出して Kafka event を投入 |
| `projection` | 90 日 | pg_partman が自動パーティション削除、Kafka consumer lag を Retention worker が監視 |
| `outbox` | 30 日 | Outbox relay 完了後に Kafka topic に `outbox.purge_ready` event を投入 |
| `pii` | 30 日 | GDPR 削除要求受信時に Kafka に `pii.erasure_requested` event を投入 |
| `import_staging` | 7 日 | import 処理完了後に Kafka に `staging.cleanup_needed` event を投入 |

`data_retention_worker` は `k1s0.tier2.domain_events` トピックの retention 系 event を消費し、KEDA により自動スケールする。ラグが `lagThreshold: 100` を超えると最大 20 レプリカまでスケールアウト。`retention_policy.yaml` が **SoT** であり、本 ScaledObject の `lagThreshold` と `maxReplicaCount` は retention カテゴリ数 × テナント数の見積もりに基づき調整する。
