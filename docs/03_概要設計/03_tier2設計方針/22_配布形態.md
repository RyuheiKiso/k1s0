# tier2 配布形態

## 一文方針
- tier2 機能カテゴリは Library 形態（in-process linkage）または Service 形態（独立 Pod）の 2 形態で配布する。同一機能を両形態で提供するカテゴリは共通 conformance test suite で両方 green を merge 条件（[tier2 強制機構](../../04_詳細設計/02_強制機構/02_tier2強制機構.md) 層 7）。

## 2 配布形態
- **Library 形態**: tier3 業務 process に in-process linkage（言語別 package、Rust crate / NuGet / Go module / npm package）
  - 利点: latency 最小、tier1 Library と同 process 内で context propagation
  - 適: tier3 業務 service がドメイン業務を処理する際の主経路
- **Service 形態**: 独立 Pod として動作（Helm / Operator manifest）
  - 利点: tier3 と独立した resource 管理、tier3 不在環境でも動作
  - 適: tier3 不在環境（admin API、cron job、external system 連携）

## 両形態提供カテゴリ
- 業務 use case のうち in-process / 独立 Pod 双方の利用が想定されるもの
- 共通 conformance test suite で両形態 green を merge 条件

## 形態別の配布規律
- Library: 内部レジストリ（cargo / NuGet / Athens / Verdaccio）唯一、Cosign signed
- Service: 内部 Harbor OCI registry 唯一、Cosign signed image

## 業務管理機能の配布形態
- admin API は Service 形態のみ（Backstage プラグイン経由）
- tier3 業務 UI から admin API を import する経路を CI で禁止

## 受入条件
- 全 tier2 配布物が内部レジストリ経由
- 両形態提供カテゴリの conformance test 両 green
- admin API の Service 形態化と業務 UI からの import 禁止

## Helm chart 構造規約

### Chart.yaml メタデータ

`src/tier2/helm/Chart.yaml` は以下の規約に従う。

| フィールド | 値・規約 |
|---|---|
| `apiVersion` | `v2`（Helm 3 形式） |
| `name` | `k1s0-{axis}`（例: `k1s0-tier2`）、ハイフン区切り |
| `type` | `application`（runnable）または `library`（shared helpers のみ） |
| `version` | チャートの SemVer（アプリバージョンと独立して管理） |
| `appVersion` | Harbor OCI イメージタグと一致させる |
| `dependencies` | v1.0.0 では `[]`（直接管理）。subchart を追加する場合は下記規約に従う |

### subchart 依存の命名規則

subchart が必要になった場合（将来的な分割拡張時）は以下の規約に従う。

```yaml
dependencies:
  - name: k1s0-{component}         # チャート名は k1s0- プレフィックス必須
    version: "~{semver}"            # チルダ範囲（マイナーバージョン固定）
    repository: "oci://harbor.k1s0.internal/charts"  # 内部 Harbor OCI のみ
    alias: {component}              # values.yaml でのオーバーライドキー
    condition: {component}.enabled  # フィーチャーフラグで無効化可能にする
```

- `name` は必ず `k1s0-` プレフィックスを付ける（外部チャートの直接依存禁止）
- 外部 OSS チャート（例: bitnami/kafka）を tier2 chart の dependency に直接追加することは禁止。外部 OSS は infra 軸で管理する

### values.yaml の tier2 固有オーバーライドポイント

`src/tier2/helm/values.yaml` の主要オーバーライドポイントとデフォルト値。

| キー | デフォルト | 説明 |
|---|---|---|
| `replicaCount` | `2` | Pod レプリカ数。Operator reconcile の `quotaClass` 連動時は Operator が上書きするため、Helm values は初期値にすぎない |
| `image.repository` | `harbor.k1s0.internal/k1s0/tier2` | Harbor 内部レジストリのみ許可 |
| `image.pullPolicy` | `IfNotPresent` | |
| `image.tag` | `""` | 空時は `Chart.yaml.appVersion` を使用 |
| `resources.limits.cpu` | `"500m"` | standard quotaClass 相当の初期値 |
| `resources.limits.memory` | `"512Mi"` | |
| `resources.requests.cpu` | `"100m"` | |
| `resources.requests.memory` | `"128Mi"` | |
| `service.type` | `ClusterIP` | LoadBalancer / NodePort は禁止（Istio VirtualService 経由） |
| `service.port` | `8080` | |
| `ingress.enabled` | `false` | 本番では Istio VirtualService を使用するため既定 disabled |
| `ingress.className` | `"nginx"` | |
| `podSecurityContext.runAsNonRoot` | `true` | production/development 区別禁止規約準拠 |
| `podSecurityContext.runAsUser` | `1000` | |
| `podSecurityContext.fsGroup` | `1000` | |
| `serviceAccount.create` | `true` | |
| `serviceAccount.annotations` | `{}` | IRSA / Workload Identity は annotations で差し込む |

### 本番デプロイでの values オーバーライド優先順位

```
chart defaults (values.yaml)
  < 環境共通 values（environments/base.yaml）
  < 環境固有 values（environments/{env}.yaml）
  < helm install --set（一時的な手動調整）
```

Operator が管理するリソース（Deployment / HPA / Ingress 等）は Operator の reconcile が Helm values を上書きするため、Helm は初期 scaffold としてのみ機能する。
