# tier2 データライフサイクル（入口・出口・bulk・品質）

## 一文方針
- テナント onboarding（初期データ移行）/ data export（ポータビリティ）/ offboarding（テナント離脱）/ bulk 操作 / data 品質パイプライン / 既存基幹との並行運用 era の 6 フェーズを Argo Workflows + Backstage Software Template で declarative 実行する。手動 SQL 実行は禁止、全フェーズで audit_event emit。

## 初期データ移行（オンボーディング）
- 新テナントの onboarding は Argo Workflow で declarative
- 必須マスタ初期化 → 権限ロール初期化 → 既定 Workflow / Rule の deploy
- 既存基幹システムからの初期 import は External Proto + tier1 Companion 経由
- 移行データは validation pipeline で品質検査（NULL / 範囲 / 整合性）後 commit

## テナント data export（ポータビリティ）
- 業務 entity / Domain Event / Workflow state / 監査ログを export
- 形式: 標準 OpenAPI yaml + JSON / Avro
- 暗号化: テナント export 公開鍵で AES-256-GCM 暗号化（テナント所有の鍵で復号）
- export 自体は audit_event に emit、`purpose='export'` 必須

## オフボーディング（テナント離脱）
- 離脱フローは Argo Workflow で declarative
- データ消去（GDPR 等の規制対応含む）: KEK destroy で当該 tenant の wrapped DEK を不可逆失効（crypto-shred）
- audit_event は 10 年保持（regulation 要件、crypto-shred 対象外）
- 離脱通知 + grace period（90 日）+ 物理削除実行

## Bulk 操作（業務管理 API として）
- bulk import / bulk update / bulk delete は admin API（[管理境界](14_管理境界.md)）
- bulk 操作は Workflow で long-running operation として表現（Start RPC → cursor 付き GetStatus）
- bulk operation の rollback は Workflow 補償処理
- bulk audit emit は per-record（操作ごと）

## データ品質パイプライン
- 入口（initial import / external integration）: validation pipeline で範囲 / NULL / 整合性 / PII 分類検査
- 内部（業務 use case）: aggregate invariants で type-level + runtime check
- 出口（export / external integration）: schema validation + envelope 暗号化
- 品質違反は alert + DLQ topic に分離

## 既存基幹システムとの並行運用（migration era）
- 既存 ERP 等との並行運用 phase（migration era）は dual-write で吸収
- tier1 Library が dual-write 経路を持ち、書込は両 backend、読取は ramp で切替（0% / 5% / 25% / 50% / 75% / 100%）
- 各 ramp 段階で 32 適合仕様 P1〜P4 invariant が両 backend で satisfied を assertion で検証
- 詳細は [移行 Pair 適合仕様](../../04_詳細設計/01_適合仕様/02_移行Pair適合仕様.md) と同型 pattern

## tier3 の拡張点
- tier3 は data lifecycle workflow を直接呼出しない
- 業務担当者は tier3 業務 UI で日々の業務操作のみ
- onboarding / export / offboarding は Backstage プラグインで業務管理者が起動

## 1.0.0 出荷時の対応範囲
- 製造業 pack の onboarding workflow（必須マスタ / 権限ロール / 既定 Workflow）
- export 機能（GDPR ポータビリティ対応）
- offboarding workflow（crypto-shred + 監査保持）
- bulk import / update / delete の admin API

## 採用しない設計
- 手動 SQL 実行による data 操作
- audit emit を伴わない data lifecycle 操作
- offboarding での crypto-shred 省略（GDPR 物理削除に置換）
- export 暗号化なし（必ずテナント鍵で AES-256-GCM）
- dual-write なしでの基幹移行
- 業務担当者による direct admin API 呼出（必ず Backstage プラグイン経由）

## Argo Workflow 入出力 contract

`src/tier2/lifecycle/argo/` に定義された 6 workflow の入出力パラメータ仕様。

### onboarding_workflow.yaml — テナントオンボーディング

| 項目 | 内容 |
|---|---|
| `kind` | `Workflow`（手動または Backstage API トリガー） |
| `activeDeadlineSeconds` | 1800 秒（30 分） |

**入力パラメータ**

| パラメータ名 | 型 | 説明 |
|---|---|---|
| `tenant_id` | UUID 文字列 | プロビジョニング対象テナントの UUID |
| `quota_class` | 文字列 | 割り当てる quota class（デフォルト: `standard`） |

**ステップシーケンス**

1. `provision-db` — テナント専用 DB スキーマ作成（`lifecycle-worker provision-db`）
2. `create-quota` — 割り当て quota 登録（`lifecycle-worker create-quota`）
3. `notify` — Outbox 経由でオンボーディング完了 Domain Event を emit（`lifecycle-worker notify-onboarding-complete`）

**出力**: なし（Outbox に `TenantOnboardingCompleted` Domain Event が投入される）

---

### offboarding_workflow.yaml — テナントオフボーディング

| 項目 | 内容 |
|---|---|
| `kind` | `Workflow`（Backstage プラグインからのみ起動） |
| `activeDeadlineSeconds` | 14400 秒（4 時間） |

**入力パラメータ**

| パラメータ名 | 型 | 説明 |
|---|---|---|
| `tenant_id` | UUID 文字列 | オフボーディング対象テナントの UUID |

**ステップシーケンス**

1. `export-data` — テナントデータを暗号化 ZIP にエクスポート（テナント公開鍵 AES-256-GCM）
2. `anonymize-pii` — `field_pii` annotation 付きフィールドを匿名化
3. `delete-tenant` — スキーマ / quota / Object Storage を削除（KEK destroy による crypto-shred）

**出力**: なし（audit_event は 10 年保持対象、crypto-shred 対象外）

---

### bulk_export_workflow.yaml — 一括データエクスポート（GDPR ポータビリティ）

| 項目 | 内容 |
|---|---|
| `kind` | `Workflow` |
| `activeDeadlineSeconds` | 28800 秒（8 時間） |

**入力パラメータ**

| パラメータ名 | 型 | 説明 |
|---|---|---|
| `tenant_id` | UUID 文字列 | エクスポート対象テナントの UUID |
| `hlc_range_start` | HLC 文字列 | エクスポート開始 HLC タイムスタンプ（wall clock TTL 禁止規約により HLC を使用） |
| `hlc_range_end` | HLC 文字列 | エクスポート終了 HLC タイムスタンプ |

**ステップシーケンス**（ステップ 2 は並列）

1. `init-export-job` — エクスポート ID 払い出し + audit_event 記録
2. `export-relational-data`（並列）/ `export-attachments`（並列）— RDB データ（CSV/Parquet）+ Object Storage 添付ファイルを並列エクスポート
3. `package-and-sign` — cosign 署名付き ZIP を生成

**出力**: cosign 署名済み ZIP（テナント鍵で AES-256-GCM 暗号化済み）

---

### promote_to_dedicated_workflow.yaml — 専用インフラへの自動昇格

| 項目 | 内容 |
|---|---|
| `kind` | `Workflow`（SLO protection layers §自動昇格から trigger） |
| `activeDeadlineSeconds` | 86400 秒（24 時間） |

**入力パラメータ**

| パラメータ名 | 型 | 説明 |
|---|---|---|
| `tenant_id` | UUID 文字列 | 昇格対象テナントの UUID |
| `slo_class` | 文字列 | 維持が確認された SLO クラス（デフォルト: `v1_gold`） |
| `hysteresis_days` | 文字列 | SLO 維持確認日数（デフォルト: `"7"`） |

**ステップシーケンス**

1. `verify-slo-compliance` — Prometheus で `hysteresis_days` 間の breach 率を確認（閾値 0.1%）
2. `provision-cnpg-cluster` — 専用 CloudNativePG Cluster CR を 3 ノード HA でプロビジョニング
3. `switch-envoy-routing` — Envoy ConfigMap を `dedicated` backend に切り替え
4. `wait-hysteresis` — 昇格後安定性確認 300 秒 suspend
5. `record-promotion-audit` — `SloPromotionCompleted` event を atomic_triple_write で記録

**出力**: なし（audit_event が `SloPromotionCompleted` で記録される）

---

### demote_to_shared_workflow.yaml — shared tier への自動降格

| 項目 | 内容 |
|---|---|
| `kind` | `CronWorkflow`（毎日 0:00 UTC に評価） |
| `concurrencyPolicy` | `Forbid`（前回実行中はスキップ） |
| `activeDeadlineSeconds` | 21600 秒（6 時間） |

**入力パラメータ（Cron固定値）**

| パラメータ名 | デフォルト | 説明 |
|---|---|---|
| `downgrade_threshold_days` | `"30"` | 連続下振れ日数の判定閾値 |
| `slo_class_ceiling` | `"v1_silver"` | この SLO クラス以下を降格対象とする |

**ステップシーケンス**

1. `scan-candidates` — Prometheus で 30 日連続 `v1_silver` 以下のテナントを列挙し、候補 ID JSON 配列を `/tmp/candidate_tenant_ids.json` に出力
2. `demote-batch`（候補 0 件の場合 skip） — 候補テナントの Envoy ルーティングを `shared` に変更
3. `record-evaluation-audit` — `SloDemotionEvaluationCompleted` event を記録（0 件評価も記録）

**出力（step outputs）**

| 出力パス | 内容 |
|---|---|
| `/tmp/candidate_tenant_ids.json` | 降格候補テナント ID の JSON 配列 |
| `/tmp/candidate_count.txt` | 候補件数（整数文字列） |
| `/tmp/demoted_count.txt` | 実際に降格した件数 |

---

### deprecation_window_workflow.yaml — API バージョン廃止ウィンドウ管理

| 項目 | 内容 |
|---|---|
| `kind` | `WorkflowTemplate`（CronWorkflow から参照） |
| `activeDeadlineSeconds` | 7200 秒（2 時間） |

**入力パラメータ**

| パラメータ名 | 型 | 説明 |
|---|---|---|
| `api_version` | 文字列 | 廃止対象 API バージョン識別子（例: `v1alpha1`） |
| `deprecation_date_iso` | ISO 8601 文字列 | 廃止予定日時（例: `2026-06-01T00:00:00Z`） |
| `phase` | 文字列 | deprecation clock フェーズ（`announce` / `migrate` / `enforce`、デフォルト: `announce`） |
| `affected_client_count` | 文字列 | 廃止対象 API を使用しているクライアント数（デフォルト: `"0"`） |

**フェーズ別動作**

| `phase` | 動作 | 開始時期 |
|---|---|---|
| `announce` | 全テナント管理者への廃止通知メール送信 | 廃止 24 ヶ月前 |
| `migrate` | 移行ガイド + 移行ツール配布 | 廃止 6 ヶ月前 |
| `enforce` | API ゲートウェイに廃止バージョンの拒否ポリシー適用 | 廃止当日 |

**ステップシーケンス**

1. `scan-api-usage` — 全テナントの API 利用状況を ClickHouse から収集
2. `execute-phase-action` — フェーズ別アクション実行
3. `record-audit-event` — `DeprecationWindowPhaseExecuted` event を Outbox 経由で emit（atomic 三表書込規約）

**出力**: なし（audit_event が各フェーズの実施記録として Outbox に投入される）
