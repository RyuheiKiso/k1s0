# tier2 読み取りモデル方針（CQRS / read model / 検索 / 集計）

## 一文方針
- 業務処理の write 経路（aggregate / atomic 三表書込）と read 経路（read model / 検索 / 集計）を CQRS で分離する。read model 更新は Outbox + Kafka + tier2 read model projector の eventual consistency 経路で行い、業務的影響を [SLO 適合仕様](../../04_詳細設計/01_適合仕様/07_SLO適合仕様.md) `v1_event_freshness` で SLA 化する。

## 書込モデルと読込モデルの境界
- **書込モデル**: aggregate / Workflow / atomic 三表書込（State change + Outbox + Audit を同 transaction）
- **読込モデル**: PostgreSQL read model table / ClickHouse 集計 / Valkey cache
- 業務 use case は write 経路と read 経路を別 API として表現（CQRS）

## Read model 更新の責務
- Outbox の Domain Event を Debezium CDC で Kafka に publish
- tier2 read model projector が Kafka を subscribe し、PostgreSQL read model table を update
- ClickHouse 集計は OTel Collector と並走の audit relay 経路
- Valkey cache は tier2 application 層で TTL 管理

## Eventual consistency と業務的影響
- read model 反映 lag は `v1_event_freshness` SLO（p95 ≤ 5000ms、`v1_event_feed` conformance class と整合）
- 業務的影響度に応じて lag tolerance を表現:
  - 「最新値必須」: write 直後の read で同一 transaction の query（aggregate 直接 query、read model 経由しない）
  - 「数秒の lag 許容」: read model 経由
  - 「分単位 lag 許容」: ClickHouse 集計

## 検索（Search）
- 業務 entity の検索は PostgreSQL の `pg_trgm` / GIN index + read model（業界共通 / 業界固有 マスタ参照含む）
- vector 検索は pgvector（[tier1 提供機能カテゴリ](../02_tier1設計方針/04_提供機能カテゴリ.md) Vector Search L1+）
- Elasticsearch / OpenSearch は採用しない（PostgreSQL pg_trgm + ClickHouse で吸収）

## 集計（Aggregation）
- 業務 KPI の集計は ClickHouse の MergeTree（time series）
- ad-hoc 集計は Apache Superset で ClickHouse 直 SQL
- リアルタイム dashboard は Perses + Prometheus

## Cache（tier1 Valkey の業務側活用）
- 高頻度 read（マスタ参照 / 認可結果）を Valkey cache
- TTL は業務的影響度に応じて設定（マスタは 1h、認可は 5min）
- cache invalidation は Outbox Domain Event subscribe で trigger
- write-through cache は採用しない（write 経路は aggregate のみ、cache は read 経路から）

## 並行制御
- 同一 aggregate に対する concurrent write は optimistic concurrency control（version 列で楽観 lock）
- 衝突は BusinessConflict subtype（[クライアント状態適合仕様](../../04_詳細設計/01_適合仕様/11_クライアント状態適合仕様.md) `stale_write` / `lost_update`）として返却
- read 側は dirty read 不可（PostgreSQL READ COMMITTED 以上）

## tier3 の拡張点
- read model schema は tier2 が所有
- tier3 は read model query API を消費するのみ
- 独自 read model の構築は禁止（tier2 read model projector 経由）

## 1.0.0 出荷時の read model
- 業界横断 read model: 通知 / 監査 / 帳票
- 業界共通 read model（製造業）: 設備 / ロット / 品目 / 拠点 / BOM の参照系
- 業界固有 read model（FA / 調達 / 検査）: 業務一覧 / KPI dashboard

## 採用しない設計
- 同 transaction 内で write + read（業務的に「最新値必須」case 以外は read model 経由）
- write-through cache
- 独自 read model 構築（tier2 read model projector 経由のみ）
- Elasticsearch / OpenSearch
- dirty read（READ COMMITTED 以上）
