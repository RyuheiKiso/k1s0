# tier2 の位置づけ

## 一文方針
- tier2 はプラットフォーム構成（5 階層論）の中位層、tier3 から見て infra / data / tier1 を隠蔽する「業務の単一の真」の保管所として位置づけられる。tier2 を迂回した tier1 / OSS 直接利用は CI で物理拒否、業務不変条件は tier2 集約で構造的に保護する。

## 5 階層論における位置
- infra（最下層）→ data → tier1 → **tier2** → tier3（最上層）
- tier2 は tier1 Library 経由でのみ infra にアクセス
- tier3 は tier2 経由でのみ業務資産にアクセス

## tier2 の中核責務
- ドメイン業務共通化（業界横断 / 業界共通 / 業界固有 / テナント固有 の 4 抽象化レベル）
- 業務資産（Domain Event / Workflow / 決定表 / 業務マスタ / DB schema）所有
- atomic 三表書込（State change + Outbox + Audit）
- BusinessConflict subtype 4 種の検出
- ABAC policy 評価（Backend-for-Library 一括評価）

## 隣接層との接合
- **infra との接合**: tier1 Library 経由のみ（直接アクセス禁止）
- **data との接合**: tier1 Library Repository abstraction 経由のみ
- **tier1 との接合**: Library / Companion 経由、OSS 直接 import 禁止
- **tier3 との接合**: tier2 公開 API（Library / Service）+ override 拡張点

## 業務管理機能との分離
- 業務管理機能（マスタ管理 / 監査検索 / 緊急対応）は admin API + Backstage プラグイン
- tier3 業務 UI に admin 機能を載せない（[管理境界](14_管理境界.md)）
