# tier3 状態管理

## 一文方針
- tier3 のクライアント状態は Server Truth (ST) / Optimistic Local (OL) / Pending Queue (PQ) / Draft (DR) の 4 layer のみを許容する。これら以外の中間 layer（UI ローカルにしか存在しない aggregate cache 等）を作ることを禁止する。1 つの値が「どの layer 由来か（lineage）」を必ず持つ。詳細は [クライアント状態適合仕様](../../04_詳細設計/01_適合仕様/11_クライアント状態適合仕様.md)。

## 4 layer 概要

| layer | source | persisted_in | PII | lifetime |
|---|---|---|---|---|
| `server_truth` (ST) | Domain Event subscription / api_response_2xx | query cache（in-memory） | NG | session（logout で purge） |
| `optimistic_local` (OL) | mutation_in_flight | query cache（overlay） | NG | until_ack_or_rollback |
| `pending_queue` (PQ) | user_action（offline 含む） | IndexedDB（encrypted） | 除外 | until_ack_or_user_discard |
| `draft` (DR) | form_input | IndexedDB（encrypted） | 除外 | until_confirm_success_or_user_discard |

## 衝突解決 tree
- 4 layer × 5 conflict event（server_truth_advance / optimistic_acknowledged / optimistic_rejected / pending_queue_resume / business_conflict_received）の組合せで取るべき動作が一意に決まる
- 「実装者の判断」の余地を残さない
- 詳細は [クライアント状態適合仕様](../../04_詳細設計/01_適合仕様/11_クライアント状態適合仕様.md) `conflict_tree.yaml` を参照

## BusinessConflict subtype（4 種）
tier2 BusinessConflict を 4 subtype に細分化、UI 分岐を 1:1 で固定:
- `stale_write`: base_version < ST.version、field-level diff disjoint → refetch + auto rebase + chained idempotency_key で auto-resend
- `lost_update`: base_version < ST.version、field-level diff intersect → 3-way merge UI + queue hold
- `supersede`: 同一 actor の後続 op が同 aggregate を既に更新済み（Idempotency-Key chain で検出） → queue entry delete + silent toast
- `concurrent_edit`: 他 actor が presence で編集中宣言 + 自身が send 試行 → presence indicator update + user choice

subtype と UI 分岐の対応は override 禁止。

## 永続化と PII 取扱
- IndexedDB 永続化は WebCrypto AES-GCM + device_bound_key で encrypted at rest
- 鍵は OS keychain（Tauri / native）または browser non-extractable CryptoKey
- PII 列は enqueue 時に strip（field_pii annotation で識別）、send 時に in-memory form state から attach
- localStorage / sessionStorage / cookie に PII 平文を置かない（[tier3 強制機構](../../04_詳細設計/02_強制機構/03_tier3強制機構.md) 層 5）

## Idempotency-Key
- 自動採番: ULID + tenant_id prefix + RPC method short hash
- TTL: 24h
- 超過時の挙動: `over_ttl_policy` に従う（mark_as_stale → require_user_confirmation_to_resend → confirm: generate_new_idempotency_key / discard: remove_entry）
- chained idempotency_key（rebase 後の再送）も chain 親子関係（`original_idempotency_key` + `chained_idempotency_key`）を tier2 cache 側で dedup 判定

## purge triggers
- `logout` / `refresh_token_expiry` / `tenant_switch` / `actor_switch` / `device_bound_key_rotate`
- 全 trigger で 4 layer storage を purge + audit emit（`client.purge.event`）

## CRDT merge invariant

tier3 の CRDT 実装（`src/tier3/typescript/packages/crdt/`）が満たすべき merge invariant を以下に定める。

### 3 条件

CRDT の merge 操作は以下の 3 条件を全て満たさなければならない。

**1. Commutative（交換可能性）**
- `merge(a, b) = merge(b, a)` が常に成立する
- マージの順序が結果に影響してはならない
- 例: A ユーザーの変更と B ユーザーの変更をどちらの順でマージしても同一結果になる

**2. Associative（結合可能性）**
- `merge(merge(a, b), c) = merge(a, merge(b, c))` が常に成立する
- マージのグルーピングが結果に影響してはならない
- 例: 3 ユーザー以上の同時編集を任意の順番でマージしても同一結果になる

**3. Idempotent（冪等性）**
- `merge(a, a) = a` が常に成立する
- 同一 operation を複数回 apply しても結果が変わらない
- at-least-once 配信（Kafka / Outbox）での重複 apply に対して安全である

### tier3 内部閉じ込めの正当化（cross-cutting spec 不要の理由）

CRDT を tier3 内部（`packages/crdt/`）に閉じ込め、cross-cutting spec を設けない理由を以下に明示する。

- **スコープの限定**: CRDT は tier3 の UI 同時編集（collaborative editing）のための実装技術であり、tier1 / tier2 の業務 domain invariant とは独立している
- **wire 形式への非露出**: CRDT の内部状態（vector clock / operation log）は tier2 との wire 形式（proto）に露出しない。tier2 への送信は「確定した mutation」のみであり、CRDT の中間状態は tier3 内部に留まる
- **cross-cutting spec の条件不成立**: cross-cutting spec は「2 軸以上にまたがる不変条件」に対して作成する。CRDT merge invariant は tier3 SPA の `packages/crdt/` に閉じており、他軸（tier1 / tier2 / infra 等）への影響がない
- **tier3 強制機構 層 1**: `packages/crdt/` が tier1 / OSS の CRDT ライブラリを直接 import する経路は ESLint deny list で禁止されており、tier3 独自実装として完結する

CRDT の 3 条件は `src/tier3/typescript/packages/crdt/` の unit test で property-based testing（fast-check 等）により検証する。

## 採用しない選択肢
- 4 layer 以外の中間 layer
- conflict event の override
- BusinessConflict subtype と UI 分岐の override
- localStorage / sessionStorage への PII 平文書込
- 自製 crypto
- per-aggregate write の concurrent in-flight 複数
- CRDT merge が上記 3 条件を満たさない実装
