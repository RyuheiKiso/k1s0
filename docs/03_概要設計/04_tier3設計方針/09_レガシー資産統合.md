# tier3 レガシー資産統合

## 一文方針
- レガシー .NET Framework 4.6.2+ の業務 exe / Service 資産は、tier2 Service を Companion + Gateway 経由 HTTP/1.1 + JSON（unary）/ HTTP/1.1 + SSE（server-streaming）で消費する形態に固定する。tier3 業務コードからは Companion runtime + tier2 Service の proto 派生 SDK のみが見える。OSS クライアントへの直接アクセスは禁止。

## 不可避性
- .NET Framework 4.6.2+ では tier2 Library / tier1 Library の直接組込は不可
- `Grpc.Net.Client` を .NET Framework で動かす場合、HTTP/2 を WinHttpHandler 経由で扱う必要があり、client streaming や一部 TLS 設定 / プロキシ周りに制約がある
- Library が抽象する Messaging / Workflow / Relational Store 等を素直に載せる土台として安定しない
- レガシー形態は Companion + Gateway を経由するか、tier2 Library を直接呼ぶかの差にとどまる（業務コードの語彙は同一）

## Companion 役割（[client 設計方針](../09_client設計方針/04_認証コンテキスト伝播方針.md) と双方向 lock）

### 役割 A: Observability / 認証コンテキスト伝播
- 標準形態: .NET Framework 4.6.2+ 向けに OpenTelemetry .NET Auto-Instrumentation を採用。CLR Profiler によるアタッチ方式で、アプリケーションのソースコード変更を不要とする
- 補助形態: Auto-Instrumentation 非対応環境（4.6.1 以前）向けに NuGet 参照型の Companion を提供
- tenant / subject attribute の注入: `k1s0.Companion.NetFx.OTelExt`（splunk-otel-dotnet fork）が CLR Profiler の IL rewrite 経由で登録する k1s0 processor で、HttpClient / HttpWebRequest / WebClient / WCF の各 stack で Activity に対し JWT claim → SetTag 実施
- 詳細は [Companion OTel 拡張](../../04_詳細設計/03_クロスカッティング適合仕様/11_companion_otel_extension.md) を参照

### 役割 B: Transport Negotiation Runtime
- tier1 Server 系 Transport Adapter Layer と対をなすクライアント実装
- 提供 API: bidi RPC に対しては言語ごとに統一インタフェース（C# 例: `IBidiChannel<TReq, TResp>`）
- 同梱 adapter: `sse_paired`（既定、HTTP/1.1 + SSE）、`long_poll`、`webhook`、`websocket`、`messaging_bridge`
- レガシー .NET Framework は Connect-RPC bidi 採用しない（WinHttpHandler の HTTP/2 制約により）

## v1_legacy_http11 専用 listener
- wire 出口は **役割 H2-A' で常設される `v1_legacy_http11` 専用 listener（別ポート 8443-legacy、TLS + HTTP/1.1、ALPN h2 offer なし）**
- Companion 起動時に WinHttpHandler の ALPN h2 probe を行い:
  - 成功 → 業務 listener（h2/h3）を選択（昇格して `v1_full_native_with_companion` 相当の経路で運用）
  - 失敗 → 当該 legacy listener に固定
- L7 firewall で当該ポートに到達できるのは `capability_matrix.lock.yaml` で `v1_legacy_http11` cell に entry を持つ tenant のみ
- 業務 SLO は当該 listener に対しては別系統で管理（`v1_legacy_http11_request_latency_p99_ms` を独立 SLO）

## prerequisite check
Companion 配布時の prerequisite:
- .NET Framework 4.6.2+ かつ Windows 10 1607+ / Server 2016+ かつ WinHttpHandler 必須
- Backstage onboarding workflow の prerequisite step として OS 版数 check を H2 reachability check と並列必須化

## per-tab subscription 上限の縮退
- `v1_legacy_http11` の per-tab subscription 上限は 6（HTTP/1.1 の物理上限）
- 機能は同等だが connection 数縛りで縮退
- 該当環境の tier3 利用者は `capability_matrix.lock.yaml` で明示 entry、SLO が degrade する旨を機械可読化

## レガシー形態の業務コード制約
- tier3 業務コードからは Companion runtime + tier2 Service の proto 派生 SDK のみが見える
- OSS クライアントへの直接アクセスは禁止（[tier3 強制機構](../../04_詳細設計/02_強制機構/03_tier3強制機構.md) 層 1）

## 長期収斂（v2 で `v1_legacy_http11` listener 廃止候補）
- 業界 OS の WinHTTP h2 普及率 trigger で 08_OSS ライフサイクル適合仕様 の `deprecation_clock` に乗る
- レガシー言語そのものが対象 fleet から退役した時点で Companion 自体の保守も終了

## 採用しない設計
- レガシー .NET Framework での Connect-RPC bidi（WinHttpHandler HTTP/2 制約）
- Library 直接組込（tier2 Service を Companion + Gateway 経由）
- OSS クライアント直接 import
- per-tab 16 subscription（HTTP/1.1 物理上限 6）
- prerequisite check の skip（Backstage onboarding workflow で必須）
