# tier3 開発者体験

## 一文方針
- tier3 業務エンジニア（ジュニア級）の inner loop は Backstage Software Template + Tilt + Companion local mock + dev container + Pact contract test + Playwright E2E + axe-core + Lighthouse CI で構成。13 層強制機構を template 自動組込で業務 UI 開発に集中できる。

## Backstage Software Template（tier3 リポジトリ生成）
- 13 層強制機構 + contract test + a11y + Web Vitals 自動組込
- 言語別 lint（cargo-deny / Roslyn analyzer / depguard / ESLint）の設定同梱
- CSP / セキュリティヘッダ宣言の template
- CI workflow（GitHub Actions）の template

## inner loop
- **Tilt**: K8s ローカル開発、業務 UI の hot-reload
- **Companion local mock**: tier1 / tier2 に接続せず tier3 を local 開発
- **dev container**: VS Code Remote Containers / GitHub Codespaces

## inner loop time budget
- proto 変更 → buf generate: ≤ 10s
- tier3 業務 UI build: ≤ 30s
- Pact contract test: ≤ 5min
- Playwright E2E（Browser SPA）: ≤ 5min
- axe-core / Lighthouse CI: ≤ 3min

## ジュニア級 onboarding
- 1 day onboarding（Backstage Software Template + dev container）
- 業務エンジニアは業務 UI 実装に集中、強制機構は template 自動組込
- onboarding tutorial（業務 UI 開発の最小サンプル）

### OnboardingTutorial 仕様（初回ログイン後の 3 ステップガイダンス）

初回ログイン後に表示される 3 ステップのインタラクティブガイダンスを以下に定める。

**Step 1: 環境確認**
- dev container（VS Code Remote Containers または GitHub Codespaces）の起動確認
- `pnpm install` + `pnpm build` が成功することを確認
- Companion local mock との接続確認（tier1 / tier2 に接続せず tier3 をローカル動作させる）

**Step 2: 最小業務 UI サンプルの起動**
- Backstage Software Template で生成された最小サンプルリポジトリを `git clone`
- `tilt up` で K8s ローカル hot-reload 環境を起動
- サンプルの CRUD フォーム（業務 entity 一覧 / 作成 / 更新）が動作することを確認

**Step 3: 強制機構の green 確認**
- `pnpm lint`（ESLint 13 層 deny list）が green であることを確認
- `pnpm test`（Pact contract test + axe-core a11y）が green であることを確認
- Lighthouse CI スコア（LCP / INP / CLS）が閾値内であることを確認

OnboardingTutorial は Backstage TechDocs plugin で提供し、MkDocs Material でレンダリングする。利用例コードは CI で「テスト済みコード」として検査する。

## ChatOps
- Mattermost slash command で tier3 業務 UI のデプロイ / preview env 起動 / Playwright E2E 起動
- 全操作を audit emit

### Mattermost slash command 仕様

tier3 業務 UI の ChatOps 操作に使用する Mattermost slash command を以下に定める。

**`/k1s0-deploy`**
- 書式: `/k1s0-deploy <service> <env> [--image <tag>]`
- 動作: 指定 tier3 サービスを指定環境（`staging` / `production`）にデプロイする
- 前提条件: Cosign 署名済み OCI image tag が内部 Harbor に存在すること
- 成功時: デプロイ完了通知をスレッドに返信し、`client.deploy.event` を audit emit
- 失敗時: エラー詳細（CI fail / image not found / policy violation）をスレッドに返信し、audit emit

**`/k1s0-status`**
- 書式: `/k1s0-status <service> [<env>]`
- 動作: 指定 tier3 サービスの現在のデプロイ状態を返す（running pod 数 / image tag / 最終デプロイ日時）
- env 省略時: staging / production 両環境の状態を返す
- 認証: Mattermost ユーザーの Keycloak subject と紐付けて操作ログを記録

**`/k1s0-rollback`**
- 書式: `/k1s0-rollback <service> <env> [--to <tag>]`
- 動作: 指定 tier3 サービスを前回デプロイ（または `--to` で指定した image tag）にロールバックする
- `--to` 省略時: 直前の green デプロイ image tag に戻す
- 成功時: ロールバック完了通知をスレッドに返信し、`client.rollback.event` を audit emit
- 操作には `v1_operator` 以上の auth_class が必要（junior engineer は `/k1s0-deploy` へのアクセス権に制限）

**共通規約**:
- 全 slash command は audit emit 必須（`purpose='chatops'`、実行ユーザーの Keycloak subject を `actor_id` に記録）
- dry-run モード（`--dry-run` フラグ）は staging 環境でのみ有効
- `production` 環境への `/k1s0-deploy` / `/k1s0-rollback` は 2 名の承認（approval workflow）を必須とする
