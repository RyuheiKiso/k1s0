# tier3 権限 UI 制御

## 一文方針
- 認可結果は tier2 が一次情報として保持し、tier3 は反映するだけで独自 cache を持たない。UI 制御は activate / deactivate / 表示 / 非表示の 4 種、認可判定そのものは tier2 / tier1 が行う。`AuthorizationDenied` の client-side cache は CI 物理拒否（[tier3 強制機構](../../04_詳細設計/02_強制機構/03_tier3強制機構.md) 層 4）。

## 4 種 UI 制御

### activate / deactivate
- 認可ありの action button: activate
- 認可なしの action button: deactivate（disabled、grayed out）
- tooltip で「権限が不足しています」を表示

### 表示 / 非表示
- 認可ありの section / row: 表示
- 認可なしの section / row: 非表示（DOM に出力しない）
- 中間状態（partial 認可）は表示 + 一部 disable

## 認可情報取得
- tier1 / tier2 から認可結果を fetch（capability descriptor）
- 認可結果は memory only（client-side cache 禁止）
- session 単位で一度取得、再取得は tenant_switch / actor_switch / step_up 後

## step_up 連動
- 認可なし action button を click → step_up flow trigger
- step_up 成功後に action 実行可能
- step_up_proven_at 有効期間内のみ高リスク access

## emergency override 連動
- `purpose='emergency'` で取得された `v1_emergency_step_up` 中は通常認可を超える action が許容
- UI に emergency badge 表示
- 全 emergency action は audit emit（強制）

## tier3 拡張点
- 業界固有 / テナント固有の認可ルール表示は tier3 override 可能
- 基本認可ロジックは tier2 ABAC policy 経由

## 採用しない設計
- 認可結果の client-side cache（localStorage / IndexedDB / cookie）
- tier3 で独自に認可判定
- 認可なし action button の hide のみ（必ず deactivate + tooltip も検討）
- step_up なしの高リスク action
