# tier3 認証認可マルチテナント

## 一文方針
- tier3 は Keycloak OIDC + BFF auth-edge を経由して認証し、access_token を一切 client-side に保管しない。tenant_id は AuthContext から取得し form / URL での受付を物理拒否する。認可結果は tier2 が一次情報として保持し、tier3 は反映するだけで独自 cache を持たない。

## 認証経路（OIDC + BFF）
- Authentication: Keycloak OIDC（[認証適合仕様](../../04_詳細設計/01_適合仕様/04_認証適合仕様.md) `v1_human_session`）
- BFF auth-edge を経由: 1 tier3 ごとに 1 BFF Service を tier1 cluster 上に配置
- DNS layout:
  - `auth.<tier3>.<tenant>.<root_domain>` → BFF
  - `app.<tier3>.<tenant>.<root_domain>` → SPA（CDN 静的）
- cookie scope: `Domain=<tier3>.<tenant>.<root_domain>`（tier3 間の cookie 漏洩を構造的に遮断）

詳細は [BFF auth-edge](../../04_詳細設計/03_クロスカッティング適合仕様/06_BFF_auth_edge.md) を参照。

## access_token 取扱
- access_token を window.\* / localStorage / IndexedDB / sessionStorage / memory / Service Worker のいずれにも置かない
- SPA 経由で BFF API に問合せても access_token は返らない（BFF は `/whoami` / `/session` などで claims subset と expiry のみ返す）
- SDK 公開 API として `getAccessToken()` 不在、CI で `forbidden_export_symbols.lock.yaml` の access_token 列を全 SDK に対して検査

## refresh_token rotation（silent renew 代替）
- BFF が access_token expiry を監視、サーバ間通信で refresh_token を回す
- SPA は何も知らない（fetch 失敗時の暗黙再試行ですら BFF 内で透過完了）
- 「iframe + prompt=none」を採用しない（Safari ITP / Firefox ETP / Chrome の third-party cookie 既定ブロック下で IdP cookie が抑止されるため）

## OIDC back-channel logout
- Keycloak から POST /logout（OIDC Back-Channel Logout 1.0）を受信できる HTTP listener を BFF が常時 expose
- logout を受けたら該当 session を Valkey から即時削除し、全 SPA タブに WebSocket / SSE で broadcast
- SPA 側は受信して即座に画面遷移

## CSRF / CORS 規律
- SPA → BFF の全 mutation request に CSRF token 必須（Double-Submit Cookie pattern + Origin/Referer 二重検査）
- SameSite=Lax 固定（OIDC redirect 戻りで Strict cookie が落ちる根拠）
- CORS は Origin allowlist を tier3 manifest から導出、wildcard 禁止、preflight cache 5 min 上限

## tenant_id 取得経路
- tenant_id は Authorization context（OIDC token claim `tid`）から取得
- form / URL / クエリパラメータで tenant_id を受け付ける経路を CI で禁止（[tier3 強制機構](../../04_詳細設計/02_強制機構/03_tier3強制機構.md) 層 3）
- 成りすまし可能な API を tier3 公開に置かない

## tenant switch / actor switch
- 明示 API（`switchTenant()` / `switchActor()`）として提供
- 内部で 4 layer storage を全 purge + 新 tenant_id / actor_id で再 init を強制（[client 認証コンテキスト伝播方針](../09_client設計方針/04_認証コンテキスト伝播方針.md)）

## 認可 UI 制御
- 認可結果は tier2 が一次情報として保持
- tier3 はそれを反映するだけ（活性 / 非活性 / 表示 / 非表示）
- localStorage / IndexedDB / cookie への認可結果保存を禁止（[tier3 強制機構](../../04_詳細設計/02_強制機構/03_tier3強制機構.md) 層 4）
- service worker の cache strategy に認可エンドポイントが含まれていないことを CI で検査

## step_up（high_risk action 直前）
- 高リスク action 直前に WebAuthn / FIDO2 / TOTP で再認証
- step_up_proven_at の有効期間内のみ高リスク access が通る
- tier2 ABAC policy の `context.action_class` と連動

## emergency override / break-glass
- `purpose='emergency'` で取得された `v1_emergency_step_up` auth_class
- always step_up: 取得時に必ず WebAuthn 等で再認証 + 理由文記入
- audit_event に強制 emit、postmortem PR 起票必須

## Tauri sidecar PSK 露出禁止
- sidecar が device adapter 認証に使う per-tenant PSK は OS keystore（DPAPI / Keychain / Secret Service）から取得
- SPA / SDK / window.\* / localStorage / memory のいずれにも一切渡さない
- SDK 公開 API として `getSidecarPsk()` / `getSidecarToken()` 等は提供しない
- これにより XSS による PSK 漏洩経路がゼロ化

## 採用しない設計
- access_token の SPA storage / window.* / cookie 平文保管
- iframe + prompt=none による silent renew
- form / URL / クエリパラメータでの tenant_id 受付
- 認可結果の client-side cache
- SameSite=Strict（OIDC redirect で cookie 落ち）
- CSP の wildcard CORS Origin
- ROPC（Resource Owner Password Credentials）
