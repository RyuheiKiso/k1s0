# tier1 言語スタック

## 一文方針
- Server 系は Rust 単一深耕（Operator / Controller のみ Go の controller-runtime / kubebuilder 生態系都合で許容）。Library は Rust / C# (.NET 8+) / Go / TypeScript の 4 言語に絞り、.NET Framework は Companion で代替する。

## Server 系
- 主要言語: Rust
- 例外: Kubernetes Operator / Controller は controller-runtime / kubebuilder の生態系都合で Go を許容

## tier2 / tier3 への配布用 Library
- 対応言語: Rust、C#（.NET 8+）、Go、TypeScript
- tier2 / tier3 のユーザー（業務）に適する言語で開発できるよう Library でサポート
- .NET Framework（4.6.2 / 4.7.2 / 4.8 等）は本 Library の対応言語に含めない

### .NET Framework を Library 対応外とする理由
- `Grpc.Net.Client` を .NET Framework で動かす場合、HTTP/2 を `WinHttpHandler` 経由で扱う必要があり、client streaming や一部 TLS 設定 / プロキシ周りに制約がある。Library が抽象する Messaging / Workflow / Relational Store 等を素直に載せる土台として安定しない
- Library 非対応経路は「ビジネス API は Gateway 経由（HTTP/1.1 + JSON, External Proto 由来）」「観測可能性 / 認証コンテキスト伝播 / Transport Negotiation は Companion（役割 A / 役割 B の二役割）」で代替する枠を既に持っている

### 将来判断
- 将来的に .NET Framework での gRPC 周辺事情が変わった場合も、Library 対応に組み入れるかどうかは「Library が抽象する全カテゴリを素直に載せられるか」を基準に再判断
- Gateway + Companion で足りているうちは Library 対応に追加しない

## 言語選定の根拠（共通）
- Rust: Server 系の主要言語。memory safety、async runtime（tokio）、強い型システム、Kani による formal verification との相性
- C# (.NET 8+): 業務エンジニアの母集団 + .NET エコシステムの厚み + LTS の予見可能性
- Go: Operator / Controller 専用。controller-runtime / kubebuilder の standard
- TypeScript: Browser SPA / Node.js / Tauri 双方の射程をカバー

## 採用しない言語
- .NET Framework（4.6.2+）: Library 対応外（Companion で代替）
- Java: tier2 / tier3 業務コード側 で Java 21 LTS は 12_client/04_採用 OSS の SDK ランタイムとして使用するが、tier1 Library の対象言語ではない（v2 候補）
- Python / Ruby: SDK ランタイム（client 軸）として使用するが、tier1 Library 対応言語ではない
- Scala: formal 軸（Stainless）の入力言語として使用するが、tier1 Library 対応言語ではない
- C / C++: formal 軸（CBMC）の検査対象として使用するが、tier1 Server 系 / Library 対応言語ではない（kernel / eBPF / HSM driver / PTP daemon 等の infra 側のみ）
