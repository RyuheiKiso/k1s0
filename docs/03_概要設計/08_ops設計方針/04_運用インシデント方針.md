# ops 運用インシデント方針

## 一文方針
- 運用 incident（SLO 違反 / capacity 違反 / change 起因 failure / dependency outage / drill failure 等の non-security incident）の lifecycle は `incident_lifecycle.lock.yaml` に build artifact として固定し、5 phase（detect / triage / mitigate / resolve / postmortem）全てに物理 action 経路と SLA を必須化、phase 不通過の incident は CI で覆面検出 + admission block する。

## 至高路線における立ち位置
- 文章 only の incident lifecycle 禁止
- postmortem skip 経路禁止、72h SLA + 14 日 merged SLA、違反は service deploy block
- severity の手動 override 禁止
- mitigation の手動 default 禁止、auto rollback が default
- 商用 incident management SaaS（PagerDuty / Opsgenie / Squadcast 等の有償 SLA）採用しない

## incident class（5 class、operational signal 別）

| class | 発火条件 |
|---|---|
| `v1_slo_breach` | 13 SLO の error budget burn rate ≥ 6x（fast or slow window）|
| `v1_capacity_breach` | per_tenant_volume / cluster headroom / partition capacity の hard threshold 違反 |
| `v1_change_induced` | deploy / migration / canary / topology change 直後の SLO 急変 |
| `v1_dependency_outage` | 上位 / 下位 service / 外部 SaaS / IDP / DNS の unavailability |
| `v1_drill_failure` | chaos drill / restore drill / red team drill で想定外 failure mode に到達 |

- security incident（threat detect 由来）は [security インシデント対応方針](../07_security設計方針/07_インシデント対応方針.md) が primary、ops は triage 後 operational impact phase の loop entry のみを bridge で受ける

## incident lifecycle（5 phase、SLA 付）

### phase 1: detect
- alert 発火 → 自製 escalation engine page → primary on-call ack
- SLA: page → ack ≤ 5 分（severity_freeze 時 ≤ 3 分）
- 物理発火: Alertmanager → 自製 escalation engine webhook（Tekton Triggers）
- artifact: `alert_event` row in ClickHouse

### phase 2: triage
- on-call が ack 後 30 分以内に incident class 確定 + Mattermost incident channel 起票 + IR ticket 作成
- SLA: ack → triage 完了 ≤ 30 分
- 物理発火: Mattermost slash command → incident.io OSS API → GitHub Issue
- artifact: `incident_event` row（incident_id / class / severity / impacted_slo / impacted_tenant / suspected_cause）

### phase 3: mitigate
- 即時対処（auto rollback / manual rollback / throttle / freeze / runbook 起動）
- SLA: triage → mitigation 開始 ≤ 5 分（severity freeze 時）、≤ 15 分（severity page 時）
- 物理発火: Argo Rollouts auto rollback / Tekton Pipeline runbook / Kyverno freeze policy / break-glass token

### phase 4: resolve
- SLO budget 復活 / capacity 平常化 / customer impact 終了の確認 → incident close
- SLA: detect → resolve total（MTTR）SLO 別 target `v1_mttr_slo_p95`:
    - `v1_slo_breach` ≤ 2h
    - `v1_capacity_breach` ≤ 1h
    - `v1_change_induced` ≤ 30min auto rollback
    - `v1_dependency_outage` ≤ 4h
    - `v1_drill_failure` ≤ 1h

### phase 5: postmortem
- resolve 後 72h 以内に postmortem PR 起票必須、merged まで関連 namespace の deploy が Kyverno で物理 block
- SLA: resolve → postmortem PR open ≤ 72h、open → merged ≤ 14 日
- 物理発火: [ポストモーテム方針](05_ポストモーテム方針.md) と双方向 lock

## incident command roles（4 役割）
- **incident commander（IC）**: on-call primary が default、複雑化時 ops lead が引継、decision authority、外部 communication 統制
- **communications lead（CL）**: Mattermost incident channel + status page の更新を統一、30 分毎の status update 必須
- **subject matter expert（SME）**: 該当 service / 軸の domain expert（rotation 階層 3）、技術的 mitigation の意思決定支援
- **scribe**: timeline 記録（actions / decisions / hypotheses）、postmortem の primary author 候補

- severity = freeze / security_bridge は 4 役割全員必須、page 級 incident は IC + scribe 最低 2 名必須、notify 級 ticket は IC のみで close 可能

## communication channel（separation of concerns）

### public（社内）channel
- `#ops-incident-<service>`（Mattermost）: team 内技術詳細の流通 channel
- `#ops-status-page`（Mattermost）: customer 影響のある incident のみ status update

### 機密 channel
- `#ops-incident-confidential`（Mattermost）: PII / security adjacency / legal sensitive な incident の内部 communication

### audit_event
- 全 channel の activity log は ClickHouse audit subject に shipping、retention は preservation_class 別に最低 7 年

## severity matrix（impact × urgency）

### impact 軸（5 段階）
- `v1_individual_user`: 単一 user の操作失敗
- `v1_tenant_partial`: 単一 tenant の partial functionality loss
- `v1_tenant_full`: 単一 tenant の full outage
- `v1_multi_tenant`: 複数 tenant の全 partial 以上
- `v1_global`: 全 tenant outage / data loss

### urgency 軸（3 段階）
- `v1_high`: 即時対応必須（SLO breach phase 4 以上）
- `v1_medium`: 1h 以内対応（phase 3 SLO breach）
- `v1_low`: next-business-day 対応（informational ticket）

- severity = (impact × urgency) で算出、severity 表は `incident_severity_matrix.lock.yaml` に build artifact 化、手書き severity 上書きは禁止

## incident.io OSS の役割
- incident.io OSS（minimal 経路）or GitHub Issue を primary IR ticket として固定
- 商用 incident.io 本体の SLA / on-call 機能は採用しない
- 全 incident は incident_id を必須化、Mattermost channel 名 / PR タイトル / postmortem に bind

## post-incident invariant
- active incident（status != resolved）が存在する間、関連 namespace への自動 deploy は Argo CD sync wave で delay
- postmortem PR 未 open（phase 4 resolved → 72h 経過）: Kyverno が関連 service の image deploy を block
- postmortem PR open / unmerged 状態が 14 日以上: service 全 deploy block

## recurrence detection
- incident.io OSS の similar_incident query で過去 30 日の同 incident_class 発生回数を集計
- 3 回以上は recurrent として escalate（quarterly review 必須 + action item elevated priority）
- recurrent incident の root cause が同一の場合は action item の implementation status を ship blocker として bind

## 強制機構との bind
- 本方針は [ops 強制機構](../../04_詳細設計/02_強制機構/07_ops強制機構.md) の以下経路で物理 enforce される:
    - 層 B: Conftest による lifecycle phase coverage / SLA within check
    - 層 D: Kyverno `block-on-active-incident` `block-on-postmortem-overdue` admission policy
    - 層 E: incident_history.lock.yaml の cosign signed retention

## 採用しない方針
- 文章 only の incident lifecycle: 禁止
- postmortem skip 経路: 禁止
- severity の手動 override: 禁止
- mitigation の手動 default: 禁止、auto rollback が default
- communication channel の単一化: 禁止
- 商用 incident management SaaS: 採用しない
- recurrence の文章 only 集計: 禁止
- incident close を SLO 復活前に行う: 禁止
