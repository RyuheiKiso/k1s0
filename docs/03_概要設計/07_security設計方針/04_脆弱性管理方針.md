# security 脆弱性管理方針

## 一文方針
- 脆弱性（CVE / GHSA / RUSTSEC / GO-yyyy / 自社発見）は Trivy + Grype + 言語別 audit + Semgrep + IaC scan の 5 経路で完全列挙し、severity 別の patch SLO（critical 72h / high 7 日 / medium 30 日 / low 90 日）を SLO 軸（13）と connect、SLO 違反時は本番 deploy を admission block で物理拒否する。

## 至高路線における立ち位置
- 商用 vuln DB（Snyk / Black Duck）採用しない、OSS DB（Trivy / Grype / OSV / GHSA / NVD）で完結
- 「次の sprint で patch」を理由に SLO を緩めることを禁止、SLO は 13 で固定
- 単一 scanner 依存禁止、Trivy + Grype の cross-check 必須
- critical CVE の active ignore 禁止、必ず mitigation pointer を threat_model.lock.yaml に登録（active mitigate）か patch 完了

## 5 検知経路

### 経路 1: image vuln scan
- primary: Trivy（CI build 時 + Harbor scan-on-push + 日次再 scan）
- cross-check: Grype（同 image / 同 SBOM）
- target: image base layer / OS package / language stdlib

#### severity escalation 規律（10_security/04 と双方向 lock）
- 両 scanner が同 severity 一致: 当該 severity の policy をそのまま適用（Critical 一致 → admission block）
- severity 不一致: `max(severity_trivy, severity_grype)` に escalate して当該 severity の policy を適用、ticket 自動起票
- 一方のみ Critical: High 扱いで ticket 起票（admission block しない、両者 Critical 一致時のみ block）
- 両者 Critical 一致時のみ admission block
- 不一致は本来の vuln DB / matcher 実装差で常時発生するため、規律としては「false negative を二重化で潰す + false positive で本番停止しない」を基本姿勢

### 経路 2: language dep audit
- Rust: cargo-audit（cargo deny advisory も併用）
- Go: govulncheck
- Node: pnpm audit（npm audit / yarn audit は使用しない、pnpm 一本）
- Python（補助スクリプト）: pip-audit

### 経路 3: SAST
- Semgrep（言語横断 OSS rules + 自社 ruleset、ruleset は build artifact）
- 言語別: cargo clippy / golangci-lint

### 経路 4: IaC scan
- Trivy IaC（OpenTofu / Helm / Kustomize / Dockerfile）
- Checkov（cross-check）

### 経路 5: 自社発見 / PenTest / red-team
- 年次外部 PenTest 必須（v1）
- 四半期 internal red-team 演習
- 発見は CVE 風 ID で自社 catalog（vulns/ 配下）に登録、Trivy ignore list と統合管理

## severity / patch SLO

### severity 判定（CVSS v3.1 + EPSS）
- critical: CVSS ≥ 9.0 OR EPSS ≥ 0.5 + CVSS ≥ 7.0
- high: CVSS ≥ 7.0
- medium: CVSS ≥ 4.0
- low: CVSS < 4.0

### patch SLO（13_SLO適合仕様 と connect）
| severity | discover → fix merged → deploy 完了 |
|---|---|
| critical | ≤ 72h |
| high | ≤ 7 日 |
| medium | ≤ 30 日 |
| low | ≤ 90 日 |

- SLO 違反は `error_budget.lock.yaml` 消費、budget 0 は本番 deploy admission block

## patch lifecycle
- **検知（自動）**: Renovate / Dependabot 風の自動 PR 起票
- **仮締め経路**: CVE が image base layer の場合は image rebuild、language dep の場合は cargo update / go get / pnpm update
- **本締め経路**: CVE 修正版に向けた upstream PR、tier1/14 OSS lifecycle の primary OSS は自社 fork も pair_target として保持
- **例外（仮締め不可能）**: mitigating control（Kyverno rule / Falco rule / network policy）で active mitigate する経路を `threat_model.lock.yaml` に登録、SLO 違反は error_budget で表現

## Trivy ignore list の規律
- 全 ignore は build artifact（`vulns/ignore.lock.yaml`）として管理、手書き `.trivyignore` 禁止
- ignore entry は `(CVE_ID, image_pattern, expires_at, reason, mitigation_pointer)` を必須化、`expires_at` 超過は CI fail
- ignore reason = `"false_positive"` は upstream 報告 PR 必須
- ignore reason = `"wont_fix_with_mitigation"` は mitigation pointer 必須（threat_model.lock.yaml に bind）

## admission block の経路
- `block-on-critical-cve-overdue`: critical CVE が 72h 超過で patch 未完了の場合、本番 cluster への新規 deploy を block
- `block-on-high-cve-overdue`: high CVE が 7 日超過で block
- `block-on-cve-budget-exhausted`: `error_budget.lock.yaml` の `cve_open_critical_count` が target 超過で block
- `block-unsigned-image`: cosign verify 失敗の image deploy を block
- `block-image-without-sbom`: SBOM 添付なし image deploy を block

## SBOM の運用
- 全 image build で Syft が SBOM 生成（SPDX + CycloneDX 両 format）、cosign で sign + Harbor に attach
- Trivy / Grype は SBOM 入力で再 scan（image なしでも SBOM のみで CVE 検出）
- SBOM は audit_event subject にも emit、過去 image の CVE 影響範囲を ClickHouse query で再評価可能
- SBOM lifecycle の retention / 監査 は [build_provenance 適合仕様](../../04_詳細設計/01_適合仕様/16_build_provenance適合仕様.md) の Build artifact retention / 監査 lifecycle（hot Harbor 90 日 / cold Ceph RGW 7 年 / audit_event CDC 永続）に責務移譲

## 採用しない方針
- 商用 vuln DB（Snyk / Black Duck）: 採用しない
- 「次の sprint で patch」を理由に SLO を緩める: 禁止
- critical CVE の active ignore: 禁止
- 単一 scanner 依存: Trivy 単独運用は禁止、Grype cross-check 必須
- source repo に CVE detail を含む security advisory を publish しない: CVE detail は GHSA / 内部 audit log のみで管理
- 未 scan image の本番 deploy: admission block で物理禁止

## 強制機構との bind
- 本方針は [security 強制機構](../../04_詳細設計/02_強制機構/06_security強制機構.md) の以下経路で物理 enforce される:
    - 層 B: Conftest による Trivy ignore list の expires_at 全 entry 検証
    - 層 D: Kyverno `block-on-cve-overdue` `block-on-trivy-grype-mismatch` admission policy
    - 層 E: cosign signed SBOM の cryptographic verification
