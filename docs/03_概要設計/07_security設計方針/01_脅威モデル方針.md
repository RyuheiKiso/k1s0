# security 脅威モデル方針

## 一文方針
- 脅威モデルは `threat_model.lock.yaml` に build artifact として固定し、actor / capability / surface / asset / mitigation の 5 軸 cross-product で完全列挙、各 cell に必ず物理 mitigation pointer を持つ。文章 only の脅威記述は CI fail。

## 至高路線における立ち位置
- 「現実には起こりにくいから登録しない」「mitigation が高コストだから緩める」判断は採らない。重みは weight で表現するが、登録は省略しない。
- ad-hoc な脅威 brainstorm のみは禁止、catalog は機械可読 lock で固定、PR 経由でのみ entry 増減。
- mitigation の優先度は文章ではなく weight（low / mid / high の三値 enum）で表現、CI で機械検証。

## 5 軸の class 列挙

### actor 軸（5 class）
| class | 説明 |
|---|---|
| `v1_external_unauth` | 未認証外部攻撃者 |
| `v1_external_auth` | 認証済み外部 actor（tenant 内 / 別 tenant 越境）|
| `v1_insider_application` | tier1 / tier2 / tier3 application identity の compromise |
| `v1_insider_operator` | cluster operator / SRE 権限 identity の compromise |
| `v1_supply_chain` | build / image / dep 経路からの compromise |

### capability 軸（5 class、actor とは独立）
- `v1_read`: 機密情報を読む
- `v1_write`: 書き換える / 仕込む
- `v1_delete`: 消す / 失効させる
- `v1_dos`: 可用性を奪う
- `v1_lateral`: 別 tenant / 別軸へ越境する

### surface 軸（5 class、actor が触れる外面）
- `v1_north_south`: tier1 RPC / Server 系 ingress
- `v1_east_west`: cluster 内 service ↔ service
- `v1_control_plane`: Argo CD / etcd / Kyverno / External Secrets / OpenBao API
- `v1_persistence`: DB / topic / object store の物理 store 直接アクセス
- `v1_supply_chain_surface`: CI runner / Harbor / Tekton / source repo

### asset 軸（5 class、被害対象）
- `v1_pii`: tier2/22 で分類された PII / sensitive
- `v1_business_data`: 業務 entity（非 PII）
- `v1_audit_log`: audit_event subject
- `v1_credential`: authn token / secret / KEK / DEK
- `v1_availability`: 可用性そのもの（SLO 違反）

### mitigation 軸（5 class、物理機構の class）
- `v1_authn_authz`: 認証 / 認可 token / OIDC / RLS POLICY
- `v1_crypto`: rest 暗号化 / transit 暗号化 / 鍵階層
- `v1_isolation`: tenant_id / RLS FORCE / network policy / namespace
- `v1_admission_block`: Kyverno admission policy / schema check / sqlx prepare
- `v1_audit_detect`: audit_event / Falco / Tetragon / k8s audit

## threat catalog の構造（threat_model.lock.yaml）
- 1 threat = 1 row、key = (actor, capability, surface, asset)。mitigation は複数を列挙可能（必須 1 以上）。
- 全 5⁴ = 625 cell の組合せうち、論理的に成立しない組合せ（例: external_unauth × control_plane）は `explicit_unreachable=true` で marking。残り全 cell に mitigation 1 以上を必須化、空欄は CI fail。

### mitigation pointer の物理形式
| kind | ref 形式 |
|---|---|
| `kyverno_policy` | `<policy_name>` |
| `db_engine` | `<option>=<value>` |
| `rls_policy` | `<table>.<policy>` |
| `cosign_verify` | `<image_pattern>` |
| `oss_runtime` | `falco-rule:<rule_id>` |
| `schema_rule` | `apicurio:<subject>:<rule>` |
| `encryption` | `tier1/11:<key_class>` |
| `admission_audit` | `<audit_subject>` |

- 文章 only mitigation（kind: textual）は禁止、CI fail。
- 例外: actor 教育 / IR playbook reference のみ kind: runbook で limited-allow（cap 5% 以下、超過は CI fail）。

## STRIDE / LINDDUN との関係
- STRIDE（Spoofing / Tampering / Repudiation / Information disclosure / Denial of service / Elevation of privilege）は capability 軸の cross-cut tag として markup、独立軸とはしない（重複を避けるため）。
- LINDDUN（Linkability / Identifiability / Non-repudiation / Detectability / Disclosure of information / Unawareness / Non-compliance）は asset = v1_pii の sub-class として markup、PII 専用脅威を網羅する。
- 両 framework は coverage check の補助 lens として CI が使用、catalog の primary key にはならない。

## weight / 優先度
- 各 threat に `likelihood` ∈ {low, mid, high} と `impact` ∈ {low, mid, high} を attribute として宣言。
- weight = likelihood × impact。
- weight に応じた SLO budget consumption を 13 SLO の `error_budget.lock.yaml` に bind。
- high × high の threat detect 時は admission block + on-call page。
- weight が low × low でも mitigation 登録は省略しない。

## 同型構造（13 軸との整合）
- 単一の真 3 yaml:
    - `formal_classes.yaml`（threat_class 5 actor）→ ※ formal 軸の formal_classes.yaml とは別物、本軸は `classes.yaml` と命名する場合あり
    - `threat_model.lock.yaml`（build artifact、catalog 物理化）
    - `mitigation_bindings.lock.yaml`（build artifact、mitigation pointer ⇔ 各軸 spec の cross-axis assertion）
- 5 層 defense-in-depth: 脅威 catalog は層 D / E に必ず物理 mitigation を持つ（層 A / B / C は augment）
- CI 不変条件: catalog の `coverage_full` / `mitigation_physical` / `no_textual_only` 等を CI で物理確認

## 採用しない方針
- ad-hoc な脅威 brainstorm のみ: catalog は機械可読 lock で固定、PR 経由でのみ entry 増減
- 「現実的に低 impact だから登録しない」: 登録省略は coverage gap として CI fail
- mitigation の優先度を文章で表現: weight は数値で表現、CI で機械検証
- actor 軸を「内部 / 外部」の 2 値のみに縮約: 5 class を保持

## 強制機構との bind
- 本方針は [security 強制機構](../../04_詳細設計/02_強制機構/06_security強制機構.md) の以下経路で物理 enforce される:
    - 層 A: jsonschema / CUE による threat_model.lock.yaml schema 検証
    - 層 B: Conftest による全 cell mitigation pointer 存在 check
    - 層 D: Kyverno admission policy（cell 別 mitigation 経路の物理機構）
    - 層 E: cosign signed snapshot publish + Ceph RGW Object Lock retention
