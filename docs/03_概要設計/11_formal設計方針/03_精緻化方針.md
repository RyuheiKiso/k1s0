# formal 精緻化方針（v1_refinement_proof）

## 一文方針
- v1_refinement_proof は、各軸で「上位の抽象 spec が下位の実装 spec を refine する」ことを TLA+ refinement mapping または Stainless refinement type で machine-checkable に証明する proof_class であり、上位 spec の safety / liveness が下位実装に必ず保存されることを 19 軸 N pair（spec ↔ implementation の pair）に対し物理 enforce する。

## 至高路線における立ち位置
- 「informal な意味の refinement」（文章で「実装は spec に従う」のみ）を禁止する。machine-checkable mapping 必須。
- linearizability の証明は refinement mapping 経由のみ採用、happens-before 順序関係は v1_temporal_safety_proof 側で別 obligation。

## 担当 proof_class メタデータ

| 項目 | 値 |
|---|---|
| 意味論 | 上位 spec S_high と下位 spec S_low の間に refinement mapping `f: states(S_low) → states(S_high)` が存在し、S_low の任意の execution が `f` を通して S_high の execution に mapped される |
| artifact | TLA+ refinement spec（S_high ↔ S_low の instance + WITH 句）+ Apalache refinement check log / Stainless refinement type proof certificate |
| cadence_class | v1_per_pair_change_or_biweekly |
| cadence_days | 14 |
| artifact_class | v1_refinement_certificate |
| orchestrator_preference | tlaplus_apalache_pipeline / stainless_dafny_pipeline |
| coverage_weight | 1.3 |
| primary defense_layers | tlaplus_apalache_pipeline / stainless_dafny_pipeline / proof_gate_kyverno |
| active cell 数 (v1 cap) | N pair = 各軸の (spec, implementation) pair 数（軸ごとに 1〜3 pair）、合計 約 35 cell |

## refinement の意味論
- **simulation**: S_low の任意の transition が S_high の transition に mapped される（forward simulation）
- **bisimulation**: 双方向に mapping、S_high の transition も S_low に mapped される
- **refinement mapping**: 状態空間の部分 mapping、変数の対応関係を `WITH` 句で陽に書く
- **linearizability**: concurrent object spec が sequential spec を refine することを refinement mapping で表現
- **data refinement**: 抽象データ型の concrete 表現が抽象 spec を refine

## 各軸の代表 refinement pair

### 08 migration
- `PairDualWriteLinearizable`: dual-write 期間中の concurrent S_low が sequential append-only S_high を refine（linearizability theorem）
- `Pair4PhaseRefinement`: 4 phase の implementation spec が phase sequence の抽象 spec を refine

### 11 key
- `PairRotationProtocolRefinement`: rotation implementation spec が KEK rotation 抽象 spec を refine
- `PairShamirReconstructionRefinement`: threshold signature reconstruction が algebraic spec を refine（Lean 補助）

### 12 schema
- `PairSchemaForwardRefinement`: N+1 schema が N schema を refine（forward compatibility 形式の refinement、補助で N schema → N+1 schema の backward）
- `PairBufBreakingRefinement`: buf-breaking decision が schema-evolution rule の refinement

### client15 SDK distribution
- 5 distribution_class 各 1 pair: full_native / legacy_dotnet / browser_spa / tauri_native / thin_business_api
- 各 pair は SDK adapter implementation が proto spec を refine、Stainless / Dafny の refinement type で証明

### security17 build_provenance
- `PairSLSAChainRefinement`: SLSA L3+ chain implementation が SLSA spec を refine
- `PairAttestationDAGRefinement`: attestation graph implementation が DAG spec を refine

### infra16 clock
- `PairHLCRefinement`: HLC implementation spec が Lamport clock + wall_clock combine の抽象 spec を refine（Lean / TLA+ co-proof）

### test15 verification
- `PairCoverageMatrixRefinement`: 実 generator output が `coverage_matrix.lock.yaml` schema spec を refine

### 07 transport
- `PairBidiProtocolRefinement`: bidi protocol implementation が abstract bidi spec を refine

### infra01 topology
- `PairFailoverRefinement`: multi-zone failover implementation が consensus protocol 抽象 spec を refine

### data01 preservation
- `PairBackupRestoreRefinement`: backup-restore implementation が lossless transfer spec を refine

### 32 data-tenant
- `PairRLSRefinement`: RLS query rewriter implementation が tenant-isolation 抽象 spec を refine（information flow lattice の refinement）

### 39 client

- `PairRunbookRefinement`: 5 signal_class の runbook implementation が abstract incident response spec を refine

- `PairProofMatrixRefinement`: `proof_matrix.lock.yaml` の generator output が axis spec の `formal_obligations` 段落の宣言的真の refinement

## workflow
- **specify**: 軸 spec の `formal_obligations` 段落で refinement obligation を `(S_high, S_low, mapping_sketch)` の triple で宣言
- **model**: TLA+ で `S_high.tla` / `S_low.tla` を separate に書き、`Refinement.tla` で `S_low_INSTANCE WITH ...` で refinement mapping を結ぶ。または Stainless で refinement type で書く。
- **prove**: Apalache で `S_low.Spec => S_high.Spec` を invariant として model check、または Stainless で refinement type が型検査を通る
- **review**: refinement mapping の妥当性 review、過剰に粗い mapping は accepted_with_assumption に downgrade
- **archive**: refinement certificate を `proof_status.lock.yaml` に fingerprint

## refinement と test 軸の bind
- test/15 の v1_property_axiom（property-based test）の対応 cell: refinement proof が verified された pair では、property test の seed pool が refinement mapping の instantiation として自動生成される（Hypothesis / fast-check / proptest の generator が refinement mapping 経由で trace を生成）。
- drift: refinement proof が unverified の状態で property test を回す場合、test 軸 cell は v1_baseline_green ではなく v1_drill_red_handled として handling artifact pointer 必須。

## 採用しない設計
- 「informal な意味の refinement」（文章で「実装は spec に従う」のみ）は禁止。
- refinement mapping を proof tool 横断で行う（TLA+ で書いた spec を Stainless で refine など）: 採用しない。1 pair につき 1 tool（TLA+ 同士または Stainless 同士）に限定し、cross-tool refinement は v2 拡張で別途検討。
- linearizability の証明を refinement mapping ではなく happens-before 順序関係で書く形: 本軸では refinement mapping 経由のみ採用、happens-before は v1_temporal_safety_proof 側で別 obligation。

## 強制機構との bind
- 本方針は [formal 強制機構](../../04_詳細設計/02_強制機構/10_formal強制機構.md) の以下経路で物理 enforce される:
    - 層 D: Kyverno `require-proof-cell-verified` admission policy
    - 層 E: cosign signed refinement certificate
    - 層 F: Apalache refinement check / Stainless refinement type 自体

## CI 不変条件（v1_refinement_proof 担当部分）
- 整合 1: `proof_inventory.lock.yaml` の全 v1_refinement_proof entry が pair_id + S_high_pointer + S_low_pointer + mapping_sketch + statement_hash 完備
- 整合 2: 全 v1_refinement_proof cell の last_verified_at が cadence_days=14 以内
- 整合 3: `counter_example.lock.yaml` の v1_refinement_proof entry が close_due_at 以内に closure
- 整合 4: refinement mapping の 1 pair につき 1 tool（tool 横断 refinement なし）
- 整合 5: generator output と手書き drift = 0
