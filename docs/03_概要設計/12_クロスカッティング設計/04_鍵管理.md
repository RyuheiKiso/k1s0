# 鍵管理

## 一文方針
- KeyHandle 抽象 + 5 key_class × 5 dimension（purpose / rotation_cadence / scope / backend / destruction_method）の bundle + KEK Shamir 分散保管（M-of-N、N=5 / M=3）+ envelope encryption + crypto-shred の 4 機構で全鍵管理を物理 enforce。tier2 / tier3 / Companion から「生 key bytes」「Secret 文字列」を扱う経路は提供しない。

## 5 key_class（[鍵管理適合仕様](../../04_詳細設計/01_適合仕様/05_鍵管理適合仕様.md)）
- `v1_data_dek`: data_encryption / 90 日 / per_tenant / software_kms_wrapped / crypto_shred
- `v1_data_kek`: kek_wrapping / 1 年 / per_tenant_or_platform / hsm_pkcs11_shamir_distributed / hsm_zeroize_all_shares
- `v1_token_signing`: signing_jwt / 90 日 / platform / hsm_pkcs11 / jwks_revoke
- `v1_audit_root_signing`: signing_audit_root / 1 年 / per_tenant / hsm_pkcs11 / external_notary_attest
- `v1_mtls_workload`: mtls_identity / 6 時間 / per_workload / spire / spire_revoke

## KeyHandle 抽象
- tier1 Library が公開する KeyHandle は opaque newtype
- 生 key bytes を保持しない、鍵操作は handle に対する method として公開（encrypt / decrypt / sign / verify）
- 4 言語（Rust / C# / Go / TypeScript）で同型 API

## envelope encryption（pii_segregated）
- column 暗号は DEK で行い、DEK は KEK で wrap して at-rest に置く
- KEK rotation は DEK の re-wrap で済み、data 再暗号化を強制しない
- DEK rotation は background batch で data 再暗号化
- AAD は `aggregate_id+version` で固定、自製 crypto 禁止

## crypto-shred（GDPR 物理削除）
- KEK destroy で当該 tenant の wrapped DEK を不可逆に失効
- KEK 物理復元不能（HSM zeroize + 全 shamir share zeroize）
- GDPR right to be forgotten の物理 enforce 経路

## KEK Shamir 分散保管（[KEK Shamir 分散](../../04_詳細設計/03_クロスカッティング適合仕様/02_KEK_shamir_distribution.md)）
- M-of-N parameter: N=5（share total、region 数）/ M=3（share threshold）
- 2 region 完全断まで KEK 物理復元継続可能
- 3 region 以上の同時断は意図的に「鍵を取れない」状態
- share custodian role: 各 region 2 名（break-glass two-person rule）
- 復元 ceremony: air-gapped host + Backstage Software Template
- vendor diversity: 各 region 別 vendor（Thales / YubiHSM / Entrust / Nitrokey 等、FIPS 140-3 Level 3）

## destruction proof は外部公証で物理担保
- audit hash chain root は外部公証（RFC 3161 trusted timestamp + Sigstore transparency log）で attest
- tier1 内で改竄しても外部攻撃面で検出可能

## 5 層 defense-in-depth
- 層 A: KeyHandle 必須引数化、生 key bytes 不可視
- 層 B: lint / 公開 API snapshot
- 層 C: cross-class integration test（rotation / destruction）
- 層 D: HSM PKCS#11 + SPIRE + OpenBao audit log
- 層 E: 外部公証 attestation

## 採用しない設計
- 生 key bytes の SDK 公開 API 露出
- Secret 文字列の業務コード直接保持
- key_class dimension override
- HSM 単一 region 配置（KEK shamir M-of-N 必須）
- 自製 crypto
- HashiCorp Vault（OpenBao MPL 2.0 のみ）
