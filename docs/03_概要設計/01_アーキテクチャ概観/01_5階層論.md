# 5 階層論

## 一文方針
- 本企画は infra / data / tier1 / tier2 / tier3 の 5 階層に分割し、各階層の責務 / 隠蔽境界 / 依存方向を物理 enforcement で固定する。tier3 から下位階層への直接アクセスはすべて構造で塞ぎ、業務エンジニアが業務不変条件を踏み抜けない構造を提供する。

## 5 階層の責務

### infra 階層
- Kubernetes cluster / OSS / ミドルウェア / 物理 storage / network
- 5 topology_class（v1_single_zone / v1_multi_zone_per_cluster / v1_multi_cluster_active_active / v1_multi_region_active_passive / v1_multi_region_active_active）
- 5 clock_integrity_class（v1_intra_rack_ptp / v1_cross_dc_ntp_smeared / v1_application_hlc_only / v1_browser_client_skew_tolerant / v1_air_gapped_legacy）
- 5 failover orchestrator
- HLC（Hybrid Logical Clock）runtime
- 25+ Kyverno admission policy

### data 階層
- PostgreSQL（CloudNativePG）/ Kafka（Strimzi）/ ClickHouse / Valkey / Apicurio Registry / Rook+Ceph / Longhorn
- 5 preservation_class（v1_local_only / v1_zone_replicated / v1_cluster_replicated / v1_cross_region_replicated / v1_global_replicated）
- 5 enforcement orchestrator（postgres_wal_streaming / kafka_replication_quorum / clickhouse_keeper_replication / ceph_multi_site / object_lock_compliance）
- 4 種 restore_drill
- expand-contract pattern migration

### tier1 階層
- Server 系（動かす成果物、Rust 主体、Operator のみ Go）
- Library（配る成果物、4 言語: Rust / C# / Go / TypeScript）
- Companion（レガシー言語向け、.NET Framework）
- 17 機能カテゴリ × 3 抽象化レベル（L3 / L2\* / L1+）
- 9 適合仕様（Bidi / 移行 Pair / 観測 / 認証 / 鍵管理 / スキーマ進化 / SLO / OSS lifecycle / テナント容量）

### tier2 階層
- ドメイン業務共通化
- 業界 pack 並立（業界横断 / 業界共通 / 業界固有 / テナント固有 の 4 抽象化レベル）
- bounded context（製造業: FA / 調達 / 検査 + 共通モジュール）
- atomic 三表書込（State change + Outbox + Audit）
- BusinessConflict subtype 4 種（stale_write / lost_update / supersede / concurrent_edit）

### tier3 階層
- 個別業務 UI（Web SPA / デスクトップ exe / レガシー .NET Framework 4.6.2+）
- 4 layer client state（Server Truth / Optimistic Local / Pending Queue / Draft）
- 業務シナリオ所有 / フォームレイアウト / 業務エラー UX / 帳票レイアウト

## 隠蔽境界
- **infra → tier1**: tier1 が infra 隠蔽 facade
- **tier1 → tier2**: tier2 は tier1 Library 経由でのみ infra にアクセス
- **tier2 → tier3**: tier3 は tier2 経由でのみ業務資産にアクセス
- **tier3 → ユーザ**: tier3 が業務語彙でユーザに表現

## 依存方向
- 単方向: tier3 → tier2 → tier1 → data / infra
- 逆方向の依存（tier1 → tier3 等）は CI で物理拒否
- 同階層内の cross-axis 参照は extension point + Domain Event 経由

## 階層別エンジニア
- infra / data / tier1 / formal / security / ops: シニア級
- tier2: 中堅級（業界 pack ごとに増減）
- tier3: ジュニア級（業務 UI に集中、強制機構で業務不変条件を構造保護）

## 階層を跨ぐ cross-cutting 機構
- BFF auth-edge（tier3 ↔ tier1）
- Tauri Companion sidecar（tier3 デスクトップ ↔ OS device）
- Companion OTel 拡張（tier3 レガシー ↔ tier1 観測）
- HTTP/2 enforcement（tier1 Server 系 ↔ tier3 client）
- KEK Shamir 分散（tier1 鍵管理 ↔ infra cluster）
- Apicurio GitOps SoT（tier1 schema ↔ data Apicurio Registry）
- protoc-gen-go FSM（tier2 / client 4 言語等価強度）
- SLO protection layers（tier2 service ↔ tier1 SLO ↔ ops）

詳細は [12_クロスカッティング設計](../12_クロスカッティング設計/README.md) を参照。

## 採用しない設計
- 5 階層を跨ぐ直接アクセス（必ず階層境界経由）
- 隠蔽境界の bypass（強制機構で物理拒否）
- 同階層内の bounded context 跨ぎ直接参照（Domain Event 経由）
